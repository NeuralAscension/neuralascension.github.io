Traps that have cost real time#

Things in this codebase that are not wrong, but are not what they look like. Every entry below was found the expensive way — by an agent or a person writing correct-looking code, watching it fail strangely, and spending real time on it. They are recorded here rather than in a chat log because chat logs do not survive, do not move between machines, and do not reach the next agent.

If you lose time to something not on this list, add it. That is the point of the file.

Scope note: this is the "you will misread this" list. Repo rules live in CLAUDE.md, how to test lives in Testing.md, and the map of everything is README.md.

1. Names that mean something other than what they say#

It reads as It actually is What it costs
SP::Npx::kHeadstageSamplingRate 100 000 — hardware TICKS per second, not the 30 kHz sample rate. The probe streams 30 kHz samples carrying 100 kHz timestamps. Every derived timestamp comes out 3.33× wrong. A brand-new test reported a perfectly correct processor as broken, twice, before the constant was checked.
waitForAvailable(consumerId, 1, available) The 1 is a timeout in milliseconds, not "wait for at least 1 sample". Read as a sample count, the whole consumer loop appears to be doing something it is not.
getDataByName(name) Get-or-CREATE. It lazily constructs any registered type, so it is non-null for almost any name, on almost any config. Using it as an existence test made an NP1-only branch always win and its NP2 counterpart unreachable dead code — a ripple detector bound to a band nothing ever wrote, reporting itself perfectly healthy at zero samples. Ask with hasData(), which does not create.
a profile's inputs: / recordings: band list A statement of what the profile WANTS, not of what the probe streams. Which bands exist is a property of the probe: a 1.0 gives hardware ap + lfp, a 2.0 gives one raw. Because the names resolve through getDataByName() (row above), naming the wrong generation's band does not fail -- it manufactures an empty buffer, draws 384 flat traces, and records a real .bin and sidecar containing nothing. A recording that looks like it worked. Since 2026-08-26 the display binds from hasData() and the recorder skips absent bands, so a profile can serve either probe; see SourceSelection.md.
getProcessorByName(name) One instance per name, for the life of the process. "The object exists" says nothing about the profile in front of you. A 1.0 profile selected after a 2.0 one gets the same proc.lfp back, still configured for a source that is gone. Announcing state off object existence is what put a green LFP button on a profile with no derived bands. Key off isProvisioned().
getConfigValue<T>() Integer-only. It goes through ryml's read_dec, so it cannot read a YAML true or a float. Silent zero/false. Parse bools and floats as strings (v == "true" \|\| v == "1" \|\| ..., std::stof) — the low_latency: and enabled: keys both do this, and so must yours.
a config's filename A config's identity is its internal top-level name: field. The directory is scanned. Renaming a file needs no code change; renaming the name: breaks every reference.
the recording sidecar's channels (and the comments describing it) Read-out CHANNEL indices, not electrode numbers. activeRecordIndices is passed straight into the data block as a direct index (Npx.cpp:92-96). The comments in RecordProcessor, and Recording.md, said ELECTRODE numbers. On NP1 bank 0 electrode == channel, so it read correctly for years. On NP2 the map is a silicon permutation and the two differ for nearly every column -- a mislabelled recording that looks perfect: real data, right length, clean sync, and only the depth is a lie. The sidecar now states columns.index_space and carries the electrode each column actually read.
the OneBox ADC's channel numbers BNC/SDR inputs, not probe read-out channels -- even though OneBoxSource publishes the ADC band from the same metadata snapshot as the probe, with the probe's electrode table sitting right there. Attaching the probe geometry to an ADC column puts a specific, plausible and completely wrong electrode number on it. BandScale::usesProbeChannelMap is the flag; the same reasoning is already why RecordProcessor refuses to apply a probe channel override to interp.npx.adc.
Pa_GetDefaultOutputDevice() A concrete endpoint, not "wherever the system default points". On this rig it returned index 1, a specific monitor's HDMI audio. A stream opened on it keeps playing there forever, so changing the Windows output device does nothing. The device that follows the default is a different one — index 0, Microsoft Sound Mapper - Output. See SpikeAudio.md §7.
np_unmapBS(x) Takes a SLOT, while its partner is np_mapBS(serial, slot). They read as a symmetric pair and are not one. Passing the serial indexes a slot table with 25420802 and faults 0xC0000005 after np_closeBS has already returned ok -- which looks exactly like a driver bug in a vendor API that already has one (#54).
waveplayer_arm() "routes DAC0 to the SMA output" It routes to DAC0, and DAC0 reaches breakout BNC IO0. The SMA half did not happen on this hardware. Measured: a 1 Hz +/-2 V square moved IO0 from sd 0.0002 to 1.9894 V while IO9 (the SMA) stayed at 4.963 V, unchanged. Four days of #49 were spent looking at the SMA.
getProcessorByName("proc.audio") != nullptr Lazily CREATES. True on every profile, including ones with no audio processor. An audio button on 1.0 sources controlling nothing. Ask IProcessor::isProvisioned().

2. Threads, and what is running when#

Processor threads do not start until Play. ProcessorManager::setupProcessors only constructs; startProcessors() runs on the play request. So at source-selection time every processor object exists, is configured, and is not running.

Consequences that have each caused a bug:

  • A QMetaObject::invokeMethod(..., Qt::QueuedConnection) issued at select time is not delivered until the thread's event loop runs — i.e. at Play. If you need state announced when the operator selects a source, call it directly (safe when the target only reads atomics and emits), which is what BandFilterProcessor::announceState() is for.
  • The long-running processor loops (BandFilterProcessor, RippleDetector) block their own event loop. They only service queued calls because they explicitly call QCoreApplication::processEvents() once per outer iteration. Delete that and every GUI command to them stops arriving.

A QTimer created on the wrong thread never fires, and says nothing. A timer belongs to the thread it was constructed on, so one created in a constructor that ran on the main thread will not tick for an object that has since been moved to a worker thread. Create per-thread timers inside a slot that already runs on that thread (slIpStartProcessor, slAwStartAudioStream), never in the constructor.

Destroying a running QThread is a FATAL abort, not an error you can catch — Qt calls qFatal, the process dies with 0xC0000409 (STATUS_STACK_BUFFER_OVERRUN), and CTest reports a crashed test with no output at all, so the assertion that actually failed is never printed. This has now bitten twice: once in AudioProcessor (a worker nothing ever joined, which killed the process during hardware teardown), and once in a test that ended without joining. In tests, use RAII teardown — QVERIFY returns from the function the moment it fails, so hand-written cleanup at the bottom is skipped exactly when a test is failing.

3. Ring buffers: the write slot is the COMMIT count#

Every consumer indexes the ring by its own count of committed samples — constDataAt(ind) is ind % capacity. So a producer's write slot must equal the number of samples it has committed, not the number it has seen.

BandFilterProcessor violated this by using one counter for both roles. It was invisible while bands ran from the first sample (the two are equal then), and became a real defect the moment bands started disabled and were switched on mid-stream: the read cursor advanced through the disabled stretch while the commit count did not, so the producer resumed writing at skipped % capacity while every consumer was still reading from committed % capacity.

Nothing throws. The band serves correct-looking numbers of the wrong age — up to a second of extra delay at 30 kHz, different every session, on a closed loop this repo defends in single milliseconds. Pinned by tests/test_bandfilterprocessor.cpp.

If you add a producer that can skip commits, it needs its own write counter. Say so in a comment, because the merged version looks tidier and someone will try to merge it back.

4. Testing#

  • QTRY_COMPARE(x, 0) is not "wait until drained". It is true the instant it is asked, so it returns immediately and proves nothing. If you need a processor to have consumed everything, wait for a positive condition, or qWait and then assert an exact count so an unfinished state fails loudly.
  • Qt Test stdout does not reach this harness. test_x.exe prints nothing you can capture and ctest --output-on-failure shows nothing either. Use Qt Test's own writer: test_x.exe -o results.txt,txt. Without this you are debugging a red suite blind.
  • A control that is disabled is not a control that is broken. Disconnect is disabled while streaming and the ripple Start is disabled with no channels — a test that clicks them and waits for something to happen will conclude the application is broken. Assert disabled instead, and drive the app into the state where the control is legal.
  • A test that asserts an ABSENCE needs a positive control. "No band buttons appear on a 1.0 probe" also passes if the source never loaded. Assert first that the 1.0 profile's own bands are on offer, then that the derived ones are not.
  • Prove a new test can fail. Inject the regression, watch it go red, revert. Every test in this tree has been through that, and two of them were found to be vacuous by doing it.
  • The GUI harness must disconnect before selecting. MainController::handleConnectRequest refuses a connect while a source is still selected, and refuses it quietly. It used to work by accident: the backend auto-quits ~2 s after its last WebSocket client leaves, so each test usually got a fresh one. When a test connected inside that window it reused a backend that still had a source, the select was dropped, and the test ran against the previous test's source — surfacing as a dozen unrelated failures about labels and units.
  • Configuring the ripple detector does not start it. Adding electrodes populates the dock and is enough for the sidecar to be written, so it looks like the detector is live — but the baseline estimation window does not begin until #rd-run is pressed. A test that set z = 0 and waited 90 s for a detection watched a detector reporting running: false, training.active: false and a null threshold for the entire wait, and blamed the feature.
  • Do not poll the cowsay for detections. #rd-cow is a status line: the next event overwrites it and lockout clears it, so a poll landing in a gap sees nothing and concludes the detector is dead. Wrap window.rippleModule.onDetected and count — a counter only goes up.
  • A recursive glob cannot see a file in the wrong place. glob(outdir + "/**/*") finds the sidecar whether it is inside the recording folder or above it, which is why the sidecar test passed for months while the file was one directory too high. If where a file lands is the property under test, assert the directory.

5. Windows, the shell, and the build#

  • The build needs vcvars64. A bare cmake --build … from a plain shell fails with Cannot open include file: 'assert.h' — which reads like a broken toolchain and is really a missing environment. Run it as cmd /c "\"…\VC\Auxiliary\Build\vcvars64.bat\" && cmake --build …".
  • QProcess::startDetached("cmd", {"/c", "<compound command>"}) silently does nothing. QProcess quotes the whole argument, so cmd receives nested quotes around a path with spaces and gives up — and startDetached still returns true. Write a script file and run that instead. (timeout also needs a console a detached process does not have; use ping -n.)
  • The Bash tool single-quote-wraps the command, so an apostrophe anywhere in a heredoc breaks it — including in prose inside a Python heredoc. Write the script to the scratchpad with the Write tool and run the file.
  • Never Get-Process chrome | Stop-Process. It closes the operator's real browser windows. Kill only the isolated debug-port profile you launched.
  • Never force-kill the backend with hardware open. The FT601 handle is released only on a clean exit; a kill costs a physical power-cycle. Shut down with the WebSocket quit command.

5a. Hardware, and telling it apart from your own bug#

A DAC channel drives nothing until its output is enabled. DAC_setVoltage() alone changes no voltage on the wire; DAC_enableOutput(ch, true) is what connects the driver. A correct WavePlayer with no enabled output produces exactly the silence you would expect from a broken one. This is the whole of issue #49.

The backend writes output.log to its WORKING DIRECTORY. Launch it with cwd=REPO and the log is REPO/output.log; the copy in build-*/bin/ is whatever an earlier session left. Check the mtime before you trust a log -- twenty minutes went into analysing a six-hour-old file and concluding the detector had bound to the wrong band. It had not.

rippleEnvelope is the detector's vital sign. No baselines and no envelopes means the detector is receiving no samples at all -- look at the source, not at the threshold. No baselines with envelopes means training is in progress or retrain() was never called. The two are indistinguishable from the outside and have nothing in common.

A wedged basestation announces itself. Two guards exist for this and both work:

source "source.npx.onebox" has not produced data in 3 s (stuck at 0 cycles)
np_arm(16) did not return within 3000 ms. Abandoning the call and continuing teardown
Virtual slot 16 was NOT released -- the box did not respond.

If you see either, stop debugging software. The cost of not noticing is hours spent proving your own correct code is correct.

A successful reconnect does NOT mean it recovered. Measured 2026-08-24: after this failure a control-plane probe (scan → map → open → close → unmap, no acquisition) came back completely clean, and I told the operator the box was fine. The next streaming attempt reproduced the fault exactly. The control plane and the data plane fail independently here — openBS succeeding says nothing about whether the box will deliver a single sample.

np_readPackets returns SUCCESS while delivering nothing. It reported code 0 on every call for three solid seconds and produced 0 packets. A return code is not liveness; only a packet count is. The codebase already says this twice (NpInterface.cpp:186, :439) because it cost a session on 2026-08-20, and it cost another on 2026-08-24.

The second np_arm() hangs when the data plane is dead. The first returns SUCCESS immediately. Since closeDataSource() opens with np_arm (close), a dead data plane surfaces as a teardown hang rather than as an acquisition error -- which points the reader at the shutdown code, where the bug is not. Bisect with a standalone program before suspecting teardown.

Sim is the control, and it is four minutes. Simulated NPX 2.0 Ripples trains three channels and produces ~19 detections in 50 s, reliably. Any "is the detector broken?" question is answered there first. That is how a hardware failure was separated from a same-evening code change, rather than by argument.

5b. A green suite is a statement about what it LINKS#

On 2026-08-24 the C++ suite reported 17/17 green while three real defects sat in the OneBox path. Not because the tests were weak, but because no test target linked a single line of OneBoxSource.cpp or NpInterface.cpp. Of everything under src/modules/neuropixels/, exactly one file was compiled into a test: NpxChannelMap.cpp, 36 lines of arithmetic.

So before trusting a green light, ask what it covers. grep spikespeak_test tests/CMakeLists.txt lists every production file any test links; anything absent from that list is untested regardless of how many suites pass.

And the defects that hide there share a signature. All three were of the form "every vendor call returns SUCCESS and nothing happens" -- a missing DAC_enableOutput, an unrouted acquisition trigger, an unbounded teardown call. None is observable from a return value, so no amount of value-checking would have found any of them. The observable is the sequence of calls, which is why tests/fake_neuropix_api.cpp exists. See Testing.md §4a.

5c. Measuring things on this rig#

Every entry below is a mistake made on 2026-08-25, each of which produced a confident wrong number before it was caught.

Two timings issued back-to-back are NOT independent. The detector fires the DAC and then the stim server. Reading detect_to_dac_us = 164 and detect_to_send_us = 172 as two independent costs, and concluding the ordering bias was 8 us, was wrong: they are sequential, so the second contains the first. Swapping the order with dac_trigger_order: stim_first gave detect_to_send_us = 6 us and detect_to_dac_us = 202 us -- the DAC call alone costs ~200 us of the detector thread, and the real ordering bias is 115 us, not 8. If two measurements share a thread, measure the swap; do not subtract.

A high percentile misses a short pulse. A 130 us stimulus pulse is about 4 samples at 30.3 kHz, so 1300 of them in a 695 s recording is 0.025% of the samples -- below even the 99.9th percentile. An edge detector thresholding at percentile(sig, 99.9) reported the stimulator's line as having NO swing at all. Use max() for pulse detection, with a debounce, and require a real swing (>1 V) rather than an adaptive fraction of whatever noise the channel has.

An adaptive threshold on a floating line detects noise. The same detector, using mean + max(0.25, half the excursion), reported ~1590 "rising edges" on two floating lines resting at 1.715 V, and auto-picked one of them as the stimulator. Floating inputs on this breakout sit at ~1.715 V and wander; anything that calls that an edge will find thousands.

rig.record(out_dir, name) writes into out_dir/name/, not out_dir. Globbing the parent finds nothing and fails as an IndexError far from the cause. And a second run into the same name adds a second timestamped sidecar beside the first -- sort by mtime, or you will silently analyse the old recording. Both happened; the second reported a 5 s smoke test's n=104 as though it were the 1000-detection run. Full layout in ClosedLoopDriving.md section 3a.

Existence is not visibility. The GUI docks (#obx-dock, the ripple dock) are built into the DOM at startup and merely hidden. A retry loop guarded on !!document.getElementById('obx-dock') exits immediately having clicked nothing, and the screenshot comes back with no panel in it -- twice, here. Test getComputedStyle(d).display !== 'none'. Same shape as the .active-view trap that live_view() already documents.

A fixed sleep after a layout change reads mid-reflow. An ad-hoc CDP probe that walked the column counts with time.sleep(2.2) between them, instead of Gui.settle_until_stable(), reported #main-container width 0 and column-header width 0 for every cell after the first four. That is indistinguishable from a page that has stopped laying out, and it was a probe reading a page that had not finished reflowing yet. The harness helpers (Gui.columns, Gui.width, Gui.settle_until_stable) exist for exactly this reason; a one-off script that hand-rolls its own clicks and sleeps inherits none of that discipline and will hand you garbage that reads as an application bug.

A control-plane probe is not a liveness test -- see section 5a. Restated here because it is the same error as all of the above: checking the thing that is easy to check instead of the thing you actually mean.

WebSocket command names are case-sensitive, and getting one wrong used to be silent. The chain matches on exact spelling: Disconnect takes a capital D, and its twelve neighbours are lowerCamel. On 2026-08-25 a script sending {"command":"disconnect"} failed to release the source for a whole four-cell hardware run; the backend then correctly refused each profile switch and logged exactly why, but the script never looked, and the files looked perfect afterwards.

Fixed 2026-08-28 (#64), so the shape of the failure has changed. An unmatched name now logs a warning and broadcasts a guiStatus error to every client, so a script that reads its socket is told. It also distinguishes a name nobody knows from a known name that arrived without its value — reporting the second as "unrecognized command" sent people hunting for a typo that did not exist. Disconnect no longer demands a value it never read. The same gap in the ripple chain is closed too, and that one was worse: it echoed full state after every action, so an unknown action came back with a plausible ACK rather than silence.

What is still true and worth keeping: prefer python/spikespeak_cli.py, which sends the right spellings, and output.log is where the backend's own account lives — it is a WIN32 binary, so nothing reaches the stdout you redirected. Covered by tests/gui/command_surface.py.

A held dashboard looks like a running suite, and a killed one loses its result. scripts/run_all_tests.py --hold keeps serving the progress page after the run finishes, so the process is still alive when the work is done -- twice on 2026-08-25 the operator asked why a completed suite was "still running". The trap underneath it is worse: Python buffers stdout when redirected, so killing the held process to move on discards everything it printed. Both output files came back 0 bytes and a ~20-minute suite result was simply gone.

That matters because the GUI suite is the gate on every push. A lost result is not an inconvenience, it is a blocked push -- and "the run completed" is not the claim you need. "It passed" is, and watching it finish is not evidence of it.

For anything automated:

python -u scripts/run_all_tests.py --no-browser --port 8765 > <scratchpad>/gate.log 2>&1

-u so the log is readable while it runs and survives an early exit, and no --hold so the process exits when the run does. Reserve --hold for a human watching the page, and stop it explicitly afterwards. Note also that the dashboard belongs to run_all_tests.py alone -- run_gui_tests.py serves no page, so offering someone a URL for that one is simply wrong.

5d. Enabling something is half a feature; disabling it is the other half#

BandFilterProcessor::setEnabledExternally(true, ...) had exactly ONE call site and setEnabledExternally(false, ...) had NONE. So RippleDetector::ensureInputBandEnabled() switched proc.lfp on -- correctly, a 2.0 probe has no hardware LFP band -- and nothing ever switched it back off. One ripple run left the LFP band filtering 384 channels for the rest of the session, with no consumer, and nothing in the GUI to say why it was on.

That is the "nothing runs that nobody asked for" rule in CLAUDE.md, broken by the feature that enforces the other half of it. Fixed 2026-08-25 with releaseInputBand(), and the same enable/release pair now exists for the audio monitor's proc.spike.

If you add an ensureXEnabled(), write releaseX() in the same commit, and give it the ownership rule both of these use: release only what you enabled. A band the operator switched on for themselves must survive the module that merely also wanted it.

And a feature that quietly does nothing is worse than one that fails. The audio monitor was silent because mListenChannel defaults to -1 and the sample loop takes a !valid branch, writing zeros -- no error, no warning, nothing in the panel. With the threshold at 0 and every other control correct, the only available conclusion was "the audio is broken". If a module cannot act without a choice nobody has made yet, either make the choice and announce it, or say out loud that it is waiting.

5e. The shape must not depend on the measurement#

Until 2026-08-25 the per-column control strip decided its own size twice, in two languages. Twelve @container tiers in toolbar.css picked one of three authored shapes for the band -- three rows, two rows, one row -- by column count and container width; updateStripMode() then measured the shape the tiers had just chosen and collapsed the strip if that did not fit.

At two columns in a 1080px window the circle closed on itself. The tier had already dropped the band to its two-row shape, so the fit test measured 274px, found it fitting in the 377px available, and did not collapse. The result was a two-row strip, which is the one shape nobody wants -- and no individual step in that loop is wrong. (The count half of the same rule, !vertical && nCols > 2, was wrong in the other direction: at three columns with the dock shut one row needs 448px and 477px was free, so it fit, and the rule collapsed every control behind a chip anyway.)

The band now has exactly one authored shape -- one row, five fixed slots, 108+80+64+84+80 + four 4px gaps + 7px padding a side + a 1px border = 448px -- and it collapses if and only if 448px does not fit beside the depth readout. Column count and orientation are no longer inputs. If you add a responsive tier to something a fit test measures, you have rebuilt this bug.

And measuring a COLLAPSED strip answers a different question. Collapsed, .column-controls is position:absolute and carries the narrow three-row reveal-overlay template, so its scrollWidth there is the overlay's width, not the in-flow band's -- read it in that state and the answer is "it fits", permanently. Drop strip-collapsed, read, restore, in the same frame, which is what ChartColumn.fitStrips() does. It also does it once per row, not once per column: each class flip is a size change the chart-area ResizeObserver picks up and re-enters on, and N of them per frame took the page down during development.

5f. requestAnimationFrame does not fire when nothing is being painted#

A layout decision deferred through rAF is a layout decision that may never happen. rAF runs only while the page is actually rendering. A minimised window, an occluded one, a background tab, or a browser driven over CDP with nothing on screen all suspend it indefinitely — the callback is not late, it is never called.

This cost a full GUI-suite red on 2026-08-26. live_view asserted that three columns in a 1080px window collapse their control strips, and they did not. The measurement was fine: probing at that exact moment gave need=446 / avail=197, and calling updateStripMode() by hand collapsed all three columns immediately. The instrumented counters told the real story —

resize: 2      the event fired, twice
raf:     0     the requestAnimationFrame callback ran zero times
fitRan:  0     so the fit never happened
err:  null     and nothing threw, because nothing ran

— and both existing paths into the fit (the chart-area ResizeObserver, and the one added while chasing this) deferred through rAF, so both were inert. The window resize handler now calls ChartColumn.fitStrips() directly, with a setTimeout(..., 0) backstop for a slow relayout; timers still fire when nothing is painted.

Note the failure mode is silent twice over: the rAF never runs, and the usual try { … } catch (e) {} around it means there is no error either. If a class is not being applied and nothing is in the console, count whether your callback ran at all before you debug what it does. Deferring draw() through rAF is still right — that is a paint, and it is correct for it to wait for one. Deferring a decision is not.

5g. Linux: three traps from the 2026-08-26 bring-up#

A container mutated while it is being iterated is the bug, even when the null check looks careful. CommandDispatcher::executeCallbacks did a range-for over mSubscriptions[commandId] and, for any subscriber whose QPointer had gone null, called removeSubscriber(...) — which erases from that same vector, and, once it empties, mSubscriptions.remove(commandId), destroying the container the loop is still walking. It reads as diligent lifetime hygiene. It is undefined behaviour, and it segfaulted the backend for real (four core dumps, always in BandFilterProcessor::slBpHandleCommand).

What made it expensive to find is when it fires. It needs a stale subscriber, so it needs a second source session in one backend process. Every GUI test but one starts clean and never sees it; band_dependency is the only one that runs after another session, so it was the only red test — and it passed when run alone, which is the most misleading signal available. If a test passes in isolation and fails in the suite, the state that matters lives in something shared, not in the test. Reap dead entries in one pass first, then iterate a copy.

On Linux the browser you launched is not the process you are holding. /usr/bin/brave-browser (and google-chrome, and chromium) are #!/bin/bash wrapper scripts that spawn the real binary as a child. subprocess.Popen therefore holds the wrapper's pid, and terminate() reaps only the wrapper — the real browser is orphaned, keeps its WebSocket to the backend open, and keeps rendering. The GUI suite left one live browser per test, ten by the end. start_new_session=True plus os.killpg fixes it; the group id is our own, so it can never reach the operator's browser.

That leak was also load-bearing by accident: the orphans held the backend's WebSocket open, which suppressed its 2 s "last client gone" auto-quit between tests. Expect fixing a leak to expose whatever the leak was silently propping up.

pkill -f <pattern> matches the shell that is running it. pkill -f spikespeak_guitest kills your own command — the pattern is in its command line — so the script dies mid-cleanup and you get a bare non-zero exit with no explanation. Twice. Match narrowly and signal pids:

PIDS=$(ps -eo pid,args | grep -F "user-data-dir=/tmp/spikespeak_guitest" | grep -v grep | awk '{print $1}')
kill -TERM $PIDS

And one that hid all of the above: scripts/run_gui_tests.py captured a failing test's stdout and stderr separately and reported only stdout, so the Python traceback went in the bin. A crashed backend and a genuine assertion failure both printed the same single line — [harness] reusing the backend on :1234. Folding stderr into stdout turned a day of guessing into one readable traceback. When a failure report is uninformative, suspect the reporter before the code.

5h. A WIN32 binary has no stdout, so redirecting it captures nothing#

add_executable(... WIN32 ...) in CMakeLists.txt makes SpikesPeak a GUI-subsystem binary on Windows. A GUI-subsystem process has no console and no inherited stdout or stderr, so this:

subprocess.Popen([... "spikespeak.py", "run", "--no-browser"], stdout=log_fh, stderr=subprocess.STDOUT)

captures exactly the two lines the Python launcher prints before it hands over, and nothing the application says. The file is 261 bytes whether the run went perfectly or the backend died on a missing Qt plugin.

That is not hypothetical: tests/gui/_harness.py opened _gui_backend.log specifically so that a failed startup would name its cause instead of "collapsing into the same 30-second wait", and on Windows that file was empty every time — the one platform the rig runs on. Fixed 2026-08-26 by reading both files.

The application's real log is output.log, written by the qInstallMessageHandler in main.cpp, in the process's working directory, rotated output.log → output.1.log → … → .5.log on each start. So:

  • Read output.log, not your redirect, when you want to know what the backend did.
  • It rotates on the NEXT start. If you run the backend twice in one script, the first run's log is now output.1.log. Copy it before starting run two, or you will read the wrong one and be very confused about why your assertion sees the previous configuration.

5i. The simulator uses the PROTOTYPE part id; the hardware reports the real one#

probeIdStr is a part-TYPE id, and the two sources do not agree on which one:

NP1.0 NP2.0 4-shank
simulated source "0" "24" (the NP2010 prototype)
real hardware "0" "2013" (the shipping NP2013 part)

ImroManager.js identified the probe by pattern-matching that string against "24", "21" and "NP2...". Sim matched. A real 2.0 probe matched nothing, so every check answered "not a Neuropixels probe" and, on the rig only:

  • the probe map went completely inert — no scroll, no click, no drag;
  • lvKind was never set, so the live view never built its depth ordering;
  • the Shank / Bank preset buttons stayed hidden;
  • record-channel selection treated the 2.0 as a 1.0.

The map kept drawing the whole time, because rendering is not gated on probe type. So it presented as "I cannot scroll the probe map" rather than as a dead editor, and the GUI suite was green throughout — no simulated fixture can reproduce a mismatch that only exists between sim and hardware.

The fix keys off probeType, the ProbeType enum the C++ itself branches on and already sends in getImroAsJson (NpInterface.hpp: 1 = NP1.0, 2 = 2.0 single-shank, 3 = 2.0 multishank), through a single probeGen() helper. tests/gui/probe_map.py pins the rule on synthetic payloads including {probeType: 3, probeIdStr: "2013"}, because that is the one case the simulator cannot present.

The general form: when a value has a "friendly" spelling and a true one, the simulator tends to carry the friendly spelling. Identify hardware by what the hardware layer decided, never by re-deriving it from a string — and when a check can only be wrong on real hardware, test the RULE on a synthetic input rather than trusting the fixture.

6. Saying what is true#

The recurring defect class in this application is announcing a REQUESTED state instead of a CONFIRMED one (issue #18, and it keeps coming back in new places):

  • The backend broadcast stateSource with the requested name before attempting the connect. A refused select therefore reported a switch that had not happened, while the previous source kept streaming — and a recording taken in that state would carry the wrong band.
  • handleTextCommand("play") returning true means the request was accepted, not that anything is acquiring. Announce from the acquisition-state change, not from the request.
  • Readiness signals must key off sender(): every RecordProcessor emits the label "recorder", so matching on the label makes one processor's readiness stand in for another's.

The rule, cheap to apply and expensive to skip: the GUI renders what the backend confirmed. If you are about to write frontend state from a click handler, stop and make the backend say it instead.
