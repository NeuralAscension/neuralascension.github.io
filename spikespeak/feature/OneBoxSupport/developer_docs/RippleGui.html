Ripple-detection GUI — design, WS contract, and integration plan#

The RippleDetection panel is a right-side dock column (≤ ¼ width, stretchable) that coexists with the Probe Map / Live Data views (a toolbar tab toggles the dock; it does not replace the main view). It drives proc.rippledetector and visualizes its per-channel state.

Scope — this doc is the GUI ↔ backend WS contract only. How to operate the dock (with annotated screenshots): ../user_docs/RippleDetection.md. The detection algorithm + per-probe data path: RippleDetection.md. This doc does not repeat either.

Status: BUILT + WIRED END-TO-END (2026-07-08). The frontend panel (webinterface/RippleModule.js) sends WS commands and renders live backend events; the backend RippleDetector emits rippleEnvelope/rippleTraining/ rippleBaseline/rippleDetected/rippleState, and applies frontend commands (start/pause/setChannels/setParam/ setZ/retrain/enable) at runtime (queued onto its worker thread, applied safely between loop iterations). Verified: a WS listener saw 649 envelope + 24 training + 2 baseline + 5 detection events over 26 s, and a runtime setChannels [5,15] was resolved + took effect live (detections then fired on [5,15]). The layout shrinks the main view (no overlap); two spinboxes added: quorum count + coincidence window (10 ms default, ±0.001). Start/Pause + Edit-lock verified headless (2026-07-08): Play auto-started (enabled=true, 3 channels trained), pause→enabled=false (0 detections while paused), setChannels[0,10,20,30] while paused merged to 4 channels, start→resume trained ONLY the new e30 (e0/e10/e20 kept their baselines), 7 detections total, no crash across the runtime channel-set mutations. Ctrl+drag channel selection is DONE: a shared RippleModule.beginElectrodeDrag custom-drag (works over the probe-map canvas AND the live-view DOM labels, unlike HTML5 DnD) — the probe view hooks it on Ctrl+mousedown via electrodeUnderCursor/np2ElectrodeUnderCursor (NP2 → global shank*1280+e); the live view hooks it on the electrode labels (Ctrl+mousedown, normal Ctrl-click select skipped). Verified headless: drop-on-dock → addElectrode (chip + per-channel column appear). The stim-server IP selector is wired too — setStimServer re-points StimulatorClient live (§2).

1. Layout (top → bottom, per the spec)#

  • Header: a single ▶ Start / ⏸ Pause button (consolidates the old Enable+Begin) + an ✎ Edit button. Semantics:
  • Start — begins the module: first-ever Start trains μ/σ from now, then detects; a Start after a Pause just resumes with the existing baselines (no retrain). Disabled with no channels selected.
  • Pause — stops detection + stimulation (envelopes keep streaming, so the panel stays live); baselines kept.
  • Edit — only enabled while paused; unlocks the config (channels + global params) for changes. While running, channels + global params are locked — EXCEPT the per-channel z-score, which stays editable live for real-time sensitivity tuning (setZ recomputes the threshold on the fly). Start re-locks the rest. (Backend is the source of truth: rippleState.enabled drives the button + lock.)
  • Row 1 — Channels: electrode chips (e50 → ch98 ✕). Editable when paused + Edit engaged. Add by left-drag an electrode from the Live Data / Probe view into the dropzone — hold Ctrl, OR just drag while the dock is open (body.ripple-open skips the Ctrl requirement) — one at a time, or type an electrode number (fallback). Removing a chip drops that channel. Adding a channel to an already-trained set trains only the new channel (kept channels keep their baselines) — see setChannels below.
  • Row 2 — Parameters (global, before the per-channel split; all seconds):
  • Parameter-estimation (training) time — line edit, validated. A Train / Retrain button reads Train until every channel is trained then Retrain (disabled with no channels, mid-train, or when not running); a progress bar + "time remaining" while training μ/σ.
  • Min time above threshold to report — line edit.
  • Lockout after detection / stimulation — spinbox, step 0.01.
  • Channels required (quorum) + Coincidence window.
  • Rows 2–3 — per-channel columns (one per selected channel): z-score spinbox (step 0.01, live-editable even while running), the threshold μ + zσ = value (Greek), a rolling envelope plot (last 500 ms, trimmed by timestamp) with the threshold as a dashed line; the column highlights for the lockout on a crossing. Status line: idle — press ▶ Start (added, not running) / training… / below threshold / ● RIPPLE.
  • Row 4 (no split): a cowsay "ripple detected" readout, a red stimulation LED lit on a confirmed fire, an enable stimulation master checkbox, a stim-server Ethernet IP selector, a clickable arm/disarm toggle (the small stim LED, see below), a ⚡ Test Fire button, the trigger selector (Pi / OneBox DAC0 / both) with its amp V box, and the four editable stim pulse fields + preview.

The numbers in the dock are NOT the defaults — and that distinction is this page's whole subject#

The values the panel shows before a rippleState arrives are JS placeholders in webinterface/RippleModule.js (DEFAULTS, plus two literals in the constructor). The values the detector actually starts with are the backend seeds in RippleDetector's member initializer list. They differ, and the backend wins the moment the socket connects:

control JS placeholder backend seed
Parameter-estimation (training) time 1200.000 s 10.0 s (mBaselineDurationSeconds)
per-channel z-score 3.00 5.0 (mZScoreThreshold)
Coincidence window 0.010 s 0.05 s (mCoincidenceWindowSeconds)
Channels required (quorum) 2 1 (mQuorumCount)
Min time above threshold 0.000 s 0.0 s — these two agree
Lockout after detection / stimulation 0.200 s 0.2 s — these two agree

An earlier version of this page listed the first three as the defaults. That is exactly the stale-default trap the RULE below exists to prevent, reproduced in the document that states the rule: a number that is real in one layer, wrong in the other, and indistinguishable on screen. If you need to know what the detector is running, read rippleState, not the panel and not this table.

2. Frontend → backend (WS JSON, sendCommand({command:"ripple", …}, 0x1000))#

action payload backend effect
start {} run the module: first-ever start trains from now + detects; a start after a pause resumes (baselines kept). Sets mEnabled=true, mTrainingOrigin if unset
pause {} stop detection + stimulation (envelopes still stream; baselines kept). Sets mEnabled=false
enable {enabled:bool} legacy bool toggle (maps to start/pause)
setChannels {electrodes:[int]} set detection electrodes (resolved via ChannelMapService). Merge / train-only-new: electrodes that persist keep their trained baseline + filter/lockout state; new electrodes get fresh untrained detectors; dropped electrodes are discarded
setParam {name, value:float} estimation_seconds / min_duration_seconds / lockout_seconds / coincidence_window_seconds / quorum_count
setZ {electrode:int, z:float} per-channel z-score threshold
retrain {} clear baselines and re-estimate μ/σ
setStimServer {ip:string, port?:int} set the StimulatorClient target. ip may itself carry host:port — and if it does, port is ignored; the separate field is read only when ip has no colon. Default 8888, and garbage after the colon falls back to it rather than failing
setStimParams {phase_us,gap_us,freq_hz,total_ms,amplitude_v} GUI-editable biphasic pulse-train params, applied to every fire (StimulatorClient::setStimParams, clamped to hardware ranges). amplitude_v is the OneBox DAC amplitude and means nothing on the Pi path (the AM 2300 is a constant-current stimulator), so the dock hides that box unless a DAC trigger is selected. Inputs fire on change, not input.
setDacTrigger {enabled:bool} fire the OneBox WavePlayer DAC as well as the stim server, from the same crossing. Re-resolves the OneBox source immediately; warns and no-ops on a profile that has none. The dock's trigger selector sends enabled: value !== "pi"
testFire {} manual single pulse: connect() (arm) + fire(), no detection needed (⚡ Test Fire button)
armStim / disarmStim {} arm / disarm the stim server (the clickable stim LED toggle, "connect/disconnect the Pi"). NOT routed through slApplyCommand — the WebSocketServer calls RippleDetector::setStimArmed(bool) directly on the main thread, which uses StimulatorClient::armFromAnyThread() / disarmFromAnyThread() (throwaway socket, status set under a lock) and broadcasts rippleStimStatus immediately. So it works even when NOT streaming (unlike the worker-thread commands).

3. Backend → frontend (WS JSON events, broadcastJson)#

event fields frontend render
rippleState {enabled, input, channels:[{electrode, channel, z, trained, mu?, sigma?, threshold?}], estimation_seconds, min_duration_seconds, lockout_seconds, quorum_count, coincidence_window_seconds, stim_server, stim_status, stim_enabled, stim_phase_us, stim_gap_us, stim_freq_hz, stim_total_ms} full panel sync (on connect / after a command)
rippleTraining {active:bool, percent:0..100, remaining_seconds} progress bar + label
rippleBaseline {electrode, mu, sigma, threshold} the μ + zσ = … per column
rippleEnvelope {ts, values:{electrode:envValue}} (throttled, ~30–60 Hz) append to each column's rolling plot
rippleDetected {ts, electrode(s), quorum:"k/N"} cowsay + LED + highlight the column(s) for the lockout

Two fields are worth calling out because a reader looking only at the panel would not guess they exist:

  • input — the registry name of the band the detector is actually bound to (data.npx.lfp on a 1.0, the derived data.lfp on a 2.0). BandModule keys off it to know whether switching the LFP band off would starve detection; see DerivedBands.md.
  • stim_enabled — the master gate (RippleDetector::setStimEnabled). It is sent explicitly rather than inferred from an empty stim_server, so a panel or a CLI can tell detection-only from stim-capable. While the gate is off, stim_status reports "disabled" rather than the client's real armed/disarmed state, because a plausible-looking "disarmed" for a client that physically cannot transmit is worse than no answer.

RULE: rippleState must carry EVERYTHING the dock displays (2026-07-20)#

rippleState is the only mechanism that keeps a browser panel in sync with a detector that was driven from somewhere else — the control CLI, ripple_tools/rig.py, or a second browser tab. Any value the panel renders but the snapshot omits will silently show a stale default while the backend runs something different.

This bit us during the NP1.0 regression: the whole 3-test run was driven over WS by rig.py, and the dock kept showing freq 100 Hz and z 3.00 while the detector was really firing at 1 Hz with z 2.50. The channel chips updated (they were in the snapshot); the numbers did not (they were not). See captured by CDP screenshot at the time (screenshots are transient — see the screenshot policy in README.md).

The fix made rippleStateJson() a member function of RippleDetector (it needs mDetectionParams and the StimulatorClient) reporting per-channel z / trained / mu / sigma / threshold plus the four stim pulse-train fields, and RippleModule.onState() applies them with the backend as the authority. Untrained channels send no mu/sigma/threshold at all so the panel renders -- rather than a stale number or a misleading 0.

When you add a control to the dock, add its value to rippleStateJson() in the same commit. Verify with ripple_tools/verify_sidecar_and_guisync.py, which sets values over WS only and then reads the rendered DOM back through CDP — never by clicking the control it is supposed to be testing. tests/gui/ripple_params.py is the gate version of the same idea: it asserts the backend's echo on a separate WebSocket connection, so frontend state alone cannot make it pass.

OPEN DEFECT — two controls violate this rule today (2026-08-31)#

The dock renders two stim controls whose values rippleStateJson() does not carry:

control frontend state in rippleState?
trigger selector — Pi / OneBox DAC0 (IO0) / both (#rd-stim-target) state.stimTarget, seeded 'pi' no — mDacTrigger is never serialized
amp V — the DAC amplitude (#rd-stim-amp) state.dacAmplitudeV, seeded 2.0 no — mDacAmplitudeV is never serialized

Both are settable (setDacTrigger, and amplitude_v on setStimParams) and both are applied. Neither is reported, so the state is three-way inconsistent: a detector driven from rig.py with dac_trigger on shows a dock reading "Pi → AM 2300", and a second browser tab shows the same. That is the identical failure mode as the 2026-07-20 regression above — a control that renders a stale default while the backend runs something else — and it is on the one path where the stale value means "you are not looking at the trigger that actually fired".

Recorded here rather than quietly fixed because it needs a backend change (.cpp) and this is a docs pass. The fix is two lines in rippleStateJson() plus two onState() branches; do it in the same commit as anything else that touches the trigger selector.

4. How it was wired (historical — SHIPPED 2026-07-08; do not implement)#

⚠️ This section is a record, not a plan. It used to be a five-step TODO written in the present tense ("today only prints the cowsay to stdout"), which stayed on the page for the better part of two months after the work shipped. A contributor could reasonably have followed it — and step 1 asked for four signals where the code deliberately has one. Everything below is already done.

The relay is one signal, RippleDetector::sigRippleEvent(QString json), carrying the whole event as JSON. Four typed signals would have meant four connections, four slots and four broadcast paths to keep in step for a payload the frontend re-parses anyway; the event's "event" field is what distinguishes rippleDetected from rippleBaseline from rippleTraining from rippleEnvelope, exactly as the §3 table says. If you are adding a new dock event, add a JSON shape, not a signal.

The rest, for orientation: the detector emits from doRippleDetectionLoop (detection at the fire() point, baseline where the threshold is computed, training progress from mCurrRawDataInd, envelope throttled to every Nth decimated sample); WebSocketServer relays it cross-thread with a queued connection, like the recorder-error relay; command:"ripple" frames are marshalled onto the detector's thread with QMetaObject::invokeMethod and applied between loop iterations — except armStim / disarmStim / setStimEnabled, which run on the main thread on purpose (see §2 and the arm/disarm section below). Ctrl+drag from the probe map and the live view is RippleModule.beginElectrodeDrag, a custom drag rather than HTML5 DnD because HTML5 DnD does not work over a canvas.

5. Notes#

  • The stim server "communicates via Ethernet" — the existing StimulatorClient (UDP to an IP:port) maps to the IP selector; enumerate local NICs backend-side for the dropdown later. Stim module reintegration is separate.
  • The detector is single-thread by design (see RippleDetectorThreading.md); the GUI does not change that.

Stim pulse preview (2026-07-14)#

Below the editable Stim pulse params (phase µs / gap µs / freq Hz / train ms) the ripple dock draws a live schematic on #rd-pulse-canvas (RippleModule._drawPulse()), redrawn on every edit: - top zone — one biphasic pulse, zoomed so the two phase lobes and the inter-phase gap are always visible and labeled; - bottom zone — the pulse train at real 1/freq spacing over the train window, with a 1/freq period marker and a <freq>Hz · train <ms> → <N> pulses summary.

So editing any value updates both the pulse shape (phase/gap widths) and the spacing/count (freq/train) immediately. Pure frontend — no rebuild and no copy step. src/main.cpp:58-62 serves webinterface/ off disk per request (the exe sits in <repo>/bin, so ../webinterface is the source directory), so editing webinterface/RippleModule.js and hard-reloading the browser is the whole loop. See RendererContract.md T-27 for the one caveat: the handler does not strip a query string, so a …js?flag=… URL 404s.

Clickable arm/disarm stim toggle (2026-07-16)#

The small stim-server LED in the Detection & stimulation card is a clickable toggle (#rd-stim-toggle, a pill wrapping the LED + status text + a ⏻ power icon) that arms/disarms the Pi — an intuitive "connect / disconnect from the Pi" control, so you don't have to tear the source down to stop stimulation.

  • NOT armed by default — arming is an explicit user action. This is the single most expensive misconception in this document's history: an earlier version claimed the detector auto-armed, and a 1000-detection OneBox run reached 944 detections with ZERO stim fires because the operator believed it. RippleDetector.cpp:188 says so in as many words — "NOT armed here either way: arming stays an explicit user action (the GUI stim LED)" — and WebSocketServer.cpp:249 records why the auto-arm was removed: selecting any source, even one whose connect then failed, put a datagram on the wire.

The gate and the arm are two different things and BOTH are required. setStimEnabled only permits datagrams to leave the host; the stimulator must ALSO be armed before a detection can trigger it. Scripted runs must call Rig.arm_stim() — record_ripples.py does, and prints the resulting stim status at the top of the run so the arming is visible. The backend logs the failure mode plainly when it happens: [RippleDetector] stimulation ENABLED -> "192.168.1.100:8888" (not armed; arm from the GUI stim LED)

  • (historical, no longer true) WebSocketServer::onSourceSelection then broadcasts the armed status so the pill shows green "armed" immediately on select (even before Play).
  • Click while armed → disarmStim → the Pi disarms and the pill goes gray. Detection keeps running, but a disarmed server ignores fire(), so no pulse goes out until you re-arm.
  • Click while disarmed → armStim → the Pi re-arms and the pill goes green.
  • The click is optimistic — the frontend flips the LED/label on every click (so rapid arm/disarm alternate correctly), and the backend broadcasts the real status right back to confirm.
  • Cowsay is short: "connected to stim server" / "disconnected from stim server".

Works WITHOUT streaming. armStim/disarmStim are NOT queued to the detector's worker thread (whose event loop only runs on Play). The WebSocketServer calls RippleDetector::setStimArmed(bool) directly on the main thread, which uses StimulatorClient::armFromAnyThread() / disarmFromAnyThread() — a throwaway UDP socket, safe from any thread, no event loop needed — and sets the status under a QMutex (mStatusMutex) so getStatus() (and the rippleState broadcast) reflect the change without waiting for an ACK. (The status mutex also makes the play-time ACK path race-free.)

Files (all need a rebuild except the JS): StimulatorClient.{hpp,cpp} (armFromAnyThread, status mutex/setStatusSafe), RippleDetector.{hpp,cpp} (setStimArmed), WebSocketServer.cpp (route arm/disarm to setStimArmed on the main thread), RippleModule.js (.rd-stim-toggle CSS, button markup, _isStimArmed(), _syncStimLed(), optimistic click binding). Verified on the live Pi 3B+ without streaming: 6/6 clicks alternated reliably — journal Device ARMED / Device DISARMED per click, pill green/gray, short cowsay (verified by CDP screenshot).
