Ripple (sharp-wave-ripple / SWR) detection — how it works + how to validate it#

The detector (proc.rippledetector, src/modules/swr/RippleDetector.cpp) fires when a hippocampal-ripple-band envelope crosses a z-score threshold. As of 2026-07-07 it is validated firing on both NP1.0 and NP2.0 geometries in simulation (SpikesPeak_Status.md §20). This is the pre-in-vivo rehearsal for the bench test: playing a ripple audio file into saline with the probe in the bath.

The data path — the detector runs DIFFERENTLY per probe#

The detector processes the LFP band at 2.5 kHz (its ripple-band FIR + envelope filters are designed for 2.5 kHz). Its input band, type, and decimation are config-driven, so it runs differently per probe:

NP1:  data.npx.lfp (int16, 2.5 kHz, native) ───────────────────► proc.rippledetector   (decimation 1)
NP2:  data.npx.raw (int16, 30 kHz) ─► proc.lfp ─► data.lfp ─────► proc.rippledetector   (decimation 12)
                                       (anti-alias low-pass, float 30 kHz)
  • NP1 reads the native data.npx.lfp DIRECTLY (int16 → cast channel 0 to float), decimation_factor: 1. No proc.lfp. Ripples live in the LFP band; the AP band must NOT be used — a real 1.0 probe high-passes AP (~300 Hz), attenuating the 150-250 Hz ripple. Reading the native LFP directly (one cast, no extra thread hop, no filter) is also the low-latency closed-loop path.
  • NP2 has only the 30 kHz wideband data.npx.raw, so proc.lfp low-passes it (Bessel −3 dB @ 400 Hz — the anti-alias filter, required before decimation, else 300 Hz-10 kHz spikes fold into the ripple band) → data.lfp (float, 30 kHz), and the detector decimates ÷12 → 2.5 kHz (÷12, not ÷10, to land exactly on NP1's native 2.5 kHz rate).
  • Detector chain (both): ripple-band FIR (RippleBandFilterCoefficients2_5kHz, 150-250 Hz) → rectify → envelope (EnvelopeFilter2_5kHz) → fire when envelope > mean + z·std with a lockout. Filter taps + z / latency tradeoffs follow Dutta et al. 2018 JNE (cited in the code). Detection electrodes are strictly GUI-driven and the module starts with 0 channels by default, waiting for user selection.
  • Baseline warm-up ≈ 16 s, rate-aware: gate = 2500·decimation·baseline_gate_seconds input samples (6 s on both NP1@2.5 kHz and NP2@30 kHz) + 2500·baseline_duration_seconds decimated samples (10 s) → first detection ~16 s. A validation run must Play ≥ ~18 s (the detector runs on Play; recording not required).

proc.rippledetector config keys (all optional; defaults preserve the NP2/h5 behaviour)#

key default meaning
input data.lfp data-object the detector consumes
input_type float int16 (native data.npx.lfp) or float (derived data.lfp)
decimation_factor 12 keep every Nth input sample → 2.5 kHz (NP1: 1, NP2: 12)
auto_start false default false (2026-07-08) — the module waits for a GUI/WS "Start"; a config may set true to auto-run on Play. (Flipped from true to fix "module enabled by default" on the h5-replay source.)

Note: All detection algorithm parameters (quorum_count, coincidence_window_seconds, min_duration_seconds, baseline_duration_seconds, baseline_gate_seconds, z_score_threshold, lockout_seconds) and the channel selection (detection_electrodes) are strictly GUI-driven and no longer supported in the YAML configuration. The detector initializes with 0 channels and default parameters, waiting for the GUI to send updates. | debug_files | true | write the 3 per-sample waveform dumps (latency cost — set false on hardware) |

All times are float seconds (most are ms-scale). Electrodes: NP1 = channelId + 384·bank (0..959); NP2 = shank·1280 + electrodeId (global). The source publishes its applied map as an IChannelMap (src/core/IChannelMap.hpp — probe-agnostic contract; Neuropixels ships the concrete NpxChannelMap, a future probe ships its own) to ChannelMapService, so selection follows the REAL map (a custom cross-bank/shank map resolves correctly, not just Bank-0 identity). The GUI sends electrodes to the backend via websockets, which resolves them to readout channels.

Multi-channel quorum + lockout. Each selected electrode runs its own detector (own baseline/threshold). A channel reports once per above-threshold episode, after staying above for min_duration_seconds. A true detection → fire() requires quorum_count channels to report within coincidence_window_seconds. After a report a channel is locked for lockout_seconds; on a true stimulation ALL channels are locked until t_stim + lockout_seconds (a channel that crossed early is held longer — they re-activate together when stimulation begins). quorum_count > number of detection_electrodes is an ERROR (configure fails, surfaced via sigIpErrorOccurred) — you may select more channels than the quorum, never fewer.

debug_files: gates lfp-data.bin / ripple-band-data.bin / envelope-data.bin — each written every processed sample (2.5 kHz × 3) with synchronous I/O in the detection hot loop. Turn off for a low-latency hardware run. ripple-detection-time.bin (one write per detection) is always written.

Runbook — validate detection headlessly (no hardware)#

⚠️ Channels + Start are now GUI/WS-driven. Since detection electrodes were removed from the configs (all params are GUI-driven), a plain select … ; play ; sleep detects nothing — the module starts with 0 channels and auto_start defaults false. Drive channel selection + Start over the WebSocket. The stock spikespeak_cli.py has no ripple verb, so use a small WS script (send raw JSON on ws://localhost:1234):

{"command":"selectSource","value":"Simulated NPX 1.0 Ripples"} # or the "… (GUI)" module config {"command":"setPlaying","value":true} {"command":"ripple","action":"setChannels","electrodes":[0,10,20]} {"command":"ripple","action":"setParam","name":"estimation_seconds","value":3} {"command":"ripple","action":"start"} # trains, then fires rippleDetected events A ready-made harness lives in the session temp scripts (rd_verify.py pattern). Expected after ~gate+baseline: per-channel rippleBaseline (thresholds ≈ 50-60), then rippleDetected events on the injected bursts.

# Legacy single-command runbook (STALE for detection now — kept for the streaming/debug-file path only):
$env:PATH = "C:\Qt\6.7.3\msvc2019_64\bin;<repo>\external\neuropixels\api\lib64\v4;" + $env:PATH
$work = "<build>\bin\RippleTests\np1"     # the detector writes its debug bins to CWD
Start-Process <build>\bin\SpikesPeak.exe -WorkingDirectory $work -ArgumentList "--no-browser" `
  -RedirectStandardOutput "$work\stdout.log" -RedirectStandardError "$work\stderr.log"
# NOTE: the "(play file)" sources open a native QFileDialog on selection and CANNOT be driven headlessly;
# use the non-play-file validation configs above for automated tests.

Debug artefacts in CWD: ripple-detection-time.bin ([f32 ts] per firing, always), and — when debug_files — lfp-data.bin / ripple-band-data.bin / envelope-data.bin ([f32 ts][f32 value] per decimated sample, ch0).

Expected (2026-07-07, both geometries, ripple_period_s: 2.0): threshold ≈ 46-53, 9 detections at ~17, 19, 21, … 33 s, each ~15 ms before the injected burst centre, zero misses, zero false positives, none during the 16 s warm-up. Verified log lines: NP1 input data.npx.lfp ( int16 ) decimation 1 baseline gate 6 s ( 15000 samples); NP2 Deriving data.lfp from data.npx.raw + input data.lfp ( float ) decimation 12.

Hardware later (the real test)#

Play a ripple audio file into saline with the probe in the bath. Add proc.rippledetector to the real probe config: NP1 (Npx1PxiNiDaq.yaml) → input: data.npx.lfp, input_type: int16, decimation_factor: 1, no proc.lfp; NP2 (Npx2Pxi.yaml) → keep/ add proc.lfp, input: data.lfp, decimation_factor: 12. Set debug_files: false. The detector's physical output is the StimulatorClient UDP "fire" → ESP32 microcontroller trigger → NI-DAQ (implemented; update for this revision).

Validate from a SAVED recording (post-hoc, no live capture)#

ripple_tools/analyze_recording.py <recdir> reconstructs the EXACT detector (the Common.hpp FIR taps) on a recorded band and, if the NI-DAQ captured the Pi-GPIO stim pulses, quantifies the closed loop — signal-chain, per-channel detection, NI-DAQ pulses, closed-loop overlay, and a detection+actuation latency histogram/KDE. Auto-handles both probes: NP1 reads the recorded lfp directly; NP2 decimates the recorded raw ×12 → 2500 Hz AND high-passes it first (the raw's large electrode DC leaks through the ripple FIR — sum(B_RIPPLE)≈0.018≠0 — and would swamp the envelope). Verified 2026-07-16 on real hardware recordings: NP1.0 full closed loop (115 ripples → 112 ai4 stim pulses, detection 7.2 ms + actuation 38.3 ms, sync 10 ppm / 0.011 ms) and NP2.0 detection (105–127 ripples, ~500 ms ITI, 7.2 ms). Verified 2026-07-20.

The ripple sidecar (<name>_ripple.json) — and the race that used to break it#

On record START the backend drops a sidecar next to the band files (RippleDetector::slWriteRippleSidecar, invoked from WebSocketServer::setRecording) recording which electrodes the detector ran on, their read-out channels, the per-electrode mu / sigma / threshold / z, the detector params, the stim pulse train, and baselines_trained.

It used to be a one-shot snapshot, and that was a bug. A recording can legitimately start before the baselines finish training — wait_baselines can return on a stale event, and training takes estimation_seconds. When that happened the sidecar froze threshold: 0, trained: false forever, even though the detector trained correctly seconds later. This hit NP1 test 1 (2026-07-20) and all three NP2 tests (2026-07-16); NP1 tests 2 and 3 were fine, which is the tell that the writer was never broken — it was a race.

Now the recording target is remembered (mSidecarDir/mSidecarName) and the sidecar is rewritten when the last detection channel finishes training, then the target is cleared on record stop (slClearRippleSidecar) so a finished recording is never touched again. Check baselines_trained before trusting the thresholds in an old sidecar; if it is false, take the thresholds from the WS capture (analyze_recording.py --ws <capture>.jsonl) instead.

Are the filters actually right?#

Yes — validated 2026-07-20 to float32 rounding (relative error ~2e-7, correlation 1.000000000) by re-running the 26-tap ripple FIR and 10-tap envelope FIR offline over the backend's own dumped input and comparing against its own output. The per-sample .bin dumps that make this possible are now behind compile-time switches that ship false. See FilterDebugging.md.
