Knowledge ops — where what you learned goes#

You worked something out. Where does it belong so the next person or agent gets it for free?

This page is the decision procedure. It exists because the answer used to be a judgment call made fresh every time, which meant the same fact landed in three places, or none.

1. The rule, in one line#

If a mistake can be made mechanically, make it impossible. If it can be computed, compute it. Write prose only for WHY.

Everything below is that rule applied.

2. The decision table#

What you have Where it goes Why there
A mistake anyone could repeat mechanically A check — a test, a guard, or a shared function. Then a one-line trap entry pointing at the check Prose needs reading and recall at the exact moment. A check fires whether or not you read anything
A rule spanning several call sites An invariant test (InvariantTests.md) Testing the bug catches the bug; testing the rule makes the class unwritable
A fact derivable from the source — ports, counts, paths, layouts scripts/facts.py, and nowhere else A derived fact cannot rot. A written one always does
Why something is the way it is, with the cost of learning it Prose, in the doc for that subsystem This is the one thing that is not mechanizable, and it is the most valuable content here
Something that cost you time and has no cheap check AgentTraps.md The catch-all. Always ask first whether it could be a check instead
Something a fresh agent must know before acting The skill, .claude/skills/spikespeak/SKILL.md It loads automatically. Keep it short and pointing outward
What happened, and when SpikesPeak_Status.md — append-only, dated The narrative record. Never rewrite history
Bench or hardware state that changes per session A dated table (e.g. OneBoxWiring.md §4) Add a row; never edit an old one. "The SMA is IO9" is only ever true of one afternoon
An operator-facing behaviour change user_docs/, and check the screenshots The GUI's labels are in there; a rename silently makes six pages wrong

The most common mistake is stopping at row 5. Writing the trap feels like completing the task. Ask whether rows 1–3 apply first — the trap is the fallback, not the default.

3. Turning a trap into a check#

Four of this repo's traps were mechanized on 2026-08-31. The pattern each followed:

Trap Became
"recording .bin frames carry a 6-byte header" python/spikespeak_io.py — one reader. The arithmetic is now unavailable to get wrong, and it refuses when a sidecar disagrees with itself rather than guessing
"don't start a second gate" A pid lock in run_all_tests.py, with a message saying why the symptom misleads
"revert the regression, then rebuild" facts.py reports the binary as stale when src/ is newer
"a dead browser hangs the suite" A deadline in python/tools/cdp.py, so it fails in seconds with a message naming the likely cause

What makes a good check:

  1. It fires at the moment of the mistake, not before it and not in review.
  2. Its message explains the misleading symptom, because the symptom is why the trap was expensive. "Two gates at once make every GUI test fail on unrelated assertions, which looks like a regression" is worth more than "lock held".
  3. It fails safe. A stale lock from a killed run must not block the next one — a guard that needs a human to clear it is worse than the collision it prevents.
  4. It can itself fail. Prove it, like any test here: induce the condition, watch it fire, revert.

When NOT to mechanize: when the rule needs judgment ("is this the right abstraction"), when it holds in one place only (an ordinary test is cheaper and clearer), or when the check would be so loose it goes red on things that are fine. A test that cries wolf gets disabled, and then you have neither the check nor the trap.

4. Adding to facts.py#

Add a fact when you catch yourself grepping for the same thing twice.

Rules: derive it, never type it. Keep each collector independent — one that breaks must not take the others down, because a partial answer beats a traceback. And if a fact you add is currently also written in prose somewhere, delete the prose. Two sources of truth is the problem being solved, and leaving both is worse than either.

5. Updating the skill#

The skill is the agent entry point and it loads automatically, so its staleness is maximally leveraged: a stale skill gives every future agent a wrong mental model before they read anything.

  • Update it in the same change that makes it stale — a GUI rename, a new suite, a moved contract.
  • Keep it short and outward-pointing. It is a map, not the territory. Depth belongs in developer_docs/; the skill says which page and why you would go there.
  • The frontmatter description matters as much as the body. It decides when the skill loads and what the listing shows. On 2026-08-31 it still said "the two test suites" and never mentioned the heatmap or detached windows — so it would not reliably trigger for exactly the work most likely to break something.
  • Facts with numbers belong in facts.py; the skill should say how to ask, not what the answer is.

6. Writing prose that earns its place#

The docs here are unusually good in one specific way: they say why, with the cost attached.

"Four days of #49 were spent watching the wrong connector." "This comment said attenuates and implemented eliminates." "It cost a 13-minute stall, and the test passes when re-run alone."

Keep doing that. A reader who knows what a mistake cost will not repeat it; a reader told only what is true will. When you fix something subtle, write the sentence that would have saved you.

And do the opposite for anything countable: no suite counts, test counts or page counts in prose. They were wrong for days in CLAUDE.md and nobody noticed. Point at facts.py.

7. The trigger for all of this#

The second time a bug of the same shape appears, stop fixing bugs and write down the rule.

First occurrence: fix it. Second: it is a class — mechanize it, or write the invariant. This repo had the same defect four times before anyone noticed the shape (InvariantTests.md), and had three instances of "edited something the running suite reads" in a single day.
