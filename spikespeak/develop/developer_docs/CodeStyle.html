Code style — the formatter, and why it has not been run yet#

Issue #24 asks for consistent formatting and suggests clang-format. .clang-format now exists and describes the style already in the tree. It has deliberately not been applied repo-wide; this page is the measurement and the plan, so that is a decision somebody makes rather than a diff that lands.

1. The style was measured, not chosen#

A preset picked off the shelf would have rewritten almost everything. Every setting below was derived by counting what is actually here — measured 2026-08-30 over src/, 104 files and 25,843 lines. (The tree is 115 files / 28,045 lines as of 2026-09-01; the absolute counts below are that snapshot, and §2 records a re-measurement that says the conclusion has not moved.)

setting evidence
IndentWidth: 4, UseTab: Never 9,664 lines indent by 4 (the 4,065 at 8 are nesting). Exactly one tab in the whole tree.
ColumnLimit: 100 p50 = 37, p90 = 97, p95 = 100, p99 = 106. 1,237 lines exceed 100; only 92 exceed 110.
BreakBeforeBraces with AfterFunction: true 638 function definitions open on the next line, 204 on the same.
AlwaysBreakAfterReturnType: TopLevelDefinitions 414 definitions are written bool ⏎ Class::method(...). The most distinctive thing about how this code looks, and clang-format expresses it exactly.
PointerAlignment: Left Type* name 338 vs Type *name 50; references 443 vs 22.

Three things are switched off on purpose:

  • SortIncludes: false. The tree mixes Qt, std, vendored SDK and local headers in an order that is sometimes load-bearing — the Neuropixels and NI-DAQ SDK headers are order-sensitive. A formatter reordering them is a compile error waiting to happen on a machine nobody is watching.
  • ReflowComments: false. The comments are the documentation in this codebase, and many are hand-wrapped tables and diagrams. Reflowing them destroys that, and it is the single change most likely to make people distrust the formatter and turn it off.
  • No .clang-tidy. Formatting and linting are different arguments; conflating them means the formatting change gets blocked on a lint debate.

Written for clang-format 12, which is what ships with the VS 2019 toolchain this repo builds with:

C:/Program Files (x86)/Microsoft Visual Studio/2019/Community/VC/Tools/Llvm/bin/clang-format.exe

(ReferenceAlignment and SortIncludes: Never are 13+ and are not used.)

2. What applying it would cost — measured#

Measured 2026-08-30, with clang-format 12:
files that would change 103 of 104
lines that would change 9,429 of 25,843 — 36.5 % of the tree
worst single file NpInterface.cpp, 1,324 lines

Re-measured 2026-09-01, same binary, same config, over the grown tree: 114 of 115 files, 9,760 of 28,045 lines — 34.8 %. Two thousand new lines moved the ratio by under two points, so nothing below needs re-deciding; the ablation table is still the 2026-08-30 run and is a comparison between variants rather than an absolute, which is what it is for.

Where that comes from, by ablation:

variant changed lines
the config as written 9,429
ColumnLimit: 0 (never reflow code) 6,280
SpacesBeforeTrailingComments: 1 9,387
KeepEmptyLinesAtTheStartOfBlocks: true 9,395
AlignTrailingComments: false 9,431
BinPackParameters: false 9,559

Line reflow is a third of the diff; the other ~6,300 lines are irreducible. That residue is real style drift — the exact thing a formatter exists to remove — so shrinking the diff by setting ColumnLimit: 0 would be buying a smaller number by giving up the rule most worth enforcing. The config keeps 100.

Everything else is noise, which is the useful result: the config is a close description, and no single setting is fighting the codebase.

3. Why it is not applied yet#

36.5 % of lines is a git blame event. Three things have to be true first, and none of them is about the formatter:

  1. No PR open across the same files. A reformat lands as a conflict in every in-flight branch. As of 2026-09-01 this condition is met: gh pr list shows nothing open, PR #69 (feature/ProbeHeatmapAndDetachedViews) merged 2026-08-30 and #81 (feature/AsapPerModule) merged 2026-09-01, and feature/OneBoxSupport was merged into develop on 2026-09-01. So the only thing still standing between here and step 3 is the operator's decision — which is what this page exists to hand them, not to pre-empt.
  2. It goes in ALONE, as one commit that changes nothing but whitespace, so a reviewer can verify that claim by rerunning the formatter rather than by reading 9,429 lines.
  3. .git-blame-ignore-revs gets that commit's SHA. The file itself landed on 2026-08-30 — header, instructions and the rule for what may go in it — and is deliberately empty of SHAs, because the reformat has not happened. Adding the SHA is a step in the reformat commit, not a separate task.

It is not automatic. Enable it once per clone:

bash git config blame.ignoreRevsFile .git-blame-ignore-revs

Without this, git blame on a third of the codebase points at the reformat instead of at the change that actually introduced the line — which is how a formatting commit costs a team more than the inconsistency did.

4. Until then: format what you touch#

Windows, VS 2019 (the toolchain the config was written for):

"C:/Program Files (x86)/Microsoft Visual Studio/2019/Community/VC/Tools/Llvm/bin/clang-format.exe" -i -style=file <file>

Windows, VS 2022 — same layout, different year, and Community/Professional/Enterprise each have their own tree:

"C:/Program Files/Microsoft Visual Studio/2022/Community/VC/Tools/Llvm/bin/clang-format.exe" -i -style=file <file>

Linux — a first-class dev path since 2026-08-26 (Building.md, Testing.md §1a), so it needs an invocation that is not a Windows absolute path:

sudo apt install clang-format          # or clang-format-14, etc.
clang-format -i -style=file <file>

A newer clang-format is safe against this config. Nothing here is a 13+ option — the two that would have been, ReferenceAlignment and SortIncludes: Never, are deliberately not used, and SortIncludes is written in the boolean form every version understands. A newer binary reads the file unchanged. What it does not guarantee is a byte-identical diff: formatters change their defaults for settings nobody has pinned, so do not mix versions inside one commit, and use one version for the repo-wide pass when it happens.

Do not reformat a file you are only reading. A feature diff with 300 unrelated whitespace lines in it is a diff nobody reviews properly, and that is a worse outcome than inconsistent bracing.

To check without writing:

clang-format --dry-run --Werror -style=file <file>

5. The staged plan#

  1. Now — .clang-format and .editorconfig land; no code changes. (done) .git-blame-ignore-revs landed alongside them on 2026-08-30, empty of SHAs by design.
  2. Merge the open PR. (done — the queue was empty on 2026-09-01; see §3.1)
  3. The reformat, alone, in one commit, immediately after a merge and before new work starts. Add its SHA to .git-blame-ignore-revs in the same commit — the file is already there and waiting; it is the SHA that is missing, not the file.
  4. Then decide whether to enforce it — a CI check or a pre-commit hook. That is its own decision, because a formatter that blocks a push at 2 a.m. on a rig is a formatter people disable. A --dry-run --Werror check over changed files only is the version worth having.

Not planned: reformatting ext/ or external/. Those are vendored and must stay byte-comparable with upstream.
