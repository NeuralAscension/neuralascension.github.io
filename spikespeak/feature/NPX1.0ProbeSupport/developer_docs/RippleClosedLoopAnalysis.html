Offline analysis of closed-loop ripple→stim recordings#

How a recorded NP2.0 ripple→stimulation test is analysed after the fact to (a) reproduce the online detector exactly from disk, (b) quantify the closed-loop latency (detection → current into the electrode), and (c) the NI-DAQ↔Neuropixels sync it all depends on — including a real off-by-one bug that was found and fixed on 2026-07-17.

This documents the analysis of RecordingTests/np2_{1channel_1required,2channel_2required,4channel_3required} (three real NP2.0 tests, 100 online ripple detections each, synthetic ripple in saline + NI-DAQ + the Pi/AM2300 stim server). Full result write-up: ../RecordingTests/NP2_RIPPLE_TESTS.md.

Tools#

  • ripple_tools/analyze_recording.py <recdir> --ws <name>_ws.jsonl [--quorum "..."] — the main analysis. Reads the recording + the WS-event capture + the ripple sidecar; writes analysis/ (signalchain, detection, nidaq, closedloop, latency, _summary.json). Works from the recording alone (no live rig).
  • ripple_tools/verify_quorum.py <recdir> --quorum N — transparent, per-channel reconstruction of the quorum state machine, for eyeballing that the offline detector reproduces the backend.
  • Both use python/spikespeak_postprocess (Recording, synchronize) + the exact FIR taps from src/core/Common.hpp.

Reproducing the NP2.0 detector EXACTLY offline#

The NP2 detector does not run on the recorded raw band directly — it runs on data.lfp, which the backend derives from raw. To reproduce it bit-for-bit (not approximately) the offline analysis replays the whole front-end (all coefficients live in src/core/Common.hpp):

  1. data.lfp — src/modules/lfp/LFPProcessor.cpp runs Avx2Filter::setDefaultLFPFilterCoefs on the 30 kHz raw: a 2nd-order Bessel low-pass, −3 dB @ 400 Hz (LFPFilterCoefficients30KHz: b=[0.00163508, 0.00327016, 0.00163508], a=[1, −1.85831868, 0.86485901]), Direct-Form-I y[n]=Σb·x − Σ_{i≥1}a·y, zero initial state. No DC removal anywhere. (Applied offline without scipy as the IIR's zero-state impulse response convolved in — exact to ~1e-16.)
  2. Decimate — the detector takes every 12th sample (RippleDetector.cpp, mCurrRawDataInd % mDecimationFactor == 0); simple decimation, no anti-alias (the Bessel already band-limited it). NP1 skips steps 1–2: it records data.npx.lfp directly (decimation 1).
  3. Ripple band — 26-tap 150–250 Hz FIR (RippleBandFilterCoefficients2_5kHz, a=[1] → pure FIR).
  4. abs(), then envelope — 10-tap FIR (EnvelopeFilter2_5kHz, a=[1]).
  5. Threshold — mean + z·σ (z=2.5) trained on the baseline window. Because the exact Bessel puts the offline envelope in the same scale the live detector used, the ONLINE per-channel threshold (from the WS rippleBaseline, keyed by electrode → remapped to read-out channel via the _ripple.json sidecar) applies directly — identical to the live detector.
  6. Quorum — per-channel rising-edge → per-channel lockout → count channels whose lastCrossTime is within the coincidence window (includes self) → fire if reporting ≥ quorum and past the shared stim-lockout, then bump all channels' lockout (RippleDetector.cpp ~728–769). Reproduced in quorum_detections().

Validation: with this exact chain the offline reconstruction reproduces the online detector on the clean tests (offline-quorum→ai4 = +1.45 ms / 0 unmatched for test 1, +3.6 ms for test 2), matching the online-instant latencies. Historical note: an earlier raw÷12 windowed-sinc approximation of data.lfp plus a DC-removal the detector never does gave the wrong scale and ~10 ms offsets — do not reintroduce it.

Closed-loop latency#

Definition: closed-loop latency = ai4 stim pulse HIGH − the causal detection that triggered it = the physical path detect → fire() → UDP → Pi GPIO → AM Systems 2300 → electrode. The causal-vs-zero-phase FIR group delay is not included (it is a fixed function of the tap count, not part of the loop).

Method: pulse-anchored — each ai4 rising edge is paired with the detection that preceded it, so the value is ≥ 0 by construction. The detection instant used is the recorded online detector firing time (rippleDetected ts = lfpTs, mapped onto the recording clock via the NPX per-sample hardware timestamp, raw_ts / 100 kHz), i.e. the actual realtime causal-detector instant — no reconstruction jitter.

Results now live in ../RecordingTests/CLOSED_LOOP_LATENCY.md (the "Closed-Loop Latency" section of the docs book), which is the single source of truth for measured latency on both probes.

Numbers published before 2026-07-21 were inflated. online_det_recording_times mixed a NOMINAL 100 kHz tick rate with the MEASURED per-sample rate, leaving a ~10 ppm scale error that grew with recording length (+6.5 ms over a 618 s run; invisible at ~70 s). It also produced a spurious "latency rises with quorum size" trend. Fixed; every recording test has been re-analysed.

NI-DAQ ↔ Neuropixels sync (and the off-by-one bug)#

A shared ~1 Hz TTL sync pulse feeds both the NPX sync input (recorded in the NPX sync field) and NI-DAQ analog ai0. Recording.synchronize() (→ spikespeak_postprocess/sync.py align_timestamps) matches the two rising-edge trains and fits a linear NI-DAQ→NPX time warp, so the recorded ai4 stim pulses land on the same clock as the recorded ripples.

The bug (fixed 2026-07-17). Test 3's NI-DAQ captured one fewer sync pulse than the NPX (78 vs 79 — it stopped ~0.8 s before the last NPX sync). The old default match="end" pairs the last N edges one-to-one, which — when the dropped pulse is at the other end — is off by one, shifting every NI-DAQ time by exactly one sync period = 1000 ms = 2 ripple cycles. On a periodic 1 Hz train this is invisible: the shifted pairing has identical inter-pulse intervals and the same 0.012 ms fit residual, so nothing flagged it. The symptom was ~half the ai4 pulses landing in ripple-free envelope troughs ("orphans") and an inflated/garbled latency. Tests 1 & 2 had matching counts (76=76, 80=80) and were never affected.

The fix. align_timestamps now defaults to match="auto" (_pair_edges_auto): estimate the true sub-period clock offset (the smaller-magnitude of the start- and end-anchored offsets — they differ by count_diff × IPI, and the true offset is < IPI/2), then nearest-edge pair the two trains within ½ IPI, so a missing pulse at either end can't cause an off-by-N. Recording.synchronize default is also "auto". Spot-check across all three tests: only test 3 had a count mismatch; auto fixes it (42→0 unmatched, latency 4.06→3.45 ms) and leaves the already-correct tests 1 & 2 byte-identical.

Lessons (worth internalising for any closed-loop timing analysis): - On a periodic sync train, a tiny fit residual does not prove correct alignment — a whole-period pairing error hides inside the periodicity. - Verify event-by-event, not nearest-neighbour. Nearest-neighbour matching on a 2 Hz signal happily pairs a 2-cycle-shifted stream (each pulse just lands on a different ripple), which masked the shift in every scalar metric until the ripples-vs-detections-vs-pulses raster (analysis/*_timeline.png) made it obvious. - Look at the per-channel envelope vs threshold (analysis/*_perchannel_at_pulses.png) + the raster FIRST, before theorising about hardware.

Reading a count mismatch correctly (NP1.0 lessons, 2026-07-20)#

When online detections, offline crossings, and ai4 pulses disagree, look at the times before theorising. Two real cases from the NP1.0 regression, both benign, both initially easy to misread as a broken detector:

1. A recording that starts before the detector arms produces a LEAD-IN. NP1 test 1 showed 117 offline crossings, 100 online detections and 99 ai4 pulses. Nothing was missed: the ai4 train starts at t = 11.24 s, which is exactly crossing #19, and crossings[18:] pairs 1:1 with the 99 pulses (max deviation 4.6 ms, mean offset +3.19 ms = the closed-loop delay plus causal-FIR group delay). So 117 = 18 pre-arm ripples + 99 stimulated. Tests 2 and 3, with no lead-in, gave exactly 100/100.

Check: compare the time of the first ai4 pulse against the crossing index, and diff the two event lists. A lead-in is a contiguous block of unstimulated crossings at the START; a real detector failure is scattered through the run.

2. The synthetic stimulus itself drops ripples. The ai4 train has nine ~1.58 s gaps at a regular 10-pulse cadence — and the offline envelope crossings show the identical gaps. That is a property of the play file, not a detection miss. Whenever a gap appears in both the input-derived crossings and the output pulses at the same instants, the stimulus is the cause.

The general rule (see the sync off-by-one bug above): verify closed-loop timing event by event against the recorded signal, never by nearest-neighbour matching on a periodic train, and never by reasoning about the hardware before plotting the envelope against the threshold.
