SpikesPeak — Module Communication (frontend ⇄ backend commands)#

How the browser UI sends commands to backend modules, and the one standard every module should follow: a per-module Q_INVOKABLE exposed over QWebChannel ("Option A"). This doc covers the modules on the standard — the Neuropixels sources (PXIe, OneBox and the sims) and the Recording sink — and gives the general recipe for the rest.

Wider context: SpikesPeak_Architecture_Review.md §7 (the Option A decision) and §3 (the WebSocket multiplexing). For the recording data path specifically, see Recording.md.

1. The transport: one WebSocket, three multiplexed channels#

The backend serves the UI over HTTP :8234 and opens it in a dedicated Chromium app-window (--tab for a system-browser tab, --no-browser for none — architecture review §1); all backchannel traffic rides one WebSocket on :1234 (NetworkClient.js ⇄ WebSocketServer.cpp), split three ways:

Channel Direction Carries Entry point
(a) Binary waveform stream C++ → JS decimated samples for the live view broadcastData → NetworkClient.handleMessage (ArrayBuffer)
(b) JSON app commands JS → C++ setPlaying, selectSource, Disconnect (global app verbs) id 0x1000 → onTextMessageReceived
(c) QWebChannel RPC JS ⇄ C++ per-module commands (the standard) + C++→JS events Q_INVOKABLE on a registered object

Channel (b) started as the small set of global verbs that aren't owned by any one module, and channel (c) is where module commands were meant to live. (A legacy binary command id 0x1001 used to carry recording toggles through a CommandDispatcher; it has been removed in favor of (c) — see §4.)

Be honest about where the line actually falls now. WebSocketServer::onTextMessageReceived matches sixteen verbs, and several of them are per-module in everything but their transport: ripple (the whole SWR dock), lowLatency (the ASAP control, #80), listRecordings / convertRecording (the Convert panel), plus getSystemState, probeHardware, setProbePort, pickDirectory, restart and quit. The reason in each case is the same and it is a real one: a Python client must be able to send it. python/spikespeak_cli.py speaks JSON over the socket and would otherwise have to implement the QWebChannel protocol (§8). Two more modules — audio and the band filters — reach C++ through CommandDispatcher ids instead (§7). So Option A is the standard for anything needing a return value from an object, not a rule that every module command rides QWebChannel; the exceptions are listed rather than pretended away.

C++→JS events (e.g. deviceReady, recordingStatus) are plain JSON text messages the server pushes to every client (WebSocketServer::setDeviceState / broadcastStatusEvent); NetworkClient dispatches them by their event field.

2. The standard: per-module Q_INVOKABLE over QWebChannel (Option A)#

Every module command is a Q_INVOKABLE method on the module's own QObject, exposed over QWebChannel. The browser binds the object and calls the method directly — there is no central command router to edit when you add a module. Adding a camera with setExposure() is just: declare the invokable, register the object, bind it in JS.

The lifecycle has four steps, all already in place for both example modules:

 (1) REGISTER            (2) BIND                  (3) INVOKE                  (4) TEARDOWN
 C++: onSourceSelection  JS: on "deviceReady"      JS: obj.method(args[,cb])   C++: on "Disconnect"
 mWebChannel             new QWebChannel(...)       →  C++ Q_INVOKABLE runs     mWebChannel
   ->registerObject(       bind channel.objects                                   ->deregisterObject(
     "registry.name",       by name substring                                       obj)
     obj)                   to window.<global>

2.1 Registration (C++, WebSocketServer::onSourceSelection)#

When a source is selected, the server resolves the profile's registry names and registers each module object under its registry name:

  • the source object (e.g. source.npx.pxi) — always;
  • the recorder processor (e.g. proc.npx.recorder) — if the profile has one.

registerObject(name, obj) only introspects the meta-object and stores a pointer; the object may live on any thread (see §5).

2.2 Binding (JS, NetworkClient.handleMessage on deviceReady)#

Once the device reports ready, the client builds one QWebChannel and binds each backend object to a window.* global by a registry-name substring:

Object (registry name) How it is picked Global
every registered object — window.channelObjects (the raw map)
source.npx.pxi, source.npx.onebox, source.npx.simdata, … keys containing "npx" and not "recorder", then the first that has getImroAsJson window.activeNpxModule
proc.npx.recorder, proc.nidaq.recorder, … "recorder" (all matches) window.activeRecorders (array) + window.recordersByName (name → object)

Both the source and the recorder names contain "npx", so the source match explicitly excludes "recorder". The final pick is by CAPABILITY, not by name order: a profile can register several npx sources — a probe and the OneBox ADC — and only the probe exposes the IMRO surface, so picking the first npx key silently bound the ADC and left an empty Probe Map. The test is typeof obj.getImroAsJson === "function", with the first npx key as the fallback.

Recording is the multi-instance case: a profile can configure several recorders (one per data source — e.g. NPX and NI-DAQ), so the binding collects all "recorder" objects into an array, and the single Record button fans out to every one (§4). window.recordersByName keeps the registry name alongside each, so a per-recorder channel selection can be routed to the right one. Keep registry names substring-distinguishable when you add modules.

window.channelObjects is set before the npx branch, deliberately: a profile with no probe — the NI-DAQ-only one — never enters that branch, so a per-device panel that keyed off something set inside it would never appear on exactly the rig it exists for. A panel finds its own object by capability, and this file does not have to know the panel exists.

2.3 Invocation (JS)#

// no return value needed -> just call it (recording fans out to every bound recorder)
window.activeRecorders.forEach(r => r.setRecording(true, dir, name, channels));

// return value needed -> pass a callback (QWebChannel delivers the result async)
window.activeNpxModule.applyMapToHardware((ok) => { /* ok is the C++ bool */ });

2.4 Teardown (C++, Disconnect)#

deregisterObject for the source(s) and every recorder; the recorder pointers are tracked in mRecorderProcs (a QList<IProcessor*> — a profile can have more than one, §4) so each can be deregistered and its error signal disconnected.

3. Module A — Neuropixels source (source.npx.pxi, source.npx.onebox, and the sims)#

The reference implementation of Option A. Six Q_INVOKABLEs on NeuropixelsSource (NpInterface.hpp) drive the IMRO panel:

Method Returns Purpose
getImroAsJson() QString serialize the current map → JSON for the UI
updateImroFromJson(json) bool validate + atomically replace the map
applyMapToHardware() bool push the map to the probe
getImroAsImroText() QString .imro text for client-side download
loadImroFromText(text) bool parse .imro contents (read client-side) into the map
saveImroToFile(path) bool server-side write (programmatic; UI uses the download instead)

Two more sit beside them and drive the Tip referencing checkbox in the same panel: setTipReferencing(bool) and isTipReferencing() — each channel referenced to its own shank tip (NP2.0 multishank) or refId 1 (NP1.0), verified through the same pause → apply → writeProbeConfiguration read-back → resume path as Apply Map.

This is not only a real-hardware surface. SimDataSource, SimData2Source and SynthRippleSource each declare the five map methods — getImroAsJson, getImroAsImroText, updateImroFromJson, applyMapToHardware, loadImroFromText — which is why the probe-map editor can be developed and GUI-tested on a box with no probe. They do not declare saveImroToFile (a server-side write with no meaning without hardware), and they do not declare the two tip-referencing invokables either — so "the sim sources expose the same surface" is true of the map editor and not of the panel around it. That gap is live: ImroManager.js guards the read-back (if (npxBackend.isTipReferencing)) but calls setTipReferencing unguarded, and nothing hides #reference-controls, so the Tip-referencing checkbox is offered on a simulated source and throws when clicked. Test for the method — a probe-shaped source is not a probe. (Checked 2026-09-01.) OneBoxSource derives from NeuropixelsSource, inherits all of it, and adds its own panel's worth on top (ADC range, the WavePlayer/DAC load-arm-fire calls, per-channel grounding, comparator thresholds) — the same pattern, more methods, no central router touched. That is the point of Option A, and OneBoxModule.js finds its object by capability rather than by source name, so it appears on exactly the rigs it applies to.

Bound to window.activeNpxModule; called from ImroManager.js. NeuropixelsSource lives on the main thread (only its acquisition worker is on a separate thread), so its invokables run directly and may return values synchronously (§5).

File I/O for these stays in the browser (read via <input type=file>, write via Blob download) — see the architecture review §7.5. Never open a modal dialog inside a Q_INVOKABLE.

4. Module B — Recording sink (proc.npx.recorder, proc.nidaq.recorder, …)#

Migrated to Option A (was a 0x1001 binary command through CommandDispatcher). One invokable on RecordProcessor (RecordProcessor.hpp):

Q_INVOKABLE void setRecording(bool enable, const QString& outputDir, const QString& namePrefix,
                              const QVariantList& channels = {});

outputDir and namePrefix come from the record modal (files land as <namePrefix>_<band>_<timestamp>.bin in outputDir). channels is the GUI record-channel selection as read-out channel indices — the browser maps the selected electrodes to channels before sending — and when non-empty on start it overrides each recording's YAML channels: for that session only; empty means the configured default. (Electrode-vs-channel is a real trap on NP2.0: see AgentTraps.md §1.)

  • Multiple recorders, one button. A profile can configure several RecordProcessor instances — e.g. config/NpxPxiNiDaq.yaml has proc.npx.recorder (records data.npx.raw) and proc.nidaq.recorder (records data.nidaq.raw). WebSocketServer::onSourceSelection registers every one; NetworkClient binds them all into window.activeRecorders; AppController.toggleRecord() calls setRecording(...) on each. This restores the old 0x1001 behavior, where the broadcast hit every recorder subscriber. (The old single-activeRecorder binding only drove the last recorder — a regression that's now fixed.)
  • Per-recorder, per-stream config — including channel selection — lives in the YAML. Each recorder's recordings: list names a data_name, a data_interpreter_name, an output_filename, and an optional channels: [...]. That channel list becomes the filter passed to the interpreter's serializeAvailableData, so e.g. channels: [0, 3] records only NI-DAQ channels 0 and 3. Each module supplies its own interpreter (interp.npx.raw → NpxDataInterpreter, interp.nidaq.raw → NiDaqDataInterpreter), so formats stay independent. (The long-term generalization — one recorder, many interpreters — is SpikesPeak_Status.md §11.1.)
  • Workflow unchanged for the user: the Record button is enabled only while playing, so it's still Play first, then Record (the recorder reads the live buffer).
  • No return value. Opening files is asynchronous (it's marshaled to the recorder's worker thread, §5), so success/failure can't come back through the call. Instead the backend pushes a recordingStatus event:

RecordProcessor::applyRecordingState --(open fails)--> emit sigIpErrorOccurred(msg) -> WebSocketServer::slBroadcastRecordingError -> broadcastStatusEvent("recordingStatus", msg, "error") // JSON text to all clients -> NetworkClient: window.guiStatus(msg,"error") + window.onRecordingError(msg) -> toolbar turns red; main.js reverts the optimistic "recording" button state

This request (invokable) + outcome (event) split is the recommended shape for any module command whose work is async or happens off the GUI thread.

5. Thread-safety — the one rule that bites#

QWebChannel invokes Q_INVOKABLEs with Qt::DirectConnection — i.e. on the GUI / transport (main) thread, regardless of the object's thread affinity. So:

  • Main-thread objects (the NPX source): invokables run on the main thread. Fine to touch state and return a value synchronously.
  • Worker-thread objects (every IProcessor sink — ProcessorManager does moveToThread): the invokable body still runs on the main thread, so it must not touch state owned by the worker thread directly. Marshal onto the object's own thread first:

cpp Q_INVOKABLE void setRecording(bool enable) { QMetaObject::invokeMethod(this, [this, enable]() { applyRecordingState(enable); }, Qt::QueuedConnection); // hops to THIS object's thread; runs after the marshal }

This is why setRecording returns void and reports outcomes via an event (§4): the real work (applyRecordingState) runs later, on the recorder's thread, where it can safely open/close files without racing the slProcessAvailableData timer slot.

Rule of thumb: return a value only from a main-thread object's invokable. For a threaded sink, make the invokable void + marshal + emit a status event.

6. Recipe — add a command to a new module#

  1. Declare a Q_INVOKABLE on the module's QObject (Q_OBJECT required). Return a value only if the object lives on the main thread; otherwise make it void.
  2. (Worker-thread objects) marshal the body to the object's own thread with QMetaObject::invokeMethod(this, functor, Qt::QueuedConnection).
  3. Register the object in WebSocketServer::onSourceSelection via mWebChannel->registerObject("registry.name", obj), and deregister it in the Disconnect handler. (Sources are already handled by the generic loop; a new sink needs a line like the recorder's.)
  4. Bind it in NetworkClient.handleMessage's deviceReady callback: window.activeX = channel.objects[keys.find(k => k.includes("yourname"))]. Keep the registry name substring-distinguishable from the others.
  5. Call it from your frontend code: window.activeX.method(args[, cb]).
  6. Async outcome? Emit a signal the server relays as a JSON event (mirror recordingStatus), and handle it in NetworkClient → window.guiStatus / a UI hook.

7. Not on the standard yet (to migrate later)#

  • Global app verbs (setPlaying, selectSource, Disconnect) still ride channel (b) JSON id 0x1000. These are app-level, not module-level, so they may legitimately stay — but a future cleanup could route them through a dedicated controller object's invokables too.
  • Three whole modules ride channel (b) as well, and did so by choice, not by neglect: the SWR dock ({command:"ripple", action:…}, RippleModule.js), the ASAP control ({command:"lowLatency", module:"proc.x", value:bool}, LowLatencyModule.js, #80) and the Convert panel (listRecordings / convertRecording, ConvertModule.js). Each of them has to be drivable from python/spikespeak_cli.py, which speaks JSON and not QWebChannel (§8), and none of them needs a return value from an object — the backend answers with an event. If your module needs both a headless client and an object return value, you need §2 and a channel-(b) verb, which is exactly what recording has.
  • Two processors subscribe to CommandDispatcher ids: AudioProcessor on 0x218 (AudioModule.js) and BandFilterProcessor on kBandCommandId = 0x219, one shared id for every band with the payload naming which (BandModule.js). The CommandDispatcher infrastructure remains, and it is generic; migrating either to a setX() invokable is the same recipe as §6. (An earlier version of this line said the recording migration removed the only UI-facing CommandDispatcher user. It removed the only one at the time; two have been added since.) Note the sharp edge that path already cost: executeCallbacks used to erase from the vector it was iterating, which is undefined behavior and segfaulted the backend — AgentTraps.md §5g.
  • IDataSource::handleWebCommand (the legacy fire-and-forget JSON hook) still exists as a no-op default with a known routing gap (architecture review §7.4); prefer Q_INVOKABLE.

8. Control CLI — channel (b) JSON as a scripting surface#

python/spikespeak_cli.py drives the app headlessly over the same WebSocket, using channel (b) JSON 0x1000 commands (not QWebChannel). WebSocketServer::onTextMessageReceived handles the CLI verbs — listConfigs, setProbeMap, setRecording, quit — alongside the existing global verbs (§7).

Deliberate divergence from Option A: recording and IMRO get a JSON command path here in addition to their QWebChannel path. setRecording fans out to mRecorderProcs by invoking each recorder's setRecording Q_INVOKABLE by name (QMetaObject::invokeMethod(..., Qt::DirectConnection, …) — the same thread + method the browser hits via QWebChannel); setProbeMap calls IDataSource::applyNamedMap (NPX override). This keeps the CLI QWebChannel-free (a Python client would otherwise have to speak the QWebChannel protocol). The GUI still uses the QWebChannel path; both call the same backend methods.

State-mirror events (stateSource / statePlaying / stateRecording, via broadcastJson) let a watching browser reflect a CLI-driven session without re-sending commands. Full reference: ControlCLI.md.
