Profiling — where the time actually goes#

This page is OVERWRITTEN, not appended to.#

It describes the build that ships today and nothing else. Re-profile, replace the numbers in place, move the date below. Do not add a second table beside the old one, and do not keep a history section here.

That is the opposite of the rule for SpikesPeak_Status.md, deliberately. Status answers what happened, so it is append-only and never rewritten. This answers what is true of the code right now — and a superseded performance number is not history, it is a wrong answer that still reads like a right one. Somebody will quote it. The history is in git log -p on this file, which is a better record than a stale table anyway.

The same reasoning is why scripts/facts.py derives rather than stores, and why countable things are banned from prose elsewhere in these docs.

Last measured: 2026-09-01, on this machine, in the shipped code — every number below comes from that run. The headline is that there is no hot spot, which is a useful thing to have written down: it is what stops the next person optimizing something that does not matter.

This is the profiling report. For closed-loop latency — the per-stage breakdown from threshold crossing to stimulus out — see LatencyProfiling.md, which answers a different question. This document is about load: CPU, GPU and where the frames go.

The machine, because a performance number without one is not a measurement:
CPU Intel Core i7-11700K, 8 cores / 16 threads — SSE2, AVX, AVX2, FMA, AVX512F
GPU NVIDIA RTX 3060 Ti, via ANGLE / D3D11
OS Windows 10
Frontend profiler ripple_tools/profile_frontend.py → frontend_profile.json
Backend CPU ripple_tools/profile_backend.py → backend_profile.json
Filter microbenchmark tests/bench_filter.cpp → build/tests/bench_filter (.exe on Windows)
Heatmap renderer benchmark ripple_tools/bench_heatmap.py → heatmap_bench.json

All four are reproducible. None is registered with ctest — see §6.

1. The frontend: ~1.5 % of one core#

Chrome's sampling profiler, 12 s per configuration, simulated NP1.0 with ripples, four columns.

configuration main thread busy real work of wall
traces, 4 columns 17.6 % 181.0 ms 1.51 %
heatmap, 4 columns 17.0 % 168.6 ms 1.40 %
heatmap, 4 columns, all 384 channels 17.9 % 173.9 ms 1.45 %

The 17–18 % "busy" figure is almost entirely (native):(idle) — the profiler counts the sample, not the work. Subtract it and the page is doing 1.4–1.5 % of one core.

"Real work" is now computed, not derived by hand. These two columns used to be worked out while writing this page, from a definition that was never written down — so on 2026-09-01 the table could not be reproduced from the JSON it came from, and nobody could tell whether it had meant non-idle, or non-idle minus V8's own (program). profile_frontend.py now emits real_work_ms and real_work_pct_of_wall (main-thread total minus (idle)), so re-running the tool regenerates the table and the definition lives in one place.

Everything else, in order, for the heaviest configuration:

(native):(program)                   100.2 ms   <- V8 itself: parse, compile, internal
NetworkClient.js:handleMessage        43.2 ms   <- the binary decode. THE hot function.
(native):(garbage collector)           7.5 ms
ChartColumn.js:pushHeatmapColumn       6.1 ms   <- heatmap aggregation, 384 channels
(native):bufferSubData                 3.9 ms   <- the actual GL upload

handleMessage is the only thing in the frontend worth optimizing, and at 43 ms per 12 s it is 0.36 % of a core.

It also measures itself, continuously and in the shipped build: NetworkClient.js logs a [PERF][NetworkClient] line with batches/s and average parse ms. That is the zero-setup way to sanity-check this figure on a machine you are not going to run the profiler on.

The renderer barely appears: bufferSubData is 3.9 ms and the draw calls do not make the list at all.

The optimization deliberately not taken#

Columns showing the same channel list each run their own gather out of the decoded frame. Sharing it across identical columns would save roughly 1 ms/s.

It was not done. It adds a cache keyed on the channel list to a path that runs 50 times a second, to save a thousandth of a core. The number is recorded here because "we chose not to optimize this" is only defensible with one.

2. The heatmap renderer: flat in channel count#

ripple_tools/bench_heatmap.py, measured in the shipped renderer on an RTX 3060 Ti (ANGLE/D3D11).

channels upload per time bin draw per frame (traces, same column)
384 2.10 µs 0.0010 ms 0.0055 ms
960 5.20 µs 0.0005 ms 0.0040 ms
1536 7.90 µs 0.0005 ms 0.0040 ms

The draw does not grow with channel count — four times the channels is the same single draw call of two triangles, and the difference between the rows is noise. What grows is the upload, linearly, because it is channels × 4 bytes per time bin.

At 1536 channels that is 7.90 µs per bin against a bin every ~10 ms: 0.08 % of a core.

"A bin every ~10 ms" is the 8 s default span, not a constant. The span is a per-column control (1 s – 1 min, see HeatmapView.md §1b) and the bin rate is bins / window, so at the 1 s end it is a bin every ~1.3 ms — eight times these numbers, and still 0.6 % of a core at 1536 channels. Quote the span with the figure or it is not a fact about anything.

Total heatmap cost end to end is ~0.2 ms/s at the default span, and it does not move the backend out of the noise — the statistic is computed in the browser, so there is no reason it should.

3. The backend: about one core, and the display mode does not change it#

ripple_tools/profile_backend.py, 20 s windows, simulated NP1.0 ripples, browser attached:

cores
traces, 4 columns 1.039
heatmap, 4 columns, all channels 1.028

One core, near enough, and the display mode does not change it. That is the shape you want: the acquisition and processing cost is set by the source and the processor graph, not by what the browser happens to be drawing.

Measured with a browser attached, unlike §4's SIMD pair, which is headless. The two are not directly comparable and are not meant to be — this one answers "what does a running rig cost", that one isolates one compile-time choice.

4. AVX2: 3.15× in the filter, and 4.5 points of a core end to end#

build/tests/bench_filter.exe, 384 channels through the LFP preset (2nd-order Bessel IIR), median of 12 reps of one second at 30 kHz:

tier per 384-channel sample row per second of data
AVX2 498.1 ns 14.94 ms — 1.49 % of one core
scalar 1566.4 ns 46.99 ms — 4.70 % of one core

3.15×, saving 32.1 ms of CPU per second of filtered probe data.

It was 2.89× until the dispatch was hoisted, and that is the interesting part#

addSample used to call useAvx2() per call. The header described that as "a load of a cached bool" — it was not. useAvx2() is a Meyers singleton in another translation unit, so every call was a real cross-TU call plus a guard-variable check, and with no LTO in this build the compiler could not see through it or inline addSampleAvx2 behind it.

addSample runs once per 8 channels per sample — 1.44 M times a second per band at 30 kHz × 384 channels. Reading the tier once at load into a namespace-scope const bool took 554.5 → 498.8 ns, a 10 % gain on the vector path for a ten-minute change, and moved the ratio from 2.89× to 3.10×.

Two things worth taking from it: a comment asserting a performance property is worth exactly nothing until somebody measures it, and the same mistake was already fixed in DisplayProcessor.cpp — the pattern existed and this file had not been brought to it.

The end-to-end measurement, corrected on 2026-09-01#

Forcing each tier and measuring the whole backend, headless, on the NP1.0 ripple configuration, --simd-reps 6 (interleaved avx2 / scalar pairs, so thermal or scheduling drift cannot be attributed to the flag):

median cores range over 6
SPIKESPEAK_SIMD=avx2 1.020 1.011 – 1.029
SPIKESPEAK_SIMD=scalar 1.065 1.047 – 1.083

4.5 percentage points of one core, and the two ranges do not overlap — the slowest AVX2 run is still faster than the fastest scalar one.

This reverses what this page said until today. It reported 1.022 vs 1.019 — "no difference" — from n = 2, and built an explanation on top: that NP1.0 gets its LFP band from the probe, so proc.lfp is never provisioned and the filter barely runs. The number is superseded and the explanation was incomplete.

The filter was never the only consumer of the dispatch. DisplayProcessor.cpp:561 calls calcMinMaxAvx2 for the per-channel display min/max, and that runs on every configuration that draws something, whether or not proc.lfp exists. So there was never a reason to expect zero here.

Two lessons, and the second is the one that generalises. A conclusion drawn from n=2 is a conclusion about an afternoon — --simd-reps exists now so a claim about this can be made at a rep count that supports it. And "no difference, and here is the mechanism" is a dangerous shape: the mechanism made a wrong number feel explained, which is exactly what stops anyone re-measuring.

The NP2.0 prediction still stands, and is still unverified here. NP2.0 has no hardware LFP, so proc.lfp derives it — 384 channels of IIR per sample — and the flag should move the process by more than it does on NP1.0. A previous one-off measured +3.8 pp, but no artifact or command was recorded, so treat it as an anecdote until somebody runs:

python ripple_tools/profile_backend.py --source "Simulated NPX 2.0 Ripples"     --simd-reps 6 --out ripple_tools/backend_profile_np2.json

5. Reproducing all of it#

python ripple_tools/profile_frontend.py
python ripple_tools/profile_backend.py                    # add --simd-reps 6 for a claim about SIMD
python ripple_tools/bench_heatmap.py

profile_backend.py is Windows-only: its CPU-time primitive shells out to a Windows facility, so the backend column is the one thing here that does not port. The other three run anywhere.

The filter benchmark needs Qt on PATH, and nothing puts it there#

build/tests/bench_filter.exe: error while loading shared libraries: Qt6Core.dll

bench_filter links Qt6::Core, and the ENVIRONMENT PATH=... that tests/CMakeLists.txt sets is given only to ctest-registered suites — which this deliberately is not (§6). So it gets nothing, and every command below fails in a plain shell until you fix that. Same trap as the app's 0xC0000135; Testing.md §1 and Building.md both state it, but a reproduce block whose commands do not run is a reproduce block that does not work.

Ask the launcher where Qt is rather than hardcoding a version:

bash python -c "import sys; sys.path.insert(0,'scripts'); import spikespeak as s; print(s.qt_runtime_dir('build'))"

The filter microbenchmark, and the same thing again with the vector path forced off. Three shells, three syntaxes — SPIKESPEAK_SIMD=scalar <cmd> is a bash env prefix and is a parser error in PowerShell, which is the shell most likely to be open on the rig:

export PATH="/c/Qt/6.7.3/msvc2019_64/bin:$PATH"           # Windows, Git Bash -- see the note above
build/tests/bench_filter.exe
SPIKESPEAK_SIMD=scalar build/tests/bench_filter.exe

$env:PATH = "C:\Qt\6.7.3\msvc2019_64\bin;$env:PATH"       # Windows, PowerShell -- see the note above
build\tests\bench_filter.exe
$env:SPIKESPEAK_SIMD='scalar'; build\tests\bench_filter.exe
Remove-Item Env:\SPIKESPEAK_SIMD                          # it persists in the session otherwise

export LD_LIBRARY_PATH="$HOME/Qt/6.11.1/gcc_64/lib:$LD_LIBRARY_PATH"   # Linux -- lib/, not bin/
build/tests/bench_filter                                  # and no .exe
SPIKESPEAK_SIMD=scalar build/tests/bench_filter

bench_filter decides its tier once per process by design — the dispatch must not change under a running acquisition — so it measures whichever tier it resolved to. Run it twice.

The same environment variable drives the C++ suite's second ctest pass, which is a correctness check rather than a measurement: see Testing.md §1 and SimdDispatch.md.

Each writes its JSON next to itself in ripple_tools/, so a re-run on another machine is directly comparable.

6. Why none of these is in the test gate#

A benchmark is a stopwatch, not an assertion. A benchmark inside the gate is a flaky test waiting for a busy machine — it would be the only suite whose result depended on what else the laptop was doing, and the failure mode is somebody adding a tolerance wide enough to make it pass, at which point it stops detecting anything.

They are built with the suite so they cannot rot, and run by hand.

If we ever want a benchmark that gates, it needs a different design: a recorded baseline, a tolerance justified against measured machine-to-machine variance, and somewhere to keep the history. That is a decision to make deliberately, not by adding add_test.

7. What is NOT measured here, and should be#

  • GPU utilization in this document is not measured — every GPU number above is a draw-call timing. But it is measured elsewhere, and on real hardware: RendererExperiment.md §3a reports GPU utilization and board power at 480 live traces on a OneBox + NP2.0 (SciChart 38.0 ± 0.4 % / 19.8 W vs WebGL2 35.9 ± 0.2 % / 19.6 W). Read that as GPU parity: the win is CPU, roughly 4×. Do not quote a GPU saving — a reviewer who checks the table will find 1.06× and 1 % power and discount everything around it. What is genuinely missing is per-process GPU attribution for a competitor comparison, where the renderer living in a browser process separate from the backend makes fair attribution awkward.
  • Anything under real hardware load. All of the above is simulated sources. The numbers should hold — sim drives the same display processor, ring buffers, WebSocket and GUI — but "should" is not "measured".
  • Multi-window cost. Each detached window is a full independent decode; the per-window cost is known analytically (~3.08 MB/s per stream) and has not been profiled at 2 and 3 windows.
