Next task — scrolling the probe map, and seeing a whole shank at once#

Status: open, specified by the operator on 2026-09-02/03, not started. Parked deliberately until the documentation work was finished.

What the operator asked for, in their words#

"ensure the heatmap view allows me to scroll up and down or all the channels of the shank selected are displayed all at once upon selection, or if it's not all channels then just whatever channels are selected we can scroll up and down the shank. The all channels within a shank being viewable also needs to be implemented for the live trace view rather than heatmap as well."

"finish up the scrolling for the probe map view (have a scroll bar added) and the other heatmap view things"

Three deliverables, then:

  1. The Probe Map view gets a scroll bar.
  2. The heatmap, when a shank is selected, shows that shank's channels in full, or lets the shown window be scrolled up and down the shank.
  3. The trace view does the same.

Why the window behaves the way it does today#

All of this lives in webinterface/ChartColumn.js, which resolves a column's band from its stream, its shank and its side filter, and then shows a window of that band:

shownSlots = useDepth ? TRACES : min(TRACES, band.count)      // TRACES is the Ch density setting
maxBottom  = max(bandStart, bandEnd - shownSlots)             // deepest slot the window may start at
slider.min = bandStart
slider.max = maxBottom                                        // ~line 946

So the pager's range is the band minus the window, and it is legitimately zero whenever the selected shank carries no more channels than the column already shows. That is correct behavior that looks exactly like a dead control, and it has already cost time twice: it is written up in LiveDataView.md, and a tutorial capture run on 2026-09-02 died on it when its column happened to be on the NI-DAQ stream, which has eight channels and therefore never pages.

There is a second, band-unaware assignment to the same property near line 1247:

this.slider.max = Config.NUM_CHANNELS - n;

which is computed from the whole probe rather than the column's band. Work out which of the two wins in each code path before changing either. If they can disagree, that is a defect in its own right and worth a test.

The heatmap is not a separate channel model: the same resolution is recorded once as this._hmBand = { start, end, chanAt } and heatmapChannels() reads it, deliberately, so that the heatmap and the traces beside it show the same channels in the same order on the same time base. A change to the window model therefore serves both views if it is made in the band resolution rather than in either renderer — that is the seam to aim for, and keeping it is a requirement, not a preference: the operator asked specifically that a heatmap and its traces be comparable.

The Probe Map is different code: webinterface/ProbeMap.js, plain canvas 2D, with a zoom model rather than a scrollbar. At default zoom the view spans roughly 67 electrode rows in about 560 px on a probe that can carry 5120 electrodes, so most of the map is off-screen with no visible affordance saying so. That is the complaint.

Constraints that are not negotiable#

  • No chart library. The traces are a hand-written WebGL2 renderer and the probe map is canvas 2D, on purpose and after measurement — RendererExperiment.md. Adding a charting or virtual-scroll dependency is the operator's decision, not a convenience.
  • The WebGL context budget is about 16. Showing "all channels at once" must not become one context per anything. Count contexts before and after — DetachedViews.md.
  • Nothing new on the hot path. The 30 kHz path is not touched by the GUI, but per-frame cost is real: a label overlay is DOM, and one element per channel across a full shank is a different order of magnitude from the current window. Measure, do not assume.
  • The frontend is served live from the working tree. Do not edit webinterface/ while a backend or a gate is running; prototype in the scratchpad and apply when nothing is up.
  • The GUI suite gates this. Anything in webinterface/ means python scripts/run_gui_tests.py, and the toolbar or a control changing means user_docs/README.md's toolbar table and user_docs/GUI-Guide.md change in the same commit.

Suggested shape, to be confirmed against the code#

Resolve the three asks into one question — what does this column show, and what can the operator move — and answer it in the band resolution:

  • Decide what "all channels of the shank" means when the shank has more channels than the column has vertical pixels. A 1.0 bank is 384 and a 2.0 shank can be far more; at some density the traces stop being readable and the honest answer is a scrollable window, which is ask 2's own fallback ("or if it's not all channels then just whatever channels are selected we can scroll").
  • Make the pager range meaningful rather than zero when the band fits: either the control disappears, or it says the whole band is shown. A control that is present, enabled and inert is the thing that wasted the time.
  • For the probe map, a real scrollbar bound to the same view state the zoom already maintains, rather than a second view model.

What "done" looks like#

  • On a four-shank 2.0, selecting a shank in a column shows that shank's channels in full, or scrolls through them, in both the trace view and the heatmap, with the two staying on the same channels and the same time base.
  • The probe map has a scroll bar that moves the view and reflects where the view is.
  • New GUI tests, each proved failable by injecting the regression and watching it go red — InvariantTests.md, and tests/gui/ for the existing shape. The invariant worth writing is not "the slider has range on this profile" but a column's pager range is never silently zero while channels remain unseen, which is the class this task is about.
  • user_docs updated in the same commit if anything an operator clicks moved.
  • Full gate green: python scripts/run_all_tests.py --no-browser --fatal.
