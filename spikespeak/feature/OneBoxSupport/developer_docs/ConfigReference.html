Configuration reference — every key, and what is NOT a key#

Written because agents keep relearning this the expensive way, including me: I invented zscore_threshold and lockout_seconds as ripple-detector config keys, wrote a profile around them, and watched a run produce nothing. Neither is a config key. They are runtime parameters, set over the WebSocket, and no amount of staring at YAML would have said so.

Extracted from the call sites (cfg.has_child, cfg[...], getConfigValue<>), then verified a second time against every shipped profile in config/. Where the two disagreed, the code won.

Driving the app headlessly — the command sequences that actually work — is ClosedLoopDriving.md. Read that one before writing a script.

The three rules that cause the most lost time#

1. A config's identity is its internal name: field, not the filename. The directory is scanned and every *.yaml is loaded; selectSource matches on name:. Renaming a file changes nothing; renaming name: breaks every reference to it.

2. Most detection parameters are NOT config keys. The ripple detector reads eleven keys from YAML. Its detection channels, z-score, lockout, quorum, minimum duration and estimation window are runtime-only — there is no way to set them in a profile, and a key you invent is silently ignored. The tables below mark this explicitly for every module.

3. Booleans are parsed from STRINGS, and the two idioms have opposite defaults. getConfigValue<> goes through ryml's read_dec and is integer-only, so it cannot read a YAML true. Every boolean is therefore compared as text, in one of two ways:

idiom true when used by
default-on anything except false / 0 / no / off debug_files, auto_start, stimulation, low_latency
default-off only true / 1 / yes / on enabled (bands), dac_trigger

Both are case-SENSITIVE. TRUE is not true, and under the default-on idiom TRUE reads as true while under default-off it reads as false. If you are adding a key, match the idiom of the processor you are adding it to and say which one you chose.

Read by ProcessorManager when it walks the processors: list and validated (must exist, must be non-empty) by ConfigManager::parseProcs -- NOT read by RippleDetector::configure(), which never touches cfg["name"]. NP1 uses "data.npx.lfp" (native 2.5 kHz hardware LFP, read directly); NP2 uses "data.lfp" (float 30 kHz produced by proc.lfp). input_type string via Utils::toStdString(cfg["input_type"].val()) "float" Selects which CircularBuffer template the input is cast to. EXACTLY the string "int16" binds CircularBuffer (NP1 direct path); ANY other value (including a typo) silently binds CircularBuffer. A mismatch with the actual buffer type is an unchecked static_cast (RippleDetector.cpp:228-234).
decimation_factor int via Utils::getConfigValue() (c4::read_dec, return value DISCARDED) 12; also 12 whenever the parsed value ends up <= 0 (guard at RippleDetector.cpp:126) Every Nth input sample is fed to the filter/detector chain, bringing the input rate down to the fixed 2.5 kHz processing rate. NP1 = 1 (input already 2.5 kHz), NP2 = 12 (30 kHz / 12). Also multiplies into mBaselineGateSamples (RippleDetector.cpp:242-243). Parse semantics: c4::read_dec zeroes the target first and stops at the first non-digit without reporting failure, so "abc" and "-1" both land on 0 and the >0 guard restores 12, while "3.5" silently yields 3.
debug_files bool-as-string; TRUE unless the literal text is "false", "0", "no" or "off" true (constructor member init, RippleDetector.cpp:69) Runtime half of the gate on the per-sample waveform dumps lfp-data.bin / ripple-band-data.bin / envelope-data.bin / ripple-detection-time.bin. CURRENTLY A NO-OP IN ANY SHIPPED BUILD: every write is also gated by the compile-time static constexpr bool DEBUGGING_RIPPLE_DETECTION_FILTERS = false (RippleDetector.cpp:40), so debug_files: true alone creates no files. Setting it true costs nothing until that constexpr is flipped.
auto_start bool-as-string; TRUE unless the literal text is "false", "0", "no" or "off" false (constructor member init, RippleDetector.cpp:80) Whether the module runs on Play. false = stay idle until a GUI/CLI "start" command; true = enable detection + begin baseline training the moment the source starts, and call ensureInputBandEnabled() so a headless run cannot silently read a disabled band.
baseline_gate_seconds double via std::stod() on the raw string (invalid text -> qWarning, keeps default) 6.0 (constructor member init, RippleDetector.cpp:70) Amplifier-settle dead time ignored before baseline collection starts. Converted to pre-decimation input samples as kLfpSamplingRate(2500) * decimation_factor * this, so it means the same wall-clock on NP1 @2.5 kHz and NP2 @30 kHz. Total warm-up to a live threshold = this + the runtime estimation_seconds.
stimulation bool-as-string; TRUE unless the literal text is "false", "0", "no" or "off" false (constructor member init, RippleDetector.cpp:66) -- stimulation is OPT-IN Master gate on the StimulatorClient. When false the client is still constructed (so the toggle works without streaming) but every send path early-returns, so no datagram can physically leave the host. Does NOT arm the stimulator -- arming stays an explicit user action. Runtime-toggleable via the setStimEnabled command. NOTE: no shipped config in config/*.yaml sets this key.
stim_ip string via Utils::toStdString(cfg["stim_ip"].val()) "192.168.1.100" UDP target host for the stimulation server (Raspberry Pi / ESP32). READ ONLY ON THE FIRST configure() -- the whole block is inside if (mStimulatorClient == nullptr) (RippleDetector.cpp:173), and the detector is a registry singleton, so re-configuring for a second profile keeps the first profile's target. Retarget at runtime with the setStimServer command instead. Not set by any shipped config.
stim_port int via Utils::getConfigValue() (c4::read_dec, return value DISCARDED), then cast to quint16 8888 UDP target port for the stimulation server. Same first-configure-only caveat as stim_ip. UNGUARDED parse: unlike decimation_factor there is no >0 fallback, so a non-numeric value (c4::read_dec zeroes the target and bails on the first non-digit) silently becomes port 0. Not set by any shipped config.
dac_trigger bool-as-string, OPPOSITE polarity to the other bools: TRUE only if the text is exactly "true", "1", "yes" or "on"; anything else (including "TRUE") is false false (member init, RippleDetector.hpp:176) Second trigger path: on a detection, also fire the OneBox DAC wave player over USB in addition to the UDP stim server, so the two paths can be compared on the same threshold crossing. Resolved lazily/reflectively at start via resolveDacTrigger() (RippleDetector.cpp:622-636, called from slIpStartProcessor at :898), so it is safe with no OneBox present -- it just warns. Not set by any shipped config.

Changed 2026-08-26 — the source-selection refactor#

The verification notes above are a record of what was checked on the day, and three of their counts are now stale by design. What moved:

  • Two new top-level keys, sim_basestation and sim_probe, tabled above. Top-level key tallies in the notes ("exactly name (28), sources (28), processors (28), sim_variant (16), gui_hidden (2)") predate them and predate three new profiles.
  • gui_hidden is now used deliberately, not just by two headless profiles. Fourteen configs carry it: the two validation profiles it was invented for, plus the twelve probe-specific hardware profiles superseded by OneBox / PXIe / PXIe + NI-DAQ. They stay loadable and CLI-selectable by name so published measurements remain reproducible.
  • proc.npx.display :: inputs is now OPTIONAL. It used to be required, and requiring it is what made a profile probe-specific. Absent, the display binds whatever bands the connected probe actually streams. A declared list still wins.
  • A recordings: entry whose data_name no band provides is SKIPPED, with an INFO line, instead of lazily creating an empty buffer and writing a zero-length .bin plus a sidecar for it.
  • The .raw-precedence flaw the notes below record is fixed. They observe that the probe-type inference in NpInterface.cpp let the .raw branch overwrite expectedProbe unconditionally while the .ap/.lfp branch was guarded, so "a profile declaring both would always be classified NP2". Declaring both is now the normal shape for a hardware profile, and it resolves to eUnknown — meaning probe-agnostic, expect nothing, warn about nothing, which is the honest answer for a profile that serves either probe.

Five call sites share this idiom: NpInterface.cpp:952, SimDataSource.cpp:280 and :297, SimData2Source.cpp:229 and :246. (A sixth instance of the same idiom, inverted, lives in Configuration.cpp:110 for gui_hidden.) - Three different parsers are in use for numbers across these six sources -- std::stod in try/catch (warn + keep default), ryml::read_dec via getConfigValue (digits-only, zeroes-then-partial-parses, no warning), and bare ryml operator>> (aborts via the default callback). Only the first is actually safe. adc_voltage_range is the sole user of the third. - In NpInterface.cpp:971-982 the probe-type inference gives ".raw" unconditional precedence: the ".raw" branch overwrites expectedProbe every time, while the ".ap"/".lfp" branch is guarded by expectedProbe == eUnknown. A profile declaring both would always be classified NP2. - Order dependency in source.npx.simadc: num_channels is parsed first (:173) and its value bounds the sync_channel / grounded_channel clamps (:189, :194). Fixed in code, so YAML key ordering does not matter -- but a narrow num_channels silently rejects an otherwise valid sync_channel. Adding a key#

  1. Add the cfg.has_child(...) read in the processor's configure(), with a default that preserves current behaviour when the key is absent. Every shipped profile predates your key.
  2. Pick a boolean idiom from the table above and say which, in a comment.
  3. getConfigValue<int> is the ONLY numeric helper, and it is integer-only. Doubles go through std::stod on the raw string; floats written as 6.0 become 6 under getConfigValue<int> without complaint.
  4. A configure() that returns false aborts the whole graph — the source will not connect. Use it only for "this profile is wrong". A missing device, a missing output, an absent optional feature: return true and report degraded state instead. See AudioProcessor::configure().
  5. Add the key to a shipped profile only if it changes that profile's behaviour. A key present in YAML that no code reads is worse than absent — it reads as configuration and is decoration.
