Control CLI — headless command interface#

python/spikespeak_cli.py drives a running SpikesPeak backend over its WebSocket (ws://HOST:1234) — the same socket the browser uses — so the whole acquire + record flow can run with no GUI clicking. It exists so tests (and agents) can launch, configure, record, and verify without a human at the mouse; an open browser mirrors the session live (source dropdown, play button, red Record button all reflect the CLI's actions).

Zero dependencies: a tiny RFC-6455 client on the Python standard library only.

There are two headless interfaces, and this page covers both: 1. the built-in console command interface — type commands at the backend's own console (no Python, no second process): a minimal connect/play/pause/disconnect/quit surface (GitHub issue #6, "command the server through the console"), and 2. the WebSocket control CLI (python/spikespeak_cli.py) — the full, scriptable, remote-capable interface (list/select/record/…) that every ripple_tools/ script is built on.

Use the console for a quick local poke; use the WebSocket CLI for anything scripted, recorded, or remote.

Built-in console command interface (type at the backend's console)#

The backend reads commands typed directly into the console it runs in (src/core/KeyboardListener.cpp → MainController::handleTextCommand) — the original "command through the console" path. No Python, no WebSocket. Confirmed working on Windows (2026-07-22) — previously Linux-only (issue #6): each typed line drives MainController, and the app exits 0 on quit.

How the console is attached - Windows — the backend is a GUI-subsystem exe, so at startup setupWindowsConsole() (main.cpp) does AttachConsole(ATTACH_PARENT_PROCESS) (inherit the console of the terminal / Qt Creator that launched it) or AllocConsole() (a fresh one), then reopens stdin/stdout/stderr to CONIN$/CONOUT$. Launch it from a terminal to type into it. - Linux — it reads the controlling terminal's stdin directly. - Headless (stdin closed / redirected) — KeyboardListener detects the closed stdin, logs console commands disabled, and stops reading. It does not quit; drive the app with the WebSocket CLI and quit from there. This is the state under --no-browser with no attached console.

The commands — the complete set (this is a deliberately minimal control surface):

type this effect (MainController)
connect <source name> connect that source; everything after connect is the config name: verbatim — no quotes, spaces allowed (connect Simulated Data, connect NPX 1.0 with NI-DAQ)
play start streaming
pause pause streaming
disconnect disconnect the source (auto-pauses first if still streaming)
quit / exit shut the server down (once MainController::isReadyToQuit())
(blank line) ignored; (anything else) → logged [MainController] Unrecognized command

No list, record, waitready, or probe-map over the console, and connect has no discovery — you must already know the source name: (from config/*.yaml or the WebSocket CLI's list). For recording, readiness-waiting, scripting, or remote control, use the WebSocket CLI below.

A console session looks like this (the [MainController] lines are the backend confirming each command):

Listening for console input...
> connect Simulated Data
[MainController] Source connected and not streaming
> play
Attempting to stream from source
[MainController] All sources have started
> pause
[MainController] Source paused
> disconnect
[MainController] Source disconnected and set to none
> quit
Shutdown initiated

WebSocket control CLI (spikespeak_cli.py) — command reference#

CLI command over the wire (0x1000 JSON) backend action
list {command:"listConfigs"} replies configList with every profile name
select "<name>" {command:"selectSource", value} onSourceSelection — full connect + wiring
waitready [timeout_s] (client-side) blocks until the source is ready (see readiness signal below)
probemap <default\|bank0\|bank1\|bank2\|PATH.imro> {command:"setProbeMap", value} IDataSource::applyNamedMap (NPX); NP1 bank presets validated
play / pause {command:"setPlaying", value} start / pause streaming
record <dir> <name> {command:"setRecording", value:true, dir, name} fan out to every recorder → files in <dir>/<name>/
stop {command:"setRecording", value:false} stop recording (streaming continues)
disconnect {command:"Disconnect", value:true} disconnect the source
quit {command:"quit"} shut the whole server down (QApplication::quit)
sleep <s>, help, exit — client-side (exit leaves the CLI, not the server)

Run modes: interactive REPL (python spikespeak_cli.py), one-shot (python spikespeak_cli.py list), scripted (--script "a; b; c"), or commands on stdin. --host / --port target a remote backend.

How the GUI mirrors a CLI session#

Each state-changing command broadcasts a state event to all clients; the browser reflects it in its toolbar without re-sending the command (main.js reflect* + NetworkClient handlers):

event emitted from browser reflects
stateSource (name) onSourceSelection / disconnect source dropdown + selectedSource
statePlaying ("1"/"0") setPlaying play button icon/green + Record enable
stateRecording (value,name) CLI setRecording path red Record button + flashing indicator
configList, serverQuitting listConfigs / quit CLI prints them; browser logs/status

stateSource is broadcast before the deviceReady connect result, so a watching browser records the source name in time for its QWebChannel bind (keyed on that name).

Recording/IMRO get this JSON command path in addition to their QWebChannel path (the GUI still uses QWebChannel). That small duplication is deliberate: it keeps the CLI QWebChannel-free. See ModuleCommunication.md.

Running the backend headless#

Linux (the current dev path — sim only, no hardware): just run the binary. On this box the Qt Creator build dir is build/Desktop_Qt_6_11_1_Release/ (Qt 6.11.1), so:

cd build/Desktop_Qt_6_11_1_Release
LD_LIBRARY_PATH=~/Qt/6.11.1/gcc_64/lib QT_QPA_PLATFORM=offscreen ./bin/SpikesPeak --no-browser &

QT_QPA_PLATFORM=offscreen is needed because the app links WebEngineWidgets/Widgets and there's no display; LD_LIBRARY_PATH points at the non-system Qt. There are no hardware DLLs to stage; the CLI drives it the same way (python spikespeak_cli.py --host localhost …), and the source to select is "Simulated Data". See SimDataLinux.md.

Windows (the historical hardware box) — runtime DLLs: the exe is normally launched by Qt Creator, which sets up the runtime environment. To launch it standalone (e.g. from a script), these directories must be on PATH or it exits instantly at the loader (before Qt) with no message — its non-system imports are Qt6*, NeuropixAPI_x64_4_1_3.dll, hdf5.dll/hdf5_cpp.dll, nicaiu.dll:

$env:PATH = "C:\Qt\6.7.3\msvc2019_64\bin;" +                                              # Qt runtime
            "C:\Users\BIOEl\Documents\Code\SpikesPeak\external\neuropixels\api\lib64\v4;" + # NeuropixAPI
            $env:PATH
# HDF5 (C:\Program Files\HDF_Group\HDF5\1.14.6\bin) is already on the system PATH; nicaiu.dll ships with the NI driver.
Start-Process -FilePath "...\build-...\bin\SpikesPeak.exe" -WorkingDirectory "...\bin" `
    -ArgumentList "--no-browser" -WindowStyle Hidden

Pass --no-browser (or --nobrowser) for automated runs: the app starts the HTTP + WebSocket servers but does not open any browser, so nothing is left open when the test ends. Open http://localhost:8234 yourself if you want to watch. Launched without a console, KeyboardListener detects the closed stdin and disables console input (instead of spinning) — the app keeps serving; drive it with the CLI and shut down with quit.

Browser launch (interactive runs). With no flag, running the executable now opens the UI in a dedicated browser app-window — a separate browser session in its own chromeless window, not a tab in your normal browsing. It uses a Chromium-family browser (brave-browser/chrome/chromium/edge, first one found) in --app mode with an isolated persistent profile at ~/.spikespeak/browser-profile (so window size/zoom persist and your normal profile is untouched). Closing that window drops the last WebSocket client, so the backend's grace timer shuts the server down shortly after — the window is the app's lifetime. Flags: --tab (a.k.a. --system-browser) opens a normal tab in your default browser instead (legacy behavior); if no Chromium-family browser is found it falls back to a tab automatically. main.cpp launchDedicatedBrowser().

Readiness signal + the correct teardown order#

  • Readiness. The NPX + NI-DAQ connect blocks the main thread for several seconds, so events only flush once it returns. When the probe is detected the backend emits guiStatus: "Found Neuropixels 1.0 Probe" (deferred from NeuropixelsSource, alongside deviceReady). waitready blocks on either — use it instead of guessing a sleep after select.
  • Teardown order matters. handleDisconnectRequest refuses to disconnect while the source is acquiring, and closing the probe mid-stream leaves the hardware in a bad state. The correct order is stop → pause → disconnect → quit. As a safety net, WebSocketServer::teardownSource() (used by both disconnect and quit) now pauses first if still streaming, so disconnect/quit are safe even if you forget to pause — but a record test should still stop first for a clean file.

Example: a full headless record test (validated on live hardware)#

python spikespeak_cli.py --script \
  "select 'NPX 1.0 with NI-DAQ'; waitready 40; probemap default; sleep 2; play; sleep 3; \
   record /path/to/RecordingTests test2; sleep 15; stop; sleep 2; pause; sleep 2; disconnect; sleep 3; quit"
# then plot + verify (saves sync.png + channels.png into the recording folder):
python examples/plot_recording.py /path/to/RecordingTests/test2

This exact flow was validated on the live rig: probe found via waitready, 15.4 s recorded (electrodes [1,192,196] @30k/2.5k + 8 NI-DAQ @40k), clean teardown, and the sync plot recovered a real +10.2 ppm clock drift between the NI-DAQ and NPX clocks (0.012 ms residual). Recording is backend-owned, so it keeps writing even if the CLI drops; when the last client disconnects an auto-shutdown grace timer starts.

When the user asks for a "Recording Test", run the canonical procedure in RecordingTest.md (this flow + plot_recording.py, and what the user looks for).

Tutorial — from zero to a recorded clip (WebSocket CLI)#

A first end-to-end run, no GUI. Uses a sim source, so no hardware is needed.

  1. Launch the backend headless (keeps serving; opens no browser): bash python run_spikespeak.py --no-browser # add --offscreen if there is no display at all
  2. See what sources exist — the names printed are the config name: fields you pass to select: bash python python/spikespeak_cli.py list

    ⚠️ A bare list connects then disconnects, and the backend auto-quits ~2 s after the last WebSocket client leaves. So for a multi-step session, do it all inside one connected --script (below), or keep a browser open on the side to hold the server up.

  3. Connect → wait until ready → stream → record 10 s → tear down, all in one connected script: bash python python/spikespeak_cli.py --script \ "select 'Simulated Data'; waitready 40; play; sleep 2; \ record RecordingTests demo1; sleep 10; stop; pause; disconnect; quit" (waitready blocks on the source's readiness signal instead of guessing a sleep; the stop → pause → disconnect → quit order is the safe teardown — see above.)
  4. Verify the files (they land in RecordingTests/demo1/, relative to the backend's working dir): bash python examples/plot_recording.py RecordingTests/demo1

More examples#

# interactive REPL — type commands one at a time, server stays up until you quit
python python/spikespeak_cli.py
>>> list
>>> select "Simulated Data"
>>> waitready 40
>>> play
>>> pause
>>> quit

# one-shot (connect, run the single command, exit) — quick config dump
python python/spikespeak_cli.py list

# stream only (no recording), hold 30 s, then stop cleanly
python python/spikespeak_cli.py --script \
  "select 'Simulated Data'; waitready 40; play; sleep 30; pause; disconnect; quit"

# apply an NP1 probe-map bank preset before streaming (real NPX 1.0)
python python/spikespeak_cli.py --script \
  "select 'NPX 1.0'; waitready 40; probemap bank1; play; sleep 5; pause; disconnect; quit"

# drive a backend running on another machine
python python/spikespeak_cli.py --host 192.168.1.50 --port 1234 list

Ripple Detection module commands#

The CLI drives proc.rippledetector too, via ripple <subcommand> — each maps to a {"command":"ripple","action":…} WS text frame, the same contract the browser dock uses (RippleGui.md §2). Every subcommand except arm/disarm is applied on the detector's worker thread, which only runs while streaming — so play first. arm/disarm run on the main thread (RippleDetector::setStimArmed) and work even when paused / not streaming.

CLI action sent payload effect
ripple channels <e…> setChannels {electrodes:[int]} set detection electrodes (merge — keeps trained ones, trains only-new)
ripple param <name> <v> setParam {name,value} one of estimation_seconds, min_duration_seconds, lockout_seconds, coincidence_window_seconds, quorum_count
ripple z <electrode> <v> setZ {electrode,z} per-channel z-score threshold (live-editable while running)
ripple start / ripple pause start / pause {} first start trains then detects; a start after pause resumes (baselines kept)
ripple retrain retrain {} clear baselines, re-estimate μ/σ
ripple stimserver <ip> setStimServer {ip} retarget the StimulatorClient
ripple stimparams <phase_us> <gap_us> <freq_hz> <total_ms> setStimParams {…} biphasic pulse-train params (clamped to hardware ranges)
ripple testfire testFire {} one manual pulse (arm + fire, no detection)
ripple arm / ripple disarm armStim / disarmStim {} main-thread — arm / disarm the stim server even when NOT streaming
ripple enable <0\|1> enable {enabled} legacy bool toggle (maps to start/pause)
ripple raw '<json>' (verbatim) your object escape hatch: sends {command:"ripple", …your fields}

Events the reader prints back: rippleState (full snapshot after every command), rippleTraining (progress %), rippleBaseline (μ/σ/threshold per channel), rippleDetected (k/N quorum + electrodes + ts). rippleEnvelope (~30–60 Hz) is drained silently so it doesn't flood the terminal.

Worked example (verified headless, sim, 2026-07-22 — fires detections in ~10 s):

python python/spikespeak_cli.py --script \
  "select 'Latency Bench NP1 (baseline delivery)'; waitready 30; play; sleep 2; \
   ripple channels 0 10 20; ripple z 0 2; ripple z 10 2; ripple z 20 2; \
   ripple param estimation_seconds 3; ripple param quorum_count 2; \
   ripple start; sleep 18; ripple pause; disconnect; quit"

It prints the training progress, the three baselines, then detections such as [ripple ● DETECTED] 2/3 ch [0, 10] ts=15.73. arm/disarm may go before play. (Any ripple-capable source works; this benchmark sim just injects frequent ripples for a fast demo.)
