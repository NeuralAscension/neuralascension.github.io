NEXT TASK (low priority) — NI-DAQ drops a trailing sync pulse vs the NPX#

Status: open follow-up, low priority. The analysis side is already handled (the sync aligner now defaults to match="auto", which survives a pulse-count mismatch — see RippleClosedLoopAnalysis.md). This note is only about the capture asymmetry, which the user considers not important and possibly not controllable.

Observation#

In RecordingTests/np2_4channel_3required (2026-07-16), the shared ~1 Hz TTL sync train was captured as: - NPX sync field: 79 pulses (0.342 … 78.343 s) - NI-DAQ ai0: 78 pulses (0.545 … 77.545 s)

The NI-DAQ recording starts ~0.2 s later and ends ~0.8 s earlier than the NPX — it misses the last NPX sync pulse (the NI-DAQ task stopped a beat before the probe stream). Tests 1 & 2 the same day captured equal counts (76=76, 80=80), so this is intermittent, not systematic.

Why it (used to) matter#

A count mismatch + the old match="end" sync default silently shifted the whole NI-DAQ→NPX map by one sync period (2 ripple cycles) and produced fake "orphan" stim pulses / wrong closed-loop latency. That is already fixed in python/spikespeak_postprocess/sync.py (match="auto"). This to-do is only about eliminating the asymmetry at the source, if it's ever deemed worthwhile.

What a future agent could check (if pursued)#

  1. Stop-order timing. Look at how the NI-DAQ task is stopped vs the NPX stream on record-stop / disconnect (src/modules/nidaq/NiDaqInterface.cpp stopAcq/slStopAcquiringData vs the NPX teardown). If the NI-DAQ DAQmxStopTask fires slightly before the probe stops, the last shared sync edge lands after the NI-DAQ window → dropped. A small stop-order tweak (stop the probe first, or drain one more NI-DAQ block) would make the capture symmetric.
  2. Start jitter. The NI-DAQ started ~0.2 s after the NPX here — confirm start-order and whether the first sync edge is reliably inside both windows.
  3. Guard rail (cheap, high value): have the recorder/analysis log a warning when the NPX and NI-DAQ captured different sync-pulse counts, so a mismatch is visible immediately rather than discovered by a garbled latency. (align_timestamps already has a — insufficient — interval-agreement warning; add an explicit len(ref_edges) != len(tgt_edges) note.)

Do NOT#

  • Do not revert the match="auto" sync default — it's the robust fix and handles this case correctly.
  • Do not treat this as blocking; the user has said it isn't important or necessarily controllable.
