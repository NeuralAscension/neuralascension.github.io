SpikesPeak — Neuropixels 2.0 support#

The NP2.0 probe: variants, geometry, the electrode↔channel wiring, the microvolt scale, and the four real-hardware streaming bugs that cost a session. The canonical hardware reference is the vendored OpenEphys plugin at Source-OpenEphys-Neuropixels-PXI/ (read it before writing hardware code).

Background: NP1.0 model + IMRO is in [../SpikesPeak_Status.md]; the live waveform view (which is already wired for 4 shanks) is in [LiveDataView.md].

Current state (2026-08-31)#

NP2.0 multishank is at parity with the 1.0 path and hardware-validated. Default map, hardware apply, the 4-shank probe-map editor, record-channel selection, the simulated 2.0 source, derived LFP, ripple detection and the full closed loop all work on a real probe. The dated write-up and its verification are §7, and the four live-hardware streaming bugs in that section are the most expensive content on this page — read them before touching acquisition start/stop, ring indices, the display timebin, or NP2 trace baselining.

The one real remaining gap is single-shank detection (§5): a real NP2.0 single-shank probe is not detected at all — NP200x resolves to eUnknown. Multishank is unaffected.

This page was originally a task runbook ("what is stubbed, and the order to build it"). All three of those gaps closed on 2026-07-06; what the runbook asked for is now §4, History, kept because the reasoning still applies to the next probe generation.

1. The probe variants#

Probe identity is the ProbeType enum — 1 = NP1.0, 2 = NP2.0 single-shank, 3 = NP2.0 multishank — set by NeuropixelsSource::discoverProbeHardware() from the part number the probe reports on open, and sent verbatim to the GUI, where ImroManager.probeGen() branches on it.

There is no detectProbe(). Earlier revisions of this page named one; grep detectProbe src/ finds only detectProbePort(), which is a different function — it returns which port carries a headstage, not which probe is on it.

RULE: never hardcode or pattern-match probeIdStr. It is the part-resolved imro type id, so the shipping 4-shank part reports 2013/2014 and only the prototypes report 24/21. Writing "24" for an NP2013 tells a reader it has a 14-bit gain-80 probe when it has a 12-bit gain-100 one — a 3.2× error in any microvolt reconstructed from the IMRO (#65; see Npx2Scale.hpp, and the guard comment in NpInterface.cpp's loadDefaultImro). Resolve it from the part number (SP::npx2Electrical(partNumber).imroTypeId), always.

Variant imro type id (informational) product # shanks electrodes
eNpx1 "0" / PRB* / NP1* — 1 960
eNpx2SingleShank 2003 / 2004 (commercial) · 21 (NP2000 prototype) NP200x 1 1280
eNpx2MultiShank 2013 / 2014 (commercial) · 24 (NP2010 prototype) NP201/NP202 4 1280/shank

The eNpx2SingleShank row is a parser capability, not a detection path. Nothing assigns that enum from hardware — see §5.

NP2 geometry (used by the live view): within-shank electrode e → column e&1 (even=Left, odd=Right), row e>>1. 384 read-out channels as on NP1. ⚠️ The electrode↔channel wiring is NOT NP1's modulo-384: within a shank the bank = electrode_local / 384 sets the range, but the channel for an electrode comes from a per-shank block-permutation lookup table. The exact tables, geometry, np_* call sequence, and IMRO format are documented in OpenEphys-NP2-Reference.md (distilled from the vendored plugin) — read it before writing the default map / apply / editor.

Counts → microvolts, and where the gain comes from#

NP2.0 is a fixed-gain probe: np_setGain is never called, so the scale is a property of the part, not of the applied map. Npx2Scale.hpp resolves it from the probe's own part number:

part ADC bits gain µV/count imro type id
NP2000 / PRB2_1_* (prototype, 1 shank) 14 80 0.7629 21
NP2010 / PRB2_4_* (prototype, 4 shank) 14 80 0.7629 24
NP2003 / NP2004 (commercial, 1 shank) 12 100 2.4414 2003 / 2004
NP2013 / NP2014 (commercial, 4 shank) 12 100 2.4414 2013 / 2014

That is a 3.2× spread between prototype and commercial, which is why guessing is not an option and why an unrecognized part number falls back to the commercial figure and writes a reason saying it did.

The gain was 84 until 2026-08-28 — a value belonging to no variant. imec's manual and spec sheet both say 100 for the shipping probe, and SpikeGLX documents the same fixed-by-type gains, so every NP2.0 microvolt figure was 1.190× too high (#65). Counts on disk were never touched, so old recordings are fully recoverable. One disagreement is recorded rather than smoothed over: Open Ephys uses 80 for every 2.0; we follow imec and SpikeGLX. The recorded side of this — which sidecar key carries the factor, and its provenance — is Recording.md §2b.

2. IMRO entry formats (all parsed/serialized already)#

From parseImroContent and serializeImro (src/modules/neuropixels/NpInterface.cpp):

NP1            (channelId bank refId apGain lfGain apFilter)     # 6 fields
NP2 multishank (channelId shank bank refId electrodeId)         # 5 fields   <-- Task 3 focus
NP2 singleshank(channelId bank refId electrodeId)               # 4 fields ; shank implicitly 0, bank=bitmask

NP2 has no per-channel gain or AP-filter fields (fixed-gain probe) — that's the big API difference from NP1.

4. History — what this page asked for, and why (2026-07-06)#

This page began as a task runbook. Its three gaps and its parity list are all closed (§7); the detail is kept only where the reasoning outlives the task.

The three gaps, in one line each. loadDefaultImro built no channels for NP2 (a connected probe yielded an empty map, so the editor and the live view had nothing to draw); applyImroToHardware had no NP2 branch; and ImroManager.js's renderElectrodeMap NP2 else-branch drew a static dot grid with no selection. All three are now built — §7 says what replaced each. The call order to mirror is in OpenEphys/Probes/Neuropixels2.cpp (selectElectrodes / setAllReferences / writeProbeConfiguration) and the geometry in Probes/Geometry.cpp.

The stub code that used to be printed here has been DELETED, deliberately. It contained mCurrentImro.probeIdStr = "24"; as the thing to build on — which is now precisely what NpInterface.cpp warns against, because "24" is the 4-shank prototype and using it for a commercial probe is a 3.2× error in any reconstructed microvolt (§1, #65). A newcomer following a runbook reintroduces the bug the repo spent a session removing, and the runbook is the last place anyone looks for the cause. The rule survives, the snippet does not.

The parity requirement, which is the part still worth having. NP2.0 was not allowed to merely stream: it had to work with everything already built for NP1.0 — the record-channel picker (Recording.md §7), a simulated 2.0 source of its own class writing data.npx.raw (NP2 has one raw buffer, not ap/lfp), a derived LFP band via proc.lfp because NP2 has no hardware LFP, the per-session recorder channel override, and the simulated NI-DAQ. The generalizable form: a new probe generation reaches parity with the infrastructure, not with "it streams" — and the parts that break are the ones that encode NP1 assumptions (modulo-384 electrode↔channel, the reserved channel 191, one shank, a hardware LFP band). Every one of those bit us.

5. The one gap that is still open — NP2.0 single-shank is not detected#

discoverProbeHardware() matches part numbers, and its NP200* branch assigns ProbeType::eUnknown:

// 2.0 Single-Shank probes usually start with "NP200"
else if (productNum.startsWith("NP200"))
{
    // Replace with your single-shank enum if you have one!
    mProbeType = ProbeType::eUnknown;
}

So plugging in a real NP2.0 single-shank does not produce a working session: the type never becomes eNpx2SingleShank, and everything downstream that branches on the type — default map, hardware apply, editor, live-view geometry — takes the unknown path.

What already exists: the 4-field single-shank IMRO format parses and serializes, the enum is defined, and several branches (parseImroContent, updateImroFromJson, bank validation at 15 for the 4-bit electrode bitmask) already handle it. What is missing is the detection assignment plus the NP2-single-shank halves of loadDefaultImro and applyImroToHardware, and a single-shank geometry in the editor. Npx2Scale.hpp already resolves NP2003/NP2004 correctly, so the microvolt scale is not part of this.

Nobody has assigned this, and no single-shank probe has been on this rig. It is listed here as a known gap rather than tabled as work in progress, because the difference matters to whoever picks it up.

Refinements (2026-07-07) — see SpikesPeak_Status.md §17–§18#

  • Mapping VERIFIED vs the official manual (Neuropixels_2-0_User_Manual_V1-0-6/): Np2::electrodeToChannel matches all 5,120 rows of the Electrode-Channel .xlsx (Figs 35+37). The electrode number is a physical site (row=e>>1 = depth, col=e&1, El0=tip); the channel number is the amplifier index with no physical meaning; the .xlsx channel→electrode is deliberately SCRAMBLED (the block permutation).

  • .imro / map VALIDATION = Np2::isConsistentEntry (in Npx.hpp): rejects any entry where channel ≠ electrodeToChannel(shank,electrode), bank ≠ electrode/384, out-of-range, or duplicate channel — in parseImroContent + updateImroFromJson (both hardware NpInterface.cpp and sim SimData2Source.cpp).
  • Probe-type mismatch dialog: NeuropixelsSource::initDataSource infers the profile's expected probe from its output data and emits sigGuiStatus(...,"probe-mismatch") → main.js showProbeMismatch modal.
  • Per-shank rectangles + tips in the NP2 editor (ImroManager.js setShankVisuals / np2Shafts/np2Tips).
  • Record-mode selection is restricted to the applied (streamable) electrodes; edit-mode clicks always yield a valid map (each of 384 channels reads one electrode). GUI test harness: python/tools/gui_scenarios.py.

Real-2.0-hardware streaming robustness (2026-07-15/16 — built + VERIFIED on a live NP2 multishank)#

First real 2.0 multishank plugged into the Windows rig. Streaming worked on a fresh connect but pause/play and pick-channels (Bank apply) froze the live view (IMEC blue LED = FPGA streaming but host not reading, or display frozen while the FIFO stayed healthy). Four independent bugs, all now fixed + verified live (CDP-driven visible browser, 6/6 interleaved pause/play + Bank 0/1/2/3 applies advancing, 0 FIFO stalls): 1. FPGA-read stall on (re)play — NeuropixelsSource::startAcq fired np_setSWTrigger immediately after mWorkerThread->start(), i.e. BEFORE the worker's read loop existed → the FPGA streamed into a FIFO nobody drained (blue LED). Now the trigger is gated on the worker's sigDswStartedAcquiring (QueuedConnection, fires after mTimer->start()), so the reader is always up first. A throttled FIFO diagnostic ([Npx2MSProbe] FIFO: read N | available M | headroom H … STALL) makes any recurrence visible in the log. 2. Ring desync after a worker recreate — applyMapToHardware() does stopAcq()→write→startAcq(), which destroys + recreates the source worker. Npx2MSProbe started mCurrWriteInd = 0, so the new worker wrote at ring position 0 while the persistent consumers (display/ripple/LFP) kept reading at the old high index → stale/garbage data. Npx1Probe already seeds its write index from getTotalSamplesAdded(); NP2 was missing it. Added the same seed to the Npx2MSProbe ctor (no-op on first worker). 3. Display frozen after a reconfigure — np_setSWTrigger re-firing on a map apply RESETS the probe packet Timestamp toward 0, but DisplayProcessor binned by that hardware timestamp with a latched gotFirstTimestamp, so the new low timestamps never exceeded the old (high) timebinEndTimestamp → advanceBucket() never ran, no frames emitted (samples consumed but never shown). slDpGenerateDisplayData now detects the >1-bin backwards jump and re-baselines the timebin, so display resumes automatically with no manual pause/play. (Pause/play had hidden this by rebuilding the processor state — and only recovered once fix #2 also landed.) Shared with NP1. 4. NP2 raw traces drift off-screen — the raw wideband carries a large, slowly-drifting electrode DC offset; the probe display path drew samples straight at yOffset+sample (0-centered assumption, true only for the hardware-high-passed AP band), so the trace drifted below its row within minutes → blank view. NetworkClient.js now AC-couples streamId === 'raw' (slow min/max-midpoint baseline, same tracker as the NI-DAQ path). Frontend-only. NP1 ap/lfp untouched. (This line said "clamped to the row band" until 2026-09-01; the code says the opposite and explains why — the baseline is seeded to the first sample so there is no initial transient to clip, and a real driven signal such as a saline ripple must be drawn at true amplitude rather than clipped flat. Raise the µV scale if it is taller than a row.) - Files: NpInterface.cpp (#1 startAcq gate + FIFO log; #2 Npx2MSProbe ctor seed), DisplayProcessor.cpp (#3 timebin re-baseline), webinterface/NetworkClient.js (#4). The three C++ fixes need build.bat --no-pause (./build.sh on Linux/macOS); #4 needs no build at all — since 2026-08-26 the exe resolves its web root as <exe>/../webinterface, which is the repo's own copy, so editing NetworkClient.js is an edit plus a hard reload (Ctrl+Shift+R). (This line said the frontend was "deployed by the build" until 2026-09-01, which was true when the fix landed and has not been since. An older version named a build-Desktop_…-Release tree and rebuild.bat; rebuild.bat still finds such a tree if you have one, but its own comment says nothing creates them any more.) Verified by CDP screenshot at the time (screenshots are transient — see the screenshot policy in README.md).
