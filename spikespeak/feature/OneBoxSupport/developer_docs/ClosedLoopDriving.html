Driving SpikesPeak headlessly — the sequences that actually work#

Every agent that has driven this rig has rediscovered the same few facts the expensive way. This is those facts. If you are about to write a script that selects a source and starts ripple detection, read this first; it will save you two failed runs, which is what it cost me on 2026-08-24.

Config keys — what you can put in a profile, and the much longer list of what you cannot — are in ConfigReference.md. This page is about the commands.

1. Use ripple_tools/rig.py. Do not hand-roll the WebSocket.#

It already exists, every closed-loop script in the repo uses it, and it knows the ordering rules below. Hand-rolling the frames is how you end up debugging your own harness instead of the rig.

import sys, os
sys.path.insert(0, os.path.join(REPO, "ripple_tools"))
from rig import Rig

rig = Rig(capture_path="events.jsonl")   # background reader thread; every event captured
rig.select("Simulated NPX 2.0 Ripples")
rig.wait_ready(timeout=45)
rig.play()

Rig maintains live state as events arrive — rig.baselines, rig.detections, rig.latency, rig.stim_fired — so you assert on what the backend said, not on what you hope it did.

2. The detection sequence, in the only order that works#

rig.set_channels([100, 150, 200]); time.sleep(0.6)   # ELECTRODES, not read-out channels
for e in electrodes:
    rig.set_z(e, 5.0)
rig.set_param("quorum_count", 1)
rig.set_param("estimation_seconds", 10.0)
rig.set_param("lockout_seconds", 0.2)
rig.retrain()            # <-- THE STEP EVERYONE MISSES
rig.start()
rig.wait_baselines(electrodes, timeout=40)           # block until every channel has a threshold

retrain() is not optional. set_channels() does not begin baseline collection. Without retrain() the detector sits with no threshold, forever, emitting nothing — and because it emits nothing, it looks exactly like a detector that is working on a quiet signal. I lost two runs to this before reading ripple_tools/run_np2_tests.py, which has had the correct sequence all along.

Then wait for baselines rather than sleeping. Training takes baseline_gate_seconds (settle) plus estimation_seconds (collection), both measured in acquired samples, so wall-clock is only a prediction. wait_baselines() returns when the thresholds actually exist.

How to tell "not training" from "trained but quiet"#

They look identical from the outside and have completely different causes.

symptom meaning
no rippleBaseline, no rippleEnvelope the detector is receiving no samples. Its input band is not producing, or the source is not streaming. Not a threshold problem.
no rippleBaseline, envelopes arriving training in progress, or retrain() was never called
baselines present, no rippleDetected trained and quiet — z is too high for this signal

rippleEnvelope is the vital sign. Zero of them means look upstream, not at z.

3. Stimulation#

rig.set_stim_params(phase_us=60, gap_us=10, freq_hz=1, total_ms=1)   # ONE biphasic pulse
rig.set_stim_enabled(True)     # master gate: without it no datagram can leave the host
rig.arm_stim(True)             # the Pi must be ARMED before it will fire

Three separate things, and all three are required. stimulation gates whether a datagram can be sent at all; arming is what the Pi needs before a fire does anything; the params shape the pulse. A 1 ms train at 1 Hz is a single pulse — use that when you want one pulse per detection rather than a burst.

rig.test_fire() fires without a detection, which is the fastest way to prove the whole path end to end before trusting a closed-loop number.

3a. Where recordings land#

rig.record(out_dir, name) does not write into out_dir. It creates out_dir/name/ and writes there, one .bin plus a .bin.json sidecar per band, each stamped with the start time:

RecordingTests/2026-08-25_trigger_ab/          <- what you passed as out_dir
  trigger_ab_ripple.json                       <- the ripple sidecar, written at record START
  trigger_ab/                                  <- what you passed as name
    trigger_ab_adc_20260825_095710.bin
    trigger_ab_adc_20260825_095710.bin.json    <- frame layout lives HERE
    trigger_ab_raw_20260825_095710.bin
    trigger_ab_raw_20260825_095710.bin.json

Two consequences worth knowing before you write an analysis script:

  • Look one level down. Globbing out_dir/*.bin.json finds nothing and the failure surfaces as an IndexError on an empty list, well away from the cause.
  • Pick the NEWEST sidecar, not the first alphabetically. A second run into the same name adds a second timestamped pair beside the first. Sorting by name and taking [0] silently analyses the OLD recording -- which is exactly what happened on 2026-08-25, reporting a 5 s smoke test's n=104 as though it were the 1000-detection run. Sort by mtime.

The sidecar is the authority on how to read the .bin: it carries frame.bytes, the header layout, payload_dtype, num_channels and sample_rate_hz. Do not hard-code a stride.

meta = json.load(open(newest_sidecar))
fb, nch = meta["frame"]["bytes"], meta["num_channels"]
raw = np.fromfile(bin_path, dtype=np.uint8)
n = len(raw) // fb
frames = raw[: n * fb].reshape(n, fb)
data = frames[:, meta["frame"]["header_bytes"]:].copy().view(np.int16).reshape(n, nch)

4. Where the logs are#

The backend writes output.log to its WORKING DIRECTORY, not next to the binary. If you launch it with cwd=REPO the log is REPO/output.log, and the copy in build-*/bin/ is whatever was left there by an earlier session.

I spent twenty minutes analysing a stale bin/output.log from six hours earlier and concluded the detector had bound to the wrong band on an NP2 probe. It had not. Check the mtime before you trust a log.

The launcher's own stdout (Press any key to continue . . .) is not the application log — that is run_spikespeak.bat pausing. Seeing only that line means the backend exited.

5. Harness rules, learned by losing runs to each#

  • Write results incrementally. A run that collects for fifteen minutes and writes at the end loses everything to a socket error during teardown. Stream to a .jsonl and flush.
  • Verify parameters took; do not assume. Every detector command is queued to its thread. Read the values back from rippleState and refuse to collect if they did not land.
  • Run unbuffered (python -u) or you are blind for the whole run and cannot tell slow from hung.
  • Match real keys, not substrings. if "auto_start" not in text is true even when the file only mentions auto_start in a comment — which is exactly what the shipped OneBox profile does. Use re.search(r"^\s+auto_start\s*:", text, re.M).
  • Never force-kill the backend with hardware open. Shut down with Disconnect then quit. If it will not exit, say so and leave it — a kill costs a physical power-cycle.

6. When the hardware is the problem, the logs say so plainly#

Two guards exist precisely so a dead rig does not masquerade as a software bug. Both fired on 2026-08-24 and correctly identified a wedged OneBox:

source "source.npx.onebox" has not produced data in 3 s (stuck at 0 cycles)
        -- acquisition is running but nothing is arriving
...
np_arm(16) did not return within 3000 ms. Abandoning the call and continuing teardown
Virtual slot 16 was NOT released -- the box did not respond.

The first is the stall watchdog: acquisition reported healthy while zero samples arrived. The second is the bounded vendor call: a basestation that stops responding no longer hangs shutdown.

If you see either, stop debugging your script — the problem is not in your code. Power-cycle the box.

And do not let a successful reconnect convince you it recovered. Measured 2026-08-24: after this failure a control-plane probe (scan → map → open → close → unmap, no acquisition) succeeded completely, which looks like a clean box. The very next streaming attempt reproduced the fault exactly — connect fine, headstage detected, software trigger fired, then zero samples and the box dead again. The control plane and the data plane fail independently. Proving the box answers openBS proves nothing about whether it will stream.

7. Sim first, always#

Every simulated source drives the same processors, ring buffers, WebSocket and GUI as real hardware. When something looks broken, reproduce it in sim before touching the rig — and if sim works and hardware does not, that is evidence about the rig, not about your code.

Simulated NPX 2.0 Ripples injects real ripple events and detects them reliably: with the sequence in §2 it trains three channels and produces ~19 detections in 50 s, every time. That makes it the control for any "is the detector broken?" question — which is how I established, in four minutes, that a hardware failure had nothing to do with a change I had made that evening.
