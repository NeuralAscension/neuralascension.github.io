Next task — the config audit that is still open#

Status: open, and the operator has called it the important one to do next (2026-09-03).

The 2026-09-02 documentation audits swept config/ twice. The first pass produced the deletion of the five *Asap.yaml copies and a set of header corrections; the second pass corrected four more headers and then died partway through verification on a usage limit, leaving its config lens the only one never finished. What follows is what survived that, re-checked by hand against the files on 2026-09-03, plus the one structural defect the sweep exposed.

Every finding below is quoted from the file as it stands today. None of them is applied.

1. Two profiles claim the same sim_variant#

config/SimNpx1LatencyBaseline.yaml:12   sim_variant: "Neuropixels 1.0 — Ripple Detection (GUI)"
config/SimNpx1RippleModule.yaml         sim_variant: "Neuropixels 1.0 — Ripple Detection (GUI)"

sim_variant is what groups a profile under the GUI's Simulated Data picker, and no two profiles should carry the same one. SimNpx1LatencyBaseline is a latency bench, not the ripple-detection GUI config; the string is a leftover from whatever it was cloned from. It does not surface today only because the file also carries gui_hidden: true, so the collision is invisible until somebody unhides it — and the same file's own header explains that it was hidden precisely to avoid putting "three buttons reading identical words in front of the operator."

Fix: give it a sim_variant that describes it, or drop the key, since a gui_hidden profile has no use for one.

Then make the class unwritable, which is the point of doing this at all — see InvariantTests.md. A python/tests case asserting that sim_variant is unique across config/*.yaml costs nothing and would have caught this the day it was introduced. test_config_no_asap_twins.py is the worked example of the shape: read every config, assert a property, and prove the test red before you rely on it.

2. A header that contradicts the line above it#

config/SimNpx1LatencyBaseline.yaml:10   gui_hidden: true
config/SimNpx1LatencyBaseline.yaml:11   # Selectable in the GUI "Simulated Data" picker (sim_variant key groups every config that carries it).

Lines 6 to 9 explain at length why the profile is hidden. Line 11 then says it is selectable in the picker. Same copy-paste as finding 1, and a reader who trusts the comment over the key is misled.

3. "differing ONLY in" understates the difference#

config/SimNpx1RippleModule.yaml:9   It is the same NP1 ripple sim as SimNpx1Ripples.yaml … differing ONLY in:
config/SimNpx1RippleModule.yaml:10    - auto_start: false   -> the module does not run until the user presses Start

Diffing the two files with comments stripped, they differ in three ways, and the omitted one is the operationally significant one:

SimNpx1Ripples.yaml SimNpx1RippleModule.yaml
gui_hidden true absent, so it is offered in the picker
sim_probe absent "1.0"
auto_start absent, defaults false false, stated

So the honest difference is which one the operator can see, and the comment names the one thing that is arguably not a difference at all. Rewrite it against a real diff.

4. "the only ripple option offered in the UI" is false#

config/SimNpx1Ripples.yaml:8   (SimNpx1RippleModule.yaml, "Ripple Detection (GUI)") is the only ripple option offered in the UI.

Six profiles carrying sim_variant are ripple sources, and all of them reach the picker: SimNpx1RippleModule, SimNpx2RippleModule, SimNpx1NiDaqRipples, SimNpx2NiDaqRipples, SimNpx2RealNiDaqRipples, and the two play-file profiles Npx1SynthRipples / NpxSynthRipples. The sentence was probably true when only the NP1 module existed. It is a claim about the UI written in a file the UI does not read, which is why nothing caught it.

5. A comment attached to the wrong recording block#

config/Npx2OneBoxDigitalIn.yaml:74   # OneBox ADC: record all 12 analog channels.
config/Npx2OneBoxDigitalIn.yaml:75   - data_name: "data.npx.adc.di"     <- the COMPARATOR band, not the analog one
config/Npx2OneBoxDigitalIn.yaml:80   - data_name: "data.npx.adc"        <- the 12 analog channels, uncommented

The comment describes the block below the one it sits on. This profile exists specifically to distinguish the analog band from the logic band, so the misplacement is worse here than it would be anywhere else.

6. A OneBox explanation inside the PXIe profile#

config/NeuropixelsNiDaq.yaml:46   Keep it: the closed-loop stimulus capture rides on it, and it costs no probe
                                  bandwidth, because the OneBox samples the ADC either way.

NeuropixelsNiDaq is the PXIe-plus-NI-DAQ profile, and the same comment three lines above correctly says a PXIe basestation has no ADC. The justification for keeping the band is then given in terms of the OneBox. Not wrong so much as answering a different profile's question; state why this profile permits the band.

7. Deferred on purpose: the inert data: keys#

25 config files carry a data: key beside name: on source outputs, about 64 lines, and the parser ignores it. Status §90 records the decision not to delete them: a blind sweep of 25 files with the GUI suite as the only check is the wrong trade for a key that does nothing. Left here so the next person knows it was a decision and not an oversight. If it is ever done, do it with a test that asserts the parser's output is unchanged, not by eye.

How to do this work#

Doc-only and config-comment-only changes still go through the gate, because config/ is read by the Python suite (test_config_channels.py, test_config_no_asap_twins.py) and by the architecture generator:

python scripts/build_docs.py                        # regenerates the architecture SVGs
python -m unittest discover python/tests            # seconds
python scripts/run_all_tests.py --no-browser --fatal

Findings 1 and 3 change behavior-adjacent keys rather than only comments, so they want the full gate. Findings 2, 4, 5, 6 are comment-only.

Do not restate suite or case counts here or anywhere outside Testing.md — see Contributing.md.
