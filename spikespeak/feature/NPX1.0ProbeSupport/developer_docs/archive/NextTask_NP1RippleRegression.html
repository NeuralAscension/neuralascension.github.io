NEXT TASK — Repeat the closed-loop ripple→stim validation on Neuropixels 1.0 (regression)#

Goal: run the SAME 100-ripple closed-loop recording + offline analysis that was just done on NP2.0, but on a real NP1.0 probe, to confirm the NP2-focused changes in the last commit did not break NP1. Then clear the result into RecordingTests/NP1_RIPPLE_TESTS.md + memory. This is a hardware task on the Windows rig (real NP1.0 + NI-DAQ PXI-6133 + the live Pi 3B+ stim server at 192.168.1.100).

Read first: RippleClosedLoopAnalysis.md (the exact offline pipeline + the sync fix), RippleDetection.md (per-probe detector input), RecordingTests/NP2_RIPPLE_TESTS.md (the NP2 result this mirrors). The user prefers directive, falsifiable claims ("check X") over hedged suggestions — state what you'll verify, run the decisive test, let them correct you.

What changed in the last commit (the regression surface)#

The commit "NP2.0 closed-loop ripple→stim validation + robust NI-DAQ↔NPX sync" touched shared code. For each, the claim to verify on NP1:

Change NP1 risk Verify (claim to falsify)
sync.py → match="auto" (default), reader.py Shared. NP1 sync uses the same aligner. NP1 synchronize() still gives ~10 ppm / <0.02 ms residual and 0-unmatched ai4↔detection.
RippleDetector.cpp sidecar + config-driven input/decimation/threshold Shared. NP1 must resolve to data.npx.lfp, decimation 1 (NOT ÷12). The _ripple.json sidecar for NP1 lists the correct read-out channels + thresholds; NP1 decimation = 1.
WebSocketServer/RecordProcessor channels override Shared. NP1 records two bands (ap+lfp). The channels override + sidecar apply correctly to NP1's ap+lfp; NI-DAQ still keeps ai0+ai4.
DisplayProcessor re-baseline on hw-timestamp reset Shared display path — highest NP1 risk. NP1 pause→play + pick-channels do NOT freeze/blank the live view (this was the NP2 symptom).
NpInterface (Npx2MSProbe seed, np_setSWTrigger gating) NP2-probe-class specific; should be inert for NP1. NP1 connect/play/pause/pick-channels stream normally.
NetworkClient.js NP2 raw AC-coupling NP1 uses ap/lfp, not raw — should be untouched. NP1 live traces render (not off-screen/flat).
StimulatorClient GUI stim params Shared, probe-agnostic. fire 60 10 1 500 → one pulse/detection on ai4 (same as NP2).
config/Npx1PxiNiDaq.yaml (record all channels) NP1 config edited. It connects, streams ap+lfp, and records.
analyze_recording.py exact-NP2-detector additions NP1 branch (detector_input() if "lfp" in bands) is separate — reads lfp directly, no Bessel. NP1 analysis produces a clean, tight, non-negative latency (0 unmatched).

NP1-specific facts (differ from NP2)#

  • Source / config: --source "NPX 1.0 with NI-DAQ" (config name: in config/Npx1PxiNiDaq.yaml). Records ap+lfp [0..383] + NI-DAQ [0..7].
  • Detector input: NP1 reads the native 2.5 kHz lfp band DIRECTLY (int16, decimation 1, no proc.lfp, no Bessel). The AP band is high-passed → unusable for ripples. (NP2 was raw→Bessel data.lfp→÷12.)
  • electrode ≈ read-out channel on NP1 (contiguous), unlike NP2 (electrode ≠ channel). record_ripples.py still records rig.resolved_channels(), so this is handled — but sanity-check the sidecar channel ids.
  • Earlier NP1 closed loop was validated 2026-07-09/16 (115 ripples→112 ai4, sync ~10 ppm) but with the OLD end-to-end latency method; recompute with the current pulse-anchored online-instant method (expect a few ms, comparable to NP2's 1.94–3.45 ms).

Procedure (mirror the 3 NP2 tests)#

  1. Confirm the Pi stim server is up (ss/systemctl over SSH per [stim-server-pi3-live] memory; do NOT trust journalctl program logs). User plays the synthetic NP1 ripple signal (ripple_tools/gen_synthetic_ripples.py --probe 1.0) into saline.
  2. Launch: python run_spikespeak.py + a browser. Connect "NPX 1.0 with NI-DAQ". Eyeball the Live Data view for the strongest LFP ripple electrodes.
  3. Record 3 tests with ripple_tools/record_ripples.py (100 ripples each), e.g. into RecordingTests/np1_{1channel_1required,2channel_2required,4channel_3required}/: - --source "NPX 1.0 with NI-DAQ" --channels <e> --quorum 1 --z 2.5 --n 100 --dir <abs> --name np1_1channel_1required - --channels <e1>,<e2> --quorum 2 ... --name np1_2channel_2required - --channels <e1>,<e2>,<e3>,<e4> --quorum 3 ... --name np1_4channel_3required Stim is single-pulse (--stim-freq 1.0 --stim-train-ms 500 = one pulse/detection) on ai4.
  4. Analyze each: python ripple_tools/analyze_recording.py <recdir> --ws <recdir>/<name>_ws.jsonl --quorum "<N> ch, <M> required" --figs <recdir>/analysis. Optionally verify_quorum.py per test.
  5. Write RecordingTests/NP1_RIPPLE_TESTS.md (mirror the NP2 report), update memory ([[ripple-recording-100-setup]]), regenerate the docs book (python scripts/build_docs.py).

Success criteria#

  • Each test: 100 online detections → ~100 ai4 pulses, 0 unmatched, tight non-negative closed-loop latency (a few ms). If a test shows "orphans"/unmatched, first check NPX-vs-NI-DAQ sync pulse counts (the auto fix should handle a mismatch, but confirm) and the per-channel envelope-vs-threshold + the ripples-vs-pulses raster — do NOT theorise about hardware before looking at those (see the sync-bug lesson in RippleClosedLoopAnalysis.md).
  • NP1 live view, pause/play, and pick-channels all work (the shared DisplayProcessor/streaming changes didn't regress NP1).

Safety (hardware attached — non-negotiable)#

  • Graceful shutdown only (WS Disconnect / quit) — a force-kill strands the IMEC board + leaves the stimulator ARMED ([[graceful-hardware-shutdown]]).
  • Do not leave the rig streaming during unrelated work ([[stop-streaming-when-idle]]); shut EVERYTHING down when done — backend + test browser + streaming ([[dont-leave-rigs-running-for-user]]). Report via saved screenshots/plots.
  • Kill only the debug-port-9222 / isolated-profile Chrome on GUI teardown, never a blanket chrome kill ([[gui-browser-teardown]]).
