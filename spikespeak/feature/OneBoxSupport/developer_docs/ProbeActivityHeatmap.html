Feature Plan — Probe Activity Heatmap (live, on the probe map)#

Status: PROPOSED (planning only — nothing built). Awaiting design decisions (§6). Goal: Once a channel map is applied and data is streaming, stop "freezing" the probe-map tab to a static selection. Instead, color the selected electrodes by live activity — a dark-mode SciChart take on the OpenEphys ProbeViewer heatmap, with the active sites "blinking"/glowing by activity level.

References: the OpenEphys source we mirror is vendored at Source-OpenEphys-Neuropixels-PXI/UI/ (ProbeBrowser, ActivityView, ColourScheme). Our probe map internals are in LiveDataView.md and webinterface/ImroManager.js.

1. How OpenEphys does it (the thing to match)#

From UI/ActivityView.cpp, UI/ProbeBrowser.cpp, UI/ColourScheme.cpp, UI/NeuropixInterface.cpp:

  • Metric = per-electrode peak-to-peak amplitude (max − min) over a sliding window, in µV. Not RMS or spike rate. (ActivityView.cpp calculatePeakToPeakValues ~344-381.)
  • Window ≈ 100 ms, refreshed at 10 Hz (startTimer(100), NeuropixInterface.cpp). AP window = 3000 samples @ 30 kHz; LFP = 250 @ 2.5 kHz.
  • Two modes: AP-band vs LFP-band activity (a combo box).
  • Optional pre-processing (both on by default): common-average reference (ADC-group-aware) + a 300-6000 Hz Butterworth band-pass, applied before min/max.
  • Colormap = Inferno (matplotlib), a 256-step LUT (ColourScheme.cpp). Black→purple→orange→yellow — already dark-mode friendly. (Viridis/Plasma/Magma/Jet also available.)
  • Normalization = fixed clim, not auto-scaling: color = inferno(p2p / clim), clim selectable {250, 500, 750, 1000} µV, default 500. No-data sites (sentinel -1) drawn grey (160,160,160).
  • Geometry: one filled rectangle per electrode, placed by integer (shank, column_index, row_index) — same grid our probe map already uses. Selected sites get a contrasting outline.
  • Channel→electrode mapping (refreshActivityViewMapping) ensures activity lands on the correct physical site even as the IMRO selection changes; the full electrode array stays grey except the connected channels.

2. The big shortcut — we already have the metric and the renderer primitives#

Two findings make this much cheaper than OpenEphys's full pipeline:

  1. Peak-to-peak is already on the wire. DisplayProcessor decimates each channel to min and max per timebin and streams both (DisplayProcessor.cpp; parsed in NetworkClient.js). So p2p = max − min per channel is computable in the browser today, with zero backend change — exactly OpenEphys's metric. Aggregate over ~100 ms of timebins for a smoothed value.

  2. SciChart v5.2.35 (our bundle) natively supports the rendering we need — verified present in lib/index.min.js: PaletteProvider / overridePointMarker (per-point coloring of a scatter series), UniformHeatmapDataSeries + HeatmapColorMap (a true heatmap), and GradientColorPalette. No canvas-overlay hack is required.

  3. The channel→electrode→geometry map already exists as window.imroLiveView.electrodeOf(channelId) (+ colOf, slotOf, isRef) in ImroManager.js. An incoming per-channel activity value maps to a probe-map point with electrode = imroLiveView.electrodeOf(ch) → row = electrode>>1, col = electrode&1.

3. Design options#

Decision 1 — WHERE activity is computed#

  • Option A — derive in JS from the existing min/max stream (RECOMMENDED to start). p2p = max − min per channel, smoothed over ~100 ms, refreshed ~10 Hz. No C++ change. Faithful to OpenEphys's core metric. Limitation: broadband (no CAR, no 300-6000 Hz band-pass), so it's "raw" activity, not spike-band-clean.
  • Option B — a dedicated C++ ActivityProcessor that mirrors OpenEphys: CAR (ADC-group-aware) + 300-6000 Hz BP + windowed p2p, streamed as a compact per-channel frame (one f32/channel at 10 Hz). More faithful, isolates the cost from the display path, but is new backend work.
  • Recommendation: A first (immediate, free); add B later if you want spike-band fidelity.

Decision 2 — HOW it's rendered (both are SciChart-native and confirmed available)#

  • Option A — PaletteProvider on the existing electrode scatter (RECOMMENDED for "blink selected"). Keep the current probe-map geometry; attach an IPointMarkerPaletteProvider to the selected series (activeLeft/activeRight) that returns inferno(activity[electrode]/clim) per point. Inactive stay grey, reference stays amber. Update the activity array + invalidate the surface each frame.
  • Pros: keeps selection context exactly as you described ("selected channels blinking by activity"); minimal change to renderElectrodeMap. Cons: per-point palette wiring; one series, many points.
  • Option B — UniformHeatmapDataSeries heatmap. Render the probe as a 2-col × N-row (NP1) / per-shank (NP2) heatmap with HeatmapColorMap (Inferno + clim). Most "OpenEphys-looking."
  • Pros: a true heatmap, built-in colormap + legend. Cons: a different visual from the selection scatter — you'd swap to it in an "activity mode" rather than recolor the existing map.
  • (Option C — canvas overlay: not needed now that A/B are available; omit.)
  • Recommendation: A if the intent is "the existing selection map comes alive"; B if you want a dedicated full-probe heatmap panel. They can coexist (A on the map, B as an optional panel).

Decision 3 — colormap#

Inferno (OpenEphys default, dark-mode native) via GradientColorPalette/HeatmapColorMap gradient stops. Offer Viridis as an alternative. (We don't need the 256-row LUT — matplotlib gradient stops reproduce it.)

Decision 4 — normalization / clim & units#

Fixed, user-selectable clim like OpenEphys (250/500/750/1000, default 500), grey for no-data. Open item: confirm the units of our min/max stream (the DisplayProcessor applies NPX gains — need to check whether the result is µV) so the clim numbers are meaningful; otherwise clim is in "display units" and we relabel. (DisplayProcessor.cpp gain logic + Npx.hpp.)

Decision 5 — what "blinking" means (please pick)#

  • Option A — brightness/color tracks activity at ~10 Hz (OpenEphys behavior): active sites glow bright (yellow), quiet sites stay dark. Reads as "live activity," not literally blinking. (recommended)
  • Option B — literal pulse: modulate marker opacity/size sinusoidally, with pulse amplitude or rate proportional to activity. Can be layered on top of A.
  • "Blinking based on activity level" could mean either — A is proven/readable; B is flashier. Tell me which (or A-with-optional-B).

Decision 6 — lifecycle / mode#

Today the map is static after render. Proposal: when streaming starts, the probe tab enters Activity Mode (auto, or via a toggle button next to the tabs) — selected electrodes are colored by activity; selection editing is disabled while live (re-enabled when paused). Decide: auto-on while streaming vs manual toggle (default on).

Decision 7 — scope of probes#

NP1.0 first (single shank, 2 columns). NP2.0 (4 shanks) reuses the same electrodeOf/shankOf mapping and either a per-shank palette or a wider heatmap — straightforward but do it after NP1.0.

4. Implementation outline (assuming JS-activity / PaletteProvider / Inferno / auto-mode)#

Frontend only (Option A/A): 1. Activity store + derivation (NetworkClient.js after each batch, or a 10 Hz timer): for each channel, p2p = max − min smoothed over ~100 ms; electrode = window.imroLiveView.electrodeOf(ch); write window.probeActivity[electrode] = p2p. (Reuse the data already parsed for the charts.) 2. PaletteProvider on the active scatter series in ImroManager.js renderElectrodeMap: implement overridePointMarker(x,y,i,opacity,md) → fill = inferno(clamp(probeActivity[md.electrode]/clim)), grey if no data. Store md.electrode per point (already storing md.text). 3. Refresh loop (~10-30 Hz requestAnimationFrame or setInterval): update probeActivity, then sciChartSurface.invalidateElement() so the palette re-evaluates. (Optional pulse = modulate opacity in the palette by a time term × activity.) 4. UI: clim dropdown (250/500/750/1000), AP/LFP mode toggle (if both streams present), a colorbar legend, and the Activity-Mode enter/exit on play/pause.

If Decision 1B (C++ activity): add src/modules/.../ActivityProcessor (CAR + BP + windowed p2p), register proc.*.activity, stream [ "activity" ][u32 nCh]([f32]×nCh) at 10 Hz; the JS step 1 then just reads that frame instead of deriving p2p. Steps 2-4 unchanged.

5. Risks / unknowns#

  • Per-point palette ergonomics: PaletteProvider exists in the bundle; confirm the exact IPointMarkerPaletteProvider signature in v5.2.35 during a spike (it's the one API I'd prototype first).
  • Units for clim (Decision 4) — verify µV vs display units.
  • Cost at 10-30 Hz: ~384-960 points re-evaluated per frame is cheap, but confirm the surface invalidation cadence doesn't fight the live charts (they share the WebGL context budget).
  • JS-derived activity is broadband (no CAR/BP) — acceptable to start; Decision 1B closes the gap.

6. Decisions I need from you#

  1. Compute activity: JS from the existing min/max stream (A) or a C++ CAR+band-pass processor (B)? (lean A)
  2. Render: PaletteProvider recolor of the existing selection map (A) or a SciChart UniformHeatmap panel (B)? (lean A for "blink selected")
  3. Colormap: Inferno (match OpenEphys) — ok? Viridis alternative?
  4. clim values + units: keep 250/500/750/1000 µV default 500? (pending units check)
  5. "Blink": color-intensity tracks activity (A) or literal pulse (B) or both?
  6. Mode: auto Activity-Mode while streaming, or a manual toggle?
  7. Probe scope: NP1.0 now, NP2.0 after — ok?

7. Effort & risk#

  • Option A/A (JS activity + PaletteProvider): ~2-3 focused days, frontend-only, low backend risk. The first hour should prototype the PaletteProvider per-point recolor to lock Risk #1.
  • Adding C++ activity (B) for spike-band fidelity: +1-2 days.
  • A UniformHeatmap panel (Render B) instead of/alongside palette: comparable, mostly layout work.
