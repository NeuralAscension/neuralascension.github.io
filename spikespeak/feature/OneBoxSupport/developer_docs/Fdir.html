FDIR — fault detection, reporting, and staying in a valid state#

Issues #11 and #16. Companion to issue #18, which fixed the same disease one layer up.

Three questions this answers: when something in the pipeline fails, how does the user find out?, how do we avoid ending up in a state nobody designed?, and what is the server doing right now -- is every part of it still turning?

1. The rule: state is announced when it is CONFIRMED, never when it is requested#

This is the whole document in one line. Everything below follows from it.

A control flow has three moments — requested, accepted, confirmed — and it is tempting to treat the second as the third, because the second is the one you have in hand when the function returns. Both layers of this codebase did exactly that, independently:

layer asserted state on… what went wrong
browser (#18) its own click Play flipped to Pause whether or not acquisition started
backend (#11) handleTextCommand("play") returning true statePlaying=1 broadcast before any source was running

handlePlayRequest() returns true once the processor threads have been asked to start. Nothing is acquiring at that point. If a source then failed, slMcOnSourcesStarted(false) stopped everything again — correctly — and told nobody, so every client went on showing a running rig that had just been shut down underneath it.

So: MainController::sigMcAcquisitionStateChanged(bool acquiring, QString reason) is the only thing that may change what clients are told about acquisition. It is emitted when the controller knows — after every source has actually started, or after the attempt has been abandoned and everything stopped again. WebSocketServer::setPlaying no longer touches statePlaying at all.

play  ->  handleTextCommand("play") == true    "accepted -- awaiting confirmation"   (silent)
      ->  every processor reports ready
      ->  sources start
      ->  sigMcAcquisitionStateChanged(true)   -> broadcast statePlaying=1           (announced)

If you add a control that can be refused, or that can fail after being accepted, follow this shape. Returning true from the request handler is not a licence to announce the outcome.

2. Fault reporting: one path, no opt-in#

IProcessor::sigIpErrorOccurred(QString) has existed since the beginning. Until #11 nothing listened to it except WebSocketServer, wired to the recorder by name. So:

  • a recorder failing to open a file → reached the user
  • proc.lfp, proc.rippledetector, a display processor failing → reached nobody

ProcessorManager now connects it for every processor it constructs:

IProcessor::sigIpErrorOccurred            (worker thread)
  -> ProcessorManager::slPmProcessorError    -- tags it with the REGISTRY KEY via sender()
  -> sigPmProcessorError(name, message)
  -> MainController::sigMcProcessorError     (queued -- see section 5)
  -> WebSocketServer::slBroadcastProcessorError
  -> guiStatus  "proc.npx.recorder: <message>"

Covered by construction: a sink added next year is included without anyone remembering to wire it.

Report vs consequence. The relay reports — it puts named text on the status line. A sink that additionally needs the UI to act keeps its own channel: the recorder's recordingStatus makes the GUI revert its optimistic "recording" state. Keep the two separate, and do not send the text down both, or the user sees one fault twice.

3. Identity comes from the sender, never from the reported name#

Processors emit hardcoded short labels that have nothing to do with their registry key:

registry key emits
proc.npx.display "display"
proc.npx.recorder "recorder"
proc.nidaq.recorder "recorder" ← the same string
proc.rippledetector "ripple"

Every RecordProcessor emits "recorder", so a profile with an NPX and an NI-DAQ recorder — SimNpx2NiDaq, Npx1PxiNiDaq, and others — reports one name for two processors. Any bookkeeping keyed on that string counts six processors as five and waits forever.

ProcessorManager::nameForSender() resolves the signalling object back to its registry key. Both the readiness set and the fault relay use it. If you touch this code, do not "simplify" it back to trusting the emitted name.

4. Startup is bounded, and a failed cycle stays failed#

Readiness used to be an int compared with ==. Two hazards, both silent:

  • a duplicate sigIpStarted pushed the counter past the total, so the equality never matched again and acquisition hung with every component reporting itself healthy;
  • a processor that never reported at all produced the same hang, with no error and no timeout.

Now: a QSet of registry keys (so a duplicate is genuinely idempotent), tested with >= and a latch, plus an 8 s watchdog (kStartupTimeoutMs). On expiry it names the processors that never checked in, stops the pipeline, and reports:

Acquisition stopped: Processor startup timed out after 8000 ms.
Never reported ready: proc.npx.display, proc.rippledetector

A declared failure is final for that cycle (mStartupFailed). Without that latch the watchdog and a slow processor race and both win — the watchdog reports the startup failed, the stragglers finish, and the manager announces the very same request started a moment later. One play request produced both outcomes and the GUI showed each in turn. This was observed, not theorised; it is why the latch exists. Late arrivals are logged and ignored, and the next startProcessors() clears it.

5. Getting a reason out of an object that is being destroyed#

The specific cause of a failed connect — No Headstage detected on any port!, a wrong FTDI driver, no basestation from scanBS — was known and thrown away. handleConnectRequest calls teardownManagers() on failure, destroying the source object before its deferred sigGuiStatus can be delivered, and Qt discards queued calls to destroyed QObjects. The one message that would help was the one guaranteed not to arrive.

A separate thread does not fix this. The message is not late — its sender is gone. What is needed is a sink that outlives every sender: src/core/ErrorLog.{hpp,cpp}, fed from logMessages(), the global Qt message handler, which already sees every thread and every object including ones destroyed moments later. WebSocketServer takes a mark() before a risky operation and asks for since(mark) if it fails.

Two properties of that sink that look wrong and are not:

  • It does not filter on QtMsgType. This codebase puts severity in the text — hardware failures are plain qDebug() << "[MAIN] ERROR: ..." lines, and the neuropixels module alone has 178 qDebug against 31 qWarning. A level filter would capture none of the messages it exists for.
  • Ordering is chronological, not newest-first. Failures cascade forwards: the first line is the cause and the rest are consequence. Newest-first led with ERROR closing probe. Code: 44 — the teardown, not the fault.

Re-entrancy. MainController emits its FDIR signals while handleTextCommand holds mMutex, and QMutex is not recursive. Subscribers are connected Qt::QueuedConnection so a handler that reacts by issuing another command cannot deadlock. Keep it that way.

6. Weight of a report: status line vs modal#

situation channel dialog?
control refused (play with no source, record with no recorder) guiStatus kind error no
processor faulted while running guiStatus kind error no
acquisition stopped after failing to start guiStatus kind error no
connect failed guiStatus kind hardware-error yes

Only hardware-error raises a blocking modal. That weight is right for "your basestation is missing" and much too heavy for "you pressed play without a source" — the control is already truthful, so a dialog would interrupt without adding information.

An error dialog must not outlive the condition it describes: a deviceReady=true dismisses a stale "Hardware not detected" modal, which otherwise sat there after the user fixed the rig and reconnected — and on a second client could describe a failure that browser never triggered.

7. State that lies#

ProgramState::recordingState was assigned exactly once, in MainController's constructor, and never again by anything. Recording is owned by WebSocketServer and RecordProcessor, so the field read eNotRecording for the whole life of the program including while a recording was running.

It has been removed. A state variable that is always wrong is worse than no state variable: it invites exactly the "am I in a valid state?" check this issue asks for, and then answers it incorrectly. acqState gained an in-class initialiser for the same reason — an enum whose default is whatever happened to be on the stack is the cheapest possible route to an unexpected state.

If MainController should know about recording (so isReadyToQuit() refuses to quit mid-record — arguably it should), wire it to the recorder. Do not re-declare the field.

8. Knowing the whole state, and whether it is still moving (issue #16)#

11 made failures reportable. #16 makes the system inspectable: what is the server doing right#

now, and is every part of it still turning?

8.1 One snapshot, answerable at any time#

getSystemState returns the lot, so a client never has to infer state from the sequence of events it happened to be connected for:

{ "event": "systemState", "acquisition": "acquiring", "source": "NPX 2.0 Multishank (OneBox)",
  "playing": true, "recording": { "active": false, "name": "" },
  "processors": [ { "name": "proc.lfp", "state": "cycling", "ready": true,
                    "cycles": 24235, "thread": true } ] }

It is also broadcast when anything in it changes, and replayed to a late-joining client. MainController::systemState() owns acquisition + processors; WebSocketServer composes recording on top, because the recorders live there. Recording is not copied into MainController -- a second copy of a state is a second thing that can be wrong, which is exactly what recordingState was (section 7).

systemState() deliberately does not take mMutex. handleTextCommand holds it for the whole of a connect or a play, and those are precisely the moments somebody most wants to look at the system; taking the same lock would make the monitor block on the thing it is monitoring. Every field is a plain value written on that thread or an atomic counter, so a snapshot taken mid-transition can be one step stale -- the right trade for never blocking.

8.2 Liveness: "started" is not "working"#

A processor can report ready and then block forever on a buffer that never fills, and every health signal in the system keeps saying it is fine. IProcessor therefore carries a monotonic cycleCount(), bumped by noteCycle() once per work cycle -- a timer slot body, or one pass of a blocking loop. ProcessorManager polls it every second and calls a processor stalled after 3 consecutive polls with no movement, naming it on the GUI status line and in the snapshot.

Three things about this that were chosen and are worth not undoing:

  • Polled, not signalled. The acquire loops run at 1 ms and the display at 20 ms; a heartbeat signal per cycle would push that through the event loop to answer a question nobody asks more than once a second.
  • Relaxed atomics. The only question ever asked is "did this change since I last looked?". Nothing is published through the counter, so there is nothing to order against.
  • Counted AFTER the wait in blocking loops. noteCycle() sits after waitForAvailable() returns, so a processor parked on a buffer that never fills genuinely stops advancing. Putting it at the top of the loop would count the parked iteration and hide the stall.

Stall detection runs only while acquiring -- the monitor stops on pause. An idle processor is not a broken one, and colouring it as one trains people to ignore the indicator.

Where the heartbeat goes matters, and it is easy to get wrong. All six calls must be in the per-cycle function, not in slIpStartProcessor/slIpStopProcessor. A misplaced one reads as a permanent stall the moment acquisition starts (which is how the first version of this was caught: proc.npx.display sat at 0 cycles while everything else advanced). The rates are the check -- proc.npx.display should tick at ~50 Hz (20 ms timer) and proc.npx.recorder at ~20 Hz (50 ms).

8.3 Recording is confirmed too#

RecordProcessor::sigRecordingStateChanged fires from applyRecordingState -- the point at which files are actually open or actually closed -- not from setRecording, which is only the request. The old stateRecording broadcast echoed the request straight back, so a start whose file open failed still told every client it was recording. The GUI now shows a pending record button and transitions only on confirmation, closing the gap this document used to list.

Watch the event shape: the GUI reads {value: <bool>, name: <string>}, not broadcastStatusEvent's {message: "1"}. A status-shaped event is read as false and a started recording looks stopped.

8.4 The indicator is labelled, not a bare dot#

The status line carries a chip -- a coloured dot, the word System, and the current count ("6 cycling", "1 stalled", "idle") -- styled with the toolbar's own band tokens so it sits level with the status text and the REC indicator. Clicking it opens the detail panel.

It was a bare dot first, and that was wrong: an unlabelled coloured dot only means something to somebody who already knows it is there, which is no use to the person who most needs it. The count sits on the chip for the same reason -- the common questions ("is it running? are all the parts turning?") are answered without opening anything. A stall turns the whole chip red and names itself there, not only in the tooltip: a fault you have to hover to discover is a fault you will not discover.

8.5 The frontend must actually be deployed#

Unrelated to the state model, but it invalidated a test and will invalidate yours. The webinterface copy used to be a POST_BUILD step on the SpikesPeak target, so it only ran when the executable relinked. Editing only .js/.css left the deployed copy stale while the build reported success, and the browser served the old frontend -- so a test of new frontend code silently exercised the old code and passed. It is now an always-out-of-date copy_webinterface target.

The served root is <exe>/../webinterface, never the source tree. When a frontend change appears not to take: curl -s http://localhost:8234/main.js | grep <your new symbol>.

9. Known gaps#

  • Sources have no liveness counter. Only processors carry noteCycle(). A source worker that stops producing is currently visible only indirectly, as every downstream processor stalling at once -- which is a usable signal, but it names the symptom rather than the cause.
  • Sources have no equivalent of sigIpErrorOccurred. IDataSource has sigGuiStatus, which is a display channel rather than a fault channel, and the connect path proves it is unreliable during teardown (section 5). ErrorLog covers the gap; a real source fault signal would be better.
  • The watchdog does not cover the source side. A source that never starts is caught only by slMcOnSourcesStarted(false), which depends on SourceManager reporting at all.
