Architecture diagrams — generated, not drawn#

Every pipeline picture in these docs is produced by scripts/make_architecture.py, which reads the code and the configs and emits SVG. Nothing here is hand-drawn, and nothing hand-drawn is allowed back in: the predecessor was a PlantUML description that drifted as modules were added and, because nothing rendered it during the build, shipped invisible — the book referenced an SVG that was never produced.
Generator scripts/make_architecture.py
Inputs src/core/Utils.cpp (the registry) + every config/*.yaml + a small provisioned-wiring table
Output developer_docs/images/architecture.svg + one per config, git-ignored
Committed copy images/architecture.svg, for the repo README only — refreshed by the docs build
Run python scripts/build_docs.py (regenerates, then refreshes the committed copy)
Verify python scripts/make_architecture.py --check --out-dir developer_docs/images
Test python/tests/test_architecture_current.py

1. What it draws#

Six stages, as horizontal bands, top to bottom:

CONFIG  →  DATASOURCE  →  DATA  →  DATAINTERPRETER  →  PROCESSOR  →  SINK

Read it downward: a profile selects a source, the source publishes named bands, an interpreter serializes a band, a processor consumes it, and a sink is a file a recording writes.

Node types are colored, not labeled by shape. The legend at the top carries the mapping. A config box shows its filename on the first line and its internal name: on the second, because a config's identity is that name: field and never the filename — the GUI and CLI select the name.

2. Where the edges come from, and the one place they do not#

Most edges are parsed straight out of the YAML:

edge from
Config → DataSource sources: entries
DataSource → Data each source's outputs:
Data → Processor a processor's inputs: or input:
Data → DataInterpreter → Processor → Sink the recorder's recordings: blocks

Three processors are wired by C++ instead, and the parser cannot see that. proc.lfp, proc.spike and proc.audio are auto-provisioned by ProcessorManager, so profiles never mention their inputs. Before 2026-09-01 they were therefore drawn as orphans — boxes with no line touching them — which reads as "connected to nothing" when the truth is "connected by code this parser does not read". The operator spotted it in the picture, which is the only place it was visible.

They are now supplied by an explicit table in the generator, AUTO_PROVISIONED:

processor input output provisioned when
proc.lfp data.npx.raw data.lfp source has raw and no native lfp — i.e. a 2.0
proc.spike data.npx.raw data.spike same
proc.audio data.npx.ap, else data.npx.raw data.audio any probe band exists

Ground truth for that table is src/core/ProcessorManager.cpp (the two auto-provision blocks), src/modules/audio/AudioProcessor.cpp (which band audio listens to) and DerivedBands.md §5.

This table is a second source of truth, and it is drawn as such. Those edges are orange and dashed, with their own legend entry — "auto-provisioned in C++ (not in the profile)" — because "the profile wires this" and "the program wires this" are different claims and a reader is owed the difference. If the provisioning rules change in C++ and this table does not, the picture will be confidently wrong; that is the cost of the table and the reason it is small and cited.

And one node the parser cannot draw at all: source.npx.auto. Nodes come from the register* calls in src/core/Utils.cpp, and source.npx.auto is not registered — it is an alias resolved at connect time in SourceManager::setupSources, which reads the basestation scan and then builds source.npx.onebox or source.npx.pxi. So it has no node, its config edge is dropped, and the two operator-facing hardware profiles are drawn without their probe source: Neuropixels comes out with no DataSource band whatsoever (its data bands appear from nowhere), and NeuropixelsNiDaq shows only source.nidaq. Checked 2026-09-01 against a fresh generator run. Nothing downstream is wrong — the missing box is the choice, which by design is not made until the rig answers. Read those two pictures with SourceSelection.md beside them, and do not conclude from the picture that a Neuropixels profile has no source.

Upward edges are real. A derived-band processor produces data, so proc.lfp → data.lfp points from the Processor band back up to the Data band. Those are routed out to the side rather than dropped — an earlier version silently discarded every backward edge and so hid the exact wiring this section exists to show.

3. Layout rules, and why each exists#

Top-down, not left-to-right. The first version made each stage a column. The canvas was then a function of the biggest stage, so with every config in one picture it came out 1580 × 2460 — a tall ribbon four times higher than wide, unreadable on any page. Stages as bands grow the diagram in the direction pages actually scroll.

Boxes are measured from their text. Fixed 200 px boxes with centered labels overflowed badly: config names run to 54 characters, about 270 px at 10 px type, spilling out of both sides and over the neighbors. Widths are now computed per node and clamped, and anything still too long is truncated with an ellipsis. The width estimate is 0.55 em per character — the standard approximation for mixed-case Latin, deliberately erring wide, because a real font metric would be a dependency.

There is a viewBox. Without one an SVG renders at its intrinsic pixel size and overflows any narrower container; with one it scales to whatever it is given.

Config boxes are clustered by the source they feed, and their edges are bundled. 36 profiles each drawing an independent curve into 9 sources crossed everywhere and carried no information you could trace. (36 and 9 are what the overall picture draws today, checked 2026-09-01; the "37" that used to stand here was the count of SVG files, which is one per config plus the overall one.) Configs are now ordered by their first source name — sources are placed alphabetically, so this puts a profile roughly above its target — and their edges converge on a single collector point just above each source. They are also drawn fainter than the rest: at that count they are context, not the subject.

4. Working on it#

Adding a source, processor, data or interpreter needs nothing here. Register it in src/core/Utils.cpp and reference it from a config; the next docs build draws it. That is the whole point of generating.

Adding a new C++-provisioned processor DOES need a line in AUTO_PROVISIONED, or it will be drawn as an orphan. There is no way around that short of parsing C++ control flow, which would be a worse trade.

A source name that is an ALIAS rather than a registered module gets no box at all — the profiles naming it come out with a missing stage, not a dangling edge. source.npx.auto is the live example; see 2. If you add another, expect the same and say so wherever the picture is read.

After changing the generator, regenerate and look at the picture. The tests check that the SVGs match the code and that the committed copy matches the generated one; neither can tell you the layout is legible. To render one without a browser window:

chrome --headless=new --disable-gpu --hide-scrollbars --window-size=1500,1050 \
  --screenshot=out.png file:///ABSOLUTE/PATH/developer_docs/images/architecture.svg

Do not commit developer_docs/images/architecture*.svg — they are git-ignored and derived. The single exception is images/architecture.svg, which the repo README embeds; GitHub renders the README from the repository and cannot see a git-ignored file. That copy is written by the docs build and asserted byte-identical to the generated one, so it is committed without being hand-maintained.

These files are deliberately not dated, unlike the screenshots (KnowledgeOps.md §8). A hand-made artifact cannot say how old it is and nothing re-derives it, so it carries a date. These are a function of the wiring and are re-derived every build — and a date stamped inside the SVG would make --check compare a fresh render against a stamped file and fail every day, destroying the mechanism that guarantees freshness in order to display a claim about it.

Date what cannot be re-derived. Check what can.
