Intan / MicroZed — open questions#

Two audiences, kept separate on purpose. §1 is for the operator to answer or decide. §2 is for the Kemere lab, written to be asked in one round rather than discovered one at a time. §3 is what we can settle ourselves without asking anyone.

Nothing here is blocking today's code — the parser and the control framing are written and tested against synthesised packets. These block connecting to a real board and, in two cases, block a design decision that is expensive to reverse later.

Status: the Intan source is registered and deliberately refuses to connect (see IntanMicroZed.md); selecting it reports not-implemented and returns the system to disconnected.

1. For the operator#

1.1 Which LFP path? — the one that changes the architecture#

The ripple detector needs an LFP band. Two ways to get one, and they are not close in cost:

what it means cost
(a) generalise BandFilterProcessor make it take a runtime channel width touches the AVX2 8-lane fan-out, kNumFilters, and both read and write strides, in code that runs at 30 kHz. Highest-risk item in the whole ticket.
(b) consume the board's on-FPGA LFP bind data.intan.lfp and point the detector straight at it input_type: int16, decimation_factor: 1 — exactly the shape the NP1.0 path already uses, which is the path we have most confidence in. BandFilterProcessor never involved.

Why this is urgent rather than academic: BandFilterProcessor hardcodes 384 as a stride (kNumFilters = kMaxChannels / 8, and both strides). A 256-channel Intan buffer through it would not error — it would scramble. So (a) is not "leave it for later"; it is "leave it for later and something silently produces wrong data if anyone wires it up in the meantime."

Recommendation: (b). It is lower risk, lower latency, and it moves work onto their FPGA — the trade this project says it wants. Upstream's own doc names "sharp-wave ripples ~150–250 Hz, phase-targeted stimulation" as the motivating use case for that filter chain, and its 30 kHz → 3 kHz CIC+FIR fully contains our 150–250 Hz band.

Blocked on Kemere question K3 — whether that LFP stream is hardware-validated.

1.2 Is this a replacement source or a simultaneous one?#

sources: is a sequence, so an Intan source composes alongside a Neuropixels probe with no architectural change. But sync between two independent clock domains is a much larger problem than either source alone, and closed-loop latency is what this system is judged on.

If simultaneous is wanted, the sync path is the 8 digital inputs (§2, K5) plus the board's 64-bit timestamp — the same shape as the existing NPX↔NI-DAQ sync-pulse alignment. If not, this stays simple. Please say which.

1.3 There is no stimulation on this hardware#

RHS — the stim-capable Intan family — is never mentioned anywhere in the upstream repository. This board records only. A closed loop on Intan would still trigger through the Pi stim server, as NPX does today.

Worth confirming that matches your expectation, because it means "Intan closed loop" is Intan-in, Pi-out, and the sync between them is question 1.2.

1.4 µV per LSB — where should the number come from?#

It appears nowhere in the upstream repo. It is a property of the RHD2000 part and of the commanded gain/bandwidth registers, which upstream lists as not yet configurable.

GET_STATUS exposes a 22-byte RHD register mirror, so the honest answer is datasheet + readback, not a constant. But that is more work than a constant, and the live view and the recording sidecar both need a number. Constant now with a TODO, or readback from the start?

1.5 Do we want the Opal Kelly board at all, eventually?#

Tracked as #76 and deferred. It needs the FrontPanel SDK — a vendored binary dependency, which is your decision under the no-new-dependency rule. Asking only so it can be closed as "not planned" if that is the answer, rather than sitting open forever.

2. For the Kemere lab#

Written to be sent as one message.

K1 — Which firmware is on the board we will use? The repository is mid-migration: docs/protocol.md documents a legacy 10-word packet header, while firmware/include/main.h and remote/net.py on main implement the 14-word "unified" framing (magic 0xCAFEBABE). Our parser discriminates both at runtime, but we need to know which to expect — and ideally the fw_version the beacon will report.

K2 — Is port B working on real hardware? The ROADMAP marks epic I phase 2 as PL/firmware/host done and timing closed, with "Remaining: on-hardware bring-up". Should we treat 128 channels as the working configuration and 256 as aspirational?

K3 — Is the on-FPGA LFP stream (type 2) hardware-validated? This decides our architecture (see 1.1). We would like to consume it directly and skip deriving the band in software. Has it been run against a real headstage, and are the default CIC+FIR parameters sensible for a 150–250 Hz ripple band?

K4 — µV per LSB. Is there a number you use, or do you read the RHD gain registers back? What do your own analysis scripts assume?

K5 — The 8 digital inputs: level or edge? The RTL appears to latch the level once per sample frame, which would mean a TTL shorter than ~33 µs can be missed entirely. Is that right? Is there an edge-capture or timestamped-event path we have missed? This is our sync line, so it matters.

K6 — Which carrier PCB revision? digital_inputs.xdc notes the GPIO routing changed on "the new carrier PCB rev" and carries a TODO that the JX1 schematic symbol is flipped (labels read 18N/18P, 16N/16P, 14N/14P, 12N/12P but are actually 17/15/13/11). We would like to know which physical pin is which digital input on the board we get.

K7 — Has anyone measured end-to-end latency, board input to host userspace? The firmware instruments its own recv→transmit window (~3 µs typical, ~10 µs max of a 33.3 µs budget), but nothing covers wire + NIC + kernel + application. We care about this specifically: it sits on our closed-loop path.

K8 — 30,000 datagrams/second on a Windows host. Have you run the receiver on Windows, or only Linux? We are sizing the receive strategy and would rather learn from your experience than rediscover it.

K9 — Is there a paper or preprint we should cite? We could not find one, and the lab's tools page does not list this system.

K10 — Would you like our C++ client back? There is no MIT-licensed C++ implementation of this protocol; ckemere/ephys-socket is GPL-3.0 so we are reading it only for understanding. Ours would be the first, and we are happy for it to be useful to you.

3. Ours to settle, no one to ask#

question how we settle it
Can QUdpSocket keep up at 30 kHz datagrams on Windows? Measure. A synthetic sender at 30,000 datagrams/s of 616 B into a bound socket, counting host-side drops. Do this before choosing the receive strategy — the alternative is a blocking-read loop or touching the native descriptor for batching, and that choice should follow a number.
Does the +2 deskew hold on real data? Already pinned in test_intanpacket against synthesised packets; confirm once against a real capture with SET_DEBUG_MODE (the FPGA's synthetic sine has a layout identical to real data, and upstream's reference client carries a model proven bit-identical to the RTL).
Trace ordering for a source with no geometry The live view's non-probe path already exists and is used by NI-DAQ and the OneBox ADC — plain channel order, CH n labels. Confirm it looks right at 128 channels, decide nothing new.
Where the µV-vs-× scale gate lives Known defect: ChartColumn.isProbeStream() tests channels.length === 384, so a 256-channel neural stream renders on the NI-DAQ multiplier scale. The honest fix is a per-stream property on the wire, not a widened count test. Tracked in IntanMicroZed.md §4.2.
