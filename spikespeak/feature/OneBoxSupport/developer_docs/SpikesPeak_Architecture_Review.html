1. Executive Summary#

SpikesPeak is a real-time electrophysiology acquisition app. A Qt/C++ backend reads Neuropixels (or simulated) data on dedicated worker threads, fans it out to independent processor threads (display decimation, disk recording, sharp-wave-ripple detection), and pushes display data to a browser UI over a single WebSocket on port 1234.

Crucially, the UI is not embedded. The backend runs a tiny static HTTP server on port 8234 (main.cpp:40-80,251-253) and opens the page in the user's system default browser via QDesktopServices::openUrl (main.cpp:266). The C++ process is a QApplication (Qt Widgets linked), so it can show native desktop dialogs even though its UI lives in an external browser. This matters for file I/O (§9).

The WebSocket is triple-multiplexed:

  1. Binary frames — decimated min/max waveform batches (C++ → JS), drawn by the WebGL2 renderer (GlRenderer.js).
  2. Application commands/events — small JSON control messages (selectSource, setPlaying, deviceReady, …) framed inside a 4-byte binary header.
  3. QWebChannel RPC — Qt's object-bridge protocol, letting JS call C++ Q_INVOKABLE methods directly (the IMRO probe-map editor: read / update / apply / save).

4. Module System (factory + registry + config)#

Everything pluggable is a named, registered object created lazily by a singleton factory.

  • Factory (ObjectFactory<tBase>, ObjectFactory.hpp): one singleton per base type (IData, IDataSource, IProcessor, IDataInterpreter). registerClass<T>(name, args…) stores a creator lambda (ctor args captured by value); createObjectByName news on first request; duplicate names are ignored with a warning.
  • Registration (Utils.cpp registerBuiltInTypes(), called from main.cpp:193): the single place every built-in module is declared — registerDataSource<T>("source.x", ctorArgs), registerData<CircularBuffer<D,A>>("data.x"), registerProcessor<T>("proc.x"), registerDataInterpreter<T>("interp.x"). HW sources are wrapped in #ifdef NPX_HW_ENABLED / NIDAQ_HW_ENABLED.
  • Registries (Registry.hpp/.cpp): getSourceRegistry()/getProcessorRegistry()/ getDataRegistry()/getDataInterpreterRegistry(). getXByName() lazily constructs + caches; clearRegistry() tears down on disconnect.
  • Config (config/*.yaml, parsed by parseAllConfigs, main.cpp:104-127,218-219): a profile is name: (the UI dropdown label) + sources: + processors:. Each child has a name: equal to a registry name, plus module-specific keys. Example (config/Npx1Pxi.yaml):

yaml name: "NPX 1.0" sources: - name: "source.npx.pxi" outputs: [ { data: "ap", name: "data.npx.ap" }, { data: "lfp", name: "data.npx.lfp" } ] processors: - name: "proc.npx.display" inputs: [ { data: "ap", name: "data.npx.ap" }, { data: "lfp", name: "data.npx.lfp" } ] - name: "proc.npx.recorder" recordings: - { data_name: "data.npx.ap", data_interpreter_name: "interp.npx.ap", output_filename: "npx_ap_recording" } - { data_name: "data.npx.lfp", data_interpreter_name: "interp.npx.lfp", output_filename: "npx_lfp_recording" }

5. Data-Pipeline Threading Model#

One producer thread → N independent consumer threads, orchestrated by MainController → SourceManager (sources) + ProcessorManager (processors).

Stage Thread Cadence Start / Stop
HW read (Npx1Probe/Npx2MSProbe) NpxWorkerThread (HighPriority) QTimer @ 1 ms PreciseTimer QThread::started→slStartAcquiringData; sigNpsRequestDaqStop→slStopAcquiringData; stopAcq() does quit()+wait(2000)
Display decimation per-processor thread QTimer @ ~20 ms (config) ProcessorManager::setupProcThread: started→slIpStartProcessor; sigPmStopProcessing→slIpStopProcessor
Disk recording per-processor thread QTimer @ 50 ms same; final flush on stop
Ripple detection per-processor thread blocking semaphore loop (no QTimer) started→slIpStartProcessor→doRippleDetectionLoop; mQuitProcessing atomic exits loop
WS broadcast main thread per Display batch sigIpDataReady→broadcastData via Qt::AutoConnection (queued) (WebSocketServer.cpp:122-149)

Start ordering (important). On play, MainController::handlePlayRequest (MainController.cpp:124-145) wires ProcessorManager::sigPmProcessorsStarted → SourceManager::slSmStartSources, then calls startProcessors(). So all consumers start and report sigIpStarted before the producer (startAcq) ever commits — a consumer is always registered before the producer notifies it. A new sink must emit sigIpStarted(name) when ready, or play never proceeds (the manager waits for every processor, ProcessorManager.cpp:132-142).

Start ordering is now bounded and confirmed (issue #11, 2026-08-20). Three changes to the same mechanism, because "waits for every processor" used to mean waits forever:

  • Readiness is keyed on the sender object, not the reported name. Processors emit hardcoded labels ("display", "recorder", "ripple") unrelated to their registry key, and every RecordProcessor emits "recorder" -- so a dual-recorder profile reports one name for two processors.
  • An 8 s watchdog (ProcessorManager::kStartupTimeoutMs) names whoever never checked in, stops the pipeline and reports it, instead of hanging silently. A cycle declared failed stays failed.
  • Acquisition state is announced only when confirmed. handlePlayRequest returning true means the request was accepted, not that anything is running; MainController::sigMcAcquisitionStateChanged is the single source of truth for clients.

Every processor's sigIpErrorOccurred is also relayed generically to the GUI, tagged with its registry key. Full detail, including why a separate error thread is the wrong shape for this: Fdir.md.

Thread affinity. Source and processor objects live in the main thread (created under MainController); processors are then moveToThread'd to their own QThread (ProcessorManager.cpp:70-104); a HW source additionally moves its worker to NpxWorkerThread. The NeuropixelsSource object itself stays on the main GUI thread — which is why its QWebChannel Q_INVOKABLEs may safely show modal dialogs (§9).

5.1 Module detail (sinks)#

  • DisplayProcessor (Npx::DisplayProcessor : IProcessor). Binds streams by registry name into per-stream StreamState (DisplayProcessor.hpp), polls getTotalSamplesAdded() (non-blocking; no consumer registration), computes AVX2 min/max decimation into time bins, and emits sigIpDataReady(QByteArray) per batch — the only processor wired to the WS broadcast.
  • RecordProcessor (Recording::RecordProcessor : IProcessor). Does not touch CircularBuffers directly; delegates to an IDataInterpreter per recordings: entry (updateReadMarkers() idle, serializeAvailableData() while recording) and writes timestamped files via QFile. Recording toggles via the setRecording(bool) Q_INVOKABLE over QWebChannel (Option A), the same per-module pattern as the NPX source — see ModuleCommunication.md. (Was binary command id 0x1001; migrated 2026-06-25.)
  • RippleDetector (RippleDetector : IProcessor). The real-time DSP path. Registers as a blocking consumer of an LFP buffer (addWaitingConsumer), runs a synchronous loop on the consumer semaphore, applies an IIR ripple-band then envelope filter (src/core/Filter), maintains a rolling mean/σ baseline (DetectionParams, RippleDetector.hpp:28-50), detects envelope > mean + z·σ (default z = 5) outside a lockout, fires a StimulatorClient, and produces two of its own output buffers (decimated ripple-band + envelope) as a new addProducer.

6. CircularBuffer Fan-Out (src/core/CircularBuffer.hpp)#

CircularBuffer<tData, tAux> : IData — single producer, multi-consumer ring, the mechanism that lets Display/Record/Ripple read the same stream concurrently.

  • Producer: setCapacity(numSamples, numDims); addProducer(int32& id) (currently caps at ONE producer — commitWrite ignores producerId > 0); write into getDataStart()/getAuxDataStart() at index % sampleCapacity(); publish with commitWrite(id, n) → bumps mSamplesWritten and release(n)s every consumer semaphore.
  • Polling consumer (Display, Record): getTotalSamplesAdded(atomic&) → available = total − myReadInd; read constDataAt(i) / constAuxDataAt(i); never blocks.
  • Blocking consumer (Ripple): addWaitingConsumer(int32& id) (allocates a per-consumer QSemaphore); waitForAvailable(id, ms, &got) blocks until the producer commits.
  • Each consumer keeps an independent read index, so consumers never disturb each other.

(NP1's Npx1Probe demuxes hardware superframes — 12 AP + 1 LFP each — into data.npx.ap and data.npx.lfp and commits both per tick.)

7.4 Architectural decision — per-module commands ride QWebChannel (Option A)#

Decision (2026-06-23): per-source web commands are exposed as Q_INVOKABLE methods over QWebChannel. This is the project standard going forward, because it preserves the multi-source/sink architecture cleanly: each source registers its own object under its own registry name and exposes its own invokables, so adding a new module (e.g. a camera under source.camera.usb with setExposure() / getFrameRate()) needs no edit to any central command router — registration + the existing registerObject loop do it.

Consequently the legacy JSON command hook was removed from NeuropixelsSource: the handleWebCommand override (the applyMap / saveImro / updateImro branches) duplicated the invokables and was unreachable — WebSocketServer::onTextMessageReceived (WebSocketServer.cpp:187-231) only routes to handleWebCommand in its else branch (messages without a "command" field), while the override early-returned unless a "command" field was present. Mutually exclusive ⇒ dead code. It is gone; the four invokables are the single path.

The generic hook still exists as IDataSource::handleWebCommand (a no-op default, IDataSource.hpp:22-24), and WebSocketServer still calls it for "command"-less messages, so a future module that wants a fire-and-forget JSON command bus can override it — but that path has the routing gap above and would need it fixed first (forward unknown command values to the active source). Prefer Q_INVOKABLE for anything needing a return value; see AddingASourceModule.md §"Per-source web commands".

7.5 File I/O convention — who writes the file, browser vs backend#

The external-browser model splits file I/O two ways. The deciding question: who produces the bytes, and how much / how continuously?

Browser-written (client-side) Backend-written (server-side)
Use for small, one-shot, config-shaped data large, continuous, real-time data streams
Examples .imro channel maps (a few KB of text) recordings (AP ≈ MB/s, gigabytes)
Who writes the browser, via the File System Access API showSaveFilePicker (or a Blob + <a download> fallback) the backend, QFile straight to disk on the SpikesPeak machine
Path browser picks + writes; the backend never learns a path (the API deliberately hides absolute paths) the backend needs a real path on its own machine
Picker the browser's own Save-As picker a native Qt dialog on the backend (see below)
Reference getImroAsImroText() ⇄ ImroManager.js Save RecordProcessor::setRecording(…, dir, name) ⇄ record modal

Why the divergence: a .imro map is a tiny string the C++ side produces once and hands to the browser to save wherever the user likes — perfect for the browser's picker, no backend path involved. A recording is the opposite: the backend generates it continuously at full rate and must write it directly to disk (routing gigabytes through the browser to write client-side would be wasteful and unreliable — a throttled/backgrounded tab would drop samples). So recording needs a real backend path, which a browser picker cannot provide (the File System Access API exposes a folder's name but never its absolute path).

  • Reading a file → client-side. <input type="file"> + FileReader → the file text to a synchronous C++ Q_INVOKABLE parser (commit atomically: parse into locals → validate → assign). Reference: loadImroFromText() ⇄ ImroManager.js Load.
  • Writing small/config files → client-side. The backend returns text from a Q_INVOKABLE; the browser writes it (picker/download). Reference: getImroAsImroText() ⇄ Save.
  • Writing large/continuous data → backend, with a native folder picker. The recorder writes to a directory the user chose. The Browse… button in the record modal sends a pickDirectory command (over id 0x1000); WebSocketServer opens QFileDialog::getExistingDirectory and returns the path in a directoryPicked event. Because this backend is a windowless server, the dialog is opened the safe way — deferred (QTimer::singleShot(0), so its modal event loop never re-enters the WebSocket/QWebChannel machinery), forced DontUseNativeDialog, relying on setQuitOnLastWindowClosed(false). (A modal dialog opened synchronously inside a Q_INVOKABLE crashed and exited the app — §9; that is why config files went client-side and why the recording picker uses the deferred pattern.) The dialog appears on the machine running SpikesPeak (the localhost setup); a typed path also works.

Rule of thumb: a Q_INVOKABLE must return promptly. Anything that blocks or spins an event loop (modal dialogs, long hardware ops) is deferred or moved off the dispatch.

8. Frontend State & Rendering (summary)#

  • main.js AppController owns UI wiring + the NetworkClient; columns/window/play/record.
  • Live waveforms: NetworkClient parses and bakes y, then hands each batch to ChartColumn.gl — a GlColumnRenderer (WebGL2) per column in #view-data, which holds the only copy of the samples. DataStore keeps per-channel display state (offsets, zoom, color), not samples.
  • Probe map: ImroManager.initProbeMap(npxBackend) builds a canvas-2D ProbeMap of probe geometry in #view-map, fetches IMRO via getImroAsJson, supports click-select / drag-window / bank presets (modulo-384 rules; reserved channel 191 drawn amber) that push back via updateImroFromJson, and Apply / Save / Load via the invokables above (Load reads the file client-side — §7.5).
  • The probe-map ↔ live-data tab bar (#main-tabs) is revealed only for NPX sources.
  • A toolbar status display (#status-display, right of Record) shows human-readable lifecycle + IMRO events (connecting, probe found, apply/load/save, play/record) via window.guiStatus → AppController.setStatus; everything also mirrors to the console ([STATUS] …).

9. Save Pipeline — getImroAsImroText (2026-06-24)#

History (three iterations): 1. Save "did nothing" — browser prompt() blind-typing a server path + silent failure. 2. A C++-driven QFileDialog opened synchronously in the Q_INVOKABLE → its nested event loop re-entered the non-re-entrant QWebChannel machinery → crash ("saving shuts off"). 3. Deferring the dialog (QTimer::singleShot(0)) fixed the crash, but the dialog was the windowless server's only window, so closing it tripped quitOnLastWindowClosed and exited the app.

Fix (current): Save is fully client-side. getImroAsImroText() (a Q_INVOKABLE) returns the .imro text; ImroManager.js saves it via the browser's native Save-As picker (showSaveFilePicker, with a Blob-download fallback) so the user chooses folder + filename. No server dialog, no nested loop, nothing to close — symmetric with the client-side Load (§7.5). Defensively, main.cpp now also setQuitOnLastWindowClosed(false) so no future transient dialog can exit the app. saveImroToFile(path) survives as a server-side writer for explicit paths (programmatic/scripts), unused by the UI; both share serializeImro().

Lesson: in a windowless server with an external-browser UI, keep UI file I/O in the browser (upload to read, download to write) — never open a modal dialog inside a Q_INVOKABLE.

Remaining / latent (not regressions)#

  • NUM_CHANNELS (384) hard-coded on both sides of the binary protocol (not negotiated).
  • handleWebCommand routing gap (§7.4) — only matters if a future module revives the JSON command bus; the IMRO path no longer uses it.

11. Completion pass — closed loop, NP2, NI-DAQ, latency (2026-06-23 → 2026-07-21)#

Everything in §1–§10 still holds. This section completes the review with what was built on top of that core and validated on real hardware. Deep dives are cross-linked; this is the architectural map.

11.1 A second probe — Neuropixels 2.0 multishank#

Npx2MSProbe (src/modules/neuropixels/NpInterface.{hpp,cpp}) is the NP2 sibling of Npx1Probe: same worker-thread + QTimer acquisition model (§5), producing a single 30 kHz wideband data.npx.raw (NP1 demuxes into ap+lfp; NP2 has one raw band). NeuropixelsSource::startAcq branches on mProbeType to construct one or the other. Geometry/mapping and what is wired vs stubbed: Neuropixels2.0.md. The probe-agnostic channel map is published through ChannelMapService (src/core/IChannelMap.hpp) so a consumer resolves electrodes → read-out channels against the real applied map, not a Bank-0 identity.

11.2 Ripple detection matured into a closed-loop DSP#

RippleDetector (§5.1) is now a full sharp-wave-ripple detector, not a stub: a per-probe input path (NP1 reads native data.npx.lfp directly, decimation 1; NP2 derives data.lfp via a proc.lfp Bessel low-pass then decimates ÷12 — both land at 2.5 kHz), a ripple-band + envelope FIR chain, a per-channel mean+z·σ baseline, and a multi-channel quorum / coincidence / lockout state machine. Channels and all detection parameters are strictly GUI/WS-driven (removed from YAML); the module starts with 0 channels and waits. On record start it writes a ripple sidecar (slWriteRippleSidecar, Q_INVOKABLE) capturing the resolved channels + trained thresholds. Algorithm + the per-probe rationale: RippleDetection.md; GUI: RippleGui.md; threading: RippleDetectorThreading.md.

11.3 The stimulation path — detect → fire → Pi → AM 2300 → NI-DAQ#

On a confirmed quorum detection the detector calls StimulatorClient (src/modules/stimulation/StimulatorClient.{hpp,cpp}), which sends a UDP fire datagram (default 192.168.1.100:8888) to a Raspberry Pi 3B+ running the pulse generator, which drives an AM Systems 2300 to emit a biphasic pulse. The Pi ACKs fired off its real-time path; the client stamps send/ACK times (mLastFireSendUs/mLastAckUs) and the GUI's STIM LED lights only on a confirmed fire. The delivered pulse is captured on NI-DAQ ai4, which is how the closed loop is measured (§11.5). Stim target is retargetable live (setStimServer); pulse params (phase/gap/freq/train) are GUI-editable. An ESP32-S3-ETH firmware twin exists (esp32s3eth_am2300_pulsegenerator/) but the production server is the Pi. Bring-up: raspberrypi_pulsegenerator/README.md; closed-loop history: ../SpikesPeak_Status.md §21–§30.

11.4 NI-DAQ as a first-class source#

source.nidaq (src/modules/nidaq/NiDaqInterface.*) streams a PXI-6133 (differential only) as data.nidaq.raw (analog volts) with a parallel DI/O stream, wired by YAML like any other source (§4). It carries the shared ~1 Hz sync TTL on ai0 and the stim pulse on ai4. Its single-reservation failure mode and the 2026-07 robustness fixes are in NiDaq.md. Recording writes nidaq (ai0..ai7) and nidaq_di bands alongside the probe bands.

11.5 Latency instrumentation + the ASAP delivery flag#

The detector emits a per-stage rippleLatency WS event after every confirmed stimulus (sample-proc, detector-backlog, detect→send, send→ACK). Closed-loop latency is defined as threshold crossing → ai4 pulse and measured offline against the NI-DAQ recording. The one architectural lever found was delivery granularity: a source's poll cadence sets how stale the oldest sample in a delivered block is. The opt-in low_latency: true YAML flag drives Npx1Probe/Npx2MSProbe::setLowLatency(), dropping the acquisition QTimer interval from 1 ms to 0 (poll every event-loop pass). It is per-source, so only a config that closes a loop pays the CPU cost. Result: sub-millisecond closed loop on both probes. Method: LatencyProfiling.md; numbers: ../RecordingTests/CLOSED_LOOP_LATENCY.md.

11.6 The command/event model today — and what is still a TODO#

§7 chose Option A: per-module frontend commands ride Q_INVOKABLE over QWebChannel. That is now the standard across multiple modules — the NPX sources, RecordProcessor::setRecording, and the ripple detector's sidecar invokables all register their own object at select time (WebSocketServer::onSourceSelection), so adding a module needs no central-router edit. Alongside it:

  • Data-plane "subscription" is config-driven and is the only subscription initialized from YAML: a processor's configure() reads its input(s): names and registers as a CircularBuffer consumer (addWaitingConsumer/polling); sources addProducer. The YAML wires who-consumes-what by registry name.
  • Inter-module events are plain Qt signals/slots (sigIpStarted/Stopped/DataReady/ErrorOccurred, sigRippleEvent, sigGuiStatus), connect()-ed imperatively in ProcessorManager/WebSocketServer — there is no event bus.
  • A partial CommandDispatcher singleton (src/core/CommandDispatch.hpp, addSubscriber / executeCallbacks) provides a runtime command pub/sub, but it is command-only, code-registered, and has exactly one subscriber (AudioProcessor.cpp:491, hard-coded id 0x218); it is being superseded by Q_INVOKABLE.

So the long-standing goal "processors subscribe to any commands/events, config-initialized + runtime-modifiable" (todo.txt:5–6) is NOT yet a unified mechanism. It is approximated by the four paths above (config-wired data plane + Qt signals + Q_INVOKABLE web commands + the single-use CommandDispatcher). A true generic event/command bus, declarable in YAML and mutable at runtime, remains the open design item.

11.7 Offline analysis + the sync machinery#

A Python post-processing stack (python/spikespeak_postprocess, ripple_tools/) reconstructs the exact detector from a recording and measures the closed loop, warping NI-DAQ time onto the NPX clock via the shared sync train. Three clock/sync bugs that silently corrupted latency were found and fixed (a ~10 ppm clock-scale ramp and two whole-period off-by-ones); the aligner now pairs robustly at either end and warns on a count mismatch. This is the reference for any recorded-timing work: RippleClosedLoopAnalysis.md.

11.8 Status#

Both probes are validated end-to-end on real hardware in saline — synthetic ripple → detection → Pi/AM 2300 → NI-DAQ ai4 — across the full quorum × delivery matrix (1000 detections/cell), sub-millisecond with ASAP. Saline bench validation is done; the next milestone is in-vivo recording under anesthesia, run by the user. Dated log: ../SpikesPeak_Status.md.
