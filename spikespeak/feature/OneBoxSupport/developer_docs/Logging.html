Logging — format, severity, and what to write#

Issue #2. Companion to Fdir.md, which consumes this log through ErrorLog.

1. The line#

Every message goes through logMessages() in src/main.cpp and comes out identically on the console and in output.log, so a pasted terminal screenshot and the file can be compared line for line:

22:44:33.291  DEBUG  [proc.rippledetector]   RippleDetector.cpp:753    [RippleDetector] resolved ...
|             |      |                       |                        |
time          level  thread                  origin                   the message as written
  • Time is time-of-day only. The date is written once in the file header, not on every line: this log is read live in a terminal beside the running rig, and a repeated date pushes the actual message off the right of the window for no information. The header also carries the build, because a log pasted into an issue is much less useful without knowing what produced it.
  • Thread matters more here than in most programs. Every processor and every acquisition loop runs on its own QThread, and ProcessorManager::setupProcThread names them, so this answers "which loop said that?" -- previously guesswork from the message prefix alone. Real values include main, proc.rippledetector, proc.npx.recorder, NpxWorkerThread, OneBoxAdcThread.
  • Origin is file:line, which requires QT_MESSAGELOGCONTEXT -- set in CMakeLists.txt, because Qt strips the context in release builds and every line would otherwise read "unknown" in the one configuration that actually runs on the rig. The function name is deliberately omitted: Qt gives the full mangled signature, which is far wider than it is useful.
  • Thread and origin are padded to fixed widths (22 and 26). A ragged column is not a cosmetic complaint: if the message does not start at the same column on every line you cannot scan down it. 22 fits the widest real thread name; anything longer pushes its own line out rather than being truncated, since losing a thread name to save a column is the wrong trade.

The main thread is identified from gMainThread, captured in main(). Comparing against QCoreApplication::instance()->thread() does not work for the earliest messages -- type registration runs before the application object exists, so every startup line printed a raw handle instead.

2. Severity goes in the LEVEL, not in the text#

This is the half of issue #2 that was actually causing damage.

The codebase used to write faults as qDebug() << "[MAIN] ERROR: No Headstage detected on any port!" -- severity in the string, at DEBUG level. 42 lines did this (32 "ERROR", 10 "WARNING"). Anything filtering or routing by QtMsgType therefore saw a debug message and treated a hardware failure as chatter, and ErrorLog had to match on the text to find faults at all.

use when
qDebug() tracing and detail. The default; no user ever needs to see it.
qInfo() milestones a user would recognise -- "probe initialised", "recording started".
qWarning() something failed and was handled or reported. Most "ERROR:" messages belong here.
qCritical() something failed that prevents the operation and is worth interrupting for.

Keep the [Subsystem] prefix -- it names the component, which the thread and file columns do not always make obvious, and the GUI shows that raw text in dialogs.

ErrorLog still matches on text as well as level. That is a safety net, not the mechanism: the convention above is a convention, not a compiler rule, and the next mis-levelled line will be written eventually. See Fdir.md section 5.

3. Two log files, on purpose#

file lifetime what it is for
output.log (next to the exe's working dir) truncated on every start watching the rig live; the current session only
<dir>/<name>/<name>_<timestamp>.log open only while a recording runs provenance for the data beside it

output.log is opened with "w", so it never survives a restart. That is fine for its job -- it is the file you tail in a terminal while working -- but it means it can never answer "what was the rig doing when this recording was written?" for data you come back to weeks later.

So a recording gets its own copy of the log, written by RecordingLog into the recording directory, sharing the recording's timestamp:

RecordingTests/logdemo/
    logdemo_20260819_231117.log        <- this
    logdemo_raw_20260819_231117.bin
    logdemo_raw_20260819_231117.bin.json
    logdemo_adc_20260819_231117.bin
    logdemo_adc_20260819_231117.bin.json

It carries the same formatted lines as output.log, so the two are comparable line for line, plus a dated header and footer.

It covers the recording, not the session -- deliberately. Only the source that was connected while recording appears in it; nothing from before Record was pressed, and nothing after it stopped. This is a design decision, not a limitation waiting to be fixed: the file's value is that everything in it pertains to the data next to it. If you want the whole session, including sources you connected and dropped beforehand, that is what output.log is for -- copy it out before restarting, because the next start will truncate it.

RecordingLog::start() is idempotent. A profile can have several recorders (NPX + NI-DAQ) and each calls applyRecordingState; the first opens the file and the rest are no-ops, and the first stop closes it. One button drives them as a group -- if that ever changes, this needs a reference count rather than a flag. Failing to open the log is logged and otherwise ignored: a recording must never fail because its provenance file could not be written.

4. What NOT to do#

  • Do not log per sample or per acquisition cycle. logMessages() fflushes both sinks on every message; at 1 ms cadence that is a syscall pair per tick on the hot path. Use the throttled IDataSourceWorker::reportStreamError() for a sustained streaming fault -- it fires after 3 consecutive failures then at most once per 5 s.
  • Do not put severity in the string and leave the level at debug. That is exactly what this issue fixed.
  • Do not strip the [Subsystem] prefix to save width. The columns tell you where a line came from mechanically; the prefix tells you which subsystem claims it, and the GUI shows it verbatim.
