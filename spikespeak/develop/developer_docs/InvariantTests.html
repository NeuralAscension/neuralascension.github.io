Invariant tests — making a defect class unwritable#

A practice this repo arrived at by having the same bug four times. It is not textbook TDD, and the difference is the point.

1. The observation that produced it#

Four separate defects, one shape: the system announced what was REQUESTED instead of what was CONFIRMED.
#16 / #18 the GUI asserted its own state instead of the server's — the play button claimed to be streaming before the command had been sent
#51 a refused source switch broadcast the requested source name, so a client that reacts to state changes acted on a rig it did not have
2026-08-30 a failed connect left source naming the thing that failed, next to acquisition: no_source
2026-08-30 Disconnect cleared the state but not the name, so a disconnected rig kept reporting its last source

Each was found, fixed, and tested. And the next one appeared somewhere the previous fix did not reach — because each test was written about the bug, not about the rule the bug broke.

The last two were only reachable at all because a source was added that deliberately fails to connect. Nothing else in the suite fails a connect with no source held, so that path had never been exercised in the project's history.

2. What an invariant test is#

Write down the property that must always hold, and check it at every transition — rather than asserting the output of the function you just wrote.

tests/gui/state_consistency.py is the worked example. It does not test a bug. It says:

I1  acquisition == "no_source"  <=>  source is empty
I2  playing  =>  acquisition == "acquiring"  (and therefore a source is held)
I3  a REFUSED connect leaves `source` exactly as it was before
I4  a SUCCESSFUL connect leaves `source` equal to what was asked for
I5  Disconnect leaves no source

I1 is load-bearing because it is a biconditional: it fails in both directions — a name without a source, and a source without a name. A one-directional check would have caught the 2026-08-30 pair and missed their inverse.

The effect is that a future connect path which publishes a name before the connect succeeds cannot pass, whatever source it belongs to and whoever writes it. The defect class stops being representable.

3. How this differs from textbook TDD#

They are compatible, and they are not the same thing.

textbook TDD invariant tests
unit the function or class about to be written the defect class, across whatever code can produce it
written before the implementation, red then green when a class of bug is identified — often after the second instance
scope this behaviour every path that could violate the rule, including code not written yet
fails when the feature is missing or wrong any code violates the rule, including code added years later by someone who never read the ticket

Textbook TDD would have produced a test for handleConnectRequest. That is useful, and it would not have caught the Disconnect instance — different function, same rule.

The other way round: an invariant test does not drive the design of a unit and is a poor tool for that. It is not a replacement for ordinary tests; it is the thing you add when you notice a pattern.

The rule of thumb: the second time a bug of the same shape appears, stop fixing bugs and write down the rule.

4. What makes one worth writing#

Not everything deserves this treatment. The ones that pay:

  • A rule that spans several call sites. If it can only be broken in one function, an ordinary test on that function is cheaper and clearer.
  • A rule with no local symptom. These bugs did not crash, throw, or log. The state was merely wrong, and every surface reported it confidently.
  • A rule a newcomer would not know. "Announce confirmed state, never requested" is not discoverable from the code; it is discoverable from four postmortems.
  • A rule where the failure is expensive. A recording labelled with the wrong source is not recoverable after the fact.

The existing suite already has several, written before this page named the practice:

test the invariant
tests/gui/state_consistency.py reported state is never internally inconsistent
tests/gui/detached_view.py window.opener === null — asserts the property (noopener), not the symptom (contexts surviving), because the symptom is invisible below ~16 contexts
tests/gui/heatmap_view.py every offered colormap is perceptually ordered — a named deny-list, so a rainbow map cannot come back
tests/test_configuration.cpp a name is an identity: no duplicate processor, source or config names
python/tests/test_sync_pairing.py a pairing offset is never a whole sync period — the failure with identical intervals, identical ppm and identical residual
scripts/run_tests.py scalar pass the portable SIMD path is executed, not merely compiled

5. Writing one#

  1. Name the class, not the instance. "Announced requested state instead of confirmed" — not "handleConnectRequest set mSourceName too early".
  2. State the rule as a predicate over observable state, so it can be checked anywhere rather than only where the bug was.
  3. Check it at every transition, not only after the operation that was broken. Both 2026-08-30 bugs were in transitions nobody had thought to check.
  4. Make it biconditional where the rule is. Half a rule catches half the bugs.
  5. Include a path that fails on purpose. The reason two of these bugs survived for months is that failure paths were never exercised — there was no way to fail a connect without unplugging hardware. IntanSource refusing is now that path, and it earns its keep every run.
  6. Prove it can fail, like any test here — inject the violation, watch it go red, revert. An invariant test that cannot fail is worse than none, because its scope makes it look like broad coverage.

6. The failure paths deserve a source of their own#

The most reusable thing to come out of this: a source that refuses on purpose is test infrastructure, not a placeholder.

IntanSource returns false from initDataSource having touched nothing, which makes the refused-connect path runnable on any machine, with no hardware, every single gate run. Two real bugs fell out of it within minutes of it existing.

If a future subsystem has a failure path that can only be reached by breaking real hardware, that is a sign it needs an equivalent — something that fails cleanly and deliberately, wired in like anything else.
