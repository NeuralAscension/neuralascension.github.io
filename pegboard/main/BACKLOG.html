5. LED check lights for built-in self tests — done

Closed 2026-08-10. The firmware change anticipated here was indeed needed; it shipped in pegboard-usb 1.1.0. (Current firmware is 1.3.0.)

22 checks, 12 in firmware and 10 on the Pi, reduced to one SELF-TEST greenlight in the status strip. Tapping it opens a panel of per-test LEDs with plain-English names, the measurement taken and the band it had to be in.

wherecommands / entry points
firmwareselftest, selftest_trigger, fw_info; one passive suite runs at boot
Piraspberry-pi5/bist.py; socket events run_selftest, run_trigger_selftest, bist_update
recordevery result lands in events.csv as bist / bist_run

Wire format is ASCII lines like the rest, so the raw log stays readable without a parser:

BIST: hx711_rate, status: PASS, value: 89.69, unit: SPS, lo: 60.00, hi: 110.00, note: ok, Seq: 38

The design decisions worth keeping

Two suites, split on whether they can stimulate. The passive suite is safe any time the task is not running. The trigger wire test drives TRIGGERPIN for 50 ms — a real pulse — and is the only way to prove the wire to GPIO26 is intact, because the Pi can confirm stimulation is being recorded only by seeing an edge it knows was sent. It is never automatic and has its own confirmation.

The greenlight is never green on absence. Any check that has not reported leaves the verdict unknown, not pass. A lamp that goes green because a test never ran would be trusted and would be wrong. The two trigger tests are the exception: not having stimulated is not a fault, so they are excluded until they have a result.

Firmware results are dropped when the board resets. Opening the serial port asserts DTR and reboots the board, so results from before describe a different boot. They also expire after 30 minutes.

Limits are tied to the real constants. scale_noise passes below half minWeightChangeReq and fails at it, because noise at the detection threshold means the rig invents placements and stimulates on them.

Measured on hardware, 2026-08-10

11/11 passive tests pass. hx711_rate 89.69 SPS, loop_period 93.94 ms (matches the 94 ms in item 2), scale_noise 0.033 g against a 1.25 g threshold, adc_headroom 12.4%, heap 281 KB, zero drops. The trigger pulse measured 50.00 ms on two consecutive runs and left the line idle-low.

One thing found doing it

The board's boot-time self test is lost. It writes into a USB endpoint no host is draining yet, so nothing arrives. app.py therefore sends selftest itself immediately after opening the port — that is what actually produces a report. Same class of problem as the stream_data re-arm.

process_data() now drains the serial link even when not streaming. It previously skipped the read entirely, so a self test run before STREAM DATA sat unread in the kernel buffer — which is exactly when an operator wants to run one. Acknowledgments and task-reset messages were being missed for the same reason.

The HX711 hang — fixed 2026-08-10

Found while writing the self tests: HX711::read() waits on DOUT with nothing but yield() and no timeout, so an unpowered or unplugged amplifier hung core 0 until the 5 s task watchdog reset the board. The symptom is the board going silent — indistinguishable from the taskYIELD() bug, which sends you at the wrong fault.

Guarding the call sites would not have been enough: get_units(8) spends ~82 ms of a ~94 ms pass inside read_average(), so a lead coming off lands mid-average roughly seven times in eight. Every conversion is now bounded (waitReady/readRawAverage/readUnits, 400 ms per conversion), which meant doing the averaging in the sketch. The arithmetic is deliberately identical to the library's — same conversions, same mean, same offset, same calibration — so the detection sequence and every tuned constant are untouched. Only the blocking behavior of an individual read changed.

A failed read abandons the pass without publishing a reading or attempting detection, so the rig can never stimulate on an amplifier that has stopped answering. The fault is reported through the self-test channel as hx711_present FAIL, repeated every 5 s, so it lights the same red lamp with the same words as any other failure.

Verified on hardware by injecting the fault — a temporary build drove DOUT high from the ESP32, which is exactly what an unplugged amplifier presents:

beforeafter
amplifier diesboard resets at 5 s (watchdog)stays alive, reports hx711_present FAIL
amplifier restored—recovers by itself, emits PASS, resumes streaming
healthy timing89.69 SPS, 93.94 ms89.69 SPS, 93.97 ms — unchanged

The fault-injection command was removed before the production flash.

One thing that fell out of the test: passes spent waiting out a timeout were being counted into the cadence average and dragged the reported loop period from 94 ms to 131 ms, so the self test warned about a loop that was fine. The accumulator now excludes faulted passes and resets on recovery.

The firmware now measures its own stages

Firmware 1.2.0 emits one Profile: line per placement. Measured on the bench, 12 placements, 2026-08-10 (analysis/bench-profile-20260810.txt):

stagemedianrangenotes
acquisition get_units(8)93.36 ms92.99&ndash;93.958 conversions at ~86 SPS
settle delay(100)99.63 ms99.04&ndash;100.00tick-quantised, slightly under 100
confirming read get_units(3)17.85 ms17.50&ndash;18.45half what 3 conversions should cost
verify &rarr; trigger0.006 ms0.005&ndash;0.0115&ndash;11 microseconds
board total210.85 ms210.49&ndash;211.44matches the firmware's own Detection Latency: 211 ms

The chain is almost perfectly deterministic: 0.95 ms of spread across 12 placements, which is what a fixed sequence of blocking calls should look like and is worth having on record as a baseline.

Two findings that only measurement could produce:

The verify-to-trigger interval is 6 us. That is the interval nothing may be inserted into, and it is now a number rather than an assertion.

The confirming read costs half what it should. Three conversions at 89.7 SPS is ~33 ms; it measures 17.9. The HX711 keeps converting during delay(100), so the first sample is already waiting when the read begins — the settle and the converter overlap. Worth knowing before anyone "optimizes" the settle: shortening it would not buy the full amount back.

Instrumentation cost: 0.0049 ms, measured on the board by the new profile_cost self test, against a 1 ms budget. Four micros() calls, two of which only run on a confirming pass. Everything else sits below TRIG_HIGH(). loop_period was 93.97 ms before the instrumentation and 94.00 ms after.

Reconciled — and it found a real bug

Two sessions were recorded on the Pi with 1.2.0 (20260810/005 Right/taVNS and 006 Left/Sham, 25 pegs and 25 stimulations each, 25 profiles each) so both views describe the same placements. The gap did not go away; it became consistent, which is what made it findable:

005006
board, pass start &rarr; trigger211.06 ms211.22 ms
recording, "firmware share"136 ms135 ms
difference&minus;75.1 ms&minus;76.2 ms

A systematic 75 ms offset, not scatter. The cause is in the firmware, at adafruitESP32Feather_s3_usb.ino:786 and :847:

unsigned long currenttime = millis() - startTime;   // top of the pass
...
readUnits(8, &current_weight);                      // ~93 ms of conversions
...
emit(MSG_WEIGHT, currenttime, current_weight);      // stamped with the OLD time

Every weight sample is timestamped ~93 ms before the reading it carries was finished. The stamp is taken at the top of the pass; the value is the mean of eight conversions taken over the following 93 ms. So the load trace is systematically attributed earlier than it happened.

That is why the two views disagree, and the size matches: the board counts from the top of the pass, the recording can only count from the sample reporting that read, and the acquisition read is 93.4 ms. The residual few ms is the clock model absorbing the fixed stamp-to-transmit lag into its offset.

Neither latency figure is wrong. They measure from different origins and both are correctly labeled — the report says "pass start &rarr; trigger" for one and "landing &rarr; stimulation" for the other. What is wrong is the sample timestamp, and it affects more than this analysis: anything that asks "when did the load change" is reading a trace shifted ~93 ms early.

Not fixed here, deliberately. The obvious change — stamp at read completion rather than pass start — alters the meaning of mcu_time_ms in every recording, and therefore what the clock model is fitting and what t_ms means. That is a schema-level decision, not a bug fix to slip in at the end of a session. It needs Shayok's call on whether existing recordings should be reinterpreted or left as they are.

Filed as its own item rather than buried here: see item 14.

10. Persist the display rotation and calibrate touch — done

Closed 2026-08-10. It had already bitten: the panel was found running upright after a reboot, displaying a layout built for sideways.

Both orientations are now first-class, and the operator chooses with a Rotate the Screen icon on the desktop (raspberry-pi5/desktop/rotate-pegboard.sh). The choice is written to ~/.config/pegboard/orientation and re-applied at login by an entry in ~/.config/labwc/autostart.

Upright is the default — it is what the panel does with no configuration at all, so if the script, the config file and the autostart entry all vanish, the display still comes up in an orientation the interface is designed for.

The root cause, which was not the rotation

The whole touchscreen design lived inside @media (max-height: 820px). Upright the viewport is 1560 px tall, so none of it applied and a 60 mm-wide panel was rendered with desktop styles: fields clipped to slivers, two charts squeezed side by side, the status strip running off the edge. The condition is now "short or narrow". Either dimension being panel-sized is what identifies a panel.

Portrait-specific layout is a separate block at the end of the stylesheet — media queries add no specificity, so placed earlier it was overridden by every lamp and dialog rule that followed. Stacked charts, one field per row, two keys per row, a wrapping status strip.

Three things that did not survive rotation on their own and now do:

  • Plotly does not track its container. A ResizeObserver on .graph-container resizes both charts.
  • The metadata sheet is positioned in absolute pixels over the chart it covers, measured once. It is re-measured on any re-layout.
  • The sheet covers the histogram, not both charts. Covering both in portrait meant STREAM appeared to do nothing — no trace was visible. The room comes from the grid instead: the histogram's row grows while the sheet is open.

Touch needs no calibration matrix. labwc is told to map the panel's touch device to the output in ~/.config/labwc/rc.xml (<touch deviceName="Waveshare Waveshare -079-HD" mapToOutput="HDMI-A-2">) and applies the output transform to touch coordinates itself. Still unconfirmed by a human finger in both orientations — verified by configuration, not by a tap.

Verified on the panel: every control, field, dialog, the on-screen keyboard and the calendar fit inside the viewport in both orientations, with no page scroll and no clipped text.

11. Validate the analysis package against real v3 data — done

Closed 2026-08-10, against six real sessions (two from 2026-08-07, four from 2026-08-10) rather than the two originally available.

The check that matters compares two independent measurements of the same events: the Pi's intervals, derived from t_ms through the fitted clock model, against the firmware's own figures. Synthetic data cannot exercise that.

That 4 ms agreement is the real result here: it says the clock model, the unified timebase and the event recording are all sound on real data.

Now a permanent regression test, test_real_v3_sessions in tests/test_pegboard.py. It skips silently where experiments/ is absent, so a clean checkout still passes.

What it turned up

The first inter-peg interval is not an inter-peg interval. It disagreed with the firmware by 621–683 ms in every session, consistently, while every other interval agreed to 4 ms. The cause is real and permanent: timer_start is stamped when the operator presses the button, but the firmware sets its own reference only after reset_scale() has re-tared — tare(10) plus get_units(40), about 50 conversions, ~590 ms at 85 SPS.

So ipis_ms(include_first=True)[0] contains roughly 600 ms of scale settling, during which the participant may already be moving. It is a coarse reaction-time proxy at best. Documented on both methods; the data-quality comparison against the firmware should start at index 1.

Not changed: the firmware could set startTime before re-taring instead, which would make the first interval meaningful. That moves a tuned constant in the start-up path, so it is left alone deliberately — flagged here rather than fixed.

13. Data-transfer script — done

Closed 2026-08-10. tools/fetch_sessions.py. Operator walkthrough is in OPERATOR_GUIDE.md, "Copying the data onto another computer".

Written in Python rather than PowerShell, at Shayok's request: one implementation for Windows, macOS and Linux instead of a Windows-only script that could not be exercised here. That decision paid for itself immediately — the whole thing was run against the live Pi, rather than shipped on the strength of a static syntax check.

Standard library only, and no SSH library: it shells out to ssh and scp, which ship with Windows 10 1809+, macOS and every Linux. A locked-down study PC needs nothing but Python — no virtualenv, no pip, no paramiko.

The questions the original note left open, and how they were answered:

Each session is staged in a temporary directory and moved into place only once verified, so a session directory never exists at the destination in a half-copied state — which is what makes the "already present" test safe to trust in the first place.

The priority-order guesses in that document's §3 were half right. -N "" and double-clicking, the top two, were both fine. What actually broke was not on the list at all.

The two bugs it found — both Windows-only, both invisible on Linux

Every multi-line script sent to the Pi arrived with CRLF line endings. ssh_run passed the script through subprocess's text mode, which translates \n to the local line ending on the way out. On Windows bash therefore saw a carriage return on every line:

bash: line 1: $'\r': command not found
sed: -e expression #1, char 10: unknown option to `s'

The inventory call failed on the very first real Windows run. This would have failed on every Windows machine, always — the platform the tool was written for was the one platform it could not talk to the Pi from.

The same mechanism put a stray carriage return into the Pi's ~/.ssh/authorized_keys, which survived only because it landed in the key's comment field. Both paths now send bytes. The Pi's authorized_keys was cleaned by hand afterwards and both keys still authenticate.

And the error message blamed the password, which was the one thing that was fine — the login had already succeeded. That is worse than the bug: it sends an operator to re-type a correct password indefinitely. Two changes:

  • ssh's exit code 255 — "I could not log in", the only failure a person can fix by typing again — is now told apart from every other error, and offers a retry in place rather than giving up. Raised by Shayok, who asked the right question about the wrong failure.
  • Every other non-zero exit now says the Pi logged us in and ran the request, and shows the Pi's own words instead of guessing.

tools/build_docs.py could not run on Windows at all. read_text() and write_text() with no encoding use the locale code page, which is cp1252 here, and the documentation is UTF-8 — it died on the first em-dash it met. Fixed the same way: the encoding is now stated rather than inherited. Both bugs are the same mistake in different clothes, which is worth remembering: anything platform-dependent that Python will guess for you, state explicitly.

Four more, found only by putting it in front of an operator

None of these would have been found by running the checklist. They came out of one real run by somebody who had not written the thing, and they compounded: together they sent a set of recordings somewhere nobody chose, in a form the person who asked for them could not open.

The folder picker opened behind the console. The tool knew this could happen — it printed "if you cannot see it, check behind this one" — and a printed warning turned out to be no protection at all. The failure is not that the operator has to hunt for the window. It is that the console appears to have frozen, so the natural response is to press Enter to unstick it; that keystroke reaches the invisible dialog, which accepts whatever folder it opened on. The operator reported both halves without connecting them: "I wasn't prompted where I wanted to put them" and "it seems to require me to press enter". Those are one bug. The dialog is now forced to the front (-topmost, lift, focus_force, and a real parent), and the warning that stood in for doing so is gone.

--dest was overwriting the operator's remembered folder. The picker opens where it opened last time, which is a good idea, but every run recorded its destination — including scripted ones. A path-handling check (1.8) ran with --dest pointing eleven directories deep into a scratch folder, and that silently became the default the next operator was offered. Only what a person picks by hand is remembered now. The general form: a convenience that learns from its input must not learn from its tests.

Staging directories were handing the data restrictive permissions. tempfile.mkdtemp creates its directory 0700, which on Windows means a permission list naming the creating token rather than one inherited from the destination — and moving a directory keeps its permissions instead of re-inheriting them. Every session carried the restriction out of staging with it. Invisible on a normal run, because the creator and the reader are the same person. Under the launcher's elevation they are not, and the delivered recordings could not be opened by the user who asked for them — after copying and SHA-256 verifying perfectly. Staging is now a plain mkdir, which inherits.

It hung after "Found it." until somebody pressed a key. Reported from the rig — "it seems to require me to press enter before it changes from found pi to asking pi what recordings it has" — and initially, wrongly, put down to console QuickEdit mode. It was real. key_auth_works runs ssh … true for its exit code alone, and did not redirect stdin; ssh forwards its own stdin to the remote command, so given an interactive console it sat there reading the keyboard. The operator's Enter was what released it.

It is invisible to every automated check in this document, because those run with output piped, and a pipe hits EOF immediately. It only appears from a real console — which is the only way an operator ever runs it. That is the whole lesson: a test harness that redirects the tool's streams has quietly changed the thing it is testing. Both that call and the scp calls now close stdin explicitly; a dry run that used to hang indefinitely finishes in one second.

That third one is the one to remember: the transfer reported complete success and the data was unusable. Every check the tool performs is about whether the bytes arrived, and not one of them asks whether anybody can read them.

With those three fixed, the run was repeated and the picker appeared in front, on the folder intended: 8 sessions, 40 files, all 40 verified against the Pi by .NET Get-FileHash as well as by the tool itself.

Flakiness that turned out to be the address, not the transfer

Repeated runs during the checks failed perhaps one time in four, with scp: Connection closed. It looked like intermittence in the transfer and was not. The checks were addressing the Pi as raspberrypi.local, and by then that name resolved to four addresses:

addressstate
fe80::…%25 link-localthe cable — answers
192.168.1.100dead, because the launcher had put the link back on DHCP
10.33.244.244the Pi's guest-Wi-Fi address — client isolation blocks it
2620:123:5020:33:…global IPv6 over that same Wi-Fi

ssh takes whichever address comes back first and falls through on failure, spending ConnectTimeout on each dead one. Every failed run took 18.5 s and every successful one 6.2 s, which is what gave it away; six scp calls to a single address ran 6/6 in ~650 ms each. An operator never meets this, because the tool addresses 192.168.1.100 over the configured link, which is one address. It is a property of the name.

It did expose a real gap, though. scp cannot take an IPv6 address the way ssh can — the colons in the address are indistinguishable from the colon separating host from path, so it needs user@[fe80::1%eth0]:path. Given the bare form it reports scp: Connection closed, which reads like a network fault and is a quoting one. Now handled by scp_target().

Two more things the failures showed, both now fixed: a session that failed to copy said only "could not be copied" and discarded scp's explanation, and a session that failed verification said only "arrived damaged" without naming the file or whether it was absent, short, or simply different. Neither is actionable. Both now say which and why.

Stressed afterwards, because "intermittent" is not an acceptable answer for the data path of a study. 100 consecutive copy-verify-delete cycles over the cable against a single address:
clean100 / 100
failed0
tool's file count disagreeing with the disk0
per cycle8 sessions, 40 files, every one SHA-256 verified
seconds per cyclemin 4.4, median 4.8, max 5.4

The spread is the point as much as the count: 4.4 to 5.4 seconds across a hundred runs is a transfer doing the same thing every time. The failures that prompted this took 18.5 s, which was the tell.

Each cycle deleted the destination and copied everything again, so this is 800 scp invocations and 4000 verified files, not one copy checked a hundred times. The file count on disk was counted independently of what the tool reported — a tool that miscounts its own successes would otherwise pass its own test. The Pi still held 8 sessions and 40 files at the end.

The harness is stress.py, deliberately kept out of the repository: it is scaffolding for one question, not a test anybody should have to maintain.

The operator guide now shows the run

Six screenshots of the real thing, 40- to 45- in screenshots/operator/: the folder picker, the recording chooser, the copy part-way through with the bar at 62%, the summary, the confirmation listing what would be removed, and the Pi cleared.

They were photographed by driving the real windows, which turned out to be its own lesson. SetForegroundWindow is refused to a process that does not already own the foreground, so keystrokes sent to a window went wherever the operator's focus happened to be — at one point four consoles were stacked up talking over each other, which Shayok spotted from the screen before the logs showed it. The dialogs are now driven by posted messages (BM_CLICK, WM_CLOSE), which need no focus, and each is captured in its own short-lived process with the script asserting that exactly one window of its own exists.

Two details worth keeping for whoever regenerates these. Capture DWMWA_EXTENDED_FRAME_BOUNDS rather than GetWindowRect: the latter includes the invisible resize border, so the first attempt caught a strip of the desktop behind it — which is a privacy problem in a page published to neuralascension.com. And the copy is quick enough that a bar part-way through is a matter of luck: 8 sessions were done in under three seconds.

The Windows launcher

tools/fetch-sessions-windows.cmd, copied to the study machine's Desktop as setupInterfaceForPiDataTransfer.cmd. It does the round trip an operator cannot be asked to do by hand: elevate, name the adapter, put the machine on 192.168.1.50, check the Pi answers, run fetch_sessions.py, then put the network back — DHCP, original adapter name, recorded beforehand rather than guessed.

This does not walk back the "Python, not PowerShell" decision above. The copying is still fetch_sessions.py and still identical on three platforms; the wrapper only does the two things Python cannot do without administrator rights.

The restore runs on every exit path, including the Pi not answering. A failed attempt must not strand a study PC on a fixed address with no route to the internet — that turns a missed transfer into a machine somebody has to fix.

Verified by stubbing the mutating commands and running all five paths: already-configured, needs-configuring, /keep, Pi-not-answering, and software-not-found. That found timeout /t 3 aborting outright ("Input redirection is not supported") whenever the script's input is not a console — replaced with a ping sleep, which has no such opinion.

fetch_sessions.py also gained a progress bar, counted in files rather than bytes because the inventory gives the exact file count before anything is copied. It draws only on a real console, and falls back from box-drawing characters to ASCII where the console's code page cannot encode them — the same lesson as the two bugs above, applied before it could bite.

Choosing which recordings to copy

Added 2026-08-11 at Shayok's request, after the first real operator run: the window that appeared asked where to put the data, and there was nothing that asked which recordings to take. A tick-list now opens after the Pi's contents are known — subject, date, session number and file count per row, everything ticked to begin with, so doing nothing gives the old behavior.

It is skipped wherever stdout is not a console, and by --all. A window nobody can answer would hang a scheduled run, and every check in this document is run that way.

Verified by building the real window and driving its buttons rather than by inspection — tkinter.Tk is wrapped so the dialog schedules a callback on itself as it opens, which exercises the actual widget tree: all ticked gives 6 of 6; None then copy gives none; None then All gives 6 again; unticking two gives exactly the other four; Cancel and closing the window with the X both return nothing, which the caller treats as "copy nothing" rather than as "copy everything".

Clearing the Pi — new, and deliberately awkward

Also 2026-08-11, at Shayok's request. Until now the rule was absolute: the Pi is the original and nothing is ever removed from it. That rule was right and is still the default; what was missing was any sanctioned way to act otherwise, so the alternative was somebody deleting directories over ssh by hand, which has none of the checks below.

After a transfer the operator is asked whether to clear from the Pi the recordings that are safely on this computer. Default no. Then:

guardwhy
never offered unless both stdin and stdout are a consoleoutput redirected to a log is a scripted run whatever stdin is attached to
every session re-verified against the Pi's hashes at that momentthe copy happened minutes ago; the question is whether it is good now
a session with no closed_utc is refusedit was never closed, so the rig may still be recording into it
the session name must be exactly subject/date/number, with no shell metacharactersthis is the only destructive command the tool builds, so its inputs are checked rather than trusted
the operator types DELETEa keystroke can be stray; a word cannot

Anything failing a guard is listed with its reason and left on the Pi. rm -rf is scoped to <remote root>/<subject>/<date>/<number> and nothing else, and --keep-on-pi suppresses the offer entirely.

Verified by driving offer_remote_delete with a stubbed ssh_run so nothing could reach the Pi: declining, accepting-then-pressing-Enter, typing yes, typing lowercase delete, and a scripted run all issue no delete; only the typed DELETE does. The name check rejects ../../etc, A/B/C; rm -rf ~, A/B/$(whoami), ` A/B/id , A/B/* and paths with spaces or the wrong depth. session_is_open treats missing, unreadable and unparseable session.json` as open — not knowing is not the same as knowing it is finished.

Exercised on the rig, 2026-08-11. Shayok typed the confirmation himself — Windows refuses keyboard focus to a background process, and an irreversible deletion of research recordings is the wrong place to work around that. Before it ran, both local copies were checked independently of the tool with .NET Get-FileHash against the Pi: Desktop\testingDataTransfer 40/40 and Documents\pegboard-data 40/40, nothing mismatched, nothing missing. The tool then re-verified all eight sessions itself, held none back, and removed them. The Pi went from 8 sessions and 40 files to 0 and 0; both local copies still read 40.

It removes the session directories and leaves the subject and date folders in place, empty, so the next recording lands where it always did.

One wording fix came out of watching it: the confirmation said "the copy on this computer becomes the only one" when there were two on that computer. It now reads "what is on this computer becomes the only copy".

The original note, for reference

Raised 2026-08-07.

A script the user double-clicks on a Windows PC that copies the pegboard recordings off the Pi into a folder they pick from a normal file-explorer dialog. Run when the Pi is connected to the Windows machine by Ethernet.

What is already known

  • The Pi's Ethernet is a static 192.168.1.100/24, NetworkManager profile MS-Study-pi. The Windows machine has to be on the same subnet — either a static address in 192.168.1.x or a crossover/direct link with one assigned. Worth deciding whether the script should detect and explain this, because it is the most likely failure and the least obvious to a non-technical user.
  • Recordings live at /home/remyelin-pi/Documents/Code/pegboard/experiments/<subject>/<date>/<session>/, five files each, a few hundred KB per session.
  • ssh/sshd are enabled on the Pi, user remyelin-pi.
  • Windows 10 1809+ ships OpenSSH, so scp is available without installing anything. That is probably the whole transport.

Questions to settle before writing it

  • Everything, or only what is new? Copying the whole tree every time gets slow and risks overwriting. Incremental — skip sessions already present at the destination — is better but needs a comparison rule.
  • Authentication. Password prompt each run is simplest and needs no setup; a key pair is smoother but has to be installed on every PC that will be used.
  • Verify after copy. These are research recordings; a size or checksum comparison before reporting success is cheap insurance.
  • Move or copy? Almost certainly copy — leave the Pi as the primary until someone deliberately clears it.
  • Shape. A .ps1 doing the work with a .bat wrapper so it is double-clickable, or a single .bat. PowerShell gives a real folder picker via System.Windows.Forms.FolderBrowserDialog.

The operator-facing part

Same audience as the operator guide: it should say what it is doing, where it put the files, how many sessions it copied, and — if it fails — whether the problem is the cable, the network, or the Pi. A bare error is no use to a research associate.

14. ~~Weight samples are timestamped ~93 ms early~~ — done

Found 2026-08-10 while reconciling the two latency views, which is exactly what having two of them was for. Closed 2026-08-10 with option 2.

adafruitESP32Feather_s3_usb.ino stamps a weight frame with millis() read at the top of the acquisition pass, then spends ~93 ms in get_units(8) before emitting that stamp with the resulting value. Every sample in every recording is therefore attributed about one acquisition read earlier than the measurement it represents.

Consequences, in order of how much they matter:

  • Anything asking "when did the load change" reads a trace shifted ~93 ms early. That includes the landing instant this report reconstructs.
  • The clock model absorbs it. The fit is a lower envelope of (mcu, arrival); a constant 93 ms stamp-to-send lag on every weight frame goes straight into the offset. So t_ms for a sample lands near when it was sent, and the error partly cancels — which is why nothing looked wrong for months.
  • Stimulation timing is unaffected. GPIO26 edges are stamped by the Pi's kernel at interrupt time and never touch this path. Every latency figure that ends at the trigger edge is sound.

The options

  1. Stamp at read completion. One line moved. Correct going forward, but mcu_time_ms changes meaning, so the clock model fits something different and old recordings are no longer directly comparable to new ones.
  2. Emit both stamps — pass start and read completion — and let the analysis choose. Costs one field on the wire, keeps old data interpretable, and makes the ~93 ms explicit rather than implicit.
  3. Leave it and document it. It has been this way for every recording ever made, the error is nearly constant, and the clock model already hides most of it.

Option 2 is the one that loses nothing.

What shipped

Option 2, as schema v4. The firmware emits both stamps on every weight frame:

Weight: %.5f, Time: %lu, ReadTime: %lu, Seq: %u

Time is the top of the acquisition pass, ReadTime is when the read completed. samples.csv gained one column, mcu_read_ms, and the clock model fits on it where it exists, falling back to mcu_time_ms for v3 recordings. ReadTime is parsed as optional, so a v3 board and a v4 Pi still work together.

The analysis package reads both versions (SUPPORTED_SCHEMAS = (3, 4)) and exposes the difference rather than hiding it: has_read_timestamps, acquisition_lag_ms(), clock_model(), mcu_to_pi_ms(). Old recordings stay directly comparable, and the ~93 ms is now explicit instead of implicit.

Documented in DEVELOPER_GUIDE.md §6 and, for the research associate, in ANALYSIS_GUIDE.md.

Decided, for the record

No self-termination. targetWeight stays above what 25 pegs weigh, so a run never ends by itself. A knock to the table could otherwise both end a session early and register a false placement. The operator always stops the run.

Task time is not recording time. session.json now carries task_duration_ms (timer start → last peg) alongside recording_duration_ms. They differ by more than 3× on a typical run, and reporting only the latter was actively misleading.

A shutdown must never be queueable. Socket.IO buffers emits while disconnected and replays them on reconnect, so a shutdown pressed against a dead server fires whenever the server next starts — potentially unattended and mid-session. Both power actions now refuse to send unless the socket is connected, and the dialog closes itself if the link drops.

Storage is a 1 TB NVMe, not an SD card. / is nvme0n1p2, ext4 noatime, ~885 GB free. More power-cut tolerant than an SD card, but not immune — the shutdown path still matters, and it also disarms the stimulator.

  • Emoji icons, not SVG. Button icons are the emoji the operator already knows. SVG line icons remain as an automatic fallback if color emoji are unavailable (e.g. after a card reimage drops the manually installed font) — detected at load by a canvas probe that sets .no-emoji on <html>. Both paths verified rendering.
