What you see, what you hear, and how old both are#

The operator's question, verbatim: "what I'm looking at, what I'm hearing, in which order, and how delayed is this from the raw data collection."

You see it first, by about 97 ms on the shipped default device — and that gap is mostly a settings choice, not a law of physics. On an NP2.0 probe on a OneBox:

path delay from the probe sample what dominates it
eye — trace on screen ~19 ms the display publishes at ~50 Hz
ear — sound from the speaker ~116 ms the audio device: 99.9 ms of output latency plus a 15 ms ring

So a spike was on screen roughly 97 ms before you heard it — as measured, on what was then the shipped default device.

This measurement is what made the default change, so the "116 ms" row is now historical. The ear figure above was taken when Pa_GetDefaultHostApi() chose the device, which on Windows means MME. Since 2026-08-25 AudioWorker::findDefaultFollower() ranks the follower endpoints by hostApiRank() and takes the fastest — DirectSound's Primary Sound Driver (rank 0) rather than MME's Sound Mapper (rank 9). Following the system default should therefore now land near the ~37 ms row of §2 rather than the ~116 ms one, and a realistic figure on real speakers is ~47 ms.

The eye/ear numbers here have not been re-measured against the new default. Re-running python ripple_tools/measure_av_latency.py is what would replace this row; until then, treat 116 ms as the cost of MME and not as the cost of the shipped configuration.

Changing the audio device is still the single largest latency win available anywhere in this document — it is now simply made for you by default rather than left to the operator. That is not a small offset — it is about four display frames — and it matters whenever the two are being compared by eye and ear at once, which is exactly what a spike monitor is for.

Numbers live in ../RecordingTests/CLOSED_LOOP_LATENCY.md by convention; this page is the METHOD and the reasoning. The measured cells are repeated here because the ordering claim is meaningless without them.

1. The two paths, and why they are so different#

Both start from the same ring buffer of probe samples. They diverge immediately.

                        data.npx.raw  (30 kHz)
                              |
        +---------------------+---------------------+
        |                                           |
   DisplayProcessor                           AudioProcessor
   bins + publishes ~50 Hz                    filters 300-6000 Hz,
        |                                     subsamples to 44.1 kHz
   WebSocket (binary)                               |
        |                                      mAudioData ring
    browser draws                                   |
        |                                     PortAudio callback
       EYE  ~19 ms                                  |
                                              host API + device
                                                    |
                                                   EAR  ~116 ms  (default)
                                                        ~47 ms   (best real device)

The display path is short because it is allowed to be lossy: it bins, publishes what it has, and the browser draws it. The audio path cannot be lossy — a gap in audio is an audible click — so it is buffered, and the buffering is almost entirely outside SpikesPeak.

2. Measured, NP2.0 on a OneBox (2026-08-25)#

term median notes
source_lag_mean_ms 1.00 ms how far behind the acquisition writer the audio converter runs
output_latency_measured_ms 99.90 ms what the device is actually doing, per callback
output_latency_ms 91.43 ms what PortAudio PROMISED at open — see why this is not the one to trust
audio_ring_depth_ms 15.11 ms converted audio queued ahead of the frame being played
raw → ear ~116.0 ms source lag + ring depth + measured output latency
raw → eye 19.2 ms median inter-frame gap, n = 973, p95 20.3 ms

The same measurement against the simulated NP2.0 source gives the same audio figures and a 20.0 ms display interval. That the figures are indistinguishable is the point: none of this latency is the probe's. It is the host audio stack and the display cadence, so it is the same on any source, and it will be the same on PXIe. (Which is worth confirming rather than assuming — see §5.)

The output latency is not ours to fix — but it IS ours to choose#

91.4 ms is what the MME host API reports for the selected device. Nothing in SpikesPeak can shrink it. Choosing a different device can, and by a lot — so the audio panel's device picker is a latency control, not a convenience.

Three things this overturns#

0. The default now follows this table. These measurements are no longer only advice: the ranking in AudioWorker::hostApiRank() is derived from this table, and the device picker lights a dot on the fastest route to each speaker. What follows is therefore the justification for a shipped behaviour, not a suggestion the operator has to act on.

1. "Use WASAPI" is wrong on this machine. It is the usual advice and it fails here: WASAPI refuses to open every real output except a virtual NoMachine device. The advice that survives measurement is DirectSound → ASUS VE278: same physical speakers as the MME default, and 13.06 ms instead of 99.90 ms.

2. PortAudio's promised latency is not merely imprecise, it is ANTI-correlated here. DirectSound promises 120 ms — the worst figure in the table — and measures 8.7–18.9 ms, the best. WDM-KS promises 10 ms and measures 19.9 ms. Ranking by the promised number picks almost exactly the wrong device, which is what the first version of the comparison script did before its own output was read properly. Trust output_latency_measured_ms; the promised figure is buffer geometry, not behaviour.

3. The ring depth matters as much as the output latency, and moves independently. WDM-KS SPDIF has the worst measured output latency of the low-latency group (19.89 ms) and the best total (~23.4 ms), because its ring sits at 2.46 ms while DirectSound's sits at ~30 ms. Optimising output latency alone would have chosen wrongly. This is why the earlier figure in this document — "≥ 92.4 ms" — was a lower bound: it omitted the ring, which had not yet been measured.

So does the ordering ever flip?#

No, not on this machine. Even the best total (~23 ms on WDM-KS SPDIF, which is a digital output and may not reach a speaker at all) is at best level with the ~19 ms display path, and the best practical option for the monitor speakers is ~47 ms. You still see it before you hear it — but the gap narrows from ~97 ms to ~28 ms simply by changing the device.

3. What is instrumented, and what it costs#

All of it reaches the GUI through the existing audioState event, which the audio dock polls at 4 Hz only while it is open.

field computed cost
source_lag_mean_ms, source_lag_max_ms on the processor thread, once per 1 ms tick 3 relaxed atomics at 1 kHz
output_latency_ms once, when the stream opens free
output_latency_measured_ms in the PortAudio callback 1 subtract + 1 relaxed store, ~690 Hz
audio_ring_depth_ms in the callback, from operands already loaded 1 subtract + 1 relaxed store
device_underflows, starved_callbacks in the callback, inside branches that only run when audio is already broken zero in the healthy case
input_peak_counts, output_peak per audio sample, one fabs + one max 44.1 kHz, not the 30 kHz path

Nothing above touches the 30 kHz acquisition loop. The per-sample work is on the 44.1 kHz audio path, which is a different thread and a different budget.

Two mistakes worth not repeating#

The first version computed the backlog at POLL time, reading mCurrSourceDataInd — a plain int64 owned by the processor thread — from whichever thread happened to call audioStateJson(). That is a data race, and it can never observe the peak, which is the only value a worst-case claim can rest on. It now accumulates on the owning thread, once per tick, and the poll drains it.

The first version also claimed the ring depth was unmeasurable, "owned by PortAudio's callback cadence rather than by anything measurable here". It is measurable — from inside the callback, which is where that cadence lives, and where both operands were already in registers.

4. Reproducing#

python ripple_tools/measure_av_latency.py "NPX 2.0 Multishank (OneBox)"

The script brings the rig up, counts binary frames in the page over a real interval (rather than trusting a configured rate), polls audioState, and tears down gracefully.

Audio commands ride a BINARY frame on channel 0x218, not the text frame rig.send() uses. A text frame carrying the same JSON is dropped silently — no error, no log. Use rig.send_module(0x218, {...}). This cost real time: text commands appeared to work only because the operator happened to be clicking the same controls in the GUI at the time.

5. Not yet measured#

The instrumentation is source-agnostic, so these should match the OneBox figures — but "should" is not "does", and the whole point of this page is that the answer was measured.

NP1.0 is the interesting one: its audio is taken from the probe's native AP band with no filtering, where NP2.0 derives the band inside the audio processor. That is a different amount of work on the same path, so the source lag could differ — the only cell here where a different answer would not be surprising.
