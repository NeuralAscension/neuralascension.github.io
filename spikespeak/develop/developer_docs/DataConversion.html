Data conversion — the sidecar contract, and what each export derives from it#

Two Python packages turn a SpikesPeak recording into a format the analysis ecosystem reads:

package target entry point
python/spikespeak_convert/ SpikeGLX (.bin + .meta) python/convert_to_spikeglx.py
python/spikespeak_postprocess/ Open Ephys (binary format) python/convert_to_openephys.py openephys

The same tree also holds the loader (spikespeak_postprocess.Recording), which reads a recording directly as NumPy/xarray without converting anything — documented in python/README.md.

Operator-facing instructions are in user_docs/Exporting-Recordings.md. This file is the contract and the reasoning.

The GUI's Convert panel runs exactly these two scripts (#77). WebSocketServer starts python/convert_to_spikeglx.py or python/convert_to_openephys.py openephys as a QProcess and writes into <recording>/spikeglx_format or <recording>/open_ephys_format, then reports a conversionResult event judged on output actually produced, not on the exit code alone. It refuses while a source is held — conversion reads and writes the same disks the recorder uses — and it refuses, saying so, when it can find no Python interpreter at all (convertPythonPath() prefers a .venv beside the repo, the one install guaranteed to have numpy, then whatever is on PATH; it does not check that numpy imports, so a bare Python that lacks it fails in the converter's own words instead). Python is not a runtime requirement of the backend and must never become one. Nothing in this document is bypassed by converting from the GUI.

1. The sidecar is the interface#

Every .bin is written with a <file>.bin.json sidecar by RecordProcessor. A converter's job is to translate that sidecar, never to re-derive what it says. Everything below is metadata_version 2; version 1 predates the scale, frame, columns and acquisition blocks and carries only band/channels/rate.

block what it settles why a converter must not re-derive it
frame bytes, header[], payload_dtype, payload_channels, layout The stride. Guessing it is the whole class of "every sample is shifted" bugs.
scale volts_per_count, gain, provenance, formula Two of the three terms differ between probe variants. See §3.
columns per-channel channel, electrode, shank, reference, gain, index_space The applied map. Assuming a default map puts sites on the wrong shank.
acquisition.imro text (the applied map verbatim), probe_type_id_str, provenance Already in SpikeGLX's own format — nothing to translate.
acquisition.probe part_number, serial, type_id Identifies the electrical spec. See §3.

Frame layouts#

NPX    [uint32 ticks][uint16 sync][int16 × payload_channels]     frame.bytes = 6 + 2·N
NI-DAQ [float64 seconds][float64 × payload_channels]             frame.bytes = 8 + 8·N

num_channels is the payload count, not the stride. Mistaking one for the other is the failure SourceFile.validate() exists to catch: the file size must divide exactly by frame.bytes.

channels: [] with num_channels: 0 is a SENTINEL, not an empty recording. It is what the writer emits when no filter was applied — "the whole block was written and the reader infers N from the file size" (src/core/RecordingMetadata.cpp) — and it is the common case, because omitting channels: from a profile means record-everything, which every operator-facing hardware profile does. A reader that takes it literally rejects exactly the recordings an operator is most likely to make: python/spikespeak_io.py did, on a good 232 MB NP2.0 file that both converters read without complaint, until it was found on the rig on 2026-09-01. frame.bytes gives N directly, so there is nothing to guess — but keep the hard refusal for a NON-empty channel list that disagrees with the frame. Both directions are pinned by python/tests/test_reader_all_channels.py.

2. Band → stream mapping#

band SpikeGLX stream Open Ephys note
raw imec0.ap continuous stream NP2.0 wideband
ap imec0.ap continuous stream both refuse — see §4
lfp imec0.lf continuous stream
adc obx0.obx continuous stream OneBox 12-channel analog
adc_di — continuous stream no SpikeGLX equivalent exists
nidaq nidq continuous stream
nidaq_di nidq continuous stream cannot share a run with nidaq

The band string comes from the profile's output_filename, and both converters key their tables off it — so renaming a band in a config makes it unconvertible (loudly).

data.lfp and data.spike are not in this table and never will be. They are registered as CircularBuffer<float,float> (src/core/Utils.cpp:139-140) with no matching interpreter, are absent from every recordings: block, and listing one makes configure() fail. That is CLAUDE.md's do not record what can be recomputed enforced by the type system, not a conversion gap.

3. Probe identity decides the microvolt scale — and it is recorded#

volts_per_count = FULL_SCALE_V / 2^adc_bits / gain, and two of those three terms differ between NP2.0 variants:

variant shanks adc_bits gain µV/count imro type
NP2000 / NP2010 (prototype) 1 / 4 14 80 0.7629 21 / 24
NP2003 / NP2004 (commercial) 1 12 100 2.4414 2003 / 2004
NP2013 / NP2014 (commercial) 4 12 100 2.4414 2013 / 2014

A 3.2× spread. The table lives in src/modules/neuropixels/Npx2Scale.hpp with its three agreeing sources (imec NP2.0 manual p.15, SpikeGLX Metadata_Help.md, Open Ephys Geometry.cpp), and is duplicated in spikespeak_convert.spikeglx.PROBES keyed by part number.

The recording says which one it is. acquisition.probe.part_number comes from np_getProbeHardwareID, so a converter resolves the spec from the file rather than from a flag. --probe still overrides — an operator correcting a mis-stamped recording is real — and when it disagrees with the recording, the export says so in userNotes.

This was wrong in three places at once, and each was invisible. Until 2026-08-28 the recording sidecar hardcoded gain 84 — a value belonging to no variant — while the live view had used the part-resolved value since #65; and the SpikeGLX exporter had only the prototype four-shank spec, so a commercial NP2014 exported as type 24 / imMaxInt 8192 / gain 80 and reconstructed 0.7629 µV/count instead of 2.4414. A uniform scale error changes no relative comparison, no detection and no latency figure, which is exactly why it survived.

The blast radius is small, and worth stating precisely rather than as a blanket warning. Of the 53 NP2.0 sidecars in RecordingTests/, 46 are metadata_version 1 and carry no scale block at all — they never claimed a microvolt, so nothing in them is wrong. Exactly 7 carry gain: 84, all dated 2026-08-26, and all of them bench tests. Counts were never affected in any recording.

4. Why the NP1.0 AP band is refused#

Both converters refuse band == "ap", and this is a property of the recording, not a gap in the tools.

The AP band's per-frame timestamp is not a per-sample clock. Within each 12-sample IMEC packet the stamps advance ≈4.36 ticks/sample and then step back by 8, netting exactly 40 ticks per packet. On a real recording ~8.3 % of frames therefore carry a timestamp that does not advance.

Forcing those to +1 — the only way to keep a sample index strictly increasing — inflates the reconstructed axis to 1.3057× the span the timestamps imply and invents ~110 000 gaps in a recording that may have lost nothing. Open Ephys stores an explicit sample_numbers array, so that would put fabricated sample numbers on disk that nothing downstream could distinguish from real ones.

The refusal is the correct behavior and the message says so, including the remedy: convert lfp (exactly uniform) instead.

Related principle, enforced in both tools: a non-uniform time base is refused, never padded. There is no --force and no --pad. Padding a gap turns a dropped-samples fault into data that looks clean (issue #63).

5. What each export derives, field by field#

SpikeGLX (spikespeak_convert/spikeglx.py)#

.meta key derived from
imSampRate / obSampRate sample_rate_hz (the profile's number — see §6)
imAiRangeMax, imMaxInt the ProbeSpec resolved from acquisition.probe.part_number
imChan0apGain / imChan0lfGain scale.gain from the recording when present, else the ProbeSpec default
imDatPrb_pn, imDatPrb_type same
~imroTbl acquisition.imro.text verbatim when present; a synthesised bank-0 default otherwise, and userNotes says which
~snsGeomMap per-channel columns.shank + columns.electrode, with the part's site pitch
~snsChanMap, snsApLfSy the saved channel list and whether an SY word was emitted
firstSample first frame timestamp ÷ ticks-per-sample

Open Ephys (spikespeak_postprocess/openephys.py)#

structure.oebin field derived from
bit_volts, units scale.volts_per_count from the recording when present (×1e6 for µV bands); the compiled table only as a metadata_version 1 fallback — see §6
channel_metadata.electrode_index columns.electrode
channel_metadata.shank columns.shank
channel_metadata.xpos / ypos derived from the recorded electrode + the part's site pitch; omitted entirely for an unrecognized part rather than guessed
sample_numbers.npy the recorded tick counter — gaps preserved, never padded

6. Known limits#

  • ~~Neither converter reads the sidecar's scale block.~~ Fixed 2026-08-28. Both now prefer the recording's own scale, in this order: an explicit operator override, then scale.volts_per_count from the sidecar, then the compiled table (which remains the fallback for metadata_version 1 recordings, whose sidecars have no scale block). The loader had the same defect and was fixed the same day, separately — Signal.to_microvolts() hardcoded AP 500 / LFP 250 and had no entry for raw at all, so it both mis-scaled NP1.0 recordings made at a non-default gain and raised on every NP2.0 recording. It now follows the same precedence. An NP2.0 raw band from a metadata_version 1 recording raises rather than guessing: the two NP2.0 families differ by 3.2× and a version 1 sidecar does not say which part it was. Covered by python/tests/test_reader_scale.py. This mattered most on NP1.0, whose gains are per channel and live in the applied IMRO: the Open Ephys export used to print "assumes IMEC LFP gain 250 … if the gain was changed in the IMRO panel this is wrong by the gain ratio", and now prints "Taken from the recording: scale.volts_per_count = 4.6875e-06 (provenance applied-map)". SpikeGLX takes imChan0apGain / imChan0lfGain the same way, and its ~imroTbl is the applied map verbatim, so the per-channel gains a SpikeGLX reader actually uses are the ones the probe was configured with. A NON-uniform band is deliberately not collapsed to one number — Open Ephys can carry per-channel bit_volts, and averaging differing gains would be exactly the silent misscaling this module refuses elsewhere. Such a recording falls back to the table until per-channel bit_volts is wired through.
  • sample_rate_hz is always the profile's number, never the device's. RecordProcessor passes the YAML value through. The OneBox ADC is declared 30300 and runs ≈30300.5 — 16.5 ppm. Both converters also report an implied rate computed from the tick counter, which is the honest one.
  • Neither export has been loaded by a vendor reader in a test. Every converter unit test is a self-check — no DemoReadSGLXData, no open-ephys-python-tools, no SpikeInterface. Round-trip verification against a real reader is unclaimed territory.
  • The OneBox ADC band's sync word is unverified. NpxDataInterpreter writes sync = packetInfo->Status >> 6 for every band it serializes, including adc, because interp.npx.adc is the same class. Both converters export whatever is there faithfully; whether it means anything on the ADC band has not been established.
  • Refusals are all-or-nothing. Both tools pre-flight the whole recording before creating any output, so one orphaned sidecar (a .bin deleted to save space) blocks the whole session. Convert the intact bands explicitly with --band.
  • Open Ephys has no output-collision guard. SpikeGLX refuses two bands landing on one stream; the Open Ephys writer has no equivalent. Not reachable with the shipped configs — the recorder's own filenames would collide first.

6a. What a recording carries besides its bands#

file written by what it settles
<band>.bin.json RecordProcessor the frame layout, scale, and per-channel map — §1
<name>_ripple.json RippleDetector the detector's configuration: electrodes, read-out channels, trained µ/σ/threshold, params, stim train
<name>_events.jsonl RippleDetector what the session did: one JSON object per rippleDetected / rippleLatency / rippleStimFired

All three live inside <dir>/<name>/, with the bands. The ripple sidecar moved there on 2026-08-28 — it used to sit one level up, so archiving the recording folder left it behind — and the event log is new the same day. Before it, detections and stim times existed only as live WebSocket messages and did not survive the session.

Neither exporter translates the event log. SpikeGLX has no place for it, and while Open Ephys does define an events directory, writing one has not been built or verified against a reader — so the file is left as JSONL beside the bands rather than half-translated into a format nothing has been shown to read. rippleEnvelope is deliberately not recorded at all: it is recomputable from the band, and writing it would put a file append on the detection path.

7. Adding a band or a probe#

A new band: add it to BAND_STREAM in spikeglx.py and to the scale table in openephys.py. An unmapped band raises SourceError naming the known bands — it is never silently skipped, and it must stay that way.

A new probe: add the part to Npx2Scale.hpp (the backend's authority, which sets what the sidecar records), then to PROBES and _PART_TO_SPEC in spikeglx.py, then to _GEOM in openephys.py. Three places, deliberately: each package installs independently, and a cross-import would make one fail on a machine that has only the other.

Run the tests. From python/, discovery picks up the whole Python suite — the converters, the loader's scale, the reader, the config channel spec and the sync pairing — which has been part of the three-suite gate since 2026-08-30, so this is the same command the gate runs:

python -m unittest discover -s tests -q
