Testing, and how to tell software faults from hardware faults#

This document covers two things that turned out to be the same thing: the unit test suite, and the method for working out whether a failure is in our code or in the rig.

Why this exists#

On 2026-08-20 a Neuropixels 1.0 probe on a OneBox stopped delivering data. Everything the software showed said the rig was healthy:

source.npx.onebox   producing 63,536
proc.npx.display    cycling  1,595
proc.npx.recorder   cycling    638
proc.rippledetector cycling 17,293
acquisition confirmed: true

Not one sample had been read. The operator watched that panel for three and a half minutes. Then Pause did nothing, Disconnect did nothing, the WebSocket stopped answering, and the process had to be force-killed — which on a OneBox leaves the FT601 USB handle claimed and forces a physical power-cycle of the hardware.

Three separate defects, each of which made the next one harder to see:

# Defect Consequence
1 noteCycle() counted poll-timer ticks, not data A dead probe was indistinguishable from a live one, and SourceManager's stall watchdog was structurally incapable of firing
2 np_readElectrodeData returning SUCCESS with 0 superframes matched neither the data branch nor the error branch The failure was silent by construction — no log line, ever
3 np_arm() was called bare on the main thread with no timeout One blocked vendor call killed the Qt event loop, and with it every shutdown path

None of these were hardware problems. The hardware problem was real, but the software's job was to say so, and instead it reported health. The software must not break because the hardware did.

1. Running the tests#

The suite runs on every build and prints a pass/fail banner. You do not have to ask for it:

build.bat            # Windows;  ./build.sh on Linux

──────────────────────────────────────────────────────────────────────────
 SpikesPeak unit tests
──────────────────────────────────────────────────────────────────────────
  ✅ PASS  test_boundedcall      0.78s
──────────────────────────────────────────────────────────────────────────
  ✅ ALL 1 SUITES PASSED
──────────────────────────────────────────────────────────────────────────

and when something breaks:

  ✅ PASS  test_boundedcall      0.78s
  ❌ FAIL  test_redlight_probe   failed
──────────────────────────────────────────────────────────────────────────
  ❌ 1 OF 2 SUITES FAILED

     2/2 Test #2: test_redlight_probe ..............***Failed    0.04 sec

     rerun one suite: ctest --test-dir <build> -C Release -R <name> --output-on-failure

A failing suite does not stop the build. That is deliberate — when something breaks you usually still want the binary so you can run it and debug. The build goes red on screen and still produces SpikesPeak.exe. For CI, configure with -DSPIKESPEAK_TESTS_FATAL=ON and red stops the build.

Other entry points:

ctest --test-dir build -C Release --output-on-failure

ctest --test-dir build -C Release -R test_boundedcall --output-on-failure

Run one suite's binary directly for the most detail — Qt Test takes -v2 for per-assertion output, and a bare function name to run a single case:

build/tests/test_boundedcall.exe -v2      # Linux: build/tests/test_boundedcall -v2

The test binaries need Qt on PATH when run this way (C:\Qt\6.7.3\msvc2019_64\bin), and their stdout does not always survive being piped through Git Bash. When you need the output as data, ask Qt Test for a file instead — this always works: test_boundedcall.exe -o result.txt,txt

Reading a red suite#

The test binaries emit nothing on stdout in this environment — verified 2026-08-24 across every suite, passing and failing alike, whether run through ctest, through a shell, or redirected to a file. So a failure used to print a bare ***Failed with no case name and no QCOMPARE diff, which made debugging a red suite guesswork.

Every suite now writes a Qt Test log via -o <name>.log,txt (see tests/CMakeLists.txt), and scripts/run_tests.py prints it for any suite that fails:

  ❌ 1 OF 18 SUITES FAILED

     FAIL!  : TestOneBoxWavePlayer::stopIsSilentWhenNeverUsed() Compared values are not the same
        Actual   (FakeNpx::calls().size()): 2
        Expected (size_t(0))              : 0

QWARN lines are included deliberately: the bounded-teardown tests report their reason that way.

One suite is written but not built: tests/test_utils.cpp (31 cases). src/core/Utils.cpp is the application's composition root — it holds registerBuiltInTypes(), which constructs every source, processor and interpreter — so linking it into a test drags in the whole application (13 unresolved externals). The helpers it covers are mostly inline in Utils.hpp, but getFileContents() is not, so the file cannot be split without touching production code. The fix is architectural and worth doing deliberately: extract the non-main sources into a SpikesPeakCore static library that both SpikesPeak.exe and the tests link. That one change unlocks unit-testing every processor and source in the codebase, and it is the single highest-leverage next step for this suite.

A machine-readable result is written to <build>/test_status.json on every run:

{ "generated": "...", "total": 1, "passed": 1, "failed": 0, "ok": true, "suites": [ ... ] }

1a. Running both suites on Linux#

Verified end to end on 2026-08-26 (Linux Mint 22.1 / Ubuntu 24.04 base, GCC 13.3.0, Qt 6.11.1, HDF5 1.10.10): 20 of 20 C++ suites, 384 cases and 10 of 10 GUI tests. Before that date the suites had never been attempted on Linux — both postdate the last Linux build by six weeks — so treat anything older than this section as untested rather than as known-good.

A Linux box with no acquisition hardware exercises everything except the vendor call layer: the same ring buffers, interpreters, display processor, recorder and ripple detector that real hardware drives. NPX_HW_ENABLED and NIDAQ_HW_ENABLED are Windows-branch-only, so the PXIe, OneBox and real NI-DAQ sources are simply never registered. A green Linux run closes no hardware row.

The two commands#

./build.sh                                  # configures build/ on first use, then builds + runs the C++ suite

DISPLAY=:0 python3 scripts/run_gui_tests.py --fatal

Pass --fatal. Without it a suite that never ran still exits 0.

Three things that are different on Linux and are not bugs#

  • The source picker has only Sim* profiles. Selecting a hardware profile does not hang half-connected: WebSocketServer broadcasts an explicit "Real Neuropixels hardware (PXI/OneBox) is not available in this build" toast. This is a behaviour only a sim-only build can exercise — Linux is the only place it is checked, so notice if it stops working.
  • source.nidaq.sim still works. The lib-free half of the NI-DAQ module compiles on every platform by design, so every Sim*NiDaq config is available.
  • Test stdout works. The empty-stdout problem that made tests/CMakeLists.txt write per-suite .log files is Windows-specific; on Linux build/tests/test_coretypes prints normally. The log files are still written and are still what run_tests.py prints on a failure.

layout_matrix's portrait half is NOT tested on Linux#

monitors() shells out to PowerShell, is wrapped in except Exception: return [], and therefore returns empty on Linux without raising. pick_monitor() then returns None, the harness prints "no monitor attached; using the default window", and both the landscape and the portrait passes run in the same 1960×1080 window — confirmed on 2026-08-26, where every one of the 16 cells in gui_layout_matrix.json reported viewport 1920x996. The cells pass, because the assertions are written in the fold rule's own live operands and hold at any size. They are still measuring a layout no operator uses.

Do not report the portrait half as passing. Closing this needs an xrandr --listmonitors parser behind the same monitors() contract (stdlib subprocess, no new dependency) and a portrait panel on the box — the 2026-08-26 machine had two landscape monitors, so the parser alone would not have helped it.

Tear down, and mind the operator's browser#

The suite writes into git-tracked developer_docs/images/gui/, so a Linux run overwrites Windows-rendered documentation screenshots. After every run:

git checkout -- developer_docs/images/gui

That pathspec and nothing else — gui_layout_matrix.json and gui_test_status.json are git-ignored and untracked, so naming them makes git abort the whole command and restore nothing.

Kill only the profile the harness launched. Its browsers live under /tmp/spikespeak_guitest_*; a blanket pkill -f brave closes the operator's real windows. Beware that pkill -f spikespeak_guitest also matches the shell running it, which kills your own command instead — match on user-data-dir=/tmp/spikespeak_guitest and signal the pids.

1b. The Python suite — the offline half, and it was ungated until 2026-08-30#

python -m unittest discover python/tests        # 121 tests, ~1.5 s

scripts/run_all_tests.py now runs it, between the C++ suite and the GUI suite. It needs no browser, no backend and no ports, and it finishes in under two seconds — so finding out the offline tooling is broken before an eleven-minute browser run is simply the cheap ordering.

It existed, it passed, and nothing ran it#

Four files, 113 tests, green — and not referenced by run_tests.py, run_all_tests.py, CMake or CTest. They ran when somebody remembered.

That is worse than having no tests there, because their existence reads as coverage. Anyone counting suites saw four Python files and assumed the gate covered them.

What it covers, and why that half matters#

file what
test_spikeglx_convert.py the SpikeGLX converter — tick cadence, sidecar consistency, run-folder naming
test_openephys_export.py the Open Ephys export
test_reader_scale.py the loader's counts→microvolts scale
test_config_channels.py the config channel spec
test_sync_pairing.py the sync pulse pairing every published closed-loop latency passes through

That last one was added on 2026-08-30 and is the reason the gap was worth closing. sync.py's own docstrings record three separate silent off-by-ones, one of which "silently added 1.000 s to a closed-loop latency" — and the function had no test at all.

Its failure mode is what makes it dangerous: a pairing shifted by a whole sync period has identical inter-pulse intervals, the same drift ppm, and the same sub-millisecond fit residual. Every quality metric the module reports looks perfect while every aligned timestamp is a second out. There is no downstream check that catches it.

The test that pins it (test_opposite_end_drops_do_not_shift_everything_by_a_whole_period) builds the exact case: both trains lose a pulse at opposite ends, so the counts are equal — which is what hides it — and both the start- and end-anchored offsets are wrong by a period.

Proved failable: disabling the wrap fix reproduces the bug precisely, reporting a pairing offset of −0.996 s, while the six unrelated cases stay green.

Adding one#

stdlib unittest + numpy only, per CLAUDE.md — no pytest, no new dependency. Put the file in python/tests/, name it test_*.py, and discover picks it up with no registration anywhere.

2. Adding a test#

  1. Create tests/test_<thing>.cpp.
  2. Add one line to tests/CMakeLists.txt: cmake spikespeak_test(test_<thing> SOURCES test_<thing>.cpp) For a component that is not header-only, add its production .cpp to the same SOURCES.
  3. Rebuild. It is registered, run, and reported automatically.

The file shape is fixed by Qt Test:

#include <QtTest>
#include "TheHeader.hpp"

class TestThing : public QObject
{
    Q_OBJECT
private slots:
    void behaviour_statedAsAClaim() { QCOMPARE(actual, expected); }
};

QTEST_GUILESS_MAIN(TestThing)
#include "test_thing.moc"          // MUST match the filename exactly

Things that will otherwise cost you a confusing half hour. Every one of these cost a build cycle while this suite was being written:

  • The trailing .moc include must match the filename exactly, lowercase.
  • Test methods must be under private slots: and return void, or they are silently not run.
  • Use QTEST_GUILESS_MAIN, never QTEST_MAIN — the latter needs a GUI.
  • Testing a QObject whose Q_OBJECT lives in a header with no matching .cpp? Put the header in SOURCES. Otherwise AUTOMOC never processes it and the target fails to link with undefined metaObject / qt_metacall / signal symbols. Listing a .hpp in SOURCES looks wrong but is exactly how you ask AUTOMOC to process a header. This bit test_processor, test_datasourceworker and test_registry — and note the last one needed the headers of the types it stores (IProcessor.hpp, IDataSource.hpp), not its own.
  • Any include chain that reaches ryml.hpp needs LIBS ryml. Utils.hpp, IProcessor.hpp and Npx.hpp all pull it in for config parsing, so even a test that never touches YAML needs it.
  • QVERIFY2 and QCOMPARE are macros, so a comma inside template arguments breaks the parse. QVERIFY2(dynamic_cast<Foo<double, int>*>(p) != nullptr, "…") fails with C2059. Hoist the cast into a named local first.
  • Watch for the most vexing parse. std::vector<Filter> bank(std::size_t(groups)); declares a function, and the range-for over it then fails with "no matching begin/end". Use braces or static_cast.

Framework choice. Qt Test, not GoogleTest or Catch2, because Qt6 is already a hard dependency: the suite adds no third-party code, no FetchContent, and builds offline on the rig machine.

Why tests get the Qt bin directory on PATH. A bare test executable launched by CTest does not inherit a developer shell's Qt path and dies instantly with 0xC0000135 (STATUS_DLL_NOT_FOUND), which CTest reports as ***Exception and which reads like a broken test rather than a missing DLL. tests/CMakeLists.txt resolves the Qt runtime directory once and puts it on every test's environment. This is the same trap that makes the application itself require run_spikespeak.bat.

3. GUI tests — the frontend is a unit too#

The C++ suite cannot reach any of the frontend, and the frontend is where most of what an operator notices actually lives: a control that folds itself out of existence, a toolbar that grows a third row, a column that renders nothing, a stream that loses its label.

python scripts/run_gui_tests.py

──────────────────────────────────────────────────────────────────────────
 SpikesPeak GUI tests
──────────────────────────────────────────────────────────────────────────
  ✅ PASS  live_view                     71.4s
  ✅ PASS  toolbar_layout                54.4s
──────────────────────────────────────────────────────────────────────────
  ✅ ALL 2 GUI TESTS PASSED
──────────────────────────────────────────────────────────────────────────

Same green/red convention as the C++ light, and a machine-readable gui_test_status.json. --only <name> runs one, --fatal makes red a non-zero exit (CI).

Why these are not part of every compile. They need a browser, a backend and ~30–70 s each, which is the wrong tax on an edit-compile loop. Run them when you touch webinterface/, and before a release. The runner starts ONE backend (with --no-browser) and shares it; each test drives its own isolated Chrome on the debug port and closes it again.

Why they are not unit tests in the jsdom sense. fitToolbar() decides whether to fold by measuring real layout — it compares row 1's natural width against the wrapper's available width. A DOM shim has no layout engine: every width would measure 0 and every assertion would pass vacuously. Only a real browser can catch these, so that is what they drive.

toolbar_layout — 15 viewport widths, 1920 → 820#

Asserts three operator-facing invariants at every width:

  1. Never more than two rows. Stated as a requirement: "I don't ever want to go past 2 rows."
  2. No control is ever lost. A control may be hidden, but only if its group has a visible peek chip to reveal it. Folding is allowed; losing a control is not.
  3. No horizontal overflow of visible content.

That third one has a trap worth knowing: folded groups are position:absolute; visibility:hidden, so they are still laid out and still contribute to scrollWidth and to element bounding boxes. A naive overflow check reports them as clipped controls. It did exactly that on 2026-08-21 and a phantom "three controls are unreachable at 820px" bug was one step from being written up. The test excludes anything inside a folded group, which is why it is correct and the ad-hoc check was not.

What the sweep documents today:

widths tier folded
1300–1920 full nothing
820–1280 tb-compact-2 view + source, both behind chips

.tb-compact never engages. The fold goes straight from full to tb-compact-2 between 1300 and 1280, so the intermediate tier — which folds only view — is dead in practice. That is not a failure (every invariant holds), but it means a whole CSS tier is carrying no weight and could be removed, or the thresholds separated so it does.

live_view — traces, labels, strips, pinning#

Covers: traces render at 1/2/3 columns (a sized canvas, and a non-zero row count reported by the column's own WebGL renderer — column.gl.rows, which a renderer that drew nothing cannot fake); the ADC column is labelled with the SDR connector name and its traces are IOn; no column is left saying "Waiting for data…" after play; a control strip collapses when the window is narrowed to 1080px at three columns — width is what makes a column too small, not column count — while the depth readout stays visible; a pin holds the strip open and survives a column rebuild; the vertical layout toggles and still renders; and dataStore.knownStreams is non-empty — the exact reading that was [] during the 2026-08-20 dead-probe session.

Adding a GUI test#

Drop a file in tests/gui/ (underscore-prefixed files are ignored, which is how _harness.py stays out of the run). The harness gives you a backend, an isolated Chrome and a streaming sim source:

from _harness import Gui, Checks

def main():
    ck = Checks()                      # collects ALL failures, not just the first
    with Gui() as g:
        g.live_view(); g.columns(3); g.width(1100)
        st = g.probe("(() => JSON.stringify({...}))()")
        ck.that(st["something"], "why this matters when it fails")
    return ck.report("my test")

Resizing over CDP does not fire resize. Emulation.setDeviceMetricsOverride changes window.innerWidth and re-runs media queries, but the page gets no resize event, so window.onresize handlers and ResizeObservers never run and the layout settles stable-but-wrong. Use Gui.width(), which dispatches the event for you. Do not diagnose the resulting symptom as a layout bug — it presents exactly like one.

Prove a new GUI test can fail. An always-green test is worthless. Inject a regression, watch it go red, then revert. toolbar_layout was validated this way — hiding #tb-peek-source while the group is folded made it report UNREACHABLE: ['tb-group tb-source'] at all seven folded widths.

4. Debugging: is it us or is it the rig?#

This is the part that actually saved time on 2026-08-20. Work top-down; each step is cheap and eliminates a large class of causes.

Step 1 — Run the simulated source. This is the single highest-value test.#

python <scratch>/probe_onebox.py "Simulated NPX 1.0 (OneBox)"

The sim sources exercise the same display processor, the same CircularBuffers, the same WebSocket path and the same GUI as real hardware. So:

  • Sim streams, hardware does not → the software data path is fine. It is the rig.
  • Neither streams → it is us, and you now have a reproducer that needs no hardware.

On the night in question this took ninety seconds and turned "the GUI is broken" into "the OneBox is wedged": sim delivered 1654 binary frames / 67 MB in 12 s on the identical build.

Step 2 — Count frames at the socket, not pixels on the screen#

"No traces" has many causes; "no bytes" has few. From the browser console:

const sock = window.app.network.socket;
let n = 0, bytes = 0;
const tap = e => { if (e.data instanceof ArrayBuffer) { n++; bytes += e.data.byteLength; } };
sock.addEventListener('message', tap);
setTimeout(() => { sock.removeEventListener('message', tap);
                   console.log({frames: n, bytes, streams: [...window.app.dataStore.knownStreams]}); }, 4000);

knownStreams is populated only from incoming binary frames, so an empty knownStreams is always a consequence of no data, never a cause. WebSocketServer::broadcastData sends to every client unconditionally — there is no subscription the browser could have failed to make.

Measure the viewport before trusting any browser geometry. An unlaid-out or hidden pane reports innerWidth: 0 and every derived measurement is garbage. Check {innerWidth, document.visibilityState} first — a whole evening was once spent chasing layout "bugs" that were an artifact of a hidden pane.

Step 3 — Ask what the counters actually count#

The System-state panel is the first thing you look at and it is the easiest thing to misread. Arithmetic settles it. On the failing run: 1,595 display cycles × 20 ms = 31.90 s, 638 recorder cycles × 50 ms = 31.90 s, 63,536 source cycles ÷ 31.90 s = 1,991/s = exactly two 1 ms workers. Every number sat at its exact nominal timer rate — which is precisely the reading you get when nothing arrives.

Since the fix, source liveness counts committed samples, so producing means data. Processor liveness still counts loop iterations, which is correct for a processor: it is answering "is this thread still turning", not "did it have work".

Step 4 — Read what the hardware is actually being told#

output.log is rewritten on every launch — copy it before restarting or the evidence is gone. Compare a failing run's connect/play sequence against a known-good one, and against the vendor sequence in OpenEphys-OneBox-Reference.md §G.

Signals that now exist and are worth trusting:

Symptom in the log/GUI Meaning
<source> has not produced data in 3 s. Acquisition is running but nothing is arriving The source is alive but the hardware is delivering nothing. Not a display bug.
np_<call> did not return within 3000 ms. Abandoning it A vendor call is wedged. The basestation needs a power-cycle; shutdown will still complete.
Skipping np_<call> -- the basestation has already stopped responding An earlier call in the same teardown already timed out; the rest are skipped deliberately.
connection abandoned: ... some teardown steps did not run The close was partial. Power-cycle before reconnecting.

Step 5 — If the rig is wedged#

A basestation that will not answer np_arm will not answer anything. Symptoms: no data on any stream (probe and ADC together — one dead acquisition trigger silences both, since SM_Output_AcquisitionTrigger is documented as the neural or ADC trigger on a OneBox), and vendor calls timing out on teardown.

The application will now always shut down cleanly. The hardware still needs a power-cycle: pull USB-C / 12 V, or press the back-panel RESET. Confirm the box is at least enumerating first:

powershell -NoProfile -Command "Get-PnpDevice -PresentOnly | Where-Object { $_.InstanceId -match 'VID_0403' }"

Status: OK means the USB bridge is fine and the FPGA is the problem. A Windows error 110 (ERROR_OPEN_FAILED) from any application means the device cannot be opened — usually a handle not released by a force-killed process, or a wedged box.

4a. Testing what the code SAYS TO THE HARDWARE#

On 2026-08-24 the C++ suite reported 17/17 green while two real defects sat in the OneBox path. The operator's reaction was the correct one: "maybe the C++ end shouldn't be 17/17 green if the way it was configured was not accurate with regards to the sequence of calls."

The reason was structural, not a lapse in effort. No test target linked a single line of OneBoxSource.cpp or NpInterface.cpp. Of everything under src/modules/neuropixels/, exactly one file was compiled into a test: NpxChannelMap.cpp, 36 lines of arithmetic. So 17/17 was a true statement about 17 things, none of which was the hardware sequence. Adding more tests of the same shape would not have changed that.

The two defects also share a property that defeats ordinary unit tests: neither is about a value a function returns.

defect what was wrong what every test saw
issue #49 arm() never called np_DAC_enableOutput, so the DAC drove nothing every call returned SUCCESS
the follow-up regression stop() made two UNBOUNDED vendor calls, on every disconnect, for a feature nobody used every call returned SUCCESS
the trigger routing SM_Output_AcquisitionTrigger was never routed; we relied on an undocumented FPGA default every call returned SUCCESS

Three defects, one signature: acquisition that returns SUCCESS from every call and delivers nothing. The observable is the sequence, not the return codes.

The seam: a link-time fake of the vendor API#

tests/fake_neuropix_api.{hpp,cpp} defines the np_* symbols itself. A test target links it instead of NeuropixAPI_x64_4_1_3.lib, and every vendor call the production code makes is recorded in order, with its arguments.

spikespeak_test(test_oneboxwaveplayer SOURCES test_oneboxwaveplayer.cpp
                                              fake_neuropix_api.cpp
                                              ${CMAKE_SOURCE_DIR}/src/modules/neuropixels/OneBoxWavePlayer.cpp
                                              ${CMAKE_SOURCE_DIR}/src/core/ConnectAttemptLog.cpp
                                              LIBS ryml)

Why link-time and not an injected interface:

  • The production code compiles unmodified. No #ifdef TEST, no virtual dispatch, no function pointer table — and therefore nothing whatsoever added to the 30 kHz acquisition path. What the test exercises is byte-for-byte what ships.
  • It cannot be bypassed. A function-pointer table can be sidestepped by a future direct Neuropixels::np_x() call, and the test then goes quietly blind. The fake is the symbol.
  • A new hardware interaction has to be acknowledged. Adding a vendor call to a tested file fails to LINK until the symbol is added to the fake.
  • It is not a new pattern here: external/neuropixels/api/stubs/ already does this for the non-Windows build.

The fake can also stop answering — FakeNpx::setBlocking("np_x", 6000) — which is how a wedged basestation is simulated with no hardware:

QWARN : [Npx] ERROR: np_DAC_enableOutput(DAC0, false) did not return within 3000 ms...
QWARN : [Npx] Skipping np_waveplayer_stop -- the basestation has already stopped responding.
PASS  : stopSurvivesAWedgedBasestation()

That is the bounded-teardown protection being demonstrated, not merely believed. Its whole purpose is that a dead basestation cannot hang shutdown — and on a OneBox a force-kill costs a physical power-cycle, because the FT601 handle is only released on a clean exit.

Two traps in tests of this kind#

Vacuous ordering. QVERIFY(indexOf("a") < indexOf("b")) passes trivially if NEITHER call happened — both are -1. Always assert the anchors exist first:

QVERIFY(enable >= 0 && arm >= 0);
QVERIFY(enable < arm);

Golden-sequence snapshots. "Assert the recorded log equals these 41 calls in this order" is one line and would have caught all three defects. Do not. It goes red on every legitimate edit, so it gets re-baselined by whoever is in a hurry, and after two re-baselines it asserts nothing. Only relational invariants belong here: X before Y, X present, X never present, teardown terminates.

Where this stops, honestly#

test_oneboxwaveplayer covers the WavePlayer's own sequence behaviourally, and the trigger-routing helper behaviourally. But "nobody calls the helper" — the defect that actually shipped — is covered only by a source-text guard, because linking OneBoxSource.cpp into a test means also linking NpInterface.cpp and defining 38 vendor symbols. The guard is labelled as one in the test file.

That larger tier is worth doing and is not blocked on the SpikesPeakCore extraction, contrary to the note at the bottom of tests/CMakeLists.txt: that note is about src/core/Utils.cpp, the composition root. OneBoxSource.cpp's only Utils:: reference is toStdString, which is inline in the header. The link closure is NpInterface.cpp plus a few small files.

5. What is worth a test here#

Prefer components that are pure, on the data path, or encode a rule that has bitten us:

  • Anything that guards a past defect. test_boundedcall is the model: it reduces the wedge to "a callee that never returns must not block the caller" and fails loudly if that regresses.
  • The data path. CircularBuffer wraparound and multi-consumer behaviour — a bug here silently corrupts recordings.
  • Pure arithmetic with a published ground truth. The NP2.0 channel↔electrode mapping is checked against imec's manual; an error there would survive into analysis.
  • Anything that decides what the operator is told. ErrorLog's severity rules and its framework-noise denylist: too loose and a benign Qt warning becomes "Hardware not detected"; too aggressive and a real fault is swallowed.

What is not worth it: anything requiring a probe, and anything whose only assertion is that a setter set something.
