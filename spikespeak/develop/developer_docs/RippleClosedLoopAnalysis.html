Offline analysis of closed-loop ripple→stim recordings#

This is the canonical reference for analyzing a recorded closed-loop test offline, and for the NI-DAQ↔Neuropixels clock/sync machinery every recorded latency depends on. It covers (a) reproducing the online detector exactly from disk, (b) the closed-loop latency measurement method (detection → current into the electrode), and (c) the sync fit + the three clock/sync bugs that were found and fixed. Companion docs:

  • Measured numbers, tables, figures (both probes): ../RecordingTests/CLOSED_LOOP_LATENCY.md — the single source of truth for results.
  • Live per-stage instrumentation + the ASAP low_latency flag: LatencyProfiling.md.

The worked examples below are the real NP1.0 and NP2.0 tests under RecordingTests/ (synthetic ripple in saline + NI-DAQ + the Pi/AM 2300 stim server): the 1000-detection quorum matrix (np{1,2}_{1ch,2ch_q2,4ch_q3}_{baseline,asap}) and the earlier 100-detection NP2 runs (np2_{2channel_2required,4channel_3required}).

Tools#

  • ripple_tools/analyze_recording.py <recdir> --ws <name>_ws.jsonl [--quorum "..."] — the main analysis. Reads the recording + the WS-event capture + the ripple sidecar; writes analysis/ (signalchain, detection, nidaq, closedloop, latency, _summary.json). Works from the recording alone (no live rig).
  • ripple_tools/verify_quorum.py <recdir> --quorum N — transparent, per-channel reconstruction of the quorum state machine, for eyeballing that the offline detector reproduces the backend.
  • Both use python/spikespeak_postprocess (Recording, synchronize) + the exact FIR taps from src/core/Common.hpp.

Reproducing the NP2.0 detector EXACTLY offline#

The NP2 detector does not run on the recorded raw band directly — it runs on data.lfp, which the backend derives from raw. To reproduce it bit-for-bit (not approximately) the offline analysis replays the whole front-end (all coefficients live in src/core/Common.hpp):

  1. data.lfp — src/core/BandFilterProcessor.cpp runs Avx2Filter::setDefaultLFPFilterCoefs on the 30 kHz raw: a 2nd-order Bessel low-pass, −3 dB @ 400 Hz (LFPFilterCoefficients30KHz: b=[0.00163508, 0.00327016, 0.00163508], a=[1, −1.85831868, 0.86485901]), Direct-Form-I y[n]=Σb·x − Σ_{i≥1}a·y, zero initial state. No DC removal anywhere. (Applied offline without scipy as the IIR's zero-state impulse response convolved in — exact to ~1e-16.)

The loop used to live in src/modules/lfp/LFPProcessor.cpp; that file no longer exists. It was lifted into the shared base src/core/BandFilterProcessor.cpp when the spike band arrived, and LFPProcessor is now a header that names the coefficients (see DerivedBands.md §1). Nothing about this reproduction changed — the coefficients are still LFPFilterCoefficients30KHz in src/core/Common.hpp, the filter is still the same 2nd-order Bessel, and all six steps below are unaffected. Only the file to read them in moved. 2. Decimate — the detector takes every 12th sample (RippleDetector.cpp, mCurrRawDataInd % mDecimationFactor == 0); simple decimation, no anti-alias (the Bessel already band-limited it). NP1 skips steps 1–2: it records data.npx.lfp directly (decimation 1). 3. Ripple band — 26-tap 150–250 Hz FIR (RippleBandFilterCoefficients2_5kHz, a=[1] → pure FIR). 4. abs(), then envelope — 10-tap FIR (EnvelopeFilter2_5kHz, a=[1]). 5. Threshold — mean + z·σ (z=2.5) trained on the baseline window. Because the exact Bessel puts the offline envelope in the same scale the live detector used, the ONLINE per-channel threshold (from the WS rippleBaseline, keyed by electrode → remapped to read-out channel via the _ripple.json sidecar) applies directly — identical to the live detector. 6. Quorum — per-channel rising-edge → per-channel lockout → count channels whose lastCrossTime is within the coincidence window (includes self) → fire if reporting ≥ quorum and past the shared stim-lockout, then bump all channels' lockout (the else if (active) branch of doRippleDetectionLoop, src/modules/swr/RippleDetector.cpp:1306-1431). Reproduced in quorum_detections().

Validation: with this exact chain the offline reconstruction reproduces the online detector on the clean tests (offline-quorum crossings match the recorded online-instant firings, 0 unmatched). Historical note — do not reintroduce this: an earlier raw÷12 windowed-sinc approximation of data.lfp plus a DC-removal the detector never does gave the wrong scale and multi-ms offsets. The exact 2nd-order Bessel data.lfp (step 1 above) is the only correct reconstruction; the approximation is wrong and is called out again in RippleDetection.md.

Closed-loop latency#

Definition: closed-loop latency = ai4 stim pulse HIGH − the causal detection that triggered it = the physical path detect → fire() → UDP → Pi GPIO → AM Systems 2300 → electrode. The causal-vs-zero-phase FIR group delay is not included (it is a fixed function of the tap count, not part of the loop).

Method: pulse-anchored — each ai4 rising edge is paired with the detection that preceded it, so the value is ≥ 0 by construction. The detection instant used is the recorded online detector firing time (rippleDetected ts = lfpTs, mapped onto the recording clock via the NPX per-sample hardware timestamp), i.e. the actual realtime causal-detector instant — no reconstruction jitter. A second, independent burst-start-anchored pairing (using the aperiodic ~1.6 s gaps between ripple bursts) cross-checks it and agrees with nearest-before on every clean recording — that cross-check is what caught bug #3 below.

Results live in ../RecordingTests/CLOSED_LOOP_LATENCY.md, the single source of truth for measured latency on both probes. Do not duplicate numbers here — this doc owns the method, that doc owns the results.

NI-DAQ ↔ Neuropixels sync — the fit and the THREE clock/sync bugs#

A shared ~1 Hz TTL sync pulse feeds both the NPX sync input (recorded in the NPX sync field) and NI-DAQ analog ai0. Recording.synchronize() (→ spikespeak_postprocess/sync.py align_timestamps) matches the two rising-edge trains and fits a NI-DAQ→NPX time warp, so the recorded ai4 stim pulses land on the same clock as the recorded ripples. Three separate bugs in this path silently corrupted latency; all are fixed. This is the canonical write-up.

Bug #1 — the clock-scale error (fixed 2026-07-21)#

online_det_recording_times mapped the detector's lfpTs (computed by the backend as ticks / a NOMINAL 100 kHz) onto the recording clock using a t0 derived from the MEASURED per-sample tick rate. Mixing the two left a ~10 ppm SCALE error, so apparent latency ramped with recording length: +6.5 ms over a 618 s run (slope 10.7 µs/s, r = 0.99), invisible on the ~70 s recordings used earlier. It also manufactured a spurious "latency rises with quorum" trend (the tests had different durations). Fix: convert detections back to hardware ticks with the same nominal constant the backend used, then map ticks→seconds with the measured rate — one conversion, no scale error. Every recording was re-analyzed; all numbers published before 2026-07-21 were inflated by this.

Bug #2 — match="end" off-by-one (fixed 2026-07-17)#

A recording's NI-DAQ captured one fewer sync pulse than the NPX (78 vs 79 — it stopped ~0.8 s before the last NPX sync). The old default match="end" pairs the last N edges one-to-one, which — when the dropped pulse is at the other end — is off by one, shifting every NI-DAQ time by exactly one sync period (1000 ms = 2 ripple cycles). On a periodic 1 Hz train this is invisible: the shifted pairing has identical inter-pulse intervals and the same 0.012 ms fit residual. Symptom: ~half the ai4 pulses landing in ripple-free envelope troughs ("orphans") + garbled latency. Fix: align_timestamps defaults to match="auto" (_pair_edges_auto) — estimate the true sub-period offset (smaller-magnitude of the start- and end-anchored offsets), then nearest-edge pair within ½ IPI, so a missing pulse at either end can't cause an off-by-N. Fixed the affected test (42→0 unmatched) and left the already-correct tests byte-identical.

Bug #3 — the whole-period wrap in match="auto" (fixed 2026-07-21)#

auto was still not enough. When the NI-DAQ drops a pulse at the start of the train, both the start- and end-anchored offsets are wrong by a whole period (observed off_start=+0.950 s, off_end=+1.950 s on a 1 Hz train), so picking the smaller-magnitude one still shifted every timestamp by ~1.000 s. Same invisible signature — 617 pulses, 9.78 ppm, 0.012 ms residual all looked perfect. It hit np1_4ch_q3_asap (257 of 995 pulses left unpaired, a physically impossible 0.433 ms minimum). Fix: both clocks are started by one host command, so the true offset is milliseconds; any whole-period component is a pairing artifact. _pair_edges_auto now reduces the coarse offset modulo the sync period into (−IPI/2, +IPI/2], with a warning when it fires. After the fix: unmatched 257→0, and the healthy recordings are bit-identical. It surfaced only because the burst-start-anchored cross-check (aperiodic ripple-burst gaps) disagreed with nearest-before by ~1 s.

Lessons (internalize these for any closed-loop timing analysis)#

  • On a periodic sync train, a tiny fit residual, matching intervals, and a clean ppm do NOT prove correct alignment — a whole-period pairing error hides inside the periodicity. Twice.
  • Anchor on the APERIODIC structure. The burst gaps (or any non-periodic landmark) expose a whole-period shift that every scalar metric misses. Cross-check nearest-before against burst-anchored pairing.
  • Verify event-by-event, not nearest-neighbor, and look at the per-channel envelope vs threshold + the raster first, before theorizing about hardware.
  • A guard rail now exists: align_timestamps warns on both a pulse-count mismatch and a modulo-wrap. Watch for those warnings. See archive/NextTask_SyncPulseCountCheck.md for the remaining capture-side asymmetry (low priority; the analysis side is fully handled).

Reading a count mismatch correctly (NP1.0 lessons, 2026-07-20)#

When online detections, offline crossings, and ai4 pulses disagree, look at the times before theorizing. Two real cases from the NP1.0 regression, both benign, both initially easy to misread as a broken detector:

1. A recording that starts before the detector arms produces a LEAD-IN. NP1 test 1 showed 117 offline crossings, 100 online detections and 99 ai4 pulses. Nothing was missed: the ai4 train starts at t = 11.24 s, which is exactly crossing #19, and crossings[18:] pairs 1:1 with the 99 pulses (max deviation 4.6 ms, mean offset +3.19 ms = the closed-loop delay plus causal-FIR group delay). So 117 = 18 pre-arm ripples + 99 stimulated. Tests 2 and 3, with no lead-in, gave exactly 100/100.

Check: compare the time of the first ai4 pulse against the crossing index, and diff the two event lists. A lead-in is a contiguous block of unstimulated crossings at the START; a real detector failure is scattered through the run.

2. The synthetic stimulus itself drops ripples. The ai4 train has nine ~1.58 s gaps at a regular 10-pulse cadence — and the offline envelope crossings show the identical gaps. That is a property of the play file, not a detection miss. Whenever a gap appears in both the input-derived crossings and the output pulses at the same instants, the stimulus is the cause.

The general rule (see the sync off-by-one bug above): verify closed-loop timing event by event against the recorded signal, never by nearest-neighbor matching on a periodic train, and never by reasoning about the hardware before plotting the envelope against the threshold.
