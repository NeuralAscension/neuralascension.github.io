Second-machine runbooks — one per configuration of issue #52#

Issue #52 gated merging feature/OneBoxSupport: the tree had to be shown to build, run and pass the suites somewhere other than the machine it was written on. That branch has merged into develop (fast-forward, 60889d7 — Status §84), so the runbooks below are no longer a merge gate: they are the standing procedure for standing this tree up on a new box, and #52 is still where the evidence goes. "A second machine" is really five configurations, and a green run on one says almost nothing about the others — they fail in different places.

This page is the procedure for each. Run one, paste the result into #52, move on.

Before any of them#

What green means today#

Three suites, not two — the Python suite joined the gate on 2026-08-30.

suite command expect
C++ build.bat (Windows) / ./build.sh (Linux, macOS) a ✅ per suite, then ALL N SUITES PASSED — seconds
Python python -m unittest discover python/tests OK — seconds, no browser, no backend
GUI python scripts/run_gui_tests.py ALL N GUI TESTS PASSED — about 10 minutes, four tests at a time
all three python -u scripts/run_all_tests.py --no-browser --fatal non-zero exit on any failure

The counts live in Testing.md and nowhere else. Read N from there rather than from this page: three documents once each carried their own copy of those numbers and all three were wrong. What this page asks of you is the opposite — record the numbers you actually saw in #52, with the commit, because "20/20" from a 2026-08-26 run and today's are not the same claim, and #52 was partly held open by exactly that ambiguity.

The GUI suite runs four tests at a time (since 2026-09-01): --jobs defaults to auto = min(4, cpus - 2), and each job gets its own backend on its own port pair and its own isolated Chrome, so nothing is shared between them. It was 35 minutes serial and is about 10 now. --jobs 1 restores the serial path, where one backend is started and shared — use it on a small box, or when a failure is easier to read one test at a time. A test that hangs is killed at SPIKESPEAK_GUI_TEST_TIMEOUT (default 900 s) and reported as a failed test, not allowed to take the run down with it. Both runners take one shared gate lock (scripts/_gatelock.py), so a second run started while one is in flight refuses and says who holds it — it does not queue, and it does not silently attach to the running gate's backend, which is what it used to do. (--force overrides; a child the gate starts itself inherits the lock through the environment.)

Prerequisites#

The C++ and GUI suites need no Python packages — they import only the standard library and this repo's own modules. The Python suite is the exception, and it is now part of the gate: several of its files import numpy at module scope, and test_band_response.py also imports scipy, so a box without them fails the suite on an ImportError rather than skipping it. scripts/requirements.txt still says both suites need nothing, which was true when it was written and is not any more.

You do need:

  • numpy (and scipy) for the Python suite: pip install numpy scipy, or the distro packages.
  • A Chromium-family browser for the GUI suite. It is discovered — Chrome, Brave, Chromium or Edge, by registry, PATH and a candidate list — and SPIKESPEAK_TEST_BROWSER overrides. If none is found the suite fails with the list of what it looked for.
  • Qt 6, a C++ toolchain, HDF5. Windows: MSVC (build.bat finds vcvars64.bat). Linux: GCC and Qt from your distribution or the Qt installer. Detail in Building.md.
  • A display. The GUI suite drives a real browser, and it never passes --headless. Headless remains unproven, and the operator has decided it does not need proving: the GUI exists to be looked at, so a display is a prerequisite rather than a gap. Do not report a headless attempt as a configuration.
  • On a clean clone, run python scripts/build_docs.py once before the Python suite if you want the docs book; the architecture-SVG test no longer needs it (it generates into a temp directory and compares against the committed images/architecture.svg), but the book itself is not built for you.

Recording a run#

For every configuration, capture and paste into #52:

date, commit (git rev-parse --short HEAD), OS + version, compiler + version, Qt version,
browser discovered, portrait display attached? (yes/no),
C++ result (N/N suites, M cases), Python result (N tests), GUI result (N/N tests),
every red test by name, and every [untested] notice the GUI runner printed.

A run without the commit is not evidence: the whole point of #52 is that "it passed" decays. The GUI runner also names any backend process that survived the run — a survivor is a failure of the run even when every test passed, and on a rig it is the thing that makes the next build die on LNK1104.

The one trap that affects every configuration#

layout_matrix's vertical pass needs a portrait display, and most machines do not have one. It used to substitute a landscape window and pass — the cells' assertions are written in the fold rule's own live operands, so they hold at any size while measuring a layout no operator uses. Both Linux runs went green that way, and both reports had to correct it in prose on a GitHub comment. Prose is not a test result.

Fixed 2026-09-01, so the suite now says this itself. displays() in tests/gui/_harness.py returns (list, reason) and separates "this platform cannot enumerate displays" from "this box has no portrait panel" — POSIX parses xrandr --query, Windows still asks PowerShell. require_display() hands the test whichever of the two happened, Checks.skip() records the axis as [untested] and scripts/run_gui_tests.py surfaces that in the run summary, and the result line reads "layout matrix (N of 16 combinations)" with N derived from what actually ran rather than printed as a literal 16.

So on a landscape-only box the vertical axis reports itself as 8 cells untested. Still record whether a portrait display was attached — "16 of 16" and "8 of 16, the rest untested" are different evidence about the same test. SPIKESPEAK_FAKE_DISPLAYS fakes the enumeration if you need to exercise the reporting without owning the hardware.

Configuration 1 — Linux, no hardware#

Proves: the build is not Windows-only; sim sources, filters, ripple detection and all three suites run on GCC. Cannot prove: anything touching the Neuropixels/NI-DAQ SDKs or the FTDI transport.

Sim-only is selected by CMAKE_SYSTEM_NAME, not by a flag — there is no way to configure a sim-only build on Windows, so this code path can only be compiled on an actual Linux box.

git clone <remote> spikespeak && cd spikespeak
git checkout develop          # feature/OneBoxSupport fast-forwarded into here (60889d7)
./build.sh

Confirm the sim branch was entered — this line at configure time is the proof:

Neuropixels hardware not enabled - only sim interface

Then, with an X session available:

DISPLAY=:0 python -u scripts/run_gui_tests.py --fatal

Report: distro, GCC version, Qt version and prefix, HDF5 version, the browser the harness discovered, whether DISPLAY was a real session or a virtual one, and all three suite counts.

This configuration PASSED from a clean clone on 2026-09-01#

Linux Mint 22.1 (Ubuntu 24.04 base, kernel 6.8), Threadripper 1950X, RTX 2080 on NVIDIA 535, GCC 13.3.0, Qt 6.11.1, HDF5 1.10.10, Brave discovered by the harness, a real X session. C++, Python and GUI all green — the run and its counts are recorded in Testing.md §1a, which is the only place counts are maintained. It supersedes the 2026-08-26 run, which was a smaller tree and, more to the point, predated the renderer.

It is what cleared the WebGL2 renderer on Linux. SciChart came out on 2026-08-27 and its hand-written replacement was A/B'd on Windows only — a hand-written renderer being exactly the GPU- and driver-dependent thing to have tested on one platform, and the harness now asserts a column has a live renderer and refuses to run without one. live_view, heatmap_view, heatmap_spatial, probe_map, detached_view and window_registry all pass on NVIDIA 535 with real WebGL.

What it found that this page could not have predicted, all since fixed: a cross-platform header that had drifted from its own .cpp and broke the Linux build (now guarded by python/tests/test_arch_parity.py, which catches it from Windows in milliseconds with no compiler); a clean clone failing the architecture-SVG test on a build step nobody had run; and two measurement tools that misbehaved on a multi-band profile — see AudioVideoLatency.md §5c.

Headless stays unproven, on purpose. That box had a real X session and a real GPU, not SwiftShader, and the harness never passes --headless. The operator has decided headless does not need proving — the GUI exists to be looked at — so do not treat it as an open row of this matrix.

Configuration 2 — Windows, no hardware#

Proves: the Windows build and all three suites are reproducible off the original box; profiles degrade honestly with nothing attached. Cannot prove: any hardware path.

This configuration has never been run. Not once. It is also the cheapest of the five — any Windows machine, no rig — and it is the one that probes a live bug, so run it first.

"No hardware" means physically disconnected: no OneBox on USB, no PXIe chassis powered. Running a simulated source on a machine that has hardware attached is not this configuration.

git clone <remote> spikespeak && cd spikespeak
git checkout develop          # feature/OneBoxSupport fast-forwarded into here (60889d7)
build.bat
python -u scripts/run_all_tests.py --no-browser --fatal

Then the part that is the actual point. Select a hardware profile with nothing attached and watch what it says:

run_spikespeak.bat --no-browser

import json, sys, time
sys.path.insert(0, "python")
from spikespeak_cli import WSClient
ws = WSClient("localhost", 1234); ws.connect()
ws.send_text(json.dumps({"command": "selectSource", "value": "PXIe"}))
time.sleep(14)
ws.send_text(json.dumps({"command": "quit"}))

Pass: a clear, specific failure naming what was not found, and deviceReady false. Fail: it appears to connect, or the failure is a generic "hardware was not detected" when the backend knew more.

Related: #51 is exactly this class of bug and is still open. Its remaining transient — a stateSource naming the source that was refused — was closed on 2026-08-28 and is covered by tests/gui/command_surface.py, but the "profile degrades honestly" half has never been observed on a Windows box with nothing attached.

Configuration 3 — Windows + OneBox + PXIe#

Proves: both transports coexist — slot enumeration, mapBS, and which basestation a profile picks. The fullest case of the five.

Partly run, 2026-08-29, 9/9 on the hardware-behavior checks (enumeration sees both and reports itself ambiguous; a probe-agnostic profile asks rather than guesses, tagged kind: "basestation-choice"; PXIe connects and streams; OneBox fails for the right reason — a missing probe, the probe being on the PXIe — which is what proves the profile reached the box it named; and the PXIe still connects afterwards). Both suites were green in that hardware state. It found one defect, now fixed: a Disconnect left deviceReady true, so the OneBox failure was reported as Still connected to "" instead of No Headstage detected on any port!.

Still to do for a full pass: a clean git clone, and a probe on the OneBox so a OneBox connect can be shown to SUCCEED rather than only to fail correctly.

Setup: OneBox on USB3 and PXIe chassis powered with the basestation seated, both at once. Power the chassis before launching — a chassis powered on afterwards is a documented cause of a confusing connect failure.

build.bat
python -u scripts/run_all_tests.py --no-browser --fatal

Then the part only this configuration can show:

  1. Enumeration is stable with both present. Launch, and check the scan sees both without either masking the other.
  2. A profile picks the intended basestation. Select PXIe by name and confirm it opens the chassis, not the OneBox; then OneBox and confirm the reverse.
  3. The ambiguity dialog. With both attached and a probe-agnostic profile, the backend cannot read the operator's intent off the hardware and must ask. Confirm the choice dialog appears, offers both, is not the blocking hardware-error dialog, and that choosing one connects that one.
  4. Closing one does not disturb the other. Connect one, disconnect, connect the other in the same session.

Record the suite counts too. The existing evidence for this configuration is a dialog exercise, not a suite result, which is why #52's checkboxes (b) and (c) are unevidenced here.

⚠️ Never force-kill the backend with a probe or OneBox open. The FT601 handle is released only on a clean exit; a kill costs a physical power-cycle. Shut down with the WebSocket quit command or the GUI's Disconnect.

Configuration 4 — Windows + PXIe, no OneBox#

Proves: the PXIe path is unaffected by the OneBox work. Cannot prove: OneBox teardown, the ADC, or the WavePlayer.

This is the regression cover that matters: the bounded-teardown and liveness changes touch NeuropixelsSource, which PXIe shares with the OneBox.

Run on the rig 2026-09-01, and it PASSED (Status §74). NP2.0 multishank moved onto the PXIe basestation with the OneBox powered off — verified as no FTDI device on USB, which is what this configuration asks for and is stronger than "no OneBox profile was selected". Four checks: the basestation scan resolves without ambiguity (1 PXIe module); the dropdown offers no OneBox profile that cannot work; connect → play → record 10 s → disconnect → reconnect → play, the reconnect streaming at a rate indistinguishable from the first connect (#54 is about the second connect); and all three suites green.

It found one defect, since fixed: python/spikespeak_io.py — introduced as the single .bin reader so two readers could not disagree — refused the recording. A sidecar with channels: [] and num_channels: 0 is the writer's documented sentinel for "the whole block was written, infer N from the frame size", and it is the common case, because omitting channels: from a profile means record-everything. Both converters read the same file without complaint. Two readers disagreeing about a documented sentinel is precisely what that module exists to prevent.

The eye/ear cell for NP2.0 on PXIe was physically available that day and was not taken — see the measure_av_latency.py step below, and AudioVideoLatency.md §5a.

OneBox physically unplugged — note that explicitly in the report, because "no OneBox profile was selected" is a different and much weaker statement.

build.bat
python -u scripts/run_all_tests.py --no-browser --fatal
run_spikespeak.bat --no-browser      # then: connect "PXIe", play, record 10 s, stop, disconnect

While you are here, and cheap because the rig is already up:

python -u ripple_tools/measure_av_latency.py "PXIe"

That fills a cell of the eye/ear matrix in AudioVideoLatency.md §5a. Pick the audio device explicitly rather than accepting the default, or the ear figure will vary by more than anything being measured — the default came up differently on two runs and moved the ear total by 5×.

Configuration 5 — Windows + OneBox, no PXIe#

Proves: the OneBox path stands alone. Cannot prove: PXIe regressions.

build.bat
python -u scripts/run_all_tests.py --no-browser --fatal

What to watch for, from the last run of this configuration (2026-08-21, second machine):

  • The GUI suite came back 5 of 6 with stream_options red, attributed to #51 and left alone. That is an explained red, not a pass, and #52's checkbox (c) asks for a pass. #51's transient has since been fixed — so re-run and see whether stream_options is green now. If it is, say so in #52: that is one of the two things holding the checkbox.
  • The ADC costs throughput. Npx2OneBoxNoAdc.yaml ("NPX 2.0 Multishank (OneBox, no ADC)") is the control, committed and reproducible. It is gui_hidden: true, so select it by exact name — hidden only means absent from the dropdown, not unselectable.

If you are chasing #63, the protocol is four cells — record 10 s at t+15 s and again at t+90 s, with and against the no-ADC control — and the band's throughput is now reported at every record stop, including a stop caused by Disconnect or quit. Look for recorded SHORT: NN.N% of nominal in the log and on the toolbar.

⚠️ Same rule as configuration 3: no force-kills with the box open.
