Simulated NP1.0 source fully working on Linux — spec + plan (APPROVED 2026-07-06)#

Goal: on a Linux dev machine with no Neuropixels/NI-DAQ hardware, get the simulated NP1.0 source working exactly like a real 1.0 probe — it builds, streams to the GUI through the normal display pipeline (depth-sorted AP + LFP columns, channel labels, per-column scale), and records so the headless spikespeak_cli.py "Recording Test" works without hardware.

Status: DONE (2026-07-06) — built + verified hardware-free. Phases 0–3 are implemented and the headless Recording Test passes against select "Simulated Data" on the Linux/no-hardware box (and synthripples records + fires the ripple detector, decision #5). See SpikesPeak_Status.md §13.4 for the outcome + file list. All five open decisions were answered by the user on 2026-07-06 (see Decisions). This remains the design record; the phase notes below are what was built.

Build/verify specifics on THIS box: Qt 6.11.1 (~/Qt/6.11.1/gcc_64), cmake/ninja from ~/Qt/Tools; the real blocker was the vendored v4/NeuropixAPI.h MSVC macros (__declspec/__stdcall) — now guarded #ifndef _WIN32 like the v3 header. Launch headless with QT_QPA_PLATFORM=offscreen ./bin/SpikesPeak --no-browser (offscreen because WebEngineWidgets needs a platform plugin and there's no display). matplotlib/pip are absent here, so plot_recording.py's PNGs were replaced by a numpy check. Context switch: the rig moved to a labmate; dev + CI now happen on Linux against the sim source. This supersedes the old "do NOT use Simulated Data" note (that was specific to the Windows hardware box, where connecting sim while real hardware was attached was the wrong path). See [[hardware-connected-testing]].

What exists today (verified 2026-07-06)#

Build (CMakeLists.txt) is already cross-platform: - if (WIN32) → defines NPX_HW_ENABLED + NIDAQ_HW_ENABLED, links NeuropixAPI_x64_4_1_3.lib, copies hardware DLLs (FTD3XX, FpgaManager, NeuropixAPI) + CalibrationInfo/. - elseif (Linux) → no NPX_HW_ENABLED; if (NOT WIN32) compiles the NeuropixAPI stubs (external/neuropixels/api/stubs/NeuropixelsAPI_x64_3_70_3_stubs.cpp). PortAudio is pulled by FetchContent (git clone → ext/portaudio), so a Linux build needs internet at configure time. - src/modules/neuropixels/CMakeLists.txt: SimDataSource, SynthRippleSource, DisplayProcessor, Npx are always built; NpInterface.{hpp,cpp} (real hardware) only when NPX_HW_ENABLED. - AVX: on GNU it uses -mavx2 -mfma intrinsics (the external .s/.asm are commented out). The real AVX filter is src/core/Avx2Filter.{cpp,hpp} (tracked). The loose src/Avx.{cpp,hpp}, src/Color.hpp, src/Logging.hpp are unreferenced orphans — not compiled, ignore them.

Sources (src/core/Utils.cpp): source.npx.simdata + source.npx.synthripples always registered; source.npx.pxi and the NI-DAQ source/recorder/display are #ifdef NPX_HW_ENABLED / NIDAQ_HW_ENABLED → absent on Linux. proc.npx.display, proc.lfp, proc.npx.recorder, interpreters are always registered.

Why sim is currently "disabled": SimulatedDataSource::processAndEmitBatch() emits the old wire format — [u32 numPoints][f32 ts][f32 min,f32 max × 384] — and WebSocketServer special-cases "Simulated Data" (lines ~257/282: it wires the sim source's dataReady straight to broadcastData, bypassing the display processors). But the current NetworkClient.handleMessage reads a stream-id header first ([u8 idLen][idStr][u32 numCh][u32 numBins]…), so the sim packet mis-parses. And config/NpxSimData.yaml is source-only (no display/record processors). So sim streams nothing usable.

Design decision: route sim through the REAL pipeline (Option A — chosen)#

Two ways to make sim "work":

  • Option A (CHOSEN) — sim emits RAW NP1.0 data into data.npx.ap / data.npx.lfp, exactly like the hardware source, and the normal proc.npx.display (+ proc.lfp, + proc.npx.recorder) processes it. The GUI then treats sim identically to a real 1.0 probe: depth ordering, AP/LFP columns, µV scale, channel selection, and recording — all for free, no display special-casing. This is the "fully working / as identical as possible" the goal asks for (decisions #1 + #2) and matches the generic-pipeline direction (SpikesPeak_Status.md §11).
  • Option B (rejected) — just refresh the sim's display-packet format and keep the special-case. Faster, but sim would still bypass depth sorting / AP-LFP split / recording, so it's not "like a real probe."

The plan below is Option A.

Decisions (resolved 2026-07-06)#

The user reviewed the plan and locked these in:

  1. Scope = stream + record, as identical to a real probe as possible. ✅ Option A. Sim rides the full data.npx.ap/lfp → display + recorder pipeline; the headless Recording Test must run end-to-end.
  2. Depth sorting = identical / probe-like. ✅ The sim source publishes a synthetic default Bank-0 IMRO map (electrode == read-out channel) so window.imroLiveView depth-sorts exactly as for hardware — NOT the sequential-order fallback.
  3. CalibrationInfo/ = git-untracked (per-lab). ✅ Already resolved — see Phase 0 + Status §13.3. Make the POST_BUILD copy conditional.
  4. No simulated NI-DAQ for now — but the direction is flexible, hardware-agnostic simulated sources. ✅ Leave NI-DAQ sim out of v1. Capture the forward-looking design in Simulated sources are PER-MODULE below (the user explicitly wants sim to eventually cover NP2.0 and non-NPX probes like NeuroNexus, with a way to pick which hardware is being simulated).
  5. Fold the synthetic-ripple source into this work. ✅ Software-simulated ripples are easier to work with than the hardware-injected ones. This matters for a concrete upcoming test: the user will later play a ripple audio file into saline with the probe in the bath (one of the final bench tests before in vivo). So source.npx.synthripples should also stream + record through the real pipeline (same Option A treatment), giving a sim source whose LFP band contains detectable ripples for the ripple detector + the saline rehearsal.

Phase 1 — Sim source produces real NP1.0 data (decisions #1, #2)#

  1. Rework SimulatedDataSource to write int16 NP1.0 packets into the registered data.npx.ap (30 kHz) and data.npx.lfp (2.5 kHz) CircularBuffer<int16, PacketInfo>s — 384 channels, a sync field, and a per-sample timestamp — instead of emitting a display packet. Reuse the hardware source's buffer-write shape so NpxDataInterpreter + DisplayProcessor + RecordProcessor consume it unchanged.
  2. Give it a believable signal: a per-channel sine (as today) plus noise, an occasional artifact channel (mirror the real [1,192,196] "damaged amp" idea so the plots look familiar), and a square sync pulse on the sync field. Keep the sync pulse — it lets the sync tooling render and rehearses the saline test even without NI-DAQ.
  3. Depth/IMRO = publish a default Bank-0 map (decision #2). The live view sorts by electrode via window.imroLiveView, populated from the source's IMRO map. The sim source must expose a default Bank-0 map (electrode == read-out channel) through the same applyNamedMap/getImroAsJson path the hardware source uses, so probemap default works and depth sorting is byte-identical to a real probe. (Do NOT use the sequential-order fallback.)

Phase 2 — Config + de-special-case (decisions #1, #5)#

  1. New/updated config/NpxSimData.yaml: source.npx.simdata with ap/lfp outputs → proc.npx.display + proc.lfp + proc.npx.recorder (channels e.g. [1,192,196], matching the Recording Test).
  2. Give source.npx.synthripples the same Option-A treatment (decision #5): it should stream + record through the real pipeline too, with ripple events in its LFP band. Either extend its config similarly or share the sim plumbing; the goal is a sim source whose LFP the ripple detector fires on (and that can stand in for the saline audio-file rehearsal). Keep simdata = the plain NP1.0 sim and synthripples = the ripple-bearing sim; both ride the real display+record path.
  3. Remove the "Simulated Data" special-casing in WebSocketServer::setPlaying (and the sim-source dataReady connect) so sim flows through onSourceSelection → display procs → broadcastData like every other source. Emit the same readiness signal (a guiStatus "Found simulated NP1.0" analogue) so waitready works.

Simulated sources are PER-MODULE (design corrected 2026-07-06)#

CORRECTION. An earlier version of this doc (decision #4) proposed one hardware-agnostic simulated source with a polymorphic "device profile." The user has since corrected this: each source module gets its OWN simulated source class. The reason is that a source's data shape is intrinsic to how that hardware transmits — an NPX 1.0 probe (int16 AP+LFP superframes into data.npx.ap/.lfp), an NI-DAQ device (double analog + a digital bitmask into data.nidaq.raw), and a future camera (variable-size frames) have nothing meaningful to share at the sample level. One class trying to be all of them would be a leaky abstraction. So:

  • One simulated source class per source module, living in that module's folder, registered by name (source.<module>.sim / source.npx.simdata / …). It writes the SAME registry data object(s), in the SAME dtype + aux (PacketInfo) shape, as that module's real hardware source — so the display / record / ripple pipeline can't tell sim from hardware. Today: SimulatedDataSource (NPX1.0, source.npx.simdata) and SynthRippleSource (source.npx.synthripples). Next: a simulated NI-DAQ source (its own class; see Status §14). Later: a camera module ships its own sim source, etc.
  • Flexibility lives INSIDE each module's sim — the scenario/signal is what varies (NPX: clean sine vs software ripples; NI-DAQ: which analog waveforms + the shared TTL sync train), parameterised by a small per-module profile struct (e.g. SimSignalProfile in SimDataSource.hpp). It is NOT one class emulating different hardware.
  • "Which simulation to run" is selected by the user — via distinct config profiles (each a dropdown entry) and/or a "what to simulate" picker shown when Simulated Data is chosen (planned; Status §14). Add a sim scenario = add a sim class (if it's a new module) or a new profile+config (if it's a new scenario for an existing module), plus a test YAML.
  • Guidance when adding ANY new hardware source: ship a sibling simulated source class in the same module so the module is testable hardware-free (this is now the standing rule — see AddingASourceModule.md).

Frontend and SciChart notes (for the display-selection work)#
