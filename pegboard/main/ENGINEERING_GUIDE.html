Engineering guide

For working on the rig itself — running it, changing it, wiring it. If you are analyzing recordings, you want ANALYSIS_GUIDE.md instead; it assumes no engineering background. If you are running participants, OPERATOR_GUIDE.md.

When something is broken: DEBUGGING.md. How it is built and why: DEVELOPER_GUIDE.md.

Running it

The display runs as a systemd service and starts on boot:

systemctl status pegboard-display

By hand instead (stop the service first, or the GPIO line and the port will already be taken):

cd ~/Documents/Code/pegboard && source venv/bin/activate && python raspberry-pi5/app.py

Then open http://127.0.0.1:5000/ on the touchscreen, or use the Pegboard desktop icon, which starts the service if needed and opens it fullscreen.

The console prints what it bound to, where data will go, and whether the stimulation input came up:

 * Pegboard display
 *   bind        : 127.0.0.1:5000
 *   data root   : /home/remyelin-pi/Documents/Code/pegboard/experiments  (schema v4)
 *   stim input  : gpio26 on /dev/gpiochip0 (edge events, bias=pull-down)

The bind address comes from the systemd unit, which sets PEGBOARD_HOST=127.0.0.1. Started by hand without that variable, app.py defaults to 0.0.0.0 — fine on the bench, wrong on the Pi now that wlan0 joins the campus guest network, so use the service.

Optional environment overrides: PEGBOARD_HOST, PEGBOARD_PORT, PEGBOARD_DATA_DIR, PEGBOARD_TRANSPORT, PEGBOARD_SERIAL_PORT, PEGBOARD_SERIAL_BAUD, PEGBOARD_GPIO_CHIP, PEGBOARD_GPIO_LINE, PEGBOARD_GPIO_BIAS.

Screen orientation

The panel runs upright (720×1560) by default, and can be turned sideways (1560×720). The UI is laid out for both. Use the Rotate the Screen desktop icon, or:

raspberry-pi5/desktop/rotate-pegboard.sh sideways   # or upright, or toggle

The choice is remembered and re-applied at login.

Before a session

Tap the SELF-TEST lamp and confirm it is green. It runs 22 checks across the board and the Pi — sample rate, load-cell noise and drift, trigger line state, message continuity, disk, clock. What each one means is in the panel itself and in OPERATOR_GUIDE.md.

The two trigger tests read not run, and that is normal — running them fires the stimulator.

The four steps

  1. STREAM — starts the live feed from the scale.
  2. METADATA — fill in subject, date, session number, type, hand, then save. This creates the session directory; recording is refused until it succeeds. A collision is shown before you save, with a one-tap fix.
  3. RECORD — starts writing to disk.
  4. TIMING — starts the task and the stimulation. Nothing stimulates until this is pressed.

Press RECORD again to finish; the session is closed, the manifest written, and the board disarmed.

RESET re-tares the scale and clears the plots. The run never ends by itself — targetWeight is deliberately unreachable, so a knock to the table cannot end a session early. The operator always stops the run.

Where the data goes

experiments/<subject>/<date>/<session>/
    session.json     manifest: metadata, clock model, provenance
    samples.csv      t_ms, pi_recv_ms, mcu_time_ms, weight_g, gpio26, epoch
    events.csv       t_ms, pi_recv_ms, mcu_time_ms, event, value, detail, epoch
    clock_sync.csv   audit trail of the clock fit
    raw_udp.log      verbatim board traffic (the name is historical; it is serial now)

t_ms is the unified timebase — the same meaning for a weight sample and a GPIO26 trigger edge, which is what makes stimulation timing comparable to load timing. The board's clock is fitted onto the Pi's, so a sample is filed under when the reading was taken, not when its packet arrived.

Full specification, including the clock model and the event vocabulary, is in DEVELOPER_GUIDE.md §6.

Two things worth knowing before you analyze anything:

  • task_duration_ms ≠ recording_duration_ms. They differ by 3× on a normal run — 61 s of task inside a 209 s recording. Use the former for performance.
  • weight_change is a delta, not a mass. It is an event, never a sample.

The hardware, briefly

Full detail is in DEVELOPER_GUIDE.md §2; this is what you need to have in your head while working on the rig.

pegs → pegboard → load cell → HX711 → ESP32-S3 ──USB──→ Raspberry Pi 5 → touchscreen
                                        │                      ↑
                                        └──── trigger wire ────┘  (GPIO26 + GND)
                                        │
                                        └──→ Spark taVNS stimulator → participant
MicrocontrollerAdafruit Feather ESP32-S3, FQBN esp32:esp32:adafruit_feather_esp32s3
Load cell ampHX711, strapped for 80 SPS (measured 89.7)
TriggerESP32 D12 → Pi GPIO26 (header pin 37), shared ground
TransportUSB serial, /dev/serial/by-id/usb-Adafruit_Feather_ESP32-S3_*-if00

Both parts are 3.3 V and the trigger line is connected directly. GPIO26 must never see 5 V.

The ESP32 runs the experiment; the Pi records it. Peg detection and stimulation do not depend on the Pi. That is the constraint every change to the firmware has to respect — see the "must not be changed casually" list in the developer guide before touching the detection path.

Firmware

export PATH="$HOME/.local/bin:$PATH"
arduino-cli compile --fqbn esp32:esp32:adafruit_feather_esp32s3 \
  --upload --port /dev/ttyACM0 microcontrollerCode/adafruitESP32Feather_s3_usb

This can only be done from a laptop, not the Pi — the Arduino toolchain's esptool is an x86-64 binary and the Pi is aarch64. Flashing means physically moving the board, so batch firmware work.

Current: pegboard-usb 1.3.0. Toolchain: arduino-cli 1.5.1, esp32 core 3.3.11, HX711 0.6.4.

Talk to the board directly with the project's own transport, which already knows not to assert HUPCL:

import sys, time
sys.path.insert(0, "raspberry-pi5")
from serial_link import SerialLink

lk = SerialLink()
while not lk.ready:
    time.sleep(0.05)
lk.write_line("selftest")          # or stream_data, start_timer, stop_timer
for _ in range(400):
    for line in lk.poll():
        print(line)
    time.sleep(0.02)

Commands: stream_data, stop_stream, reset, start_timer, stop_timer, selftest, selftest_trigger (this stimulates), fw_info.

Setting up a Pi from scratch

git clone https://github.com/NeuralAscension/pegboard.git ~/Documents/Code/pegboard
cd ~/Documents/Code/pegboard && ./raspberry-pi5/install-pi.sh

Idempotent — it is how you apply an update, not just how you build a card. --check reports what it would change without changing anything.

Deploying a change

rsync -a --exclude __pycache__ raspberry-pi5/ \
  remyelin-pi@192.168.1.100:~/Documents/Code/pegboard/raspberry-pi5/
ssh remyelin-pi@192.168.1.100 'sudo systemctl restart pegboard-display'

Publishing the docs

docs/ is served at neuralascension.com/pegboard/. This repository is private and stays private: rather than serving GitHub Pages from here, the docs workflow builds the site and pushes it into the public neuralascension.github.io repository, which is what already holds the apex domain. Spikespeak publishes the same way.

pegboard (private)  --build-->  site/  --push-->  neuralascension.github.io
                                                   └── pegboard/
                                                       ├── index.html   <- generated version list
                                                       ├── main/        <- from main
                                                       └── develop/     <- from develop

Every branch publishes to its own directory, /pegboard/<branch>/, and the bare /pegboard/ is a generated index listing whichever versions exist. So:

URLwhat it is
neuralascension.com/pegboard/version list
neuralascension.com/pegboard/main/the released docs
neuralascension.com/pegboard/develop/the working docs
neuralascension.com/pegboard/develop/DEVELOPER_GUIDE.htmla specific page

One directory per branch is not cosmetic. The copy step runs rsync --delete, which strips anything from its target that is not in the current build. An earlier version of this workflow published main to /pegboard/ itself, and that delete would have treated /pegboard/develop/ as stale and removed it. Keeping every branch one level down puts a floor under the delete. Nothing outside /pegboard/<branch>/ is writable by a publish, apart from the regenerated index.

Branch names containing / are flattened with -, so feature/x publishes to /pegboard/feature-x/.

Build it locally first — same script the workflow runs, no network, no credentials:

python3 tools/build_docs.py -o /tmp/site && xdg-open /tmp/site/index.html

One-time setup

The workflow needs to write to a different repository, and the automatic GITHUB_TOKEN cannot leave the repo it runs in. So it needs a token of its own, added once:

Step 1 — create a fine-grained personal access token at github.com/settings/personal-access-tokens/new, with exactly these settings:

fieldvalue
Resource ownerNeuralAscension
Repository accessOnly select repositories → neuralascension.github.io
PermissionsContents → Read and write (under Repository permissions)
Expirya date you will notice — see below

Grant that one repository and nothing else. The token can then only write the website; it cannot reach this repository or any other.

Expiry is a real choice, not a formality. When the token lapses the workflow fails loudly on the checkout step — it does not quietly publish a stale site — but nothing republishes until you replace it.

Step 2 — add it as a secret here, in this repository: Settings → Secrets and variables → Actions → New repository secret. Name it SITE_DEPLOY_TOKEN, spelled exactly that, and paste the token as the value.

Step 3 — run it: Actions → docs → Run workflow, and pick a branch. From then on it runs by itself on any push to main or develop that touches docs/, tools/build_docs.py, or the workflow file. The last step of the run prints the URL it published to.

When it fails

symptomcause
Input required and not supplied: tokenSITE_DEPLOY_TOKEN is not set, or is misspelled
404 checking out the website repotoken expired, or was not granted neuralascension.github.io
403 on pushtoken has Contents: Read, not Read and write
build produced nothingbuild_docs.py failed — the guard is doing its job, an empty site never replaces a working one
pages live but images brokenscreenshots were not committed to this repo
nothing published, run greensite unchanged; nothing to publish — the build was byte-identical, which is normal

Do not add a CNAME file to this repository. The apex domain belongs to the organization site; a CNAME here would try to claim it.

Working without the Pi

.venv-dev/ has flask, flask-socketio, numpy, matplotlib and scipy. app.py runs without gpiod and reports the stimulation input as unavailable, so the whole UI can be developed off-hardware:

PEGBOARD_HOST=127.0.0.1 ./.venv-dev/bin/python raspberry-pi5/app.py

The self-test panel will show pi.gpio_capture red, which is correct on a laptop rather than a fault.

Tests

python3 -m unittest discover -s tests -v

tests/test_display.py covers the Pi side — the clock model, the recorder, the telemetry parser, the self tests — and is standard library only so it runs on the Pi itself. GPIO tests skip where there is no gpiochip.

tests/test_pegboard.py covers the analysis package.
