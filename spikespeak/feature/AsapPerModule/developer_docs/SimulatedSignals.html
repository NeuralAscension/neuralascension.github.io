Simulated signals — what the fake probes emit, and why#

SpikesPeak simulates a Neuropixels 1.0 probe two ways. This page is about what they put in each band, the one thing they both used to get wrong, and how to check them.

1. The two paths#

live simulator play-file generator
code src/modules/neuropixels/SimDataSource.cpp scripts/gen_synthetic_ripples.py
band model src/modules/neuropixels/SimBandResponse.hpp scripts/np1_band_model.py
used by SimNpx1Ripples, SimNpx1RippleModule, plain SimNpx1 Npx1SynthRipples
signal generated per sample, live pre-rendered .h5, replayed

They model the same probe, so they must agree. That is not a convention — it is checked, by python/tests/test_band_response.py, which parses the constants out of the C++ header and compares them against the Python ones.

2. The band split#

A real 1.0 probe splits each channel into two bands:

  • AP — high-passed at 300 Hz. The corner is not our guess: the vendor API exposes exactly one control for it, setAPCornerFrequency(..., bool disable_high_pass), documented in external/neuropixels/api/include/v4/NeuropixAPI.h as "true for disabling the 300Hz high-pass cut-off filter". One boolean, one fixed corner.
  • LFP — low-passed at 500 Hz (the published 0.5–500 Hz band).

Both are modelled as single-pole, causal filters. The order is an assumption, stated plainly: imec publishes the corner frequencies and not the orders. First order is the conservative choice — a steeper real filter would attenuate the AP-band ripple more than we model — and the physically likely one, since a per-channel multi-pole active filter is a lot of area and power to spend 384 times over on a probe this size.

The number that matters#

A 200 Hz ripple sits below the 300 Hz AP corner, so it is attenuated. It is not removed:

gain = r / sqrt(1 + r²),  r = f/fc = 200/300
     = 0.5547            (−5.1 dB)

Relative to what the LFP band shows (which is itself down 0.9285 from its own 500 Hz low-pass), the AP band carries 0.597 — about three fifths.

f AP gain LFP gain AP/LFP
150 Hz 0.447 0.958 0.467
200 Hz 0.555 0.928 0.597
250 Hz 0.640 0.894 0.716

So ripples appear in both bands. The detector reads the LFP band because that is where they are cleanest — not because the AP band is empty.

3. The bug this page exists because of#

Until 2026-08-31 both paths made ripples vanish from the AP band, by two different mistakes.

The live simulator injected the burst into the LFP band only, justified by a comment in generateApSample:

"NO ripple here: on a real 1.0 probe the AP band is high-passed (~300 Hz), which attenuates the 150-250 Hz ripple band"

Every word of the premise is true and the conclusion does not follow. attenuates was implemented as eliminates.

The play-file generator did filter the AP band, with sosfiltfilt(butter(4, 300, 'high')). That is an excellent analysis filter and a poor hardware model: zero-phase filtering applies the response twice, so a 4th-order design rolled off like an 8th-order one. Measured, a 200 Hz ripple came out at 0.0375 of its input.

Both files said "as on real hardware". They disagreed by a factor of fifteen, and neither number was reachable from the other file.

Why it went unnoticed#

Each path was internally consistent, and the claim lived in prose. There was no assertion anyone could run that would come out false. That is the whole reason the model now lives in two small dependency-free modules with tests either side of it: the C++ header is free of Qt and the vendor API, and the Python model is separate from the generator (which imports h5py, absent from the gate's Python — so a test importing the model through the generator could not run in CI, which is precisely how the drift survived).

What it would have cost#

Anything calibrated against the simulated AP band — a detector threshold, an artifact rejector, a spike-sorting sanity check, a figure in a paper — was calibrated against a silence no real probe produces. On real NP1.0 data, ripples in the AP band are plainly visible. It is also why CatGT and SpikeGLX offer to high-pass the AP band again offline: the hardware filter is gentle enough that low-frequency content survives it.

4. What ripple_amplitude means#

ripple_amplitude in a config is the burst peak as seen in the LFP band, not the amplitude of some underlying wideband source. The AP band gets the same burst scaled by apOverLfpGain().

This is a deliberate choice of reference. Defining it wideband instead would be marginally purer and would shift the LFP band — and therefore every validated detector threshold — by ~7%, for no gain in realism, since the amplitude is a free parameter of a simulation either way. The 2026-08-31 fix adds signal to the AP band and leaves the LFP band bit-for-bit unchanged.

The carrier phase is modelled too (the AP copy leads by ~78° at 200 Hz, because a high-pass differentiates). The envelope group delay is not: at 200 Hz it is 0.37 ms against a 30 ms envelope sigma — about 1% of the burst width, below anything the detector resolves.

5. Checking it#

Unit tests, run by the normal gate:

build.bat

test_simbandresponse — 8 cases pinning the response: corner at −3 dB, DC asymptotes, monotonicity across 1–2000 Hz, the 0.5547 and 0.597 figures, and the disabled-high-pass case.

python -m unittest discover python/tests

test_band_response.py — the same numbers on the Python side, plus an impulse test asserting the filter is causal (nothing appears before the impulse — sosfiltfilt would fail it), plus the cross-language constant comparison.

End-to-end, on a real recording#

Both unit suites test the model. To confirm the simulator actually emits it, record and measure:

python python/spikespeak_cli.py --script "select 'Simulated NPX 1.0 Ripples'; sleep 14; play; sleep 3; record <dir> apcheck; sleep 14; stop; sleep 2; disconnect; sleep 2; quit"

Band-pass both bands 150–250 Hz, take the Hilbert envelope, and compare burst peaks. Measured 2026-08-31 with ripple_amplitude: 100:

measured expected
AP burst amplitude 59.5 counts 59.7 (0.597 × 100)
AP / LFP ratio 0.582 0.597
burst interval 2.00 s 2.0
AP burst over its in-band noise floor 43× —

Reading the .bin. Recording files are not a plain [samples × channels] int16 array — each frame carries a 6-byte header before the channel data, and the sidecar's frame.bytes gives the stride. Reshaping without it produces garbage that looks like real data: full-scale rails, std ~7700, and plausible-looking "bursts" at the wrong spacing. ripple_tools/fair_ab.py has the correct reader.

The ratio scatters (0.56–0.66) while the AP amplitude does not, because the denominator moves: the LFP band has a 3.5× higher in-band noise floor (4.99 vs 1.41 counts). Same per-sample noise amplitude, but the LFP band samples at 2.5 kHz instead of 30 kHz, so that noise power is concentrated into a twelfth of the bandwidth. Compare the AP amplitude against its prediction, not the ratio.

6. If imec ever publishes the filter order#

Change it in two places, and the test that compares them will tell you if you missed one:

  1. AP_FILTER_ORDER in scripts/np1_band_model.py
  2. the gain expression in src/modules/neuropixels/SimBandResponse.hpp

Then update the pinned constants in both test files. test_band_response.py asserts on the C++ source text specifically so that changing one side alone goes red rather than going unnoticed.
