The heatmap column — time × channel, on the GPU#

A live-view column draws either traces or a heatmap of the same channels: time on one axis, channel on the other, color carrying a per-bin statistic. It is the Open Ephys probe-viewer idea, built to this codebase's rules.

This is not the probe-map heatmap. That is a different, still-unbuilt feature — coloring the spatial electrode map by activity, with no time axis, the way SpikeGLX's Shank Viewer does. See ProbeActivityHeatmap.md. The two share a metric and nothing else.

1. What it shows#

Whatever stream the column's dropdown is on. The heatmap is a rendering mode, not a band: point the column at ap, lfp, raw, adc or nidaq and it colors that.

Statistic: peak-to-peak per channel per time bin, in the stream's own units (µV for a probe band, V for NI-DAQ and the OneBox ADC).

Window: per column, 1 s to 1 min — default 8 s, newest at the right edge. The 8 s default matches probe-viewer's TRANSPORT_WINDOW_TIMEBASE; the ladder is 1, 2, 4, 8, 15, 30 s and 1 min (ChartColumn.js, hmWinSelector). See §1b — it is not the toolbar's Time, and the difference matters.

Channel axis: the same channels, in the same order, as the traces — so switching modes never moves a channel. The density dropdown gains an All option in heatmap mode: 384 traces in one column is unreadable, 384 rows of heatmap is the ordinary way to look at a probe, and on the GPU it is the same single draw call as 20.

Or every shank at once, ordered by depth — the shank dropdown gains All shanks · depth. See §1a.

1a. Merged shanks, ordered by depth#

On a multishank NP2.0 the shank dropdown offers All shanks · depth: every channel from every shank in one column, sorted by physical depth with the shallowest at the top.

Neither existing ordering can express this, and that is the whole point. Both sort by shank first — packed is (shank, col, row) and interleaved is (shank, row, col), both built in ImroManager.recomputeDepthOrdering() — so each stacks one whole shank above the next and two electrodes at the same depth on different shanks land ~96 rows apart. Sorting by row first interleaves them:

                    packed / interleaved          merged · depth
    top     shank 0, shallow → deep          all shanks at the shallowest row
            shank 1, shallow → deep          all shanks one row down
            shank 2, shallow → deep          …
    bottom  shank 3, shallow → deep          all shanks at the tip

The comparator has five keys, and ascending array index is display order, top to tip:

const isRef = (c) => (lv.isRef && lv.isRef(c)) ? 1 : 0;
const row   = (c) => lv.rowOf(c) || 0;
out.sort((a, b) => (isRef(b) - isRef(a))          // 1. REF first: it has no depth
                || (row(b)   - row(a))            // 2. DESCENDING row -- row 0 is the TIP
                || (lv.shankOf(a) - lv.shankOf(b))// 3. shank ascending
                || (lv.colOf(b)   - lv.colOf(a))  // 4. column DESCENDING -- Right before Left
                || (a - b));                      // 5. total-order backstop

REF is a separate boolean key, never a depth sentinel. The packed ordering pins REFs with a sentinel sort row — REF_ROW = 1e6, ImroManager.js:207 — and feeding any sentinel through this comparator's depth key would be wrong twice over, whether it is that one or the more tempting Infinity. The code says so at the call site and it is worth repeating:

  • this axis is labeled in micrometers, so a sentinel fed through the depth key prints as a depth (20,000,000 µm). That is a lie the operator cannot see.
  • Infinity - Infinity is NaN, and a comparator returning NaN has undefined behavior. Two REFs cannot currently meet — NP1_REFERENCE_ELECTRODES is {191, 575, 959}, all mapping to channel 191 — but that is an accident of NP1's modulo-384 wiring, not a property anybody stated, and it would break silently the moment the set grew.

Column sorts DESCENDING, Right before Left, which is not arbitrary: the existing L+R view at density All already emits R above L, so matching it means a single-shank probe sees nothing move when this is switched on. Both electrodes in a row are at identical depth, so their relative order carries no information — which makes "don't move anything" the only thing left to optimize for.

Key 5 is the one to keep. The two older comparators stop after three keys and lean on Array.prototype.sort being stable, which is safe there because (row, col) uniquely identifies an electrode within one shank. Merging inverts that: on a 4-shank probe up to eight channels share a row, so ties are the common case rather than the impossible one, and the result must not depend on the engine's stability guarantee or on input order.

The depth model is faithful; the lateral one is not#

Ordering by depth is sound on both generations: y depends only on the row (electrode >> 1) and the shanks are tip-aligned, so equal rows really are equal depths. The x model is a simplification — NP1.0 electrodes actually stagger over four x positions (11, 27, 43, 59 µm) and the frontend's even = Left / odd = Right split flattens that to two columns. Which is precisely why this option orders by depth and says nothing about lateral position.

The axis becomes micrometers#

With shanks merged, an electrode number is the wrong label: numbering restarts per shank, so e300 names up to four sites, and at any one height there are up to eight electrodes (4 shanks × 2 columns). Naming one implies a precision the row does not have. So the ticks switch to depth in µm — lv.rowPitchUm(), 20 µm on NP1.0 and 15 µm on NP2.0.

Two independent sources already in this repo agree on those numbers, which is why they are constants and not a guess:

NP1.0 NP2.0
vendored Open Ephys Geometry.cpp:180 / :267 y = (i - i%2) * 10 → 20 µm/row y = (l - l%2) * 7.5 → 15 µm/row
python/spikespeak_convert/spikeglx.py ProbeSpec (from SpikeGLX's IMROTbl) z_pitch=20.0 (:164) z_pitch=15.0 (:168, :173)

spikeglx.py computes z = row * z_pitch (:144) over row = electrode // 2 (:142) — bit for bit the frontend's e >> 1.

Do not reach for ROW_SPACING or NP2_SHANK_SPACING in ImroManager.js — those are canvas drawing units for the probe map, not microns, and they are 9 and 6. Do not import shank_pitch either: the ordering never compares lateral position.

It is distance from the probe TIP, not depth in tissue. Nothing in this codebase knows the insertion depth. The readout says · from tip for that reason; calling it depth would be free to write and impossible for the operator to catch.

Why it is an option on the shank dropdown#

Because another heatmap control would widen the column band, and the band's width decides at how many columns the whole strip folds behind the reveal chip — the view selector alone moved that from four columns to three (§10). It would also mean editing every CSS area map. And it belongs there on its merits: that dropdown is the "which shanks" control.

That argument was tested five days later. The span selector (§1b) was added as a new control, and it cost exactly what this paragraph predicts: 64 px more band, and a cell in eight area maps — of which the first attempt supplied two. The conclusion is not "never add one", it is that the price is real and an option on an existing dropdown is free.

It is offered only in heatmap mode, and only when lv.shanks().length > 1. Traces cannot do it: the vertical offset is baked into the shared sample data, so one global ordering serves every trace column, and a merged-across-shank ordering would need a third baked series alongside the packed and interleaved ones. The heatmap has no such constraint — it permutes rows of a texture, which costs one upload.

Cost: one sort, cached against the ordering revision#

heatmapChannels() is called from syncHeatmap(), which is called from draw(), which runs per frame. A 384-element sort per frame is the kind of cost that never shows up in a profile as one line and does show up in the total. So the permutation is cached, keyed on imroLiveView.rev() + '|' + selectedColKey — the ordering revision and the side filter, which are its only two inputs. rev() is bumped in recomputeDepthOrdering() and nowhere else, so the cache is rebuilt when a probe map is applied or cleared, and at no other time.

Keying on lvAtSlot by identity would work today and stop working the moment somebody sorts in place; comparing contents is 384 elements on a per-frame path.

1b. The span is per column, and it is not the toolbar's Time#

Added 2026-08-31. Two controls now set a time axis and they are deliberately different ones:

control sets lives
toolbar Time seconds of history in trace columns one setting for the page
column span (cc-hmwin) seconds of history in this heatmap per column

Why not just use the toolbar's Time. A heatmap earns its keep by showing minutes of the whole probe at once; at the trace default of 1 s it wraps its ring before anything is readable. Forcing the two onto one control would make the heatmap useless at the span traces want.

Why it needed a control at all. Before this, the span was a hardcoded constant with no control and no label, so a heatmap column and a trace column could sit side by side showing 8 s and 1 s with nothing on screen saying so — an 8× difference in the x axis between two columns of the same probe. That is not a subtle infelicity; it is a misleading picture.

So every column now names its own span in its readout (timeBaseLabel()), in both view modes — a label that appears only in one mode is a label nobody learns to look for. 1 s and 2 s are on the ladder precisely so a heatmap and a trace column can be put on the same span deliberately, which is the one case where reading one against the other is legitimate.

Changing it reallocates nothing. The span is stored as seconds-per-texture-column (heatmapSecondsPerColumn = window / bins), so the ring keeps its width and simply accumulates for longer or shorter before each push. That is also why the cost varies with span — see §5 and §8.

2. Peak-to-peak was free, and that decided the design#

The display stream already carries min and max per channel per time bin — that is what makes a trace's vertical segment. So max - min is one subtraction on two values the parse loop has already loaded into registers:

if (heatCols) heatPk[ch] = (vMax - vMin) * heatUnitScale;

No new processor, no new stream, no extra byte on the socket, and no new thread. The entire backend cost of the headline statistic is zero.

It is taken BEFORE the display baking. Two lines later vMin/vMax acquire the vertical offset, the per-column zoom and (for raw) an AC-coupling baseline — they become plot coordinates, which no legend could label. AC-coupling cancels in a difference anyway, which is part of why peak-to-peak is the honest statistic to take from this point in the pipeline.

The whole path is behind heatCols — a nullable list of the columns wanting heat, resolved once per frame (NetworkClient.js). With no heatmap column open the cost is a scan of at most four columns and a boolean.

3. Why it shares the column's WebGL2 context#

Not an optimization. A hard constraint.

Chrome grants roughly 16 WebGL2 contexts per renderer process and, when you exceed that, force-loses the oldest ones — silently, asynchronously, with getContext still returning non-null every time. Measured, not recalled: creating 40 contexts in one document returned non-null 40 times, killed indices 0–23 oldest-first, and left exactly 16 alive.

So the over-budget failure mode is not an error you can branch on. It is another column going black, some time later, for no visible reason.

Four columns already cost four contexts. A canvas per heatmap would double that before any detached window exists. GlHeatmap is therefore handed the column's existing gl and owns one program and two textures inside it. An unused heatmap costs one unused shader, not a context.

GlColumnRenderer builds it lazily, on the first switch — features arrive available and off, applied to GPU objects.

4. The ring is in the texture, and nothing scrolls#

data texture   R32F, width = time bins, height = channels
one time bin = ONE COLUMN, written with a single texSubImage2D of channels × 4 bytes
a write cursor advances and wraps; the fragment shader adds it modulo the width

Per bin the CPU uploads 1.5 kB for a 384-channel probe. Per frame it issues one draw call of one full-viewport triangle. There is no per-cell CPU work anywhere in the path, and nothing is ever copied to make room.

A triangle rather than a quad, and from gl_VertexID rather than a buffer: three vertices, no VAO state to save or restore, and it touches none of the trace renderer's bindings.

More channels than pixels: take the MAX, never a sample#

384 channels in a 200 px column has fewer pixels than channels. Nearest-neighbor sampling would silently drop channels — and the one it drops could be the only one firing, which makes the display actively misleading rather than merely coarse. The shader loops over the channels inside its pixel and takes the maximum, bounded at 16 fetches.

Averaging was rejected for the same reason: it hides a hot channel among quiet neighbors.

Never-written bins are their own color#

The texture is initialized to NaN and the shader paints those in the plot-background color. Painting them at the bottom of the ramp would draw a solid block of "silence" that is really "no data yet" — a lie the operator cannot see.

5. Aggregation: why the default window is 8 s and not 0.76 s#

Bins arrive at roughly 1000/s (20 per frame × 50 frames/s). A ring is a few hundred columns wide. One texture column per arriving bin therefore wrapped the display in about three quarters of a second — measured, and unreadable.

Incoming bins are aggregated by max into one texture column per window / bins seconds — about 10.5 ms at the 8 s default in a 760 px column, so ~95 columns/s instead of ~1000.

That rate is a function of the span, not a property of the view (§1b): columns/s = bins / window, so the ladder runs from ~13/s at 1 min to ~760/s at 1 s — eight times the default and most of the way back to the raw bin rate this aggregation exists to avoid. Nothing breaks there; it is simply the setting that costs the most, and it is one click away.

Max, never mean. The job of this view is to show that a channel did something; averaging a burst together with the quiet milliseconds around it is precisely how you fail to see it.

Aggregation also cuts the upload rate by the same factor, which is why the per-second cost is 0.2 ms of CPU rather than 2 ms.

6. Color, and the legend#

The colormap is a 256×1 RGB texture, sampled once per fragment by the hardware's own filtering unit. Coloring is free.

Five maps. The dropdown order is the table order and the first is the default:

map note
viridis (default) perceptually uniform, color-blind safe
afmhot monotonically increasing luminance; prints and photocopies legibly
inferno, magma, plasma perceptually uniform

Every map on the list is perceptually ordered, and that is a closed list rather than an oversight. jet was offered until 2026-08-30 and was removed at the operator's request. A rainbow map is not a neutral choice of palette: its cyan and yellow bands are perceived as edges, so it draws boundaries across smooth data and flattens the real gradient elsewhere, and it is not color-blind safe. Open Ephys' probe-viewer offers it; that is not an argument. Adding one back is an operator's decision, and it belongs at the end of STOPS, never first — the first entry is what every new column starts with.

They are stored as nine published anchor stops each, interpolated to 256 entries — 36 strings. afmhot is reproduced exactly rather than approximately: matplotlib defines it piecewise-linearly with breakpoints at 0.25, 0.5 and 0.75, and all three fall on anchors.

Anchors, not polynomial fits, and this was learned the hard way. The first version used coefficients written from memory. It rendered viridis as mauve: readPixels returned [153,129,154] where the map says [59,82,139]. A screenshot looked entirely plausible. A colormap that is subtly wrong is worse than an obviously wrong one — nobody notices, and every judgement is made against a scale the legend misdescribes. Anchors are checkable by inspection: viridis really does run #440154 → #FDE725.

The legend#

A vertical color bar with its two ends and midpoint labeled, plus the unit. It sits in the flex row beside the plot rather than over it: overlaying would cover data, and the operator would have to move the thing they are trying to read.

It is painted from colormapBytes() — the same table the shader samples. A CSS gradient would have been fewer lines and a second source of truth; a legend that disagrees with its plot is worse than no legend.

Open Ephys' probe-viewer has no color key at all — verified by reading its source: the only callers of getColorForNormalizedValueInScheme are the three heat-cell writers, and there is no color-bar widget. The operator reads a color against two unlabeled spin boxes. SpikeGLX does have one (ShankViewLut), labeled 0 → range.

The color axis never auto-ranges#

It is set by the operator, remembered per statistic, and fixed. A scale that moves on its own makes two moments of the same recording incomparable, which defeats the point of having a legend. SpikeGLX takes the same position; probe-viewer does too, but with nothing to read the number against.

7. Units — the factor of 100 that nearly shipped#

Values arrive from the display stream in display units, not microvolts: DisplayProcessor multiplies volts by 1e4 where true microvolts need 1e6, so one display unit is 100 µV (Config.MICROVOLTS_PER_DISPLAY_UNIT, already used by the per-column µV scale control).

The first build pushed 0.21 to the texture under a legend reading "500 µV" — off by a hundred, in the direction that makes a healthy probe look silent. NetworkClient now applies the factor for probe bands and leaves NI-DAQ and the ADC in volts, and the legend's unit follows the stream.

tests/gui/heatmap_view.py asserts a peak above 5, which no display-unit value can reach.

8. What it costs#

Measured on this machine by ripple_tools/bench_heatmap.py, in the shipped renderer, with gl.finish() inside every timed block so WebGL's asynchrony cannot hide the work:

384 ch 960 ch 1536 ch
texSubImage2D of one time bin 2.10 µs 5.15 µs 7.85 µs
one heatmap paint (GPU included) 0.001 ms 0.001 ms 0.001 ms
the same column as traces 0.006 ms 0.004 ms 0.004 ms

The draw is flat in channel count — one draw call of one triangle either way. The upload scales linearly, as it must: it is nChannels × 4 bytes.

At the 8 s default (~95 columns/s) the whole per-second cost of a 384-channel heatmap is about 0.2 ms of CPU — 0.02 % of one core. At the shortest span the operator can pick, 1 s, it is eight times that: ~1.6 ms/s, 0.16 % of one core — still nothing, which is the answer that matters, but quote the span with the number or it is not a fact about anything.

Chrome coarsens performance.now() to ~100 µs as a Spectre mitigation unless the page is cross-origin isolated, so the first run of the benchmark reported exactly 0.000 for every cell. Each timed block is now 2000 uploads or 200 paints and the per-operation figure is the division. If you write a browser microbenchmark here, size it for the clock before you believe it.

ripple_tools/plot_heatmap_comparison.py renders the comparison against probe-viewer and SpikeGLX. Every competitor number on that figure is derived from source constants and labeled as such on the figure itself; the only measured numbers are ours.

9. Adding a statistic#

Pk-Pk works. RMS and Spike rate are listed and disabled, because the browser cannot compute them: it receives per-bin min and max and nothing else. RMS needs every sample squared; a spike rate needs thresholding at 30 kHz. Offering them would relabel the legend and its units while the shader went on coloring by peak-to-peak — plausible-looking and wrong.

To add one:

  1. Compute it in the backend, over the band the audio path uses — data.npx.ap on NP1.0 (the probe high-passes it in hardware) or the derived 300–6000 Hz Bessel on NP2.0 (SpikeBandFilterCoefficients30kHz). This is where the AVX2 dispatch from issue #34 pays: the statistic is over 384 channels, and Avx2Filter already runs 8 lanes at a time with a scalar twin and a runtime check.
  2. Publish it per bin on a module channel, one value per channel — the same shape the heatmap already consumes.
  3. Add the case to ChartColumn.HEATMAP_DEFAULT_MAX and HEATMAP_UNITS, and enable the option.

The audio processor's "threshold" is NOT a spike threshold. It is a subtractive dead-zone waveshaper — a digital diode on the audio waveform. Reuse the audio path's band; a spike-rate statistic needs a real threshold-crossing detector, and should carry SpikeGLX's "stay low for N samples" anti-bounce criterion, which probe-viewer's pure-hysteresis version lacks.

Band power should be a Goertzel, not an FFT. probe-viewer runs a full 256-point real FFT per channel per pixel column and reads exactly one of the 129 output bins — 99.2 % of the transform is discarded, ~92 000 FFTs/s at 384 channels. A Goertzel computes the one bin that is used, in O(N), allocating nothing.

10. Things that will bite you#

  • A heatmap-only control needs a cell in EIGHT area maps — in-flow, the pin variant, and vertical, each with a filters and a no-filters form, plus the two stacked collapsed-overlay templates. CSS Grid does not error on an unplaced item; it quietly adds an implicit row.

This has now bitten three times. Three unplaced controls grew the collapsed panel to 122 px covering 15 % of the plot; then the vertical map — which states its own one-row template because a full-width row never needs to collapse — was missed entirely and made the strip 66 px instead of 34; then on 2026-09-01 the span selector .cc-hmwin was found to have shipped with a class in ChartColumn.js and no grid-area at all, so it had been auto-placing since 2026-08-31. layout_matrix caught the second; nothing caught the first or third but somebody reading the CSS.

So it is a check now, not a warning. python/tests/test_column_grid.py asserts the rule rather than the instance: every cc-* class the frontend sets is placed, every area named in a template is defined, and every template declares as many tracks as its widest row uses. Worth knowing that the first fix for the third occurrence was itself incomplete — two of the eight maps were updated and six were missed, and only the check found that. - Adding a control moves the fold threshold. The trace band went from 448 px to 556 px — the view switch and the pin — so on a 1920 px screen the horizontal strip now collapses at three columns instead of four. That is the existing mechanism working, but it is a user-visible change and user_docs/GUI-Guide.md states the number. A heatmap column's band is 780 px (it spends the µV scale track on the span, the statistic, the colormap and the top of the color axis), so it folds at a wider column again. Both are just --cc-cols + gaps + padding + border; the arithmetic is in RendererContract.md §3.3. - [hidden] loses to .cc-scale { display: flex }. The HTML attribute is a UA rule and any class selector setting display outranks it. - setViewMode() early-returns when the mode already matches, which it does at construction — so the initial state of a control belongs where the control is created, not in the handler that changes it. - preserveDrawingBuffer is false. A readPixels from a later task returns zeros and is indistinguishable from a renderer that draws nothing. Call paint() and read in the same task. - parseInt('all') is NaN, and NaN|0 is 0. The All option collapsed a column to one trace. The shank dropdown's all is deliberately not stored in selectedShank for the same reason: it is a separate mergeShanks boolean, so every arithmetic use of selectedShank keeps working without a guard. - An option that only exists in one mode has to be retired on the way out of it. setViewMode() calls refreshFilterOptions() in both directions; a merge left selected after a switch back to traces would render one shank while the control claimed all four. - No sim source in this repo is multishank. SimulatedData2Source::loadDefaultImro puts all 384 channels on shank 0, so the merge option never appears under sim and a test that only ran there would be exercising its absence. tests/gui/heatmap_spatial.py injects a synthetic 4-shank imroLiveView for the ordering and checks the real model separately; its docstring records the gap that leaves (a real 4-shank probe, which needs hardware).
