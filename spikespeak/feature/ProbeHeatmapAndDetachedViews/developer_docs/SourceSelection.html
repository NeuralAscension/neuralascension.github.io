Source selection — the rig names itself#

The operator picks a basestation. The probe is discovered, not declared.

Before 2026-08-26 the Source dropdown listed twelve hardware profiles, because every probe/basestation pairing had been materialised as its own YAML: Npx1OneBox, Npx2OneBox, Npx2OneBoxNoAdc, Npx1Pxi, Npx2Pxi, Npx1PxiNiDaq, and so on. Picking the wrong one did not produce an error — it produced a rig that looked like it was working.

Between 2026-08-26 and 2026-08-27 it listed three (OneBox / PXIe / PXIe + NI-DAQ). Since commit 4670d2c those three are gui_hidden: true and the menu lists:

None
Neuropixels              (source.npx.auto — basestation AND probe read from the rig)
PXIe with NI-DAQ         (only when a PXIe module is detected)
Simulated Data…

OneBox / PXIe / PXIe + NI-DAQ remain selectable by name from the control CLI, and are surfaced in the menu only when the scan is ambiguous — see §2, where source.npx.auto REFUSES to pick with both a OneBox and a PXIe attached and the GUI raises a basestation-choice dialog instead.

This document is how that works and what you have to know before editing a profile.

1. Why a profile could ever be "wrong for the probe"#

A Neuropixels 1.0 streams two hardware bands, data.npx.ap (30 kHz) and data.npx.lfp (2.5 kHz). A 2.0 streams one, data.npx.raw, and its LFP band does not exist until SpikesPeak derives it. So which bands exist is a property of the probe, and a profile that named them was a profile pinned to one probe.

The failure mode was the bad part. Every band name in a profile is resolved with getDataRegistry().getDataByName(), and that getter creates what you ask it to look up (AgentTraps). Selecting the 1.0 profile with a 2.0 probe connected therefore did not fail: it manufactured empty data.npx.ap and data.npx.lfp buffers, bound the live view to them, and drew 384 permanently flat traces. The recorder did the same and wrote a real .bin and a real sidecar containing nothing. A probe-mismatch warning was added to cover this (NeuropixelsSource::initDataSource), which helped, but the underlying arrangement still asked the operator to answer a question the hardware could answer itself.

2. What resolves the probe, and when#

np_getProbeHardwareID returns the probe's part number when the basestation opens, and discoverProbeHardware() maps it to a ProbeType. The ordering that makes everything below work is in MainController::handleConnectRequest:

setupSources(profile)      <-- opens the basestation, detects the probe, allocates ITS bands
setupProcessors(profile)   <-- everything probe-dependent is decided here, after the answer exists

setupSources runs to completion first. So by the time any processor is configured, the data registry already holds exactly the bands this probe streams and nothing else. Reading the registry is therefore the same answer as asking the probe, without a second vendor call and without a second place for the two to disagree.

The invariant this rests on, stated so it can be checked: every source registers its bands inside initDataSource(), which setupSources calls. Verified across every one of them — NeuropixelsSource, OneBoxSource, NIDAQSource (via scanForDataSource, called from initDataSource), NiDaqSimSource, SimulatedDataSource, SimulatedData2Source, SimOneBoxAdcSource and SynthRippleSource. A source that deferred band creation to startAcq() instead would silently break every row of the table below: the display would bind nothing and the recorder would skip everything, with no error at either end. If you add a source, register its bands in initDataSource().

Every probe-dependent decision keys off that, using hasData() — the non-creating query. Using the creating getter for these tests would return "yes" for every band on every probe and defeat the entire mechanism; that exact bug once made the 2.0 branch of the ripple auto-provision unreachable dead code.

what decided by where
which buffers exist branches on the detected mProbeType NeuropixelsSource::initDataSource
live-view streams binds every band hasData() reports ProcessorManager::setupProcessors
derived lfp / spike auto-provisioned on 2.0 only, disabled ProcessorManager — DerivedBands.md
ripple detector input native data.npx.lfp ÷1 on a 1.0, derived data.lfp ÷12 on a 2.0 ProcessorManager
spike audio auto-provisioned on any probe, silent ProcessorManager
recorder bands entries whose band is absent are skipped RecordProcessor::configure

Three of those six already worked this way. The refactor added the display and recorder rows and collapsed the profiles that the other three had made redundant.

Auto-provisioned is not running. Every band and processor above arrives available and off, per the rule in CLAUDE.md: a disabled band advances its read index and does nothing else. The GUI's band buttons and the Ripple dock's Start turn them on.

3. What a hardware profile still declares#

Only what is genuinely an operator's decision.

name: "OneBox"
sources:
  - name: "source.npx.onebox"
    outputs:
      - data: "ap"                    # 1.0 only  |  listing BOTH generations is what
        name: "data.npx.ap"           #              marks this profile probe-agnostic
      - data: "lfp"                   # 1.0 only
        name: "data.npx.lfp"
      - data: "raw"                   # 2.0 only
        name: "data.npx.raw"
      - data: "adc"                   # OneBox 12-ch analog input; presence enables the stream
        name: "data.npx.adc"
processors:
  - name: "proc.npx.display"          # no inputs: -- bound from what the probe streams
  - name: "proc.npx.recorder"
    recordings:                       # absent bands are skipped, so one list serves both probes
      - data_name: "data.npx.ap"
        ...

Three things are worth spelling out:

outputs: is a permission list, not a demand. The source reads it to decide whether to enable the OneBox ADC, and to work out whether the profile expects a particular probe. It does not create the bands — the probe branch does. Listing a band the probe does not stream costs nothing.

Declaring both generations disables the probe-mismatch warning, deliberately. A profile naming only one generation still warns when the other is connected, and should: it was written for that probe. A profile naming both is stating that it serves either, and the warning would be noise.

No inputs: on the display is the normal case. You may still write one and it still wins — scale_factor and num_channels overrides only exist there — but anything you list is a band you have now pinned by hand.

channels: is what these files are for. Omitted means all channels, which is the right default for a general profile: it cannot know which three matter on your rig, and a recording that silently kept 3 of 384 is not recoverable afterwards. Narrow it per band when you know.

3a. The basestation names itself too#

source.npx.auto resolves to the OneBox or the PXIe source from a scan that opens nothing. To the IMEC API the two are the same kind of device: np_scanBS() discovers both and np_getDeviceList() reports each one's platformid (NPPlatform_PXI / NPPlatform_USB). np_openBS() is where the exclusive claim starts, and the scan never gets there.

Both source classes were already doing exactly those calls, separately -- the PXIe path to find a slot while skipping OneBoxes, the OneBox path to find a serial while skipping PXIe modules. They are now one helper, SpikesPeak::Npx::basestations() in BasestationScan.hpp, because a third copy is where the three start to disagree. It caches: np_scanBS() is a vendor call on the main thread, and basestations are not hot-plugged mid-session. rescanBasestations() forces a fresh look.

Ambiguity is asked about, never resolved by a rule. If a OneBox and a PXIe module are both attached, SourceManager refuses the connect and the GUI offers the two explicit profiles instead. Only one basestation is supported at a time, and guessing which one the operator meant is the same silent-wrong-source failure the whole mechanism exists to remove. That case is real, not theoretical: the machine this was built on reports 1 PXIe module and 1 OneBox.

The GUI asks the backend what is attached with the probeHardware command before offering anything, so it can hide PXIe with NI-DAQ on a rig with no PXIe module and prompt when the answer is ambiguous. The reply is cached backend-side, so opening the menu is not a vendor call.

3b. More than one probe is a question, not a default#

detectProbePort() returns the FIRST port carrying a headstage. On a rig with several that is an arbitrary one, and silently streaming an arbitrary probe is the same class of failure as silently streaming the wrong band -- everything looks healthy and the data came from somewhere else.

So listProbePorts() counts them, and if there is more than one the connect stops and the GUI asks which port to use. The choice is held in a static on NeuropixelsSource, because the question is raised by a connect that fails: it has to outlive that failure so the retry can honour it. The dialog also says plainly that multi-probe acquisition is in the backlog and not a priority, so nobody has to wonder whether the restriction is a bug.

listProbePorts() is deliberately separate from detectProbePort() rather than a mode on it. The latter carries the OneBox's power-up retry loop (up to 8 attempts over ~4 s), and rewriting two hardware paths whose retry behaviour cannot be exercised without the hardware in front of you is not a change worth making for tidiness. The enumeration runs afterwards, when the headstage is known awake, so one pass is enough.

4. The old profiles are hidden, not deleted#

The twelve superseded profiles carry gui_hidden: true. They are out of the operator's dropdown and still selectable by exact name from the control CLI:

python python/spikespeak_cli.py

then select "NPX 2.0 Multishank (OneBox)".

That split is deliberate. Their names are how every measurement script, runbook and issue comment reproduces published work — the closed-loop latency figures among them — and a config's identity is its internal name: field. Deleting them would break reproduction of results we have already reported. The GUI gets short; the archive stays runnable.

The same flag also carries the operational variants that are not everyday choices: the ASAP (low_latency:) profiles, the no-ADC control that issue #63 needs, and the digital-input profile from #67.

5. The Source control is a menu, not a <select>#

The visible control is #src-btn, a toolbar button that opens #src-menu — an anchored popup in the app's own palette. AudioModule made this call first, for its device picker, and wrote down why:

A native <select>'s popup is OS-drawn — the starred rows rendered green on WHITE the instant it opened, which is what the dock's own dark palette exists to avoid.

Source was the last native <select> in the toolbar and had exactly that problem.

#selectSource still exists and is still the single state holder. It is hidden, not deleted. The menu writes its .value and dispatches the same change event a native select fired, so everything downstream is untouched: reflectSource()'s careful no-re-send logic, rebuildSourceOptions(), the control CLI, python/tools/gui_scenarios.py, and the GUI tests that connect by setting .value and dispatching change. One state holder, one code path — a parallel copy is a thing that can disagree.

syncSourceButton() mirrors the select onto the button (label and disabled state) and is called from every path that changes either, including the ones a remote change arrives on: a CLI-driven session and a second browser both land in reflectSource().

The menu's three levels#

Source ▾
├─ HARDWARE
│   ├─ OneBox           USB basestation — probe + 12-channel ADC
│   ├─ PXIe             PXIe chassis — probe only
│   └─ PXIe + NI-DAQ    PXIe chassis + the NI-DAQ card's inputs
├─ Simulated Data  ›    → systems → probe → scenario
└─ None

The simulated branch drills down in place. It was briefly a separate centred modal; a dropdown that hands you to a modal halfway through a decision is two surfaces for one choice.

Both axes come from the config, never from a table in the frontend:

sim_variant:     "Neuropixels 2.0 Multishank (OneBox + ADC)"   # the leaf label
sim_basestation: "OneBox"        # optional -- OneBox | PXIe
sim_probe:       "2.0"           # optional -- 1.0 | 2.0

An omitted axis means "independent of it", and the variant is offered under every value of that axis. The plain sine-wave sources are the real case: source.npx.simdata opens no basestation at all, so filing it under OneBox or PXIe would invent a distinction the data does not have — but hiding it unless the operator guessed a basestation would be worse. This is the rule most likely to rot, because the obvious implementation (exact match) silently drops those variants while the menu still looks perfectly reasonable. tests/gui/sim_picker.py asserts it in both directions.

A JS-side map of the same information would be a second place to remember, and the one that quietly omits the next scenario somebody adds. Adding a simulated scenario is still a one-file change.

showSimPicker(onPick) is kept as an entry point — it now opens the menu at its simulated step rather than a modal — because the GUI tests and gui_scenarios.py both call it.

Its look is borrowed, on purpose#

SOURCE_MENU_CSS in main.js contains no new colour. Every value comes from #band-menu (BandModule.js) and #aud-dock / #aud-devmenu (AudioModule.js) — the two surfaces an operator meets most often, and which already agree with each other deliberately. The mapping is listed above the CSS block so a change to one can be carried across.

Two things that looked cosmetic and were not:

  • The picker sat at z-index: 1000, below #aud-dock and #band-menu at 2147480000. An open dock covered it. It is now 2147480002 — above the docks and menus, still below #cfm-veil (2147482000) and #hwfault-veil (2147483000) so a confirmation or a hardware fault opens over it.
  • The stylesheet was injected lazily on first menu open, and it carries the rule that hides #selectSource — so the native <select> sat visible in the toolbar beside its own replacement until somebody happened to open the menu once. It is injected at startup. sim_picker.py asserts the select is actually out of sight, which is what caught it.

6. Adding things#

A scenario to the simulated picker — write the config, give it sim_variant: plus whichever of sim_basestation: / sim_probe: genuinely apply. Nothing else.

A band to a hardware profile — add it to outputs: and, if it should be recorded, to recordings:. If the probe does not stream it, both are ignored. If you want it in the live view with a non-default width or scale, that is when you write an inputs: entry.

A new probe generation — the part-number match in discoverProbeHardware() and the electrical table in Npx2Scale.hpp are the two places that decide what a part number means. Note the match is by prefix, which is why NP2003 and NP2004 currently fall through to eUnknown.
