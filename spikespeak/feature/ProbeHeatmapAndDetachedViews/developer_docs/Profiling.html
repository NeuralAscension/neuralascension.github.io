Profiling — where the time actually goes#

Measured on this machine, in the shipped code, on 2026-08-30. The headline is that there is no hot spot, which is a useful thing to have written down: it is what stops the next person optimizing something that does not matter.

This is the profiling report. For closed-loop latency — the per-stage breakdown from threshold crossing to stimulus out — see LatencyProfiling.md, which answers a different question. This document is about load: CPU, GPU and where the frames go.
Frontend profiler ripple_tools/profile_frontend.py → frontend_profile.json
Backend CPU ripple_tools/profile_backend.py → backend_profile.json
Filter microbenchmark tests/bench_filter.cpp → build/tests/bench_filter.exe
Heatmap renderer benchmark ripple_tools/bench_heatmap.py → heatmap_bench.json

All four are reproducible. None is registered with ctest — see §6.

1. The frontend: ~1.2 % of the main thread#

Chrome's sampling profiler, 12 s per configuration, simulated NP1.0 with ripples, four columns.

configuration main thread busy real work of wall
traces, 4 columns 18.2 % 149.8 ms 1.25 %
heatmap, 4 columns 18.1 % 144.7 ms 1.21 %
heatmap, 4 columns, all 384 channels 18.2 % 172.6 ms 1.44 %

The 18 % "busy" figure is almost entirely (native):(idle) — the profiler counts the sample, not the work. Subtract it and the page is doing 1.2–1.4 % of one core.

Everything else, in order, for the heaviest configuration:

(native):(program)                    99.4 ms   <- V8 itself: parse, compile, internal
NetworkClient.js:handleMessage        42.0 ms   <- the binary decode. THE hot function.
ChartColumn.js:pushHeatmapColumn      10.9 ms   <- heatmap aggregation, 384 channels
(native):(garbage collector)           8.8 ms
(native):bufferSubData                 4.2 ms   <- the actual GL upload

handleMessage is the only thing in the frontend worth optimizing, and at 42 ms per 12 s it is 0.35 % of a core. The renderer barely appears: bufferSubData is 4.2 ms and the draw calls do not make the list at all.

The optimization deliberately not taken#

Columns showing the same channel list each run their own gather out of the decoded frame. Sharing it across identical columns would save roughly 1 ms/s.

It was not done. It adds a cache keyed on the channel list to a path that runs 50 times a second, to save a thousandth of a core. The number is recorded here because "we chose not to optimize this" is only defensible with one.

2. The heatmap renderer: flat in channel count#

ripple_tools/bench_heatmap.py, measured in the shipped renderer on an RTX 3060 Ti (ANGLE/D3D11).

channels upload per time bin draw per frame (traces, same column)
384 2.10 µs 0.0010 ms 0.0055 ms
960 5.15 µs 0.0005 ms 0.0040 ms
1536 7.85 µs 0.0005 ms 0.0040 ms

The draw does not grow with channel count — four times the channels is the same single draw call of two triangles, and the difference between the rows is noise. What grows is the upload, linearly, because it is channels × 4 bytes per time bin.

At 1536 channels that is 7.85 µs per bin against a bin every ~10 ms: 0.08 % of a core.

Total heatmap cost end to end is ~0.2 ms/s, and it moves the backend by +0.3 pp — which is within the noise of the two measurements either side of it.

3. The backend: 1.02 cores, and the SIMD tier barely moves it#

ripple_tools/profile_backend.py, 20 s windows, simulated NP1.0 ripples:

cores
traces, 4 columns 1.036
heatmap, 4 columns, all channels 1.039

One core, near enough, and the display mode does not change it. That is the shape you want: the acquisition and processing cost is set by the source and the processor graph, not by what the browser happens to be drawing.

4. AVX2: 2.89× in the filter, and a null result that is not one#

build/tests/bench_filter.exe, 384 channels through the LFP preset (2nd-order Bessel IIR), median of 12 reps of one second at 30 kHz:

tier per 384-channel sample row per second of data
AVX2 554.5 ns 16.63 ms — 1.66 % of one core
scalar 1600.0 ns 48.00 ms — 4.80 % of one core

2.89×, saving 31.4 ms of CPU per second of filtered probe data.

The end-to-end measurement said zero, and that is also true#

Forcing each tier and measuring the whole backend on the NP1.0 ripple configuration:

cores
SPIKESPEAK_SIMD=avx2 1.022
SPIKESPEAK_SIMD=scalar 1.019

No difference. It is a true measurement of a case where the filter barely runs: NP1.0 gets its LFP band from the probe, so proc.lfp is never provisioned and the ripple detector filters only its handful of detection channels.

That yields a falsifiable prediction — NP2.0 has no hardware LFP, so proc.lfp derives it, 384 channels of IIR per sample, and the flag should move the process by roughly the 3 points the microbenchmark implies. Measured on NP2.0 with the derived band on: +3.8 pp.

The lesson is about benchmarks, not about AVX2. An end-to-end measurement answers "does this matter in this configuration", and it is easy to read the answer as "does this matter". Both numbers belong in the record; neither alone is the story.

5. Reproducing all of it#

python ripple_tools/profile_frontend.py
python ripple_tools/profile_backend.py
python ripple_tools/bench_heatmap.py
build/tests/bench_filter.exe
SPIKESPEAK_SIMD=scalar build/tests/bench_filter.exe

bench_filter decides its tier once per process by design — the dispatch must not change under a running acquisition — so it measures whichever tier it resolved to. Run it twice.

Each writes its JSON next to itself in ripple_tools/, so a re-run on another machine is directly comparable.

6. Why none of these is in the test gate#

A benchmark is a stopwatch, not an assertion. A benchmark inside the gate is a flaky test waiting for a busy machine — it would be the only suite whose result depended on what else the laptop was doing, and the failure mode is somebody adding a tolerance wide enough to make it pass, at which point it stops detecting anything.

They are built with the suite so they cannot rot, and run by hand.

If we ever want a benchmark that gates, it needs a different design: a recorded baseline, a tolerance justified against measured machine-to-machine variance, and somewhere to keep the history. That is a decision to make deliberately, not by adding add_test.

7. What is NOT measured here, and should be#

  • GPU utilization attributable to the browser process. Every GPU number above is a draw-call timing, not a utilization figure. The renderer lives in a browser process separate from the backend, which makes per-process GPU attribution on Windows genuinely awkward — and it is exactly the axis a competitor comparison needs.
  • Anything under real hardware load. All of the above is simulated sources. The numbers should hold — sim drives the same display processor, ring buffers, WebSocket and GUI — but "should" is not "measured".
  • Multi-window cost. Each detached window is a full independent decode; the per-window cost is known analytically (~3.08 MB/s per stream) and has not been profiled at 2 and 3 windows.
