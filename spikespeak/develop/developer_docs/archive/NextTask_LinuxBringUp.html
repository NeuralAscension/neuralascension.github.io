1. Scope — what "Linux works" can and cannot mean here#

What is in scope#

A Linux box with no acquisition hardware can prove everything except the vendor call layer:

  • it configures and builds from a clean clone with GCC;
  • the C++ suite (19 targets) is green;
  • the backend runs, serves the frontend on :8234 and the WebSocket on :1234;
  • a simulated source streams — and streaming is not a screenshot, it is frames arriving at the socket (see §4 of Testing.md, and step 6 below);
  • a simulated source records, with sane sidecars;
  • the GUI suite (10 tests) is green, driving a real browser over CDP against that backend.

That is worth doing because of how this codebase is built: every simulated source drives the same ring buffers, the same interpreters, the same display processor, the same recorder, the same ripple detector and the same WebSocket as real hardware. That was a deliberate design choice, recorded in SpikesPeak_Status.md §13.4 as "Option A". So a green Linux run exercises the entire application except np_* and DAQmx* themselves.

What is out of scope, and cannot be faked#

#52 criterion Linux verdict
Build from a clean clone with no path edits In scope. The most valuable row here — a GCC/Linux clone is the harshest possible test of "no hardcoded paths".
Both suites green In scope, and the hard part. See §5.
Real Neuropixels: PXIe connect / stream / record / reconnect Out of scope. Not possible. NPX_HW_ENABLED is defined only inside the Windows branch (CMakeLists.txt:118,149); the vendored NeuropixAPI_x64_4_1_3.lib/.dll is a Windows import library and there is no .so in the tree.
Real OneBox: connect / stream / record / DAC / WavePlayer / clean teardown Out of scope. Same gate. NpInterface, OneBoxSource and OneBoxWavePlayer are excluded from the target entirely (src/modules/neuropixels/CMakeLists.txt:20-30).
NI-DAQ Out of scope. NIDAQMX.lib and the /DELAYLOAD:nicaiu.dll link option are Windows-branch-only (CMakeLists.txt:147,165-176). NIDAQmx.h is itself cross-platform, but the vendored library is not — real NI-DAQ on Linux would need libnidaqmx.so, which is a new dependency and therefore an operator decision, not something to take (CLAUDE.md, and SpikesPeak_Status.md §14).
Throughput / closed-loop latency numbers Measurable, but not comparable. Never measured on Linux. See §7.

Do not attempt to make hardware work on this box, and do not report a Linux run as closing a hardware row. Say plainly in your report which rows you closed and which are structurally unavailable.

One thing you get for free that Windows does not test#

Selecting a hardware profile on a sim-only build does not hang half-connected. WebSocketServer detects the unregistered module and broadcasts an explicit toast — "Real Neuropixels hardware (PXI/OneBox) is not available in this build… use a simulated source instead" (src/core/WebSocketServer.cpp:265-282). Confirm you see that. It is a real behaviour that only a sim-only build can exercise, and if it has rotted, Linux is the only place it shows.

2. The July 2026 claim, and exactly how much weight it deserves#

The claim is true, specific, first-hand — and it is about the application, not about the tests.

developer_docs/SimDataLinux.md carries a status banner: DONE (2026-07-06) — built + verified hardware-free, naming the box's Qt 6.11.1 (~/Qt/6.11.1/gcc_64), cmake/ninja from ~/Qt/Tools, the headless launch QT_QPA_PLATFORM=offscreen ./bin/SpikesPeak --no-browser, and the actual blocker it fixed: the MSVC __declspec/__stdcall macros in the vendored v4/NeuropixAPI.h. SpikesPeak_Status.md §13.1–§13.7 corroborates with a file list, a CLI-driven record verified with numpy, the ripple detector firing on synthripples, and the NP1.0 record-channel-selection UI driven and screenshotted in Brave over CDP on Linux/:0.

I checked that the enabling fixes are still in the tree today:

  • external/neuropixels/api/include/v4/NeuropixAPI.h:20-26 and :2248-2252 collapse NP_EXPORT/NP_CALLBACK/NP_APIC to nothing under #ifndef _WIN32, mirroring the v3 header. That header is included by a dozen always-compiled translation units, so without those guards nothing builds at all.
  • The non-Windows branch still compiles the Neuropixels stubs (CMakeLists.txt:193-198).
  • CalibrationInfo/ and data/ — the two directories a fresh clone will not have — are no longer copied anywhere at all (2026-08-26). The exe builds into <repo>/bin and resolves them as <exe>/../<name>, which is the repo root, so their absence is simply nothing found rather than a build step that fails. The if(EXISTS) guards that used to protect a clone are gone with the copies they guarded.

So: high weight for "no porting work is needed; the platform split is real and has been maintained". Low weight for "it builds today." Two reasons, and the second is decisive:

  1. 50 commits touching src/ have landed since 2026-07-09, and none of them has been compiled by GCC. The whole OneBox effort is in there. Reading found no MSVC-only constructs, but reading does not instantiate templates: missing #includes that MSVC supplies transitively, and dependent-name lookup in templates, are the two classic MSVC→GCC failures and neither is visible to grep. Budget a round of trivial-but-numerous compile errors.
  2. Both test suites postdate the last Linux build entirely. git log --diff-filter=A puts tests/CMakeLists.txt and tests/gui/_harness.py at commit d9620fd, 2026-08-21 — six weeks after. "Both suites pass on Linux" has therefore never been true, never been false, and never been attempted, on any machine.

Treat this task as a re-verification of the application and a first verification of the suites.

3. Prerequisites#

Required — the build will not configure or run without these#

What Version / package Why, and what happens without it
x86_64 CPU with AVX2 — CMakeLists.txt:90-93 puts -mavx2 -mfma on the whole SpikesPeak target under GCC, so the compiler may vectorise anything. An aarch64 box cannot build this at all (no immintrin.h).
GCC, C++20 any GCC with full C++20 Clang is not wired up. CMakeLists.txt:90 tests CMAKE_CXX_COMPILER_ID MATCHES "GNU" only, so a Clang build gets no AVX flags and dies exactly as the test targets do in §4 step 1. Use GCC until that string becomes "GNU|Clang".
CMake ≥ 3.19 (CMakeLists.txt:5) —
Ninja any The build driver everything documents.
Qt ≥ 6.7, components Core Gui Widgets Network WebSockets WebChannel (+ Test), all requested explicitly since 2026-08-26. WebEngine is no longer required — see the note below CMakeLists.txt:13-21. Ubuntu 24.04's distro Qt6 is 6.4.2 — below the floor. The July box used a Qt-installer 6.11.1 under ~/Qt, which is what find_qt_prefix() globs for.
HDF5 with C++ and HL libhdf5-dev find_package(HDF5 REQUIRED COMPONENTS CXX HL) at CMakeLists.txt:25-28; the target links HDF5::HDF5. See the troubleshooting row in §8 — this one is a genuine unknown on your distro.
git + outbound network at configure time — ext/ is git-ignored and empty. PortAudio (GIT_TAG 87e35e7) and rapidyaml (v0.9.0, with its c4core submodules) are FetchContent-cloned during cmake -S . -B (CMakeLists.txt:33-48). On an air-gapped or proxied lab machine this is a hard stop.
python3 3.8+ CMakeLists.txt:481 find_package(Python3 COMPONENTS Interpreter QUIET) drives the build's ✅/❌ banner; without it the C++ suite still runs under ctest but the banner does not print.
libasound2-dev install before the first cmake configure PortAudio's ALSA host API is a cmake_dependent_option on ALSA_FOUND (ext/portaudio/CMakeLists.txt:335-341) and does not fail without it — you silently get a PortAudio with zero host APIs, and the failure surfaces much later as a red audio_panel GUI test.
libgl1-mesa-dev — Qt Gui/Widgets link.

On Qt WebEngine — REMOVED 2026-08-26. You no longer need it.

This section used to say WebEngine was a hard find_package requirement that nothing in src/ called, and asked whoever hit it to install it and flag it. It was flagged, the operator approved dropping it, and it was removed and re-verified on the Windows rig — which is where it had to be done, because it changes that build too.

grep -rn "QWebEngine" src/ is empty and always was; the GUI is an external browser and there has never been a QWebEngineView. The catch was that WebEngine transitively supplied Qt::Widgets, Qt::Gui and Qt::WebChannel — the last one genuinely used, by WebSocketServer.cpp:46 — so deleting it alone produced Target "SpikesPeak" links to target "Qt::Widgets" but the target was not found, a worse error than the one it fixed.

All six components are now requested explicitly:

find_package(Qt6 6.7 REQUIRED COMPONENTS Core Gui Widgets Network WebSockets WebChannel)

Verified on Windows: Qt6WebEngine* appears zero times on the link line, all 20 C++ suites and all 10 GUI tests pass. So qt6-webengine-dev and its NSS/X/dbus chain are no longer a Linux prerequisite. If you are on a checkout older than this, the original analysis is in the commit. Propose it to the operator; do not slip it into a bring-up.

Required for the GUI suite only#

4. Step by step#

Work from a clean clone, in a flat build/ directory. Both matter — see step 0.

Step 0 — before you configure: three things that are broken today#

4.0.a — FIXED 2026-08-26. The .sh launchers are executable in the index now. git ls-files -s build.sh run_spikespeak.sh _dobuild.sh reports mode 100755 for all three, so a fresh clone can run them directly.

They were 100644 for a long time, which gave Permission denied on a fresh clone while the .bat siblings worked by extension — the first thing a Linux user hit. If you ever need to fix this again for a new script, note that it takes both halves: git update-index writes the index and leaves the file on disk exactly as unexecutable as it was.

chmod +x <script>.sh                     # makes it run NOW
git update-index --chmod=+x <script>.sh  # records the bit for everyone else

Or sidestep it entirely by always invoking python3 scripts/spikespeak.py run …, which is what the wrapper does anyway.

4.0.b — Mostly fixed on 2026-08-26; read this only if you are on an older checkout. The build now writes the app to <repo>/bin, and find_exe() looks there first (scripts/spikespeak.py), so the exe is found regardless of how the build tree is shaped. build/ is the one build tree and ./build.sh configures it for you.

The historical hazard, for an older clone: find_exe() globbed only <repo>/build*/bin while the root run_spikespeak.py globbed nested trees (build*/*/bin), so a Qt-Creator-shaped build/Desktop_Qt_6_11_1_Release/bin/SpikesPeak was visible to one launcher and not the other. SPIKESPEAK_EXE still overrides everything if you need it. Two launchers doing one job with different globbing is how the next person loses an hour — worth collapsing if you touch this.

4.0.c — --offscreen is a documented flag that this launcher does not have. Only run_spikespeak.py strips it; scripts/spikespeak.py:187 passes unrecognised args straight to the exe, where QCommandLineParser::process() rejects unknown options and exits. Use the environment variable, not the flag — and usually you need neither, because scripts/spikespeak.py:182-183 sets QT_QPA_PLATFORM=offscreen for you when DISPLAY is unset.

4.0.d — "headless" is decided by DISPLAY alone, which a Wayland session does not set. scripts/spikespeak.py:182 tests only DISPLAY, so on a Wayland-only desktop the launcher declares the box headless and forces the offscreen platform even though a perfectly good display is attached. Harmless for the backend (it is a windowless server), but do not read that line as evidence that there is no display for the GUI suite — check WAYLAND_DISPLAY too before you conclude you need Xvfb. Export QT_QPA_PLATFORM=xcb (or wayland) to override; the launcher only sets it when it is unset.

Step 1 — The one certain build breaker — FIXED 2026-08-25#

Already done; verify rather than apply. tests/CMakeLists.txt:85-93 now carries the GCC guard, and its comment names this runbook as where the problem was found. Confirm it is there before you configure, then move on to step 2 — pasting the block below a second time is harmless but the rest of this section describes a tree that no longer exists.

The original analysis, kept because it explains why the guard is needed:

-mavx2 -mfma is attached to the SpikesPeak target only (CMakeLists.txt:90-93). The spikespeak_test() function is a plain add_executable with no compile options at all (tests/CMakeLists.txt:39-101), and two test targets — test_avx2filter (:130) and test_bandfilterprocessor (:141-144) — compile src/core/Avx2Filter.cpp, which calls _mm256_fmadd_ps, _mm256_load_ps and _mm256_store_ps with no __attribute__((target)) and no runtime dispatch (src/core/Avx2Filter.cpp:5,111,117,129,136).

MSVC accepts AVX2 intrinsics with no flag. GCC does not:

error: inlining failed in call to 'always_inline' '_mm256_fmadd_ps':
       target specific option mismatch

This landed with the test suite on 2026-08-21, after the last Linux build, which is exactly why nobody has hit it. Add to spikespeak_test() in tests/CMakeLists.txt, mirroring what the app target already does:

if(CMAKE_CXX_COMPILER_ID MATCHES "GNU|Clang")
    target_compile_options(${NAME} PRIVATE -mavx2 -mfma)
endif()

No behaviour change on MSVC, no new dependency. Note that the test author anticipated GCC at runtime — tests/test_avx2filter.cpp:73-77 has a __builtin_cpu_supports branch — only the compile flags were missed.

Success looks like: nothing yet. You have made a change you cannot verify until step 3.

Step 2 — Configure#

cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release \
      -DCMAKE_PREFIX_PATH=$HOME/Qt/6.11.1/gcc_64

Since 2026-08-26 ./build.sh (i.e. python3 scripts/spikespeak.py build) configures build/ on first use with Ninja + Release + compile_commands.json, discovering Qt and Ninja itself, and then builds. On a box with one suitable Qt that is the whole of steps 2 and 3:

./build.sh

Configure by hand, as above, when you want to watch the configure output or when the Qt it picks is not the one you meant. find_qt_prefix() scans /opt/Qt, ~/Qt, /usr/lib/qt6 and /usr/local/opt/qt6 and takes the newest version that has a gcc_64 / macos / clang kit — but it cannot know your distro Qt is too old, and it has no opinion about HDF5. Setting Qt6_DIR or CMAKE_PREFIX_PATH in the environment overrides it entirely.

Point CMAKE_PREFIX_PATH at a Qt that actually clears 6.7 — and check the one you are pointing at, not whatever is first on PATH: $HOME/Qt/6.11.1/gcc_64/bin/qmake -query QT_VERSION. A bare qmake6 -query QT_VERSION answers for the distro Qt, which is exactly the Qt you are trying to avoid, so it can read 6.4.2 while your configure is perfectly fine (or the reverse). If find_package(HDF5) misses, append the HDF5 prefix to the same variable (the second Windows machine needed exactly this, SpikesPeak_Status.md §51.2).

Success looks like: Configuring done / Generating done, plus a line reading Neuropixels hardware not enabled - only sim interface (CMakeLists.txt:194). That message is the confirmation that the platform split worked. If you do not see it, you are not building the Linux branch and everything after this is meaningless.

Also expect messages about data/ and CalibrationInfo/ being absent. Those are correct on a clone.

Failure modes: a Qt below 6.7 fails here, not at compile — it is the single most likely first failure. A missing WebEngine fails with a bare "Could not find a package configuration file". No network fails inside FetchContent.

Two configure aborts that are NOT your machine's fault#

Both were found by reading on 2026-08-26 and deliberately left alone, because each is a dependency question and CLAUDE.md makes that the operator's call, not the agent's. Expect them, and report which one you hit rather than quietly working around it.

1. Could NOT find HDF5 (missing: HL). Operator decision 2026-08-26: HDF5 STAYS. It is not optional -- SynthRippleSource.cpp reads the synthetic-ripple play files through the HDF5 C++ API, and scripts/gen_synthetic_ripples.py writes them with h5py. Install libhdf5-dev, which supplies CXX and HL together; the Linux box found both with no help.

The one precise caveat, so nobody rediscovers it: the HL component is never called from C++ (grep -rn "H5LT\|H5TB\|H5DS\|hdf5_hl" src/ is empty) and HDF5::HDF5 wraps HDF5_LIBRARIES, not HDF5_HL_LIBRARIES. So if some distro ever fails configure on HL specifically, dropping that one word is safe and does not touch play-file support. Do not drop HDF5 itself.

Original note: CMakeLists.txt asks for find_package(HDF5 REQUIRED COMPONENTS CXX HL), but nothing in src/ uses the high-level API — grep -rn "H5LT\|H5TB\|H5DS\|hdf5_hl" src/ returns nothing, and the target links HDF5::HDF5, which wraps HDF5_LIBRARIES only, not HDF5_HL_LIBRARIES. So on a distro where FindHDF5 does not turn up libhdf5_hl, configure aborts over a component that would contribute nothing to the link.

Install libhdf5-dev (which normally supplies it) first. If it still fails, dropping HL from that line is a one-word change and is very likely correct — but say so in your report rather than committing it silently, and add message(STATUS "HDF5 ${HDF5_VERSION} include=${HDF5_INCLUDE_DIRS} libs=${HDF5_LIBRARIES}") so the next person can see what resolved.

2. Qt WebEngine — RESOLVED 2026-08-26, removed. Skip this one. Kept below only so an older checkout still explains itself.

~~Qt WebEngine is required but appears unused — and deleting it fails DIFFERENTLY.~~ find_package(Qt6 …) requests Core WebEngineWidgets WebSockets Network (+ Test), yet grep -rn "QWebEngine" src/ returns nothing. On a distro-Qt box you must install qt6-webengine-dev and its NSS/X/dbus chain to link a module nothing calls.

The trap: Qt::Widgets and Qt::Gui are linked by the target but never requested — they arrive only transitively through WebEngineWidgets. So the obvious fix, deleting that component, turns one configure error into Target "SpikesPeak" links to target "Qt::Widgets" but the target was not found. If you go that way, request them explicitly first:

find_package(Qt6 6.7 REQUIRED COMPONENTS Core Gui Widgets WebSockets WebChannel Network WebEngineWidgets)

then removing WebEngineWidgets becomes a one-line change that works. (QWebChannel is used by WebSocketServer.cpp and is also only arriving transitively today.) Do not drop WebEngine without asking — it is a dependency decision.

If configure fails, the tree is NOT left poisoned any more#

CMake writes CMakeCache.txt before find_package runs, so a configure that dies on Qt or HDF5 used to leave a cache behind — and every later ./build.sh then saw it, decided the tree was configured, skipped configure and died on a missing build.ninja with no mention of Qt at all. Since 2026-08-26 scripts/spikespeak.py checks the configure exit code, deletes the partial cache and stops, so the next run re-configures and prints the real reason. If you ever see a build failure that names build.ninja and nothing else, delete build/CMakeCache.txt by hand and re-run.

Step 3 — Build#

cmake --build build          # or ./build.sh, which does configure + build in one

Success looks like: a binary at bin/SpikesPeak — the repo's own bin/, not the build tree; this moved on 2026-08-26 — and the per-suite ✅/❌ banner from scripts/run_tests.py, which runs as an ALL target on every build. Per CLAUDE.md: a compile that produced a binary is not a green build. A red C++ suite does not stop the build by default — it is easy to walk past, so do not. Add -DSPIKESPEAK_TESTS_FATAL=ON if you want red to be fatal.

On the FIRST build use cmake --build build directly, not ./build.sh. The wrapper redirects the entire build into _build.log in the repo root and prints only its last 10 lines. On the one build where you expect a page of GCC errors and where the ✅/❌ banner is the whole point, that hides both. It also drops a scratch file in the repo — gitignored, so git status stays clean while the folder does not, which is exactly the mess CLAUDE.md bans. Use the wrapper once the build is quiet, which is what it is for.

Expect a first-build fix pass. See §2. Every fix should be a small, well-commented commit referenced on #52, and every fix that is a portability fix rather than a Linux special case is the most valuable output of this whole task.

Success looks like: ALL N SUITES PASSED. There are 19 registered targets in tests/CMakeLists.txt today. Windows quoted "15 suites, 316 cases" on 2026-08-21 and the tree has grown since. Report the number from your actual Linux run — do not copy the Windows figure.

All 19 are hardware-free by construction. test_oneboxwaveplayer links tests/fake_neuropix_api.cpp instead of the vendor library (tests/CMakeLists.txt:161-166), so it compiles OneBoxWavePlayer.cpp unmodified on a box that has never seen a OneBox — note that this means Linux compiles a file the Linux application does not.

If a test fails rather than failing to build, the likeliest divergences are the float comparisons in test_avx2filter and test_filter (GCC contracts FMA differently and uses a different libm). A red suite here is a genuinely interesting finding — those cases have only ever executed against MSVC. Read build/tests/<name>.log; run_tests.py prints it for any suite that fails. (That file logger exists because in this environment the tests' stdout arrives empty — see the long comment at tests/CMakeLists.txt:66-92. The reasoning behind it is Windows-specific; whether stdout works on Linux is worth a line in your report.)

Step 5 — Run the backend#

./run_spikespeak.sh --no-browser

Always --no-browser for automated work (CLAUDE.md) — otherwise main.cpp opens a window in the operator's default browser on top of whatever you drove yourself.

Success looks like: the app stays up, output.log appears in the working directory, and http://localhost:8234 serves the frontend. The launcher prints the LD_LIBRARY_PATH it assembled and the exec line; read them.

What the launcher does for you on Linux (scripts/spikespeak.py:158-186): resolves Qt from the build's CMakeCache.txt Qt6_DIR onto LD_LIBRARY_PATH, skips the vendored IMEC DLL directory (Windows-only), skips HDF5 (system loader path), and sets QT_QPA_PLATFORM=offscreen when DISPLAY is unset. The 0xC0000135 trap that makes run_spikespeak.bat mandatory on Windows has no Linux equivalent beyond the Qt lib dir, and CMake's build-tree RPATH usually covers even that.

CLAUDE.md applies here even without hardware: do not leave the backend up while you are not using it. A running backend holds the binary open and the next build fails to link.

Step 6 — Stream from a simulated source#

Drive it headlessly rather than clicking:

python3 python/spikespeak_cli.py --script "select 'Simulated NPX 1.0 (OneBox)'; waitready 40; play; sleep 15; record /tmp/sp_linux_check linux1; sleep 10; stop; pause; disconnect"

Simulated NPX 1.0 (OneBox) is the GUI suite's default source and is composed purely of source.npx.simdata + source.npx.simadc (config/SimNpx1OneBox.yaml) — no hardware type, so it is selectable on a sim-only build. Every source, interpreter and processor those configs name is registered outside both #ifdef NPX_HW_ENABLED and #ifdef NIDAQ_HW_ENABLED (src/core/Utils.cpp:89-98, 123-128, 149-170).

Success looks like — and this is the part people get wrong: per CLAUDE.md's "sim first" rule and Testing.md §4, count binary frames at the socket, not pixels on screen. A control-plane probe is not a liveness test; a dead probe once reported a completely healthy rig for three and a half minutes. Then check the recording from the files, never from a wall clock:

records = os.path.getsize(bin_path) // sidecar["frame"]["bytes"]
percent = 100.0 * (records / RECORD_SECONDS) / sidecar["sample_rate_hz"]

frame.bytes is declared in the sidecar — do not hardcode it.

Also worth 30 seconds: select a hardware profile and confirm you get the explicit "not available in this build" toast from §1, rather than a hang.

Recordings go to /tmp, never into the repo (CLAUDE.md: never commit recording-test data).

Step 7 — The GUI suite#

Its own section. Go to §5.

On scripts/run_all_tests.py. CLAUDE.md offers it as the one command for both suites, and since §5.1 was fixed on 2026-08-26 it is the right way to run both:

python3 scripts/run_all_tests.py --no-browser --fatal

Pass --no-browser: it webbrowser.opens its live progress page (:340) otherwise, which on a box whose display situation you are still establishing is one more variable. Pass --fatal so a suite that never ran cannot read as a pass.

Step 8 — Tear down#

Shut the backend down with the WebSocket quit command or the GUI's Disconnect. Kill only the isolated debug-port browser profile the harness launched — a blanket pkill chrome closes the operator's real windows. Leave nothing running: no SpikesPeak, no stray browser, ports 1234/8234 free.

5. The GUI suite on Linux#

This is the part most likely to block, and the honest headline is: it has never been run on Linux. Below is exactly what is known, what is a guess, and what to do first when it breaks.

5.1 The .bat blocker — FIXED 2026-08-26#

Both entry points used to start the backend by Popen-ing run_spikespeak.bat through the shell, which is Windows-only, so the suite could not start a backend on Linux at all. Both now call scripts/spikespeak.py directly (tests/gui/_harness.py:237-245, scripts/run_gui_tests.py:116-121) — no executable bit needed, no shell=True, and it reuses the interpreter already running the tests. There are no .bat references left anywhere in the test path.

5.1a When the backend does not come up — read the log, do not guess#

Fixed 2026-08-26, and it is the difference between a five-minute diagnosis and an afternoon. Both runners used to send the backend's stdout and stderr to DEVNULL, so every distinct Linux failure — no exe, no Qt runtime, no platform plugin — collapsed into the same 30-second wait and one line saying the backend did not come up.

The child's output now goes to _gui_backend.log in the repo root (git-ignored), the last 25 lines are printed inline on failure, and the path is named in the error. On this box, with a deliberately broken exe, that reads:

❌ backend did not come up on :1234
  its output (…/_gui_backend.log):
    [spikespeak] ERROR: SpikesPeak binary not found. Build first (python scripts/spikespeak.py build) or set SPIKESPEAK_EXE.

The three you are most likely to see on Linux, all of which now appear in that log:

In _gui_backend.log Means
[spikespeak] ERROR: SpikesPeak binary not found nothing built, or it went somewhere unexpected — check bin/SpikesPeak
libQt6Core.so.6: cannot open shared object file Qt runtime not on LD_LIBRARY_PATH; the launcher sets it from the build cache, so the cache may name a Qt you have since moved
qt.qpa.plugin: Could not load the Qt platform plugin "xcb" no display, or the xcb platform plugin's own deps are missing. scripts/spikespeak.py sets QT_QPA_PLATFORM=offscreen when DISPLAY is unset — if DISPLAY is set but broken it will not, so unset it or export the variable yourself

5.1b A suite that never ran can no longer report green#

Also fixed 2026-08-26, and it mattered most on exactly this machine. Three defects lined up so that a completely failed Linux run printed ALL SUITES PASSED:

  • run_all_tests.py never forwarded --fatal to either child, and both children return 0 on failure unless they get it — so a red C++ suite exited 0 and was judged on that exit code;
  • run_gui() initialised ok = True and only ever lowered it on a test_end event, so zero events meant a pass;
  • run_gui_tests.py returned 0 when the backend never appeared, unless --fatal was passed.

All three are closed: --fatal is forwarded to both children, a run that reports no test results is treated as a failure with an explicit message, and a missing backend always exits non-zero. Verified by simulating a broken backend — run_all_tests.py --no-browser --fatal now prints SOMETHING FAILED and exits 1 where it used to print green.

You should still pass --fatal yourself, and you should still be suspicious of a green run that finished suspiciously fast. The rule from CLAUDE.md stands: a compile that produced a binary is not a green build, and neither is a suite that printed a banner without running anything.

The fix, and it is small. Branch on os.name and call the cross-platform launcher that already exists, dropping shell=True:

[sys.executable, os.path.join(REPO, "scripts", "spikespeak.py"), "run", "--no-browser"]

scripts/spikespeak.py already does the LD_LIBRARY_PATH and offscreen-platform work that run_spikespeak.bat does with PATH. No new dependency.

Do not rely on the "just pre-start a backend" workaround. Both call sites do probe :1234 first and print "reusing the backend on :1234" (_harness.py:232-234, run_gui_tests.py:113-128), so it looks like a zero-code route — but it gets you exactly one test. Each GUI test is its own subprocess (run_gui_tests.py:143-155), and the backend auto-quits 2000 ms after its last WebSocket client disconnects (src/core/WebSocketServer.cpp:72-90). When the harness kills its Chrome at the end of test one, no client remains and the backend goes away before test two starts. Pre-starting is useful for a single manual smoke run and nothing more — which is fine, because §5.1 is fixed and the harness now starts its own backend on Linux.

(One consequence worth knowing: the harness only sends quit on exit if it started the backend — self._backend is None otherwise — so a backend you started by hand is yours to tear down.)

5.2 Is headless viable? Unknown — and here is the first diagnostic#

The harness launches Chrome with --app and --window-size and never --headless (tests/gui/_harness.py:273-283) and Page.captureScreenshot (:493-514). The Browser.setWindowBounds + fullscreen transition (:297-317) is guarded by if self.monitor: — and on Linux self.monitor is always None (§5.4), so that path is dead code here and is one risk you do not have. With no display, Chrome exits immediately and CDP(port=…) raises "no CDP endpoint on :" after the 7 s sleep.

There are two routes and nobody has tried either on Linux:

  • A real desktop session. This is the one with evidence behind it: SpikesPeak_Status.md §13.6/§13.7 and GuiTesting.md:146-150 both record Brave being launched as an app window and driven over CDP on Linux/:0 in July, working.
  • Xvfb, at a screen at least as large as the harness's default 1960×1080 window:

bash xvfb-run -s "-screen 0 1960x1080x24" python3 scripts/run_gui_tests.py --fatal

Add --no-sandbox only if you are running as root in a container. Note Xvfb has no window manager, so fullscreen and window-bounds semantics differ from a real session — that is part of what is untested.

Do not add --headless to the harness. Browser.setWindowBounds, the fullscreen transition and the real-layout fidelity the suite exists to measure all behave differently in headless, and several tests assert on measured viewport size.

The highest-risk unknown, and the first thing to check when tests fail confusingly: WebGL. webinterface/ChartColumn.js:291 calls SciChart.SciChartSurface.create, which needs WebGL and a 3.4 MB scichart2d.wasm. Chrome from ~125 onward refuses WebGL on the SwiftShader software rasterizer unless launched with --enable-unsafe-swiftshader, and the harness passes no such flag. If WebGL is unavailable the surface promise rejects, every column reports a dead 8 px canvas, and live_view, layout_matrix, shrink_window and toolbar_layout all fail in a way that reads exactly like a layout regression rather than a missing GPU.

First diagnostic when the GUI suite fails on Linux: call g.errors() — the page-side error collector the harness installs (_harness.py:101-124). It will name a WebGL failure explicitly. Do that before you debug a single layout assertion. If it is WebGL, try the real-display route, or add --enable-unsafe-swiftshader under Xvfb and say in your report that you did.

5.3 Second-order unknown: the backend may not survive Page.reload#

The harness reloads to arm its error collector (_harness.py:290-292). At that instant the browser is the backend's only WebSocket client, and the 2 s grace timer is running. GuiTesting.md:150-152 warns about this in as many words. It survives on Windows because the reload reconnects well inside 2 s. On a slower, software-rendered Linux box, page init is slower. If the suite dies during the very first test with "backend did not come up", suspect this, not the launcher.

Related: every sleep in the harness was tuned on a Windows hardware box — 13 s after selectSource (:262), 7 s after Chrome launch (:283), 3+3 s after reload (:292,:295), 6 s default settle (:353). If they prove short, widen them toward the settle_until_stable pattern (:437) rather than just increasing the numbers. Each test also has a 900 s subprocess timeout (run_gui_tests.py:151), and the suite is ~11 minutes on Windows; software rendering could multiply that.

5.4 Monitor selection degrades silently, and you must not let it pass as green#

monitors() shells out to PowerShell + System.Windows.Forms::Screen (tests/gui/_harness.py:144-151). It is wrapped in except Exception: return [], so on Linux nothing raises — pick_monitor() returns None, Gui.__init__ prints "no monitor attached; using the default window" and falls back to 1960×1080 (:204-217).

tests/gui/layout_matrix.py:237-238 then runs both its landscape pass and its portrait pass in the same landscape window. Vertical mode exists precisely because it is a portrait-monitor feature, so half that matrix measures a configuration no operator uses — and it does not fail, it passes. The #52 brief already flags this as a thing you must not let quietly pass.

The assertions themselves are safe: layout_matrix.py:18-19 states outright that they are written in the fold rule's own live operands (oneRowNeed vs avail) precisely so they hold on any monitor, and ChartColumn.fitStrips (webinterface/ChartColumn.js:572-600) measures scrollWidth/clientWidth live rather than against a constant.

Two acceptable outcomes. Pick one and say which: - Add an xrandr --listmonitors parser behind the same monitors() contract — stdlib subprocess, no new dependency; or - Accept the degradation and state in your report that the portrait half of layout_matrix was not tested on Linux.

5.5 The suite writes into the repo — clean up after it#

Gui.shoot() saves into developer_docs/images/gui/ (_harness.py:493-514, layout_matrix.py:33,108,224), and nine of those PNGs are git-tracked and embedded in the docs book. A Linux run will overwrite Windows-rendered documentation screenshots with differently-fonted Linux ones. This exact clobber already happened on the second Windows box (SpikesPeak_Status.md §51.6: "silently overwrote the committed vertical doc screenshot with a landscape capture (reverted)").

After every Linux GUI run:

git checkout -- developer_docs/images/gui

That pathspec and no other. gui_layout_matrix.json and gui_test_status.json are git-ignored (.gitignore:125 and :103) and therefore untracked, so naming them here makes git abort the whole command with "pathspec ... did not match any file(s) known to git" — and restore nothing, including the screenshots you were actually trying to revert. Delete those two files if you want them gone; they were never going to be committed.

Never commit doc screenshots from the Linux box.

5.6 What green looks like#

10 GUI tests (tests/gui/*.py less _harness.py): audio_panel, band_dependency, error_paths, layout_matrix, live_view, record_flow, ripple_params, shrink_window, stream_options, toolbar_layout.

Every one of them selects a simulated source, so none needs hardware. The default is Simulated NPX 1.0 (OneBox) and it is overridable with SPIKESPEAK_GUI_SOURCE (tests/gui/_harness.py:130) if you need to isolate a config.

stream_options is expected GREEN. It was red for #51 up to 2026-08-24 and is green now, and per the second-machine brief it should stay that way. If you find it red on Linux, that is a finding, not a known issue — do not wave it through on the strength of a stale note.

9. Do not#

  • Do not add a dependency to make something work. Not a library, not a service, not a runtime. Xvfb, libnidaqmx.so and the WebEngine removal are all operator decisions — name them, stop, and let the operator choose (CLAUDE.md).
  • Do not "fix" a test by weakening its assertion. A red audio_panel on ALSA or a red toolbar_layout on DejaVu is information. File it.
  • Do not report a compile as a green build. Both suites, every time, with the numbers from your own run.
  • Do not let a silent degradation read as a pass — the portrait-monitor fallback and the GUI runner's exit-0-on-no-backend are both designed to look fine.
  • Do not commit doc screenshots, recording data, or scratch files. Logs and captures go to the session scratchpad, not the repo.
  • Do not conclude the codebase is broken on Linux because the first build has errors. Fifty commits have never met GCC. That is expected, and fixing them is the job.
