Handoff — read this before changing anything

Written 2026-08-14, at the end of the session that made the data transfer work on Windows. For whoever picks this up next, human or agent.

It says what is genuinely verified against what is merely written, where the traps are, and what is left. It does not repeat the architecture — that is DEVELOPER_GUIDE.md, and the one fact that matters most is already there:

The ESP32 runs the experiment. The Pi records it. Peg detection and stimulation happen on the microcontroller and do not depend on the Pi. If the Pi dies mid-session the participant is still being stimulated; it just is not being recorded.

An older handoff from 2026-08-07 is in archive/AGENT_HANDOFF.md. It is superseded.

The Pi's experiments/ is empty. Eight ThumperBunny sessions were copied to the study PC and then deliberately cleared from the Pi on 2026-08-14, exercising the new clearing feature. The subject and date folders were left in place so the next recording lands where it always did. Those recordings now exist only on the study PC, in two folders on one disk — which is redundancy against a bad file, not against a dead drive.

2. The trap that produced five of the six most recent bugs

Every one of these was a place where Python silently guesses a platform-dependent default, and every one was invisible from Linux:

what was guessedwhat it cost
line endings — subprocess text mode translates \n to the local endingthe tool sent bash a CRLF script and could not read the Pi's contents from any Windows machine, ever
file encoding — read_text() uses the locale code pagebuild_docs.py died on the first em-dash and had never run on Windows
temp-directory permissions — mkdtemp creates 0700, and a move keeps permissions rather than re-inheritingrecordings arrived that the user could not open, after copying and verifying perfectly
inherited stdin — ssh forwards its own stdin to the remote commandthe tool hung after "Found it." until somebody pressed a key

If you write anything that touches files, subprocesses or encodings: state the behavior explicitly rather than letting it be inherited. encoding="utf-8", stdin=subprocess.DEVNULL, bytes rather than text for anything crossing to the Pi.

The meta-trap: a harness that hides the bug it is testing

The stdin hang was invisible to every automated check in this repository, because those checks pipe the tool's output. A pipe hits EOF immediately; an interactive console does not. The tool only misbehaved when run the way an operator actually runs it, and it was reported from the rig before it was reproduced here.

So: if a check redirects the thing's streams, it has changed the thing. Anything console-facing needs at least one run in a real console before it is believed.

3. tools/fetch_sessions.py — what to know before editing

Standard library only, no SSH library, shells out to ssh and scp. That is deliberate: a locked-down study PC needs nothing but Python. Keep it that way.

The design rules, in priority order:

  1. Copy, never move — except through the explicit clearing prompt below.
  2. Never overwrite. A session already present is skipped.
  3. Verified by SHA-256, per file. Size comparison is not enough.
  4. Every failure names the culprit — cable, address, Pi, or password. A bare error is useless to a research associate.

Staging is a plain mkdir, not mkdtemp. Do not "tidy" this back. See the permissions row above; the comment at the call site explains it.

The clearing prompt is deliberately awkward and should stay that way. It is never offered unless both stdin and stdout are a console; every session is re-verified against the Pi's hashes at that moment rather than trusted from the copy minutes earlier; a session with no closed_utc is refused because it may still be recording; the session name is checked against a strict subject/date/number pattern before it goes anywhere near rm -rf; and the operator types DELETE. Guard tests live in the session record, not in the test suite — if you touch this, re-prove that declining, pressing Enter, typing yes, typing lowercase delete, and a scripted run all delete nothing.

--dest does not update the remembered folder. Only a folder a person picked by hand does. A path-handling test once left its scratch directory as the next operator's default, and the next real run copied a study's data into it.

4. The rig's network, which is stranger than it looks

The documented setup is the Pi at a static 192.168.1.100 and the PC at 192.168.1.50/24. Both of those are true and neither is the whole story.

The Windows link is not persistent. tools/fetch-sessions-windows.cmd configures the adapter, copies, and puts the network back on every exit path including failure — so between transfers the wired adapter is on DHCP with no DHCP server, and 192.168.1.100 is unreachable. That is correct behavior, not a fault. A failed transfer must not strand a study PC on a fixed address with no route to the internet.

Do not address the Pi by name. raspberrypi.local has resolved to as many as four addresses at once: the cable's IPv6 link-local, the static IPv4, the Pi's guest-Wi-Fi IPv4, and a global IPv6 over that Wi-Fi. ssh takes whichever comes back first and spends ConnectTimeout on each dead one. This looked exactly like an intermittent transfer failure — roughly one run in four — until the timing gave it away: every failed run took 18.5 s and every successful one 6.2 s. Six calls to a single address ran 6/6 in ~650 ms. Use an address.

Two related facts worth not rediscovering:

  • The Pi's guest-Wi-Fi address is useless from the study PC — client isolation.
  • Windows interface indices change. The wired adapter's scope id went from %25 to %4 between sessions, which silently breaks any hard-coded link-local address.

scp cannot take an IPv6 address the way ssh can. The colons are indistinguishable from the host/path separator, so it needs user@[fe80::1%eth0]:path. Given the bare form it reports scp: Connection closed, which reads like a network fault and is a quoting one. scp_target() handles it.

5. Driving the Windows GUI, if you ever need to again

The operator-guide screenshots (40- to 45-) were taken by driving the real windows. Three things cost time:

SetForegroundWindow is refused to a process that does not already own the foreground. So SendKeys goes wherever the user's focus happens to be. At one point four consoles were stacked up talking over each other, and the operator spotted it on screen before any log showed it. Drive dialogs with posted messages instead — BM_CLICK for real Win32 buttons, WM_CLOSE for a Tk window (Tk draws its own widgets, so they are not child windows and BM_CLICK cannot find them).

Capture DWMWA_EXTENDED_FRAME_BOUNDS, not GetWindowRect. The latter includes Windows' invisible resize border, so a capture picks up a strip of whatever is behind the window. These images publish to a public site.

Assert that exactly one of your windows exists before and after each step, and run each dialog in its own short-lived process. Guessing which window is yours is how the above happens.

6. What is verified, and what is not

Verified on hardware: all ten checks in the Windows checklist (now archived); 100 consecutive copy-verify-delete cycles clean (800 scp invocations, 4000 verified files, 4.4–5.4 s each); the clearing exercised on the rig against two independently hash-checked copies; 22 built-in self tests; the analysis package against six real v3 sessions; the GUI power-off; the install script idempotent at 18 steps.

Written but not proven:

  • Touch is configured, not confirmed by a finger in both orientations (backlog item 10). It is mapped in rc.xml and believed correct.
  • The "close the display only" branch of the power dialog has never run (backlog item 12).
  • usb_mode=1 hardware CDC has never been tried against a slow reader (backlog item 2). The TinyUSB default works; this is an optimization.

Two test failures on Windows are pre-existing and not yours: test_pegboard.py needs numpy, which is in the repo venv and not in the system Python; and test_free_space_is_not_the_same_as_writable probes the POSIX path /proc/nonexistent/pegboard expecting it to be unwritable, which does not hold on Windows. 51 tests, 1 failure, 1 error, 4 skipped is the expected result there.

7. Repository hygiene worth knowing

.gitignore has no effect on files already in the index. venv/ and experiments/ are both correctly listed and had both been force-added at some point, so 1,601 files sat staged and the ignore rules were silently bypassed for them. They were removed from the index on 2026-08-11 (files untouched on disk). If they reappear, this is why — git rm --cached -r, not another ignore rule.

docs/site/ is a build product and gitignored. Regenerate with python3 tools/build_docs.py; --check parses without writing.

The archive is not rendered into the site, deliberately — it is explicitly historical and building it would suggest otherwise.

8. If you are picking a next task

The backlog is the real list, and closed items are kept in place with their reasoning rather than deleted — read them before re-litigating a decision. The things most worth doing, in rough order:

  1. Get the recordings off the study PC. Two copies on one disk is the weakest link in the whole chain right now.
  2. Confirm touch in both orientations with a finger — the last unverified thing in the operator-facing path.
  3. Decide whether pyproject.toml should track the system version. It is at 0.1.0 while the system is 1.0; the README explains the split, but a future reader will still ask.
  4. The first inter-peg interval is not an inter-peg interval (item 11). It contains ~600 ms of scale settling. Documented on both methods, not fixed, because the fix moves a tuned constant in the start-up path.

Two standing rules from the person who owns this rig, worth internalizing:

"Transient" is not an explanation. If something fails intermittently, script it in a loop until the mechanism is named. The 100-cycle stress run exists because of this, and it found the real cause.

Do not claim a check passed before observing it, and do not touch the git index unasked.
