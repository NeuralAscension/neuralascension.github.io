Feature Plan — Probe Activity Heatmap (live, on the probe map)#

Status: STILL UNBUILT — but read the note below first, because a NEIGHBOURING feature now exists and people keep confusing the two.

There are two heatmaps, and this document is about the one that does not exist yet#

BUILT, 2026-08-30 — the TIME × CHANNEL heatmap. A live-view column can now be switched from traces to a scrolling raster: time on one axis, channel on the other, colour carrying peak-to-peak. That is the Open Ephys probe-viewer model. It is documented in HeatmapView.md, implemented in webinterface/GlHeatmap.js, and covered by tests/gui/heatmap_view.py.

THIS DOCUMENT is about the SPATIAL map — colouring the electrodes on the probe map, in their real geometry, with no time axis. That is the SpikeGLX Shank Viewer model, and it is still unbuilt.

They are different views of the same metric, and both are worth having: a raster shows you when, a spatial map shows you where on the shank.

What the built one hands this one for free: the metric pipeline. Per-channel per-bin values already reach the page (NetworkClient, one subtraction on min/max the display stream was already sending), the colourmaps already exist as verified 256-entry tables with a shared legend painter (GlHeatmap.js: colormapBytes(), six maps, perceptual-first), and the units question is settled (display units are 100 µV — see HeatmapView.md §7). §2's "we already have the metric" is therefore more true than when it was written, not less.

What it still owes: the rendering half, below.

The goal stated below and the OpenEphys reference work (§1) are unaffected and still good. The feasibility argument is not: it rested on SciChart, and SciChart is gone.

Invalidated 2026-08-27 by the removal of SciChart. The vendored bundle (webinterface/lib/index.min.js + scichart2d.js + scichart2d.wasm) was deleted from the repo that day. Both of this document's rendering options were SciChart-native features, and both were justified here by the fact that they were verified present inside that bundle: PaletteProvider / overridePointMarker (§3 Decision 2 Option A) and UniformHeatmapDataSeries + HeatmapColorMap / GradientColorPalette (Option B). Neither API exists in the front end any more, so §2's "no canvas-overlay hack is required" is exactly backwards and §3 Decision 2 no longer offers a choice. This is a design that has lost its foundation, not a document with the wrong vendor name in it — do not read the option letters as still meaning anything.

What survives unchanged: §1 (what OpenEphys does), §2 findings 1 and 3, §3 Decisions 1, 3, 4, 5, 6 and 7, and the whole of the metric side. The channel→electrode→geometry map is still window.imroLiveView.electrodeOf(channelId) in ImroManager.js, which the removal did not touch.

A direction to investigate, explicitly NOT a verified plan: the probe map is now drawn by webinterface/ProbeMap.js in plain canvas 2D, keeping the clear() / appendRange(xs, ys, metas) series API the old scatter had. A heatmap would most likely be drawn there — per-electrode fill is a natural thing for a 2D canvas and the metas channel already carries per-point data — but nobody has prototyped it, measured it, or checked it against the culling and reactive-redraw behavior ProbeMap.js actually implements. Whoever picks this up owns that spike; treat the paragraph you are reading as a lead, and re-derive §3 Decision 2 from scratch.

Worth weighing before committing to canvas 2D: SpikeGLX draws exactly this view on the GPU, all pads in ONE glDrawArrays(GL_QUADS) with a per-vertex colour array, and only touches a pad's colour when the statistic updates rather than per frame. A canvas-2D fill per electrode is 384–1536 fillRect calls per repaint. That may well be fine at probe-map refresh rates — the point is that it should be measured against the alternative rather than assumed, and GlHeatmap.js is now a worked example of the WebGL2 path in this codebase if it turns out not to be.

Goal: Once a channel map is applied and data is streaming, stop "freezing" the probe-map tab to a static selection. Instead, color the selected electrodes by live activity — a dark-mode take on the OpenEphys ProbeViewer heatmap, with the active sites "blinking"/glowing by activity level.

References: the OpenEphys source we mirror is vendored at Source-OpenEphys-Neuropixels-PXI/UI/ (ProbeBrowser, ActivityView, ColourScheme). Our probe map internals are in LiveDataView.md and webinterface/ImroManager.js.

1. How OpenEphys does it (the thing to match)#

From UI/ActivityView.cpp, UI/ProbeBrowser.cpp, UI/ColourScheme.cpp, UI/NeuropixInterface.cpp:

  • Metric = per-electrode peak-to-peak amplitude (max − min) over a sliding window, in µV. Not RMS or spike rate. (ActivityView.cpp calculatePeakToPeakValues ~344-381.)
  • Window ≈ 100 ms, refreshed at 10 Hz (startTimer(100), NeuropixInterface.cpp). AP window = 3000 samples @ 30 kHz; LFP = 250 @ 2.5 kHz.
  • Two modes: AP-band vs LFP-band activity (a combo box).
  • Optional pre-processing (both on by default): common-average reference (ADC-group-aware) + a 300-6000 Hz Butterworth band-pass, applied before min/max.
  • Colormap = Inferno (matplotlib), a 256-step LUT (ColourScheme.cpp). Black→purple→orange→yellow — already dark-mode friendly. (Viridis/Plasma/Magma/Jet also available.)
  • Normalization = fixed clim, not auto-scaling: color = inferno(p2p / clim), clim selectable {250, 500, 750, 1000} µV, default 500. No-data sites (sentinel -1) drawn gray (160,160,160).
  • Geometry: one filled rectangle per electrode, placed by integer (shank, column_index, row_index) — same grid our probe map already uses. Selected sites get a contrasting outline.
  • Channel→electrode mapping (refreshActivityViewMapping) ensures activity lands on the correct physical site even as the IMRO selection changes; the full electrode array stays gray except the connected channels.

2. The big shortcut — we already have the metric and the renderer primitives#

Half of this heading is dead as of 2026-08-27. The metric shortcut (finding 1) and the geometry shortcut (finding 3) hold. The renderer primitives (finding 2) were SciChart's, and SciChart was removed. See the banner at the top.

Two findings make this much cheaper than OpenEphys's full pipeline:

  1. Peak-to-peak is already on the wire. DisplayProcessor decimates each channel to min and max per timebin and streams both (DisplayProcessor.cpp; parsed in NetworkClient.js). So p2p = max − min per channel is computable in the browser today, with zero backend change — exactly OpenEphys's metric. Aggregate over ~100 ms of timebins for a smoothed value.

  2. ~~SciChart v5.2.35 (our bundle) natively supports the rendering we need — verified present in lib/index.min.js: PaletteProvider / overridePointMarker (per-point coloring of a scatter series), UniformHeatmapDataSeries + HeatmapColorMap (a true heatmap), and GradientColorPalette. No canvas-overlay hack is required.~~ VOID 2026-08-27. All four of those APIs came from the vendored bundle, and the bundle was deleted — webinterface/lib/ now holds qwebchannel.js and nothing else. The verification was honest when it was done and it is worthless now, because the thing verified is not in the tree. There is no inherited rendering capability to build on: the drawing has to be designed, not selected.

  3. The channel→electrode→geometry map already exists as window.imroLiveView.electrodeOf(channelId) (+ colOf, slotOf, isRef) in ImroManager.js. An incoming per-channel activity value maps to a probe-map point with electrode = imroLiveView.electrodeOf(ch) → row = electrode>>1, col = electrode&1.

3. Design options#

Decision 1 — WHERE activity is computed#

  • Option A — derive in JS from the existing min/max stream (RECOMMENDED to start). p2p = max − min per channel, smoothed over ~100 ms, refreshed ~10 Hz. No C++ change. Faithful to OpenEphys's core metric. Limitation: broadband (no CAR, no 300-6000 Hz band-pass), so it's "raw" activity, not spike-band-clean.
  • Option B — a dedicated C++ ActivityProcessor that mirrors OpenEphys: CAR (ADC-group-aware) + 300-6000 Hz BP + windowed p2p, streamed as a compact per-channel frame (one f32/channel at 10 Hz). More faithful, isolates the cost from the display path, but is new backend work.
  • Recommendation: A first (immediate, free); add B later if you want spike-band fidelity.

Decision 3 — colormap#

Inferno (OpenEphys default, dark-mode native), as gradient stops. Offer Viridis as an alternative. (We don't need the 256-row LUT — matplotlib gradient stops reproduce it.) (This decision is unaffected by the SciChart removal; only the two API names it used to cite for the gradient — GradientColorPalette / HeatmapColorMap — went away, and a color ramp is a handful of lines anywhere.)

Decision 4 — normalization / clim & units#

Fixed, user-selectable clim like OpenEphys (250/500/750/1000, default 500), gray for no-data. Open item: confirm the units of our min/max stream (the DisplayProcessor applies NPX gains — need to check whether the result is µV) so the clim numbers are meaningful; otherwise clim is in "display units" and we relabel. (DisplayProcessor.cpp gain logic + Npx.hpp.)

Decision 5 — what "blinking" means (please pick)#

  • Option A — brightness/color tracks activity at ~10 Hz (OpenEphys behavior): active sites glow bright (yellow), quiet sites stay dark. Reads as "live activity," not literally blinking. (recommended)
  • Option B — literal pulse: modulate marker opacity/size sinusoidally, with pulse amplitude or rate proportional to activity. Can be layered on top of A.
  • "Blinking based on activity level" could mean either — A is proven/readable; B is flashier. Tell me which (or A-with-optional-B).

Decision 6 — lifecycle / mode#

Today the map is static after render. Proposal: when streaming starts, the probe tab enters Activity Mode (auto, or via a toggle button next to the tabs) — selected electrodes are colored by activity; selection editing is disabled while live (re-enabled when paused). Decide: auto-on while streaming vs manual toggle (default on).

Decision 7 — scope of probes#

NP1.0 first (single shank, 2 columns). NP2.0 (4 shanks) reuses the same electrodeOf/shankOf mapping and either a per-shank palette or a wider heatmap — straightforward but do it after NP1.0.

4. Implementation outline (assuming JS-activity / PaletteProvider / Inferno / auto-mode)#

Steps 2 and 3 are void as of 2026-08-27 — PaletteProvider / overridePointMarker and sciChartSurface.invalidateElement() went with the bundle. Steps 1 and 4 stand: deriving p2p from the min/max already on the wire, and the clim / mode / legend UI, are both renderer-independent, and so is the Decision-1B backend variant at the end. Do not follow steps 2 and 3; they are kept so the shape of the missing piece is visible — a per-electrode fill function plus a redraw trigger — not as instructions.

Frontend only (Option A/A): 1. Activity store + derivation (NetworkClient.js after each batch, or a 10 Hz timer): for each channel, p2p = max − min smoothed over ~100 ms; electrode = window.imroLiveView.electrodeOf(ch); write window.probeActivity[electrode] = p2p. (Reuse the data already parsed for the charts.) 2. PaletteProvider on the active scatter series in ImroManager.js renderElectrodeMap: implement overridePointMarker(x,y,i,opacity,md) → fill = inferno(clamp(probeActivity[md.electrode]/clim)), gray if no data. Store md.electrode per point (already storing md.text). 3. Refresh loop (~10-30 Hz requestAnimationFrame or setInterval): update probeActivity, then sciChartSurface.invalidateElement() so the palette re-evaluates. (Optional pulse = modulate opacity in the palette by a time term × activity.) 4. UI: clim dropdown (250/500/750/1000), AP/LFP mode toggle (if both streams present), a colorbar legend, and the Activity-Mode enter/exit on play/pause.

If Decision 1B (C++ activity): add src/modules/.../ActivityProcessor (CAR + BP + windowed p2p), register proc.*.activity, stream [ "activity" ][u32 nCh]([f32]×nCh) at 10 Hz; the JS step 1 then just reads that frame instead of deriving p2p. Steps 2-4 unchanged.

5. Risks / unknowns#

  • The renderer itself is now the top risk, and it is no longer a signature question. ~~Per-point palette ergonomics: PaletteProvider exists in the bundle; confirm the exact IPointMarkerPaletteProvider signature in v5.2.35 during a spike (it's the one API I'd prototype first).~~ The bundle is gone (2026-08-27). What replaces this risk is larger: how per-electrode activity color is drawn at all, and what that costs inside ProbeMap.js's existing culling and reactive-redraw behavior. That is a spike to run before any of §6 can be answered, not a signature to look up.
  • Units for clim (Decision 4) — verify µV vs display units.
  • Cost at 10-30 Hz: ~384-960 points re-evaluated per frame is cheap, but confirm the redraw cadence doesn't fight the live charts. (The "they share the WebGL context budget" reasoning this bullet used to give stopped being true on 2026-08-27: the probe map is canvas 2D and the traces are WebGL2, so they no longer share a context. They still share the main thread and the GPU, so the question stands — the mechanism behind it has to be re-argued.)
  • JS-derived activity is broadband (no CAR/BP) — acceptable to start; Decision 1B closes the gap.
