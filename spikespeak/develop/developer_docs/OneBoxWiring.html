OneBox connectors and rig wiring#

What is bolted into the hardware, what is a patch cable, and which of the two you are looking at.

This page exists because those three things kept getting confused, at real cost: four days of #49 were spent watching the wrong connector, and on 2026-08-31 an agent talked itself into a hardware-contention warning by treating a back-panel SMA and a breakout BNC as the same node.

1. The distinction that matters#

layer changes? example
Connectors on the box never the box has an SDR, an ADC, a DAC and a back-panel SMA 1
Fixed routing inside the box never (it is silicon) DAC0's output arrives on breakout BNC IO0
Patch wiring on the bench every session which IO the SMA is patched to; what is on IO2

Almost every wiring mistake in this project has been reading a line from the third row as though it came from the second. A statement like "the SMA is IO9" is only ever true of one afternoon.

2. The connectors (fixed)#

The front panel carries SDR, ADC and DAC. The back panel carries SMA 1.

The 12-channel stream SpikesPeak reads arrives over the SDR connector, through the imec NPOB_SDR_02 breakout, whose BNCs are labeled IO0–IO11. That is why the live view says OneBox ADC (SDR) and labels its traces IO0…IO11 — the trace and the connector you patch into carry the same name.

IO0…IO11 are breakout BNCs. They are not the SMA, not the ADC connector and not the DAC connector.

3. Fixed routing, measured rather than assumed#

DAC0 → breakout BNC IO0#

The vendor API documents waveplayer_arm() as "routing output DAC0 to the SMA output". It does not. Measured on this hardware: a 1 Hz ±2 V square moved IO0 from sd 0.0002 to 1.9894 V while IO9 — where the SMA was patched that day — stayed at 4.963 V, unchanged.

Consequences worth holding onto:

  • The WavePlayer's analog output appears on IO0, so anything patched to IO0 shares a node with a DAC output driver. That is only live while the WavePlayer is armed — arm() calls np_DAC_enableOutput(DAC0) and disarm clears it — but it is worth knowing before shorting IO0 to another driven source.
  • This is not a statement about the SMA. SMA 1 has no fixed IO number at all — see the next subsection. (§4 is the dated bench table; it tells you where the SMA was patched on a given day, which is a different kind of claim.)

SMA 1 has no IO number#

SMA 1 is a physical connector on the back of the box. It becomes readable as an ADC channel only because somebody patches it to a breakout BNC, and it is therefore a different channel on different days. It has been IO9; as of 2026-08-31 it is IO11.

There is no sense in which "SMA 1 is IOn" is a property of the hardware. Any document, comment or default that says so is describing one session.

2026-08-24 — Pi stim trigger SMA 1 — IO6 → IO4 loopback

Note what IO9 has been, oldest to newest: a train gate, then the SMA, then nothing. It is not "the SMA channel".

The current wiring, and what it is good for#

IO0 and IO11 are shorted, so two ADC channels at opposite ends of the array carry one electrical node. That is the strongest available test of the comparator demux (#67): the comparator states are the last 12 of 24 samples in each packet, and the characteristic failure of that unpacking is an off-by-one or a stride error, which presents as channel N carrying channel N±1's bit. With one signal on one channel that is invisible — you see a square wave and conclude it works. With the same node on IO0 and IO11, the two comparator streams must be bit-identical sample for sample, and any disagreement is our software by construction.

⚠️ While IO0 is shorted to a driven line, do not arm the WavePlayer — that would put the DAC0 output driver and the external source on the same node.

A default that is right for one bench and silent about it is the failure mode here. A sync channel pointed at the wrong index produces a recording that looks fine and aligns wrong — the same shape as the align_timestamps off-by-one, which was invisible because the intervals still looked right.

6. The OneBox ADC band, and how to work with it#

The twelve BNCs above are inputs to a real acquisition band, with its own name, its own clock and its own scale. That band is documented in five places for five different reasons — the live view's label, the recorder's sidecar, the analyzer's flags, the config key, the packet layout — so the facts you need to read one of its recordings are collected here.

fact value where it comes from
band name on disk and in configs data.npx.adc → files <name>_adc_<stamp>.bin every profile that declares a data.npx.adc output -- config/*OneBox*.yaml, plus Neuropixels.yaml and NeuropixelsNiDaq.yaml, which reach a OneBox through source.npx.auto -- and interp.npx.adc
what the GUI calls it OneBox ADC (SDR) webinterface/ChartColumn.js streamLabel()
channels 12, labeled IO0…IO11 after the breakout BNCs kOneBoxAdcChannelCount in src/modules/neuropixels/OneBoxAdc.hpp
clock ~30300 Hz, and it is not the probe's 30 kHz sample_rate_hz: 30300 in every profile that declares the band
input range ±2.5 / ±5 / ±10 V, config key adc_voltage_range:, default 5 OneBoxSource::initDataSource
counts → volts 6553.6 counts/V at ±5 V (32768 / 5) asked of the device with np_ADC_getStreamConversionFactor at every range change, and written into the sidecar's scale block

The two clocks are the point, and the reason not to worry about them. The ADC runs at 30300 Hz while the probe runs at 30000 — but both stream from one device and both carry the same 100 kHz hardware tick counter in their packet info. So a stim pulse captured on the ADC and a threshold crossing on the probe are already on a shared clock, and no sync fit is involved. That is the single biggest reason a OneBox rig captures its stimulus monitor here rather than on a second card (LatencyProfiling.md).

What the ADC cannot tell you: pulse width#

At ~30.3 kHz one sample is 33 µs, so a ~130 µs stimulus pulse spans about four of them. Measured across 67 consecutive fires of an identical commanded pulse on 2026-08-21, the threshold-crossing width came out as 1, 2 or 4 samples purely by where the pulse landed relative to the sample clock. Taking the most-populated bin gives a number that looks like a confirmation and is not one.

Occurrence, count and timing: yes — to within a sample. Shape or width: no. Ground truth for width is an oscilloscope. Full working, and the figure that got a wrong caption because of it, in LatencyProfiling.md.

The flag the offline analyzer needs, and the silence if you forget it#

ripple_tools/analyze_recording.py looks for a nidaq band by default. On a OneBox recording there is none, so without --stim-band adc --stim-channel <n> it reports no closed-loop latency and exits 0 — a clean run, a figure, and the one number you wanted quietly absent:

python ripple_tools/analyze_recording.py <recdir> --ws <recdir>/<name>_ws.jsonl \
    --stim-band adc --stim-channel 2 --figs <recdir>/analysis

The channel is bench wiring (§4), not a property of anything.

The comparator band, data.npx.adc.di#

Every ADC channel also feeds a comparator, always, whether or not anyone reads it. Those twelve logic bits ride in the same packet as the analog counts: an ADC packet carries 24 samples — 0–11 the analog counts, 12–23 the comparator states (OneBoxAdcWorker::slDoAcquireDataLoop). channel_count is a prefix length, so asking the vendor API for 12 gets the analog half and costs nothing, which is why the digital path is off unless you ask for it.

  • Naming a data.npx.adc.di output in a profile is the whole switch: it widens the read to 24 and turns on the per-batch demux.
  • Exactly one shipped config declares it — config/Npx2OneBoxDigitalIn.yaml, name: "NPX 2.0 Multishank (OneBox + digital in)" — and that config is gui_hidden, so the band exists but no dropdown entry produces it.
  • Its stream id is adc_di, and ChartColumn.streamLabel() has no entry for it, so it renders through the fallback as ADC_DI Band rather than a written name. That is cosmetic, and worth knowing before you go looking for a label that was never authored.
  • The two rings are indexed by the same write index and must have the same capacity; the worker drops the digital half loudly rather than write past the end if they ever differ.
  • The comparator is a Schmitt pair in absolute volts (TTL defaults 0.7998 / 1.9997 V) and the thresholds persist in the device across sessions, so a previous run's narrowed window is still there for whoever connects next.

Input range, and the trap in it#

The ADC offers ±2.5 V, ±5 V or ±10 V, set per profile with adc_voltage_range: and defaulting to ±5 V. At 6553.6 codes/V a 5 V input is 32768 codes — exactly one past int16 max.

So a 5 V logic signal on the default range sits on the rail: real 5 V drivers idle slightly above 5 V unloaded and square edges ring, so the analog trace clips flat. The trap is that the comparator bit beside it stays perfectly correct, so a digital-input test looks entirely healthy while its analog channel is saturated.

Use adc_voltage_range: 10 for logic-level signals. The comparator thresholds are absolute volts (TTL defaults 0.7998 / 1.9997 V, a Schmitt pair — it holds between them) and stay valid at any range.
