Debugging guide

For the engineer. What to check first, the techniques that actually work on this rig, and the traps that each cost hours the first time.

Architecture and file-by-file reference: DEVELOPER_GUIDE.md.

1. Start with the self test

Before reading any code: open the display, tap the SELF-TEST lamp, and read the panel. 22 checks across the board and the Pi, and most of the failures below have a light of their own. It is faster than any of the techniques in this document and it is right more often.

From a shell instead:

ssh remyelin-pi@192.168.1.100 'journalctl -u pegboard-display --since "-5min" --no-pager | grep -i bist'

Or straight at the board, with no Pi involved:

printf 'selftest\n' > /dev/ttyACM0 && timeout 8 cat /dev/ttyACM0

2. Symptom → what is actually wrong

symptomfirst thing to check
Chart flat at zero, but movingCorrect. An untouched pegboard reads ~0 g
Chart not moving at allIs streaming on? Then ESP32 lamp, then the USB cable
Board goes silent after ~5 s of activityTask watchdog. A loop is missing a real vTaskDelay — see §4
Board silent after exactly ~53 messagesThe same, and this is its signature: 53 × 94 ms = 5.0 s
Streaming stops the moment the Pi app restartsOpening the port resets the board and clears its stream flag. app.py re-sends stream_data; if you added reopen logic, account for it

3. Techniques

Deploy to the Pi

rsync -a --exclude __pycache__ raspberry-pi5/ remyelin-pi@192.168.1.100:~/Documents/Code/pegboard/raspberry-pi5/
ssh remyelin-pi@192.168.1.100 'sudo systemctl restart pegboard-display'

The Pi uses the same layout as the repo. It did not until 2026-08-10 — it was display/ there, from a checkout stranded before the rename — so anything written before that date which mentions display/ is stale.

Flash the firmware

export PATH="$HOME/.local/bin:$PATH"
arduino-cli compile --fqbn esp32:esp32:adafruit_feather_esp32s3 \
  --upload --port /dev/ttyACM0 microcontrollerCode/adafruitESP32Feather_s3_usb

This can only be done from the laptop, not the Pi — the Arduino toolchain's esptool is an x86-64 binary and the Pi is aarch64, with no route to install another. Flashing means physically moving the board. Plan firmware work in one batch before handing the board back.

Toolchain on the laptop: arduino-cli 1.5.1, esp32 core 3.3.11, HX711 0.6.4.

Talk to the board directly

The project's own transport is the least surprising way in — it already knows not to set HUPCL:

import sys, time
sys.path.insert(0, "raspberry-pi5")
from serial_link import SerialLink

lk = SerialLink()
while not lk.ready:
    time.sleep(0.05)
lk.write_line("selftest")
for _ in range(400):
    for line in lk.poll():
        print(line)
    time.sleep(0.02)

Drive the UI on the Pi

Launch Chromium with the DevTools port open, then drive it over the protocol. simple_websocket is already in the Pi's venv — pyserial and requests are not.

ssh remyelin-pi@192.168.1.100
export XDG_RUNTIME_DIR=/run/user/1000 WAYLAND_DISPLAY=wayland-0
nohup chromium --ozone-platform=wayland --start-fullscreen --no-first-run \
  --remote-debugging-port=9222 --user-data-dir=/tmp/pegboard-kiosk \
  --app="http://127.0.0.1:5000/" </dev/null >/tmp/kiosk.log 2>&1 &
import json, urllib.request, simple_websocket
t = json.load(urllib.request.urlopen("http://127.0.0.1:9222/json"))
p = next(x for x in t if x["type"] == "page")
ws = simple_websocket.Client(p["webSocketDebuggerUrl"])
ws.send(json.dumps({"id": 1, "method": "Runtime.evaluate", "params": {
    "expression": "document.getElementById('toggleButton_streamData').click()",
    "returnByValue": True}}))
print(ws.receive(timeout=10))

Note the launch must be detached from the SSH session (nohup + redirect all three streams); backgrounding it alone gets it killed when ssh exits.

Screenshots

ssh remyelin-pi@192.168.1.100 'XDG_RUNTIME_DIR=/run/user/1000 WAYLAND_DISPLAY=wayland-0 grim /tmp/shot.png'
scp remyelin-pi@192.168.1.100:/tmp/shot.png .

Rotate the display

~/Documents/Code/pegboard/raspberry-pi5/desktop/rotate-pegboard.sh upright
~/Documents/Code/pegboard/raspberry-pi5/desktop/rotate-pegboard.sh sideways

The choice is stored in ~/.config/pegboard/orientation and re-applied at login by an entry in ~/.config/labwc/autostart.

Local development without the Pi

.venv-dev/ has flask, flask-socketio, numpy, matplotlib, scipy. app.py runs without gpiod and reports the stimulation input as unavailable, so the UI can be worked on entirely off-hardware — the self-test panel will show pi.gpio_capture red, which is correct on a laptop.

PEGBOARD_HOST=127.0.0.1 ./.venv-dev/bin/python raspberry-pi5/app.py

Tests

python3 -m unittest discover -s tests -v

Runs on the Pi itself (standard library only). GPIO tests skip automatically where there is no gpiochip.

4. Traps

Every one of these was found the hard way.

pkill -f matches the shell's own command line. ssh pi 'pkill -f "app.py"; python app.py &' kills the SSH session, because the remote shell's argv contains app.py. Use two separate calls, or a pattern the command does not itself contain — pkill -f "app[.]py" works.

Opening a CDC serial port resets the ESP32. DTR assertion reboots it, which also clears its stream flag — so it goes silent and looks frozen. serial_link.py deliberately does not set HUPCL, and app.py re-sends stream_data after any (re)open. Do not add reopen-on-error logic without accounting for this.

Anything the board prints before the host attaches is gone. Not buffered — dropped. The firmware's boot-time self test writes into a USB endpoint nobody is draining and simply vanishes, which is why app.py sends selftest itself after opening the port rather than waiting for the automatic run. Assume the same of any future boot banner.

HX711::read() never times out. It waits on DOUT with nothing but yield(), so an unpowered or unplugged amplifier would hang the acquisition core until the 5 s task watchdog fired. Every read in the sketch is now bounded (waitReady/readRawAverage/readUnits) and the board reports hx711_present FAIL instead of dying — but the library call itself is still a trap, so do not reintroduce a bare scale.get_units(), read_average() or tare() anywhere.

The touchscreen does not send touch events to the browser. ~/.config/labwc/rc.xml sets mouseEmulation="yes" for the panel, so every finger press arrives at Chromium as a mouse press/move/release. A mouse drag does not pan an overflow:auto container — it selects text — which is why the self-test list scrolled perfectly under synthesised touch events (CDP Input.dispatchTouchEvent bypasses the emulation) and not at all under a real finger. Drag-to-scroll is implemented in JS for pointer drags; it stands aside for genuine pointerType === 'touch'. Test touch behaviour with Input.dispatchMouseEvent, not dispatchTouchEvent, or you are testing a path the hardware never takes.

An open file descriptor outlives the device. Unplug the board and link is still a valid object wrapping a dead fd, so "USB cable to the board" read port open with nothing connected. The device node disappearing from /dev/serial/by-id is the authority, not the handle.

taskYIELD() does not feed the FreeRTOS watchdog. It only yields to equal-or-higher-priority tasks, so the idle task never runs and the 5 s TWDT fires. Every pinned task loop needs a real vTaskDelay. Symptom: streaming stops after exactly ~53 messages.

Socket.IO buffers emits across a disconnect and replays them on reconnect. A shutdown pressed against a dead server fired minutes later when the service restarted, and powered off the Pi. Guarded now, but assume any emit can be deferred.

Plotly resolves autorange into a concrete range written back onto the layout object you passed. Re-passing that layout then reads as a user-set range and the axis stops tracking forever. Both axes are driven explicitly every frame.

Plotly does not track its container. After a rotation or any re-layout the charts keep their old pixel canvas. A ResizeObserver on .graph-container calls Plotly.Plots.resize for both.

The CSS overflow shorthand resets both axes. An overflow-y: auto earlier in a rule is silently undone by a later overflow: hidden. This made a scroll fix look applied when it did nothing.

Media queries add no specificity — source order decides. A portrait block placed before the lamp and dialog rules was overridden by every one of them. It lives at the end of the stylesheet for that reason.

The panel profile is keyed on "short OR narrow". Keyed on max-height alone it stopped applying the moment the panel was left in its native portrait orientation, and the whole touchscreen design silently fell back to desktop styles.

Flask caches templates when debug=False. TEMPLATES_AUTO_RELOAD = True is set, but the browser still needs a reload.

The chip strip re-renders on session-state change, deleting anything appended to it. The status lamps re-mount themselves on a timer because of this.

NetworkManager autoconnect races manual nmcli con up. With autoconnect-priority 100, every manual activation was interrupted, surfacing as ASSOC-REJECT status_code=16 — which looks exactly like an auth failure and sends you hunting the wrong problem.

nmcli radio wifi off/on wedges the Broadcom radio on this Pi (brcmfmac: set chanspec ... fail, reason -52, empty scans). Recover with modprobe -r brcmfmac_wcc brcmfmac && modprobe brcmfmac. Avoid the command.

5. Reading a recording after the fact

The session directory carries its own evidence. In events.csv:

  • bist rows — every self-test result at the time, with its measurement and limits. If the rig was degraded during a session, it is written down.
  • stim_rise / stim_fall — what the participant actually received, timed by the kernel rather than inferred.
  • clock_epoch — the board restarted its timer; do not compare mcu_time_ms across one.

clock_sync.csv is the audit trail for t_ms. If converged is false or skew_ppm is implausible, t_ms is falling back to arrival time and the sample timestamps are worth less than usual — the GPIO edges are unaffected.

raw_udp.log is verbatim board traffic (the name is historical; it is serial now). Sequence numbers are in it, so a gap is visible by eye.

6. The Pi's clock

The Pi has no battery-backed clock — its RTC reads 1970 on every boot — and no reliable internet. It has already misfiled a session once by being ~20 h behind, and nothing in the system notices, because a wrong date produces a perfectly valid recording in the wrong folder.

The pi.clock_date self test now watches for this: it warns when the clock is not NTP-synchronised, and fails when a recording already exists dated in the future, which is proof rather than suspicion.

Check and fix from a machine that knows the time:

ssh remyelin-pi@192.168.1.100 'timedatectl'
ssh remyelin-pi@192.168.1.100 "sudo date -s '$(date -u '+%Y-%m-%d %H:%M:%S')' && sudo fake-hwclock save"

It will drift again.

7. What is verified, and what is only written

Worth keeping honest, because a lot of time has gone into discovering that something "working" had never really been tested.

Verified on real hardware

  • Two complete 25-peg sessions, right and left hand, 2026-08-07 — the first and only real end-to-end data.
  • USB serial: 2241 messages, zero sequence gaps.
  • Detection latency 211 ms, pulse width 1036 ms, GPIO edge −6 ms before the reported message.
  • Decomposed latency across 50 pegs: sampling lag 94 ms, detect+settle 133 ms, total landing→stimulation 227 ms. Superseded — the 2026-08-10 profiled sessions measure 229 ms (IQR 227–231); see CLOSED_LOOP_LATENCY.html.
  • stop_timer disarm: acknowledged, board reports reset, streaming continues.
  • GPIO26 edge capture via internal-bias toggling on a spare line: 10/10 edges.
  • Self tests, 2026-08-10: 11/11 firmware checks pass; the greenlight, the panel and both suites driven end-to-end on the Pi; the trigger wire loopback passed — 53 ms measured on GPIO26 against 50 ms commanded.
  • Both display orientations, on the panel, with live data.
  • 54 tests in tests/test_display.py, 1 skipped without a gpiochip.
  • Reboot survival: service, emoji font, GPIO claim.

Written and reviewed but NOT verified against real data

  • The pegboard analysis package. 35/35 of its own tests pass and it reads the eight legacy .txt files and synthetic v3 sessions — but it has never been run against the two real v3 sessions. Backlog item 11.
  • GUI power-off, which has only ever fired accidentally via a queued command replayed on reconnect. "Close the display only" has never been run.
  • Touch input after rotation. labwc is told to map the panel's touch device to the output and applies the transform itself, so it should follow — but nobody has tapped the screen in both orientations to confirm it.
