Filter debugging — the .bin dumps, the kill switches, and how to validate the filters#

The ripple pipeline runs two filter stages that are easy to get wrong and hard to eyeball live. Both can dump their intermediate signals to .bin files so they can be checked offline. Both dumps ship OFF; this page is how to turn them on, validate the filters, and turn them back off.

The two kill switches#

Flag File Default Gates
DEBUGGING_RIPPLE_DETECTION_FILTERS src/modules/swr/RippleDetector.cpp (top) false lfp-data.bin, ripple-band-data.bin, envelope-data.bin, ripple-detection-time.bin
DEBUGGING_LFP_FILTERS src/modules/lfp/LFPProcessor.cpp (top) false lfp-filter-data.bin

They are static constexpr bool, so when false the file creation, every per-sample write, and the close all compile out — no branch, no cost on the detection hot path, and nothing appears in the working directory. The ripple flag is ANDed with the pre-existing runtime config key debug_files: (see config/*.yaml), so you need both to get dumps: DEBUGGING_RIPPLE_DETECTION_FILTERS = true and debug_files: true.

Why they are off. These write one record per sample per channel into the process working directory — ~1 MB per channel per 30 s for the ripple dumps, ~350 KB/s for the LFP dump — landing as untracked .bin files in the repo root, from a write on the real-time detection path. They are a development aid, never something to leave on for a recording session.

Dump formats#

All little-endian float32, written per sample, and N-way interleaved when N detection channels are active (in mDetectionChannels order — the same timestamp repeats once per channel):

File Record Meaning
lfp-data.bin (ts, lfp) detector INPUT (NP1: native int16 LFP cast to float; NP2: derived float LFP)
ripple-band-data.bin (ts, ripple) after the 26-tap 150–250 Hz FIR
envelope-data.bin (ts, envelope) after abs() + the 10-tap envelope FIR
ripple-detection-time.bin (ts) one record per quorum detection
lfp-filter-data.bin (ts, raw_in, lfp_out) the LFP module's Bessel low-pass, for DEBUGGING_LFP_FILTERS_CHANNEL

ts is the LFP-clock timestamp in seconds (hardware timestamp ÷ sampling rate).

Validating the filters#

ripple_tools/validate_filters.py re-runs the same two FIRs offline over lfp-data.bin and compares against the backend's own ripple-band-data.bin / envelope-data.bin, sample for sample. The offline coefficients in ripple_tools/plot_demo.py (B_RIPPLE, B_ENV) are transcribed from src/core/Common.hpp (RippleBandFilterCoefficients2_5kHz, EnvelopeFilter2_5kHz) — they are verified identical.

# with the flags on and a short session recorded:
python ripple_tools/validate_filters.py --dir .

It prints three comparisons per channel and passes when the relative error is < 1e-4:

  • ripple band (26-tap FIR) — offline FIR over the dumped LFP vs the backend's ripple band
  • envelope (10-tap FIR) — the full offline chain vs the backend's envelope
  • envelope from backend rb — offline envelope filter fed the backend's OWN ripple band; this isolates which stage is wrong when the envelope disagrees but the ripple band matches

Result — validated 2026-07-20 (PASS)#

Two channels, 66,725 samples each, from a simulated NP1.0 session:

comparison max abs err relative correlation
ripple band (26-tap FIR) 2.2e-05 2.0e-07 1.000000000
envelope (10-tap FIR) 1.4e-05 1.8e-07 1.000000000
envelope from backend rb 1.1e-05 1.5e-07 1.000000000

Relative error ~2×10⁻⁷ is exactly float32 rounding on a signal of RMS ~108 — i.e. the backend's filters are bit-level correct implementations of the reference. Both filter stages are causal, zero-initial-state Direct-Form FIRs applied sample by sample, which is exactly np.convolve(x, b)[:len(x)] — that equivalence is what makes the offline reconstruction in analyze_recording.py trustworthy.

This also independently corroborates the recording-side result: on the NP1.0 hardware tests the offline envelope crossings paired 1:1 with the ai4 stim pulses (99/99, max deviation 4.6 ms), which could not happen if the online filters diverged from the offline ones. See RippleClosedLoopAnalysis.md and RecordingTests/CLOSED_LOOP_LATENCY.md.

Housekeeping#

The dumps are written to the process working directory, which for python run_spikespeak.py is the repo root. They are untracked build litter, not data:

rm -f lfp-data.bin ripple-band-data.bin envelope-data.bin ripple-detection-time.bin lfp-filter-data.bin

Delete them after any debugging session. If you find them in a fresh checkout, someone shipped a flag flipped to true — check both files listed at the top of this page.
