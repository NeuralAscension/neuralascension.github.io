SpikesPeak — Source architecture: taming the config explosion + arbitrary/NeuroNexus/replay sources (design options)#

A planning brief (no implementation) for reorganizing "source options." When this was written there were 23 near-duplicate config profiles behind two hand-synced pickers; Phase 1 shipped on 2026-08-26 (see the STATUS banner below), and as of 2026-09-02 config/ holds 31 files behind two operator-visible hardware entries (Neuropixels, PXIe with NI-DAQ — basestation and probe read from the rig), an Intan entry that refuses to connect, and the simulated picker. What remains awkward is adding a new kind of source (an arbitrary simulated Neuropixels geometry, a NeuroNexus probe on the Intan interface, or replaying a recorded file by hitting Play). This doc maps the current state and lays out multiple options with a phased recommendation for the maintainer + collaborator to choose from.

Wider context: builds on SimDataLinux.md (the "one sim class per module" ruling + the future-device seam), AddingASourceModule.md (the IDataSource contract), SyntheticSources.md (procedural sim + .h5 playback), and SpikesPeak_Architecture_Review.md §7 (per-module Q_INVOKABLE, no central router). Related: NextTask_CommandEventBus.md — source selection today leans on the same fragile string-matching a topic bus would replace. Tracking: SpikesPeak_Status.md §19.1 (file playback goal) + §34. Transient NextTask_ brief — fold the durable design into a topic doc once a direction is chosen; git mv to archive/ when done.

Do NOT implement any of this yet. This is a decision doc.#

STATUS 2026-08-26 — PHASE 1 IS DONE. Goal 1 ("fewer / better-organized source options") is delivered: twelve hardware profiles collapsed to three, one picker, no label collisions, no accidentally-invisible configs. (Overtaken the next day, 2026-08-27: those three went gui_hidden behind two self-naming entries, Neuropixels and PXIe with NI-DAQ — see §2.1.) The durable design is written up in SourceSelection.md; the rest of this brief remains a decision doc for Phases 2 and 3, which are untouched.

It was reached by a different route than §4.1 proposed, and the difference is worth recording. Option A assumed the cross-product had to be collapsed by a config layering (include:) loader in Configuration.cpp. None was needed. The axis doing most of the multiplying — the probe — is discoverable: the basestation reports the part number on connect, and setupSources() finishes before setupProcessors(), so every probe-dependent binding can be resolved from the detected probe rather than from a profile. Removing that axis takes 2 (probe) x 3 (basestation/NI-DAQ) down to 3 files with no new loader and no new config semantics. §4.1's "capability-tagged list" survives as exactly two optional keys, sim_basestation: and sim_probe:, and only for the simulated picker, where there is no hardware to ask.

Of the remaining axes named in §2.2, ADC on/off and scenario did not collapse: they are still one profile each, now gui_hidden so they are out of the operator's way while staying CLI-selectable. ASAP delivery did, on 2026-09-02: it is a runtime request (#80) and its five profile copies are gone. Making the other two runtime toggles is real work and is not what "fewer options" required.

1. Context — the problem and the goals#

Problem: the source layer grew by hand-materializing every combination as its own YAML, and the picker that surfaces them was bolted on twice (hardcoded HTML for real sources, a dynamic sim_variant list for sims). The result was 23 near-identical configs, label collisions, two sim configs invisible to the GUI, and human-facing name strings ("(play file)", "onebox", "NPX") driving real control flow.

Goals the new design must serve (maintainer, 2026-07-24): 1. Fewer / better-organized source options — stop the combinatorial config sprawl and the dual picker. 2. Simulate arbitrary Neuropixels sources — one parameterized sim, not a new class per geometry. 3. NeuroNexus probes on the Intan interface — a future hardware source family (Intan = acquisition box, NeuroNexus = the probe). 4. Restream a recorded file by hitting Play — a first-class file-playback source that reproduces the exact data.* streams a live source would, so display / ripple-detection / recording are unchanged.

2. Current state as of 2026-09-02 (what any plan must build on)#

2.1 Registered source classes — 9 total (src/core/Utils.cpp::registerBuiltInTypes)#

Registry name Class / file Gate Role
source.npx.simdata SimulatedDataSource — modules/neuropixels/SimDataSource.* always NP1.0 procedural sim → data.npx.ap+.lfp
source.npx.sim2 SimulatedData2Source — modules/neuropixels/SimData2Source.* always NP2.0 procedural sim → data.npx.raw
source.npx.synthripples SynthRippleSource — modules/neuropixels/SynthRippleSource.* always HDF5 .h5 FILE PLAYBACK (the only file-driven source today)
source.npx.simadc SimOneBoxAdcSource — modules/neuropixels/SimOneBoxAdcSource.* always Simulated OneBox 12-ch ADC → data.npx.adc; composes with a sim probe source to make a hardware-free OneBox
source.intan.microzed IntanSource — modules/intan/IntanSource.* always Intan over the MicroZed Ethernet interface (#74). Registered and visible, and refuses to connect (the network layer is not built) — the deliberate failure path InvariantTests.md §6 relies on
source.npx.pxi NeuropixelsSource — modules/neuropixels/NpInterface.* #ifdef NPX_HW_ENABLED Real NPX 1.0/2.0 on a PXIe basestation (vendor NeuropixAPI)
source.npx.onebox OneBoxSource — modules/neuropixels/OneBoxSource.* #ifdef NPX_HW_ENABLED Real NPX 1.0/2.0 on a OneBox (USB): the same probe/IMRO machinery as PXI, plus the box's own data.npx.adc (+.adc.di) when the profile asks for it
source.nidaq.sim NiDaqSimSource — modules/nidaq/NiDaqSimSource.* always Simulated NI-DAQ → data.nidaq.raw(+.di)

source.npx.auto is not a class but an alias: SourceManager::setupSources (SourceManager.cpp) resolves it to .pxi or .onebox from a basestation scan (resolveAutoSource, BasestationScan.hpp) before the registry is consulted, and refuses when the scan is ambiguous. That is what the two visible hardware profiles (Neuropixels, PXIe with NI-DAQ) name — see SourceSelection.md.

2.2 The config explosion — 31 YAMLs as of 2026-09-02, still a cross-product#

Probe family {NP1 · NP2} × source realness {real · procedural-sim · file} × NI-DAQ {none · real · sim} × scenario {plain sine · ripples · ripple-detector-GUI · module-only} × delivery {baseline · ASAP}. When this was written 23 of the dozens of possible combinations were checked in; on 2026-09-02 it is 31 (36 until the five ASAP copies were deleted that day) — the OneBox rows, the ADC / digital-in variants, the latency benches and the Phase 1 entries arrived since — and they still differ by a few lines each. What Phase 1 changed is not the count but what the operator sees: the probe axis is discovered rather than declared, the basestation axis is resolved by source.npx.auto behind the Neuropixels / PXIe with NI-DAQ entries, the sims sit behind one Simulated Data… picker, and the per-combination hardware profiles are gui_hidden (CLI-only). The smells as of 2026-07-24, and where each stands: - Three configs share one sim_variant label ("Neuropixels 1.0 — Ripple Detection (GUI)") → the picker showed visually-identical entries. Still true of the files (SimNpx1RippleModule + the two SimNpx1Latency* benches), but the benches are gui_hidden, so only one reaches the picker. - Two sim configs (SimNpx1Ripples, SimNpx2Ripples) had no sim_variant → invisible to the GUI by accident. Now hidden on purpose (gui_hidden: true, with a comment saying why). - The real-hardware dropdown was hardcoded in HTML and omitted the OneBox and NiDaqOnly profiles (and the *Asap copies, since deleted on 2026-09-02), profiles. Gone — see §2.3; the comment in index.html now reads "Do not add profiles here".

2.3 One selection mechanism — but control flow still keys off name substrings#

  • Real and sim sources both come from the backend. listConfigs (WebSocketServer.cpp, the configList reply) returns every config name, the simVariants subset (name + sim_variant label + the optional basestation / probe cascade axes) and the guiHidden subset; main.js rebuildSourceOptions() builds the Source dropdown from it and showSimPicker() opens the cascaded sim picker. index.html #selectSource is a hidden state element holding a two-entry pre-connect fallback, not a list to edit — a new config/*.yaml appears with no frontend change (README.md, "Not a hotspot, despite appearances"). This is the one dynamic list §4.1 asked for, minus the capability tags.
  • "(play file)" in the name still switches the picker row to a file-path + Browse + ▶Play control (main.js renderSimScenario, the picker's last step) and makes selectSource route an .h5 path to SynthRippleSource (WebSocketServer.cpp).
  • Control flow keys off human-facing name substrings — "(play file)" (above), and "onebox" / "pxi" to word the not-in-this-build message (WebSocketServer.cpp). NetworkClient.js no longer gates the QWebChannel bind on "NPX". Fewer than in July, still fragile, and still the case for §4.3.

2.4 The contract + the three seams (already partly built)#

  • IDataSource (src/core/IDataSource.hpp): initDataSource/closeDataSource/startAcq/stopAcq + an IDataSourceWorker on its own QThread; register output buffers via getDataByName + addProducer; publish an IChannelMap to ChannelMapService. Multiple sources compose freely — sources: is a YAML sequence, each entry an independent producer (that's how NPX + NI-DAQ coexist in one profile).
  • (a) Arbitrary NPX sim — SimulatedDataSource and SimulatedData2Source are near-duplicates; SimSignalProfile/Sim2SignalProfile already externalize the signal knobs, but geometry (shank count, bank model, band layout) is hardcoded per class. IChannelMap/NpxChannelMap already encodes both NP1 (electrode = ch + 384·bank) and NP2 (electrode = shank·1280 + electrodeId) geometry — the seam exists.
  • (b) NeuroNexus/Intan — partly built (#74): src/modules/intan/ holds the MicroZed wire protocol (IntanProtocol.hpp), the packet decoder (IntanPacket.*, tested against synthesized packets) and an IntanSource that is registered, visible and refuses to connect because the socket layer and buffers do not exist yet. The NeuroNexus geometry (an IChannelMap) is still zero code, and the question that blocks the rest — a 256-channel buffer through the 384-stride BandFilterProcessor would scramble, not error — is recorded in IntanSource.hpp and IntanOpenQuestions.md. NIDAQSource remains the template for wrapping a vendor SDK behind a worker.
  • (c) File replay — already exists in embryo: SynthRippleSource plays an HDF5 .h5 into the same data.npx.* buffers a live probe writes (dataset data int16, 1-D broadcast or 2-D per-channel, attr sampling_rate), paced to wall-clock. Gaps: it reads .h5 but the recorder writes .bin + .bin.json (format mismatch); it's NPX-only (can't replay NI-DAQ); one static file. Status §19.1 already names the fix: "generalize SynthRippleSource to replay an arbitrary saved file, aligned with the recorder's on-disk format." The sidecar already stores data_name/record_format/sample_rate_hz, so binding the correct registered buffer generically is feasible.

2.5 The binding constraint (from SimDataLinux.md:177-203)#

The maintainer rejected a single polymorphic "hardware-agnostic" sim source in favor of one sim class per source module, with per-module flexibility for the scenario, not the hardware family. So: unifying the two NPX sims (same family) is consistent; a mega-source spanning NPX + NeuroNexus + NI-DAQ is not.

3. Design axes#

Axis Options
Config sprawl keep N full YAMLs · base + overlay/include layering · small canonical set + runtime params
Picker keep dual (HTML + sim_variant) · one dynamic capability-tagged list · descriptor-driven UI
Source identity match on human name substrings (today) · structured tags in config · a source-type descriptor registry
NPX sim keep 2 classes · unify into one geometry-parameterized NpxSimSource
File replay format keep .h5-only (SynthRippleSource) · read the recorder's .bin+.bin.json · support both
New hardware family (NeuroNexus/Intan) new modules/intan/ module (mirror NIDAQSource) — orthogonal, additive

4. Options#

4.1 Option A — Config consolidation + one dynamic picker (lowest effort, no source C++)#

Collapse the 23 YAMLs with a base + overlay loader (a profile include:s a base and overrides a few keys) or reduce to a canonical set + a couple of runtime parameters (probe, nidaq on/off, ASAP on/off, scenario). Replace the hardcoded HTML options and the sim_variant list with one backend-provided, capability -tagged list ({probe, realness, nidaq, scenario, delivery}) the UI groups/filters — killing the dual mechanism, the label collisions, and the invisible configs. - Delivers: goal 1 (fewer/organized options). Not 2/3/4. - Pros: minimal, no hardware-source risk, immediate UX win. Cons: needs a config-layering loader (Configuration.cpp) + a picker rewrite; leaves the sim-class duplication and file-replay/NeuroNexus untouched.

4.2 Option B — Unify the NPX sim + add a general FilePlaybackSource (medium; hits goals 2 & 4)#

  • Merge SimulatedDataSource + SimulatedData2Source → one NpxSimSource whose YAML profile carries geometry (shanks, electrodes/shank, bank model), band layout (ap+lfp split vs single raw + rates), and channel count — "simulate arbitrary NPX." Feed geometry into NpxChannelMap; the worker writes N bands of the configured width. Consistent with the §2.5 ruling (one class, one family).
  • Add FilePlaybackSource that reads the recorder's .bin+.bin.json set, rebuilds the exact CircularBuffer<dtype,aux> for each recorded band from the sidecar (data_name, record_format, sample_rate_hz), addProducers, and streams at rate — so any recording replays by hitting Play, NPX or NI-DAQ, display/detector/record unchanged. Generalizes SynthRippleSource (fold it in or keep .h5 as one reader behind the same source). Aligns with Status §19.1.
  • Delivers: goals 2 & 4 (and shrinks the config count as a side effect). Pros: directly on-target; reuses the proven producer/worker + IChannelMap seams. Cons: sim-source rewrite needs sim rebuild + A/B validation vs the current two classes; the .bin reader must mirror the recorder byte layout exactly.

4.3 Option C — Source-type descriptor model (largest; the clean long-term architecture)#

Introduce a formal source-type registry: each source kind registers a descriptor {kind: live|sim|file-replay, probeFamily, producesStreams, needsFile?, params-schema}. Configs reference a type + params instead of hand-wiring sources: by registry name; the picker is generated from descriptors (no HTML/sim_variant duality, no name-substring branching). New kinds (NeuroNexus/Intan, file-replay) just register a descriptor + module. - Delivers: goals 1–4 under one model; removes the fragile string-matching (§2.3). Pairs with NextTask_CommandEventBus.md — both replace ad-hoc string routing with a registry. Pros: the extensible end-state. Cons: biggest change — touches config schema, WebSocketServer selection, and the frontend picker; do it after the cheaper wins prove the shape.

4.4 Option D — NeuroNexus/Intan module (orthogonal + additive; goal 3)#

Independent of A/B/C: a new src/modules/intan/ with IntanSource : IDataSource (#ifdef INTAN_HW_ENABLED, wrapping the Intan RHX/RHD SDK, writing int16 into a new data.intan.raw), an IntanChannelMap : IChannelMap encoding the NeuroNexus geometry, and a simulated sibling (the AddingASourceModule.md standing rule). Mirrors the NIDAQSource SDK-wrapper pattern. Ships when the hardware arrives; cleanest atop Option C.

5. Recommended path (phased — pick per appetite)#

  1. Phase 1 = Option A. Immediate relief for "too many options" with no hardware-source risk: config layering + one capability-tagged picker. Fixes the dual mechanism, label collisions, and hidden configs.
  2. Phase 2 = Option B. Deliver the two concrete capabilities the maintainer named: one parameterized NpxSimSource (arbitrary NPX sim) + a FilePlaybackSource aligned to the recorder format (Play-to-restream). Validate in sim before trusting on hardware.
  3. Phase 3 = Option C (optional) if/when the name-substring routing or a new source family (NeuroNexus) makes the descriptor model pay for itself. Pairs naturally with the command/event bus.
  4. Option D (NeuroNexus/Intan) lands with the hardware, ideally on top of Phase 3.

Invariants for every phase: a replay/sim source must produce the same data.* streams a live source would (display/detector/record unchanged); align file replay to the recorder's .bin+.bin.json (don't invent a format); keep the SimDataLinux ruling (one sim class per hardware family); keep sources composable (NPX + NI-DAQ in one profile).

6. Open questions for the team#

  • Config layering vs canonical-set-plus-params for Phase 1 — which is less surprising to hand-edit? (The repo prizes YAML you can tweak + re-select without a rebuild.)
  • Fold SynthRippleSource into FilePlaybackSource, or keep it as the .h5 reader behind the same source? (.h5 playback + gen_synthetic_ripples.py are validated — don't regress them.)
  • How far to unify the NPX sim — geometry + bands from YAML, or keep NP1/NP2 as two thin subclasses over a shared core? (§2.5 permits either within the family.)
  • Descriptor model now or later — is the string-matching pain (§2.3) acute enough to justify Phase 3 before NeuroNexus, or defer until it lands?
  • Picker UX — group by probe family? by realness (live/sim/replay)? Expose ASAP as a per-profile toggle rather than separate configs? (Done: #80 made it a runtime request; the *Asap copies were deleted 2026-09-02.)
