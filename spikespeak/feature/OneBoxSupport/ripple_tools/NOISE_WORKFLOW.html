Baseline-noise workflow (record → metrics → figures → report + deck)#

Reusable pipeline built for the 2026-08-18 PXIe-vs-OneBox audit. It takes any set of SpikesPeak recordings ("cells"), characterizes their baseline noise, and produces presentation-grade dark figures, a self-contained HTML report, and an offline reveal.js deck.

Everything works from recordings only — no backend, no hardware.

TL;DR — analyze a new set#

python ripple_tools/run_noise_analysis.py --session RecordingTests/<session>

That needs exactly one hand-written file: RecordingTests/<session>/cells.json.

1. Record the cells#

Each cell is one condition = one recording directory. Keep the pipeline identical across cells (same config, same channels, same reference) so only the variable under test differs.

Drive the GUI (user watching) or headlessly:

python ripple_tools/record_baseline.py --source "NPX 2.0 Multishank" \
    --out RecordingTests/<session> --name <cell_name> --duration 60

Recordings land in RecordingTests/<session>/<cell_name>/<cell_name>_raw_<ts>.bin(+.json).

Safety: never force-kill the backend with a real probe attached — pause → disconnect → quit.

2. Describe the cells — RecordingTests/<session>/cells.json#

[
  {"dir": "RecordingTests/<session>/pxie_grounded",   "group": "PXIe",   "variant": "grounded"},
  {"dir": "RecordingTests/<session>/pxie_ungrounded", "group": "PXIe",   "variant": "ungrounded"},
  {"dir": "RecordingTests/<session>/onebox_grounded", "group": "OneBox", "variant": "grounded"}
]
  • group — the thing being compared (basestation, probe, rig). Each group gets its own color family.
  • variant — the condition within the group. A variant starting with un / no / off / without is treated as the "absence" case: hatched bars, de-emphasized line. (Careful: test the prefix, not a substring — "grounded" contains "un" as gr-UN-ded.)
  • Name the variant for what physically changed, not for what you assume it means. The 2026-08-18 study originally used "grounded"/"ungrounded"; both were wrong. What varied was where a wire from the bath terminated — SMA shell (= chassis/PC ground), Faraday cage, or nowhere — so the variants became chassis tie / cage tie / no tie. In IMEC's sense "grounding" the bath means wiring it to the probe's own REF/GND pads, which none of those conditions did.
  • Optional: "color": "#rrggbb", "key": "...", "label": "..." to override the defaults.

Paths are relative to the repo root. Cells may live in other session dirs — mixing is fine.

3. Run it#

python ripple_tools/run_noise_analysis.py --session RecordingTests/<session>            # everything
python ripple_tools/run_noise_analysis.py --session RecordingTests/<session> --scale 1.6 # bigger type
python ripple_tools/run_noise_analysis.py --session RecordingTests/<session> --figures-only

--scale sets figure font size: 1.0 on-screen, 1.35 default (large room), 1.6+ very large room.

Figures for a projected deck#

The multi-panel grids are for a report read on a monitor. Scaled into a 1280x800 slide they shrink to ~20% of their rendered size, which is unreadable in a room. For a deck, generate one metric per figure:

python ripple_tools/deck_figures.py --out RecordingTests/<session>/analysis --scale 2.1

That writes fig_slide_*.png (horizontal bars so cell names read normally, ~1.85:1 aspect to match the slide) and build_deck.py picks them up, giving each figure the full canvas.

Outputs to RecordingTests/<session>/analysis/:

file what
noise_metrics.json every metric per cell (the report + deck read this)
noise_table.md side-by-side markdown table
fig_metric_bars.png headline: wideband / AP-band RMS / noise floor (log)
fig_psd_grid.png one PSD panel per cell — per-channel (grey) + common-mode (color)
fig_comb_overlay.png common-mode overlay across cells in the line/comb region
fig_timeseries.png 250 ms common-mode snippet per cell
report.html self-contained, theme-aware report (figures embedded)
presentation.html self-contained dark reveal.js deck (reveal.js inlined → works offline)

4. Edit the narrative#

noise_compare.py is fully generic — it never needs editing for a new dataset.

The prose in build_report.py / build_deck.py is specific to a finding, so update the narrative sections for a new story. All numbers are pulled from noise_metrics.json, so they never go stale: use D['<cell_key>']['rms_ap_uv'] rather than typing a value. Cell keys are group_variant lowercased (e.g. pxie_grounded); noise_metrics.json["order"] lists them.

What gets measured#

Per channel and for the common-mode signal (mean across channels):

  • DC offset, wideband RMS
  • LFP-band RMS (1–300 Hz) and AP/spike-band RMS (300–5000 Hz, mains harmonics notched out)
  • Ripple-band RMS (150–250 Hz) — the SWR detection band, reported both raw and with the 60 Hz harmonics that fall inside it (180 / 240 Hz) removed, so you can see whether mains matters there
  • CAR residual — noise left after common-average referencing, in the AP and ripple bands, plus the % reduction. Shows how much noise is removable in software vs how much must be fixed in hardware. Reference = mean of the OTHER channels (excluding the channel itself, which with few channels would subtract part of its own signal and understate the residual). ⚠️ With N channels this adds the others' independent noise, inflating the residual by ~sqrt(1 + 1/(N-1)) for purely independent noise — +22% at N=3. So with few channels a CAR residual larger than the raw value means the noise is essentially independent (nothing for CAR to remove), not that CAR "hurts". Treat the CAR number as an upper bound until you record more channels.
  • Spectral noise floor — median PSD in 0.3–5 kHz with line harmonics removed → µV/√Hz (bandwidth-independent, the fairest "how quiet is it" number)
  • 60 Hz mains magnitude + prominence over the local floor
  • Interference comb — auto-detects the strongest sharp line in 45–520 Hz, gathers its harmonics, reports the fundamental and total comb RMS
  • Common-mode fraction and inter-channel correlation, in the wideband and AP band separately — the pair that distinguishes shared pickup (correlation → 1) from independent thermal noise (→ 0)

Spectra use a pure-NumPy Welch (Hann, 65k/131k segments, 50% overlap, per-segment detrend); scipy is not required.

Conventions & gotchas#

  • Raw probe band only. --band raw by default; an auxiliary band (e.g. the OneBox 12-channel adc analog input, which shares a recording) is never analyzed by accident.
  • µV scale. ADC→µV uses SpikesPeak's NP2 factor 1e6/84/4096 = 2.906 µV/bit (DisplayProcessor.cpp). Every ratio/correlation is scale-independent; treat absolute µV as the app's convention. For NP1.0 recordings the ap/lfp factors in spikespeak_postprocess.reader apply instead — pass the right band and adjust U if you extend this to NP1.
  • Figures are dark-only. They're PNGs, so they can't follow the viewer's theme; the report frames them as instrument panels and reads correctly in light mode too.
  • Deck is offline-safe. reveal.js is vendored in ripple_tools/vendor/ and inlined at build time, so the deck needs no network. It also avoids the opaque cross-origin "Uncaught Error: Script error." a CDN copy produces, and hash/history is enabled only over http(s) (on file:// history.replaceState throws a SecurityError).

Two traps this workflow has already hit#

  1. Testing clock-lock with integer periods only. Folding a record at integer sample periods cannot detect a lock at a rational ratio. The 2026-08-18 interferer sits at fs x 15/4096 — 4096 samples = 15 cycles — so integer folds (268-278) all washed out and produced a confident wrong answer. If you suspect a clock relationship, fold at candidate super-periods (N samples = k cycles) too.
  2. Frequency stability measured in units of the same clock. A signal locked to the acquisition clock is stable by construction when you measure it against that clock. Do not read low ppm spread as evidence of an external crystal source.

Verifying a surprising result#

The 2026-08-18 finding was counterintuitive, so it was checked by re-deriving the claims from the raw recordings with independent code (a Workflow fan-out of agents, each writing its own NumPy, none importing these tools). Worth repeating whenever a result would change how the rig is operated.
