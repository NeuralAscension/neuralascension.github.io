ESP32-S3-ETH — AM Systems 2300 pulse generator (Waveshare)#

An ESP32 alternative to the Raspberry Pi stim server, driving the AM Systems 2300 over its 3-line DB-9 control interface. It is a behavioural twin of raspberrypi_pulsegenerator/pulse_generator_am2300.c: same UDP port, same command grammar, same ACKs, same pulse-train maths. SpikesPeak needs no change to use it — point the Ripple dock's stim-server field at this board and everything (including the confirmed-fire red LED) behaves exactly as with the Pi.

Sketch: esp32s3eth_am2300_pulsegenerator.ino. Verified to compile for esp32:esp32:esp32s3 (arduino-cli 1.5.1, esp32 core 3.3.10, Ethernet 2.0.2) — 26% flash, 6% RAM.

Wiring#

ESP32-S3-ETH AM 2300 DB-9 Role
GPIO 15 pin 4 On/Off — HIGH = output on
GPIO 16 pin 8 Sign — HIGH = +phase, LOW = −phase
GPIO 17 pin 9 Pulse/Baseline — held HIGH = use the PULSE amplitude knob
GND pin 5 Ground — a common ground is required

Set the pulse amplitude on the 2300's front-panel PULSE knob; this firmware controls timing and polarity only, exactly like the Pi build.

Why not the old pin numbers#

esp32s3_pulsegenerator/ (the previous sketch, for a different board) used STIM_PIN = 13. On the ESP32-S3-ETH, GPIO13 is the W5500 SCLK — using it would fight the Ethernet bus. These pins are reserved on this board and must not be used for stim:

Reserved Pins
W5500 Ethernet MISO 12, MOSI 11, SCLK 13, CS 14, RST 9, INT 10
microSD CS 4, MOSI 6, MISO 5, SCK 7
WS2812 RGB LED 21
Internally occupied (Waveshare FAQ — PSRAM) 33–37
Boot straps / USB 0, 43, 44, 45, 46, and 19/20 (USB D−/D+)

GPIO 15/16/17 are in Waveshare's own usable-IO list and collide with none of the above.

Network#

Static 192.168.1.100:8888, matching the SpikesPeak StimulatorClient default. Change ip/gateway/ subnet at the top of the sketch if your rig differs. Only one device may hold that IP — power off the Pi (or any older ESP32) before using this board.

UDP protocol (identical to the Pi)#

Send Effect Reply
connect arm (replies even if already armed, so a re-connect refreshes the GUI) armed
quit disarm; aborts a running train disarmed
fire train with the current parameters fired (after the train)
fire <phase_us> <gap_us> <freq_hz> <total_ms> set all four, then fire fired
fire <phase_us> <freq_hz> <total_ms> set three (gap unchanged), then fire fired

A fire while disarmed is ignored — no pulse, no ACK. Defaults are 60 µs phase / 10 µs gap / 100 Hz / 500 ms, the same constants as the Pi.

total_pulses = total_ms × freq_hz / 1000, clamped to a minimum of 1 — so 1 Hz + 500 ms = exactly one biphasic pulse per detection, which is the setting SpikesPeak uses for the closed-loop ripple tests.

The fired ACK is sent after the train completes, entirely off the real-time pulse path, so it adds no per-edge jitter. It is addressed to the sender captured when the fire arrived, not to whoever spoke last.

Timing#

Edges are single-store writes to the ESP32-S3 GPIO_OUT_W1TS/W1TC registers (no digitalWrite() overhead) — the counterpart of the Pi build's direct-register path. Each pulse is emitted inside a FreeRTOS critical section so an interrupt cannot land mid-pulse; that is skipped automatically if a requested pulse would hold interrupts off for more than 2 ms.

Two deliberate departures from the Pi, both forced by running on an MCU rather than Linux:

  • the inter-pulse period sleeps off the bulk and spins only the last 2 ms (a pure spin would starve FreeRTOS and trip the task watchdog on long/slow trains); the next pulse still starts within microseconds;
  • there is no mlockall/SCHED_FIFO/isolcpus equivalent — the critical section plays that role.

Everything else — the phase/gap/polarity sequence, the train maths, the abort check placement — is line-for-line the same as the Pi source.

Build & flash — use flash.ps1#

.\flash.ps1              # erase + build + flash + run   (most robust)
.\flash.ps1 -NoErase     # quick app-only reflash
.\flash.ps1 -Erase       # erase ONLY -> chip rests in the ROM bootloader with a STABLE USB port

It polls every serial port and fires esptool at whichever appears, retrying until it wins, so an unstable or briefly-appearing port stops mattering. Build it manually if you prefer:

arduino-cli compile --fqbn "esp32:esp32:esp32s3:CDCOnBoot=cdc,USBMode=hwcdc" esp32s3eth_am2300_pulsegenerator

Use CDCOnBoot=cdc. The default (Disabled) sends Serial to UART0 instead of USB, so no COM port appears once the sketch runs — which looks exactly like a dead board.

Flashing gotchas that cost a full afternoon on 2026-07-20#

Trap What you see Fix
Arduino IDE open esptool: "port is busy" / Access denied Close the IDE entirely. Its serial-discovery daemon opens every port the instant it appears and wins the race. Two programs cannot hold one COM port.
COM number changes Flashing "works sometimes" The ROM bootloader and the running app enumerate as different USB devices, so Windows assigns them different COM numbers. Never hardcode a port — scan them all (flash.ps1 does).
App kills USB / short window Port appears <1 s, repeatedly Hold GPIO0 low (BOOT) through a power-cycle → ROM bootloader, no app, port persists indefinitely. GPIO0 is only sampled at reset, so it must be low before power/RST arrives.
Watchdog reboot loop Port appears ~1 s, over and over, forever A loop() that never yields starves the idle task → task WDT reboots every ~5 s → USB re-enumerates each time. This firmware disables the TWDT (see setup()); do not "fix" it by adding delay() — that costs latency (below).
PowerShell 2>&1 on esptool Script aborts on normal output esptool writes progress to stderr; PowerShell turns that into ErrorRecords. Don't redirect it; check $LASTEXITCODE.
Flashing only 0x10000 after a full erase Flash "succeeds", board never boots An erase removes the bootloader + partition table too. After an erase write the merged image at 0x0.

If the USB port is dead#

Brief-but-repeated enumeration with GPIO0 held low through a power-cycle means the fault is physical: in download mode the USB stack is pure ROM, so no firmware can cause or cure it. Confirm with a known-good data cable and a second board. A board with a damaged USB connector is still fully usable via UART0 (GPIO43 TX / GPIO44 RX / GND, GPIO0 low for download) with a USB-TTL adapter, which both flashes and monitors it. For a headless rig board that is arguably the better setup regardless.

Serial (115200) prints the link/IP on boot and one line per connect / fire / quit, mirroring the Pi's journal output — but prefer the status UDP command, which needs no USB at all.

Bench check before trusting it#

  1. Serial shows [ETH] IP 192.168.1.100 UDP :8888 and Device is DISARMED.
  2. python ripple_tools/pi_check.py is Pi-specific; for this board just send UDP by hand — connect must reply armed, and fire 60 10 1 500 must reply fired.
  3. Scope the 2300 output (or capture it on NI-DAQ ai4, as the Pi runs are verified): one biphasic pulse, 60 µs positive / 10 µs zero / 60 µs negative.
  4. quit must reply disarmed and leave On/Off LOW.

Untested on hardware as of 2026-07-20 — written, compile-verified, and diffed against the Pi source, but not yet run against a physical 2300. Do step 3 on a scope before any animal use.
