Neuropixels 2.0 Multishank on a OneBox#

Start to finish with the hardware that is on the rig right now: a Neuropixels 2.0 multishank probe on a Neuropixels OneBox (the USB basestation), including the OneBox's own 12-channel ADC.

Connect, set the probe map, watch the signal, record it, and shut down without costing yourself a power-cycle. For the toolbar reference see README.md; for the illustrated generic walkthrough see GUI-Guide.md; the 1.0-on-PXIe equivalent of this page is Neuropixels-1.0.md.

📷 Screenshots to be added — placeholders are marked 📷. A missing capture is a missing screenshot, not a missing feature.

What is different about a OneBox, in one paragraph. To SpikesPeak the probe is the same probe: the same channel map, the same live view, the same recorder, the same ripple detector. Two things change. It opens over USB 3 through an FTDI driver instead of a PXIe chassis, which is the only step that can fail in a OneBox-specific way; and it brings a 12-channel analog input of its own, which streams as an extra band beside the probe the way the NI-DAQ does on a PXIe rig. There is no NI-DAQ on this rig — the OneBox ADC is where a sync line or a stimulus monitor gets captured.

1. Before you start#

What must be connected#

Item Check
OneBox power Its own supply, plugged in and on. USB alone does not power it.
USB 3 cable To a USB 3 port on the SpikesPeak machine (blue port / SS mark). A USB 2 port enumerates the box and then starves the data stream.
Headstage cable From a OneBox probe port to the headstage. SpikesPeak finds the port itself — you do not tell it which one.
Probe Seated firmly in the headstage dock.
SDR breakout The imec NPOB_SDR_02 board on the SDR connector, if you want the ADC channels on BNCs (§7).
Reference / ground Wired as your prep requires, before the probe goes anywhere near saline or tissue.

The FTDI driver — one-time, and version-critical#

The OneBox is an FTDI FT601 USB-3 bridge. The Neuropixels API will not talk to it without the right D3XX driver, and it is fussy about which one:

  • Install FTD3XXDriver_WHQLCertified_1.3.0.10 (from ftdichip.com).
  • Do not install 1.4.0.x. The newest driver does not work with the OneBox. If it is already there, uninstall the device in Device Manager first, then install 1.3.0.10.
  • What you should see: with the OneBox powered and plugged in, Device Manager lists FT601 USB 3.0 Bridge Device under Universal Serial Bus controllers.

SpikesPeak checks the driver when you select a OneBox source and tells you in plain words if it is wrong. It never installs anything — driver installation is yours, and needs admin rights.

⚠️ The one rule that has a real cost attached#

Never force-kill the backend while the OneBox is connected. No Task Manager End task, no taskkill /F, and do not close the black console window with its ✕ while a box is open.

The FT601 USB handle is released only on a clean exit. Kill the process and the handle stays claimed: the next connect either fails to find the box or maps it and then delivers no data — and the only fix is to walk to the rig and physically power-cycle the OneBox (or press the back-panel RESET). Shut down the way §9 describes; it takes ten seconds.

Two more habits worth having:

  • Bring the rig up for a measurement, take it, bring it down. Do not leave it connected or streaming while you do something else. A probe streaming into nothing is a probe nobody is watching, and long idle streams have caused trouble on this rig before.
  • Do not change or apply a probe map while a recording is running.

2. Launch, and reach the GUI#

  1. Run run_spikespeak.bat (in the repo root). A console window opens with the log, and your default browser opens at http://localhost:8234. - Run the launcher, not bin/SpikesPeak.exe directly. The exe on its own exits with 0xC0000135 — it needs Qt, the Neuropixels API and HDF5 on PATH, which the launcher supplies. - If you would rather open the browser yourself, run run_spikespeak.bat --no-browser and browse to http://localhost:8234.
  2. What you should see: a toolbar with Source: None, a status box reading Ready, and a greyed-out ▶ Play button.
  3. Any browser works, and you can open the page on a second monitor. Closing the last browser tab quits the backend after a ~2-second grace, so a refresh is safe — but the deliberate shutdown order in §9 is the one to use with hardware attached.

3. Select the OneBox source#

  1. Open the Source dropdown and pick Neuropixels.

📷 Source dropdown

You name neither the basestation nor the probe. Neuropixels scans, finds the OneBox, opens it, and the probe identifies itself; everything that depends on which probe it is (which bands exist, whether the LFP has to be computed, what the ripple detector reads) follows from that answer. The 12-channel ADC streams alongside.

If a PXIe module is plugged into this machine as well, the scan is ambiguous, so the auto entry is withdrawn and the menu asks which basestation to use — pick OneBox there.

Until 2026-08-26 there were five OneBox entries, one per probe and per variant, and picking the wrong one silently gave you flat traces and an empty recording. Those, and the explicit OneBox / PXIe / PXIe + NI-DAQ overrides, still exist for reproducing old measurements and are still selectable by name from the control CLI — but they are no longer in the dropdown unless the scan is ambiguous. See §3a.

  1. What you should see, in this order (watch the status box on the left of the second row): - Connecting to Neuropixels… (the status line is built from the profile name, so it says Connecting to OneBox… only if you picked the explicit override) - green: Found Neuropixels 2.0 Multishank probe - green: Connected — device ready - the Probe Map and Live Data tabs appear, and a ▣ OneBox tab appears beside them - ▶ Play and Disconnect become enabled

📷 Connected — toolbar with the ▣ OneBox tab

The ▣ OneBox tab is the giveaway that you really are on the box and not on a PXIe profile: it only appears when the connected source can actually do OneBox things.

  1. The ADC does not announce itself. The probe gets a green line; the ADC gets nothing. You will know it came up when OneBox ADC (SDR) appears in a column's band dropdown once you press Play (§5). If it never appears, see §10.

  2. If the status box goes red, read it — the OneBox messages name the fix (power, driver, another program holding the box). §10 has them all.

3a. The variants that are no longer in the dropdown#

Three OneBox profiles remain available from the command line only, because they are measurement tools rather than everyday choices. Select them with the control CLI (select "<exact name>"):

Name What it is
NPX 2.0 Multishank (OneBox, no ADC) Probe only. The control profile for throughput measurements; the ADC band does not appear.
NPX 2.0 Multishank (OneBox + digital in) Adds the ADC's 12 comparator outputs as a separate logic-level band.
NPX 2.0 Multishank (OneBox, ASAP) · NPX 1.0 (OneBox, ASAP) Latency-benchmark variants — do not use for an experiment. Identical to the normal profile except the source polls the probe on every event-loop pass instead of every 1 ms, which costs about a whole CPU core of busy-spin. They exist so an ASAP-vs-default comparison differs by that one setting. See ../developer_docs/LatencyProfiling.md.

Taking them out of the dropdown is the point: they used to sit right beside the profile you wanted, and nothing stopped you picking one by accident.

4. The probe map — choosing which electrodes record#

A 60-second primer on the 2.0 multishank#

A Neuropixels 2.0 multishank probe has 4 shanks × 1280 electrodes = 5120 sites, and the probe reads out 384 channels total — shared across all four shanks. So a full map is a partition: every one of the 384 channels is routed to exactly one electrode, somewhere on some shank.

  • Each shank is divided into banks of 384 electrodes by depth: Bank 0 (deepest, at the tip), 1, 2, and Bank 3, which is a partial bank — only 128 electrodes.
  • The electrode → read-out-channel wiring is a block permutation, not identity. Electrode 100 on shank 0 is channel 196; electrode 200 is channel 248. You never have to compute this, but it is why a channel number and an electrode number disagree on screen, and why the ripple dock shows you both (e100 → ch196).
  • Unlike a 1.0, the 2.0 has no reserved reference channel — nothing is greyed out for that reason.

The editor enforces all of it. What you are doing is: choose 384 electrodes, apply them to the probe, then stream.

Editing the map#

  1. Click the Probe Map tab. The mode radio must be on Edit Map.
  2. All four shanks are drawn side by side, labeled 0, 1, 2, 3 left → right (matching the imec manual), each with its shaft and tip. Green = this electrode's channel is active and will stream; gray = available, not selected.

📷 NP2 4-shank map editor on the OneBox

  1. Choose electrodes, three ways: - Shank + Bank buttons — pick a shank in the Shank dropdown, then Bank 0 / 1 / 2 / 3. This fills all 384 channels from that one shank and bank. Fastest way to a valid map. - Click an electrode — routes that electrode's channel to that electrode. Use it to hand-tune. - Drag a vertical box on one shank — assigns that run of electrodes. Mixing shanks is the normal case: fill shank 0 bank 0, then drag a run on shank 2, and the channels move with you.
  2. Save .imro downloads the current map; Load .imro reads one back in. Loading only displays the map — it is not on the probe until you Apply.

Designing a complicated multishank map? Do it in a dedicated tool — neurocarto or similar — export a .imro, then Load .imro here and Apply. That is genuinely easier than any acquisition GUI's editor, this one included.

Tip referencing#

The Tip referencing checkbox under the map buttons flips every channel between the external reference (default, unchecked) and the probe tip. On a multishank probe each channel references its own shank's tip.

  • It is written to hardware immediately — there is no Apply step for it.
  • What you should see: Tip referencing enabled (referencing to probe tip) in green. If the write fails, the checkbox flips itself back and the status goes red, so the box always shows what the probe is actually doing.

Applying the map to the probe#

Click Apply Map to Hardware. SpikesPeak does the safe sequence for you: pause streaming if it is running → write the map → read it back and verify → resume streaming.

What you should see when it took:

  • green status: Applied updated probe map successfully
  • in Live Data, the traces re-order and re-label — they are sorted by depth (deepest at the bottom) and labeled by electrode, e.g. 100L, so a map change visibly moves them
  • the column depth readout in each header changes to the new electrode range (e.g. e383 ↕ e0)

Until you press Apply, the probe keeps its previous map. Edits live in the editor only. A green electrode is a request until Apply says otherwise.

5. The live view#

Press ▶ Play (status: Streaming started); the view switches itself to Live Data on the backend's confirmation.

  • The Play button tells you the state by color: green ▶ when paused ("press to play"), and a white ⏸ inside a green pulsing ring while streaming.

Columns, rows and density#

Control (toolbar) What it does
Columns / Rows How many strips, 1–4.
Horizontal ⬌ / Vertical ⬍ Horizontal = side-by-side columns (20 channels each by default) for a landscape monitor. Vertical = full-width stacked rows (40 each), for a portrait monitor.
Ch Channels per strip: Auto / 20 / 40 / 60 / 80 / 120.

| Window (sec) | Time width of the view: 1 / 2 / 5 / 10 s. |

Cost of density. Columns × Ch is what the browser draws. Since 2026-08-27 it is drawn by a hand-written WebGL2 renderer that holds a solid 60 fps across the whole range this GUI offers, 4 × 120 = 480 traces included (measured on this rig, OneBox + NP2.0). Frame rate is display smoothness only — acquisition, recording and ripple detection are unaffected either way.

Each strip also has a vertical slider (plus ▲/▼) to scroll through depth, and its header shows the depth readout — the deepest and shallowest thing currently on screen.

Per-column band selection#

Every column picks its own band from its own dropdown, so you can watch the probe and the ADC side by side. On this rig the choices are:

Band in the picker What it is
RAW Band The probe's real stream: 30 kHz, all 384 channels. A 2.0 probe has no hardware AP/LFP split — this is the only band that comes off the probe.
LFP Band Derived by SpikesPeak: 2nd-order Bessel low-pass at 400 Hz. This is where ripples live.
Spike Band Derived: 2nd-order Bessel band-pass, 300–6000 Hz.
OneBox ADC (SDR) The box's own 12 analog inputs (§7).

The two derived bands ship OFF and must be switched on. They filter all 384 channels in software, which costs real CPU, so nothing runs them until you ask. Use the Bands ▼ button in the second toolbar row: the menu lists LFP band and Spike band with an ON/OFF state each, and the button carries a count of how many are running.

📷 The Bands menu — LFP on, Spike off

  • Turning a band on makes it available; each column then selects it (or not) in its own dropdown. Turning it off removes it from those dropdowns, because a stream that has stopped arriving is not something you should be able to select.
  • Starting the ripple detector turns the LFP band on for you — it needs it, so it enables it and the button goes green because the backend did it, not because the GUI guessed.
  • Trying to turn the LFP band off while detection is running raises a blocking dialog that names both consequences; confirming stops detection first.

Scale, labels and the depth readout#

The scale box beside the band dropdown changes unit with the band — the unit label next to it is the caption; there is no control captioned Scale:

  • Probe bands (RAW / LFP / Spike) → µV: the peak-to-peak microvolts that fill one trace row. Smaller number = zoomed in.
  • OneBox ADC (SDR) → V/row: real volts per trace row. A 3.3 V logic pulse needs at least ~3.3 V/row to fit on screen.

Labels and the readout follow the same logic:

Band Trace labels Depth readout
Probe 100L — electrode + left/right column. Hover for shank / read-out channel. e383 ↕ e0 (shallowest ↕ deepest)
OneBox ADC IO0 … IO11 — named after the BNC on the breakout IO11 ↕ IO0

Click a trace label to select that channel, then use the scroll wheel over the chart to zoom just that one. Click again to deselect.

The control strip (changed 2026-08-25 — this is the current behavior)#

The per-column strip of controls (band, shank, L+R, scale, density) stays fully visible whenever it fits. It folds away to a small ▾ controls chip only when the column is genuinely too narrow — the row needs 448 px beside the depth readout.

On the 1920-px screen on this rig, in practice:

Layout Strip
1, 2 or 3 columns, ripple dock closed open
4 columns folded to the chip
3 columns with the ripple dock open folded — the dock costs about 380 px, which is enough to push three columns over the line
Vertical (rows), any number of rows always open — a stacked row is the full window width

When it is folded: hover the chip to peek at the controls, and click it — or press Ctrl+Shift+<n> for column n — to pin it open. There is also a ◉ pin button inside the revealed strip. The depth readout never hides, in either state: it is the only thing telling you which electrodes a column is showing.

6. Recording#

First: choose which channels to record#

The OneBox and Neuropixels profiles record ALL channels by default (they cannot know which few matter on your rig); the superseded NPX 2.0 Multishank (OneBox) profile ships with channels: [1, 192, 196] — deliberate, because a full 384-channel raw stream is a lot of disk. If you want more (or fewer), set it here before you record.

  1. Probe Map tab → switch the radio to Select Recording Channels. This works any time, before or during Play.
  2. Only the applied map's electrodes are shown: green = will record, blue = applied but not recording.
  3. Click an electrode to toggle it, or drag a vertical box to add a run. Record all and Unselect all are the bulk buttons.
  4. Press Set recording channels to commit. What you should see: the status line under the buttons confirms the count.

The OneBox ADC is not affected by this picker, on purpose. It always records the 12 channels its profile configures. A probe read-out index means nothing to an analog input, and on a OneBox rig the ADC band is where your stim monitor and sync line are captured — silently dropping it would make the recording unanalysable. There is no ADC channel grid in the GUI; to change what the ADC records, edit the profile's channels: list (see ../developer_docs/ConfigReference.md).

Then: record#

Recording is a deliberate two-step, so you never start writing by surprise.

  1. Make sure you are playing — Record is disabled when paused.
  2. Press ● Record. A dialog asks for a recording name (animal / id) and an output directory on the SpikesPeak machine — Browse… opens a folder picker on that machine. Click Set Location. What you should see: a muted-red ring on the Record button (armed), and a status line Armed — click ● Record to start "<name>" → <dir>/<name>/. Nothing is on disk yet.
  3. Press ● Record again to START. What you should see: the Record button goes solid red, and a ● REC → name badge appears beside the status (the dot blinks; the name does not, so you can read it). Hover the badge for the full path.
  4. Press ● Record again to STOP. Files close. Streaming keeps going — only ⏸ Pause stops the stream. You can start a new recording without pausing; it gets its own folder and timestamp.

What appears on disk#

Everything for one recording lands in <directory>/<name>/:

📷 The recording folder — raw + adc + sidecars + log

File What it is
<name>_raw_<timestamp>.bin The probe band.
<name>_raw_<timestamp>.bin.json Its sidecar (below).
<name>_adc_<timestamp>.bin The OneBox ADC, 12 channels.
<name>_adc_<timestamp>.bin.json Its sidecar.
<name>_<timestamp>.log A copy of the backend log for the life of this recording — what the rig was doing when the file was written.

All the files in one recording share one timestamp, so a set always groups.

What the sidecar tells you#

Each .bin is self-describing. Open the .json in any text editor:

  • band — raw or adc; sample_rate_hz — 30000 for the probe, 30300 for the ADC.
  • channels — the list actually written, in file column order. For the probe these are electrode numbers as shown on screen; for the ADC they are ADC channel numbers (IOn).
  • num_channels — how many payload channels. This is not the frame stride.
  • frame — the part that saves you: header (uint32 timestamp, uint16 sync), header_bytes (6), payload_dtype (int16), payload_channels, total bytes, and a literal layout string [uint32 timestamp][uint16 sync][int16 x num_channels]. Read num_channels as the stride and every sample de-interleaves wrong — that mistake once produced "anomalous" ADC statistics that were investigated as a hardware fault. Use frame.bytes.
  • units — adc_int16 for both bands: the file holds raw counts, not volts. For the OneBox ADC at the ±5 V range the device reports one count = 0.000152588 V, i.e. 6553.6 counts per volt — divide by that offline. (The live view already does this for you, which is why it can show real volts.) If you change the ADC range, the conversion changes with it.

To load a recording in Python, use python/spikespeak_postprocess — see ../python/README.md. If the ripple detector had detection channels when you pressed Record, you also get a <name>_ripple.json carrying the online thresholds and the resolved detection channels — from the GUI Record button and from the control CLI (CommandLineControl.md) alike; both go through the same recorder. It lands in <dir>/, beside the <dir>/<name>/ recording folder, so archive the parent directory.

7. The OneBox ADC band#

What it is for. Twelve analog inputs, ~30.3 kHz, sampled by the same box as the probe. It is the OneBox's answer to the NI-DAQ AI/O stream on a PXIe rig, and on this rig there is no NI-DAQ — so this is where you capture:

  • a stimulus monitor (the stimulator's own trigger or monitor output, fed back in, so the pulse is in the recording),
  • a sync line from another instrument, so two systems can be aligned offline,
  • any behavior / TTL signal you want on the same clock as the neural data.

Because the ADC and the probe are two streams from one device, they need no cross-device sync alignment — which is the single biggest reason to prefer it over a second acquisition card.

Which connector is which channel#

SpikesPeak numbers the twelve channels 0–11 and labels the traces IO0 … IO11, after the BNCs on the imec NPOB_SDR_02 breakout that plugs into the SDR connector. imec's documentation describes ADC0 as the standalone "ADC" SMA connector on the box and ADC1–11 as reaching the breakout.

On this rig the wiring is:

Line Patched to
IO0 The WavePlayer / DAC0 output — this is an output, not a free input. Do not drive anything into it.
IO2 The Raspberry Pi stimulator's trigger pin — so the stim pulse is captured in the recording.
IO6 → IO4 A loopback, for checking the ADC path with a known signal.
IO9 A cable from the OneBox SMA, which makes the SMA signal readable as an ADC channel.

Be honest with yourself about the mapping before you trust it. The channel-to-connector correspondence has not been verified end-to-end on this rig — with nothing patched in, all twelve channels sit at a common mid-scale level (measured ~1.37 V on 2026-08-21, ~1.7 V on 2026-08-24) and several behave oddly, and that is recorded as an open question, not a known-good setup (../SpikesPeak_Status.md §51.5). Before you rely on a channel number, patch a known signal in (a 1 Hz, 1 V sine, or the IO6 → IO4 loopback) and confirm the amplitude, the frequency, and which trace it lands on.

The ▣ OneBox panel#

Click the ▣ OneBox tab. The panel is draggable by its header (it will otherwise sit over the trace you opened it to look at).

📷 The ▣ OneBox panel

  • Input voltage range — ±2.5 V, ±5 V (default) or ±10 V. Changing it changes what one count is worth; the backend re-reads the true volts-per-count from the device and republishes it, so the live view keeps reading correct volts at every range. What you should see: the status line in the panel confirms ADC range set to ±N V — live view rescaled…. Pick the smallest range your signal fits in.
  • Digital input (comparator thresholds) — each ADC line also feeds a comparator that produces one logic bit. It is a Schmitt trigger, so it takes two voltages: the bit falls to 0 below the low threshold and rises to 1 above the high one, and holds its state between them. Pick the IO channel, set the two voltages, press Apply. Read device shows what the box actually stored (slightly different from what you typed — it quantizes against an internal reference), and the bit row shows the live 12-bit state, IO11…IO0. These persist in the device across sessions, so a previous run that narrowed a window leaves it narrowed for whoever connects next — press Reset all to put all twelve back to the boot pair 0.800 / 2.000 V before you trust them. This section is what feeds the adc_di band used by the (OneBox + digital in) profile in §3a, and it appears only on a real OneBox: a simulated one has no comparators.
  • Ground unused inputs — a grid of IO0…IO11. An unconnected input floats at a mid-scale voltage — the panel's own note says ~1.7 V — and picks up whatever is switching next to it (measured: IO1 and IO3 rose from 0.0001 to 0.019 / 0.064 V sd while the DAC played). Clicking a channel here holds it at 0 V instead, and the button goes green only when the backend confirms it. Only do this for a BNC with nothing plugged into it — driving a line something else is also driving is contention, not grounding. IO0 is disabled: it is the WavePlayer output.
  • Analog output (WavePlayer → DAC0 / BNC IO0) — Pulse width, Gap, Pulses, Amplitude, Playback rate, a Repeat tick-box, and Load / Arm / ⚡ Fire / Stop. This drives another instrument's trigger input, so it emits positive pulses, not a biphasic stimulus waveform. Amplitude is calibrated at 6553.6 codes/V (confirmed twice by measurement).
  • Checking the shape on a scope? Tick Repeat before Arm — a single 60 µs pulse fired once is invisible on a free-running scope.
  • The ADC cannot verify this output. At 30.3 kHz one ADC sample is 33 µs, and the WavePlayer's resolution at 100 kHz is 10 µs. Use an oscilloscope to check pulse width.
  • The output really is on DAC0 → breakout BNC IO0, not the back-panel SMA, whatever the vendor documentation for arming implies. That was measured, and arming provably does not disturb the sync line.

8. Ripple detection and closed-loop stimulation#

This works on the OneBox exactly as it does on PXIe, and it has the same operating manual: RippleDetection.md — read that one for picking channels, thresholds, quorum, training, and live z-tuning. Only the OneBox-specific parts are here.

  • The OneBox profile gets the detector and the derived LFP band automatically, provisioned from the probe that connects rather than declared in the file. Both are inert until you start them from the GUI — carrying them costs nothing when unused.
  • Open the dock with ◉ Ripple Detection in the second toolbar row (the same row that carries Bands ▼ and the ▣ OneBox tab). Opening it takes about 380 px off the live view, which is what folds a three-column control strip (§5).
  • A 2.0 probe has no hardware LFP band, so the detector reads the derived one. Pressing ▶ Start enables it for you; you do not have to remember.
  • Stimulation is opt-in, twice. The dock's enable stimulation master switch is off by default (off = detection only; no datagram can leave this host), and the stim server must be armed. A detection transmits nothing until both are true. The red STIM LED lights only on a confirmed fire, not on detection.
  • Trigger dropdown — where a detection goes: | Option | Path | |---|---| | Pi → AM 2300 | The validated UDP → Raspberry Pi → AM Systems 2300 path. The Pi drives a constant-current stimulator; amplitude is set on the instrument, not in the GUI. | | OneBox DAC0 (IO0) | The box's own WavePlayer, out of breakout BNC IO0. No network hop. Amplitude in volts, here. | | both (for an A/B) | Fires both from the same threshold crossing — a paired comparison, not two runs matched afterwards. |
  • Latency, measured on this rig: the closed loop runs at 0.55 ms on NP2.0 over the OneBox with ASAP delivery (0.92 ms on NP1.0) — see ../RecordingTests/CLOSED_LOOP_LATENCY.md. The OneBox-DAC-versus-Pi comparison has not been measured yet; do not assume one is faster.

Algorithm and data path: ../developer_docs/RippleDetection.md. Stim server setup: ../raspberrypi_pulsegenerator/README.md.

9. Shutting down properly#

This is the step with a real cost attached. Do it in this order every time.

  1. Stop the recording, if one is running — press ● Record so the button stops being solid red and the ● REC badge disappears. Files are closed only when you do this.
  2. Pause the ripple module, if it is running — ⏸ Pause in the dock, so nothing can fire during teardown.
  3. ⏸ Pause the stream on the toolbar. What you should see: the Play button returns to a green ▶, status Streaming paused.
  4. Disconnect. What you should see: status Source disconnected, Source back to None, the Probe Map / Live Data / ▣ OneBox tabs disappear, Play greys out. Behind that one click the backend stops the WavePlayer, puts the SMA back to input, closes the probe, closes the basestation and releases the OneBox's virtual slot — that release is what lets the next connect succeed.
  5. Quit the backend. Either close the browser tab (the backend exits about 2 seconds after the last client disconnects) or type quit at the backend console. The console window closes on its own.
  6. Confirm nothing is left running — no SpikesPeak.exe in Task Manager, and no stray browser tab holding a WebSocket open.

Never shortcut this with End task, taskkill /F, or the console window's ✕ while the box is connected. See §1 for what that costs.

If you see this message on the way out — The OneBox stopped responding while the connection was being closed… power-cycle it (or press the back-panel RESET) before connecting again. — then the box wedged during teardown. The app still exits cleanly, but the box is in an unknown state: power-cycle it before the next connect. SpikesPeak bounds every teardown call for exactly this reason, so a wedged box no longer hangs shutdown.

10. Troubleshooting#

What you see What it means / what to do
No Neuropixels OneBox was detected over USB The box is off, the USB cable is out or in a USB 2 port, or the FTDI driver is missing. Check Device Manager for FT601 USB 3.0 Bridge Device, then reconnect.
The installed FTDI driver (1.4.x) is not compatible with the OneBox… Exactly what it says. Uninstall it in Device Manager and install D3XX 1.3.0.10 (§1).
A OneBox was found but could not be mapped to a slot Press Disconnect, reconnect. If it persists, power-cycle the OneBox.
A OneBox was detected but could not be opened. Check that it is not in use by another program Another acquisition program (Open Ephys, SpikeGLX) has the box — close it. Or a previous SpikesPeak was force-killed and never released the USB handle: power-cycle the box.
A Neuropixels basestation was found, but no headstage was detected on any port The headstage cable. Re-seat both ends and reconnect.
Headstage found, but no Neuropixels probe was detected The probe is not firmly seated in the headstage dock.
Connect succeeds, Play works, the clock runs — but no traces and no data The known OneBox fault where the box accepts everything and then delivers zero packets. SpikesPeak's watchdog reports it within a few seconds; teardown may also stall. Power-cycle the OneBox and reconnect. If it repeats, say so — it is tracked as issue #59, which is closed as recovered and mitigated rather than fixed: the fault is on the vendor side, not in SpikesPeak's code, and SpikesPeak's watchdog is the mitigation.
A dialog appears that will not close, offering only Restart SpikesPeak or Close SpikesPeak Two hardware connects have failed in this process, and the third acquisition crashes the backend with no teardown — the one outcome the safety rules exist to prevent. So SpikesPeak stops the session first, on purpose: there is no ✕, no Escape, no clicking past it. Press Restart SpikesPeak (a fresh process clears the condition), then fix what made the connects fail before trying again. Detail: ../developer_docs/HardwareFaultGuard.md.
▶ Play is greyed out No source connected, or the probe is not ready yet. Watch the status box.
● Record is greyed out You have to be playing first.
Only 3 channels in the recording That is the default of the superseded NPX 2.0 Multishank (OneBox) profile only. On Neuropixels / OneBox it means the GUI record-channel selection was narrowed: Probe Map → Select Recording Channels → Record all → Set recording channels before you record (§6).
OneBox ADC (SDR) is not in the band dropdown You selected (OneBox, no ADC), or the ADC failed to enable. Check the backend console / output.log (in the backend's working directory).
ADC traces are flat, or all sit at the same mid-scale voltage Nothing is patched into those BNCs. A floating input does not idle at 0 V — it sits somewhere around 1.4–1.7 V on this rig and picks up crosstalk. Use ▣ OneBox → Ground unused inputs for the BNCs with nothing plugged in, and never for one that is connected.
The WavePlayer fires but nothing appears on the scope You are on the wrong connector: the output is DAC0 → breakout BNC IO0, not the SMA. And a single 60 µs shot is invisible on a free-running scope — tick Repeat before Arm.
A column's controls have collapsed to a ▾ controls chip The column is narrower than 448 px. Hover to peek, click or Ctrl+Shift+<n> to pin — or use fewer columns, close the ripple dock, or switch to Vertical ⬍, where the strips are always open.
LFP Band / Spike Band are missing from a column's dropdown They are derived bands and ship off. Turn them on in Bands ▼.
The live view does not match the map you just drew You did not press Apply Map to Hardware. Edits stay in the editor until you do.
You switched profiles and the data looks like the old one Known: a source switch after the first one can silently fail to take effect, and the resulting files look perfectly normal. Disconnect first, then select the new profile, and confirm the bands you expect are actually present before you record anything you care about.
The app exits immediately with 0xC0000135 You ran bin/SpikesPeak.exe directly. Use run_spikespeak.bat.
http://localhost:8234 shows nothing The backend is not running, or it auto-quit ~2 s after the last browser tab closed. Relaunch.
Anything red in the status box Hover it for the full message and time, then read the backend console — output.log in the backend's working directory carries the underlying error.
