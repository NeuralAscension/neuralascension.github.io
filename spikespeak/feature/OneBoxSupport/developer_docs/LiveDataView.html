SpikesPeak — Live Data View (waveform display)#

How the streaming waveform view works: the data plane, the depth / shank / electrode-column model, the per-column filters, and the orientation. Read this before touching ChartColumn.js, DataStore.js, NetworkClient.js, or the live-view glue in main.js / ImroManager.js.

Sibling docs: probe-map editor + IMRO is in [../SpikesPeak_Status.md]; the whole-system picture (hosting, threading, QWebChannel) is in [SpikesPeak_Architecture_Review.md].

1. Data plane (how a sample reaches a trace)#

C++ DisplayProcessor ─► WebSocket :1234 (binary) ─► NetworkClient.handleMessage()
   per-pixel min/max decimation                         │  parses [streamId][nPts][ts, (min,max)*nCh]...
                                                         ▼
                              DataStore.streams[streamId] = [ channel0, channel1, … channel383 ]
                                                         │   each channel = { yOffset, yOffsetInterleaved,
                                                         │                    zoom, color } — DISPLAY STATE
                                                         │                    ONLY, no sample buffer
                                                         ▼   bake y, hand the batch straight on
                              ChartColumn(s).gl — a GlColumnRenderer (WebGL2) per column;
                              `appendRow(row, xs, ys, n)` for every column showing that channel.
                              The renderer's buffer is the ONLY copy of the samples.
  • The browser receives decimated data (min+max per timebin), not the raw 30 kHz — volumes are modest. NetworkClient bakes a channel's batch once into reusable scratch arrays, then calls appendRow() once per column that is showing that channel.
  • The samples are stored once, by the renderer. DataStore used to hold a pair of chart-library FIFOs per channel that the renderer read back out; it holds no sample buffer at all now, only the per-channel display state the renderer needs before the first sample arrives. Feeding the renderer from anywhere other than that one point in NetworkClient means re-deriving the offset and the scale — see RendererContract.md.
  • THE key constraint: the vertical position (yOffset) is baked into the data values (y = channel.yOffset + value*zoom) before the renderer ever sees them, and every column showing that channel is handed the same baked array ⇒ a channel sits at one vertical position per baking. Because the L+R view needs a different ordering than L/R (interleaved vs packed — §5), each batch is baked twice, once per ordering: js yPacked[o] = channel.yOffset + value*zoom; // L / R / non-probe columns yInterleaved[o] = channel.yOffsetInterleaved + value*zoom; // L+R columns NetworkClient bakes only the ordering the visible columns actually need (default B ⇒ interleaved only), per dataStore.appendPacked / appendInterleaved set by AppController.updateAppendModes(). Two fixed orderings is the ceiling — arbitrary per-column positioning would still need per-column data (§5).

2. Probe geometry (NP1 and NP2)#

Electrodes form 2 columns with rows of increasing depth:

electrodes shanks within-shank index e column row (depth)
NP1 960 1 e = channel + 384*bank e & 1 (even=L, odd=R) e >> 1 (0…479)
NP2 1280 / shank 4 e = electrodeId (shank from map) e & 1 e >> 1 (0…639)
  • Row 0 is the TIP (deepest in the brain). Higher electrode number ⇒ shallower, up the shank.
  • Electrodes 2k (left) and 2k+1 (right) share row k = the same depth.

3. The depth / shank / column model#

Computed in ImroManager.js → recomputeDepthOrdering() from the applied map, re-run on every map apply. Every active read-out channel gets a global slot:

slot = rank of the channel when ALL channels are sorted by  (shank ASC, column ASC [L before R], row ASC [deep first])

main.js → relayoutByDepth() then sets channel.yOffset = slot * spacing and clears the (now-stale) data. Because the y-axis is normal (min at the bottom), slot 0 = the tip sits at the bottom.

Bands#

A contiguous run of slots for one (shank, column) selection. Since L precedes R within a shank, a shank's "both" band is just their union — also contiguous:

NP1 slots:  [ shank0 Left  by row ][ shank0 Right by row ]
            └──── band "0-L" ─────┘└──── band "0-R" ─────┘
            └──────────────── band "0-B" (both) ─────────┘
NP2 slots:  [s0L][s0R][s1L][s1R][s2L][s2R][s3L][s3R]   (each by row)

A column showing L or R just zooms its y-axis to that band's slot range — packed, depth-sorted, no gaps.

Interleaved ordering (the L+R view)#

L+R reads by electrode number (0L, 1R, 2L, 3R, …), not L-block-then-R-block. That's a second ordering, (shank ASC, row ASC, col ASC) → slotI + per-shank band bandI(shank) (each shank's run is contiguous, so its whole-shank band is that run). A single baked offset can't be both interleaved and packed, so the L+R view is fed the interleaved baking (positioned by slotI); L/R are fed the packed one. relayoutByDepth sets both offsets (yOffset = slot·spacing, yOffsetInterleaved = slotI·spacing). When an active electrode's L/R partner is absent (custom map), interleaved order just shows consecutive same-side electrodes (e.g. 50L, 52L) — still strictly electrode-ascending.

Reserved channel (NP1 ch 191 → REF)#

The NP1 reserved internal-reference channel (191) is not a recording electrode. The probe-map editor never re-banks it, so it stays on bank 0 (electrode 191); left to float by depth it sorts to the deepest slot on any non-bank-0 map (it becomes the smallest active electrode) and confusingly lands at the bottom-right. Instead recomputeDepthOrdering pins reserved channels (NP1_RESERVED_CHANNELS) to the shallow (top) end of their column via a sentinel sort row (REF_ROW = 1e6), and ChartColumn labels the trace REF (imroLiveView.isRef). The reference trace stays visible at a fixed, marked spot (right column, since electrode 191 is odd; absent from the Left view). NP2 has no equivalent here.

window.imroLiveView API (the contract between ImroManager and the live view)#

method returns
hasOrdering() true once an NP1/NP2 applied map exists
kind() 'NP1' | 'NP2' | null
shanks() sorted shank indices present, e.g. [0] or [0,1,2,3]
slotOf(channelId) / channelAtSlot(slot) packed slot ↔ channel (L/R views)
slotIOf(channelId) / channelAtSlotI(slot) interleaved slot ↔ channel (the L+R view)
electrodeOf(channelId) within-shank electrode index
shankOf(channelId) / colOf(channelId) shank / 0=L 1=R
isRef(channelId) true for a reserved internal-reference channel (NP1 ch 191) — pinned + labeled REF
band(shank, colKey) packed {start, count}; colKey ∈ {'L','R','B'}
bandI(shank) interleaved {start, count} for a shank (the L+R band)
total() active channel count (384)

4. ChartColumn — per-column filters + drawing#

Each display column (ChartColumn) owns: - Two header dropdowns — shankSelector (one entry per shank; disabled for single-shank NP1) and colSelector (L+R / Left / Right). refreshFilterOptions() populates them from imroLiveView and is called on map apply (relayoutByDepth) and column (re)build (buildColumns). Both are hidden for non-probe sources (audio/NIDAQ) — those fall back to channel order + labels. - this.bottomSlot — the lowest (deepest) visible slot; the vertical slider scrolls it within the band. Slider rail is labeled shallow (top) / deep (bottom). - draw() — picks the column's mode: L+R ⇒ interleaved ordering (seriesField = 'dataSeriesInterleaved'); L/R ⇒ packed ordering ('dataSeries'); non-probe ⇒ channel order. seriesField names the baking the column wants, not an object hanging off the channel — NetworkClient reads it (via col.glUsesInterleaved) to decide which of the two y arrays to hand this column. Then clamps bottomSlot, sets a normal y-axis range, and rebuilds glChanToRow — read-out channel → renderer row, -1 for "this row shows nothing" — top-first, so each on-screen slot is labeled <electrode><L|R> (e.g. 100L), or REF for a pinned reserved channel; hover shows detail. Changing colSelector calls window.onLiveFilterChange so the needed baking starts being produced. Selection + wheel-zoom still key off the read-out channel.

Orientation summary: deep (tip) at the bottom, shallow at the top; electrode labels increase upward. A previous build used an inverted y-axis range; this view uses an explicit normal range instead — if depth ever appears upside-down, flip the range/slot sign in draw()/relayoutByDepth().

The control strip: one row if it fits, otherwise collapse#

The band above each chart — stream selector, Shank, L+R, the µV scale, the density count — has exactly one authored shape: one row. Five fixed slots, 108 + 80 + 64 + 84 + 80 = 416px, plus four 4px gaps, 7px of padding a side and a 1px border = 448px. It folds behind its ▾ controls chip if and only if those 448px do not fit beside the depth readout:

// ChartColumn.fitStrips()
avail    = columnHeader.clientWidth - depthReadout.offsetWidth - 24;   // depthReadout = .page-info
collapse = band.scrollWidth > avail;                                   // band.scrollWidth === 448

Column count and orientation are not inputs to that decision. Header height is 46px expanded, ~36px collapsed.

The rule until 2026-08-25 was (!vertical && nCols > 2) || doesNotFit, and it was wrong in both directions — measured on a 1920×1080 monitor:

  • 3 columns, ripple dock shut — one row needs 448px and 477px was free, so it fits. The count clause collapsed it anyway and every control vanished behind the chip.
  • 2 columns in a 1080px window — a @container tier had already dropped the band to its two-row shape, so the fit test measured that (274px), found it fitting in 377px, and never collapsed. The result was a two-row strip: the one shape nobody wants.

The second fault is why the band now has a single authored shape. The thing being measured must not depend on the measurement's own answer. The twelve @container tiers that used to pick between a 3-row, a 2-row and a 1-row band per column count (thresholds 622 / 1239 / 1856 / 2473px of #main-container width, header heights 124 / 102 / 74 / 46px) are deleted. Do not reintroduce a shape tier in toolbar.css.

The decision is made once per row and applied to every column — ChartColumn.fitStrips() is static for two reasons, both of them faults that were already paid for:

  1. .column-container is flex: 1 1 0 and Chrome distributes the flex remainder in 1/64px LayoutUnits while clientWidth rounds to an integer, so two siblings at 601.98 and 602.02 report 601 and 602 and can land on opposite sides of the threshold. One column collapsed and its neighbour not is two header heights in one row, and traces starting at different Y — the exact thing the fixed-slot header exists to prevent.
  2. The measurement drops strip-collapsed to read the in-flow width. Once per column that is N class flips per frame, each one a size change the chart-area ResizeObserver picks up, which calls straight back in. It took the page down during development. Once per row it is one flip, and the observers see one settled answer.

A hidden view is not a narrow one: selecting the Probe Map tab sets #view-data to display:none, the observer then fires at 0×0 and avail goes negative. fitStrips() bails on avail <= 0 and keeps the last decision, rather than expanding every strip while nobody is looking and painting a 448px band into a 378px column on the way back.

The collapsed reveal overlay keeps the old narrow 3-row template, deliberately. It is position: absolute, so its rows cost neither header height nor trace height — and #view-data is overflow: hidden, which clips an absolutely-positioned descendant. A 448px overlay in a column too narrow to hold one would have its right-hand controls destroyed on the last column: 275px worth at 1080px with the ripple dock open and four columns.

Measured after the change (1920×1080 monitor, NPX 2.0 sim):

layout column width strip header
horizontal, 1 col, dock shut 1894px one row 46px
horizontal, 2 col, dock shut 945px one row 46px
horizontal, 3 col, dock shut 628px one row 46px (collapsed before)
horizontal, 4 col, dock shut 470px collapsed 36px
horizontal, 2 col, dock open 763px one row 46px
horizontal, 3 col, dock open 507px collapsed 36px
horizontal, 4 col, dock open 379px collapsed 36px
vertical, every column count ~1530–1894px one row 46px

Vertical never collapses because a stacked row is 1530–1894px wide and 448px always fits — the old orientation exemption is now a consequence of the rule, not a special case. Sweeping window width at 2 columns: one row at 1920 / 1600 / 1400 / 1300 / 1280, collapsed at 1200 / 1150 / 1100 / 1080 (at 1200 one row needs 448px and only 437px is available).

tests/gui/layout_matrix.py asserts the rule in its own operands — collapsed must equal not (oneRowNeed <= avail), both read from live layout — plus uniformity: every column in a row must report the same header height and the same collapse state. The old shared-container-query design guaranteed uniformity structurally; a measurement does not, so it is asserted. The one-line and header-height invariants (stripH <= 40, headerH <= 52) used to sit behind an if vertical: gate, which is precisely why a two-row horizontal strip ran green for months; they now run on both axes for every column that is not collapsed.

5. Design notes (the baked-offset constraint)#

The yOffset is baked into the samples (§1), so each distinct vertical ordering needs its own baking:

  1. L+R interleaved vs L/R packed put the same channel at different positions ⇒ two bakings of every batch (packed, interleaved). To keep cost down, NetworkClient bakes only the ordering in active use (updateAppendModes() from the columns' filters; default B ⇒ interleaved only, so it's ~1× baking in the common cases). Because the offset is baked in, the samples a column already holds belong to the layout that was in force when they arrived — which is why GlColumnRenderer.setLayout() drops them when the row count or the capacity changes, and why relayoutByDepth() does the same.
  2. No "all shanks" option. Each column picks one shank (all-shanks + a single L/R column is non-contiguous in slot space). View all four NP2 shanks with four columns.
  3. A third ordering (e.g. arbitrary per-column packing) would still need a per-column baking of every batch (bake ~Ncolumns× instead of ~1×), or a renderer that positions a row itself rather than taking the offset baked in — a bigger cost than the current two fixed orderings.

6. Lifecycle — backend quits with the browser#

src/core/WebSocketServer.cpp/.hpp: a single-shot grace timer (2 s). When the last client disconnects the timer starts; a new/again connection (onNewConnection) cancels it; on timeout it calls QCoreApplication::quit(). Net effect: closing the browser quits SpikesPeak.exe, but a page refresh (disconnect→reconnect within 2 s) does not. If no browser ever connects, nothing schedules a quit. (Works alongside quitOnLastWindowClosed(false) — that governs window close, this governs client disconnect.)

7. Files in this subsystem#

File Role
webinterface/NetworkClient.js parse binary stream; bake the needed (packed / interleaved) y values and appendRow() them into every column showing the channel
webinterface/DataStore.js per-stream channels: display state only — yOffset/yOffsetInterleaved, zoom, color, and the appendPacked/appendInterleaved flags. No sample buffer
webinterface/GlRenderer.js GlColumnRenderer: the WebGL2 renderer — one vertex buffer and one draw call per column, and the only copy of the samples
webinterface/ChartColumn.js one live-view column: its GlColumnRenderer, dropdowns, slider, draw() (mode select), refreshFilterOptions(), fitStrips() (the once-per-row strip fit decision)
webinterface/toolbar.css the column header's one authored shape: fixed control slots, the 46px definite header height, the collapsed reveal overlay
webinterface/main.js AppController: relayoutByDepth(), updateAppendModes(), column build, status, x-axis
webinterface/ImroManager.js recomputeDepthOrdering() + window.imroLiveView (ordering/bands)
webinterface/Config.js NUM_CHANNELS=384, TRACES_PER_COLUMN=20, CHANNEL_VERTICAL_SPACING
src/core/WebSocketServer.* transport + the lifecycle grace timer
