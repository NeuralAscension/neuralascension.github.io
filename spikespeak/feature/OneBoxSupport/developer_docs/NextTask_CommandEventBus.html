SpikesPeak — A modular command/event subscription bus (design brief + options)#

An open design brief with multiple solution options and a recommended plan for the one remaining architectural TODO: a single, config-declared, runtime-modifiable layer through which any module can say "notify me when X happens" or "send me command Y" — for both commands and events — with delivery that never runs inline on the acquisition/detection hot path.

Wider context: requirements come from ../NextSessionPrompts/01_command_event_subscription.md. Current state of the command/event model is SpikesPeak_Architecture_Review.md §7 (the per-module Q_INVOKABLE "Option A" decision) and §11.6 (the four partial mechanisms this bus unifies). The frontend⇄backend command standard is ModuleCommunication.md. Tracking lives in ../SpikesPeak_Status.md §31 (the retired todo.txt items 5–6). This is a transient NextTask_ brief — when the bus is built, fold the durable "how it works" into ModuleCommunication.md (or a new MessageBus.md) and git mv this to archive/.

1. Context — why this, why now#

Every module-to-module wire in SpikesPeak today is one of four things, and none of them is config-declared, runtime-modifiable, and covers both commands and events:

  • The data plane is config-declared but data-only and load-time-only (input: → a CircularBuffer consumer; to rewire you disconnect and reconnect).
  • Events are hardcoded Qt signals connect()-ed by hand in C++.
  • Frontend commands are per-module Q_INVOKABLE over QWebChannel — great for the browser, but C++-method-defined, not a general subscribe.
  • A real but vestigial CommandDispatcher does runtime command pub/sub, but it is command-only, C++-registered, and has exactly one (inert) subscriber.

Adding any new cross-module notification means editing C++ in a central place. The goal is one clean layer that lets a processor declare its subscriptions in YAML, lets the GUI/CLI rewire them live, and dispatches off the hot path so a slow subscriber can never stall acquisition or detection. The low-level plumbing already exists (thread-safe fan-out, cross-thread queued delivery, a per-module config parser) — this task is the unifying layer on top, plus a reference migration of the one existing subscriber.

Intended outcome: a module declares subscribe: [evt.ripple.detected, cmd.record.start] in its config and receives both after load; the same subscriptions can be added/removed over WS/CLI live; a deliberately slow handler is measured not to slow the detection loop; the same API carries a command and an event.

The primitives to reuse: - Thread-safe fan-out with cross-thread delivery already works: CommandDispatcher::executeCallbacks dispatches via QMetaObject::invokeMethod(sub.contextObj, sub.callback, Qt::AutoConnection, data) (CommandDispatch.hpp:106-107), so a subscriber on another thread receives the call queued onto its own event loop. This is the exact "off the hot path" property the bus needs. - A per-module config-subtree parser already hands each processor its own YAML node: IProcessor::configure(ryml::ConstNodeRef cfg) (IProcessor.hpp:19), driven by ProcessorManager::setupProcessors (ProcessorManager.cpp:27-64). The data plane self-subscribes inside configure() — the shape to mirror. - String-keyed registries with no central switch: getProcessorByName / getDataByName lazily construct from ObjectFactory<T> (Registry.cpp, ObjectFactory.hpp:98); one flat registration list in registerBuiltInTypes() (Utils.cpp:78-146). Adding a module already needs no central-router edit — the bus must preserve that.

Two latent defects in the seed (fix if we evolve it; avoid if we replace it): 1. removeSubscriber scopes its lock inside if (lock) { QMutexLocker lock(&mMutex); } (CommandDispatch.hpp:62-64) — the locker is destroyed at the closing brace, so the mutation below runs unlocked. 2. executeCallbacks holds mMutex across the entire fan-out loop (CommandDispatch.hpp:89-113), so a same-thread subscriber's handler runs while the mutex is held → a handler that re-subscribes/unsubscribes deadlocks. (Latent only because today's single subscriber is cross-thread.) The header's own TODO says it "will need to be modified into a slot" (:85-86).

Scope boundary — do NOT route the sub-ms closed loop through the bus. On quorum the detector calls mStimulatorClient->fire() inline on its own thread (RippleDetector.cpp:927) to hit sub-millisecond latency; only the notification emit sigRippleEvent(json) (RippleDetector.cpp:259) is queued to the main thread. The bus is for that notification-and-command traffic — the direct stim fire() stays a direct call.

3. Requirements & acceptance criteria (from the brief)#

  • A — A processor declares "subscribe me to topics A, B" in its YAML and receives them after load.
  • B — The same subscriptions can be added/removed at runtime (over WS/CLI) and take effect live.
  • C — A subscriber's handler runs on its own thread; a deliberately slow handler does not slow the acquisition/detection loop — measured, not asserted (this repo's rule).
  • D — Works for both a command (e.g. "start recording") and an event (e.g. "ripple detected") through the same API.
  • E — Modular: adding a publisher/subscriber needs no edit to a central switch (mirror how Q_INVOKABLE registration avoids a command router).
  • F — Documented here → folded into ModuleCommunication.md/MessageBus.md; todo.txt:5–6 closed into SpikesPeak_Status.md §31.

4. The design decisions (orthogonal axes)#

Every option below is a set of choices along these axes. Naming them up front makes the options comparable.

Axis Choices Notes
Topic identity uint16 id · string name · both Strings match the repo idiom (data.npx.lfp, proc.rippledetector) and read well in YAML; uint16 matches the binary WS frame + CommandDispatcher.
Payload QByteArray · QVariant · QJsonObject · Message{topic,kind,payload} The GUI already ships JSON-inside-a-QByteArray (binary id 0x1000, Commands.hpp:12-17); reusing that unifies wire + in-process.
Command vs event explicit kind enum · namespace convention (cmd.* / evt.*) · ignore the distinction Same delivery either way; the distinction is documentation/routing sugar.
Delivery / threading Qt::QueuedConnection invoke · dedicated dispatcher QThread · per-subscriber lock-free inbox Queued invoke reuses Qt's thread-safe event queue and is non-blocking for the publisher; the inbox mirrors the data plane for subscribers with no live event loop.
Config schema subscribe: [names] · subscriptions: [{topic,handler}] · commands:/events: split Mirror the existing input:/inputs: convention parsed in configure().
Runtime mutation one WS subscribe/unsubscribe command routed to the bus The control-plane entry; keep the fan-out generic (no per-topic C++).
Ownership global getMessageBus() accessor · MainController-owned · injected A global accessor matches getCommandDispatcher()/getDataRegistry(); must be cleared on teardown like the registries.

5. Solution options#

5.1 Option A — Evolve CommandDispatcher in place#

Grow src/core/CommandDispatch.{hpp,cpp} into the bus: add string topics alongside the uint16 id, add an evt.*/cmd.* namespace, force Qt::QueuedConnection in the fan-out (so a same-thread publisher never runs a handler inline), fix the two locking bugs, and add a subscribe: parse step in configure().

  • Pros: least new code; reuses the proven fan-out + QPointer dead-subscriber cleanup; the (inert) 0x218 subscriber keeps working; one file is most of the change.
  • Cons: CommandDispatcher is explicitly being phased out in favour of Q_INVOKABLE (review §7/§11.6) — reviving it fights the stated direction; the name says "command" not "event"; QByteArray-only payload; global Meyers singleton with a private ctor is awkward to reset per-connect and to unit-test.

5.2 Option B — New MessageBus sibling that supersedes CommandDispatcher (recommended)#

A fresh src/core/MessageBus.{hpp,cpp} — string topics, QByteArray payload (JSON by convention), delivery forced to the subscriber's thread via Qt::QueuedConnection. Subscriptions are declared in YAML and wired inside IProcessor::configure() via a shared base-class helper, so no central router is touched. Publishing is getMessageBus().publish(topic, payload) from any thread, non-blocking. The two live users (the 0x218 subscription and sigRippleEvent) migrate onto it as the reference; CommandDispatcher retires.

  • Pros: unifies commands + events behind one API; matches the brief's "new sibling that supersedes it"; string topics read naturally in YAML and reuse the registry-name idiom; minimal per-module boilerplate (one virtual slot + a config list); clean lifetime (cleared on teardown like the registries); testable.
  • Cons: a genuinely new subsystem (more up-front code than A); must migrate the inert 0x218 and the live sigRippleEvent and prove parity; inherits the busy-loop/event-loop caveat (see §9).

5.3 Option C — Declarative signal/slot auto-wiring#

No new bus object. Add a YAML wiring block (connections: [{from: "proc.rippledetector/sigRippleEvent", to: "proc.audio/slOnRipple"}]) and a small engine that resolves both ends by registry name and connects them at load with QObject::connect(..., Qt::QueuedConnection) using the runtime meta-object; runtime connect/disconnect over WS. Events are already signals, so this leans entirely on Qt's own machinery.

  • Pros: reuses Qt's thread-safe, already-queued connection engine; zero new payload format; the smallest runtime.
  • Cons: every publisher must expose a matching signal and every subscriber a matching slot with identical signatures — imperative commands map poorly (there's no natural "signal" for "start recording"); string signal/slot lookup is fragile and untyped; there is no abstract topic namespace (you wire concrete symbols, not stable topics), so it fails the "unified commands and events through one API" criterion (D) cleanly.

5.4 Option D — Lock-free topic inbox (data-plane style) (variant / fallback)#

Model the control plane on the data plane: each subscriber owns a small CircularBuffer-style inbox per topic that the publisher commitWrites into and the subscriber drains explicitly in its loop. No event loop required.

  • Pros: consistent with the repo's proven producer/consumer idiom; bounded and back-pressure-friendly; works for busy-loop processors (RippleDetector, LFPProcessor) that only processEvents() between batches.
  • Cons: subscribers must poll/drain (more boilerplate); heavier than a queued signal for low-rate control traffic; single-producer today. Best kept as the documented fallback for the specific subscribers that can't run an event loop, not the default.

6. Recommended approach — Option B, locked decisions#

Build MessageBus with these axes fixed, keeping Option D's inbox as a documented fallback and Option C's insight (reuse Qt's queued delivery) inside the implementation.

  • Topic = string, namespaced cmd.* (imperative) / evt.* (notification) — e.g. evt.ripple.detected, cmd.record.start. Human-readable in YAML, mirrors data.*/proc.*.
  • Payload = QByteArray, UTF-8 JSON by convention for structured data — the exact shape the GUI already sends (0x1000 JSON-over-binary). "Fast but not too inconvenient" (todo.txt:5), and unifies wire + in-process without a new type.
  • Delivery = Qt::QueuedConnection marshalled to each subscriber's thread affinity. Publisher just posts and returns → non-blocking. Snapshot the subscriber list under the mutex, then invoke outside the lock (avoids the §2 deadlock and lets a handler re-subscribe safely).
  • Ownership = global getMessageBus() accessor (matches getCommandDispatcher()), cleared on teardown in MainController::teardownManagers right where the registries are cleared (MainController.cpp:61-93).

API sketch (src/core/MessageBus.hpp):

class MessageBus : public QObject {
    Q_OBJECT
public:
    // any thread; non-blocking; delivers queued to each subscriber's thread
    void publish(const QString& topic, const QByteArray& payload = {});
    // context gives thread affinity + auto-removal when it dies (QPointer)
    void subscribe(const QString& topic, QObject* context,
                   std::function<void(const QString& topic, const QByteArray&)> handler);
    void unsubscribe(const QString& topic, QObject* context);
    void clear();                                   // teardown: drop all subscriptions
private:
    QMutex mMutex;
    QHash<QString, QVector<Subscription>> mSubs;    // Subscription{ QPointer<QObject>; handler; }
};
MessageBus& getMessageBus();

Delivery (fixes both §2 bugs):

void MessageBus::publish(const QString& topic, const QByteArray& payload) {
    QVector<Subscription> snapshot;
    { QMutexLocker lk(&mMutex);                     // held only to copy the list
      snapshot = mSubs.value(topic); }
    for (const auto& s : snapshot) {
        if (s.contextObj.isNull()) continue;        // dead subscriber
        QMetaObject::invokeMethod(s.contextObj,     // marshalled to s's thread
            [h = s.handler, topic, payload]{ h(topic, payload); },
            Qt::QueuedConnection);                  // NEVER inline on the publisher's thread
    }
}

Config schema (mirrors input:), parsed in configure():

processors:
  - name: "proc.audio"
    input: "data.npx.ap"
    subscribe:                        # NEW — list of topics this module receives
      - "evt.ripple.detected"
      - "cmd.audio.mute"

Zero-boilerplate wiring — add one base-class helper + one virtual slot to IProcessor, so a module overrides a single method and never touches the manager:

// IProcessor.hpp
public slots:
    virtual void slOnBusMessage(const QString& topic, const QByteArray& payload) {}   // default no-op
protected:
    void configureSubscriptions(ryml::ConstNodeRef cfg) {   // call from configure()
        if (!cfg.has_child("subscribe")) return;
        for (auto t : cfg["subscribe"]) {
            QString topic = /* toQString(t.val()) */;
            getMessageBus().subscribe(topic, this,
                [this](const QString& tp, const QByteArray& p){ slOnBusMessage(tp, p); });
        }
    }

8. Validation — measure, don't assert#

The acceptance criteria are only met when measured. Reuse the existing latency instrumentation (rippleLatency per-stage timers + ripple_tools/latency_breakdown.py, see LatencyProfiling.md).

  1. Off-hot-path (criterion C) — the load-bearing test. Add a throwaway subscriber whose slOnBusMessage does QThread::msleep(50), subscribe it to evt.ripple.detected, run the sim closed loop, and compare the detector loop period and closed-loop threshold→ai4 latency against the same run with no slow subscriber. Pass = no measurable change (the sleep is absorbed on the subscriber's thread). Confirm the direct stim fire() path is untouched.
  2. Config load (A). A YAML subscribe: list is honoured: publish the topic after load, confirm receipt.
  3. Runtime (B). subscribe over WS mid-stream → the module starts receiving; unsubscribe → it stops — live, no reconnect.
  4. One command + one event, same API (D). evt.ripple.detected still reaches the browser (parity with the old signal), and cmd.record.start starts a recording — both via publish.
  5. Lifecycle. Connect→disconnect→reconnect leaves no stale subscriptions (clear() on teardown); a destroyed subscriber is auto-dropped (QPointer).

9. Risks & gotchas#

  • Busy-loop subscribers have no live event loop. RippleDetector/LFPProcessor run a blocking while and only drain queued events at QCoreApplication::processEvents() between batches (RippleDetector.cpp:~1007). Queued bus deliveries to those modules land only at that cadence. Mostly a non-issue (they are publishers, not subscribers), but any busy-loop subscriber needs the processEvents cadence or the Option D inbox fallback. Document per-subscriber.
  • Never route the sub-ms stim path through the bus (RippleDetector.cpp:927 stays a direct fire()).
  • Unbounded queue growth if a high-rate topic meets a slow subscriber → offer a bounded/coalescing option per topic before shipping high-rate evt.*.
  • Teardown ordering: clear() the bus (and join worker threads) before the registries free the modules — mirror the existing cleanupProcessors → clearRegistry order (MainController.cpp:61-93).
  • Don't reintroduce the two CommandDispatcher bugs — snapshot-then-invoke outside the lock, and hold the mutex only to copy the subscriber list.
  • Q_INVOKABLE stays for request/response browser RPC (Option A, review §7). The bus is for fire-and-forget notifications/commands, not for calls that return a value to the caller.

11. Open questions to confirm before building#

  • Topic granularity: flat strings (evt.ripple.detected) only, or do we want wildcard/prefix subscriptions (evt.ripple.*)? (Recommend: start flat; add prefix matching only if a real need appears.)
  • kind field or namespace convention? Recommend the cmd.*/evt.* naming convention over a separate enum — simpler, self-documenting in YAML.
  • Retire CommandDispatcher fully, or thin-shim it onto MessageBus for one release? (Recommend: full removal — its only subscriber is inert and its only dispatch path is dead code.)
  • Payload contract: standardise on JSON-in-QByteArray for all structured topics (recommended), or allow raw binary for specific high-rate topics?
  • Handler contract: one virtual slOnBusMessage(topic, payload) per module (recommended, minimal boilerplate) vs per-topic named handlers declared in YAML.
