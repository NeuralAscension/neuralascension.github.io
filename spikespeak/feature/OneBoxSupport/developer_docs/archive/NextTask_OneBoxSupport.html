SpikesPeak — Adding Neuropixels OneBox support (implementation plan)#

Status: planning brief (branch feature/OneBoxSupport, started 2026-08-18). No SpikesPeak code changed yet. This doc is the crash-safe source of truth for the task. Reference: OpenEphys neuropixels-pxi (local copy Source-OpenEphys-Neuropixels-PXI/; upstream github.com/open-ephys-plugins/neuropixels-pxi). Every IMEC API call below was verified against the vendored header external/neuropixels/api/include/v4/NeuropixAPI.h (the .lib/.dll we actually link, NeuropixAPI_x64_4_1_3).

TL;DR — The OneBox is just another basestation to the IMEC API. It is enumerated by the same scanBS(), and once it is mapped to a virtual slot and opened, reading a probe through a OneBox is byte-for-byte identical to PXI (readPackets/readElectrodeData). So OneBox support = (1) a different open step (USB platform + mapBS + FTDI driver check), plus (2) OneBox's two extra I/O paths that PXI doesn't have: a 12-channel ADC (analog in) and a DAC/WavePlayer (analog out — a native, hardware-timed closed-loop stim output). The probe-streaming workers and the whole IMRO/channel-map pipeline are reused unchanged.

0. What the user needs to do once (FTDI driver)#

The OneBox is a USB-3 device built on an FTDI FT601 bridge. The IMEC API refuses to talk to it unless the correct FTDI D3XX driver is installed, and it is picky about the version.

  • Install this exact driver: FTD3XXDriver_WHQLCertified_1.3.0.10_Installer.zip Official FTDI direct link: https://ftdichip.com/wp-content/uploads/2024/06/FTD3XXDriver_WHQLCertified_1.3.0.10_Installer.zip (landing page: https://ftdichip.com/drivers/d3xx-drivers/). Run the setup executable inside the zip.
  • Do NOT install 1.4.0.x — the newest D3XX driver is incompatible with the OneBox and the device will not be recognized. If 1.4.0.x is already present it must be removed first (Device Manager → uninstall the device, then install 1.3.0.10).
  • Verify: after install + plugging in a powered OneBox, Device Manager shows "FT601 USB 3.0 Bridge Device" under Universal Serial Bus controllers.
  • The API can self-report the required version at runtime — checkFtdiDriver() returns required, current, is_driver_present, is_version_ok (only works while a OneBox is powered on — an FTDI library limitation). SpikesPeak will call this on OneBox selection and show a clear GUI status if the driver is missing/mismatched (see Phase 1). The reference plugin hardcodes the required version as 1.3.0.10, matching the driver above.

Driver installation is a manual, elevated action — the user installs it; SpikesPeak never installs a driver. Our code only detects and reports.

1. Current state in SpikesPeak#

  • Real Neuropixels today = one class NeuropixelsSource (registry name source.npx.pxi) in src/modules/neuropixels/NpInterface.{hpp,cpp} (~2k lines), gated #ifdef NPX_HW_ENABLED (Windows only; Linux compiles the API stubs and uses sim sources). Registered in src/core/Utils.cpp registerBuiltInTypes().
  • NpInterface.hpp already anticipates this task: cpp // Going to need another constructor for the OneBox // probably a layer of abstraction before the NeuropixelsSource // object is created with knowledge of onebox constructor or pxie constructor ...
  • source.npx.onebox is a phantom. config/OneBoxTest.yaml references it but nothing registers it, so WebSocketServer::onSourceSelection (~line 123) hits the "OneBox is not supported in this build yet" hardware-error dialog. That stub is what we replace.
  • The source contract is IDataSource (src/core/IDataSource.hpp): initDataSource / closeDataSource / startAcq / stopAcq, producing into a registered CircularBuffer via addProducer/commitWrite, with a worker (IDataSourceWorker) on its own QThread. See developer_docs/AddingASourceModule.md.
  • Existing probe-streaming workers (both in NpInterface.cpp, both slot/port/dock-based, so they are already platform-agnostic): Npx1Probe (np_readElectrodeData → data.npx.ap + data.npx.lfp) and Npx2MSProbe (np_readPackets → data.npx.raw).

2. How the OneBox differs from PXI — verified against the vendored v4 API#

2.1 Enumeration & open (the ONE genuinely-different step)#

Both platforms come out of the same scan. The differentiator is a struct field:

typedef enum { NPPlatform_None=0, NPPlatform_PXI=0x1, NPPlatform_USB=0x2, NPPlatform_ALL=0x3 } NPPlatformID_t;
struct basestationID { NPPlatformID_t platformid; /* ...serial... */ };   // v4 line 36–48
Step PXI (today, initBasestation) OneBox (new openBasestation override)
scan np_scanBS() np_scanBS() (same call scans USB and PXIe)
list np_getDeviceList(list, 16) same
pick np_tryGetSlotID() → first PXI slot iterate list, keep entry with platformid == NPPlatform_USB; read its serial via np_getDeviceInfo(slot, &info)
map (PXI already has a physical slot) np_mapBS(serial_number, virtualSlot) — OneBox has no chassis slot, so you assign it one. Reference convention: first virtual slot = 16. np_unmapBS(slot) on close.
open np_openBS(slot) np_openBS(virtualSlot) (identical once mapped)
driver — np_checkFtdiDriver(&required,&current,&present,&ok) first; if !ok emit a hardware-error guiStatus naming the required version and stop.

Everything after open — np_openPort / np_detectHeadStage (ports 1–4), np_getProbeHardwareID → ProbeType, buffer sizing, IMRO — is the same code.

2.2 Probe streaming — identical, reuse as-is#

Verified: OneBox exposes the probe through the same np_readPackets / np_readElectrodeData on its (virtual) slot. Npx1Probe and Npx2MSProbe are reused unchanged. No new probe worker.

2.3 OneBox ADC — analog input (the new data stream)#

OneBox-only. 12 analog input channels (NUM_ADCS = 12 in the reference), fixed sample rate ≈ 30300.5 Hz, int16 samples.

Rig note (2026-08-18): the user's OneBox has the BNC breakout board attached via the SDR connector, so all 12 ADC channels are available (per OpenEphys: ADC 0 is the standalone "ADC" SMA connector; ADC 1–11 require the breakout via the SDR connector). The user wants this ADC streamed "similar to the NI-DAQ with the PXIe system" — i.e. a live stream alongside NI-DAQ (NI-DAQ stays for PXIe rigs; it is not wired to the OneBox). This is the Phase-2 deliverable.

Verified API:

  • np_ADC_readPackets(slot, PacketInfo* pck, int16_t* data, channel_count, packet_count, &packets_read) — streams into the same CircularBuffer<int16, Neuropixels::PacketInfo> type the probe uses (same aux struct → free reuse of the interpreter/display/recorder). Poll status with np_ADC_getPacketFifoStatus.
  • np_ADC_setVoltageRange(slot, ADCrange_t) — ADC_RANGE_2_5V | ADC_RANGE_5V | ADC_RANGE_10V.
  • np_ADC_getStreamConversionFactor(slot, &lsb_to_voltage, &bit_depth) — authoritative counts→volts scale (use this instead of hardcoding bitVolts).
  • np_ADC_enableProbe(slot, enable) — enable the ADC data path.
  • Comparators (per channel, used as "digital in" / hardware trigger source): np_ADC_setComparatorThreshold(slot, ch, v_low, v_high), np_ADC_readComparator(s).

OneBoxADC in the reference derives from DataSource, not Probe — i.e. it is a sibling stream, not a probe. In SpikesPeak it becomes a second producer on a new buffer data.npx.adc.

2.4 OneBox DAC + WavePlayer — analog output (native closed-loop stim)#

OneBox-only. This is the strategically important part for this lab. Verified API:

  • WavePlayer (arbitrary waveform out on SMA/DAC0): np_waveplayer_writeBuffer(slot, int16_t* data, len), np_waveplayer_setSampleFrequency(slot, Hz), np_waveplayer_arm(slot, single_shot), np_waveplayer_stop(slot). Arm routes DAC0→SMA and waits for a trigger.
  • DAC (static/level out, 12 channels): np_DAC_setVoltage(slot, ch, V), np_DAC_setVoltages(slot, mask, V[]), np_DAC_enableOutput(slot, ch, on), np_DAC_setDigitalLevels(slot, ch, vHi, vLo), np_DAC_setProbeSniffer(slot, dacCh, port, dock, channel, source) (mirror a live probe electrode to a DAC — analog monitor scope-out).
  • Trigger routing (switch matrix, already used by the PXI code for sync): np_switchmatrix_set/get/clear, np_switchmatrix_setOutputTriggerEdge, endpoints incl. SM_Output_SMA (OneBox back-panel SMA), SM_Output_WavePlayerTrigger, SM_Output_DAC0..11, SM_Input_ADC0..15 (comparator outputs), SM_Input_SWTrigger1/2. Software trigger: np_setSWTrigger(slot) / np_setSWTriggerEx(slot, flags) (default WavePlayer SW trigger = SM_Input_SWTrigger2).

Two closed-loop modes this unlocks (both are follow-on phases, not the first milestone): 1. Software-triggered — our ripple detector fires → waveplayer_arm + setSWTriggerEx → OneBox emits the pre-loaded biphasic waveform. Drops the UDP→Pi→AM2300 network hop from the current path (~2–3.5 ms). 2. Fully hardware — route an ADC comparator threshold → WavePlayer trigger in the switch matrix. Sub-ms, zero software in the loop, but only a raw amplitude threshold (no real ripple detector). Useful as a backstop / calibration mode. This complements — does not replace — the validated ripple→UDP→Pi/AM2300 stim path (developer_docs/StimClosedLoop*, [[stim-closed-loop-validated]]).

2.5 v3 vs v4 API skew — checked#

Per-symbol presence in the vendored headers is identical for the OneBox surface (mapBS, ADC_readPackets, NPPlatform_USB, checkFtdiDriver, ADC_getStreamConversionFactor all present in both); v4 only adds (e.g. DAC_setVoltages). No regression — building against our v4 lib is safe.

3. Design — keep it simple (one new file pair, reuse everything else)#

Guiding constraint (user): don't over-engineer; OneBox and PXI can share, but NpInterface.cpp is already ~2k lines and must not balloon. OneBox's genuinely-new code (USB open + ADC worker + DAC/WavePlayer) is ~350–400 lines, which would push NpInterface past ~2.4k. So that new code gets its own file pair; the shared 95% is reused by a thin inheritance seam that barely touches NpInterface.

3.1 The seam (minimal change to NpInterface)#

  1. In NeuropixelsSource, split the platform-specific enumeration out of initBasestation() into a virtual bool openBasestation() (its default body = today's PXI scan/open — PXI behavior unchanged). Make the members OneBox needs (mSlot/mPort/mDock, discoverProbeHardware(), the IMRO methods, the worker-thread spin-up in startAcq, publishChannelMap) protected instead of private. Net effect on NpInterface: one method split + visibility change. No size growth to speak of.
  2. If OneBox needs different sync/switch-matrix defaults (it does — SMA is on the back panel, plus ADC/DAC endpoints), also make setSyncAsPassive() (or a small configureSwitchMatrix()) virtual.

3.2 New file: src/modules/neuropixels/OneBoxSource.{hpp,cpp}#

class OneBoxSource : public NeuropixelsSource {   // IS-A Neuropixels source; specializes open + adds ADC/DAC
    Q_OBJECT
protected:
    bool openBasestation() override;      // USB scan + getDeviceInfo(platformid==USB) + checkFtdiDriver + mapBS(16) + openBS
public:
    bool initDataSource(ryml::ConstNodeRef cfg) override;  // base init (probe) THEN set up ADC producer
    bool startAcq() override;             // base startAcq (probe worker) THEN start ADC worker
    bool stopAcq() override;  bool closeDataSource() override;  // stop/close ADC + unmapBS, then base

    // Phase-2 stim (Q_INVOKABLE over QWebChannel, like the IMRO hooks):
    Q_INVOKABLE bool loadWaveform(const QString& jsonSamplesOrPath);
    Q_INVOKABLE bool armWaveplayer(bool singleShot);
    Q_INVOKABLE bool fireWaveplayer();     // setSWTriggerEx
    Q_INVOKABLE bool setDacVoltage(int ch, double v);
private:
    OneBoxAdcWorker* mAdcWorker;  QThread* mAdcThread;
    SP::CircularBuffer<int16, Neuropixels::PacketInfo>* mAdcData;
};

// ADC streaming worker — mirrors Npx2MSProbe, but np_ADC_readPackets on the slot (no port/dock).
class OneBoxAdcWorker : public SP::IDataSourceWorker { /* QTimer poll → np_ADC_readPackets → commitWrite */ };

Registered in Utils.cpp under #ifdef NPX_HW_ENABLED: SP::registerDataSource<SP::Npx::OneBoxSource>("source.npx.onebox", /*seed slot*/16, 1, 1, nullptr); plus SP::registerData<SP::CircularBuffer<int16, Neuropixels::PacketInfo>>("data.npx.adc"); and a matching interp.npx.adc.

Why inherit NeuropixelsSource rather than rename to a neutral base? Least churn, and it literally implements the maintainer's header comment. If you later prefer symmetry, the drop-in refactor is: rename NeuropixelsSource → NpxProbeSource (base), add a trivial PxiSource subclass for the default open, and OneBoxSource stays as-is. Deferred — not needed to ship OneBox.

3.3 Simulated OneBox sibling (standing rule: ship a sim with every hardware source)#

Cross-platform (no vendor lib → always compiled, like NiDaqSimSource). Reuse an existing probe sim for the neural stream and add a small simulated ADC producer (12 ch of sine/noise) into data.npx.adc, so the entire OneBox module — display, recording, and the ADC path — is testable on Linux with no hardware. Options: a SimOneBoxSource class, or compose the existing SimulatedData2Source + a tiny SimOneBoxAdc in one profile. (Neural-stream sim shape is hardware-specific per the SimDataLinux ruling; the ADC sim is new, so it gets its own small class.)

3.4 Data streams summary#

Buffer Type Producer Notes
data.npx.raw / .ap / .lfp CircularBuffer<int16, PacketInfo> reused probe worker same as PXI
data.npx.adc (new) CircularBuffer<int16, PacketInfo> OneBoxAdcWorker 12 ch, ~30.3 kHz; scale via ADC_getStreamConversionFactor

The ADC channel map is trivial (N analog channels, no electrode geometry) — a thin IChannelMap or reuse the generic one; display/recorder need no changes because the buffer type matches.

4. Phased plan#

  • Phase 0 — seam (small, no behavior change). Extract openBasestation() virtual + protected members in NpInterface. Rebuild Windows; confirm PXI still streams (regression, not a rewrite).
  • Phase 1 — OneBox probe acquisition (the milestone). New OneBoxSource.{hpp,cpp}: USB open + FTDI check
  • mapBS; reuse probe workers + IMRO. Register source.npx.onebox; update config/OneBoxTest.yaml to a real profile; add the "Neuropixels OneBox" <option> in webinterface/index.html and remove the "not supported" branch in WebSocketServer::onSourceSelection. **Deliverable: a probe on a OneBox streams
  • records + runs ripple detection exactly like PXI.**
  • Phase 2 — ADC stream (NEXT; user attaching the SDR breakout 2026-08-18). OneBoxAdcWorker (mirrors Npx2MSProbe, calls np_ADC_readPackets on the slot) → new buffer data.npx.adc (CircularBuffer<int16, Neuropixels::PacketInfo>, 12 ch, ~30.3 kHz) + interp.npx.adc (reuse NpxDataInterpreter). Wire into OneBoxSource: initDataSource override (base probe setup THEN add ADC producer + np_ADC_enableProbe(slot,true) + np_ADC_setVoltageRange), startAcq/stopAcq overrides (base probe worker THEN ADC worker on its own QThread). Display approach (decided): reuse the NPX DisplayProcessor as a SECOND input (band id adc), but first make its per-stream numChannels configurable — today DisplayProcessor.cpp hardcodes state.numChannels = 384 (the wire header already sends a per-stream count, so the browser handles variable widths — NI-DAQ relies on this). Read the count from the config input (e.g. num_channels: 12) or the bound buffer's dimensions. Add adc: 'OneBox ADC' to ChartColumn.streamLabel (webinterface/ChartColumn.js) so the band dropdown shows it. Config: add a 2nd outputs: entry + a 2nd proc.npx.display input + a proc.npx.recorder entry for data.npx.adc in Npx2OneBox.yaml/Npx1OneBox.yaml. This gives a NI-DAQ-style separate, labeled, recordable stream while reusing the int16/PacketInfo probe pipeline. (Alt considered + rejected: a dedicated OneBoxAdcDisplayProcessor like NiDaqDisplayProcessor — more code, and NiDaq's is double/NiDaqPacketInfo so not directly reusable for the int16 ADC.) Lets the OneBox capture sync pulse in, stim monitor, behavior signals — ALONGSIDE (not replacing) NI-DAQ, which stays for PXIe rigs.
  • Phase 3 — simulated OneBox sibling. So Phases 1–2 are validatable on Linux with no hardware; wire into the sim picker.
  • Phase 4 — WavePlayer/DAC stim (closed loop). Load a biphasic waveform, software-trigger it from the ripple detector as an alternative low-latency stim output; optional ADC-comparator hardware-trigger mode. Validate latency A/B vs the UDP→Pi/AM2300 path.
  • Phase 5 — OneBox GUI panel. ADC range + per-channel enable/comparator, DAC/WavePlayer setup — mirror the reference OneBoxInterface. Only after the streams are proven.

Ordering rule: prove each phase in sim before hardware; then bring up hardware saline first, then in vivo (matches this repo's standing test discipline, [[hardware-connected-testing]]).

6. Build / platform notes#

  • Real OneBox source is Windows-only, same #ifdef NPX_HW_ENABLED gate as PXI (the vendored lib/dll is _x64 Windows). The sim sibling and the data.npx.adc buffer/interpreter are lib-free → compiled on all platforms (Linux stubs unaffected — they don't need the OneBox symbols because the real source isn't built there).
  • Calibration: probes on a OneBox still use the per-serial ADC + gain CSVs already handled by the repo's CalibrationInfo/ mechanism (SpikesPeak_Status.md §9.1). The OneBox's own ADC is scaled by ADC_getStreamConversionFactor, no CSV.
  • Safety: OneBox is real hardware — obey [[graceful-hardware-shutdown]] / [[stop-streaming-when-idle]] (never force-kill while a probe/OneBox streams; disarm the WavePlayer on graceful quit).

7. Open questions for the team#

  1. ADC as sync source? Once the OneBox ADC streams, it could capture the sync pulse + stim monitor directly, potentially replacing the NI-DAQ in the closed-loop sync analysis. Keep NI-DAQ, or migrate to OneBox ADC for OneBox rigs?
  2. WavePlayer vs Pi/AM2300 for stim. Do we want the OneBox WavePlayer as the primary low-latency stim output (Phase 4), or keep it as a second option beside the validated UDP path? (Affects how much Phase-4 GUI/latency work to prioritize.)
  3. Virtual slot number. Reference uses 16 for the first OneBox. Fine to hardcode 16 (single OneBox), or scan for a free virtual slot to be multi-OneBox-ready later?
  4. Rename the base now or later? Ship OneBox as a subclass of NeuropixelsSource (least churn) and defer the NpxProbeSource/PxiSource rename, or do the symmetric rename up front?
  5. Multi-basestation. PXI code today stops at the first basestation. A rig could have a PXIe and a OneBox. Out of scope for v1 (one source at a time), but the sources: list already composes — worth a note.
