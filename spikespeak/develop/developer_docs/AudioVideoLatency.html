What you see, what you hear, and how old both are#

The operator's question, verbatim: "what I'm looking at, what I'm hearing, in which order, and how delayed is this from the raw data collection."

You see it first, by about 97 ms on the shipped default device — and that gap is mostly a settings choice, not a law of physics. On an NP2.0 probe on a OneBox:

path delay from the probe sample what dominates it
eye — trace on screen ~19 ms the display publishes at ~50 Hz
ear — sound from the speaker ~116 ms the audio device: 99.9 ms of output latency plus a 15 ms ring

So a spike was on screen roughly 97 ms before you heard it — as measured, on what was then the shipped default device.

This measurement is what made the default change, so the "116 ms" row is now historical. The ear figure above was taken when Pa_GetDefaultHostApi() chose the device, which on Windows means MME. Since 2026-08-25 AudioWorker::findDefaultFollower() ranks the follower endpoints by hostApiRank() and takes the fastest — DirectSound's Primary Sound Driver (rank 0) rather than MME's Sound Mapper (rank 9). Following the system default should therefore now land near the ~37 ms row of §2 rather than the ~116 ms one, and a realistic figure on real speakers is ~47 ms.

The eye/ear numbers here have not been re-measured against the new default. Re-running python ripple_tools/measure_av_latency.py is what would replace this row; until then, treat 116 ms as the cost of MME and not as the cost of the shipped configuration.

Changing the audio device is still the single largest latency win available anywhere in this document — it is now simply made for you by default rather than left to the operator. That is not a small offset — it is about four display frames — and it matters whenever the two are being compared by eye and ear at once, which is exactly what a spike monitor is for.

Numbers live in ../RecordingTests/CLOSED_LOOP_LATENCY.md by convention; this page is the METHOD and the reasoning. The measured cells are repeated here because the ordering claim is meaningless without them.

1. The two paths, and why they are so different#

Both start from the same ring buffer of probe samples. They diverge immediately.

                        data.npx.raw  (30 kHz)
                              |
        +---------------------+---------------------+
        |                                           |
   DisplayProcessor                           AudioProcessor
   bins + publishes ~50 Hz                    filters 300-6000 Hz,
        |                                     subsamples to 44.1 kHz
   WebSocket (binary)                               |
        |                                      mAudioData ring
    browser draws                                   |
        |                                     PortAudio callback
       EYE  ~19 ms                                  |
                                              host API + device
                                                    |
                                                   EAR  ~116 ms  (default)
                                                        ~47 ms   (best real device)

The display path is short because it is allowed to be lossy: it bins, publishes what it has, and the browser draws it. The audio path cannot be lossy — a gap in audio is an audible click — so it is buffered, and the buffering is almost entirely outside SpikesPeak.

2. Measured, NP2.0 on a OneBox (2026-08-25)#

term median notes
source_lag_mean_ms 1.00 ms how far behind the acquisition writer the audio converter runs
output_latency_measured_ms 99.90 ms what the device is actually doing, per callback
output_latency_ms 91.43 ms what PortAudio PROMISED at open — see why this is not the one to trust
audio_ring_depth_ms 15.11 ms converted audio queued ahead of the frame being played
raw → ear ~116.0 ms source lag + ring depth + measured output latency
raw → eye 19.2 ms median inter-frame gap, n = 973, p95 20.3 ms

The same measurement against the simulated NP2.0 source gives the same audio figures and a 20.0 ms display interval. That the figures are indistinguishable is the point: none of this latency is the probe's. It is the host audio stack and the display cadence, so it is the same on any source, and it will be the same on PXIe. (Which is worth confirming rather than assuming — see §5.)

The output latency is not ours to fix — but it IS ours to choose#

91.4 ms is what the MME host API reports for the selected device. Nothing in SpikesPeak can shrink it. Choosing a different device can, and by a lot — so the audio panel's device picker is a latency control, not a convenience.

Measured on this machine, 2026-08-25, same probe, muted, ranked by measured latency:

idx host API device promised measured ring depth raw → ear
5 DirectSound Primary Sound Driver 120.00 ms 8.71 ms 27.17 ms ~36.9 ms
6 DirectSound ASUS VE278 (NVIDIA) 120.00 ms 13.06 ms 33.17 ms ~47.2 ms
8 DirectSound LG HDR WFHD (NVIDIA) 120.00 ms 13.06 ms 33.54 ms ~47.6 ms
7 DirectSound Digital Audio (S/PDIF) 120.00 ms 18.14 ms 29.89 ms ~49.0 ms

Refused to open: WASAPI on indices 10, 11, 12 and WDM-KS on 19, 20. That includes WASAPI → ASUS VE278, the entry for the actual monitor speakers.

Three things this overturns#

0. The default now follows this table. These measurements are no longer only advice: the ranking in AudioWorker::hostApiRank() is derived from this table, and the device picker lights a dot on the fastest route to each speaker. What follows is therefore the justification for a shipped behaviour, not a suggestion the operator has to act on.

1. "Use WASAPI" is wrong on this machine. It is the usual advice and it fails here: WASAPI refuses to open every real output except a virtual NoMachine device. The advice that survives measurement is DirectSound → ASUS VE278: same physical speakers as the MME default, and 13.06 ms instead of 99.90 ms.

2. PortAudio's promised latency is not merely imprecise, it is ANTI-correlated here. DirectSound promises 120 ms — the worst figure in the table — and measures 8.7–18.9 ms, the best. WDM-KS promises 10 ms and measures 19.9 ms. Ranking by the promised number picks almost exactly the wrong device, which is what the first version of the comparison script did before its own output was read properly. Trust output_latency_measured_ms; the promised figure is buffer geometry, not behaviour.

3. The ring depth matters as much as the output latency, and moves independently. WDM-KS SPDIF has the worst measured output latency of the low-latency group (19.89 ms) and the best total (~23.4 ms), because its ring sits at 2.46 ms while DirectSound's sits at ~30 ms. Optimising output latency alone would have chosen wrongly. This is why the earlier figure in this document — "≥ 92.4 ms" — was a lower bound: it omitted the ring, which had not yet been measured.

So does the ordering ever flip?#

No, not on this machine. Even the best total (~23 ms on WDM-KS SPDIF, which is a digital output and may not reach a speaker at all) is at best level with the ~19 ms display path, and the best practical option for the monitor speakers is ~47 ms. You still see it before you hear it — but the gap narrows from ~97 ms to ~28 ms simply by changing the device.

3. What is instrumented, and what it costs#

All of it reaches the GUI through the existing audioState event, which the audio dock polls at 4 Hz only while it is open.

field computed cost
source_lag_mean_ms, source_lag_max_ms on the processor thread, once per 1 ms tick 3 relaxed atomics at 1 kHz
output_latency_ms once, when the stream opens free
output_latency_measured_ms in the PortAudio callback 1 subtract + 1 relaxed store, ~690 Hz
audio_ring_depth_ms in the callback, from operands already loaded 1 subtract + 1 relaxed store
device_underflows, starved_callbacks in the callback, inside branches that only run when audio is already broken zero in the healthy case
input_peak_counts, output_peak per audio sample, one fabs + one max 44.1 kHz, not the 30 kHz path

Nothing above touches the 30 kHz acquisition loop. The per-sample work is on the 44.1 kHz audio path, which is a different thread and a different budget.

Two mistakes worth not repeating#

The first version computed the backlog at POLL time, reading mCurrSourceDataInd — a plain int64 owned by the processor thread — from whichever thread happened to call audioStateJson(). That is a data race, and it can never observe the peak, which is the only value a worst-case claim can rest on. It now accumulates on the owning thread, once per tick, and the poll drains it.

The first version also claimed the ring depth was unmeasurable, "owned by PortAudio's callback cadence rather than by anything measurable here". It is measurable — from inside the callback, which is where that cadence lives, and where both operands were already in registers.

4. Reproducing#

python ripple_tools/measure_av_latency.py "NPX 2.0 Multishank (OneBox)"

The script brings the rig up, counts binary frames in the page over a real interval (rather than trusting a configured rate), polls audioState, and tears down gracefully.

Audio commands ride a BINARY frame on channel 0x218, not the text frame rig.send() uses. A text frame carrying the same JSON is dropped silently — no error, no log. Use rig.send_module(0x218, {...}). This cost real time: text commands appeared to work only because the operator happened to be clicking the same controls in the GUI at the time.

5. Measured, NP1.0 on PXIe (2026-08-28)#

A different probe generation on a different transport, and the two terms this system owns are unchanged.

term NP2.0, OneBox (2026-08-25) NP1.0, PXIe (2026-08-28)
source_lag_mean_ms 1.00 ms 1.00 ms (mean 0.97, min 0.40, max 1.00, n = 23)
source_lag_max_ms — 2.40 ms median, 3.20 ms worst
audio_ring_depth_ms 15.11 ms 3.45 ms
output_latency_measured_ms 99.90 ms 18.87 ms
output_latency_ms (promised) 91.43 ms 120.00 ms
audio device MME → Sound Mapper (default) DirectSound → Primary Sound Driver
raw → ear ~116.0 ms ~23.3 ms
raw → eye 19.2 ms (n = 973, p95 20.3) 19.4 ms (n = 906, p95 20.2)

Audio ran on the right band, which is the precondition that makes the row mean anything: input_band = data.npx.ap, filtered = false, channel 19, 0 underflows, 0 starved callbacks.

What this settles#

The source lag does not depend on the transport. This was the one term expected to differ. PXIe delivers over the PCIe backplane and the OneBox over FT601 USB, in different block cadences, and the audio converter runs 1.00 ms behind the acquisition writer on both — same value to two decimals.

Nor does it depend on how the band is produced. NP1.0 hands the audio path a native AP band the probe has already high-passed and it is passed through unfiltered; NP2.0 has no AP stream and the audio processor derives the 300–6000 Hz band itself. That is a materially different amount of work on the same path, and it does not show up: 1.00 ms either way. The band-pass is simply not where the time goes.

The eye is the display cadence and nothing else. 19.4 ms against 19.2 ms, on a different probe, a different basestation and a different day.

Held the device fixed, and the ear is the same to 0.04 ms#

The first NP1.0/PXIe run came up on a different default device from the 2026-08-25 OneBox session, so its ear total could only say "the defaults differed". Re-measured across every output device on the rig, same probe, same session (2026-08-29):

idx host API device promised measured ring depth raw → ear
6 WDM-KS SPDIF Out (HD Audio SPDIF out) 11.00 ms 8.71 ms 3.04 ms ~12.7 ms
2 DirectSound Primary Sound Driver 120.00 ms 13.79 ms 33.33 ms ~48.1 ms
3 DirectSound Digital Audio (S/PDIF) 120.00 ms 18.87 ms 31.45 ms ~51.3 ms
0 MME Sound Mapper (default) 91.43 ms 98.08 ms 16.96 ms ~116.0 ms
1 MME Digital Audio (S/PDIF) 91.43 ms 99.72 ms 16.22 ms ~116.9 ms

Refused to open: WASAPI → Digital Audio (S/PDIF), index 4.

MME / Sound Mapper is the row that settles it. It is the device both original sessions defaulted to, and it reads 116.04 ms on NP1.0 + PXIe against 116.0 ms on NP2.0 + OneBox in §2. Forty microseconds apart, across a different probe generation and a different transport. source_lag is 1.00 ms on every device that opened, on both rigs.

So the ear budget contains nothing that belongs to acquisition. §2 argued that from the device spread on one rig; this is the same conclusion from the other direction, holding the device fixed and changing everything else.

The device list itself has changed since 2026-08-25 — six outputs now, nine then, with the NVIDIA/monitor entries absent — so the index numbers in §2's table do not correspond to these. Match rows by host API and device name, never by index. Individual fast devices also move run to run (DirectSound/Primary Sound Driver: 8.71 ms measured then, 13.79 ms now), which is what you would expect of a term dominated by host scheduling. The slow device is the stable one, and it is the one that matches.

A caution about the ear column. The NP2.0/OneBox row of the original summary quoted ≥ 92.4 ms, which is source lag + the promised output latency. §2 quotes ~116.0 ms for the same run: source lag + ring depth + the measured latency. Both describe one session. The measured form is the one this page argues for and the one used throughout above.

5b. What "promised" and "measured" actually are — and what neither of them is#

Added 2026-08-30, after the 100 ms gap between the two columns was (rightly) called suspicious.

"Promised" is a compile-time constant, not a device property#

Every DirectSound row in §2 reads exactly 120.00 ms. That is not a coincidence and not a device spec:

/* ext/portaudio/src/hostapi/dsound/pa_win_ds.c:159 */
#define PA_DS_WIN_WDM_DEFAULT_LATENCY_    (.120)

PaWinDs_GetMinLatencySeconds() → PaWinDS_GetMinSystemLatencySeconds() returns that constant for every Windows 2000+ system, for every DirectSound device, and it becomes defaultLowOutputLatency → our suggestedLatency → the stream's reported outputLatency.

So the device never promised 120 ms and never beat it by 100 ms. PortAudio's DirectSound backend simply does not report a per-device latency. (It is overridable by the PA_MIN_LATENCY_MSEC environment variable — which is the tell that it was always a knob, not a measurement.)

The earlier framing of this table as "advertised is anti-correlated with reality" was wrong in a way worth naming: a constant cannot be anti-correlated with anything. It carries no information.

"Measured" is better, and is still PortAudio grading its own homework#

output_latency_measured_ms is timeInfo->outputBufferDacTime - timeInfo->currentTime, read inside the callback — how far ahead of now this buffer is scheduled to be heard, on the host API's own clock. That is a real per-buffer quantity and it is the right one to rank by.

But it is still self-reported. For DirectSound it derives from the play cursor, whose granularity is coarse and which some drivers report optimistically. Nothing in this document has ever been checked against a microphone, a scope, or any instrument outside the process.

What that does and does not invalidate#

status
the ranking between host APIs, and therefore hostApiRank() and the device policy stands — every row is the same self-report mechanism, so the comparison is apples-to-apples
the relative claim "MME is 5–10× worse than anything else" stands, and it is the robust finding
the absolute raw → ear milliseconds unverified. It is a sum of self-reported terms, and it is quoted as though it were an acoustic measurement

How to actually settle it#

The same instrument-level method the competitor benchmark needs (#75): play a known impulse through the audio path and capture it externally — a microphone into a second DAQ channel, or a scope on the line output — alongside the trigger that produced it. One afternoon, and it converts the whole ear column from self-report into measurement. Until then, quote the ranking, not the absolute number.

5c. Measured, simulated NP1.0 on Linux / ALSA (2026-09-01)#

The first row from a different operating system and a different host API, taken during the issue #52 configuration-1 gate. No probe: Simulated NPX 1.0 (OneBox) on Linux Mint 22.1, PipeWire 1.0.5 presenting a PulseAudio server, PortAudio on ALSA. The source is simulated, so this row says nothing about any transport — which is the point. Everything upstream of the audio path is replaced, and the terms this system owns are asked whether they move.

term NP2.0, OneBox (Windows) NP1.0, PXIe (Windows) Sim NP1.0, Linux/ALSA
source_lag_mean_ms 1.00 ms 1.00 ms 1.08 ms (median 1.07, p5–p95 1.06–1.09, n = 20)
source_lag_max_ms — 2.40 ms 2.40 ms
audio_ring_depth_ms 15.11 ms 3.45 ms 6.67 ms
output_latency_measured_ms 99.90 ms 18.87 ms 14.20 ms
output_latency_ms (promised) 91.43 ms 120.00 ms 8.71 ms
audio device MME → Sound Mapper DirectSound → Primary Sound Driver ALSA default (PipeWire), 20 devices offered
raw → ear ~116.0 ms ~23.3 ms ~22.0 ms
raw → eye 19.2 ms 19.4 ms ~19–21.6 ms (see the caveat below)

available: true, input_band = data.npx.ap, filtered = false, 0 starved callbacks, 0 device underflows. Audio output works on this box; it is not merely "not fatal".

source_lag_mean_ms is 1.08 ms. Windows measured 1.00 ms on two transports and two probe generations; changing the operating system, the host API and the source moves it by 80 µs. That term is the application's, and it does not appear to be anything else's.

Promised is BELOW measured here, which inverts Windows. On Windows the promise over-stated the device on one row (91.43 promised vs 99.90 measured) and wildly over-stated it on the other (120.00 vs 18.87). ALSA promises 8.71 ms and delivers 14.20 ms. §5b's warning stands and generalises: the promise is a compile-time constant per host API, not a device property, and it is wrong in both directions depending on which host API you ask.

The raw → eye figure needs a caveat, and measure_av_latency.py currently gets it wrong on a multi-band config. The script's EYE median is computed over every binary frame, and this config publishes three — ap, lfp and adc — in one burst per display tick. Two of every three gaps are therefore intra-burst, and the reported median collapses to 0.6 ms, which is not a display cadence and must not be quoted as one. Counting frame sizes separates them: 139.06 frames/s over 3 distinct sizes = 46.35 publish ticks/s = 21.6 ms, median inter-tick gap 18.9 ms — i.e. the same ~19 ms as both Windows rows. The Windows rows were taken on configs where the burst was one frame, so the bug did not show. Fix the script to group by tick before quoting its EYE number on any multi-band profile.

Also found here#

ripple_tools/rig.py raises ValueError: I/O operation on closed file from its reader thread at teardown — the capture file is closed while _reader is still writing to it. It fires after the measurement, so it does not affect the numbers above, but it makes a clean run end in a traceback.
