SIMD dispatch — what AVX2 is worth, and when#

Issue #34 asked for runtime AVX2 detection with an operator override. This is what shipped, what it measures, and the one result that looked like a failure and was not.
Detection + tier src/core/CpuFeatures.hpp / .cpp
The dispatched filter src/core/Avx2Filter.cpp — addSample() picks addSampleAvx2() or addSampleScalar()
Build rule SPIKESPEAK_AVX2_SOURCES in CMakeLists.txt
Tests tests/test_cpufeatures.cpp, and tests/test_avx2filter.cpp run on both paths
Benchmark tests/bench_filter.cpp → build/tests/bench_filter.exe

1. The bug was the build, not the missing check#

Before this, the Linux build applied -mavx2 -mfma to the whole application target. GCC was therefore free to emit AVX2 anywhere — in Qt glue, in string handling, in code nobody wrote with vectors in mind. On a pre-Haswell CPU that binary does not degrade, it takes SIGILL, wherever the compiler happened to vectorize.

A runtime check added to a binary like that only moves the crash. So three things had to change together, none of which works alone:

  1. AVX2 applies to a named file list, so the rest of the binary is baseline x86-64.
  2. Every entry point into one of those files is guarded by useAvx2().
  3. The guarded paths have a scalar twin.

CpuFeatures.cpp is deliberately absent from that list: it is the thing that decides whether AVX2 is safe to execute, so it has to run where AVX2 is not.

Windows had the opposite situation and got away with it: no /arch flag at all, so MSVC emitted AVX2 only where somebody had written _mm256_* by hand — correct by accident, and only until someone added a flag.

CPUID is not sufficient#

XCR0 is checked too. A CPU can report AVX2 while the OS has not enabled YMM state saving, in which case the upper register halves are not preserved across a context switch. That does not crash — it computes wrong answers, intermittently, under load, which is strictly worse.

FMA is checked separately from AVX2, because Avx2Filter's inner loop is _mm256_fmadd_ps and they are separate CPUID bits.

2. The override#

SPIKESPEAK_SIMD=auto      the default: AVX2 when the CPU and OS both support it
SPIKESPEAK_SIMD=scalar    force the portable path — for A/B, or to bisect a numerical difference
SPIKESPEAK_SIMD=avx2      require it; falls back with a warning if the CPU cannot

Requesting avx2 on a machine that cannot run it falls back rather than refusing to start. An acquisition system that will not launch is worse than one that launches slower.

3. What it is worth: about 3× in the filter#

tests/bench_filter.cpp runs 384 channels through the LFP preset (2nd-order Bessel IIR). It measured 2.89× when this page was written, 3.10× once the dispatch was hoisted out of addSample, and 3.15× at the last measurement — useAvx2() was a Meyers singleton in another translation unit, so a per-call check was a real cross-TU call, not the "load of a cached bool" the header claimed. Reading the tier once into a namespace-scope const bool bought 10 % on the vector path.

The current table lives in Profiling.md §4 and is maintained there, because that page is overwritten in place rather than appended to: a superseded performance number is not history, it is a wrong answer that still reads like a right one.

The benchmark is built with the suite so it cannot rot, but is not registered with ctest: it is a stopwatch, not an assertion, and a benchmark in the gate is a flaky test waiting for a busy machine. The tier is decided once per process by design, so it measures whichever tier it resolved to — run it twice. It links Qt6::Core, and only ctest-registered suites get the Qt PATH injected, so run it the way Profiling.md §5 shows or it dies on Qt6Core.dll.

4. The result that looked like a failure — and was a measurement, not a result#

This section used to report a null result end to end on NP1.0, and it was wrong. Reversed 2026-09-01. The whole-backend comparison read 1.022 vs 1.019 cores from n = 2 and was written up as "no difference at all". Re-run at --simd-reps 6, interleaving the two tiers so drift cannot be blamed on the flag, it is 1.020 vs 1.065 — 4.5 percentage points of one core, with ranges that do not overlap: the slowest AVX2 run beats the fastest scalar one. The current numbers are in Profiling.md §4.

The explanation was worse than the number. The null was justified by a real mechanism — NP1.0 takes its LFP band from the probe, so proc.lfp is never provisioned (ProcessorManager requires data.npx.raw and no data.npx.lfp) and the ripple detector filters only its handful of detection channels. All true, and all irrelevant to the conclusion, because the filter was never the only consumer of the dispatch: DisplayProcessor.cpp:561 calls calcMinMaxAvx2 for the per-channel display min/max, on every configuration that draws anything. There was never a reason to expect zero.

The NP2.0 prediction stands and is still the sharper case — NP2.0 has no hardware LFP, so proc.lfp derives it, 384 channels of IIR per sample — but the one +3.8 pp figure this page used to quote for it came with no artifact and no command, so it is an anecdote until somebody re-runs it the way Profiling.md §4 sets out.

Two lessons, and the second is the one that generalizes. A conclusion from n = 2 is a conclusion about an afternoon; --simd-reps exists so a claim here can be made at a rep count that supports it. And "no difference, and here is the mechanism" is a dangerous shape — the mechanism makes a wrong number feel explained, and an explained number is one nobody re-measures. An end-to-end measurement answers "does this matter in this configuration"; the microbenchmark answers "does this matter". Both belong in the record, and neither alone is the story.

5. The gate runs both paths, and this was not optional#

scripts/run_tests.py runs the whole C++ suite a second time with SPIKESPEAK_SIMD=scalar.

Demonstrated rather than assumed: an off-by-one deliberately injected into the scalar twin left the whole C++ suite green, because this machine has AVX2 and never executes that body. The forced pass failed instantly and named the divergence.

A single run is not a statement about the code — it is a statement about the CPU the run happened on. The fallback path is what executes on a machine without AVX2, and this is the only coverage it can ever get on a machine that has it. The second pass costs ~1.6 s.

The pass is skipped when the machine has no AVX2 to disable, and says so rather than implying it proved something.

6. Adding another dispatched routine#

  1. Put it in a file on SPIKESPEAK_AVX2_SOURCES.
  2. Give it a scalar twin over the same state. Avx2Filter's twin is a transliteration sharing mX/mY, so the filter's history lives in exactly one place; a twin with its own state is a second history to keep in step by hand.
  3. Guard the entry point with useAvx2(). The branch is a load of a cached bool and is perfectly predicted — do not reach for a function pointer, which costs an indirect call and hides both bodies from the inliner.
  4. Cross-check the two against an independent implementation if one exists. tests/test_avx2filter.cpp checks Avx2Filter against the separate scalar SpikesPeak::Filter, so the scalar pass proves the twin against a third party rather than against itself.
  5. Do not call useAvx2() per sample. It is cheap, but a branch that can be hoisted out of a 30 kHz loop belongs outside it.
