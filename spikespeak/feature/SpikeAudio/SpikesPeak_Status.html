1. ARCHITECTURAL OVERVIEW#

SpikesPeak is a modular C++20/Qt6 backend with a JavaScript/SciChart frontend that runs in an EXTERNAL browser: the backend serves the UI over HTTP :8080 and opens the system browser; all backchannel traffic rides ONE WebSocket on :1234, triple-multiplexed into (a) a binary waveform stream, (b) JSON app commands, and (c) Qt QWebChannel RPC. Per-source controls (the IMRO editor) are Q_INVOKABLE methods on the source object, exposed over QWebChannel. Full detail: developer_docs/SpikesPeak_Architecture_Review.md.

2. FEATURE GOAL#

Interactive Neuropixels channel-map (IMRO) configuration from the browser UI: visualize the probe, select which electrodes/channels to record, load/save .imro files, and push the map to hardware. Focus so far: Neuropixels 1.0 (960 electrodes -> 384 read-out channels). NP2.0 multishank is next.

3. NEUROPIXELS 1.0 ELECTRODE MODEL (implemented)#

  • 960 physical electrodes feed 384 read-out channels by modulo-384 wiring: channel C = electrode % 384 ; bank B = floor(electrode / 384) ; electrode = C + 384*B.
  • Each read-out channel carries exactly ONE electrode, so selecting an electrode for channel C deselects its bank-siblings automatically (the model is 384 channel objects, one bank each).
  • Bank 2 is a HALF-bank: electrodes 768-959 only => valid for channels 0-191 only (191 + 384*2 = 959 exists; 192 + 768 = 960 does not).
  • RESERVED channel 191: its three bank electrodes (0-indexed 191/575/959 = the manual's 1-indexed 192/576/960, spaced 3.84 mm) are the internal-reference sites, not recording electrodes. The UI draws them amber and blocks selecting them; applyImroToHardware skips np_selectElectrode for 191.
  • Reference IDs: {0=ext, 1=tip, 2..4=on-shank-ref at banks 0/1/2}; applyImroToHardware maps these to EXT_REF / TIP_REF / INT_REF(bank). The .imro NP1 entry is: (channelID bank refID apGain lfGain apFilter)

4. C++ BACKEND (implemented, NpInterface.cpp/.hpp)#

  • Data model ImroTable / ImroChannel (inline-initialized; no indeterminate fields).
  • SIX Q_INVOKABLE methods on NeuropixelsSource, all reached over QWebChannel: getImroAsJson() - serialize current map -> JSON for the UI getImroAsImroText() - serialize current map -> .imro TEXT (browser downloads it; the UI Save) updateImroFromJson() - validate + atomically replace the map (channel/bank range + NP1 electrode-existence checks; rejects bad payloads without corruption) applyMapToHardware() - push current map to the API + np_writeProbeConfiguration loadImroFromText(text) - parse .imro file CONTENTS (read client-side by the browser) into the map saveImroToFile(path) - SERVER-SIDE write to an explicit path (programmatic; not used by the UI)
  • IMRO parsing refactored: parseImroFile() (reads a file) -> parseImroContent() (parses a string). The parser parses into LOCALS, validates, then commits ATOMICALLY -- this fixed a latent bug that corrupted mCurrentImro on a failed/incompatible load (it overwrote the header before the probe-type check). NP1 entries are range-validated (channel in [0,384), electrode < 960).
  • Hardware abstraction: np_selectElectrode / np_setGain / np_setReference / np_setAPCornerFrequency, with every return code checked; channel 191 electrode-selection skipped (reserved; constant kNp1ReservedChannel).
  • Lifetime/safety hardening from the 2026-06-22 review applied (worker teardown + wait, member init, leak-free init-failure paths, per-instance scratch buffer, etc.).

5. JS FRONTEND (implemented, ImroManager.js)#

  • SciChart probe map: dark-mode WebGL scatter of the NP1.0 geometry; green = selected recording electrode, gray = available, amber = internal-reference site (191/575/959).
  • Selection (all honor the modulo-384 rules; reserved channel 191 is never modified):
    • CLICK an electrode -> route its channel to that electrode's bank (siblings auto-deselect).
    • DRAG a vertical box -> select a contiguous 384-electrode window (always a valid full map).
    • Bank 0/1/2 presets (Bank 2 = half-bank: channels 0-191 -> bank 2, 192-383 -> bank 0). Edits push to C++ via updateImroFromJson() and re-render WITHOUT re-zooming (no view jump).
  • Apply Map button -> applyMapToHardware() (Q_INVOKABLE).
  • Save .imro button -> getImroAsImroText() -> the browser downloads the .imro CLIENT-SIDE (Blob). No server dialog (symmetric with Load). main.cpp sets quitOnLastWindowClosed(false) defensively.
  • Load .imro button -> browser reads the file CLIENT-SIDE, hands the text to loadImroFromText(); on success the UI re-fetches + re-renders (auto-zoom to the loaded block) so the loaded channels light up. Load does NOT auto-apply -- the user clicks Apply to push to HW.
  • Handshake: NetworkClient waits for the C++ deviceReady event before binding QWebChannel, then binds window.activeNpxModule by registry-name substring ("npx").

6. KEY ARCHITECTURAL DECISIONS#

  • Per-module commands ride QWebChannel Q_INVOKABLE (Option A): each source registers its own object and exposes its own invokables, so new modules (e.g. a camera) need no central command-router edit. The legacy handleWebCommand JSON path was removed (it was dead + unreachable).
  • FILE I/O STANDARD (external-browser architecture) -- now documented in developer_docs:
    • READ a file -> do it CLIENT-SIDE in the browser ( + FileReader) and pass the TEXT to a synchronous C++ Q_INVOKABLE parser. No server dialog, no event-loop re-entrancy. Reference implementation: Load .imro -> loadImroFromText().
    • WRITE a file -> CLIENT-SIDE too: a Q_INVOKABLE returns the file TEXT and the browser downloads it (Blob + ). No server dialog. Reference: Save .imro -> getImroAsImroText(). (A server-side modal dialog in a Q_INVOKABLE crashed -- nested loop re-entering QWebChannel -- and once deferred it EXITED the app: the dialog was the windowless server's only window, tripping quitOnLastWindowClosed. main.cpp now sets quitOnLastWindowClosed(false) defensively.)

8. LIVE DATA VIEW: DEPTH / SHANK / COLUMN + APP LIFECYCLE (this session, 2026-06-24)#

Full detail + the data-plane contract: developer_docs/LiveDataView.md.

  • The streaming waveform view now orders traces by DEPTH using the APPLIED map. Each read-out channel gets a global SLOT = its rank sorted by (shank ASC, column ASC [L before R], row ASC [deep first]), where for a within-shank electrode e: column = e&1 (even=Left, odd=Right), row = e>>1 (row 0 = tip). yOffset = slot*spacing on a NORMAL y-axis, so the TIP (deepest) sits at the BOTTOM, shallower upward.
  • Traces are labeled by ELECTRODE + side, e.g. "100L" (hover shows shank / column / read-out channel). This fixed the earlier "scrambled, non-monotonic" labels (channel order != depth order for mixed maps).
  • PER-COLUMN FILTERS: each display column has TWO dropdowns -- Shank (one entry per shank; DISABLED for NP1's single shank) and electrode column (L+R / Left / Right). The column zooms its y-axis to that contiguous slot BAND; the slider scrolls within the band. Set col1=Left, col2=Right to see both physical columns side-by-side. Non-probe sources hide the dropdowns and fall back to channel order.

Because "L+R" needs a DIFFERENT order than L/R-only (interleaved vs packed), each channel now carries TWO series -- a PACKED one (dataSeries; L/R views, depth-sorted) and an electrode-INTERLEAVED one (dataSeriesInterleaved; the L+R view, ordered 0L,1R,2L,3R...). Remaining deliberate limit: no "all shanks" option (each column = one shank); a third ordering would need per-column data (see developer_docs/LiveDataView.md S5).

CALIBRATION (2026-06-26): the per-probe ADC + gain CSVs are VENDORED locally at /CalibrationInfo (copied from the OpenEphys install, deployed next to the exe by POST_BUILD). NpInterface.cpp resolves them via QCoreApplication::applicationDirPath()/../CalibrationInfo//_{ADCCalibration,gainCalValues}.csv -- the same convention as config/. Was a hardcoded OpenEphys absolute path. UPDATE (2026-06-26, per user): the OpenEphys FALLBACK was REMOVED (it only ever resolved on one machine). If a probe's local CSVs are missing, NpInterface.cpp now qCritical-logs AND emits IDataSource::sigGuiStatus, which WebSocketServer relays as a {"event":"guiStatus","kind":"error"} message -> the red toolbar status in the GUI (NetworkClient -> window.guiStatus). The emit is DEFERRED (QMetaObject::invokeMethod queued) so it lands after onSourceSelection has registered the source + connected sigGuiStatus. sigGuiStatus is a new, reusable C++ source -> GUI alert channel on IDataSource (parallels the recorder's recordingStatus relay).

9.2 ACQUISITION WORKER -- Npx1Probe (NpInterface.cpp ~247-379)#

  • startAcq() spawns a QThread + Npx1Probe worker (HighPriority); a Qt::PreciseTimer at 1 ms drives slDoAcquireDataLoop; np_setSWTrigger(mSlot) starts hardware streaming. State -> eStreaming.
  • Each tick: np_readElectrodeData into a PER-INSTANCE scratch (mSuperframes, up to 64 superframes; was a static local -> made per-instance for safety). NP1 superframe = 12 AP timestamps + apData[12][384] + lfpData[384] + Status[12].
  • DEMUX: per superframe, write 1 LFP sample (384 ch) to the LFP buffer and 12 AP samples (384 ch each) to the AP buffer, each with PacketInfo (Timestamp/Status); commitWrite(producerId, 12) AP and (...,1) LFP per superframe; write indices advanced modulo capacity (guards mid-copy wraparound).
  • stopAcq(): emit sigNpsRequestDaqStop -> worker stops the timer; thread quit + wait(2s); np_arm(mSlot) flushes the hardware buffer; worker/thread pointers nulled (Qt deletes via finished()).

9.3 DUAL STREAMS + DISPLAY#

  • NP1 produces TWO buffers: data.npx.ap (30 kHz) and data.npx.lfp (2.5 kHz), both CircularBuffer. (NP2 uses a single data.npx.raw.)
  • proc.npx.display (DisplayProcessor) consumes each and emits per-pixel min/max-decimated batches to the browser; proc.npx.recorder records them (Task 2).

9.4 GAIN / REFERENCE / FILTER MAPPING (applyImroToHardware + getGainIndex)#

  • getGainIndex: gain VALUE -> API index {50:0,125:1,250:2,500:3,1000:4,1500:5,2000:6,3000:7} (default 500 -> 3).

11.1 GENERIC, PLUGGABLE RecordProcessor -- "record whatever, given a data interpreter"#

  • PROBLEM: RecordProcessor is effectively single-purpose today. Although it already delegates the byte layout to an IDataInterpreter, the interface + the processor bake in NPX/flat-stream assumptions: RecordProcessor itself owns the QFile + QDataStream and the [uint32 ts][uint16 sync][int16 x 384] 774-byte shape lives in NpxDataInterpreter::serializeAvailableData(QDataStream&, QVector filter). That fits NPX (and would fit NIDAQ analog), but NOT a camera (variable-size frames -> a video container + a timestamp sidecar, which a single flat QDataStream cannot express).
  • GOAL: RecordProcessor records ANY module's data -- NPX AP/LFP now; NIDAQ auxiliary inputs, a camera module, or anything else later -- driven entirely by a per-module IDataInterpreter that knows that module's data shape AND its on-disk format. RecordProcessor stays format-agnostic ("logs whatever").

  • THE PATTERN TO MIMIC = NeuropixelsSource's multi-probe design (S9.1-9.2): NeuropixelsSource (one IDataSource) detects ProbeType and drives a POLYMORPHIC IDataSourceWorker (Npx1Probe / Npx2MSProbe), each worker knowing exactly one probe's acquisition. The recording analog: RecordProcessor (one IProcessor) drives a POLYMORPHIC IDataInterpreter per configured recording (NpxDataInterpreter / NidaqDataInterpreter / CameraDataInterpreter), each knowing exactly one module's serialization. The interpreter is to RecordProcessor what the probe worker is to the source.

  • THE EXACT LAYERED STRUCTURE (three layers): LAYER 1 -- RecordProcessor (generic orchestrator; format-agnostic). Owns ONLY: the worker thread + poll timer, the list of active recordings, and the Start/Stop lifecycle (setRecording). On Start -> tell each interpreter to begin; each tick -> tell each to flush; on Stop -> tell each to end. Knows NOTHING about channel counts, sample widths, file layouts, or stream types. (Moves the QFile/QDataStream/774-byte ownership it has today DOWN to Layer 2.) LAYER 2 -- IDataInterpreter subtype (per-module; the pluggable format+SINK layer; the analog of the per-probe worker). One concrete class per data kind, shipped by the owning module and registered by name "interp..". Each one OWNS ITS OWN OUTPUT TARGET, so a recording can be a single binary file, OR a binary + a .meta sidecar, OR a video container + a timestamp index -- whatever that data needs. Knows: which registry data object/CircularBuffer it reads, the sample shape, the serialization, and the metadata header. LAYER 3 -- the data object (CircularBuffer or other) the source produced. Unchanged; the interpreter binds to it by registry name in configure(), exactly as today.

  • REQUIRED INTERFACE CHANGE (IDataInterpreter): generalize from "write samples into a QDataStream the processor handed me, filtered by a QVector of channel indices" (NPX-flavoured; one flat stream) to an OUTPUT-OWNING lifecycle. Target contract (names illustrative): bool configure(cfg) // bind data object + per-recording config (filename, filter, rate) bool beginRecording(QString basePath)// interpreter OPENS whatever files/containers it needs void writeAvailable() // pull new samples from its buffer and append (replaces // serializeAvailableData(stream, filter)) void endRecording() // flush + close ALL its outputs void updateReadMarkers() // unchanged: advance read index while idle QString describeFormat() [optional] // emit a sidecar header (rate, N, probe, IMRO, dtype) -- // also closes the "no metadata header" gap (Recording.md S5) The QDataStream and the QVector filter become INTERNAL details of interpreters that want them (NPX, NIDAQ analog); a camera interpreter ignores both and writes frames its own way.

  • PER-MODULE INTERPRETERS (examples that motivate this): interp.npx.ap / interp.npx.lfp (EXISTS, NpxDataInterpreter) -> [uint32 ts][uint16 sync][int16 x384] (+ a future .meta sidecar) interp.nidaq.analog / .digital (FUTURE, NidaqDataInterpreter)-> NIDAQ aux inputs in NIDAQ's own layout (timestamp + per-channel f32/uint, its own channel count) interp.camera.frames (FUTURE, CameraDataInterpreter)-> a video container (or per-frame files) PLUS a [frame#][hw-ts][sync] index sidecar so frames align to the neural clock

  • WIRING (already this generic -- no central edit needed): config/.yaml proc..recorder lists "recordings:", each = { data_name, data_interpreter_name, output_filename [, channels, rate] }. To record a new stream: add a recordings: entry naming the new interp.*, and registerDataInterpreter <...>("interp..") in Utils.cpp. RecordProcessor needs NO edit -- same "add a config entry, nothing central to touch" property the source/QWebChannel command side already has.
  • NET: RecordProcessor sheds all NPX specifics; each module ships an interpreter describing how to log its data; recording works for any module that provides one. Until built, behaviour is unchanged (NpxDataInterpreter keeps working as-is). When built, extend Recording.md (format-per-interpreter) and AddingASinkModule.md (how to add an interpreter).

11.2 SINK COMMAND THREADING -- main-thread handle + worker behind it (removes the QWebChannel marshal)#

  • CONTEXT: developer_docs/ModuleCommunication.md S5. QWebChannel invokes Q_INVOKABLEs synchronously on the GUI/transport thread (DirectConnection, so it can return values), NOT the object's own thread. Because ProcessorManager moveToThread's the ENTIRE IProcessor onto a worker thread, a sink's invokable (e.g. RecordProcessor::setRecording) lands on the wrong thread and must marshal back with QMetaObject::invokeMethod(..., Qt::QueuedConnection) -- a wart repeated on every sink invokable.
  • LONG-TERM FIX (the agreed direction): mirror NeuropixelsSource, where the QObject the browser talks to lives on the MAIN thread and only an acquisition WORKER (IDataSourceWorker) lives on its own thread. Apply the same handle/worker split to sinks:
    • The IProcessor "handle" -- config + Q_INVOKABLE command surface + QWebChannel registration -- stays on the MAIN thread.
    • The data loop (timer/poll or blocking consume) runs on a WORKER moved to its own thread (an IProcessorWorker, analogous to IDataSourceWorker).
    • Commands then run on the main thread NATURALLY (no marshal in the invokable) and reach the worker via ordinary queued signals/slots -- the explicit, idiomatic cross-thread hop -- with each piece of shared state owned by exactly one side. COST: a ProcessorManager refactor + splitting each processor into handle+worker (RecordProcessor, DisplayProcessor, RippleDetector). Large, but it removes the footgun for ALL sinks and makes sink commands look exactly like source commands. (This pairs naturally with 11.1 -- do them together: the generic RecordProcessor handle on the main thread, its interpreters/worker doing the writing.)
  • INTERIM (optional, if we want the wart gone sooner): a one-line IProcessor helper runOnSelf(functor) wrapping the QueuedConnection marshal (ModuleCommunication.md S5 option A). Keeps it lock-free, hides the boilerplate. Not a substitute for the split -- just nicer until then.

New firmware esp32s3eth_am2300_pulsegenerator/ for the Waveshare ESP32-S3-ETH (W5500 Ethernet), giving a second, interchangeable AM Systems 2300 stim server. Why a new file rather than editing esp32s3_pulsegenerator/. 27.2 Where the time goes (n=1000, live Pi, simulation)#

Our compute is free: filters+FSM 2 us, dispatch 4 us. The dominant local term was the detector backlog: median 400 us, max 2000 us, quantised to exact multiples of 400 us = one NP1 LFP sample period. That is the signature of BLOCK DELIVERY: sources commitWrite(n) a whole block and waitForAvailable() drains it, so the oldest sample in a block of N is already (N-1)x400 us stale before any consumer can see it.

Correction to an earlier claim in this project: "have the detector process the newest sample first" was WRONG and would have made things worse -- the detector already processes oldest-first within microseconds of arrival, and cannot skip samples (the FIRs are stateful). The staleness is created UPSTREAM by delivery granularity and cannot be recovered downstream.

27.3 The ASAP flag -- opt-in, per-source#

low_latency: true on a SOURCE node makes it deliver in the smallest blocks the clock allows (SimulatedDataSource::initDataSource -> SimNpx1Worker::setLowLatency, production tick 1 ms -> 0). Default unchanged, so no existing config moves; only configs that actually close a loop pay the CPU.

A/B, n=1000 each (SimNpx1LatencyBaseline vs SimNpx1LatencyAsap, identical but for the flag):

stage (median us) baseline ASAP change
detector backlog 400 (max 2000) 0 (max 400) eliminated
sample -> quorum 2 5 +3
detect -> datagram out 4 12 +8
datagram -> ACK 1312 830 -482
TOTAL detect -> ACK 1316 840 -476 (-36%)
spread (sd) 431 129 3.3x tighter

Caveat, stated so the number is not oversold: the datagram -> ACK gain is not all real stimulus speed-up. The ACK is timestamped in onReadyRead, which runs during processEvents() BETWEEN batches, so with 1 ms batching the backend could sit on an arrived ACK before noticing it. The ai4 edge is unaffected by when we notice the ACK. The defensible claim for the closed-loop definition is the backlog: ~400 us median (up to 2 ms) removed -- ~15% of the measured 2.60 ms.

  • device_us is unpopulated: the stock Pi replies with a bare fired. The backend already parses fired <us>, and the ESP32 firmware already computes it, so one line on either device would split "network" from "stimulator execution".

29.2 A SECOND sync off-by-one — the wrap bug (np1_4ch_q3_asap)#

One of the four recordings came back with 257 of 995 pulses unpaired and a physically impossible 0.433 ms minimum. It was NOT the hardware and NOT a repeat of the 2026-07-17 match="end" bug.

When the NI-DAQ drops a sync pulse at the start of the train, both the start- and end-anchored offsets in _pair_edges_auto are wrong by a whole period (measured: off_start=+0.950 s, off_end=+1.950 s), so picking the smaller-magnitude one still shifted every NI-DAQ timestamp by exactly 1.000 s. Sync diagnostics look perfect either way — 617 pulses, 9.78 ppm, 0.012 ms residual.

Fix: reduce the coarse offset modulo the sync period into (-ipi/2, +ipi/2], with a warning when it fires (python/spikespeak_postprocess/sync.py). Two clocks started by one host command are offset by milliseconds; any whole-period component is a pairing artefact. After the fix: unmatched 257 → 0, median 0.963 ms, and the three healthy recordings are bit-identical to before.

How it was caught, and the generalisable lesson. The measured detection→pulse offset was 1001.0 ms with a p5–p95 spread of only 0.3 ms — 1.000 s plus the true ~1 ms latency. On a strictly periodic 500 ms stimulus train a whole-period shift still pairs every pulse to a detection at ~1 ms and looks perfect. It only became visible at the aperiodic landmarks — the ~1.6 s gaps between ripple bursts, where the last two pulses of each burst had no detection. Never validate a periodic signal by nearest-neighbour pairing; anchor on the aperiodic structure. Both plotting scripts and the analyzer now cross-check burst-anchored against nearest-before pairing, and they agree on all nine recordings.

35.1 Why OneBox is a separate source class, not a config flag#

OneBox is the USB (FTDI FT601) sibling of the PXIe basestation: same IMEC NeuropixAPI v4, same probe workers, same CircularBuffer streaming — but a different enumeration and open path, plus hardware PXIe does not have (a 12-ch ADC, a DAC/WavePlayer, its own switch matrix). NpInterface.cpp was already ~2 k lines, so OneBox went in its own pair:

  • src/modules/neuropixels/OneBoxSource.{hpp,cpp} (NEW, 105 + 380 lines) — class OneBoxSource : public NeuropixelsSource. Everything probe-side is inherited; only basestation-specific behaviour is overridden.
  • NpInterface.{hpp,cpp} grew two virtual hooks whose defaults are the existing PXIe behaviour, so the PXIe path is untouched by construction:
  • virtual bool openBasestation() — default: PXIe scan/open. OneBox: np_checkFtdiDriver → np_scanBS → pick the device whose basestationID.platformid == NPPlatform_USB → np_mapBS(serial, 16) → np_openBS.
  • virtual int detectProbePort() — default: the PXIe np_openPort-gated sweep of ports 1–4. OneBox: ports 1–2.
  • Members moved private → protected; initBasestation() STEP 1/STEP 2 now call the two hooks.
  • initDataSource now calls closeDataSource() when initBasestation() fails, so a failed attempt does not leave the device half-open.
  • Registry (src/core/Utils.cpp): source.npx.onebox, data.npx.adc, interp.npx.adc.
  • Configs: config/Npx1OneBox.yaml, config/Npx2OneBox.yaml (NEW). config/OneBoxTest.yaml DELETED — it was a phantom source (referenced an unregistered type, so selecting it only produced the "not supported" dialog).
  • GUI: two new source options, NPX 1.0 (OneBox) / NPX 2.0 Multishank (OneBox).

Driver: OneBox needs FTDI D3XX 1.3.0.10 — not the 1.4.0.x line. Installed by the maintainer this session. Status LED: red = idle / not opened, green = opened. The OneBox lives at virtual slot 16.

35.2 The connect bug: PXIe gates ports with np_openPort, OneBox does not#

The first hardware attempt failed with "No Headstage detected on any port". Root cause: the initial implementation reused the PXIe port sweep verbatim, and OpenEphys's OneBox.cpp calls np_detectHeadStage directly on ports 1–2 — np_openPort is a PXIe-only call and is absent from their OneBox path. That is exactly what detectProbePort() exists to express.

Worth recording because it contradicts the reference: on this OneBox, calling np_openPort best-effort before detectHeadStage is what actually works — detection succeeds on attempt 0 with it. The override therefore does best-effort np_openPort + np_detectHeadStage, wrapped in a retry loop (8 × 500 ms) because the headstage is not always up the instant the basestation opens. Verified live: [OneBox] Auto-detected Headstage at Port: 1 (attempt 0).

35.3 ⚠️ SAFETY — the "bricking" bug, and how OneBox must be closed#

Several times the OneBox came back blinking red with np_scanBS finding nothing — it looked bricked. Two independent causes, both now fixed, both worth knowing:

  1. Hard-killing the backend. The FTDI handle is released only on a clean exit. TaskStop / Stop-Process / taskkill on a backend with an open OneBox leaves the device claimed. This is the same rule already in force for the PXIe probe + NI-DAQ: always shut down via the WS Disconnect/quit path. Force-kill is sim-only.
  2. The close sequence itself was wrong. closeDataSource had been left on the inherited PXIe path, which routes SM_Output_SMA <- SM_Input_PXI0 — i.e. it drives the OneBox's SMA line. The maintainer asked directly whether this matched OpenEphys; it did not. OneBoxSource::closeDataSource now mirrors OneBox.cpp: ADC off → setSyncAsInput() (clear the StatusBit + SMA outputs, then StatusBit <- SMA) → closeProbe → closeBS → np_unmapBS. It deliberately does not call the base implementation.

The maintainer confirmed OpenEphys re-opened the device stably green afterwards — i.e. the device was in a bad configuration, never damaged. Connect → disconnect → reconnect is now verified repeatedly.

35.4 The 12-channel ADC as its own stream#

Decision (maintainer): the OneBox ADC is a stream alongside NI-DAQ, not a replacement — NI-DAQ stays for PXIe rigs and is not wired to the OneBox.

  • OneBoxSource::initDataSource does the base init, then np_ADC_enableProbe, np_ADC_setVoltageRange(ADC_RANGE_5V), and logs np_ADC_getStreamConversionFactor.
  • The ADC runs on its own QThread with its own worker (OneBoxAdcWorker), independent of the probe workers; startAcq/stopAcq own its lifecycle.
  • DisplayProcessor.cpp: num_channels is now per-stream configurable. It was hardcoded 384 in two places (the calcMinMax AVX loop — which also needed a scalar tail — and the advanceBucket serialisation). A 12-channel stream was impossible before this.

  • ChartColumn.streamLabel gained adc: 'OneBox ADC'.

36.1 Simulating OneBox vs PXIe: only the ADC differs#

Asked directly whether a simulated OneBox differs from a simulated PXIe basestation. For the probe stream it does not -- once a basestation is open the path is identical (same Npx1Probe/Npx2MSProbe workers, same IMRO pipeline, same data.npx.ap/lfp/raw). That is precisely why the real OneBoxSource inherits all of it and overrides only how the basestation is FOUND and CLOSED (S35.1) -- and those overrides are pure IMEC-API calls (np_checkFtdiDriver, np_mapBS, setSyncAsInput) that a sim never performs, so "simulating" them would exercise nothing.

What OneBox genuinely adds, data-wise, is the 12-channel ADC. So that is the only new sim class, and the simulated OneBox is composed, not subclassed: the existing sim probe (source.npx.simdata / source.npx.sim2, untouched) + the new ADC source, wired together in YAML. Same shape as how source.nidaq.sim composes with a probe sim. The DOWNSTREAM wiring -- data.npx.adc, interp.npx.adc, the 12-trace display band, the recorder -- is what the real OneBox config uses, and that is the part worth exercising. (data.npx.adc + interp.npx.adc were already registered OUTSIDE the NPX_HW_ENABLED guard, so no registry change was needed.)

  • src/modules/neuropixels/SimOneBoxAdcSource.{hpp,cpp} (NEW) -- source.npx.simadc. Worker on its own QThread, wall-clock paced like SimNpx2Worker, writing int16 + PacketInfo into data.npx.adc. Built unconditionally (NOT behind NPX_HW_ENABLED), so it works on Linux / sim-only too.
  • Signal model, in volts, quantised with the hardware's own 5 V/32768 factor so a volt lands on exactly the count the real device would produce: ch0 = 0/3.3 V TTL square (the standalone "ADC" SMA), ch1 = GROUNDED (noise floor only -- the same visible contrast as grounding an input on the rig), ch2 = slow DC drift, ch3 = 50 Hz mains + harmonic, ch4+ = sines spread 1 Hz..1 kHz. Gaussian noise floor on every channel. All knobs YAML-editable.
  • config/SimNpx1OneBox.yaml / config/SimNpx2OneBox.yaml (NEW) -- both appear in the GUI "Simulated Data" picker as Neuropixels 1.0 / 2.0 Multishank (OneBox + ADC).

37. TWO BASESTATIONS ON ONE HOST: THE np_tryGetSlotID BOOL TRAP + BASESTATION RELEASE (2026-08-18)#

Swapping the NP2.0 probe from the OneBox back to the PXIe chassis failed to connect. Two independent problems were stacked, and the software one had been latent in the repo for a long time.

37.1 ROOT CAUSE -- np_tryGetSlotID returns a bool, and the test was inverted#

NP_EXPORT bool NP_APIC np_tryGetSlotID(const basestationID* bsid, int* slotID);

It returns bool, not NP_ErrorCode. The slot search tested errorCode == Neuropixels::SUCCESS, i.e. compared that bool against 0 -- exactly inverted. A successful lookup (true) FAILED the test; a failed lookup (false) PASSED it.

This was harmless for as long as only PXI devices were ever attached, which is why it survived: the API writes the slot through the pointer regardless, so the loop simply never broke and detectedSlot was already correct by the time it fell out. Attaching a OneBox is what broke it -- the OneBox returns false, matched == SUCCESS, and broke the loop on the first device with no slot resolved. Because it depended on device enumeration order it would have looked intermittent and unrelated to the OneBox. The give-away in the log was a contradictory pair:

[MAIN]: Note single basestation supported only. Search stopped at first detected slot.
[MAIN] ERROR: Failed to resolve a physical PXI Slot ID!

The same trap appeared a second time in the new release helper (§37.2) and was caught the same way -- Unused PXI device (ID 0) has no resolvable slot while the slot was plainly resolvable. Worth remembering: in this API most calls return NP_ErrorCode, but np_tryGetSlotID returns bool.

The search now also skips non-PXI devices outright and requires an actually-valid slot before accepting it, so a second basestation can neither be mistaken for ours nor abort the search.

37.2 Releasing the basestation this profile will NOT use#

Maintainer's directive: "we can have multiple but keep searching for the right one. close the one that's not going to be used... which one is used is based on the config file."

New NeuropixelsSource::releaseForeignBasestations(NPPlatformID_t keepPlatform), called from BOTH openBasestation() implementations -- the PXIe path keeps PXI, OneBoxSource keeps USB -- so the config (source.npx.pxi vs source.npx.onebox) decides which basestation is ours and everything else is handed back. Best-effort throughout; nothing in it is fatal to our own connect.

  • USB (OneBox): it has no physical slot, so it must be mapped to a virtual one before it can be addressed at all. Map -> setSyncAsInput (clear the StatusBit + SMA outputs, then route StatusBit <- SMA) -> closeBS -> unmapBS. The SMA step is NOT optional: closing a basestation does not turn off its SMA output, so a OneBox released without it can be left DRIVING that line -- the bad-configuration state from S35.3. Never route SMA <- anything here.
  • PXI: resolve the slot, closeBS.

Confirmed on hardware in both directions:

[MAIN] Released unused OneBox (USB, ID 25420802) -- SMA set to input, basestation closed, virtual slot freed.
[MAIN] Released unused PXI basestation at slot 3 , closeBS code: 0

The maintainer confirmed the OneBox status LED goes green after the release, i.e. it is genuinely handed back rather than left claimed.

37.3 The other half: the chassis was not enumerated at all#

Before any of the above could be judged, the PXIe module had to actually exist on the bus. It did not:

[MAIN] scanBS enumerated 1 basestation(s):
[MAIN]   device 0 platformid 2 (USB/OneBox) ID 25420802

Windows had no imec device either (the only driverless PCI entries were Intel chipset parts), so this was never a software problem. "No PXI basestation on the bus" (chassis / cabling / boot order, and the message says so) now reads differently from "a PXI device is present but its slot is unresolvable" (seating). The old single message pointed at seating for both and sent the investigation the wrong way.

38. TOOLBAR RELAYOUT + THE "READ SCICHART GEOMETRY BEFORE LAYOUT" BUG CLASS (2026-08-18)#

Front-end only. A toolbar the maintainer described as "awkward", and channel labels that did not line up with their traces at 60 rows, turned out to share a theme: three separate places read SciChart geometry before layout had run, and each swallowed the resulting failure.

38.1 THE BUG CLASS -- SciChart geometry is only valid after layout#

sciChartSurface.seriesViewRect and axis.getCurrentCoordinateCalculator() are not readable until the surface has laid out. Before that, seriesViewRect throws

Cannot get seriesViewRect before layout has ocurred. Move code that calls to be triggered by sciChartSurface.rendered

and a coordinate calculator comes back with viewportDimension: 0. Both call sites were inside a try/catch or behind an if (sv && sv.height > 0) guard, so the failure was silent and the fallback looked plausible -- which is why both survived a long time.

The rule: anything that measures the plot area must run from the surface's rendered event. Both fixes below do that, and draw() also calls the label one opportunistically so it self-corrects on data updates once a layout has happened.

⚠️ One trap when subscribing to rendered: do not write a reactive property unconditionally from the handler. shankTip.svgString = ... invalidates the annotation and schedules another render, so an unguarded write feeds itself a redraw every frame. Guard on "did the value actually change".

38.2 Channel labels did not line up with their traces (worst at 60+ rows)#

Two faults compounding:

  1. The overlay was never pinned to the plot area. Code existed to do it, but it read seriesViewRect from draw() -- a data-update path, before layout -- so the guard was always false and the block never executed once. The overlay kept its full-wrapper height while the traces occupied the inset plot area: measured wrapper 857 px vs plot area top 10, height 832. That produced a DRIFT, not an offset: first label −9.8 px, last +14.8 px. At 20 rows the pitch is 41.6 px so a 25 px swing stays inside a row and merely looks slightly off; at 60 rows the pitch is 13.9 px, so the same swing exceeds a full row -- which is when it became obvious.
  2. justify-content: space-around collapses once the labels stop fitting. A label is ~19 px tall, so 60 of them need 1140 px in an 832 px plot. Free space goes negative, flex stops distributing, and the labels bunch.

Fixed by placing each label arithmetically at (i + 0.5) / shownSlots of the plot area -- the same maths as the axis range ([bottom*spacing - spacing/2, topRange*spacing + spacing/2] spans exactly shownSlots rows, each trace centred in its row). Exact at any density, independent of label height, and it also handles a gap mid-band, which the flex version could not.

40.2 The measurement is structurally simpler on a OneBox — the S39.4 question, answered#

The brief (§39.4) flagged one thing to settle before recording: how the stim capture is synchronised to a USB-attached probe. Answer: capture it on the OneBox's own ADC, and the problem disappears.

On a PXIe rig the pulse lands on the NI-DAQ — a second device with its own clock — so the pulse edge and the detection instant only become comparable after a sync fit against a shared TTL train. That fit is where the off-by-one of §24 mis-paired a periodic signal and cost a session. On a OneBox the probe and the ADC are the same device: every sample of both bands carries a tick from the one 100 kHz counter, so

t_seconds = (tick - tick_of_first_raw_sample) / (fs_raw × measured_ticks_per_sample)

applied identically to detections and pulse edges puts them on one axis. No sync model, no sync channel, nothing to mis-pair. analyze_recording.py --stim-band adc --stim-channel <n> (stim_events_same_clock()); without the flag the analyser looks for a nidaq band, finds none, and silently reports no closed-loop latency at all.

Wiring: Pi On/Off = GPIO17 = header pin 11 → OneBox IO2 = ADC channel 2. Reads as a clean logic line (idle 0.0002 V, peak 3.296 V, ~93 µs pulses). One biphasic stimulus puts SEVERAL edges on that line, so edges are grouped into events: 1309 raw edges → exactly 1000 events, and the count is identical for any grouping gap from 1 ms to 100 ms. That insensitivity is the evidence the extra edges are pulse structure rather than noise or double-triggering.

40.3 Two SILENT traps this path exposed (both fixed)#

Neither raised an error; both produced plausible-looking output.

  1. setRecording's channel override rewrote the ADC band too. It carries PROBE read-out indices, but interp.npx.adc also matches contains("npx") — so recording "just the detection channel" set the ADC to channel 0 and discarded the stim capture. That is a 670 MB recording that looks complete and cannot be analysed at all. PXIe never hit this because the stim lived on the NI-DAQ, a separate recorder. Fixed in RecordProcessor.cpp (exclude adc). Check the sidecars: raw = your detection channels, adc = all 12.
  2. The analyser chose the ADC as the PROBE band. Its raw-band heuristic accepted any npx-format band whose name lacked "lfp" — which data.npx.adc satisfies — and bands come back alphabetically, so adc beat raw. The offline reconstruction then ran on the analog inputs and the stim square wave read as ~1000 "ripples" on the stim channel (reported fs=2525Hz channels=[0..11], 1011 crossings). Fixed; the sanity check is that header line, which must read fs=2500Hz channels=[<detection channels>].

After both fixes the run is four-way consistent: online 1000 = offline 1000 = pulses 1000, unmatched 0. That agreement is the check to demand before quoting a latency from any closed-loop recording.

41.1 The merge — three things that were right there and wrong here#

The other rig's changes were correct on the machine they were written for. That is exactly what made them worth reading carefully rather than fast-forwarding.

  1. The vendored HDF5 runtime would have shadowed ours. da2b934 vendors an HDF5 2.x runtime and copies it next to the exe so a fresh clone runs with no HDF5 installed. Its own comment names the hazard — the DLLs "MUST match the HDF5 that find_package linked against" — but the guard was only EXISTS, which is now always true because the DLLs are git-tracked. This rig links 1.14.6 (vendored hdf5.dll 5,868,544 bytes vs the installed 4,320,768), and the exe's own directory wins the Windows DLL search — so every build here would have compiled against 1.14.6 and loaded 2.x at runtime. That failure is silent: the loader is satisfied and only HDF5 calls misbehave. The copy is now gated on the version actually linked (SP_HDF5_RUNTIME=auto|vendored|system to override); unknown → skip, i.e. fail safe.
  2. Stimulation became opt-in, which silently breaks closed-loop RECORDING. Defaulting stim off is the right call — it is what stopped unsolicited datagrams reaching an unrelated device at 192.168.1.100 on the other bench. 41.2 Issue #18 — ask, then reflect#

The GUI moved its own controls on click and assumed the backend agreed. Pressing Play flipped the button to Pause whether or not acquisition ever started, so the most important thing the toolbar communicates — is this rig running? — was a statement about the last click, not about the rig.

togglePlay() no longer changes any state. It sends setPlaying and marks the request pending; reflectPlaying(), driven by the backend's statePlaying event, is now the only place the button's meaning changes. The in-flight gap is drawn as waiting (disabled + slow pulse) — not as a dead control and not as the new state, which is the whole failure the issue describes. A request unresolved after 5 s clears itself, because a permanently stuck control is worse than an optimistic one.

The backend held the matching half of the bug: a refused play returned quietly, so even a correct client had nothing to reflect. setPlaying now always reports the resulting state, and says why when the answer is no.

Refusals are not errors, but a failed connect is. Pressing Play with no source is routine: status line, no dialog (the hardware-error kind routes to a modal, so these are emitted as plain error). A failed connect is the opposite case and used to be the quieter of the two — the GUI saw only deviceReady=false, which renders as "Source disconnected", identical to a normal teardown. On the second rig a OneBox failed to connect and said nothing at all. It now always raises a dialog.

41.3 Getting the real reason out of a dying object#

The specific cause was known and being thrown away. handleConnectRequest calls teardownManagers() on failure, destroying the source object before its deferred sigGuiStatus can be delivered — and Qt discards queued calls to destroyed QObjects. The one message that would help the user was precisely the one guaranteed not to arrive.

A separate thread does not fix this (it was the first idea, and it is the wrong shape): the message is not late, its sender is gone. What is needed is a sink that outlives every sender. logMessages() — the global Qt message handler — already sees every message from every thread, including objects destroyed moments later. New src/core/ErrorLog.{hpp,cpp} is a mutex-guarded bounded tail fed from there; WebSocketServer takes a mark() before a connect attempt and asks for since(mark) if it fails, so only that attempt's lines can ever be shown.

Two non-obvious choices, both learned by looking at the output:

  • Filtering on QtMsgType would capture NONE of the messages this exists for. This codebase puts severity in the text: the hardware failures are plain qDebug() lines reading [MAIN] ERROR: ..., and the neuropixels module alone has 178 qDebug against 31 qWarning. Matching the convention that exists beat rewriting 178 call sites to acquire a tidier one. Explicit markers rank above merely-suspicious wording ("failed", "could not") so a real diagnosis is never crowded out.
  • Ordering is chronological, not newest-first. A hardware failure cascades forwards: the first line is the cause, the rest are consequence. On a probe-less basestation the log reads "No Headstage detected on any port!" and only then "ERROR closing probe. Code: 44" — the teardown, not the fault. Newest-first led with that noise.

42. FDIR — MAKING FAILURES REACH THE USER, AND KEEPING THE PIPELINE IN A STATE WE DESIGNED (2026-08-20)#

GitHub issue #11 ("FDIR"): handle errors from processors and relay that to the GUI; determine how not to end up in an invalid or unexpected state. It is the sibling of §41.2's issue #18, and the first thing the investigation turned up is why: the backend had the same bug #18 fixed in the browser, one layer down.

42.1 The rule — announce CONFIRMED state, never REQUESTED state#

handlePlayRequest() returns true once the processor threads have been asked to start. Nothing is acquiring at that point. WebSocketServer::setPlaying treated that true as "we are streaming" and broadcast statePlaying=1. If a source then failed, slMcOnSourcesStarted(false) stopped everything again — correctly — and told nobody, so every client went on showing a running rig that had just been shut down underneath it.

MainController::sigMcAcquisitionStateChanged(bool, reason) is now the only thing that may change what clients are told about acquisition, emitted when the controller knows. Verified ordering in the log:

[WebSocketServer] play accepted -- awaiting acquisition confirmation     <- announces nothing
[ProcessorManager] Processors ready: 1..3 of 3
[ProcessorManager] All processors started
[MainController]  All sources have started
[WebSocketServer] acquisition confirmed: true                            <- broadcasts statePlaying

42.2 Processor faults now reach the user — generically#

IProcessor::sigIpErrorOccurred has existed from the beginning and nothing listened to it except WebSocketServer, wired to the recorder by name. A recorder failing to open a file reached the user; the identical fault in proc.lfp, proc.rippledetector or a display processor reached nobody. ProcessorManager now connects it for every processor it builds, tags it with the registry key, and relays it out as "proc.npx.recorder: <message>". New sinks are covered by construction.

Report and consequence are kept apart: the relay reports (status line); the recorder keeps its own recordingStatus channel to make the GUI revert its optimistic "recording" state. The frontend no longer prints the recorder text twice, and "no recorder bound for this source" moved to guiStatus — it is a refused control, not a processor fault.

42.3 Three silent hangs in the readiness mechanism#

Readiness was an int compared with ==:

  1. Identity came from the reported name. Processors emit hardcoded labels unrelated to their registry key, and every RecordProcessor emits "recorder" — so SimNpx2NiDaq, Npx1PxiNiDaq and friends report one name for two processors. I hit this while fixing it: my first version used a QSet of reported names, which would have counted 6 processors as 5 and hung every dual-recorder profile. The old counter survived only by accident, counting signals rather than identities. Now resolved via nameForSender(). Verified on the real case — two recorders, both reporting "recorder", tracked as proc.npx.recorder and proc.nidaq.recorder.
  2. A duplicate sigIpStarted wedged it permanently. ++ past the total and == never matches again: acquisition hangs with every component reporting itself healthy. Now a set tested with >= and a latch.
  3. A processor that never reported produced an unbounded wait. Now an 8 s watchdog (kStartupTimeoutMs) names the culprits, stops the pipeline, and reports: "Acquisition stopped: Processor startup timed out after 8000 ms. Never reported ready: ...".

A declared failure is final for that cycle. Testing the watchdog with a deliberately absurd 1 ms timeout exposed a race worth keeping: the watchdog reported failure, the stragglers then finished, and the manager announced the same request started a moment later — one play request producing both outcomes, with the GUI showing each in turn. mStartupFailed latches it; late arrivals are logged and ignored.

42.4 Other invalid-state fixes#

  • handlePlayRequest used non-unique connections. They are torn down in handlePauseRequest, which only runs on a successful pause — so a play that failed to start left them, and the next play added a second identical connection, starting the sources twice from one request. Now Qt::UniqueConnection.
  • ProgramState::recordingState was a field that always lied. Assigned once in the constructor and never again by anything; recording is owned by WebSocketServer/RecordProcessor, so it read eNotRecording for the life of the program including while recording. Removed — a state variable that is always wrong is worse than none, because it invites exactly the validity check #11 asks for and then answers it incorrectly. acqState gained an in-class initialiser.
  • setupProcessors left a half-built graph on failure. Now rolls back what it built.
  • An error dialog outlived its condition. The "Hardware not detected" modal sat there after the rig was fixed and reconnected — and on a second client could describe a failure that browser never triggered. A deviceReady=true now dismisses it. (Spotted by the user, on a second GUI.)
  • Re-entrancy: the FDIR signals fire while handleTextCommand holds a non-recursive QMutex, so subscribers are Qt::QueuedConnection.

43. KNOWING THE WHOLE SYSTEM STATE — AND WHETHER IT IS STILL MOVING (2026-08-20)#

GitHub issue #16 ("Track global state of system"): the overall state of the server should be known at any time (acquisition, processors, record), and maybe a monitor to make sure all processors are cycling. The direct continuation of §42 — #11 made failures reportable, #16 makes the system inspectable.

43.1 One snapshot, answerable at any time#

New getSystemState command returns everything in one object; it is also broadcast whenever anything in it changes, and replayed to a late-joining client:

{ "event":"systemState", "acquisition":"acquiring", "source":"NPX 2.0 Multishank (OneBox)",
  "playing":true, "recording":{"active":false,"name":""},
  "processors":[ {"name":"proc.lfp","state":"cycling","ready":true,"cycles":24235,"thread":true} ] }

MainController::systemState() owns acquisition + processors; WebSocketServer composes recording on top because the recorders live there. Recording is deliberately not copied into MainController — a second copy of a state is a second thing that can be wrong, which is precisely what the removed recordingState was (§42.4). systemState() also does not take mMutex: handleTextCommand holds it for the whole of a connect or a play, and those are exactly the moments somebody most wants to look at the system, so taking the same lock would make the monitor block on the thing it monitors. One-step-stale beats blocking.

43.2 Liveness — "started" is not "working"#

A processor can report ready and then block forever on a buffer that never fills, and every health signal in the system keeps saying it is fine. IProcessor now carries a monotonic cycleCount(), bumped by noteCycle() once per work cycle (6 call sites). ProcessorManager polls it every 1 s and calls a processor stalled after 3 still polls, naming it on the GUI status line and in the snapshot.

Choices worth not undoing: polled, not signalled (acquire loops run at 1 ms — a heartbeat signal per cycle would flood the event loop to answer a once-a-second question); relaxed atomics (the only question is "did this change?"); counted AFTER the wait in blocking loops, so a processor parked on a dead buffer genuinely stops advancing. Stall detection runs only while acquiring — an idle processor is not a broken one.

The placement trap, hit immediately. My first pass inserted 3 of the 6 noteCycle() calls into slIpStopProcessor instead of the per-cycle slot, because the script matched the connect(...) reference rather than the definition. The monitor caught it on the first hardware run: proc.npx.display sat at 0 cycles / stalled while everything else advanced. The rates are the check — proc.npx.display should tick at ~50 Hz (20 ms timer), proc.npx.recorder at ~20 Hz (50 ms). Both now do, exactly.

43.3 Recording is confirmed too (closes the §42 gap)#

RecordProcessor::sigRecordingStateChanged fires from applyRecordingState — where files are actually open or actually closed — not from setRecording, which is only the request. The old stateRecording broadcast echoed the request straight back, so a start whose file open failed still told every client it was recording. That echo is gone; the GUI now shows a pending record button and transitions only on confirmation, exactly like play in §41.2.

⚠️ Event shape: the GUI reads {value:<bool>, name:<string>}, NOT broadcastStatusEvent's {message:"1"}. My first version used the status shape — the GUI would have read false and a started recording would have looked stopped. Caught before testing, by reading the handler.

45. SOURCE LIVENESS — AND WHY THE COUNTERS ARE NEVER RESET (2026-08-20)#

The gap §43 left open. Sources now carry the same heartbeat as processors, and a dead source names itself instead of showing up as five stalled processors.

45.1 The reset question, decided#

The counters are never reset. One writer (the worker/processor thread), one reader (the monitor). A reset would make the manager a second writer, and a poll in flight could observe a decrease — which the delta logic reads as "no movement", i.e. a spurious stall at exactly the moment acquisition starts. The managers take a baseline at start and derive the per-run figure by subtraction (guarded against unsigned wrap).

That asymmetry is the whole argument: a monotonic counter can always be turned into a per-run number by the reader; a reset counter can never be turned back into a lifetime total. So both figures are available for free. resetStreamErrors() nearby is not a counter-example — the worker resets its own counter on its own thread.

The user chose to show both columns (This run / Total), with the caveat that the numbers get large — so they are compacted above 100k (2.1M) with the exact figure on the cell tooltip, and the column is width-fixed with tabular numerals so it cannot jitter.

45.2 Two things sources do that processors do not#

  1. Their workers are per-run objects — created in startAcq, destroyed on stop — so a worker's counter restarts at zero every run and cannot carry a lifetime figure. SourceManager banks each source's count into mLifetime before stopAcq destroys the workers (afterwards it is unrecoverable) and reports bank + current. Caught in testing: without it the Total column silently equalled This-run and read 0/0 while paused.
  2. A source may run several loops. NI-DAQ builds one worker per device; a OneBox runs the probe and its 12-ch ADC. Hence acquisitionWorkers() returns a LIST. ⚠️ An override must EXTEND the base list, not replace it — OneBoxSource first returned only its ADC, which hid NeuropixelsSource's probe worker: a probe that stopped while the ADC kept ticking would have raised nothing, i.e. exactly the failure this feature exists to catch. The panel now prints ×N beside a multi-worker source so an unmonitored loop is visible rather than assumed.

Workers cannot be found generically — moveToThread forbids a parent, so findChild returns nothing — which is why the accessor exists. Default is an empty list: a source that never overrides it is unmonitored rather than falsely "stalled".

45.3 A dead source silences its victims (user's decision)#

One dead source stalls every processor downstream. Reporting each as its own fault buries the cause, so while any source is stalled MainController::slMcOnProcessorStalled suppresses the processor alerts and processorStates(blockedBySource) reports them as blocked. The snapshot still lists them — nothing is hidden, only the alert is — and the panel shows a banner saying the processors are blocked, not faulty.

Coarse by design: the rule asks "is ANY source stalled?", not "is the source THIS processor reads from stalled?" (the graph is bound by buffer name and is not walked). With one probe per profile the answer is identical; noted in Fdir.md §9 for the two-source case.

45.4 GUI#

Chip highlights while the panel is open (user request — previously it looked identical open or closed, so a panel hidden behind the window read as "nothing happened"). A stalled source makes the chip say source stalled and turns the whole chip red, since it outranks any processor state.

GitHub issue #2 (open since 2025-06-18): "Every time a log message is written, log useful information such as the timestamp, class it was called from, etc." Both halves done — the metadata the issue asks for, and the severity inconsistency I hit during §42.

46.1 What every line now carries#

logMessages() printed only the message. It now emits, identically to console and output.log:

22:44:33.291  DEBUG  [proc.rippledetector]   RippleDetector.cpp:753    [RippleDetector] resolved ...
time          level  thread                  origin                    message as written

47. PROCESSORS REPORT STARTED WHEN THEY HAVE RUN, NOT WHEN THEY HAVE SCHEDULED (2026-08-20)#

GitHub issue #13, open since 2025-06-18: "Every processor is triggered to run through a slot. Some processors use this slot to start a timer that triggers a different slot. When that slot is run for the first time, it should emit the started signal, not the slot that started the timer."

Fourth in the same family as §41–§46: a component announcing a state it has not reached.

47.1 Why it matters, concretely#

MainController starts the SOURCES only once every processor has reported sigIpStarted. A timer-driven processor emitted it from slIpStartProcessor — the slot that merely starts the QTimer — so the producer could begin committing samples while a consumer had not yet run a single pass. The ordering guarantee the design intends ("a consumer is always registered before the producer commits") was weaker than it looked.

47.2 The fix, and the trap that shapes it#

IProcessor::armStarted(name) records the label instead of emitting; noteCycle() — already called once per work cycle for the §45 liveness counter — emits sigIpStarted on its first call after arming. Four timer-driven processors switched: proc.npx.display, proc.nidaq.display, proc.npx.recorder, proc.audio.

⚠️ LFPProcessor and RippleDetector were deliberately NOT changed, and must not be. They emit directly and then block on waitForAvailable. Their first cycle cannot complete until samples arrive; samples arrive only once the sources start; the sources start only after every processor reports ready. Deferring their report deadlocks the pipeline — and it would surface as a startup watchdog timeout (§42.3), pointing at the wrong thing entirely. Caught by reading the loops before writing the change, not by hitting it.

The uniform-looking fix is the wrong one here. The rule is per-drive-mode, and AddingASinkModule.md rule #1 is now a table making that explicit.

47.3 Verified — the timings prove the mechanism#

Simulated NP2.0 + NI-DAQ (6 processors, both classes) and the real NP2.0 on the OneBox. Threads all start within ~5 ms of each other, then:

processor reports ready matches
proc.lfp, proc.rippledetector +1 ms immediate — blocking pair, unchanged
proc.npx.display, proc.nidaq.display +19–21 ms their 20 ms display timer
proc.npx.recorder, proc.nidaq.recorder +50–51 ms their 50 ms record timer

Each processor's delay equals its own configured timer period — which is the independent evidence that the signal now comes from the tick rather than from the slot that scheduled it. "All processors started" → "Starting all sources" follows only after. Real hardware showed the same (display +25 ms, recorder +57 ms).

Restart re-arming verified (the failure that would have hung the rig): three consecutive play/pause cycles each produced a complete readiness set with identical timings — armStarted re-arms on every start, because slIpStartProcessor runs again each time the thread is restarted.

49. A DEAD PROBE MUST NOT LOOK HEALTHY, AND MUST NOT COST A POWER-CYCLE (2026-08-20/21)#

An NP1.0 on the OneBox stopped delivering data. The hardware fault was real and is not ours. What is ours is that the software reported a healthy rig for three and a half minutes, and then could not be shut down.

This section is the fifth in the §41–§47 family — a component announcing a state it has not reached — but with the sharpest consequence so far: the operator had to force-kill the backend, which on a OneBox leaves the FT601 handle claimed and forces a physical power-cycle.

49.1 What the operator saw, and why every part of it was wrong#

source.npx.onebox   producing 63,536        proc.npx.display    cycling  1,595
proc.npx.recorder   cycling    638          proc.rippledetector cycling 17,293
acquisition confirmed: true                 GUI: "Waiting for data…"   Time: 0.00s

Not one sample had been read. The arithmetic gives it away once you look: 1,595 display cycles × 20 ms = 31.90 s; 638 recorder cycles × 50 ms = 31.90 s; 63,536 ÷ 31.90 s = 1,991/s = exactly two 1 ms workers. Every counter sat at its exact nominal timer rate — which is precisely the reading you get when nothing arrives.

Three defects, each hiding the next:

  1. noteCycle() counted poll-timer ticks, not data. SourceManager's stall watchdog looks for cycleCount() standing still, and a free-running timer never stands still — so the watchdog, its 3 s threshold and its excellent message were all correct and structurally unable to fire.
  2. SUCCESS with zero superframes matched neither branch. np_readElectrodeData returning "fine, nothing" is not the data path and not the error path, so the loop swallowed it silently, forever. The OneBox ADC read had the identical hole.
  3. np_arm() ran bare on the main thread with no timeout. It never returned. That killed the Qt event loop, and with it Pause, Disconnect, the WebSocket, and the console quit.

49.2 The fixes#

Liveness now means data. noteCycle() moved to after a committed write in Npx1Probe, Npx2MSProbe and OneBoxAdcWorker. No new watchdog was written — the existing FDIR machinery was already right and simply had to be given a number that means what it says. Verified on the failing hardware:

guiStatus: source.npx.onebox has not produced data in 3 s. Acquisition is running
           but nothing is arriving -- check the hardware connection

Vendor calls are bounded. New src/core/BoundedCall.hpp (runBounded / runBoundedCode) runs a callable on a detached thread and gives up after a timeout. On timeout the call is abandoned, not cancelled — there is no safe way to kill a thread inside a driver, so it is left blocked and leaks. That is the correct trade: a leaked thread costs a stack and dies with the process moments later; an unresponsive main thread costs the operator their shutdown and a power-cycle. Callers must capture by value only — an abandoned call that touches this turns a hang into a use-after-free.

src/modules/neuropixels/NpBounded.hpp wraps that for the teardown paths as npStep, with an alive latch: once one call fails to return the rest are skipped, because a basestation that has stopped answering will not answer the next one either, and paying four timeouts turns a 3 s pause into a 12 s freeze. Applied to np_arm on stop and to the whole of both closeDataSource() paths.

Verified on the wedged hardware — the application now exits cleanly in 9 s where it previously hung forever:

[MAIN] Arming PXI slot 16 to flush hardware buffer before close...
[Npx] ERROR: np_closeProbe did not return within 3000 ms. Abandoning it and continuing teardown
[Npx] Skipping np_closeBS  -- the basestation has already stopped responding.
[Npx] Skipping np_unmapBS  -- the basestation has already stopped responding.

Teardown logs stopped lying. The close summary and "Released virtual slot 16" used to print unconditionally, including for steps that had just been skipped. A teardown that reports work it did not do is worse than one that reports nothing: the next person reads it and rules out the slot mapping as the reason their reconnect fails.

output.log rotates (output.1.log … output.5.log). It used to be truncated on every start, and during this very investigation two restarts destroyed the log of the fault being investigated.

49.3 What was NOT changed, deliberately#

  • np_arm stays on the OneBox stop path. It is inconsistent with closeDataSource(), which documents np_arm as a PXIe-oriented step deliberately dropped — but the vendor reference has OpenEphys using arm(slot) precisely to stop acquisition, and removing it risks leaving the FPGA streaming into nothing. Bounding it is the right fix; removing it is not.
  • The play path still does not arm before triggering. np_arm has three call sites and none is on the play path: the arm is issued once at connect and inherited by every later play, with an unbounded gap in between (~2 s in scripted runs, 61 s in the failing GUI session). The vendor sequence is switchmatrix_set → arm → setSWTrigger; we do the third alone, and SpikesPeak never sets SM_Output_AcquisitionTrigger, only reads it. This is a genuine latent defect and a plausible contributor, but it could not be tested — a basestation that will not answer np_arm on teardown will not answer it on play either. Do not apply it blind; test it after a power-cycle.
  • Sim sources still count ticks. Consistency would argue for changing them, but they pace to wall-clock with an early return when no samples are due, so the change risks false "stalled" warnings for no real gain — sim does not wedge the way hardware does.

49.4 The hardware, separately#

The OneBox itself needs a power-cycle: np_arm(16) not returning means it will not answer even a reset request. The FT601 bridge still enumerates (VID_0403&PID_601F, Status: OK), so the USB stack is fine and the FPGA is not. OpenEphys reporting error 110 is the Windows ERROR_OPEN_FAILED, not a Neuropixels code — NP_ErrorCode stops at 58.

Worth recording as a signature: the probe and the 12-channel ADC died together. SM_Output_AcquisitionTrigger is documented as the neural or ADC acquisition trigger on a OneBox, so one dead trigger silences both streams at once.

The last known-good run was 17:35–17:40 (RecordingTests/wp_loopback, wp_square) — a GUI run, not a scripted one, which rules out the scripted-vs-GUI axis entirely. The WavePlayer experiments in that window remain the most plausible thing to have left the box in this state (waveplayer_arm routes DAC0 onto the SMA, which setSyncAsInput() configures as an input), but that is unproven and FPGA state does not survive a power-cycle, so it may not be reproducible.

50.5 The suite found three real defects on its first run#

All three are in Avx2Filter / its only caller, and all three are latent, not active — worth stating precisely, because "we found bugs in the filter on the closed-loop path" would otherwise read far more alarmingly than the facts justify. LFPProcessor is the only user of Avx2Filter, and it configures freshly-constructed filters exactly once, which is the single case all three bugs happen not to reach. (RippleDetector and AudioProcessor use the scalar Filter, which never had any of these problems.) Every one of them is now fixed, and guarded by a test.

1. The coefficient setters appended instead of replacing. Avx2Filter::setDefault{LFP,RippleBand,Envelope}Coefs() push_back()ed onto mBCoefs/mACoefs without clearing, then set mNum*Coefs to the new preset's tap count. Apply LFP (3 taps) then ripple (26 taps) to one object and the filter that actually ran was three LFP taps followed by the first 23 ripple taps — neither filter, silently. The scalar Filter assigns, so the two implementations disagreed across a reconfiguration. Re-applying the same preset was only accidentally harmless: the duplicates sat past the mNum*Coefs bound, but both vectors grew without limit every time.

2. addSample() wrote through a null pointer on an unconfigured filter. With no coefficients set, mX is empty and the aligned 32-byte store went straight through mX.data(). The scalar Filter has always guarded this (isInitialized() → 0.0f); the vector one now emits silence, which is the honest answer. This case previously could not even be tested — the attempt would have taken the whole suite down.

3. LFPProcessor::setup() appended 48 more filters every time it ran. No clear() before the population loop. Measured on the rig: setup() runs once per session on the paths exercised, and three connect/disconnect cycles produced three start/stop pairs and no second setup — so this one never fired in practice. Fixed defensively.

Verified after the fix: test_avx2filter 15/15 with 0 skipped (the AVX2 path genuinely runs on this machine, it does not silently skip), a sim NP2.0 source drives LFPProcessor start→run→stop with 0 warnings, and three connect/disconnect cycles deliver an identical 286 frames each.

The test that pinned defect 1 was originally written to assert the broken behaviour so the suite would stay green. That is the wrong default — a test asserting a bug cements it — so it was inverted to assert equivalence with a freshly configured filter, and it now passes against the fix.

51. SECOND WORKSTATION — ONEBOX, NO PXIe: WHAT SURVIVED THE MOVE (2026-08-21)#

The headline: the software is more portable than the build was. Every suite passed unchanged and the OneBox path validated end to end on a second, independent rig — but the application could not start at all until a load-time DLL dependency was made a runtime one.

51.1 The blocker: one missing DLL made the whole app unlaunchable#

52.4 #53 — sidecars now describe the frame (trap FIXED, verification still open)#

num_channels counts the payload. An NPX frame is [uint32 ts][uint16 sync][int16 x N] = N + 3 int16. The layout was already documented — in the comment above writeMetadataSidecar() — just nowhere a reader could see it. It now ships in every sidecar as a frame block. Verified on a 15 s NP2.0 recording: frame.bytes: 12, file size divides evenly, filesize/12/30000 = 15.00 s. The old reading claims 30.00 s for the same file.

Older recordings are unchanged and still need the stride worked out by hand.

53.5 THE ONE THAT MATTERED — a re-enabled band was silently stale#

Found by an adversarial review of the diff, not by any test that existed.

BandFilterProcessor used one counter for two roles: the read cursor into data.npx.raw, and the write slot into its own output ring. A disabled band advances the first and commits nothing, so they diverge by exactly the length of the disabled stretch — while every consumer indexes the ring by its own committed-sample count (constDataAt is ind % capacity).

That was correct only for a band running from the first sample, which is what every profile used to do. §53.2 turned it into the default path. The producer would resume writing at skipped % capacity while consumers still read from committed % capacity, and the band would then serve correct-looking samples of the wrong age: up to a second of extra delay at 30 kHz, different every session, on a closed loop this repo defends in single milliseconds. Nothing throws, nothing logs, and no test that checks "is data flowing" would see it.

The write slot now follows the commit count. tests/test_bandfilterprocessor.cpp (new, 17th suite) pins it and was proven able to fail by restoring the single counter.
