Detached windows#

Two different things detach, and they are separate mechanisms that share one registry:

detached view detached SWR dock
what more columns of the same live streams, no toolbar the SWR Detector dock as its own window
opened from ⧉ in the view group ⧉ in the dock header (#rd-dockbtn)
URL index.html?view=detached index.html?view=ripple
marker on <html> .detached-view .ripple-window
predicate detachedView() — webinterface/main.js rippleWindow() — same file
registry role view ripple
redock close it the same button, both directions

They are mutually exclusive — both read ?view=, so no page is ever both. §1–§5 are written about the view window, which came first; §6 is the dock.
Opener + detached mode AppController.openDetachedView() / detachedView() in webinterface/main.js
Ripple-only mode RippleModule.detach() / rippleWindow() in webinterface/main.js

1. It is the same page with a flag#

index.html?view=detached. Not a second page.

A separate view.html would need its own bootstrap, its own column construction and its own X-axis plumbing — a second implementation of the thing whose behavior has to match the first exactly, because the entire point is that a detached column behaves identically to an attached one. The flag reuses all of it and hides what does not belong.

The class goes on <html>, not <body>, so the stylesheet can hide the toolbar before the body exists and a detached window never flashes a toolbar it is about to remove.

The opener passes the shape it wants — ?cols=, ?ch=, ?orientation= — because a window you opened to see more should not come up with the main window's remembered column count.

2. noopener is the load-bearing detail#

This is the whole design decision, and it is not a security nicety.

Chrome grants roughly 16 WebGL2 contexts per renderer process, and force-loses the oldest when you exceed that — silently, asynchronously, with getContext still returning non-null. Measured in real Chrome, three ways:

how the window was opened result
same-origin <iframe> parent made 10, iframe made 10 → parent's oldest 4 died, 16 alive total
plain window.open popup parent made 10, popup made 10 → parent's oldest 4 died — same shared pool
window.open(..., 'noopener') popup made 10 and the parent lost nothing — its own budget

A noopener popup lands in a new browsing-context group, which means a new renderer process, which means its own 16.

Four columns already cost four contexts. Without noopener, opening a third window is what blacks out the first window's columns — for no visible reason, some seconds later.

The price, stated rather than buried#

window.open returns null, window.opener is null, and the popup is unreachable from the opener. So it opens its own WebSocket and decodes its own copy of the stream.

That works: WebSocketServer::broadcastData fans out to every client unconditionally, and the auto-quit is keyed on the client list becoming empty, so closing one of two windows starts no shutdown. Late joiners are already a first-class case — sendStateSnapshot() replays source, ready, playing and recording state to a new socket.

But each window is a full parse of ~3 MB/s per stream. That cost is real, and it is why this is a button and not the default.

2a. Counting the windows — and why the backend is not asked#

The front end knows how many windows are open. webinterface/WindowRegistry.js carries presence over a BroadcastChannel; the count shows as a badge on the detach button and in every window's document.title.

The paradigm, chosen against two alternatives#

The winner does not change the data path. Not by one byte. Presence is a UI feature, not a throughput optimization, and saying otherwise would be the easiest thing in this document to get wrong.

The numbers, from the emit path rather than from memory. One display packet is a 12 B header for a three-letter stream id — [u8 idLen][idLen bytes][u32 numChannels][u32 numBins], DisplayProcessor.cpp:302-310, so the header's size depends on the id — plus 20 bins of 1 + 2 × 384 floats (min and max per channel) = 61,532 B for raw, emitted every 20 ms:

configuration streams per window 3 windows
NP2.0 (raw) 1 3.08 MB/s 9.2 MB/s
NP1.0 (ap + lfp) 2 6.15 MB/s 18.5 MB/s
option verdict
(A) status quo — no cross-window awareness Runner-up, and genuinely close. Identical data path to the winner. Its only loss is that the operator cannot tell how many windows exist; main.js had confessed this in a comment for weeks — "nothing would be tracking how many exist". An operational annoyance, not an acquisition defect.
(B) BroadcastChannel registry Winner. ~120 B per window per 2 s — 200 B/s at three windows, 0.002 % of the data path — on a setInterval, touching neither the frame path nor the acquisition thread.
(C) relay — one window owns the socket and forwards Loses on every axis. It does not save the decode (the expensive half is Float32Array → per-channel append, which every window still does). It replaces a kernel-handled loopback read with a structured-clone copy — BroadcastChannel accepts no transferables — of 61 kB, 50×/s, per receiver, on the owner's main thread: at three windows on NP1.0 that is 7.4 MB/s of added main-thread copying to save ~0. postMessage with a transferable would avoid the copy but needs a handle, which noopener removed — and reintroducing it forfeits the context budget this whole design exists to protect. It also makes closing the owner window kill everyone's data.

Why BroadcastChannel does not cost the isolation#

BroadcastChannel delivery is scoped by origin, not by browsing-context group, opener relationship, or renderer process. noopener severs the JS handle and moves the popup to a new renderer; it has no bearing on whether two same-origin documents share a channel. So presence reaches across the severed handle without undoing the severing — which is exactly why postMessage and window.opener are disqualified and this is not.

It is a built-in browser API. No library, no bundle, no vendored anything.

The backend cannot produce the right number anyway#

This is stronger than "the backend does not need to know". m_clients counts sockets. scripts/run_gui_tests.py opens one. command_client.py opens one. A backend-derived window count would read 2 with one browser open and a test harness attached. Windows are a browser-side fact, so they are counted browser-side — no new message, no broadcast on every connect, no work on the thread that runs acquisition.

Mechanics#
channel spikespeak-windows-v1 — versioned, so two builds during a hot reload do not count each other
heartbeat 2 s
stale after 6.5 s (three missed beats plus margin)
leaving pagehide → bye. Not unload — deprecated, and already not fired in conditions Chrome ships. pagehide also covers the bfcache, which is the same thing from every other window's point of view; pageshow re-announces.
a crash sends nothing, so the reap is the backstop — the only path that needs the timer at all
ordering sorted by open time, id as tiebreak, computed independently and identically in every window, so "View 2" means the same window everywhere with nobody assigning it

Addressing, which is the half that is not just a count#

postTo(id, type, payload) routes a small control message to one window. It earns its keep on the one thing noopener made impossible: a popup cannot be focused from the opener, because there is no handle. Clicking the count badge sends identify to every peer, and each window focuses itself.

There are two message types, not one. identify is above; ripple-redock is the detached SWR dock handing itself back (§6). Note the asymmetry, because it is the design rule worth copying: the dock's restore is keyed on the peer set disappearing, not on the message arriving — so the message is an optimization for the common case, and every other way of losing the window still works. A control message you must receive is a control message that strands you when you don't.

It carries presence and control only, never sample data — see (C) above for what routing data through it would cost.

One real scoping limit#

Same-origin means http://localhost:8234 and http://127.0.0.1:8234 would not see each other. Detached windows are immune: openDetachedView() builds its URL from window.location.pathname, so it inherits the opener's origin. Only a hand-typed second window could mismatch — and such a window cannot work today anyway, because Config.WEBSOCKET_URL is hardcoded to ws://localhost:1234.

Why the badge, and not a toolbar chip#

#sys-health is the established chip idiom and it already carries a live count in .sys-detail, so a "Views · 2" chip would have matched the house style. It costs ~104 px of toolbar row 1, and row 1 width is the scarce resource — it is what decides when groups fold away. A badge inside the button that creates the windows costs ~20 px and puts the number next to the control that changes it. The chip was the more conventional answer and the width decided against it.

3. What a detached window keeps and loses#

Keeps: the columns, the per-column control band (including the heatmap controls), and the view-shape controls — column count, channels per strip, orientation. A window you cannot reshape is a window you have to close and reopen.

Loses: everything that drives the rig — transport, record, source selection, the probe-map tab and the module tabs (#module-tabs: SWR Detector, Convert, audio, bands). The rig has one operator, and two play buttons in two windows is an invitation to a mistake nobody needs. The probe map goes too: its editor writes to the probe, which is rig control.

That rule was dead for months. It was written as `.detached-view .tb-modules, #ripple-toggle,

audio-toggle` — and none of those three selectors has existed in the tree for a long time, so the#

rule matched nothing and every detached window has been offering a second SWR Detector while this page said it did not. Found 2026-09-01 by checking the selectors against the DOM instead of re-reading the sentence. It now hides the container, because each module appends its own button and any list of ids is a list the next module falsifies — and tests/gui/detached_view.py asserts it, since a hiding rule with no assertion is a comment.

Shared, and easy to miss: the view-shape controls write the same localStorage keys the main window reads at load. Change the column count in a detached window and the main window adopts it next time it opens. That is one remembered shape per browser, not per window — defensible, but it is not what "keeps its own shape" would lead you to expect.

A detached window cannot spawn its own children. Each would open another socket and another full decode with nothing counting them.

4. Testing one#

Two facts the test had to learn:

  • Runtime.evaluate is not a user gesture unless you ask for one, and Chrome's popup blocker silently swallows window.open without one. The first version clicked the button, got "clicked" back, and no window ever appeared. Pass userGesture=True.
  • The popup is a separate CDP target. The harness attaches to pages[0], so reaching the detached window needs a second connection selected by URL.

The noopener check asserts the property, not the symptom#

The first version asserted that the opener kept its contexts. That check could not fail: eviction only happens past ~16 contexts, so with four opener columns and two popup columns a shared pool has no visible consequence at all. Removing noopener and running it passed cleanly.

It now asserts window.opener === null, which is the observable of noopener and is what puts the popup in its own browsing-context group. The regression fails instantly.

Asserting a symptom that only appears past a threshold is a test that reports the threshold, not the code.

5. A backend bug this surfaced#

The detached window came up with the right URL, a complete readyState, an empty title and no scripts.

startSimpleHttpServer in src/main.cpp never stripped the query string. The request line carries the whole request-target, so /?view=detached&cols=2 did not equal /, was not rewritten to /index.html, and was opened as a file literally named ?view=detached&cols=2.

This was never specific to detached views: any URL with a query string 404'd, and nothing in the tree had ever used one. The server now strips query and fragment before resolving, and refuses paths containing .. — every asset it serves is addressed from the root, so a traversal is never a legitimate request.

6. The detached SWR dock#

Added 2026-08-31. The dock's header carries the same ⧉ button in both directions: in the main window it detaches, in the detached window it redocks.

main window                                    detached dock (?view=ripple)
  #rd-dockbtn ──detach()──▶ window.open(?view=ripple, "noopener,popup=yes,560x980")
                            dock.classList.remove("open")      html.ripple-window
                                                               dock fills the page (inset: 0)
  reattach()  ◀──ripple-redock──  postTo(main.id, ...) ◀──── #rd-dockbtn ──redock()
                                                               window.close()

560 × 980, tall and narrow, because the dock is a column of per-channel strips: height is the dimension it actually wants. noopener for the same reason as the view window (§2) — the popup gets its own browsing-context group and therefore its own WebGL context budget.

A blocked popup must not close the in-page dock. If window.open returns null the dock stays where it is and says why. Closing it first and then discovering the popup was blocked would leave the operator with no ripple UI at all and nothing on screen explaining it — and this dock is the one that arms a stimulator.

Restore is keyed on the PEER SET, not on the message#

The redock button sends ripple-redock, but that is not what restores the dock. onChange does:

const anyRipple = this.windows.list().some((w) => w.role === 'ripple' && !w.self);
if (!anyRipple) window.rippleModule.reattach();

Every way of losing that window converges on one path — the redock button, the window's own X, a crashed tab, a laptop lid. The message only makes the common case immediate; the peer set is what makes the uncommon ones work at all. A design keyed on the message would restore the dock when the operator pressed the button and silently strand it in every other case, and those other cases are exactly the ones nobody tests by hand.

Symmetrically, redock() calls window.close() regardless of whether it found a main window to post to: if the main window has gone the dock has nowhere to return, and leaving this one open strands the operator in a window with no toolbar.

What the badge counts#

renderWindowCount() uses windows.count() over every role, so detaching the dock makes the main window's title read "SpikesPeak (2 windows)" — the dock is a window and is counted like one. View n numbers views only. The two are counted differently on purpose: the badge answers "how many of these am I running", which is about sockets and decode cost, while the view number answers "which view is this", which only views have.

Testing it#

tests/gui/ripple_detach.py, and it is the harder of the two to test: the assertion has to survive the dock existing in a different window from the one the harness drove. tests/gui/detached_view.py covers the view window and now also asserts that #module-tabs is absent there — see §3.
