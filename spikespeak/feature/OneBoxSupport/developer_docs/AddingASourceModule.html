Developer Guide — Adding a New Source Module#

A source ingests data from somewhere (hardware, network, file, simulation) and produces it for the rest of the pipeline. In SpikesPeak a source is an IDataSource subclass. This guide shows how to add one that matches the existing sources and rules.

Read SpikesPeak_Architecture_Review.md §4–§6 first for the factory/registry/config model and the CircularBuffer contract. For consumers, see AddingASinkModule.md.

0. The contract (src/core/IDataSource.hpp)#

class IDataSource : public QObject {
    Q_OBJECT
public:
    virtual bool initDataSource(ryml::ConstNodeRef cfg) = 0; // open + size buffers + addProducer
    virtual bool closeDataSource() = 0;                       // release hardware/resources
    virtual bool startAcq() = 0;                              // begin producing (spin worker)
    virtual bool stopAcq()  = 0;                              // stop producing (join worker)
    virtual void handleWebCommand(const QJsonObject&) {}      // generic no-op hook (see §8)
signals:
    void dataReady(const QByteArray& data);                  // optional direct-to-browser path
};

Lifecycle is driven by SourceManager + MainController: setupSources → initDataSource(cfg) · play → slSmStartSources → startAcq() · pause → stopSources → stopAcq() · disconnect → cleanupSources → closeDataSource().

There are two production patterns. Prefer A — it's what all current sources use, and it's what lets Display/Record/Ripple treat your source identically to hardware:

Pattern Use when Example How data leaves the source
A. Producer into a CircularBuffer (preferred) Anything that should ride the normal pipeline — real hardware AND simulated NeuropixelsSource, SimulatedDataSource, SynthRippleSource, NIDAQSource addProducer → write → commitWrite; sinks read the buffer
B. Direct emit (legacy, avoid) — (none) emit dataReady(bytes) straight to the browser

Note (2026-07-06): SimulatedDataSource used to be Pattern B (it emitted display bytes and was special-cased in WebSocketServer). It was rewritten to Pattern A so the simulated NPX 1.0 source rides the real display + record pipeline exactly like hardware (SimDataLinux.md). No source uses Pattern B anymore; don't add new ones.

Standing rule — ship a simulated sibling. When you add a hardware source module, also add a simulated source class in the same module (its own class — data shape is hardware-specific; do NOT try to make one generic sim source for all hardware — SimDataLinux.md). It writes the SAME registry buffer(s) in the SAME dtype/aux shape as the real source, so the module is fully testable with no hardware. See SimulatedDataSource (NPX) as the template; a simulated NI-DAQ source is the next one (Status §14).

1. Threading rules#

  • The IDataSource object lives on the main thread. Do not block it.
  • For continuous acquisition, create a worker (IDataSourceWorker) and moveToThread a dedicated QThread, driven by a QTimer (NeuropixelsSource::startAcq is the template).
  • Worker slots: slStartAcquiringData() / slStopAcquiringData(); signals sigDswStartedAcquiring() / sigDswFinishedAcquiring().
  • Wire QThread::started → slStartAcquiringData, a stop signal → slStopAcquiringData, sigDswFinishedAcquiring → QThread::quit, and finished → deleteLater for both.
  • In stopAcq() emit your stop signal, then thread->quit() + thread->wait(2000) before closing hardware (don't close a device a worker is still reading — see review §10/H1).
  • A simulated source uses the same worker-thread pattern (see SimulatedDataSource / SimNpx1Worker — a QThread + a QTimer that generates samples into data.npx.ap/.lfp, paced to wall-clock like SynthRippleWorker), so it never blocks the main thread.

2. Step-by-step#

2.1 Create the class#

src/modules/<yourmod>/MySource.{hpp,cpp}, subclass IDataSource, add Q_OBJECT, delete copy (SP_NO_COPY_OR_ASSIGN). Implement the four lifecycle methods.

2.2 (Pattern A) Get/size your output buffer + register as producer#

In initDataSource:

auto* obj = SP::getDataRegistry().getDataByName("data.mymod.raw");      // registered in Utils.cpp
if (!obj) { /* log + return false */ }
mBuf = static_cast<SP::CircularBuffer<int16, MyAux>*>(obj);
mBuf->setCapacity(SP::kMaxBufferSamples, numChannels);
if (!mBuf->addProducer(mProducerId)) return false;   // mProducerId written back by reference
mDataSourceState = SP::DataSourceState::eOpen;
return true;

In the worker loop: write into mBuf->getDataStart() + writeInd*numDims (+ getAuxDataStart()), then mBuf->commitWrite(mProducerId, nSamples). Honor wraparound with writeInd % sampleCapacity().

The buffer is single-producer today (addProducer caps at 1). One source instance per buffer.

2.3 (Pattern B) Or emit directly#

Build a QByteArray in the DisplayProcessor wire format (review §2 / NetworkClient.handleMessage) and emit dataReady(bytes). WebSocketServer::setPlaying connects your source's dataReady to broadcastData for the Simulated Data-style path.

2.4 Register the type — src/core/Utils.cpp registerBuiltInTypes()#

SP::registerDataSource<SP::MyMod::MySource>("source.mymod.thing" /*, ctorArgs... */);
// Pattern A also needs its buffer registered:
SP::registerData<SP::CircularBuffer<int16, MyAux>>("data.mymod.raw");

Gate hardware behind the right #ifdef (e.g. NPX_HW_ENABLED) if it links a vendor SDK. Ctor args are forwarded by the factory (e.g. NeuropixelsSource is registered with seed slot,port,dock,parent — though it auto-detects real values in initBasestation).

2.5 Add a config profile — config/MyThing.yaml#

name: "My Thing"                 # <-- exact string shown in the UI Source dropdown
sources:
  - name: "source.mymod.thing"   # <-- registry name from 2.4
    outputs:
      - { data: "raw", name: "data.mymod.raw" }
processors:                       # optional: which sinks run for this profile
  - name: "proc.npx.display"
    inputs: [ { data: "raw", name: "data.mymod.raw" } ]

initDataSource receives this source subtree as cfg; read whatever you need from it (cfg.has_child("imro_path") is the NPX example). Configs are copied next to the exe on build.

2.6 Wire the UI dropdown — webinterface/index.html#

Add an <option> under #selectSource whose value exactly equals the profile name:. - If your source should show the probe-map / QWebChannel panel, make the option text contain "NPX" (the JS gate selectedSource.includes("NPX"), NetworkClient.js:132, and updateViewForSource, main.js:107) — or generalize that gate if you add a non-NPX module type.

2.7 CMake — add sources to the target#

In src/modules/<yourmod>/CMakeLists.txt:

target_sources(SpikesPeak PRIVATE MySource.hpp MySource.cpp)

and add_subdirectory(<yourmod>) from src/modules/CMakeLists.txt if the folder is new. Guard hardware-only files behind the NPX_HW_ENABLED-style check as neuropixels/CMakeLists.txt does.

8. Per-source web commands (the camera example)#

Full standard + recipe: ModuleCommunication.md. It documents the register → bind → invoke → teardown lifecycle, the thread-safety rule, and a worked source (NeuropixelsSource) and sink (RecordProcessor) example. This section is the short version.

To let the browser drive your source, expose Q_INVOKABLE methods — the project standard (review §7.4, "Option A"). They auto-register on the QWebChannel via the existing registerObject loop the moment your source is selected; nothing central to edit. The browser binds your object to a window.* global by a registry-name substring in NetworkClient's deviceReady handler (ModuleCommunication.md §2.2) — keep your registry name substring-distinguishable.

class CameraSource : public IDataSource {
    Q_OBJECT
public:
    Q_INVOKABLE bool   setExposureUs(int us);     // returns success → JS callback
    Q_INVOKABLE QString getSettingsAsJson() const; // returns data → JS callback
};

JS (once bound to window.activeCameraModule): cam.setExposureUs(5000, ok => …).

  • Methods run synchronously on the main GUI thread and must return promptly. Do not open a modal dialog (or any nested event loop) inside one — QWebChannel dispatches invokables synchronously, so a nested loop re-enters its machinery and crashes. Defer it with QTimer::singleShot(0, this, …). (This was a real bug — see review §9.)
  • File I/O follows the project standard (review §7.5): keep it in the browser — read a file client-side (<input type="file"> → text → a synchronous parser invokable, like loadImroFromText); write by returning text from an invokable and downloading it browser-side (like getImroAsImroText). Don't open server-side dialogs.
  • Prefer Q_INVOKABLE whenever you need a return value.
  • Do not revive handleWebCommand for this: it's a no-op hook with a known routing gap (review §7.4). It only makes sense for future fire-and-forget JSON commands, and only after that gap is fixed.

Checklist#

  • [ ] MySource : IDataSource with Q_OBJECT, 4 lifecycle methods, copy deleted
  • [ ] Pattern A: buffer fetched + addProducer + commitWrite; or Pattern B: emit dataReady
  • [ ] Worker on its own QThread; stopAcq does quit()+wait() before close
  • [ ] registerDataSource<…>("source.…") (+ registerData<…> for Pattern A) in Utils.cpp
  • [ ] config/<Profile>.yaml with name: + sources: (+ processors:)
  • [ ] <option> added to #selectSource (text contains "NPX" if it needs the probe panel)
  • [ ] target_sources in the module CMakeLists.txt
  • [ ] (optional) Q_INVOKABLE web commands
  • [ ] Builds clean (see README.md → Build)

Reference implementations: SimulatedDataSource (simplest, Pattern B) · NeuropixelsSource (full hardware, Pattern A, worker thread, Q_INVOKABLE) · SynthRippleSource (synthetic streaming).

Liveness (issue #16)#

Your worker inherits noteCycle() from IDataSourceWorker. Call it once per completed acquisition cycle, in the loop body -- never in slStartAcquiringData/slStopAcquiringData, where it reads as a permanent stall the moment acquisition begins. SourceManager polls the counter every second and reports the source stalled after 3 s of no movement, which is the only thing that distinguishes "connected and running" from "connected and silently producing nothing".

Then override the accessor so the manager can find it:

QList<SpikesPeak::IDataSourceWorker*> acquisitionWorkers() const override {
    return mWorker ? QList<SpikesPeak::IDataSourceWorker*>{ mWorker }
                   : QList<SpikesPeak::IDataSourceWorker*>{};
}

Two rules:

  • If you derive from another source, EXTEND its list, do not replace it. OneBoxSource returning only its ADC worker hid the probe worker it inherits, so a dead probe would have raised nothing.
  • Return empty while stopped. The workers genuinely do not exist between runs, and "no worker" must read as "nothing to check" rather than as a fault.

Not overriding it at all is safe -- the source is simply unmonitored -- but then a silent stall on that source is invisible. Full contract: Fdir.md section 8.5.
