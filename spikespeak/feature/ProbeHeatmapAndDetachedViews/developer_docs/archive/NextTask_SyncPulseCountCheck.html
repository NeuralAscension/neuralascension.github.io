NEXT TASK (low priority) — NI-DAQ captures a different sync-pulse count than the NPX#

Status: open follow-up, low priority — analysis side fully handled; only the capture-side source asymmetry remains. The sync aligner survives a pulse-count mismatch at either end (see the three clock/sync bugs in RippleClosedLoopAnalysis.md), and a count-mismatch warning now fires automatically (added 2026-07-21, python/spikespeak_postprocess/sync.py). This note is only about eliminating the asymmetry at the source, which the user considers not important and possibly not controllable.

What we now know (updated 2026-07-21)#

The original observation was a trailing drop: in np2_4channel_3required (2026-07-16) the NI-DAQ captured 78 sync pulses vs the NPX's 79 — it started ~0.2 s later and ended ~0.8 s earlier, missing the last NPX pulse. Tests the same day captured equal counts (76=76, 80=80), so it is intermittent, not systematic.

The 1000-detection quorum runs (2026-07-21) showed it can also drop at the START. np1_4ch_q3_asap captured 617 NI-DAQ pulses vs 618 NPX, missing the first shared edge. That is what exposed sync bug #3 (the whole-period wrap): with the drop at the start, both the start- and end-anchored offset estimates were off by a full period, so match="auto" still mis-shifted every timestamp by ~1.000 s until the modulo-period fix. So the capture asymmetry is not always trailing — a source-side fix must make both ends symmetric.

Why it (used to) matter — now defused on the analysis side#

A count mismatch is the precondition for an off-by-one that silently shifts the NI-DAQ→NPX map by a whole sync period (2 ripple cycles) and manufactures fake "orphan" stim pulses / wrong latency. All of that is fixed in analysis: match="auto" + the modulo-period wrap (bug #3 fix) pair correctly whichever end drops, the burst-anchored cross-check catches a residual whole-period shift, and the new count-mismatch warning makes the asymmetry visible immediately instead of via a garbled latency. This to-do is now purely about the hardware capture, if ever deemed worthwhile.

What a future agent could still check (if pursued) — source-side only#

  1. Stop-order timing. How is the NI-DAQ task stopped vs the NPX stream on record-stop / disconnect (src/modules/nidaq/NiDaqInterface.cpp stopAcq/slStopAcquiringData vs the NPX teardown)? If DAQmxStopTask fires slightly before the probe stops, the last shared sync edge lands after the NI-DAQ window → trailing drop. Stopping the probe first, or draining one more NI-DAQ block, would make it symmetric.
  2. Start jitter. The NI-DAQ started ~0.2 s after the NPX in the trailing-drop case and earlier in the start-drop case — confirm the start-order and whether the first shared sync edge reliably lands inside both windows. A start-drop is the more dangerous one (it fed bug #3).

The robust fix (recommended direction): a non-periodic sync code, not a square wave#

The real cure is to stop using a periodic ~1 Hz square wave as the sync signal. Every bug above (both off-by-ones) is only possible because the train is periodic — a whole-period shift is indistinguishable from a correct pairing, so a dropped edge at either end is ambiguous. Make the sync signal self-identifying and the ambiguity disappears entirely:

  • Drive the shared sync line from an external generator that emits a non-repeating, decodable pattern — think "a QR-code / barcode over time" rather than a metronome. Options, roughly in order of effort: a PRBS / Gold / Barker code (each window of edges is locally unique, so any captured segment self-locates by cross-correlation), or a serially-encoded incrementing counter / timestamp (each "pulse group" literally carries its own index).
  • Both acquisitions then align by matching the code content, not by counting edges from an end — a dropped or extra edge can never cause a whole-period slip because no two positions look alike.
  • This also removes the burst-anchored-vs-nearest-before cross-check as a necessary safeguard (it stays useful as a check), and makes the count-mismatch warning informational rather than load-bearing.

This is the recommended long-term direction if the capture asymmetry is ever worth eliminating at the source. It is a hardware + a small decoder change, not a probe/NI-DAQ stop-order tweak — and it is more robust than any stop-order fix could be. Until then, the analysis-side handling above is sufficient.
