Live-view rendering performance — SciChart limits, what we tried, and the off-ramps#

Everything we measured about rendering hundreds of streaming channels in the SpikesPeak browser live view (SciChart.js v5.2.35), what optimizations moved the needle (spoiler: almost none), why, and the concrete paths to go faster if we ever need to. Raw benchmark numbers live in benchmarks/CHANNEL_DENSITY_REPORT.md; this doc is the narrative.

TL;DR#

  • SciChart renders on ONE main thread. It has no OffscreenCanvas/Web-Worker mode, and its .wasm is single-threaded (it uses WASM-SIMD, not threads), so COOP/COEP/SharedArrayBuffer do nothing for it.
  • On this box (RTX 3060 Ti, 16 cores) the wall is ~320 on-screen line series (e.g. 4 columns × 80): the main thread saturates at 100%, FPS drops to ~40. Below ~160–200 series it's a solid 60 fps.
  • The bottleneck is the DRAW of many series, not data ingestion. We moved the parse to a Web Worker and it changed nothing — because appendRange + SciChart's draw dominate, and both must stay on the main thread with SciChart.
  • There is no SciChart-side software fix that recovers 60 fps at 320 series. The real fix is to move the WebGL drawing off the main thread — which means a different renderer (SciChart can't). Keep the density ≲ 160–200 for now (the per-column channel dropdown lets users dial it).

Measured SciChart values (this desktop, 1920×1080, sim NP2 384-ch RAW @ 30 kHz)#

On-screen series = columns × channels-per-strip. Cost scales ≈ linearly with series count; FPS holds 60 until the main thread saturates, then collapses.

Runtime facts confirmed live: self.crossOriginIsolated === false, SharedArrayBuffer === undefined, navigator.hardwareConcurrency === 16, GPU = ANGLE/D3D11 RTX 3060 Ti. The GPU and 15 CPU cores are idle while the one render thread pegs.

What we tried (and the measured result)#

Attempt What Result Why
E — SciChart best-practices fifoCapacity, isSorted, containsNaN, batched appendRange with typed-array subarrays were already in place; we added SciChartDefaults.wasmBufferSizesKb = 32768 No FPS change (4×80 still ~40 fps / 100 %) That's memory-fragmentation tuning, not a frame-rate fix. The append path was already optimal.
A — Web Worker for data ingest A "transform worker": moved the binary parse + per-sample offset-baking off the main thread; posts transferable Float64Arrays; main thread only does appendRange + draw. Implemented + verified (worker active, traces render, graceful fallback). No gain at ANY density (4×40 = 65 % vs 63 %; 4×80 still ~43 fps / 100 %). Reverted. The parse was never the bottleneck. The draw of hundreds of line series (+ appendRange) dominates the main thread, and neither can move off it in SciChart. The worker round-trip offset the small parse saving.
B — SciChart in a Worker (OffscreenCanvas) (researched, not attempted) Not possible SciChart is DOM-coupled (interaction, tooltips; our channel labels are DOM overlays). No OffscreenCanvas/worker support.
D — COOP/COEP → SharedArrayBuffer (researched, deliberately skipped the C++ rebuild) Pointless SciChart's .wasm is single-threaded regardless; it uses WASM-SIMD. crossOriginIsolated does nothing for it.

The lesson: the "you have 16 cores, 1 is used" framing was correct, but the movable work (parse) wasn't the actual limiter. Always measure before believing a threading fix. SciChart's single-threaded draw is the hard floor here.

Optimizations that DON'T apply / are already done#

Per SciChart's own perf guidance, most tricks are already in the codebase or moot: - Single-surface-with-y-offset (all channels on one surface, offset in Y) — this is exactly what each ChartColumn already does internally (baked yOffset, one hidden Y axis, drawLabels:false). - Suppress axis/gridline drawing — already off (drawMajorGridLines:false, drawLabels:false). - FIFO typed-array series — already on (fifoCapacity, isSorted, containsNaN). - SubCharts API (SciChartSubSurface, consolidate the N column surfaces → 1 surface / 1 draw loop) — the ONE untried SciChart lever. Surfaces already share one WebGL context by default, so the expected win is only the per-surface overhead the data showed (~6 %: 80 series as 1×80 = 22 % vs 4×20 = 28 %). Not a fix for the 320-series wall; a modest polish at best, for a non-trivial refactor of ChartColumn.

The real fix (future): move WebGL drawing off the main thread — a different renderer#

The only way to break the ceiling is to render in a Web Worker via OffscreenCanvas, so the draw runs on an idle core and the GPU is fed directly. SciChart can't; several alternatives can, all keeping the HTML/CSS/JS UI (you wrap your own headers/labels/sliders around the canvas — the flexibility we want). (Researched via agy web-search 2026-07-12; treat the specifics as leads to verify with a small proof-of-concept, not gospel.)

Path 1 — Custom WebGL2 in a Worker (OffscreenCanvas) [recommended if we DIY]. Draw the line strips yourself in a worker; ingest the WS binary in the worker and push floats straight to GPU vertex buffers (zero-copy transferables); the main thread does nothing. Max performance (1000+ series @ 60 fps, ~0 % main-thread), MIT-friendly. Cost: you write the shaders, the scrolling window, and the axes/labels (but axes/labels can stay HTML/CSS — our strength). Reference implementations: - webgl-plot — MIT, WebGL line plotter, worker/OffscreenCanvas-capable, oscilloscope-style, 1000+ lines; basic (no built-in axes/legends → you supply the chrome). https://github.com/danchitnis/webgl-plot - narration.studio — WebGL2-in-a-worker high-density waveform drawing. https://github.com/stevenwaterman/narration.studio - regl / twgl — thin WebGL helpers, fully worker-compatible, if we want a bit more structure than raw GL.

Path 2 — LightningChart JS (commercial drop-in). Native OffscreenCanvas/worker rendering (reportedly since ~v8.3), production axes/zoom/legend, 800+ series @ 60 fps in a worker. Cost: proprietary license (~$2,750/dev — verify current pricing/version). Least effort, but a paid dependency. https://lightningchart.com/js-charts/docs/

Path 3 — SciChart SubCharts refactor (keep the current license). Consolidate to one surface (SciChartSubSurface). Low-to-medium effort, reuses SciChart — but still single-threaded on the main thread, so it only trims the ~6 % per-surface overhead and will hit the same wall at 768+ channels. A stopgap, not a solution.

What high-channel neural web viewers actually do (context): Neurosift (Flatiron / J. Magland) uses custom Canvas2D/WebGL + client-side level-of-detail decimation + WASM loaders (LINDI); NWB Explorer pre-downsamples server-side; real-time EEG/oscilloscope monitors write custom WebGL line-strip shaders in workers. The common thread: decimate to pixels + draw off the main thread, not a heavyweight main-thread chart library.

Recommendation: if/when SciChart's ceiling actually blocks the science, the best fit for "keep the web UI, swap the renderer" is Path 1 (webgl-plot or custom WebGL2 in a worker) — MIT, off-main-thread, and it leaves all the UI chrome to HTML/CSS/JS. Path 2 if we'd rather buy than build. This is a separate project; not urgent while ≤ ~200 on-screen series covers the workflows.

Practical guidance for now#

  • Keep total on-screen series ≲ 160–200 for rock-solid 60 fps (e.g. 4 × 40, or 2 × 80). 240 (4×60) is usable but at ~86 % main-thread with occasional hitches; 320 (4×80) drops frames — for a quick look only.
  • The per-column channels dropdown (Auto/20/40/60/80/120, independent per column/row) lets users spend the budget where they want it — dense on one strip, sparse on the others.
  • Real multi-band loads (NP1 AP+LFP + NI-DAQ + ripple detection + recording) add main-thread work on top, so the practical ceiling is lower than the single-band sim numbers.
