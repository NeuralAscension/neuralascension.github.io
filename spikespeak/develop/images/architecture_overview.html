SpikesPeak — Architecture Overview#

Current as of 2026-09-02. This is the page to read first; the prose is checked against the files it cites (python/tests/test_doc_citations.py fails the gate on a dead file:line), and the diagrams are generated from the code, so neither can drift silently.

The pipeline diagrams here are generated from the code, not drawn. scripts/make_architecture.py parses the source/processor registry in src/core/Utils.cpp and every config/*.yaml, and scripts/build_docs.py re-runs it on each build (~0.15 s). Add a source, a processor or a config and the pictures follow on the next python scripts/build_docs.py. The predecessor was a hand-maintained PlantUML description that drifted and, because nothing rendered it during the build, shipped invisible; the last hand-drawn class diagram was removed on 2026-09-01. How the generator works, and its one deliberate second source of truth, is in ../developer_docs/ArchitectureDiagrams.md.

The diagrams on this page ARE committed, and that is deliberate. The book's own copies (developer_docs/images/architecture*.svg) stay git-ignored and are rebuilt on every build, but GitHub renders this page from the repository, so everything it embeds has to be in the repository. python scripts/make_architecture.py --check reports drift without writing anything, and python/tests/test_committed_docs_render.py fails the gate if a committed document ever embeds a file that is not committed.

The whole system, generated#

Every profile the backend can load, in one graph — dense on purpose. It is the map for what exists; for a single experiment use the per-profile diagrams at the end of this page.

Each diagram is a top-down pipeline: Config (the YAML profile, labeled with its internal name: — the string the GUI and CLI actually select) → DataSource → Data (the named bands it publishes) → DataInterpreter → Processor → Sink (the files a recording writes). A config's identity is that name: field, never the filename (../developer_docs/ConfigReference.md). Orange dashed edges are wired by C++, not by the profile — see §2.

What SpikesPeak is#

A Qt/C++20 real-time neural acquisition and closed-loop stimulation backend with a browser front-end. The backend is a windowless QApplication that serves the UI over HTTP :8234 and carries all live traffic over one WebSocket :1234. Data follows a single-producer / multi-consumer ring-buffer model with a thread per source and a thread per sink; it is judged on milliseconds of latency and samples not dropped, so nothing runs that nobody asked for and nothing is added to the 30 kHz path.

Hardware/Sim ─►[Source]─► CircularBuffer ─►[Sinks: Display / Record / LFP / Spike / Ripple / Audio]─► browser / disk / stim
   (worker thread)        (1 producer,          (each in its own thread)
                           N consumers)
        browser ◄── WebSocket :1234  (binary waveform stream + JSON commands + QWebChannel RPC)
        (served HTTP :8234)

CircularBuffer<tData, tAux> (src/core/CircularBuffer.hpp): the source is the single producer (addProducer → write at getDataStart() → commitWrite(id, n), which bumps the sample count and releases one semaphore per waiting consumer). Each sink is an independent consumer (addWaitingConsumer → block on waitForAvailable(id, ms, &n) → read via constDataAt / constAuxDataAt → advance its own read marker), so Display, Record and the band filters read the same stream at their own pace. A sink that derives a new stream (proc.lfp, proc.spike) is itself a producer into a downstream buffer.

1. The connect path, end to end, and its three stop points#

Picking a Source in the GUI sends a JSON selectSource on the WebSocket (channel 0x1000, §6). WebSocketServer hands it to MainController::handleConnectRequest (src/core/MainController.cpp:97), which builds a SourceManager and a ProcessorManager, instantiates the profile's source (initDataSource) and its processors (configure), gives each processor its own QThread, and registers the source's Q_INVOKABLE object on the QWebChannel. Three places on that path stop and ask instead of guessing, and each reaches the operator through a sink that outlives the failing connect (a queued signal from a connect that then fails is never delivered — the trap that hid the third of these for weeks):

  1. Which basestation? source.npx.auto is not a registered module. SourceManager (src/core/SourceManager.cpp:54) resolves it to source.npx.onebox or source.npx.pxi from a scan that opens nothing, and refuses when a OneBox and a PXIe are both attached; the GUI raises the basestation-choice dialog and the menu then offers the explicit OneBox / PXIe / PXIe + NI-DAQ (../developer_docs/SourceSelection.md).
  2. Which probe? Two probes on one basestation: NpInterface parks the port list in ConnectChoice (src/core/ConnectChoice.hpp), the connect fails, and WebSocketServer (src/core/WebSocketServer.cpp:345) takes the parked question and broadcasts probe-choice; the operator's pick goes back as setProbePort. Fixed 2026-09-02 (Status §89).
  3. Could not connect. Any other failure produces the Could not connect dialog (src/core/WebSocketServer.cpp:283), and ConnectAttemptLog (src/core/WebSocketServer.cpp:383) counts it per transport: a second failed connect on the same transport stops the session before the next acquisition can fault (#54) — ../developer_docs/HardwareFaultGuard.md. A probe-less open and the "which probe?" question both count.

2. Four processors the profile does not wire, and the hasData rule#

ProcessorManager provisions four processors itself, after the profile's own, so a profile need never mention them (src/core/ProcessorManager.cpp:128, :193, :234):

processor input output provisioned when
proc.lfp data.npx.raw data.lfp the source has a raw band and no native LFP — a 2.0
proc.spike data.npx.raw data.spike same
proc.audio data.npx.ap, else data.npx.raw data.audio any probe band exists
proc.rippledetector data.npx.lfp (a 1.0's native band), else data.lfp — an LFP band exists and the profile declared no detector; created idle until the dock's Start

The rule that makes those decisions correct: test with hasData(), never getDataByName(). The getter creates any registered type on first use, so it answers "yes" for every band on every profile — which once bound an auto-provisioned detector to the 1.0 native band on a 2.0 probe, where nothing ever wrote it, and the module sat at zero samples forever while reporting itself healthy. The derived bands are the worked example of "available and off": ../developer_docs/DerivedBands.md §5. The generator draws these four edges orange and dashed because "the profile wires this" and "the program wires this" are different claims.

3. Faults, liveness, and the confirmed-state rule#

  • Liveness is counted at the source, per worker. A source exposes its acquisition workers for polling (src/core/IDataSource.hpp:40); source liveness means data committed and processor liveness means the loop turned, which differ on purpose — a dead probe once reported a healthy rig for three and a half minutes because the wrong one was read (../developer_docs/Testing.md §4). The GUI's System pill (webinterface/SystemMonitor.js, #16) shows the counters.
  • Unrecoverable faults stop the session in a dialog (webinterface/HardwareFaultModal.js), whose only exits are restart or close — the #54 guard above is the first user.
  • The GUI announces CONFIRMED state, never REQUESTED. Play, record, the probe map, the source pick, the low-latency state: every control reflects what the backend has reported back, not what was clicked. The same defect was written four times before the rule got an invariant test (../developer_docs/InvariantTests.md, tests/gui/state_consistency.py).

4. Play, Pause, Disconnect — the order, and the bounded teardown#

  • Play (handlePlayRequest): processors start first — each thread starts, the processor adds its consumer and blocks on the buffer, then emits sigIpStarted. When all are ready, SourceManager calls startAcq() on the source, which spins up its worker and begins producing. A sink that never emits sigIpStarted would stall the start.
  • Steady state: worker loops → commitWrite → wakes consumers → Display serializes a min/max batch → sigIpDataReady → WebSocketServer::broadcastData → browser.
  • Pause: stop the source worker first, then signal the processors to stop and quit their threads.
  • Disconnect (src/core/MainController.cpp:172): if still streaming, pause first — the live worker writing the AI and DI buffers used to race the teardown and crash the backend — then close the sources, clear the registries (which deletes the buffers) and tear down the managers.
  • Every vendor call in the Neuropixels teardown is bounded (src/modules/neuropixels/NpBounded.hpp over src/core/BoundedCall.hpp, since 2026-08-21), so a wedged basestation no longer hangs shutdown. The rule it protects: never force-kill the backend with a probe or OneBox open — the FT601 USB handle is released only on a clean exit, and a kill costs a physical power-cycle. Shut down with the WebSocket quit or the GUI's Disconnect; the backend also quits itself ~2 s after the last client disconnects.

5. The low-latency graph (#80)#

ASAP delivery is a runtime request on a module's data path, not a profile. Every node that can carry it implements ILowLatencyCapable (src/core/LowLatency.hpp:45 — supportsLowLatency, exposesLowLatency, isLowLatency, lowLatencyPending, setLowLatency) and sits in the graph as an IGraphNode (src/core/LowLatency.hpp:94), so a request on a processor propagates upstream to the source that feeds it. The wire command is {command:"lowLatency", module, value} (src/core/WebSocketServer.cpp:1425); the reply is a lowLatencyState broadcast carrying, per module, active and pending — a source applies the flag at its next startAcq, so it reports pending until Play. Three clients make the request and wait for the confirmed state: the GUI's ⚡ ASAP tab (webinterface/LowLatencyModule.js), the control CLI's asap verb (python/spikespeak_cli.py), and ripple_tools/rig.py's set_low_latency() + wait_low_latency(), which the latency tooling uses instead of the five *Asap.yaml profile copies deleted on 2026-09-02 (../developer_docs/LatencyProfiling.md).

6. Transport: one WebSocket, triple-multiplexed, and ports as options#

  • HTTP :8234 — a QTcpServer serves webinterface/ from the working tree (edit a file, reload the page) and, by default, opens the UI in a dedicated browser app-window (--tab for a tab in the operator's browser, --no-browser for none).
  • WebSocket :1234 carries three logical channels: the binary waveform stream ([streamId][nPts][ts,(min,max)×nCh]…); JSON app commands (id 0x1000: selectSource, setPlaying, Disconnect, lowLatency, quit …, and the events back — deviceReady, guiStatus, systemState, lowLatencyState); and QWebChannel RPC (id 0x1001) for per-module Q_INVOKABLEs — the probe map, recording, the OneBox and NI-DAQ panels. The old binary-command path through CommandDispatch is gone but for one subscriber, AudioProcessor (../developer_docs/ModuleCommunication.md).
  • Both ports are options — --ws-port and --http-port (src/main.cpp:536) — so two backends can share a machine (the GUI test runner runs four). Config.js ships ws://localhost:1234, which is right for a normal run and wrong for a custom port, so the HTTP server rewrites Config.js on the way out with the port actually in use (src/main.cpp:107).
  • Lifecycle: a 2 s grace timer starts when the last client disconnects and quits the app on timeout; a page refresh cancels it.

8. The two stimulation paths#

  • Network stimulator — proc.rippledetector fires a UDP fire through src/modules/stimulation/StimulatorClient.cpp to the Raspberry Pi stimulation server, which drives the AM Systems 2300. Enable and arm are separate, and both are required; the ripple dock's ⚡ Test Fire exercises the path without a detection. Closed-loop latency, threshold crossing to the pulse on the NI-DAQ, is measured offline (../developer_docs/ClosedLoopDriving.md, ../developer_docs/LatencyProfiling.md).
  • OneBox DAC — with dac_trigger: true the same detection raises a pulse on the OneBox's DAC0 (BNC IO0, #49) through src/modules/neuropixels/OneBoxWavePlayer.cpp, and dac_trigger_order says whether the DAC or the network fire goes first; the OneBox ADC records the stimulus back (data.npx.adc, and the comparator band data.npx.adc.di).

Per-profile pipelines#

One diagram per config/*.yaml, generated with the rest. These are the useful ones day to day: they answer "what does this profile actually wire up" without reading the YAML.

Neuropixels — the profiles you actually select

Neuropixels uses source.npx.auto: the basestation and the probe are both read from the rig, and a machine with both a OneBox and a PXIe attached raises a choice rather than guessing — then you pick OneBox, PXIe or PXIe + NI-DAQ by name.

The Npx1Pxi / Npx2OneBox / … family below are the legacy explicit profiles, kept for reproducing old measurements and hidden from the dropdown. Npx2OneBoxDigitalIn (architecture_Npx2OneBoxDigitalIn.svg) is the one carrying the data.npx.adc.di comparator band that the OneBox dock's threshold panel configures.

Neuropixels 2.0 — hardware

PXIe

OneBox — Npx2OneBox is what the current rig runs.

Npx2OneBoxNoAdc is a measurement control, not an operational profile: it differs from Npx2OneBox in exactly one variable — whether the 12-channel ADC band exists — which is what makes it usable as the control arm of a recording-throughput measurement. A session recorded with it has no stimulus channel at all, because the closed-loop stimulus is captured through that ADC.

NI-DAQ only

No probe: the PXI-6133 analog/digital inputs alone. Useful for exercising the DAQ half of a rig independently of a probe.

Play-file (synthetic ripple) profiles

Replay a recorded or synthesised HDF5 file through the same pipeline as hardware — which is why a detector tuned on a play file behaves the same on a probe. See [../developer_docs/SyntheticSources.md].

Simulated — NPX 1.0

No hardware at all, but the same display processor, ring buffers, WebSocket and GUI as a real probe. That is what makes "run it in sim first" a diagnostic rather than a gesture: if sim streams and hardware does not, it is the rig and not the code ([../developer_docs/Testing.md] §4).
