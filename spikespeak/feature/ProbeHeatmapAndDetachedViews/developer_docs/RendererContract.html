THE LIVE-VIEW RENDERER CONTRACT#

Status: normative specification of what ships. Two renderers are under it:

file technology draws
Traces webinterface/GlRenderer.js — GlColumnRenderer WebGL2 the live-view traces, one canvas per column
Probe map webinterface/ProbeMap.js — ProbeMap canvas 2D the electrode / bank / shank map

There is no charting library. webinterface/lib/ holds qwebchannel.js and nothing else.

This document's job is to let someone change the renderer without changing what the operator sees. Where it says MUST, it is stating something an operator can see or a test can read; divergence is a bug — in the change, or in this file.

Files under specification: webinterface/ChartColumn.js, GlRenderer.js, ProbeMap.js, DataStore.js, NetworkClient.js, main.js, Config.js, style.css, toolbar.css, ImroManager.js, as of branch feature/OneBoxSupport @ 2026-08-28.

Why the renderer is shaped like this — the measured comparison against the library it replaced, the mechanism, and the buffer-layout decision — is RendererExperiment.md. This file does not repeat it. Read it before proposing a different architecture: it will tell you which of your assumptions was already tested.

1. THE INTERFACE#

1.1 Construction and lifecycle#

new ChartColumn(colIndex, startChannel, channelsPerColumn,
                mainContainerEl, dataStore, onDrawCallback, onColTracesCb)

Call site: main.js:616. MUST be pure DOM — it constructs the element tree (§3.2) and appends it to mainContainerEl. It MUST NOT touch the GPU, allocate buffers, or need await.

  • colIndex: int — 0-based; used for the chart-area element id and for onColTracesCb/onColumnPinChanged.
  • startChannel: int — a SLOT index in the depth ordering, not a channel id. buildColumns() staggers it as i * traces (main.js:615). Stored as this.bottomSlot.
  • channelsPerColumn: int|falsy — this.tracesPerColumn = channelsPerColumn || Config.TRACES_PER_COLUMN (20).
  • dataStore: DataStore — stored, never mutated except via the documented fields in §2.4.
  • onDrawCallback: () => void — () => AppController.forceXAxisUpdate().
  • onColTracesCb: (colIndex:int, rawSelectValue:string) => void — the raw string from the density <select>; '' means Auto.

Initial state MUST be: selectedShank = 0, selectedColKey = 'B', currentStreamId = null, userPickedStream = false, selectedChannelIndices = new Set(), onScreenSeries = [], onScreenLabels = [], gl = null, glChanToRow = null, glRows = 0.

await col.initialize()              // main.js:622 — async, MUST be awaited

Constructs the GlColumnRenderer on this.chartAreaDiv, installs the context-lost hook, allocates the fixed pool of tracesPerColumn display slots + tracesPerColumn label elements, and observes the chart area for resize. It does not allocate vertex buffers: draw() does that (§2.6 step 8), because the row count and the point capacity are only both known there. Nothing may call draw() before this resolves.

A lost GL context MUST be reported, not absorbed (ChartColumn.js:326-335): the column sets this.gl = null and calls window.app.reportError(...). An empty live view is exactly what a dead probe looks like, and this view's whole job is to be trusted about whether data is arriving. Every this.gl touch point is null-guarded so a lost context stops drawing rather than throwing.

col.destroy()                       // main.js:588

MUST destroy the renderer first (gl.destroy(), ChartColumn.js:859), then disconnect the ResizeObserver, empty onScreenSeries, and remove this.container from the DOM. It MUST NOT touch DataStore — the per-channel display state there outlives every column.

Teardown MUST NOT raise a fault that did not happen. GlColumnRenderer.destroy() sets its _dead flag before calling WEBGL_lose_context.loseContext(), because that call fires the webglcontextlost listener synchronously — without the flag, every ordinary column rebuild (orientation flip, column count, density change) reported a graphics fault to the operator.

1.5 The renderer surface#

GlColumnRenderer is the only renderer object, and this is the whole of its public surface. A replacement MUST present the same one; every call site is listed so you can see there is nothing else.

new GlColumnRenderer(hostEl)                       // ChartColumn.js:309 — appends a canvas filling hostEl
gl.onContextLost = () => {…}                       // ChartColumn.js:326 — assignable hook, not an event
gl.setLayout(rows, capacity, palette)              // ChartColumn.js:719 — (re)allocate; DROPS held samples
gl.setYRange(min, max)                             // ChartColumn.js:707 — plot coordinates, from draw()
gl.setXRange(min, max)                             // main.js:762      — seconds, per column per batch
gl.appendRow(row, xs, ys, n)                       // NetworkClient.js:209
gl.commitFrame()                                   // NetworkClient.js:216 — one per column per frame
gl.setRowColor(row, hex)                           // ChartColumn.js — color of the channel on that row
gl.clearRow(row)                                   // ChartColumn.js — row rebound to a new channel
gl.clear()                                         // main.js — relayout / baking change
gl.pointCount()                                    // main.js:284 — points held on row 0, -1 if unavailable
gl.destroy()                                       // ChartColumn.js:859
gl.rows                                            // read by tests/gui/live_view.py
glAvailable()                                      // exported; true when the browser can run it at all

Normative properties of that surface:

  • appendRow, setXRange and setYRange MUST NOT paint. They record and request; painting is coalesced (§2.5). A renderer that paints synchronously in any of them fails this contract.
  • commitFrame() is the single upload point. appendRow writes only the CPU mirror.
  • setLayout drops the samples it held, and that is correct. The vertical offset is baked into Y at append time (§2.4), so samples taken under the previous layout carry the previous row positions. Same reasoning as AppController.relayoutByDepth().
  • pointCount() MUST answer out of the renderer's own storage. It is the anti-blank-surface guard (§1.6); a number derived from anywhere else can report health for a canvas that draws nothing.
  • Buffer allocation does not go through a renderer handle. DataStore.initializeStream(streamId, numChannels) and DataStore.updateWindowSize(seconds) take no renderer argument and hold no samples. Reintroducing such a parameter — or a col.xAxis.visibleRange writer — is a regression: it is how stream registration once came to be gated on a graphics handle (T-22).

1.6 Probes the test suite and the benchmark read (MUST keep working)#

  • window.__glColumns (main.js:626) — the columns with a live renderer. It is not test scaffolding: NetworkClient.js:195-218 walks it as the per-frame delivery list, precisely so the hot path is an array walk instead of reaching for window.app. It must keep both meanings.
  • GUI harness, tests/gui/_harness.py:481: (window.__glColumns || []).length must be non-zero after live_view(). The harness refuses to run otherwise, because an empty canvas would let the whole suite pass vacuously.
  • GUI suite, tests/gui/live_view.py SERIES_PROBE: app.columns[i].gl.rows must be an integer > 0 for at least one column, and must not throw.
  • GUI suite, live_view.py / stream_options.py: at least one <canvas> per column with clientWidth > 0 and clientHeight > 100 (60 in stream_options). An SVG-only or DOM-only renderer fails the suite as written.
  • Benchmark: window.__benchPointCount(colIndex) (main.js:281-286) → the column renderer's own occupancy; -1 for no such column or a lost context. It saturates at calculateCapacity() (2400 at a 1 s window), so it proves "streaming and bound" and nothing finer. benchmarks/cdp_bench.py calls it with no fallback, deliberately: a fallback that reads some other object's count keeps returning a plausible number after the renderer changes.

If you re-point any of these probes you MUST prove the new one can fail — inject a regression, watch it go red, revert — per CLAUDE.md. Two of them have already been vacuous once.

2. THE DATA CONTRACT#

2.1 Wire frame (informative for the renderer, normative for anything touching NetworkClient)#

One WebSocket binary message = one frame = one stream, little-endian, IEEE-754 float32 (DisplayProcessor.cpp:291-293, forwarded byte-for-byte by WebSocketServer::broadcastData, WebSocketServer.cpp:797-802):

[u8 idLen][idLen bytes UTF-8 streamId][u32 numChannels][u32 numBins]
then numBins × { f32 tsSeconds ,  numChannels × ( f32 min , f32 max ) }
  • streamId ∈ ap, lfp, raw, adc, nidaq (nidaq_di is specified, not shipped).
  • numChannels is per stream: 384 for a probe band, 12 for the OneBox ADC, device count for NI-DAQ. Never assume 384 (DisplayProcessor.cpp:456-457).
  • min is written first, then max (DisplayProcessor.cpp:458-470; read at NetworkClient.js:133-134). Swapping them still renders — inverted segments — so it fails silently.
  • Timestamp is float32 seconds at the bin MIDPOINT.
  • Units are not on the wire: ap/lfp/raw arrive in hundreds-of-µV (Config.MICROVOLTS_PER_DISPLAY_UNIT = 100); adc/nidaq arrive in volts.
  • Payload start offset is 1 + idLen + 8 — 11/12/14 bytes, not 4-byte aligned, which is why NetworkClient.js:87 copies (new Float32Array(event.data.slice(offset))).

2.2 Rate and volume — what the renderer must sustain#

Quantity Value
Frames per second per stream 50 (20 bins × 1 ms of data)
Timebins per frame 20 (timebins_per_update, 20/20 in every shipped config)
Bin width 1 ms = 100 ticks of the 100 kHz timestamp clock
Points appended per channel per frame 40 (20 bins × min+max) = 2000 pts/s/channel
Bytes/s, one 384-ch stream ~3.08 MB/s (61,532 B/frame for raw)
Worst shipped case NP1 ap + lfp + nidaq concurrently

Each bin contributes two points at the same x, so a bin renders as a vertical min→max segment. Any renderer that assumes strictly increasing x will collapse or mis-draw these.

2.3 Where the samples live — there is exactly one copy#

DataStore holds no sample buffer at all. Per channel of each stream it holds display state only (DataStore.js:62-77):

{ yOffset, yOffsetInterleaved, zoom, color, acMin?, acMax? }

The samples exist once, in the column renderer that is going to draw them: NetworkClient hands each decoded batch straight to GlColumnRenderer.appendRow() (NetworkClient.js:195-218). There used to be a pair of chart-library FIFOs per channel that the renderer read back out; that second copy was the expensive half of the old renderer.

Consequence a replacement must accept: nothing else can hand the renderer the data again. If the renderer drops its buffers those samples are gone, and the only correct recovery is to draw what arrives next. setLayout() does exactly that, deliberately.

Capacity (DataStore.calculateCapacity(), DataStore.js:47-50):

cap = ceil(REFRESH_RATE_HZ(50) * POINTS_PER_UPDATE(20) * 2 * windowSeconds * CAPACITY_BUFFER_MULTIPLIER(1.2))

= 2400 points/row at the 1 s default, 24 000 at 10 s. DataStore.updateWindowSize() only records the new number; the reallocation happens in the next draw(), and it drops the held samples — correct, because the window changed and the points it held no longer span it.

Buffer layout — series-major, double-length, compacted (GlRenderer.js:21-33). Row r owns a contiguous span of 2 * capacity points and is written sequentially; the visible window is drawArrays(LINE_STRIP, rowBase + head - capacity, capacity) — ONE contiguous span, so no ring-wrap segment stitches the newest sample to the oldest across the screen. When a row's head reaches the end, the last capacity points are copied to the front and the head resets: one larger upload roughly once per second, and nothing per frame.

A future change may pick a different layout, but it must clear the bar this one was chosen against. Time-major — one contiguous bufferSubData for the whole frame — measured up to 12× cheaper on upload, and is not used, because a time-major ring cannot express "draw the last window as one strip" through a static strided index buffer: the wrap point becomes a visible slash across every trace. The price of series-major is 0.36 ms/frame at 320 series, about 2 % of a 17.4 ms budget. Revisit the layout when 0.4 ms is the thing in the way, and only with the seam solved.

2.4 y-baking — the single most important rule#

The vertical position and the vertical scale of a trace are baked into the Y samples at append time by NetworkClient (NetworkClient.js:136-184). The renderer MUST NOT re-offset, re-scale, auto-range, or auto-fit anything. Y values are absolute plot coordinates.

probe (numCh === 384) and streamId !== 'raw':   s = v * channel.zoom
probe and streamId === 'raw':                   AC-couple: envelope min/max with DECAY = 0.9995,
                                                baseline = midpoint, s = (v - baseline) * zoom,
                                                DELIBERATELY NOT CLAMPED
non-probe (adc / nidaq):                        AC-couple as above,
                                                gain = (CHANNEL_VERTICAL_SPACING / NIDAQ_UNITS_PER_ROW) * zoom,
                                                then HARD-CLAMPED to ±0.47 * CHANNEL_VERTICAL_SPACING
y = channel.yOffset            + s   -> the packed baking       (NetworkClient.js:183)
y = channel.yOffsetInterleaved + s   -> the interleaved baking  (NetworkClient.js:184)

Consequences the renderer must accept: a zoom or offset change does not alter samples already held, so the view re-scales gradually over one window; AppController.relayoutByDepth() (main.js:677-700) sets yOffset = slot * 3.0 and yOffsetInterleaved = slotI * 3.0 precisely because old samples carry the old layout.

Which baking is produced is gated by dataStore.appendPacked / appendInterleaved, recomputed by AppController.updateAppendModes() from every column's selectedColKey and whether its stream is 384-wide. Which baking a column receives is its glUsesInterleaved flag, set in draw().

The renderer's only vertical control is setYRange(), and the shader is a plain linear map into clip space (GlRenderer.js:48-52). There is nowhere for a hidden transform to live, and that is the point.

2.5 What happens per frame#

There is no per-frame draw call in the data path. Per decoded frame the app does exactly:

  1. NetworkClient bakes the batch once per channel, then walks window.__glColumns and calls appendRow(row, xs, ys, n) for each column showing that stream, using glChanToRow[ch] to find the row and glUsesInterleaved to pick the baking;
  2. one commitFrame() per column showing that stream — the single GPU upload;
  3. AppController.forceXAxisUpdate() calls gl.setXRange(latest - windowSize, latest) on every column;
  4. one textContent write of the time display.

Therefore the renderer MUST coalesce to at most one paint per animation frame regardless of how many appends and range writes arrive (50/s per stream, ×N streams — on a 3-stream 4-column config that is ~600 range writes/s).

And it MUST NOT rely on requestAnimationFrame alone. rAF does not fire in a window Chrome believes is occluded or backgrounded, which is the condition the GUI suite and the benchmark both run in. GlColumnRenderer.requestPaint() therefore asks rAF and sets a 24 ms timer (~1.5 frames at 60 Hz); whichever fires first paints and cancels the other, so a healthy foreground window still paints on the vsync clock and nothing double-draws. Removing either scheduler is a regression — see T-6, and AgentTraps.md §5f.

X range is not set here. A row is fed because glChanToRow points at it and for no other reason: isVisible and stroke are written and read by nobody (T-30).

3. THE VISUAL CONTRACT#

Everything below is a MUST unless marked otherwise. The test of a renderer change is that the operator cannot tell it happened.

3.1 Plot area#

  • Background — and the one value in this document that exists nowhere else. The plot ground is css .chart-container-wrapper { background: radial-gradient(circle, #3C3C3F 0%, #1C1C1E 100%); } in webinterface/style.css:365-376. It originally came from the chart library's default dark theme, was in no stylesheet, and vanished with the bundle; it has been reproduced explicitly. The bundle is deleted, so if that CSS rule is removed there is nowhere left to recover these values from except this paragraph. Reinstate them from here.
  • The trace canvas clears to TRANSPARENT (gl.clearColor(0,0,0,0), GlRenderer.js:117) so the gradient shows through, which is also why the gradient lives on the wrapper and not on the canvas. A renderer that paints an opaque ground silently flattens the plot background to a flat color — it will look fine in isolation and wrong beside anything that remembers the gradient.
  • Padding around the plot: none. THE PLOT AREA IS THE DIV. The canvas is position:absolute; inset:0 inside #chart-container-N, which is 100% × 100% of .chart-container-wrapper. There is no axis strip and no surface inset to account for. This also fixed a real latent bug: the channel-label overlay used to be pinned to the library's inset plot rect while the traces were drawn into the full div, so every label sat slightly high of its trace. Any future renderer that insets its plot area must inset the label overlay by the same rect, or it reintroduces that misalignment.
  • No gridlines. No axes. No tick labels. No annotations. No legend. No zoom/pan/cursor modifiers. Nothing paints but the traces. Vertical position comes from setYRange and the baked Y; horizontal from setXRange.
  • Traces: gl.LINE_STRIP, one drawArrays per row, 1 px, no markers, no fill. The context is created with antialias:false, depth:false, stencil:false, preserveDrawingBuffer:false (GlRenderer.js:93-96) — MSAA on a 1 px line strip costs fill rate for a difference nobody asked for. The drawing buffer is the host box × min(devicePixelRatio, 2). A stroke wider than 1 px is not portably available from a GL line and would have to be built from geometry; nothing needs one.
  • Palette — keyed to the READ-OUT CHANNEL, and it must stay that way. Config.PALETTE is seven entries: #FF4500, #FFD700, #32CD32, #00BFFF, #6495ED, #DA70D6, #FF69B4, assigned once per channel at DataStore.initializeStream as PALETTE[channelIndex % 7] and never reassigned. draw() pushes each row's color with gl.setRowColor(i, channels[ch].color) as it binds the row, so a trace keeps its color when it moves rows — which is the entire point: color is how an operator follows one channel while paging the slider. Because depth ordering permutes channels into rows, the on-screen sequence is deliberately NOT a clean repeating 7-cycle; a clean cycle down the column is the signature of the bug. Do not re-key the palette to the row. setLayout() fills the color buffer with PALETTE[row%7] but that is a placeholder for rows never assigned, not the keying. Keying by row was shipped briefly in the WebGL renderer and repainted a trace a different color on every scroll; see SpikesPeak_Status.md 62. setRowColor guards on equality, so the re-upload costs one call per row per rebind, not per frame.
  • Y direction: NORMAL. Offsets grow upward, so slot 0 (tip / deepest) sits at the BOTTOM and electrode numbers increase upward.

4. THE PROBE MAP#

webinterface/ProbeMap.js draws the electrode / bank / shank map into #probe-map-root with canvas 2D. It is constructed once per device by initProbeMap() (ImroManager.js:363), which is called from NetworkClient.js:416-417 when a probe appears. ProbeMap.js is loaded as a classic script before ImroManager.js (index.html:11-12) and publishes window.ProbeMap and window.ProbeMapNumberRange; that order is load-bearing.

4.1 The API is deliberately old-fashioned — keep it#

ImroManager builds the whole map through two calls per series, clear() and appendRange(xs, ys, metas), and positions everything else in data coordinates. ProbeMap keeps exactly that surface, which is why the ~700 lines of electrode/bank/shank logic in ImroManager did not change when the library was removed. That was the trade: a slightly dated API here bought a rewrite that could not silently change which electrode an operator selected. A change that "modernises" the API pays that risk back.

Surface Contract
map.addSeries(name, style) → ProbeSeries style = {fill, stroke, radius, labelSide:'left'\|'right'\|null}
series.clear() / series.appendRange(xs, ys, metas) metas[i].text is the label; a series appended without metas draws no labels, which is how NP2.0 suppresses 5000 electrode numbers it has no room for
map.xAxis.visibleRange = new ProbeMapNumberRange(min, max) the spelling the call sites already used; yAxis likewise
map.addShaft(...), map.addTip(...), map.setSelectionBox(...) rectangles and the arrow tip, in data coordinates, with reactive isHidden / x1,x2,y1,y2
map.destroy() cancels the pending frame, disconnects the ResizeObserver, removes the canvas

4.2 What it MUST keep doing#

  • Coordinates. Data x grows right; data y grows UP (row 0 is the probe tip, at the bottom), so the y transform flips because canvas y grows down. Nothing auto-ranges — ImroManager sets both ranges explicitly for NP1.0 and NP2.0.
  • The plot fills the canvas. There are no axes to inset it, so xToPx/yToPx are plain linear maps that are valid immediately. The predecessor had to read a layout-dependent rect and could only do so after layout; that is what left a visibly off-center shank tip. The arrow tip is now drawn from the shaft's data-coordinate width, so there is no cached pixel width to go stale.
  • Reactive writes schedule exactly one redraw — and writing the SAME value must schedule none. ImroManager relies on a property write repainting the map in fifteen places (six selectionBox.isHidden writes, the drag's y2, and setShankVisuals' eight). Requiring a manual requestDraw() at each site means the first one anybody forgets leaves the operator looking at a stale probe map, which looks exactly like a working one. The equality guard in reactive() is the other half of the contract: an unconditional reactive write feeds itself a redraw every frame.
  • Cull to the visible y range first. NP2.0 holds up to 5120 electrodes and the view shows ~600 data units of a 5750-unit probe, so a redraw touches on the order of a hundred points. This is what makes a drag redraw inside one rAF; it is not an optimization nicety.
  • Draw order: shafts and tips below everything, then electrodes, then each series' labels in a second pass, then the drag-selection box on top.
  • Nothing runs while the operator is not interacting. No animation loop, no timer. Redraws come from property writes and the ResizeObserver only.
  • Device pixel ratio: the backing store is matched to devicePixelRatio and reassigned only when it changed — assigning width/height clears the canvas and forces a reallocation.
  • Series set and sizes: seven series so color and label side are per group — activeLeft/Right #00FF00, inactiveLeft/Right #333333, availableLeft/Right #4F9DDE, reference #FFB300; dot radius 5.5, reference radius 6.5; label font 16px sans-serif, offset radius + 5 outward on the series' side.

5. ACCEPTANCE — proving a renderer change safe#

5.1 The control arm is what ships, measured now#

Compare against the current renderer, re-measured on the same machine in the same session. Do not use a number from a previous session, and do not use benchmarks/bench_channel_density_scichart.csv as a control — that CSV and RendererExperiment.md are the record of the library that was replaced, not a live baseline.

For orientation, the shipping renderer on the real rig (OneBox + Neuropixels 2.0, four columns of 120 = 480 on-screen traces) measured: renderer main thread 0.225 of a core, all browser processes 0.541 cores, GPU 35.9 % at 19.6 W, and a solid 60 fps. The win over the library it replaced was 4.28× less renderer main-thread CPU and 2.45× less total browser CPU; GPU utilization differed by 1.06× and board power by 19.8 → 19.6 W, which is parity. The win is CPU. Do not claim a GPU saving — an earlier simulated GPU figure did not survive contact with hardware.

5.3 The counter, and when it inverts#

window.__perfStats = { fps:int, frameMsMean:float, frameMsP95:float,
                       frameMsMax:float, samples:int, heapMB:float|null }   // main.js:262-310, republished ~1/s
window.__perfReset = () => void

__perfStats is a main-thread rAF loop and Performance.getMetrics().TaskDuration is the renderer main thread. Both are valid for the shipping renderer because it paints on the main thread. Both invert the moment a renderer draws in a worker or on OffscreenCanvas — main would report a serene 60 fps at 3 % busy while the worker drew at 12. If you move painting off the main thread, fix the counter first, keep the object shape byte-identical so cdp_bench.py needs no change, and re-measure the current renderer with the corrected counter: its numbers must not move. If they move, the counter is wrong, not the renderer.

frameMsMean = mean of inter-frame deltas since reset; frameMsP95 = sorted[floor(0.95*len)]; frameMsMax = sorted[len-1]; buffer capped at 600 entries; deltas outside (0, 1000) ms discarded.

6. THE TRAPS#

T-1 — The renderer does not own the layout. yOffset and zoom are baked into Y at append time (NetworkClient.js:183-184). Y values are absolute plot coordinates. Do not re-offset, do not auto-range, do not normalize. A zoom change does not touch buffered samples; the view re-scales over one window. That is correct behavior, not a bug to fix.

T-2 — There is only one copy of the samples. DataStore holds none. If the renderer drops its buffers, that data is gone — there is nowhere to re-read it from. Every reallocation is therefore a deliberate decision about losing up to one window, not an implementation detail.

T-3 — Blank traces with a perfectly healthy socket. Two separate gates must be open. Only the bakings a visible column needs are produced (dataStore.appendPacked / appendInterleaved), so any change to currentStreamId, selectedColKey or tracesPerColumn MUST call window.onLiveFilterChange() before the next draw(). And a row receives data only because glChanToRow[ch] points at it — which only draw() builds — so a column that has never drawn receives nothing at all. Ordering matters at rebuild too: refreshStreamSelectors() then updateAppendModes() (main.js:639-640).

T-4 — Two bakings per channel, not one. Packed depth order, and electrode-interleaved order (0L,1R,2L,3R…). selectedColKey === 'B' takes the interleaved baking; L/R take the packed one. The column announces which it wants through glUsesInterleaved, and the tap reads that flag per frame.

T-5 — Both x values of a min/max pair are the same timestamp. A renderer that dedupes or assumes strictly increasing x will erase the vertical extent of every bin.

T-6 — requestAnimationFrame alone paints nothing under test. Chrome throttles an occluded or backgrounded window: rAF stops and setTimeout is clamped to ~1 Hz. requestPaint() therefore schedules rAF and a 24 ms timer, whichever fires first. The first version had rAF alone and painted 1.0 frames/s under the GUI harness with every buffer full and correct — broken exactly where it was being judged. Keep both schedulers, and keep the harness's occlusion flags (§5.2).

T-7 — draw() loops i < TRACES but positions with shownSlots. For i >= shownSlots the computed top exceeds 100 %; harmless only because those labels are display:none and their rows are never mapped. Preserve both.

T-8 — Label DOM order is top-first. Index 0 = shallowest = slot topRange. Slot 0 is the tip and sits at the bottom. If depth appears upside-down, flip the range/slot sign in draw()/relayoutByDepth(), not the vertical mapping.

T-9 — Labels are placed arithmetically. space-around only lands on slot centers while the labels fit; past ~30 rows free space goes negative and they bunch and drift off their traces (style.css:148-153). Do not "simplify" back to flex.

T-10 — fitStrips() measures column 0 only, on purpose. flex:1 1 0 distributes in 1/64 px LayoutUnits while clientWidth rounds, so per-column measurement puts siblings on opposite sides of the threshold and produces two header heights in one row; and per-column class flips fire the chart ResizeObserver recursively (it took the page down during development). It also removes/restores strip-collapsed within one frame, and returns early on avail <= 0.

T-11 — Do not reintroduce @container shape tiers for the band (toolbar.css:723-740). Twelve tiers were deleted because the tier decided the shape and updateStripMode() then measured whatever shape the tier had chosen. The shape must not depend on the thing being measured.

T-12 — The collapsed band is position:absolute on purpose. In flow, revealing it resizes the chart and the ResizeObserver repaints on every hover. It also keeps the narrow 3-row template, because #view-data is overflow:hidden and a 448 px overlay in a narrow column loses ~275 px of controls.

T-13 — Per-slot label state must be cleared at the TOP of the loop (fixed 2026-08-27). The label elements are reused across draws — only their text is rewritten — so anything set in one branch survives into a later draw whose branch never sets it. label.onmousedown and cursor:'grab' were assigned only in the probe-electrode branch and cleared nowhere, so switching a column from a probe band to the OneBox ADC or NI-DAQ left a drag handler bound with the previous channel's electrode captured in its closure: the label still looked draggable and dragging it fired with a stale index.

They are now cleared unconditionally at the start of each slot iteration, and only set in the branch that wants them — deliberately, so that a branch added later cannot inherit the bug by omission. tests/gui/stream_options.py asserts a non-electrode stream leaves zero labels carrying the handler or the grab cursor; without the fix it reports 20.

T-14 — draw() is the sole owner of shank/side visibility. refreshFilterOptions() used to set it and caused a visible flash, because its test (hasOrdering()) is weaker than draw's (hasOrdering() && channels.length === 384). refreshFilterOptions() also early-returns with no ordering, so stale shank options can survive a source change.

T-15 — isProbeStream() is channels.length === 384, by count, never by name. isVoltsStream() is a hardcoded currentStreamId === 'adc'. Any future 384-wide non-probe stream silently gets probe scaling; any 383-channel probe silently gets the volts-per-row clamp.

T-16 — bottomSlot is a slot index, not a channel id. slider.min/max set in buildHTML and in setTracesPerColumn are transient; draw() overwrites them from the band bounds every time.

T-17 — chSelector.value = String(tracesPerColumn) falls back to '' (Ch:Auto) for any count not in the option list — e.g. a __tracesOverride of 30 from a benchmark.

T-18 — Pin state does not survive a rebuild. buildColumns() destroys every instance; AppController.pinnedColumns is the only thing that outlives them.

T-19 — setTracesPerColumn() does not resize the renderer. It rebuilds the display-slot and label pool only; draw() is the single place that calls setLayout(), keyed on glRows !== TRACES || glCap !== cap. Adding a second reallocation site is how the row count and the buffer shape drift apart.

T-20 — Inline styles beat the stylesheet in two places. .channel-slider-container reads 60px in CSS but is inline 30px (deliberate — 27 px per column back to the traces); .vertical-slider reads 80 % but is inline 100 %.

T-21 — Sentinel zeros look like signal. An empty timebin writes 0.0f for min and max (DisplayProcessor.cpp:460-470), so a stalled band draws a flat line at its yOffset, not a gap. This is exactly the healthy-looking-dead-probe failure CLAUDE.md warns about. Count binary frames at the socket, not pixels.

T-22 — Do not gate anything on a renderer handle. The first frame of every new stream is discarded (NetworkClient.js:82-85), and stream registration is gated on columns EXISTING (main.js:653). That test used to read columns[0].wasmContext — the chart library's handle — which became permanently false when the library went, so no stream was ever registered and the view stayed blank with a perfectly healthy socket. Gate on the thing you mean.

T-23 — forceXAxisUpdate() runs per batch per stream, not per animation frame (main.js:753-765) — ~600 setXRange calls/s plus ~150 textContent writes/s on a 3-stream config. setXRange stores two floats and requests a paint, so this is cheap now; it is still work nobody asked for at the rate it runs, and it is renderer-independent. Fix it there, or it gets miscredited to a renderer change.

T-24 — µV is U+00B5 MICRO SIGN. Writing uV produced four false failures against a correct application (tests/gui/stream_options.py).

T-25 — Header height is DEFINITE (height: 46px), never min-height. min-height lets a column with more controls grow and puts the charts on different baselines.

T-26 — The canvas must stay transparent. The plot background is a CSS gradient on .chart-container-wrapper and the GL context clears to (0,0,0,0) so it shows through. Clearing to an opaque color "so the canvas has a background" flattens the gradient — and those values are now recoverable only from §3.1, because the theme that produced them was deleted with the bundle.

T-27 — Editing webinterface/*.js needs no build. The copy targets were removed from CMakeLists.txt on 2026-08-26 and src/main.cpp:57-62 serves the directory off disk per request. But that handler never strips a query string, and ? is an illegal Windows filename character — so any …js?flag=… URL 404s until that line is fixed.

T-28 — Rig and teardown rules apply (CLAUDE.md): always --no-browser; kill only the isolated debug-port Chrome profile you launched, never a blanket Get-Process chrome | Stop-Process; bring the backend down when not actively measuring, because a live backend holds bin/SpikesPeak.exe and the next build dies on LNK1104 — and the tempting fix is a kill, which is forbidden with a OneBox open.

T-29 — Buffered samples carry the layout they were baked under, so three things MUST clear them. The y offset and the packed/interleaved ordering are applied to each sample when it is appended, so any change to either makes everything already held wrong — it keeps drawing at its old height until it scrolls out, under a label that now says something else. Three call sites exist and each is load-bearing, not tidiness:

change who clears what
a row is rebound to a different channel ChartColumn.draw() via glRowChan gl.clearRow(i)
depth relayout (relayoutByDepth) AppController._clearRenderedSamples() gl.clear()
packed ↔ interleaved switch (updateAppendModes) AppController._clearRenderedSamples() gl.clear()

All three were previously served by clearing the chart library's per-channel buffers. When those buffers were removed the calls became guarded no-ops on a field that no longer existed — they still ran, and did nothing, which is why this needs to be a trap and not a footnote. glRowChan must also be reset whenever setLayout() runs, or the next draw believes the rows are already bound.

T-30 — onScreenSeries[i].isVisible is written and read by nobody. It is a name kept from the object model the renderer replaced. Setting isVisible = false does not hide a row — an unmapped row simply stops being fed, which is what glChanToRow[ch] = -1 expresses. Do not build a feature on it without wiring it to something first. (.stroke IS live again: it holds the channel color that draw() hands to gl.setRowColor.)

T-31 — A clean 7-color cycle down a column means the palette keying has regressed. Color is keyed to the read-out channel, and depth ordering permutes channels into rows, so the correct picture is an irregular color sequence. If a column ever shows a tidy repeating red-yellow-green-blue-… down the screen, something has gone back to keying by row — the traces will also change color as you page the slider, which is the quicker way to confirm it.

Open questions this contract does not settle#

  • The trace canvas caps its backing store at min(devicePixelRatio, 2) while ProbeMap uses the raw ratio. Whether that visibly differs above 2× has not been checked on such a display.
  • .chart-area in style.css:206-209 matches no element ChartColumn builds — probably dead, not proven.
  • Ripple-dock and audio-dock styling live in JS-injected stylesheets and are outside this contract except for .channel-label.listening and the --rd-dock-w margin.
