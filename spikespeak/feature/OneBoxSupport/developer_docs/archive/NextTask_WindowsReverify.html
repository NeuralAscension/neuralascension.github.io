Next task — re-verify the Linux changes on Windows, and finish #52#

You are on Windows. The Linux configuration of #52 is done (2026-08-26: both suites green, clean clone, no path edits — SpikesPeak_Status.md §59). It closed five checklist rows and left four Windows configurations and one core-code change that has only ever run on Linux.

This file is the brief. README.md is the doc map and the repo-root CLAUDE.md is the standing rules; read both first. For configuration 5 specifically, NextSession_SecondMachine_OneBox.md is still the detailed runbook and this file does not replace it.

1. The one thing that actually needs you: commit 7e2b2fa#

CommandDispatcher::executeCallbacks was erasing from the vector it was iterating. It segfaulted the backend on Linux — four core dumps, all SIGSEGV in BandFilterProcessor::slBpHandleCommand. Fixed by reaping dead subscribers in one pass before iterating a copy. The same commit also fixes removeSubscriber, whose QMutexLocker was constructed inside its own if (lock) { … } block and so released the mutex before the erase it was meant to guard.

The bug was never Linux-specific. Linux was just where the trigger finally lined up.

Why you may never have hit it#

The crash needs a stale subscriber, which needs a second source session in one backend process. Processors subscribe in configure() and are destroyed on source teardown; nothing unsubscribes (#66), so their entries stay behind and go null.

band_dependency is the only GUI test that runs a session after another has been torn down. On Linux one backend served audio_panel and then band_dependency, so its first session was already a second session. Whether the Windows suite shares a backend across tests the same way is a hypothesis I could not test — check it rather than assume it. If Windows gives each test a fresh backend, then Windows has never exercised the two-session dispatch path, before or after the fix, and the run below is the first time it is tried anywhere on hardware.

Note band_dependency's own second Gui context (the NP1.0 one) only reads state — it asserts no band buttons appear — so it never sends a band command and never triggers the dispatch.

The reproduction — do this by hand, it takes two minutes#

Operator actions, no test harness needed:

  1. Connect a source that has derived bands (any NP2.0 profile — derived lfp/spike).
  2. Disconnect.
  3. Connect again.
  4. Enable a derived band from the Bands toolbar button.

Pre-fix that is a segfault. Post-fix output.log should show, once, on the first band command of the second session:

[CommandDispatcher] Dropping N destroyed subscriber(s) for 537

537 is 0x219, kBandCommandId. Linux reported Dropping 4. Then the band enables normally and the backend stays up.

Blast radius — narrower than it first looks#

Only two command ids go through this dispatcher:

id subscriber
0x218 (536) AudioProcessor — the audio panel
0x219 (537) BandFilterProcessor — the derived band buttons

Ripple commands do not use it; they go through onTextMessageReceived as {"command":"ripple", …}. So what you are regression-testing is the audio panel and the derived band buttons, not the whole command surface. audio_panel and band_dependency in the GUI suite cover both, which is most of the job — the hand reproduction above is for the two-session case the suite may not reach on Windows.

This is the only commit of the three that touches code the rig runs. The other two are test-side.

4. What Linux could not close, and you can#

  • Every hardware row. NPX_HW_ENABLED / NIDAQ_HW_ENABLED are Windows-branch-only and the vendored libraries are Windows import libraries. PXIe, OneBox, real NI-DAQ, DAC, WavePlayer and the closed-loop latency matrix are structurally unavailable on Linux — not skipped, impossible.
  • layout_matrix's portrait half. On Linux monitors() shells out to PowerShell inside except Exception: return [], so it returns empty without raising and both the landscape and portrait passes ran in the same window — all 16 cells reported viewport 1920x996. They passed, which is the problem. Windows is the only place this can be tested at all, and only on a box with a portrait panel (the original rig's is 1080×2560, per #52). If your box has one, this is the one run that makes those eight cells mean something. If it does not, say so rather than letting them pass.
  • Closed-loop latency. Defined as threshold crossing → stimulus pulse observed on the NI-DAQ or the OneBox ADC. Linux has no instrument to observe the pulse, so no number exists and none was invented. Everything in LatencyProfiling.md is yours.
  • #63, the recording shortfall. Neither the ~22 % ADC cost nor the decay to ~66 % at t+90 s reproduces on Linux sim. That does not close #63 — simulated source, not a OneBox — but it says the decay is not in the platform-independent record path, which points at the transport or the machine. Worth knowing before you spend a day in RecordProcessor.

6. Traps#

  • --fatal, always. Without it a suite that never ran still exits 0. run_all_tests.py forwards it to both children since 2026-08-26.
  • The GUI suite overwrites git-tracked doc screenshots in developer_docs/images/gui/. The nine committed PNGs are currently the Windows-rendered ones (a Linux run clobbered them and they were restored), so a Windows run regenerating them is consistent rather than a clobber — but check the diff before committing, and never commit Linux-rendered ones.
  • Never blanket-kill Chrome — only the isolated debug-port profile the harness launched. And note pkill/Get-Process filters can match the shell running them; on Linux pkill -f spikespeak_guitest killed its own command twice. Match narrowly.
  • Hardware safety is unchanged and non-negotiable: never force-kill the backend while a probe or OneBox is connected. Shut down via the WebSocket quit or the GUI's Disconnect.
