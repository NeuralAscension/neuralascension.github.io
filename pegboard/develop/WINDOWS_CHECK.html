Checking the transfer tool on Windows

This was run on 2026-08-11 — Windows 11 Pro 23H2, build 22631. All ten checks pass. What it found, and the five bugs fixed as a result, are recorded under item 13 in BACKLOG.md; the results are not duplicated here. The checklist stays as written, because it is worth re-running on the next study PC, and because §3's guesses about what would break are instructive against what actually did.

A runnable checklist for validating tools/fetch_sessions.py on a real Windows machine. Written for an agent or engineer with a Windows box and network access to the Pi.

Why this document exists. The transfer tool was written and exercised on Linux against the live Pi — the algorithm is verified, and every failure path was triggered deliberately. What has never run is the Windows side: the folder picker, the paths, the console, and OpenSSH-on-Windows. Those are the parts most likely to differ, and none of them can be tested from here.

Everything below is a check with an expected result. Record what actually happened, not what should have.

0. Before you start
Windows10 build 1809 or later, or Windows 11
Python3.8+, from python.org, installed with "Add Python to PATH" ticked
NetworkAn Ethernet cable to the Pi, and this machine set to 192.168.1.50/255.255.255.0
The PiSwitched on, 192.168.1.100, user remyelin-pi
The repoCloned or copied so tools\fetch_sessions.py is present

Confirm the prerequisites first, because a failure here looks like a failure of the tool:

python --version
where ssh
where scp
ping 192.168.1.100

where ssh returning nothing means OpenSSH Client is off. Turn it on under Settings → Apps → Optional features → Add a feature → OpenSSH Client. That is itself a finding worth recording: it means the tool's "missing tools" message will fire on a stock machine.

1. The checks

1.1 It refuses cleanly with no network

Unplug the Ethernet cable, then:

python tools\fetch_sessions.py

Expect: the "Cannot see the pegboard Pi" block, listing cable → power → address, and a wait for Enter. No Python traceback. If you see Traceback (most recent call last), that is a bug — capture it.

Plug the cable back in.

1.2 First run, with the key offer

python tools\fetch_sessions.py

Expect, in order:

  1. Found it.
  2. An offer to set up passwordless access. Answer Y.
  3. ssh-keygen runs if %USERPROFILE%\.ssh\id_ed25519 does not exist.
  4. A password prompt from ssh itself. Type the Pi's password.
  5. Done. This computer can now copy data without a password.

Watch for: the key generation is invoked with an empty passphrase via -N "". Python's subprocess passes that as a genuinely empty argument, but this is the single most likely Windows-specific failure in the whole tool. If ssh-keygen instead prompts for a passphrase, or errors, record the exact message.

Then confirm it took:

ssh -o BatchMode=yes remyelin-pi@192.168.1.100 true
echo %ERRORLEVEL%

0 means key auth works.

1.3 The folder picker

Still in the same run:

Expect: a normal Windows folder-choosing window, titled "Choose the folder to copy the pegboard recordings into". It may open behind the console — the script warns about that, and whether the warning is warranted is itself worth recording.

Choose a new empty folder, e.g. %USERPROFILE%\Documents\pegboard-data.

Watch for: tkinter is bundled with the python.org installer but absent from some minimal or store installs. If it is missing the script should fall back to asking for a typed path rather than crashing. Force that path with:

python -c "import tkinter"

If that errors, the fallback is what you will be testing.

1.4 The copy

Expect: one line per session, each ending copied and checked (5 files), then a summary naming the folder.

Then verify independently of the tool — do not take its word for it:

dir /s /b %USERPROFILE%\Documents\pegboard-data

Every session should hold exactly five files: session.json, samples.csv, events.csv, clock_sync.csv, raw_udp.log.

Spot-check one hash against the Pi:

certutil -hashfile "%USERPROFILE%\Documents\pegboard-data\ThumperBunny\20260810\001\session.json" SHA256
ssh remyelin-pi@192.168.1.100 "sha256sum Documents/Code/pegboard/experiments/ThumperBunny/20260810/001/session.json"

They must match. certutil prints the hash with spaces and in upper case; compare ignoring those.

1.5 It does not copy twice

Run it again, same folder.

Expect: Already on this computer : N, To copy : 0, and Everything is already here. Nothing to do.

1.6 An interrupted copy resumes

Delete one file out of one session, then re-run:

del "%USERPROFILE%\Documents\pegboard-data\ThumperBunny\20260810\001\samples.csv"
python tools\fetch_sessions.py --dest "%USERPROFILE%\Documents\pegboard-data"

Expect: To copy : 1, and that session re-fetched. A session missing a file must not count as present.

1.7 Corruption is caught

Append a byte to a copied file and ask for a verification pass:

echo tampered >> "%USERPROFILE%\Documents\pegboard-data\ThumperBunny\20260810\002\events.csv"
python tools\fetch_sessions.py --dest "%USERPROFILE%\Documents\pegboard-data" --verify

Expect: DAMAGED ThumperBunny/20260810/002, and an instruction to delete the folder and re-run. It must not delete anything itself.

1.8 Long and awkward paths

Windows is where path handling breaks. Try a destination with a space and one that is deep:

python tools\fetch_sessions.py --dest "%USERPROFILE%\Documents\peg board data"
python tools\fetch_sessions.py --dest "%USERPROFILE%\Documents\a\b\c\d\e\f\g\h\i\j\pegboard"

Expect: both work. The space is the important one — it is passed to scp as an argument.

1.9 Double-clicking

In Explorer, double-click tools\fetch_sessions.py.

Expect: a console window opens, the tool runs, and the window stays open at the end waiting for Enter. If it closes instantly the operator can never read the summary, which defeats the point — record it.

This depends on .py being associated with the Python launcher. If it opens in an editor instead, that is a finding: the operator guide would then need to tell people to right-click → Open with → Python.

2. What to report back

For each check: pass, fail, or not-run, and for anything that failed, the exact message. Then:

  • Windows version and build, Python version.
  • Whether OpenSSH was already enabled or had to be turned on.
  • Whether tkinter was present.
  • Whether double-clicking worked.
  • Anything in the wording that would confuse a research associate rather than an engineer — that is as much a defect here as a crash.

Update the "Verified" section of item 13 in BACKLOG.md with the result, and note the Windows version it was verified on. Right now that section says the Windows side is unverified; it should say what actually happened.

3. Known-untested, in priority order

If time is short, these are the checks most likely to find something:

  1. 1.2 — ssh-keygen -N "" with an empty argument.
  2. 1.9 — double-click behavior, since that is how an operator will run it.
  3. 1.8 — a destination path containing a space.
  4. 1.3 — tkinter presence, and the picker opening behind the console.

Everything else was exercised against the live Pi on Linux and is unlikely to be platform-specific.

How that list held up, 2026-08-11. The top two were fine, and 1.8 was fine. Number 4 was half right for the wrong reason — tkinter was present, but the picker did open behind the console, and the consequence was not "the operator hunts for the window": the console looked frozen, Enter was pressed to unstick it, and the invisible dialog accepted a folder nobody chose.

What actually broke was not on the list at all, and could not have been: every multi-line script sent to the Pi arrived with CRLF line endings, so the tool could not read the Pi's contents from any Windows machine. The lesson for the next checklist is that the risky part was not the platform-specific API anyone thought to list — it was the place where Python silently guesses a platform-dependent default.
