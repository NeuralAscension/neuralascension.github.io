Developer Guide — Adding a New Sink (Processor) Module#

A sink (a.k.a. processor) consumes data a source produced and does something with it: decimate for display, write to disk, run DSP, drive stimulation, or produce a new derived stream. In SpikesPeak a sink is an IProcessor subclass. This guide shows how to add one that matches the existing processors and rules.

Read SpikesPeak_Architecture_Review.md §4–§6 first (factory/registry/config + CircularBuffer). For producers, see AddingASourceModule.md. To let the browser command your sink, see §5 and ModuleCommunication.md (mind the worker-thread rule).

0. The contract (src/core/IProcessor.hpp)#

class IProcessor : public QObject {
    Q_OBJECT
public:
    virtual bool configure(ryml::ConstNodeRef cfg) = 0;   // read your config subtree, bind inputs
signals:
    void sigIpStarted(const QString& processorName);      // MUST emit when ready (see §1)
    void sigIpStopped(const QString& processorName);       // emit after you stop
    void sigIpDataReady(const QByteArray& data);           // optional: bytes → browser
    void sigIpErrorOccurred(const QString& errMsg);
public slots:
    virtual void slIpStartProcessor() = 0;                 // runs ON your own thread at start
    virtual void slIpStopProcessor() = 0;                  // stop request from ProcessorManager
};

ProcessorManager (ProcessorManager.cpp:70-104) gives every processor its own QThread, moveToThreads it, and wires: QThread::started → slIpStartProcessor · sigPmStopProcessing → slIpStopProcessor · sigIpStopped → QThread::quit · sigIpStarted → readiness set · sigIpErrorOccurred → GUI status line.

1. The three iron rules#

  1. Report started when you have actually RUN, not when you have scheduled yourself (issue #13).

Which of the two forms you use depends on how your sink is driven, and the distinction is not stylistic -- getting it wrong either understates readiness or deadlocks the pipeline:

your sink is do this why
timer-driven call armStarted("name") in slIpStartProcessor; noteCycle() emits on the first tick the start slot only schedules work. Reporting there lets the sources begin committing samples before you have run a single pass
a blocking loop emit sigIpStarted("name") directly, immediately before entering the loop see the warning below

⚠️ A blocking-loop sink must NOT defer its report. Its first cycle cannot complete until samples arrive; samples arrive only once the sources start; and MainController starts the sources only after every processor has reported ready. Deferring deadlocks the pipeline -- and it surfaces as a startup watchdog timeout, which points at the wrong thing entirely. LFPProcessor and RippleDetector emit directly for exactly this reason, and that is correct: they are ready, in the only sense available to them.

Either way, if you never report it, the source never starts and nothing streams. This ordering is what guarantees you are a registered consumer before the producer commits a sample.

Two things about the name you pass are easy to get wrong:

  • It is a label, not an identity. Readiness is tracked by the registry key, resolved from the SENDER object, not from the string you pass. Existing sinks pass short hardcoded labels ("display", "recorder", "ripple") and every RecordProcessor instance passes "recorder" — so a profile with an NPX and an NI-DAQ recorder emits the same name twice. Anything that keyed readiness off the string would count two processors as one and wait forever. Pass something sensible, but nothing depends on it being unique.
  • Not emitting it is now diagnosed, not merely fatal. A startup watchdog (ProcessorManager::kStartupTimeoutMs, 8 s) reports which processors never checked in, aborts the play attempt, and tells the GUI. It used to hang silently with every component claiming health. A cycle declared failed stays failed — a straggler that reports afterwards is logged and ignored rather than resurrecting the request. 2. Call noteCycle() once per work cycle. It is a protected IProcessor method: one relaxed atomic increment, cheap enough for a 1 ms path. ProcessorManager polls it every second and reports your sink stalled if it has not moved for 3 s while acquiring -- because "reported ready" is a one-off claim and a sink that blocks forever on a buffer that never fills otherwise looks perfectly healthy (issue #16, Fdir.md section 8).

Put it in the per-cycle function -- the timer slot body, or one pass of your blocking loop -- and never in slIpStartProcessor/slIpStopProcessor; a misplaced call reads as a permanent stall the moment acquisition starts. In a blocking loop put it after the waitForAvailable() returns, so parking on a buffer that never fills genuinely stops the count.

  1. Do your work on your own thread, and stop cleanly. Either a QTimer (poll) or a blocking loop (semaphore) — but slIpStopProcessor must end it and emit sigIpStopped(name) so the thread can quit.

2. Consumption patterns — pick one#

Pattern Mechanism Latency Example
Poll QTimer tick → getTotalSamplesAdded() → read available = total − myReadInd ~timer interval DisplayProcessor (20 ms), RecordProcessor (50 ms)
Block addWaitingConsumer(id) once, then loop on waitForAvailable(id, ms, &got) minimal RippleDetector

Both read samples via constDataAt(i) / constAuxDataAt(i) with an independent read index — you never disturb other consumers of the same buffer (review §6).

A blocking loop must still service its stop flag. RippleDetector calls QCoreApplication::processEvents() in its loop so slIpStopProcessor (which sets an atomic mQuitProcessing) is seen.

3. Output — pick what fits#

  • To the browser: emit sigIpDataReady(QByteArray). For the display stream, match the wire format in review §2 (so NetworkClient.handleMessage parses it). WebSocketServer::setPlaying connects the configured display processor's sigIpDataReady → broadcastData.
  • To disk: delegate to an IDataInterpreter (the RecordProcessor pattern). Each recordings: entry names a data_*, a data_interpreter_name, and an output_filename; the interpreter's serializeAvailableData(QDataStream&, filter) does the format-specific write.
  • A new derived stream: become a producer too — register a CircularBuffer in Utils.cpp, addProducer, write + commitWrite (the RippleDetector ripple-band/envelope outputs). Now other sinks can consume your output.

4. Step-by-step#

4.1 Create the class#

src/modules/<yourmod>/MySink.{hpp,cpp}, subclass IProcessor, add Q_OBJECT.

4.2 configure(cfg) — bind inputs from your config subtree#

bool MySink::configure(ryml::ConstNodeRef cfg) {
    for (auto in : cfg["inputs"].children()) {
        std::string name = SP::Utils::toStdString(in["name"].val());   // e.g. "data.npx.lfp"
        auto* obj = SP::getDataRegistry().getDataByName(name);
        if (!obj) return false;
        auto* buf = static_cast<SP::CircularBuffer<int16, Neuropixels::PacketInfo>*>(obj);
        // poll: stash buf + a currReadInd; or block: buf->addWaitingConsumer(mConsumerId);
    }
    return true;
}

cfg is your processor node from the YAML (inputs:, recordings:, or your own keys).

4.3 slIpStartProcessor() — start, then announce#

void MySink::slIpStartProcessor() {
    mTimer = new QTimer(this);                 // poll pattern
    mTimer->setTimerType(Qt::PreciseTimer);
    mTimer->setInterval(20);
    connect(mTimer, &QTimer::timeout, this, &MySink::slProcess);
    mTimer->start();
    emit sigIpStarted("proc.mymod.thing");     // <-- rule #1
}

(Block pattern: spin your while(!mQuit) loop here after emitting sigIpStarted.)

4.4 Process + 4.5 stop cleanly#

slProcess reads available samples and produces output (§3). slIpStopProcessor stops the timer/loop, flushes, and emit sigIpStopped("proc.mymod.thing").

4.6 Register the type — src/core/Utils.cpp#

SP::registerProcessor<SP::MyMod::MySink>("proc.mymod.thing");
// if you write files: SP::registerDataInterpreter<…>("interp.mymod.x");
// if you emit a derived stream: SP::registerData<SP::CircularBuffer<float,float>>("data.mymod.out");

4.7 Add to a config profile's processors: list#

processors:
  - name: "proc.mymod.thing"
    inputs: [ { data: "lfp", name: "data.npx.lfp" } ]

Add it to whichever config/*.yaml profiles should run it. Processors are optional per profile (ProcessorManager treats "no processors" as success).

4.8 CMake#

target_sources(SpikesPeak PRIVATE MySink.hpp MySink.cpp) in the module CMakeLists.txt (+ add_subdirectory if new).

5. Web commands from the browser (the recording example)#

Full standard + recipe: ModuleCommunication.md. RecordProcessor is the worked sink example there.

To let the browser drive your sink, expose a Q_INVOKABLE — the same per-module "Option A" pattern a source uses (AddingASourceModule.md §8). RecordProcessor::setRecording(bool) is the reference. (Recording happens to be a multi-instance case — a profile can have several recorders, so the browser binds them into window.activeRecorders and the Record button calls each; a single-instance sink just binds to one global. See ModuleCommunication.md §2.2 / §4.)

⚠ The one difference that bites a sink: threads. A source's invokables run on the main thread, but every sink is moveToThread'd onto its own worker thread (§0). QWebChannel invokes a Q_INVOKABLE with Qt::DirectConnection — i.e. on the GUI thread, not your worker thread. So the invokable body must not touch state owned by your worker thread (timers, file handles, read indices) directly — marshal it onto your own thread first:

// header:  Q_INVOKABLE void setRecording(bool enable);
void MySink::setRecording(bool enable) {
    // Runs on the GUI thread (QWebChannel/DirectConnection). Hop to OUR thread so we never
    // race slProcess (the timer/loop slot) on shared state.
    QMetaObject::invokeMethod(this,
        [this, enable]() { applyState(enable); },   // applyState runs on this sink's thread
        Qt::QueuedConnection);
}

Consequences of the marshal: - The invokable is void (the real work happens later, off-thread) — don't return a result from a sink invokable; a main-thread source can, a worker-thread sink can't. - Report the outcome asynchronously via emit sigIpErrorOccurred(msg).

You no longer wire this up yourself. ProcessorManager connects sigIpErrorOccurred for every processor it builds, tags it with your registry key, and relays it out to the GUI status line as "<proc.your.name>: <msg>". Nothing to opt into, and new sinks are covered by construction.

This is worth stating plainly because the signal existed for a long time while nothing listened to it — the only subscriber anywhere was WebSocketServer, wired to the recorder by name. A recorder fault reached the user; the identical fault in proc.lfp or the ripple detector went nowhere. If you find yourself adding a bespoke error signal and hand-wiring it in WebSocketServer, you are rebuilding the thing that failed. Use sigIpErrorOccurred.

A sink that also needs a UI consequence (not just a report) still adds its own channel — the recorder does, to make the GUI revert its optimistic "recording" state. Keep the two separate: the relay reports, your channel acts.

Registration is NOT automatic for sinks. A source is auto-registered by the generic registerObject loop; a sink is not. Add an explicit mWebChannel->registerObject("proc.mymod.thing", proc) in WebSocketServer::onSourceSelection (and a matching deregisterObject in the Disconnect handler), the way the recorder is wired. Then bind it in JS by a registry-name substring (ModuleCommunication.md §2).

Checklist#

  • [ ] MySink : IProcessor with Q_OBJECT
  • [ ] configure(cfg) binds inputs from the registry by name
  • [ ] Consumption: poll (getTotalSamplesAdded) or block (addWaitingConsumer/waitForAvailable)
  • [ ] slIpStartProcessor sets up work and emits sigIpStarted(name) (rule #1)
  • [ ] the per-cycle function calls noteCycle() (rule #2) -- not the start/stop slots
  • [ ] slIpStopProcessor stops + flushes + emits sigIpStopped(name)
  • [ ] Output wired: sigIpDataReady / IDataInterpreter file / new producer buffer
  • [ ] registerProcessor<…>("proc.…") in Utils.cpp
  • [ ] Added to the relevant config/*.yaml processors: lists
  • [ ] target_sources in the module CMakeLists.txt
  • [ ] (optional) Q_INVOKABLE web command — marshal to your thread + explicit registerObject (§5)
  • [ ] Builds clean (see README.md → Build)
