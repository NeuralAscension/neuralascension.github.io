4. Fire-path E2E — PASSED ✅#

Harness: python/tools/stim_udp_listener.py (ESP32 stand-in on 8888/8889) + python/tools/stim_fire_test.py (WS driver). The driver plays the NP2 synthetic file, points stim at 127.0.0.1:8888, detects for 16 s, then switches the target LIVE to 127.0.0.1:8889 and detects for 16 s.

Result (run 2026-07-09): - rippleState.stim_server tracked 192.168.1.100:8888 → 127.0.0.1:8888 → 127.0.0.1:8889; stim_status = configured throughout. (Proves WS setStimServer routing + setTarget + rippleStateJson echo.) - 24 detections → 24 UDP datagrams, payload exactly b'fire', each to the currently-selected target: Phase 1 → 8/8 on port 8888; after the live switch → 16/16 on port 8889. 1:1 with detections.

This verifies the GUI is the source of truth for the stim target and that fires follow it live. The stim hardware is not required — the loopback UDP listener stands in for the ESP32.

To reproduce: 1. python run_spikespeak.py --no-browser (from a normal terminal) 2. python python/tools/stim_udp_listener.py 3. python python/tools/stim_fire_test.py Pass = payload=b'fire' on 8888 in phase 1, on 8889 in phase 2, and the driver prints stim_server flipping 8888→8889. (Or drive the GUI by hand via python/tools/cdp.py on Chrome --remote-debugging-port=9222.)

5. Launching the backend (important) — the DLL/PATH gotcha#

SpikesPeak.exe links Qt6*, NeuropixAPI_x64_4_1_3.dll (external\neuropixels\api\lib64\v4), hdf5.dll/hdf5_cpp.dll (C:\Program Files\HDF_Group\HDF5\1.14.6\bin), and nicaiu.dll (System32). If Qt + Neuropix + HDF5 are not on PATH, the exe exits at the loader with 0xC0000135 (STATUS_DLL_NOT_FOUND) before main() — a silent instant exit, no output.log. Qt Creator's run environment sets this up; for terminal/automation launches use run_spikespeak.py (which prepends those dirs). This — not the keyboard-listener/stdin — was the cause of the earlier "backend won't stay up" failures.

6. ESP32 wire format (confirmed from esp32s3_pulsegenerator.ino)#

UDP port 8888. Commands matched via strcmp: "fire" (biphasic pulse via RMT), "connect" (arm, LED green), "quit" (disarm). No ACK/reply — so stim_status can only mean "we enqueued a datagram without a local socket error", never true reachability. connect() sends "connect" at construction; fire() sends the 4-byte "fire" (firmware null-terminates it). Verified on the wire: the listener saw b'fire'.

9. NP1.0 real-hardware closed loop with a synthetic ripple — VERIFIED ✅ (2026-07-15)#

The first fully closed loop on a real probe: a real NP1.0 streaming a synthetic ripple drove live SWR detection → single-pulse stim on the Pi 3B+ stim server → confirmed fired ACK → red STIM LED, with the biphasic pulse captured back on the NI-DAQ. This is the saline/synthetic bench rehearsal the earlier sections called "still open" (a real ripple driving the fire, vs. the manual ⚡ Test Fire).

Rig. Real NP1.0 (PRB_1_4_0480_1_C, serial 20097903862) on Slot 3 / Port 4 / Dock 1 + NI-DAQ PXI-6133 (PXI1Slot2, 8× AI @ 40 kHz differential + port0 DI). Config NPX 1.0 with NI-DAQ (Npx1PxiNiDaq.yaml): detector reads native data.npx.lfp (int16, decimation 1, gate 1 s). Pi 3B+ pulsegenerator active at stimserver@192.168.1.100:8888; control PC 192.168.1.201.

Single-pulse config (per the operator). Stim pulse 60 µs phase / 10 µs gap / 1 Hz / 500 ms train. At 1 Hz the Pi computes total_pulses = 500·1/1000 = 0.5 → clamped to 1 ⇒ exactly one biphasic pulse per detection (StimulatorClient::setStimParams also clamps total_ms ≥ 1). The ripple-dock pulse preview redrew to "1 Hz · train 500 ms → 1 pulse" on edit; backend echoed stim params -> 60us … 1 Hz, 500 ms.

Arming. Selecting the config constructs the detector, which auto-sends connect() → Pi replies armed (green server LED). ⚡ Test Fire then fired one pulse; Pi journal logged -> Fire: phase=60us gap=10us freq=1Hz total=500ms and -> ACK 'fired' -> 192.168.1.201:…, and the GUI lit the red STIM LED + cowsay "⚡ Pulse fired (confirmed)".

z-score (per the operator). The synthetic ripple envelope peaks right at z ≈ 3, so z = 3 only grazes threshold (few detections). z = 2.5 (threshold ≈ μ+2.5σ ≈ 28–38) puts the threshold cleanly below the ripple peaks and detects every burst — the definitive runs use z = 2.5.

Detection tests (each: fresh training ~6 s, then live detection + closed-loop fire, all recorded @ z=2.5).

Test Electrodes Quorum Result Reported quorum NI-DAQ ai4 pulses
1 — single channel 1 1 47 detections → 47 confirmed fires 1/1 43
2 — multichannel quorum 1,100,200,300 3 of 4 56 → 56 3/4 (varying trio) 52
3 — unanimous quorum 1,100,200,300 4 of 4 41 → 41 4/4 (all four) 37

Every detection produced a confirmed Pi fired ACK (1:1). Raising the quorum 3→4 suppresses non-unanimous events (test 2 fired on "3/4" coincidences; test 3 only on "4/4"), demonstrating the coincidence gate.

Hardware-level proof — the stim pulse on the NI-DAQ. The Pi On/Off line (GPIO17) is wired to NI-DAQ ai4. Each recording captured the actual biphasic pulses on ai4 (3.3 V logic): 43 / 52 / 37 fire-events for tests 1 / 2 / 3 (≈ the confirmed fires; the few-count delta = recording-window edges). A single pulse shows the expected two ~60 µs lobes separated by the ~10 µs interphase-gap notch. ai0 + DI line 2 carry the ~1 Hz NP1.0 sync. NI-DAQ recorded on every test (all 8 AI + 8 DI @ 40 kHz).

Algorithm confirmation (offline, independent). The detector's pipeline was reproduced from the recorded LFP using the exact FIR taps from src/core/Common.hpp (26-tap 150–250 Hz ripple band + 10-tap envelope): recorded LFP → ripple band → rectified envelope → threshold crossings reproduce the live detections.

NI-DAQ ↔ Neuropixels time sync. The closedloop + nidaq figures warp NI-DAQ time onto the NPX clock via the shared 1 Hz sync pulse (spikespeak_postprocess.reader.synchronize, NPX sync field vs NI-DAQ ai0): 34 pulses, ~10 ppm drift, 0.010 ms residual — so the ai4 stim pulses line up with the LFP signal to ~10 µs.

Closed-loop latency (NP1.0 LFP band). ripple_tools/latency.py runs the exact causal FIRs on the recorded LFP and quantifies, per ripple: - Detection latency = causal (realtime) threshold-crossing − zero-phase (filtfilt, delay-free, same taps) crossing = the causal filter group delay. Both enforce the 200 ms lockout (so the offline count reproduces the live one). median ≈ 6.4–7.0 ms. - Actuation latency = NI-DAQ ai4 pulse (synced) − detection crossing (processing + UDP + Pi + GPIO). median ≈ 1.4–3.7 ms (the sub-ms spread incl. small negatives is offline-crossing-vs-fire-instant + sync alignment jitter). - Total ripple→stim ≈ 8–11 ms (*_latency.png, histogram + KDE). Consistent with the NP1 native-LFP design being the low-latency path (no proc.lfp, direct int16 read).

Fixes / features (2026-07-15/16). - Clickable arm/disarm stim toggle (2026-07-16): the small stim-server LED in the ripple dock is a clickable pill that arms/disarms the Pi ("connect/disconnect the Pi") without tearing the source down — armed by default, and it works WITHOUT streaming. Routed to RippleDetector::setStimArmed(bool) on the main thread (thread-safe StimulatorClient::arm/disarmFromAnyThread + status QMutex), so it doesn't need the worker event loop (which only runs on Play); optimistic click + short cowsay ("connected/disconnected from stim server"). Backend StimulatorClient+RippleDetector+WebSocketServer, frontend RippleModule.js; rebuilt; verified on the live Pi with no streaming — 6/6 clicks alternated (journal Device ARMED/DISARMED per click; ripple_tools/shots/toggle_*.png).
