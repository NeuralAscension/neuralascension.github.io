Intan on the MicroZed — the design, and what is not known yet#

Target: kemerelab/MicroZedIntanInterface — the Kemere lab's Zynq-7020 Intan interface. MIT licensed.

Status: research complete, no code written. Tracked as #74. The stock Intan RHD2000 evaluation board (Opal Kelly USB) is deliberately out of scope and tracked separately as #76 — it is the same chip protocol over a different transport, and it is the one that would need a vendored SDK.

Everything below was read out of the upstream repository and this one. Where something could not be determined it says so rather than guessing — §1.2 is the list, and it is load-bearing: a protocol we have not read is a protocol we cannot implement.

0. Headline, so nobody has to read to the bottom#

This needs no new dependency. The MicroZed board is driven entirely by TCP control + UDP data over ordinary BSD sockets. SpikesPeak already requires Qt6 Network (CMakeLists.txt:33-36) and already drives a QUdpSocket in src/modules/stimulation/StimulatorClient.cpp. No vendored SDK, no vendor DLL, no driver, no #ifdef hardware gate, no platform gate. That makes this strictly cheaper than the stock Intan RHD2000 evaluation board, which would require the Opal Kelly FrontPanel SDK — a genuine vendored dependency needing an operator decision under the CLAUDE.md rule. If Intan support is going to be built, build the MicroZed path first.

But we cannot start writing the parser yet. The upstream repo's prose documentation and its reference client disagree about the wire format, and we do not know which firmware is on the operator's physical board. That is settled by §1.2 and §6, not by guessing.

1. What we know, and what we do not#

1.1 What the target is (established)#

github.com/kemerelab/MicroZedIntanInterface — MIT, single-author (Caleb Kemere), created 2025-06-18, main last committed 2026-07-11, branch activity to 2026-07-26, 3 stars, 1 fork, 11 open issues. A lab-internal instrument, not a community project.

  • Hardware: MicroZed SoM (Xilinx Zynq-7020, xc7z020clg400-1) on a custom KiCad carrier PCB (three revs in-tree: 011/100/110). ~0.65 A @ 5 V, single USB-C for power + 115200 8N1 debug console.
  • PL (FPGA fabric) runs the entire acquisition datapath: a DDR-SPI FSM (80 states @ 84 MHz, 4× oversampling a 24 MHz SPI clock, 35 cycles per sample frame), cable-delay phase compensation, BRAM packetization, and an on-chip CIC+FIR LFP decimator. The PL builds the complete wire packet; the PS does no header math.
  • PS (ARM) runs bare-metal on both Cortex-A9 cores — no Linux. Core 0 = fast loop (TCP commands, BRAM reads via AXI CDMA, UDP TX). Core 1 = serial console. Network stack is lwIP NO_SYS, fully polled, run-to-completion, no interrupts. Boot is FSBL + bitstream + two ELFs packed into BOOT.bin on a FAT32 SD partition. Toolchain Vivado/Vitis 2025.1.
  • Channels: two Omnetics cables (port A, port B), each 2 CIPO lines × (REG + DDR) × 32 ch = 128 ch; 256 ch total, "up to four chips". SET_CHANNEL_ENABLE (0x13) is an 8-bit mask, one bit per 32-ch stream, and bit order is also packet order: A_CIPO0_REG, A_CIPO0_DDR, A_CIPO1_REG, A_CIPO1_DDR, B_CIPO0_REG, B_CIPO0_DDR, B_CIPO1_REG, B_CIPO1_DDR.
  • Chips: RHD2164 (64 ch, DDR, chip ID 4) and RHD2132 (32 ch, no DDR, chip ID 1) are the only parts the auto-detect recognizes. RHD2216 is never mentioned. RHS (the stim-capable family) is never mentioned anywhere in the repo — this design has no stimulation capability.
  • Rate: 30,000 Hz exactly, and it is architectural: 84e6 / 80 / 35 = 30000. There is no SET_SAMPLE_RATE command in the command table or in remote/net.py's constants. Changing it appears to require a Vivado rebuild.
  • Transport (this is the operator's "Ethernet version"): TCP control on 0x6900 / 26880, UDP data on 0x6800 / 26624, UDP discovery beacon on 0x6880 / 26752 at ~1 Hz. Default board IP 192.168.18.10; default UDP destination compiled in as 192.168.18.100:0x6800, re-pointable at runtime with SET_UDP_DEST (0x50).
  • TCP control frame is settled: fixed 20 bytes LE, struct.pack('<IIIII', 0xDEADBEEF, cmd_id, ack_id, param1, param2); ack is 3 bytes, ACK_SUCCESS = 0x06, ACK_ERROR = 0x15. Full command table transcribed in the research notes (START/STOP/RESET_TIMESTAMP/SET_PHASE per port/SET_CHANNEL_ENABLE/GET_STATUS/READ_REGISTER/WRITE_REGISTER/SET_FAST_SETTLE/SET_DIGOUT/LFP_*).
  • Sample encoding: 16-bit offset binary, midscale 0x8000 = 0 µV. Two samples per 32-bit word, low half first. Cycle-major interleave across enabled streams.
  • The +2 pipeline deskew is mandatory and easy to get wrong: because of the 2-command SPI readback pipeline, amplifier channel ch (0..31) lands at cycle ch + 2; cycles 0, 1 and 34 carry aux/register readback, not neural data. The Open Ephys plugin shipped this bug once (fix/channel-reorg-aux-deskew in the ROADMAP). Any SpikesPeak parser applies the +2 shift or it produces plausible, wrong data.
  • Sync path exists and is usable: 8 LVCMOS33 digital inputs (programmable_logic/constraints/digital_inputs.xdc, pins W16/V16/W20/V20/P20/N20/U19/U18, all PULLDOWN) are latched once per sample frame into header word 6 bits [7:0] (data_generator_core.sv:655-667, :746), alongside a monotonic 64-bit master timestamp with a RESET_TIMESTAMP command. This is the same shape as the NPX↔NI-DAQ sync-pulse alignment we already do.
  • Existing clients: remote/net.py (131 KB, MIT — the reference implementation, includes a bit-exact debug-mode sine model, cable auto-detect, and a DataValidator), and ckemere/ephys-socket, a forked Open Ephys DataThread in C++ — GPL-3.0. ⚠️ Read ephys-socket for understanding; do not copy code out of it into SpikesPeak. MIT (net.py, the docs) is the only license we can lift from.
  • No hardware needed to develop: SET_DEBUG_MODE (0x12) makes the PL emit a synthetic sine with a layout identical to real data, and net.py carries a reference model of it proven bit-identical to the RTL.

1.2 What we do NOT know — be blunt#

A protocol we have not read is a protocol we cannot implement. The following are open items, not guesses:

  1. WHICH WIRE FORMAT THE OPERATOR'S BOARD SPEAKS. This is the blocker. docs/protocol.md documents a legacy 10-word header whose word0 magic is 0xDEADBEEF. docs/unified-packet-format.md, firmware/include/main.h and remote/net.py on main implement a newer "unified" framing: an 8-word common header (word0 magic 0xCAFEBABE) + a 6-word broadband sub-block = 14 header words, all stream types multiplexed onto one UDP port with a stream_type tag (1 = BROADBAND, 2 = LFP, 3 = WAVELET). The repo's own CLAUDE.md still says 10 words — it is stale. GET_STATUS is documented as a 160-byte struct with a _Static_assert, while net.py unpacks out to byte offset 288 and the ROADMAP refers to a 98-byte status; that struct has grown at least three times and the doc did not follow. The README names the authority: remote/net.py and firmware/include/main.h are authoritative; protocol.md is "the readable summary". Do not implement a parser from protocol.md. Silver lining: the magic word order is inverted between the two framings (legacy sees 0xDEADBEEF first, unified sees 0xCAFEBABE first), so a runtime version discriminator is one word deep and nearly free. Combine that with the beacon's fw_version field.
  2. µV per LSB. Appears nowhere in the repo. It is a property of the RHD2000 part (bundled datasheet docs/Intan_RHD2000_series_datasheet.pdf, unread) and of the commanded gain/bandwidth registers, which the ROADMAP lists as not yet configurable. We need a defensible number for the live view scale and the recording sidecar. GET_STATUS exposes a 22-byte RHD2000 register mirror — the honest answer is datasheet + readback, not a constant.
  3. Whether port B works on real hardware at all. ROADMAP epic I Phase 2 is marked in-progress: PL/firmware/host done, timing closed, but "Remaining: on-hardware bring-up". The ~18 MB/s full-256-channel bandwidth measurement was also never run on hardware. Treat 256 channels as a paper figure and 128 as the working one until proven.
  4. End-to-end latency, board input → host userspace. The board instruments only its own recv→transmit window (~3 µs typical, ~10 µs max of a 33.3 µs budget). Nothing upstream measures wire + NIC + kernel + application. 30,000 datagrams/second on a Windows host is an unmeasured risk and it sits on the closed-loop path — the exact number this project is judged on.
  5. Are the 8 digital inputs edge-detected or level-sampled? The RTL latches the level once at packet start, so a TTL shorter than ~33 µs can be missed entirely. No edge-capture or timestamped-event mechanism was found. ROADMAP epic A's "configurable digital input capture" is still open, so this may be in flux.
  6. Which PCB revision the operator has. digital_inputs.xdc says the GPIO routing changed on "the new carrier PCB rev" and carries a TODO that the JX1 schematic symbol is flipped (labels read 18N/18P, 16N/16P, 14N/14P, 12N/12P but are actually 17/15/13/11). Which physical pin is which digital input depends on the board in hand.
  7. Whether the on-FPGA LFP stream is hardware-validated. This matters more than it looks — it is the proposed escape from the biggest cost item (§4.3).
  8. No paper or preprint exists. Searches for the repo and for a Kemere-lab MicroZed/Zynq/Intan system returned nothing; the lab's own tools page (rnel.rice.edu/research/tools.html) does not list it. The in-repo docs are the documentation of record. (The Hackaday "open source MicroZed carrier card" hit is Viktor Nikolov's, unrelated.)

1.3 Two upstream hazards we inherit#

  • The ICMP storm. Documented, measured, and directly relevant: if the host has a UDP port the board is sending to and nothing is bound/draining it, the host kernel replies ICMP port-unreachable at stream rate, and the board's fully-polled lwIP must process every one. Measured: recv→transmit spikes from ~27 µs to 40–63 µs against a ~33 µs budget → TX descriptor exhaustion → the board drops broadband samples. That is why upstream collapsed all streams onto one port. Rule for our implementation: any socket the board is told to send to must be bound and drained continuously, and the socket must be opened before SET_UDP_DEST / START, and closed after STOP.
  • Boot fragility. Board boot takes >20 s; net.py's beacon timeout is 45 s (raised after an 8 s timeout caused clients to give up and hammer the board). There is a documented GEM RX-hang that needed a firmware self-heal, five claude/rxwedge-* branches, and a suspected stale-DDR / lwIP-pbuf-pool problem still TODO in upstream's CLAUDE.md. Our client must stay fully passive until it hears the beacon, then use bounded, paced TCP connect retry.
  • We would become the fourth hand-synchronized consumer of a contract upstream itself admits it cannot keep in sync (ROADMAP epic H, "single-source register/packet contract", still open). Plan for the wire format to move under us. That is an argument for a single, small, well-tested parser translation unit with a version discriminator — not for spreading offsets across the module.

2. The module shape#

New directory src/modules/intan/, structurally a sibling of src/modules/nidaq/. Copy the NI-DAQ module's structure, not the neuropixels module's — NI-DAQ is our worked example of a non-imec device, and NiDaqDisplayProcessor is the better-behaved of the two display processors.

2.1 Classes#

Class Role Notes
IntanSource : IDataSource Lives on the main thread. Owns the TCP control socket, the config, and the worker threads. Implements the 4 pure virtuals: initDataSource, closeDataSource, startAcq, stopAcq. Overrides acquisitionWorkers(). Returns false from applyNamedMap() (correct — no probe map).
IntanSimSource : IDataSource The hardware-free sibling. Mandatory, not optional (AddingASourceModule.md §0, CLAUDE.md "Sim first, always"). Its own class. Template: NiDaqSimSource — QTimer(1 ms, Qt::PreciseTimer) on its own QThread, paced to std::chrono::steady_clock (target = elapsed*effRate, write only the shortfall), wraparound-safe min(due, cap - writeInd, 4096), noteCycle() first in the loop, readiness emitted via a queued sigGuiStatus.
IntanUdpWorker : IDataSourceWorker The socket reader. Its own QThread. slStartAcquiringData / slStopAcquiringData; emits sigDswStartedAcquiring / sigDswFinishedAcquiring / sigDswError; calls noteCycle() once per loop in the loop body, reportStreamError / resetStreamErrors per read.
IntanControl TCP command framing (the 20-byte struct), ack matching by ack_id, GET_STATUS decode, beacon discovery. Pure logic + QTcpSocket/QUdpSocket; unit-testable without a board.
IntanPacket The parser. One translation unit, version-discriminated. Header decode, +2 cycle deskew, stream de-interleave, offset-binary → signed. This is where the wire format lives. Nothing else in the module knows a byte offset. Test it against captured/synthesized packets in the C++ suite.
IntanDataInterpreter : IDataInterpreter The recorder's only view of the data. configure, serializeAvailableData, updateReadMarkers; override sampleWidth() → mData->sampleDimensions() so a record filter is validated before recording opens; implement frameSpan()/resetFrameSpan() from the board's 64-bit timestamp + per-stream SEQ.

IntanPacketInfo (aux struct) Per-sample aux. See the open decision in §6/Q of the operator list — likely its own struct (64-bit timestamp + SEQ + digital_in[7:0]), not Neuropixels::PacketInfo (whose 32-bit timestamp is a worse fit and whose reuse drags in the imec display/interpreter assumptions).

2.2 Threads — and where the socket read lives#

The UDP recvfrom loop runs on IntanUdpWorker's dedicated QThread, and must never run on the Qt main thread. Reasons, in order of how badly they bite:

  1. Rate. One datagram per 30 kHz sample frame = 30,000 datagrams/second, up to 616 B each, ~18.5 MB/s at 256 ch. The main thread also services the WebSocket server, the QWebChannel, and every Q_INVOKABLE the browser calls. A single 20 ms hiccup on the main thread is ~600 datagrams behind.
  2. The board punishes us for being slow (§1.3, ICMP storm / socket-buffer overrun). Falling behind on the host is not merely our problem; an undrained or slow socket costs board-side samples.
  3. IDataSource objects live on the main thread by contract and must not block (AddingASourceModule.md §1).

Receive discipline, prescribed by upstream and worth copying verbatim: one socket, promiscuous drain — a tight recvfrom → ring loop that does nothing else, with a large SO_RCVBUF; demux by stream_type and all parsing happen downstream of the ring. net.py splits _recv_loop from _demux_loop for exactly this reason and counts host ring overflow separately from board drops. We should do the same and surface both counters.

Open question for implementation, to be measured not assumed: whether QUdpSocket + readyRead on the worker's event loop keeps up at 30k datagrams/s on Windows, or whether we need a blocking-read loop (or recvmmsg-equivalent batching, which Qt does not expose — that would mean touching the native socket descriptor). Measure before choosing. This is a latency/CPU question and belongs in the report headline per CLAUDE.md.

Lifecycle, copied from NIDAQSource::closeDataSource: in stopAcq() emit the stop signal, then thread->quit() + thread->wait(2000) before closing anything. For a socket source: send TCP STOP, then join the reader thread, then close the sockets. Closing the socket out from under a blocked recvfrom is the socket analogue of the freed-task race that comment exists to prevent.

2.3 Buffers#

Pattern A, in initDataSource, exactly as AddingASourceModule.md §2.2 specifies:

getDataRegistry().getDataByName("data.intan.raw")
  → null-check → static_cast<CircularBuffer<int16, IntanPacketInfo>*>
  → setCapacity(maxSamples, numChannels)
  → addProducer(mProducerId)   // by reference; refuses a second producer

Worker writes at getDataStart() + (writeInd % sampleCapacity()) * numDims, aux at getAuxDataStart() + writeInd, then commitWrite(mProducerId, nSamples).

The invariant that must not be broken (SourceSelection.md §2): bands are registered in initDataSource(), because that is what setupSources calls and setupProcessors runs after it. This bites harder for a network source than for anything we have built so far, because the natural instinct is to wait for the first UDP packet to learn the channel-enable mask. You cannot. The TCP GET_STATUS / SET_CHANNEL_ENABLE exchange that determines the channel count must complete inside initDataSource, before setCapacity. A source that defers band creation to startAcq() silently binds nothing in the display and skips everything in the recorder, with no error at either end.

Bands to register: data.intan.raw (30 kHz broadband) and — if we take option (b) in §4.3 — data.intan.lfp (the board's on-FPGA decimated stream). Aux/telemetry (chip temperature, supply voltage, chip ID, future IMU) should be a separate band if we take them at all; the OneBox precedent (issue #67) is that sharing a band across an analog stream and non-analog bits prints a microvolt scale on things that are not microvolts.

Do not name any Intan band data.npx.*. ProcessorManager.cpp keys its derived-band auto-provisioning off hasRaw && !hasNativeLfp to infer "this is an NP2.0"; an Intan band under an npx name would trip it.

2.4 Registration — four edits outside the module#

  1. src/core/Utils.cpp registerBuiltInTypes() — registerData<CircularBuffer<int16,IntanPacketInfo>>("data.intan.raw"), registerDataInterpreter<>("interp.intan.raw"), registerProcessor<> for the display + recorder, registerDataSource<IntanSource>("source.intan.microzed") and <IntanSimSource>("source.intan.sim").
  2. src/modules/CMakeLists.txt → add_subdirectory(intan).
  3. config/Intan.yaml + config/IntanSim.yaml — identity is the internal top-level name:, not the filename. The sim variant omits both sim_basestation: and sim_probe: (an omitted axis means "independent of it"; tests/gui/sim_picker.py asserts this both directions).
  4. Nothing in the Source menu — it is built from the configs now.

No CMake gate of any kind. Unlike nidaq/ (delay-loaded nicaiu.dll) and neuropixels/ (vendored imec API), every file here compiles on every platform, including the Linux sim box. That is a genuinely better position than either existing hardware module.

2.5 Per-source GUI controls#

Q_INVOKABLE on IntanSource, auto-registered on the QWebChannel by the existing loop, modeled on NIDAQSource::niDaqInfo() / setAiVoltageRangeIndex(). Natural surface: channel-enable mask, per-cable phase (SET_PHASE / SET_PHASE_B), fast settle, LFP decimation params, board IP.

Hard rule, from a real past crash: these dispatch synchronously on the main GUI thread. Never open a modal dialog or spin any nested event loop inside one — QWebChannel re-enters its own machinery and crashes. Defer with QTimer::singleShot(0, ...).

Settings must outlive a disconnect. NiDaqInterface.hpp documents the trap: disconnecting destroys the device objects (SourceManager::cleanupSources clears the registry), so a selection stored on the instance dies with the very event that applies it — "choosing a range and reconnecting produced No range chosen — defaulting to the widest window, i.e. the control did nothing at all." The fix there is process-lifetime static maps keyed by device name. Intan has the identically-shaped settings (mask, per-cable phase, applied at connect) and should key its statics by board IP or MAC (the beacon carries the MAC as the unique device id).

⚠️ AddingASourceModule.md §2.6 is STALE and will mislead whoever executes this. It still says to put "NPX" in the option text to get the probe panel. That gate is gone in both places and both removals are documented in-place as bugs: main.js:644 and NetworkClient.js:443/:525 note the profiles are now named "OneBox"/"PXIe"/"Neuropixels", none contains the literal, so "the probe branch was taken in simulation and skipped on the rig" — the gate "had inverted itself into reset on hardware, keep stale state in simulation, which is exactly backwards." Binding is now by capability (npxKeys.find(k => typeof channel.objects[k].getImroAsJson === "function")), and window.channelObjects is set for any ready source specifically so a non-probe device can have its own panel. An Intan source needs no name games and correctly gets no IMRO panel. Fix §2.6 as part of this work.

3. The dependency question — answered#

No vendored SDK. No driver. No kernel module. No vendor DLL. No new dependency of any kind.

The board speaks plain little-endian fixed-layout structs over TCP and UDP. SpikesPeak already has everything needed:

  • CMakeLists.txt:33-36 — find_package(Qt6 6.7 REQUIRED COMPONENTS Core Gui Widgets Network WebSockets WebChannel). Network is already a required component.
  • src/modules/stimulation/StimulatorClient.cpp already drives a QUdpSocket in production, in the closed loop.

This is the decisive fact for sequencing. The stock Intan RHD2000 evaluation board would require the Opal Kelly FrontPanel SDK — a vendored binary dependency that under the CLAUDE.md rule is an operator decision, not a convenience. The MicroZed path costs zero on that axis. If we are doing Intan, do MicroZed first.

Caveats that are not dependencies but are worth stating: - ckemere/ephys-socket is GPL-3.0. Read it as documentation; do not link it and do not copy from it. remote/net.py and the in-repo docs are MIT and are the safe reference. - There is no MIT-licensed C++ implementation of this protocol anywhere. Ours would be the first. That is a cost (we write the parser) and a benefit (no license entanglement).

4. What breaks — the concrete list#

4.1 Degrades gracefully today — no work needed#

Assumption Why it is fine
IChannelMap / probe geometry Publishing nothing is legitimate and already shipping: ChannelMapService::hasMap() returns false, forwarders return −1. NI-DAQ (8 ch) and the OneBox ADC (12 ch) run this way every session. IChannelMap.hpp states the design intent explicitly ("a future NeuroNexus / other probe → its own IChannelMap subclass"). This is a supported path, not a fallback.
Recorder sidecar vocabulary RecordingMetadata.hpp:107-112 already has bool usesProbeChannelMap = true — added for the OneBox ADC precisely so we do not "put a plausible, specific and completely wrong electrode number" in the sidecar. Ripple detector input plumbing Fully config-driven (input, input_type, decimation_factor, baseline_gate_seconds, …) and reads through constDataAt(), so the input stride is taken from the buffer and is width-correct at any channel count. Its two internal scratch stores are setCapacity(2500, kMaxChannels) (lines 301, 303) — over-allocated for 256 ch, harmless, but a hard ceiling above 384.

A 256-channel Intan stream is therefore rendered on the NI-DAQ "×multiplier" scale instead of a microvolt scale. For a neural source this is wrong in a way an operator notices in the first thirty seconds. Same constant also drives :433 maxTopChannel, :1180 density clamp, :1193-4 slider max. The honest fix: make "is this neural / does it have a µV scale?" a per-stream property on the wire, not a channel-count comparison. DataStore.js:52-56 is already per-stream correct and NetworkClient.js:73 confirms the header carries per-stream channel count, so the plumbing exists. The cheap fix (widen the count test) leaves the same bug for the next device. This is a frontend contract change and the 11-minute GUI suite gates it.
Display processor scale inference DisplayProcessor::bindStream casts every non-derived stream to CircularBuffer<int16, Neuropixels::PacketInfo>* and infers scale by substring-matching the data name (.ap → imec 500× gain, .lfp → 250×, .raw → NP2 scale, .adc → volts/count); anything else → scaleFactor = 1.0f. numChannels defaults to 384 unless an explicit inputs: entry says otherwise. Don't reuse it. Write IntanDisplayProcessor on the NiDaqDisplayProcessor model: channel count from sampleDimensions(), scale from a YAML scale key.
ProcessorManager native-band table ProcessorManager.cpp:108-114 holds a fixed table {"ap","data.npx.ap",384} … {"adc_di","data.npx.adc.di",12} and auto-binds whichever of those hasData(). Intan bands are not in it. Either add the Intan bands to the table, or pin them by hand with an explicit inputs: block in the profile — SourceSelection.md §3 says that is legal and still wins. Prefer the profile first (less core churn), promote to the table if it becomes routine.
Sample rate has three homes that can diverge Rate is not in CircularBuffer at all. It arrives via YAML (sample_rate_hz on the display block and on every recordings: entry), compile-time constants (SP::Npx::kSamplingRate etc.), and device objects (NIDAQDevice::mSampleRate = 40000.0 hardcoded). NiDaqInterface.hpp names the hazard: "two numbers that happen to agree in every config that ships and can silently diverge." Intan must state 30000 in the display block and in every recorder entry, and the source should assert its own rate against the config rather than trusting agreement.
Offset-binary → signed conversion Every sample needs − 0x8000. Do it in the source's write loop as a per-batch vectorizable transform, not per-sample with any clock read/allocation/lock nearby. CLAUDE.md: nothing per-sample on the 30 kHz path.

4.3 ⚠️ THE BIG ONE — BandFilterProcessor hardcodes 384 as a stride#

This is the largest single item and it sits on the closed-loop path, which is what this system is judged on.

BandFilterProcessor derives data.lfp and data.spike, and on a single-band source it is the only way the ripple detector gets an LFP. Verified in the file:

:35   static constexpr int kNumFilters = SP::kMaxChannels / kChannelsPerFilter;   // 384 / 8 = 48
:106  mRawData = static_cast< SP::CircularBuffer<int16, Neuropixels::PacketInfo>* >(dataObj);
:118  mBandData->setCapacity(30000, SP::kMaxChannels);
:221  ... mRawData->getConstDataStart() + (rawDataInd * SP::kMaxChannels);
:227  float* bandDataStart = mBandData->getDataStart() + (bandDataInd * SP::kMaxChannels);

A 256-channel Intan buffer fed through this reads and writes at the wrong stride. It would not error. It would produce scrambled data that looks like data.

Two escapes. This is an operator decision, per CLAUDE.md, not a convenience to be taken:

  • (a) Generalize BandFilterProcessor to a runtime channel width. Touches the AVX2 8-lane filter fan-out, kNumFilters, both strides, and the hardcoded input buffer type — a core-path change to code that runs at 30 kHz. Benefits every future non-384 source. Highest risk item in this ticket.
  • (b) Consume the board's own on-FPGA decimated LFP stream as a second registry band data.intan.lfp, and point the ripple detector straight at it: input: data.intan.lfp, input_type: int16, decimation_factor: 1 — exactly the shape the NP1.0 path already uses, which is the path we have most confidence in. BandFilterProcessor is never involved. The board's chain is CIC + compensation FIR, 30 kHz → 3 kHz (R = 10), host-uploadable Q1.17 taps, design target flat to ~1 kHz with ≥46 dB alias rejection — and upstream's own doc names "sharp-wave ripples ~150–250 Hz, phase-targeted stimulation" as the motivating use case. It fully contains our 150–250 Hz band. Almost certainly lower latency than deriving in software, and it moves work off our CPU onto the FPGA — which is exactly the trade this repo says it wants.

Recommendation to put to the operator: (b) first, (a) later if a second non-384 source ever needs it. The blocker on (b) is §1.2 item 7 — whether the LFP stream is hardware-validated upstream — which is Kemere question K7.

One more consequence worth stating in the Intan profile: with no channel map published, RippleDetector.cpp:1029-1039 falls back to ch = (e >= 0 && e < kMaxChannels) ? e : 0 — electrode number is channel index. For Intan that is arguably the correct semantics, but the config numbers silently change meaning depending on whether a map exists. Say so in the profile comments.

5. Order of work — cheapest first, sim first#

Sim first is the repo's standing rule (AddingASourceModule.md §0, CLAUDE.md "Sim first, always"), and here it is unusually cheap because the transport is a socket. Every stage below except S6 and S7 runs on the Linux box with no hardware.

S0 — Ask the Kemere lab (§6) and read the source of truth. One round of questions, plus a line-by-line read of remote/net.py (131 KB) and firmware/include/main.h, plus ckemere/ephys-socket for cross-check. Budget a full day. Nothing below can start until the wire format is known. Deliverable: a written byte-layout spec with a version discriminator, checked into developer_docs/.

S1 — IntanSimSource + the buffer + a profile. NiDaqSimSource-shaped synthesizer writing straight into data.intan.raw. Proves the registry wiring, initDataSource band registration, liveness (noteCycle), the display path, and the recorder — with zero protocol risk. Green C++ suite.

S2 — IntanPacket parser + C++ unit tests. Header decode with the magic-word version discriminator, +2 deskew, cycle-major de-interleave against the enable mask, offset-binary conversion, SEQ gap detection. Tested against synthesized packets and against net.py's bit-exact debug-mode sine reference model. This is the highest-value test in the whole ticket — the parser is the one thing that cannot be checked by looking at the screen.

S3 — a mock board, on loopback. Not a synthesizer into the buffer (that was S1) but a process that emits the real UDP packet format, so the real IntanSource — sockets, discovery, TCP handshake, ring drain, reassembly, gap detection — is exercised end to end with no hardware. Upstream lists "Python mock board" as planned-but-not-done, so this does not exist and we would be first. It costs a socket. It runs in both suites on Linux. This is what catches a wire-format regression when upstream moves under us.

S4 — IntanSource (real), driven by the mock. Discovery beacon → paced TCP connect → GET_STATUS → SET_CHANNEL_ENABLE → setCapacity → addProducer, all inside initDataSource. Socket bound and draining before SET_UDP_DEST/START; sockets closed after the reader thread joins. Q_INVOKABLE controls with the disconnect-survival statics.

S5 — display + recorder + sidecar. IntanDisplayProcessor (NiDaq-shaped), IntanDataInterpreter with sampleWidth() and frameSpan(), usesProbeChannelMap = false, acquisition{} populated with board IP / firmware version / mask / phase / MAC. Fix the frontend µV gate here (§4.2) — the GUI suite gates this and it is 11 minutes, run it.

S6 — first contact with the real board, in SET_DEBUG_MODE. No headstage needed. Validates the whole path against a known synthetic signal whose expected values we have from net.py. Measure here: datagram loss on Windows at 30k/s, host ring overflow vs board-reported drops, CPU on the reader thread. If Windows cannot drain 30k datagrams/s, we find out now and it is a socket problem, not a neuroscience problem.

S7 — real headstage, one cable. Port A only, RHD2164 or RHD2132. Cable phase sweep hunting the ASCII INTAN pattern. Real neural data on screen. Then: the digital-input sync path against a shared TTL train, exactly the way we align NPX to NI-DAQ.

S8 — the LFP / closed-loop decision (§4.3), and only then ripple detection on Intan. Whichever of (a) or (b) the operator picks. Then end-to-end closed-loop latency measurement, which is the number that decides whether this is usable.

S9 (defer, explicitly out of scope): port B / 256 channels — upstream has not validated it on hardware. Aux/telemetry bands. IMU. Anything RHS/stim (does not exist on this board at all).

6. Questions only the Kemere lab can answer — ask these in one go#

Protocol / firmware 1. Which firmware is on our board, and which packet framing does it emit — the legacy 10-word header (word0 0xDEADBEEF) or the unified 14-word broadband framing (word0 0xCAFEBABE)? What fw_version does its beacon report? Is blobs/BOOT.bin on main the one we should be running? 2. Is the unified framing final, or still moving? Should we implement both with a runtime discriminator, or target unified only? 3. docs/protocol.md says GET_STATUS returns 160 bytes with a _Static_assert; net.py unpacks to offset 288; the ROADMAP mentions 98. What is the current status struct, and is there a version field in it? 4. Is there any machine-readable definition of the register/packet contract we could consume, or is hand-syncing the only option? (ROADMAP epic H suggests you want the former.)

Signal / calibration 5. What is the µV-per-LSB figure for this board as configured, and which RHD2000 gain/bandwidth registers does the firmware boot with? Can we read the commanded state back reliably from the register mirror in GET_STATUS? 6. Are amplifier bandwidth / DSP high-pass configurable today, or fixed at whatever the bitstream boots with?

LFP stream — this one is on our critical path 7. Is the on-FPGA LFP stream implemented and validated on real hardware? What decimation and filter does it ship with, is it byte-stable, and would you recommend we consume it rather than deriving LFP in software?

Hardware in hand 8. Which carrier PCB revision is our board (011 / 100 / 110)? Given the flipped-JX1 TODO in digital_inputs.xdc, which physical header pin maps to which digital_in_0[n] on that revision? 9. Has port B ever captured real data on hardware, or is 256 channels still a paper figure? Should we plan for 128? 10. Which headstages do we actually have — RHD2164, RHD2132, something else? Does RHD2216 enumerate? (It is not mentioned anywhere in the repo.)

Sync and closed loop 11. Are the 8 digital inputs level-sampled once per 33.3 µs frame (which is what the RTL looks like) or edge-captured? Can a TTL shorter than one frame be missed? Is edge capture planned? 12. Is there any board-level fast TTL/trigger OUTPUT suitable for closed-loop stim? We can see only the Intan auxout via SET_DIGOUT (0x76), with a ~1-packet GPIO-mirror path and an uncharacterized software/TCP path. Is a hardware trigger out planned? 13. Can the 30 kHz sample rate be changed at all without a Vivado rebuild, and is the PL clock parameterizable? 14. What end-to-end latency have you measured, board input to host userspace? We can see your recv→transmit instrumentation (~3 µs typ / ~10 µs max of 33.3 µs) but nothing covering wire + NIC + kernel + app.

Operational 15. Has anyone run this against a Windows host at 30,000 datagrams/s? Any known socket-buffer or NIC settings we should start from? 16. What is the current state of the GEM RX-hang / stale-DDR issues, and the rxwedge-* branches? Is the self-heal on main sufficient? 17. Are hotplug / DHCP / de-hardcoded IPs coming? We would prefer not to build a client around a hardcoded 192.168.18.x that changes under us. 18. Would you accept an MIT-licensed C++ client contributed back, and is remote/net.py the reference you would want us to track? 19. Is there a paper or preprint we should cite? We could not find one, and it is not on the lab tools page.
