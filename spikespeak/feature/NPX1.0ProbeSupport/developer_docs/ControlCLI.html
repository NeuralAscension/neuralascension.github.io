Control CLI — headless command interface#

python/spikespeak_cli.py drives a running SpikesPeak backend over its WebSocket (ws://HOST:1234) — the same socket the browser uses — so the whole acquire + record flow can run with no GUI clicking. It exists so tests (and agents) can launch, configure, record, and verify without a human at the mouse; an open browser mirrors the session live (source dropdown, play button, red Record button all reflect the CLI's actions).

Zero dependencies: a tiny RFC-6455 client on the Python standard library only.

Commands#

CLI command over the wire (0x1000 JSON) backend action
list {command:"listConfigs"} replies configList with every profile name
select "<name>" {command:"selectSource", value} onSourceSelection — full connect + wiring
waitready [timeout_s] (client-side) blocks until the source is ready (see readiness signal below)
probemap <default\|bank0\|bank1\|bank2\|PATH.imro> {command:"setProbeMap", value} IDataSource::applyNamedMap (NPX); NP1 bank presets validated
play / pause {command:"setPlaying", value} start / pause streaming
record <dir> <name> {command:"setRecording", value:true, dir, name} fan out to every recorder → files in <dir>/<name>/
stop {command:"setRecording", value:false} stop recording (streaming continues)
disconnect {command:"Disconnect", value:true} disconnect the source
quit {command:"quit"} shut the whole server down (QApplication::quit)
sleep <s>, help, exit — client-side (exit leaves the CLI, not the server)

Run modes: interactive REPL (python spikespeak_cli.py), one-shot (python spikespeak_cli.py list), scripted (--script "a; b; c"), or commands on stdin. --host / --port target a remote backend.

How the GUI mirrors a CLI session#

Each state-changing command broadcasts a state event to all clients; the browser reflects it in its toolbar without re-sending the command (main.js reflect* + NetworkClient handlers):

event emitted from browser reflects
stateSource (name) onSourceSelection / disconnect source dropdown + selectedSource
statePlaying ("1"/"0") setPlaying play button icon/green + Record enable
stateRecording (value,name) CLI setRecording path red Record button + flashing indicator
configList, serverQuitting listConfigs / quit CLI prints them; browser logs/status

stateSource is broadcast before the deviceReady connect result, so a watching browser records the source name in time for its QWebChannel bind (keyed on that name).

Recording/IMRO get this JSON command path in addition to their QWebChannel path (the GUI still uses QWebChannel). That small duplication is deliberate: it keeps the CLI QWebChannel-free. See ModuleCommunication.md.

Running the backend headless#

Linux (the current dev path — sim only, no hardware): just run the binary. On this box the Qt Creator build dir is build/Desktop_Qt_6_11_1_Release/ (Qt 6.11.1), so:

cd build/Desktop_Qt_6_11_1_Release
LD_LIBRARY_PATH=~/Qt/6.11.1/gcc_64/lib QT_QPA_PLATFORM=offscreen ./bin/SpikesPeak --no-browser &

QT_QPA_PLATFORM=offscreen is needed because the app links WebEngineWidgets/Widgets and there's no display; LD_LIBRARY_PATH points at the non-system Qt. There are no hardware DLLs to stage; the CLI drives it the same way (python spikespeak_cli.py --host localhost …), and the source to select is "Simulated Data". See SimDataLinux.md.

Windows (the historical hardware box) — runtime DLLs: the exe is normally launched by Qt Creator, which sets up the runtime environment. To launch it standalone (e.g. from a script), these directories must be on PATH or it exits instantly at the loader (before Qt) with no message — its non-system imports are Qt6*, NeuropixAPI_x64_4_1_3.dll, hdf5.dll/hdf5_cpp.dll, nicaiu.dll:

$env:PATH = "C:\Qt\6.7.3\msvc2019_64\bin;" +                                              # Qt runtime
            "C:\Users\BIOEl\Documents\Code\SpikesPeak\external\neuropixels\api\lib64\v4;" + # NeuropixAPI
            $env:PATH
# HDF5 (C:\Program Files\HDF_Group\HDF5\1.14.6\bin) is already on the system PATH; nicaiu.dll ships with the NI driver.
Start-Process -FilePath "...\build-...\bin\SpikesPeak.exe" -WorkingDirectory "...\bin" `
    -ArgumentList "--no-browser" -WindowStyle Hidden

Pass --no-browser (or --nobrowser) for automated runs: the app starts the HTTP + WebSocket servers but does not open any browser, so nothing is left open when the test ends. Open http://localhost:8080 yourself if you want to watch. Launched without a console, KeyboardListener detects the closed stdin and disables console input (instead of spinning) — the app keeps serving; drive it with the CLI and shut down with quit.

Browser launch (interactive runs). With no flag, running the executable now opens the UI in a dedicated browser app-window — a separate browser session in its own chromeless window, not a tab in your normal browsing. It uses a Chromium-family browser (brave-browser/chrome/chromium/edge, first one found) in --app mode with an isolated persistent profile at ~/.spikespeak/browser-profile (so window size/zoom persist and your normal profile is untouched). Closing that window drops the last WebSocket client, so the backend's grace timer shuts the server down shortly after — the window is the app's lifetime. Flags: --tab (a.k.a. --system-browser) opens a normal tab in your default browser instead (legacy behavior); if no Chromium-family browser is found it falls back to a tab automatically. main.cpp launchDedicatedBrowser().

Readiness signal + the correct teardown order#

  • Readiness. The NPX + NI-DAQ connect blocks the main thread for several seconds, so events only flush once it returns. When the probe is detected the backend emits guiStatus: "Found Neuropixels 1.0 Probe" (deferred from NeuropixelsSource, alongside deviceReady). waitready blocks on either — use it instead of guessing a sleep after select.
  • Teardown order matters. handleDisconnectRequest refuses to disconnect while the source is acquiring, and closing the probe mid-stream leaves the hardware in a bad state. The correct order is stop → pause → disconnect → quit. As a safety net, WebSocketServer::teardownSource() (used by both disconnect and quit) now pauses first if still streaming, so disconnect/quit are safe even if you forget to pause — but a record test should still stop first for a clean file.

Example: a full headless record test (validated on live hardware)#

python spikespeak_cli.py --script \
  "select 'NPX 1.0 with NI-DAQ'; waitready 40; probemap default; sleep 2; play; sleep 3; \
   record /path/to/RecordingTests test2; sleep 15; stop; sleep 2; pause; sleep 2; disconnect; sleep 3; quit"
# then plot + verify (saves sync.png + channels.png into the recording folder):
python examples/plot_recording.py /path/to/RecordingTests/test2

This exact flow was validated on the live rig: probe found via waitready, 15.4 s recorded (electrodes [1,192,196] @30k/2.5k + 8 NI-DAQ @40k), clean teardown, and the sync plot recovered a real +10.2 ppm clock drift between the NI-DAQ and NPX clocks (0.012 ms residual). Recording is backend-owned, so it keeps writing even if the CLI drops; when the last client disconnects an auto-shutdown grace timer starts.

When the user asks for a "Recording Test", run the canonical procedure in RecordingTest.md (this flow + plot_recording.py, and what the user looks for).
