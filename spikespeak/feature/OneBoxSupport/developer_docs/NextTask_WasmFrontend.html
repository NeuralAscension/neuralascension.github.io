NEXT TASK — The WASM front-end branch: what it should actually be#

Status: open runbook, written 2026-08-25. Not started. Nothing here is implemented. This is the plan for a feature branch that diverges from develop to replace the SciChart live view. It is written for an engineer or agent arriving with no context; every step names the fault or the measurement that motivates it.

Decided already, do not re-litigate: SciChart is being removed (operator approved). The replacement must be free / open source — LightningChart JS is rejected on cost. The UI chrome (headers, dropdowns, sliders, docks, channel labels) stays HTML/CSS/JS; that flexibility is a stated strength and is not on the table.

Read first: RenderingPerformance.md — it is the measured evidence this runbook is built on, and it already contains one reverted experiment that a naive WASM branch would repeat. Then LiveDataView.md (why the offset is baked into the samples), GuiTesting.md + GuiTestCoverage.md (the gate), and CLAUDE.md (latency and dropped samples first; no new dependencies; available-and-off).

0. The honest framing — read this before planning anything#

The operator asked for "a branch that moves the front end to WASM." Taken literally that is not the first lever, and this runbook says so up front rather than doing what was asked and missing the win.

The bottleneck is measured, and it is the main-thread DRAW. RenderingPerformance.md TL;DR: "The bottleneck is the DRAW of many series, not data ingestion. We moved the parse to a Web Worker and it changed nothing." That attempt (its "What we tried" table, row A) was implemented, verified working, measured, and reverted: 4×40 went 63 % → 65 % main-thread busy, 4×80 stayed at ~43 fps / 100 %. The stated cause is that appendRange and SciChart's draw both have to stay on the main thread, so relocating the parse bought a saving the worker round trip ate.

"WASM owns the binary decode" is that experiment again with a different compiler. The decode is not where the time goes, and it is not even much code: the backend has already decimated 30 kHz to min/max pairs in AVX2 (DisplayProcessor::calcMinMax), so the browser reads a header ([u8 idLen][idStr][u32 numChannels][u32 numBins], NetworkClient.js:61-90) and views a Float32Array. 50 frames/s/stream, 61,532 bytes each for a 384-channel raw stream — about 3 MB/s. It is voluminous, not complex, and it has already been measured at zero.

"WASM owns the ring buffers" is already true — they are in WASM today, just SciChart's. DataStore.initializeStream(wasmContext, ...) allocates two XyDataSeries FIFOs per channel into SciChart's heap, which is why main.js:16-18 raises wasmBufferSizesKb to 32768. Re-homing them into a second WASM heap so they can be copied to the GPU is a step sideways.

So the ordering this runbook recommends is:

Move the draw off the main thread first, in plain JS (OffscreenCanvas + WebGL2 in a Web Worker). Then measure. Only then decide whether any WASM is justified, with a profile attached.

That is not a refusal of the operator's goal. It is the ordering that makes the goal reachable: RenderingPerformance.md row A failed because SciChart's draw could not follow the parse off the main thread. Remove SciChart and that cause is gone — at which point "should the numeric core be WASM" becomes a live question again, answerable with a number instead of an argument. There is a real WASM case waiting on the far side of the renderer change (§2, phase 5); it is just not first.

And one thing must be said plainly so nobody mis-sells this branch. By CLAUDE.md's own two headline metrics — closed-loop latency and dropped samples — this branch scores zero. The browser is downstream of the AVX2 decimation and off the closed loop entirely; the display emit crosses a QThread boundary as a queued connection, and broadcastData (WebSocketServer.cpp) writes to every client unconditionally. A slow browser cannot back-pressure acquisition or the detector. The honest case for this branch is channel density, the offset-in-shader capability unlock, and eventually one fewer dependency. Latency and dropped samples are a regression gate here, not a target. Any framing that implies a latency win is false and will be caught.

The one indirect, real, and so-far-untested coupling: at 4×80 the browser main thread is 100 % busy and the WebSocket onmessage handler shares it, while the backend's fan-out has no bytesToWrite() check — so a saturated browser grows the backend's socket write buffer on the Qt main thread. Moving the socket into the worker fixes the drain. Treat that as a hypothesis to measure (phase 4), not a benefit to bank.

1. Recommendation#

Settled 2026-08-25. The operator picked the browser-capability route and explicitly deferred Rust/WASM out of this branch. The recommendation below was written before that call and agrees with it; §5 phase 5 carries the deferral.

Three positions were drafted for this branch. Take position 2 — DRAW-FIRST: OffscreenCanvas + WebGL2 in a plain-JS worker, with WASM owning nothing until a measurement says otherwise.

Position Verdict Why
1 — One boundary: WASM owns socket → pixels as one indivisible unit Rejected as the first step; harvest its ideas Its diagnosis is right (row A failed because the boundary was in the wrong place, not because workers don't help) and its data model is right (Y-only f32 ring, offset in the shader, X implicit in the ring index). But it is unfalsifiable in one step: if the fused C++/Emscripten column is slow you cannot tell whether the loser was the renderer, the toolchain, or the fusion. Its own kill criterion — "build it twice, once in plain JS" — is position 2, arrived at the expensive way.
2 — DRAW-FIRST, plain JS, WASM only on evidence RECOMMENDED It attacks the stage the repo has actually measured as the limiter; it adds zero build-time and zero runtime dependencies in phases 1–4; and every phase is independently revertable behind a flag. It keeps the WASM question open and answers it with a profile. If the operator later approves a toolchain, nothing is thrown away — the kernel drops into the same worker behind the same interface.
3 — Pixel Kernel: one C++ core compiled twice (native for the C++ suite, WASM for the browser) Deferred to phase 5 — and it is the right shape if WASM happens Its real contribution is not the toolchain, it is decimate-to-pixels on arrival: at the 1 s window a ~450 px-wide column carries roughly 4 points per pixel, at 10 s roughly 44, and every one is carried and re-processed each frame. Incremental pixel-column min/max is the largest remaining fixed cost once the draw moves, and it is window-size independent. Its testability argument is also correct: C++ is the only toolchain whose core lands in the 1.6 s build suite rather than the 5-minute browser suite. But it is a dependency ask, and a dependency ask follows the measurement — it does not precede it.

One line: ship position 2; hold position 3's pixel-decimation kernel as the phase-5 WASM proposal, to be taken to the operator only with a worker-thread profile showing the numeric core as the top cost.

2. Pin down "what WASM owns" — the three candidates, each answered#

"WASM for the front end" is an operator phrase, not a specification. It decomposes into exactly three candidate owners, and each is separately refutable.

(a) Rendering — WASM is orthogonal. The draw has to leave the main thread; the language it is compiled from is irrelevant to that. A WebGL2 line-strip renderer is a few hundred lines of JS plus a vertex and a fragment shader, and the shader already runs on the GPU either way. Verdict: not WASM's job. This is the whole win, and it is a plain-JS win.

(b) The binary-frame decode — already measured at zero. RenderingPerformance.md row A. Verdict: no, unless phase 4's profile contradicts it.

(c) The ring buffers — must move, but out of the chart library, not into a second WASM heap. Today data literally cannot exist before a chart does: main.js:460 wraps the whole working body of handleNewStream in if (this.columns.length > 0 && this.columns[0].wasmContext) — no chart, no stream, silently — and updateWindowSize is gated identically at :576. That cut has to happen under any renderer decision. The buffers become plain Float32Array rings owned by the worker; if a WASM kernel later lands they become views over its linear memory with no interface change. Verdict: re-home now, in JS.

The one genuine WASM candidate, for phase 5: the per-sample display transform plus incremental decimation to pixel columns. The transform (NetworkClient.js:120-186) is the per-channel decaying min/max AC-couple (DECAY = 0.9995), the zoom multiply, the offset add, and the NI-DAQ ±0.47×spacing clamp — 20 timebins × 384 channels × 2 = 15,360 scaled values per frame at 50 frames/s. The decimation does not exist yet and is the bigger prize. Both are straight-line float arithmetic over typed arrays, which is exactly what a JIT does well — which is why the phase-5 gate in §8 is deliberately hard to pass.

A structural win that falls out of the renderer change and that no amount of WASM delivers: the vertical offset stops being baked into the sample values. Today NetworkClient.js:183-184 writes channel.yOffset + value into one series and channel.yOffsetInterleaved + value into a second complete duplicate series, which is why DataStore allocates two FIFOs per channel for all 384 channels. In a vertex shader the offset is a per-channel uniform: the interleaved series stops being allocated, re-ordering becomes free, and LiveDataView.md §5.2's "No 'all shanks' option" restriction lifts. Lead with this when justifying the branch — it is a capability SciChart cannot sell at any price, and unlike frame rate it is not arguable.

3. The dependency question — three different asks, do not blur them#

CLAUDE.md makes a new dependency an operator decision. These three are not the same decision, and the branch must present them separately.

Ask Phases 1–4 Phase 5 (only if the gate fires) Notes
Build-time toolchain NONE. Emscripten SDK — genuinely new, needs an explicit operator yes. This repo has no JS build tooling at all: no package.json anywhere in the tree, and the CMake copy_webinterface target copies the directory verbatim. A worker file and a shader are text files that land in webinterface/ and get copied. emsdk would be the repo's first frontend build step, and it carries a sub-decision: build out-of-band and commit the .wasm, or wire emcc into CMake. Committing a binary artifact is itself an operator call.
Runtime library NONE, and trending to −3.4 MB. unchanged webinterface/lib/ ships index.min.js 2,148,228 B + scichart2d.wasm 1,279,360 B + scichart2d.js 161,661 B. qwebchannel.js (16,460 B) stays — QWebChannel RPC is out of scope. webgl-plot, regl and twgl are references to read while writing the shader, not packages to vendor. LightningChart is already refused on cost. Test side: numpy only (already present); scikit-image / SSIM is refused.
Browser capability COOP/COEP is a two-line change to the hand-rolled HTTP server in src/main.cpp, which today writes only status + Content-Type + Content-Length. Everything is same-origin, so isolation breaks no asset load. same Not needed by the recommended design, and deliberately left unpulled: transferables cover the socket → worker hop, and OffscreenCanvas covers the draw. It is required only if the main thread must later read the rings without a copy (SharedArrayBuffer) or if WASM threads are wanted. RenderingPerformance.md row D recorded COOP/COEP as pointless for SciChart (its .wasm is single-threaded); that finding does not carry over to a renderer we own.

The point to make to the operator explicitly: a WASM runtime is not a new runtime here. The browser ships one, and this front end has been shipping 1.28 MB of somebody else's WASM since day one. That ask is net-negative. The toolchain is the only genuinely new dependency on this branch, and it is not needed before phase 5.

4. What must NOT change#

  1. The WebSocket contract. Freeze it. The protocol on :1234 is not just the browser's API — it is also the API for the Python CLI, ripple_tools/, and scripts/run_gui_tests.py, which opens its own raw WS client alongside the browser. Any header change must additionally be made twice in C++ (DisplayProcessor.cpp:233-243 and NiDaqDisplayProcessor.cpp:184-191 each hand-write the same header; there is no shared encoder), or the NPX and NI-DAQ stream families diverge silently. The one exception permitted is the alignment pad in phase 0 — and it lands on develop, not on the branch.

Scope that exception correctly, because it is narrower than it looks. The text half of the protocol is the shared API. The binary display frame has exactly one consumer: the browser. python/spikespeak_cli.py:214 reads opcode 0x2 and drops it on the floor (# opcode 0x2 == binary display stream -> drained + ignored), and nothing under ripple_tools/ parses a display frame either — those tools read recorded .bins. So the pad is a two-writer C++ change plus one JS reader, and it does not touch a Python consumer at all. Do not let §4.1 talk you out of a change it does not actually cover. 2. The QWebChannel path. qwebchannel.js stays; the module Q_INVOKABLE commands stay; the substring-plus-duck-typing object discovery in NetworkClient.js stays exactly as written. There is no schema — the backend registry names are the contract. Reimplementing Qt's RPC is out of scope. 3. The state-snapshot ordering. stateSource must land before deviceReady; the browser's QWebChannel bind is keyed on the source name. Bind on a different trigger and every module panel silently empties — a cosmetic-looking failure with a contract-level cause. 4. The latency budget. Nothing on this branch may touch the acquisition, detection or stimulation path. Before merge, run the standard closed-loop ripple check; any measurable latency increase or any dropped sample kills the merge, because the expected effect is exactly zero and a non-zero result means something was wired wrong. 5. Available-and-off. Every phase ships behind a flag with SciChart as the default until its gate passes. This is the DerivedBands.md §5 pattern, and CLAUDE.md requires it. 6. console.error is fatal to the suite. All ten GUI tests call check_clean(), which fails on a failed resource load, an uncaught exception, an unhandled rejection or a console.error. A WebGL context-lost handler that logs an error reddens the entire suite. Renderer diagnostics go through console.warn. Hard constraint on the new code, not a style preference. 7. The GUI suite passes before every push. python scripts/run_gui_tests.py, ~5 min, not part of the compile. Hard operator rule. Every phase below leaves the branch green and is independently revertable.

5. The phases#

Each phase states what lands, how it is proved, and the gate before the next one. Each is a separate commit range that can be reverted without touching the ones before it.

Before any of it — the edit loop on this branch is not the one you are expecting. The HTTP server serves <exe>/../webinterface, not the source tree (CMakeLists.txt:270-285, copy_webinterface). Editing a .js file and reloading the browser does nothing; you must re-run cmake --build for the copy target to fire. And the backend must be down before that build, or the link dies on LNK1104: cannot open file — and per CLAUDE.md you may not force-kill it, so it is Pause → Disconnect → quit every cycle. On a branch that is almost entirely front-end work this is the dominant per-iteration cost, and it is the first thing an engineer will hit. Budget for it, or spend the first hour making copy_webinterface a directory symlink / junction on the dev box so a reload is a reload.

Phase 1 — The spike: one column, one stream, WebGL2 in a worker, flag-gated off#

What lands. ?renderer=webgl2 — which requires phase 0's query-string fix first; it 404s against today's server — puts column 0 only on a new path: an OffscreenCanvas transferred from chart-area-0 to a plain-JS Web Worker running one WebGL2 line-strip program, with yOffset as a per-channel uniform so the interleaved buffer is never allocated. Columns 1–3 stay on SciChart, in the same window, on the same live stream. Fed from NetworkClient's existing per-channel scratch buffers via transferables. No DataStore rewrite, no label-overlay change, no ImroManager, no wire-format change, no toolchain, no zoom, no stream switching.

Why this is the right first cut. It is self-comparing: the same signal drawn by both renderers a few hundred pixels apart, in one process at one instant — the parity check this repo cannot otherwise perform, with no cross-session sim drift.

How it is proved. benchmarks/cdp_bench.py at the 80-series cell with the phase-0 presented-frame counter. Baseline from RenderingPerformance.md: 80 series = 60 fps at 30 % main thread (2 × 40 row; take the 1 × 80 figure from your own sweep rather than interpolating).

Gate: the worker column holds 60 fps at ≤ 5 % main-thread busy attributable to it, and the full GUI suite passes with the flag both off and on. If it lands within ~2× of SciChart's main-thread cost at that density, stop — see §8.

Phase 2 — Cut DataStore free of the chart library#

What lands. DataStore owns plain Float32Array rings with no wasmContext argument; main.js:460 and :576's early-returns disappear; capacity moves off calculateCapacity()'s float64 X-and-Y, two-series-per-channel model to Y-only with X implicit in the ring index. The whole 117-line file is rewritten. SciChart columns are fed from the same rings via appendRange, so both renderers still work.

Why now. Streams currently cannot exist before a chart does. That is a defect under any renderer, and it specifically blocks a non-SciChart column 0 from ever discovering a stream.

How it is proved. live_view.py's knownStreams > 0 assertion — the suite's only genuine data-arrival check — must still pass, now keyed on renderer readiness rather than wasmContext. Do not delete it: it is what distinguishes streaming from a healthy-looking dead rig (CLAUDE.md, "Sim first, always").

Do not expect a residency win in this phase — expect the opposite. SciChart draws out of its own XyDataSeries FIFOs; feeding it from the new rings does not free them, it adds a second copy alongside them, so phase 2 measured on its own raises heap. The ~8× figure is the phase-3/4 end state, once SciChart is no longer the thing being drawn from. Record heap at phase 2 anyway, but record it as the transition cost it is; quoting it as a win here is how a real regression gets shipped as a milestone.

Gate: GUI suite 10/10 with the flag off (SciChart driven from the new rings) and on.

Phase 3 — The renderer interface, and all four columns behind the flag#

What lands. A ~10-method Renderer interface (createSurface, addAxisRange, allocChannel, bindSlot, setVisible, setStroke, append, clear, resizeCapacity, destroy) covering all 16 explicit SciChart.* construction sites in the live view, with both implementations behind it. The WebGL2 renderer grows what the spike skipped: wheel zoom, stream switching, shank/L-R filters, window-size changes, resize, and context-loss recovery that logs through console.warn. Plot-rect geometry is posted to the main thread on resize only — never per frame, or the worker win is spent back on style recalculation (syncLabelOverlayGeometry currently runs on every rendered event and writes four inline styles per column).

How it is proved. The parity harness (§6) at 1×20, 2×40 and 4×80, plus the full density sweep (§7).

Gate — the branch's headline gate: 320 on-screen series (4 × 80) at 60 fps with main-thread busy under ~40 %, against today's 45 fps / 100 %. Measured with the ripple dock open as well as closed (§7). Plus GUI suite 10/10 with the flag off and on.

Phase 4 — Move the socket into the worker; flip the default#

What lands. The worker opens its own data-only WebSocket, or the existing socket moves into the worker and relays JSON strings back to main. Decide the split deliberately: today one socket multiplexes the binary display frames and the entire JSON control plane — QWebChannel transport frames, ripple events, hardware-fault and probe-mismatch blocking modals, state mirroring, the config list. The ripple envelope event is throttled to ~25 Hz, so relaying strings is cheap; the risk is in the split, not the transfer.

"The worker opens its own socket" is the worse half of that choice, and the reason is in the backend. WebSocketServer::broadcastData (WebSocketServer.cpp:794-798) is a bare for (client : m_clients) sendBinaryMessage(data) — there is no per-client subscription. A second socket from the same browser therefore does not move the binary stream off main, it duplicates it: the main-thread socket keeps receiving every 61.5 kB frame and paying the receive + discard, and the backend's fan-out cost doubles for one browser. Either move the existing socket wholesale into the worker, or add a subscribe/unsubscribe to the protocol — which §4.1 says is frozen. Choose knowingly; do not discover this at the bench. Then, and only if every gate above has held, flip the flag default to the new renderer with SciChart still selectable for one release.

How it is proved. The drain hypothesis is tested here rather than assumed: with the browser at 4×80, measure the backend's socket write-buffer growth before and after. This is the one place the front end touches the backend, and nobody has measured it.

Gate: GUI suite 10/10 with the new renderer as the default; the closed-loop regression check clean; and a worker-thread profile captured, because that profile is the input to phase 5.

Phase 5 — WASM, only if the profile says so#

OPERATOR DECISION, 2026-08-25: this phase is OUT OF SCOPE for the branch. Asked where to lean, the operator chose the browser-capability route — WebGL2 and OffscreenCanvas, which are already in every browser and are not a new dependency of any kind — and said of a Rust/WASM pipeline: "might be the direction we head to in the future but the feature branch shouldn't worry about that."

So phases 0–4 are the branch. This phase stays written down because the analysis is worth keeping and because phase 4's profile is what would justify reopening it — but nobody should start it, and the emsdk toolchain ask in §3 does not arise. If phase 4 lands and the profile still shows a main-thread numeric cost worth removing, bring this back as its own proposal with that profile attached.

What is proposed (not committed). Position 3's kernel: decode + display DSP + incremental min/max decimation to pixel columns, in C++ compiled by Emscripten, glue-free (--no-entry, -sSTANDALONE_WASM, own bump allocator, no exceptions or RTTI), with the same .cpp compiled natively into the existing Qt Test suite. C++ specifically because tests/CMakeLists.txt's spikespeak_test(NAME SOURCES ...) links production .cpp files directly, so the numeric core gets a QCOMPARE in the 1.6 s build suite instead of being testable only through the 5-minute browser suite — and min/max decimation is associative, so "decimating already-decimated pairs equals decimating once" is a one-line assertion. Rust + wasm-bindgen is the runner-up and loses on shipping a generated JS shim and on adding a second systems language; AssemblyScript needs npm in a repo with no package.json; Zig is a third language for no gain.

Precondition — this is the operator decision. Do not open this phase without all three of: (a) the phase-4 worker-thread profile showing decode+transform+decimate as the top cost on the worker, (b) the phase-0 avgParseMs numbers, (c) a plain-JS decimator to compare against. Take all three to the operator together with the toolchain ask, as one ask, not three.

Gate: §8's phase-5 kill criterion. It is deliberately hard, and a tie means no toolchain.

Not in this branch: the probe map#

ImroManager.js carries roughly half of the front end's SciChart references across ~1,400 lines — scatter series with point markers and data labels, box and custom annotations, ZoomExtentsModifier, and seriesViewRect hit-testing for click-to-select electrodes. GuiTestCoverage.md §5 lists the probe map as not covered by any GUI test, and it is the surface that writes hardware configuration (Apply Map to Hardware) and picks recording channels.

6. The parity problem#

Nothing in this repo compares pixels. Gui.shoot() writes PNGs and no caller ever reads one back; the handful of tracked frames under developer_docs/images/gui/ are docs illustrations captured against a free-running sim, not goldens. So "draws the same thing as SciChart" currently has no mechanical meaning. Inventing that meaning is part of the branch, and it must land with phase 1, not after.

What the parity harness actually needs#

  1. A deterministic fixture. Every current test drives a free-running sim, and an image comparison against a moving target is noise. Cheapest option: replay a captured binary frame byte-for-byte into both renderers, with no backend at all. Second option: a play-file source with the stream paused. Note the fixture spec that a naive renderer gets wrong: the wire carries two points per timebin (a decimated min and a max), not raw samples. A renderer that treats them as ordinary samples draws a plausible-but-wrong envelope with a green suite.
  2. A renderer-neutral probe, implemented identically by both renderers: col.probeRender() -> {seriesCount, pointsPerSeries, plotRect, yForValue(v), colorOf(i)}. It replaces the dead SERIES_PROBE and is what cdp_bench.py reads. It may return a Promise — the worker owns this state and a synchronous getter would have to mirror it back to main on every frame, which is the cost the branch exists to avoid. cdp.py:63 evaluates with awaitPromise=True, so Gui.probe() already resolves a promise transparently; the only requirement is that it resolves to a JSON string, because _harness.py:457 is json.loads(self.c.eval(js)).
  3. Structural assertions, not pixel equality. Exact pixel equality between SciChart's WASM rasteriser and a WebGL2 line strip is unachievable by construction (antialiasing, joins, endpoint rounding), so it must not be the gate. Assert instead: - the same number of visible traces; - each trace centreline within N px of ((i + 0.5) / shownSlots) × plotHeight — ChartColumn.js's own rule, asserted as a rule rather than a table; - a known input amplitude landing on the same pixel row within tolerance; - stroke colour matching Config.PALETTE[i % len] exactly — colour is discrete, so assert it exactly even though geometry gets a tolerance.
  4. An optional clipped-screenshot diff via the existing Gui.shoot(clip_selector=...) path, scored as mean absolute difference on a downsampled grayscale using numpy only (already available test-side). scikit-image / SSIM would be a new dependency — refuse it.
  5. Three cells, not sixteen: 1×20, 2×40, 4×80.

Mechanics. run_gui_tests.py globs tests/gui/*.py, so a new file joins the suite automatically and changes the pass count — no runner work. Select the renderer with an environment variable (mirroring the existing SPIKESPEAK_GUI_SOURCE / SPIKESPEAK_TEST_BROWSER pattern) and run the suite twice, rather than driving two browsers inside one test; each test file already pays ~20 s of fixed launch and settle cost.

The precedent that makes this non-optional: benchmarks/CHANNEL_DENSITY_REPORT.md opens with a correction that an earlier sweep accidentally measured empty surfaces. A renderer branch with no "traces are actually drawn" assertion will make that mistake again — and this time it will be shipped.

How to measure so the comparison is real:

  • Same script, same sweep, same box: benchmarks/cdp_bench.py (COLS = [1,2,4] × TRACES = [20,40,60,80], 7 s settle per cell), same sim profile. Do not hand-roll a new rig — a new rig makes the before/after incomparable, which is the whole point of quoting the old table.
  • Fix the counter first (phase 0). window.__perfStats is a main-thread rAF loop and main_thread_busy comes from CDP TaskDuration — also main-thread. Moving the draw off main makes both meaningless unless the counter reports presented frames from where the draw happens. Publish the same object shape so cdp_bench.py is unchanged.
  • Control the client count. broadcastData fans the same bytes to every connected client with no subscription and no backpressure, and run_gui_tests.py opens its own WS client alongside the browser. A one-client baseline against a two-client "after" is not a comparison.
  • Measure with the ripple dock OPEN as well as closed. RippleModule.js starts an unconditional rAF loop at dock construction that never stops, and its draw reallocates a canvas (cv.width = cv.clientWidth) per channel per frame. The published table was taken on a bare live view, so the real operator ceiling is lower than 320. Report both columns. (That loop is also proof this codebase already hand-draws to a canvas without a chart library.)
  • Sweep the window size — ten minutes, zero code, and almost certainly never done. Change the Window dropdown 1 s → 10 s at a fixed series count: that is a 10× change in points per series, and updateWindowSize genuinely reallocates the FIFOs. If FPS and main-thread busy are flat, vertex count is not the cost and per-series draw-call overhead is — which weakens the phase-5 decimation case before anyone writes a line of C++. If it degrades, decimation is confirmed as a lever. The published table looks like it was taken at the default 1 s window throughout.
  • Report residency, not just FPS. Current model: calculateCapacity() = 50 × 20 × 2 × window × 1.2 points per series, float64 X and Y, two series per channel, 384 channels — which is why wasmBufferSizesKb is 32768. A Y-only float32 ring with X implicit should be roughly 8× smaller. That is a checkable milestone independent of frame rate.

8. Kill criteria#

Primary — kills the branch. If the phase-1 spike does not bring main-thread busy below ~10 % at a sustained 60 fps at the 80-series cell — that is, if OffscreenCanvas + WebGL2 in a worker lands within ~2× of SciChart's measured cost there — then moving the draw off the main thread is not the lever either, and the branch stops before DataStore is touched. RenderingPerformance.md row A was implemented, verified, measured at zero and reverted; this branch must be willing to end the same way, and phase 1 is scoped so that ending is cheap. Measure with the corrected counter or the number is meaningless.

Scale gate — kills phase 3 even if the spike passed. If 4 × 80 / 320 series does not reach 60 fps at under ~40 % main-thread busy, the branch has not bought the density it exists to buy. Ship the flag off, keep SciChart as the default, write the numbers into RenderingPerformance.md, and revisit. The fallback is the existing guidance: keep density ≲ 160–200 as a permanent constraint rather than a temporary one.

Correctness gate — kills the merge regardless of frame rate. If the parity harness cannot be made to distinguish "drawing correctly" from "drawing nothing" — specifically, if killing the worker does not turn the new assertion red — then the branch has no gate the hard pre-push rule can rely on, and it does not ship at any speed.

Regression gate. Any measurable closed-loop latency increase, or any dropped samples, in the standard ripple check. Expected effect is zero, so a non-zero result means something was wired wrong rather than that a trade-off was made.

Phase-5 gate — the one aimed at the WASM ask itself. Abandon the kernel unless both hold: the WASM decode+decimate stage costs ≤ half the plain-JS reference implementation on the same frames, and that saving is ≥ 5 % of one core at the 4 × 80 wall. The 5 % floor is not arbitrary: the wall is 100 % of one core at 45 fps, and a saving below that cannot close a 45 → 60 fps gap. A tie means the operator is being asked to install a build-time SDK for no measured gain, which is exactly the trade CLAUDE.md's dependency rule exists to refuse. In that case the honest recommendation is: ship the JS worker renderer, keep the pixel-decimation design, and withdraw the toolchain ask entirely. This is a real risk, not a formality — the workload is a few MB/s of straight-line float arithmetic over typed arrays, which is what a JIT does well.

Earlier and cheaper, from phase 0. If the recorded avgParseMs at 4 × 80 is under ~2 ms of the 20 ms inter-frame budget, the decode half of phase 5 is dead on arrival on frame-rate grounds and only the decimation half survives. Report the number either way. Its current absence is the weakest link in every argument on this branch, including this document's.
