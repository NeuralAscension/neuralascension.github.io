SpikesPeak — Module Communication (frontend ⇄ backend commands)#

How the browser UI sends commands to backend modules, and the one standard every module should follow: a per-module Q_INVOKABLE exposed over QWebChannel ("Option A"). This doc covers the two modules migrated to the standard so far — the Neuropixels source and the Recording sink — and gives the general recipe for the rest.

Wider context: SpikesPeak_Architecture_Review.md §7 (the Option A decision) and §3 (the WebSocket multiplexing). For the recording data path specifically, see Recording.md.

1. The transport: one WebSocket, three multiplexed channels#

The backend serves the UI over HTTP :8234 and opens the system browser; all backchannel traffic rides one WebSocket on :1234 (NetworkClient.js ⇄ WebSocketServer.cpp), split three ways:

Channel Direction Carries Entry point
(a) Binary waveform stream C++ → JS decimated samples for the live view broadcastData → NetworkClient.handleMessage (ArrayBuffer)
(b) JSON app commands JS → C++ setPlaying, selectSource, Disconnect (global app verbs) id 0x1000 → onTextMessageReceived
(c) QWebChannel RPC JS ⇄ C++ per-module commands (the standard) + C++→JS events Q_INVOKABLE on a registered object

Channel (b) is the small set of global verbs that aren't owned by any one module. Channel (c) is where module commands live. (A legacy binary command id 0x1001 used to carry recording toggles through a CommandDispatcher; it has been removed in favour of (c) — see §4.)

C++→JS events (e.g. deviceReady, recordingStatus) are plain JSON text messages the server pushes to every client (WebSocketServer::setDeviceState / broadcastStatusEvent); NetworkClient dispatches them by their event field.

2. The standard: per-module Q_INVOKABLE over QWebChannel (Option A)#

Every module command is a Q_INVOKABLE method on the module's own QObject, exposed over QWebChannel. The browser binds the object and calls the method directly — there is no central command router to edit when you add a module. Adding a camera with setExposure() is just: declare the invokable, register the object, bind it in JS.

The lifecycle has four steps, all already in place for both example modules:

 (1) REGISTER            (2) BIND                  (3) INVOKE                  (4) TEARDOWN
 C++: onSourceSelection  JS: on "deviceReady"      JS: obj.method(args[,cb])   C++: on "Disconnect"
 mWebChannel             new QWebChannel(...)       →  C++ Q_INVOKABLE runs     mWebChannel
   ->registerObject(       bind channel.objects                                   ->deregisterObject(
     "registry.name",       by name substring                                       obj)
     obj)                   to window.<global>

2.1 Registration (C++, WebSocketServer::onSourceSelection)#

When a source is selected, the server resolves the profile's registry names and registers each module object under its registry name:

  • the source object (e.g. source.npx.pxi) — always;
  • the recorder processor (e.g. proc.npx.recorder) — if the profile has one.

registerObject(name, obj) only introspects the meta-object and stores a pointer; the object may live on any thread (see §5).

2.2 Binding (JS, NetworkClient.handleMessage on deviceReady)#

Once the device reports ready, the client builds one QWebChannel and binds each backend object to a window.* global by a registry-name substring:

Object (registry name) Substring match Global
source.npx.pxi "npx" and not "recorder" window.activeNpxModule
proc.npx.recorder, proc.nidaq.recorder, … "recorder" (all matches) window.activeRecorders (array)

Both the source and the recorder names contain "npx", so the source match explicitly excludes "recorder". Recording is the multi-instance case: a profile can configure several recorders (one per data source — e.g. NPX and NI-DAQ), so the binding collects all "recorder" objects into an array, and the single Record button fans out to every one (§4). Keep registry names substring-distinguishable when you add modules.

2.3 Invocation (JS)#

// no return value needed -> just call it (recording fans out to every bound recorder)
window.activeRecorders.forEach(r => r.setRecording(true));

// return value needed -> pass a callback (QWebChannel delivers the result async)
window.activeNpxModule.applyMapToHardware((ok) => { /* ok is the C++ bool */ });

2.4 Teardown (C++, Disconnect)#

deregisterObject for the source(s) and the recorder; the recorder pointer is tracked in mRecorderProc so it can be deregistered and its error signal disconnected.

3. Module A — Neuropixels source (source.npx.pxi)#

The reference implementation of Option A. Six Q_INVOKABLEs on NeuropixelsSource (NpInterface.hpp) drive the IMRO panel:

Method Returns Purpose
getImroAsJson() QString serialize the current map → JSON for the UI
updateImroFromJson(json) bool validate + atomically replace the map
applyMapToHardware() bool push the map to the probe
getImroAsImroText() QString .imro text for client-side download
loadImroFromText(text) bool parse .imro contents (read client-side) into the map
saveImroToFile(path) bool server-side write (programmatic; UI uses the download instead)

Bound to window.activeNpxModule; called from ImroManager.js. NeuropixelsSource lives on the main thread (only its acquisition worker is on a separate thread), so its invokables run directly and may return values synchronously (§5).

File I/O for these stays in the browser (read via <input type=file>, write via Blob download) — see the architecture review §7.5. Never open a modal dialog inside a Q_INVOKABLE.

4. Module B — Recording sink (proc.npx.recorder, proc.nidaq.recorder, …)#

Migrated to Option A (was a 0x1001 binary command through CommandDispatcher). One invokable on RecordProcessor (RecordProcessor.hpp):

Q_INVOKABLE void setRecording(bool enable);   // open (true) / close (false) the output files
  • Multiple recorders, one button. A profile can configure several RecordProcessor instances — e.g. config/NpxPxiNiDaq.yaml has proc.npx.recorder (records data.npx.raw) and proc.nidaq.recorder (records data.nidaq.raw). WebSocketServer::onSourceSelection registers every one; NetworkClient binds them all into window.activeRecorders; AppController.toggleRecord() calls setRecording(...) on each. This restores the old 0x1001 behaviour, where the broadcast hit every recorder subscriber. (The old single-activeRecorder binding only drove the last recorder — a regression that's now fixed.)
  • Per-recorder, per-stream config — including channel selection — lives in the YAML. Each recorder's recordings: list names a data_name, a data_interpreter_name, an output_filename, and an optional channels: [...]. That channel list becomes the filter passed to the interpreter's serializeAvailableData, so e.g. channels: [0, 3] records only NI-DAQ channels 0 and 3. Each module supplies its own interpreter (interp.npx.raw → NpxDataInterpreter, interp.nidaq.raw → NiDaqDataInterpreter), so formats stay independent. (The long-term generalisation — one recorder, many interpreters — is SpikesPeak_Status.md §11.1.)
  • Workflow unchanged for the user: the Record button is enabled only while playing, so it's still Play first, then Record (the recorder reads the live buffer).
  • No return value. Opening files is asynchronous (it's marshaled to the recorder's worker thread, §5), so success/failure can't come back through the call. Instead the backend pushes a recordingStatus event:

RecordProcessor::applyRecordingState --(open fails)--> emit sigIpErrorOccurred(msg) -> WebSocketServer::slBroadcastRecordingError -> broadcastStatusEvent("recordingStatus", msg, "error") // JSON text to all clients -> NetworkClient: window.guiStatus(msg,"error") + window.onRecordingError(msg) -> toolbar turns red; main.js reverts the optimistic "recording" button state

This request (invokable) + outcome (event) split is the recommended shape for any module command whose work is async or happens off the GUI thread.

5. Thread-safety — the one rule that bites#

QWebChannel invokes Q_INVOKABLEs with Qt::DirectConnection — i.e. on the GUI / transport (main) thread, regardless of the object's thread affinity. So:

  • Main-thread objects (the NPX source): invokables run on the main thread. Fine to touch state and return a value synchronously.
  • Worker-thread objects (every IProcessor sink — ProcessorManager does moveToThread): the invokable body still runs on the main thread, so it must not touch state owned by the worker thread directly. Marshal onto the object's own thread first:

cpp Q_INVOKABLE void setRecording(bool enable) { QMetaObject::invokeMethod(this, [this, enable]() { applyRecordingState(enable); }, Qt::QueuedConnection); // hops to THIS object's thread; runs after the marshal }

This is why setRecording returns void and reports outcomes via an event (§4): the real work (applyRecordingState) runs later, on the recorder's thread, where it can safely open/close files without racing the slProcessAvailableData timer slot.

Rule of thumb: return a value only from a main-thread object's invokable. For a threaded sink, make the invokable void + marshal + emit a status event.

6. Recipe — add a command to a new module#

  1. Declare a Q_INVOKABLE on the module's QObject (Q_OBJECT required). Return a value only if the object lives on the main thread; otherwise make it void.
  2. (Worker-thread objects) marshal the body to the object's own thread with QMetaObject::invokeMethod(this, functor, Qt::QueuedConnection).
  3. Register the object in WebSocketServer::onSourceSelection via mWebChannel->registerObject("registry.name", obj), and deregister it in the Disconnect handler. (Sources are already handled by the generic loop; a new sink needs a line like the recorder's.)
  4. Bind it in NetworkClient.handleMessage's deviceReady callback: window.activeX = channel.objects[keys.find(k => k.includes("yourname"))]. Keep the registry name substring-distinguishable from the others.
  5. Call it from your frontend code: window.activeX.method(args[, cb]).
  6. Async outcome? Emit a signal the server relays as a JSON event (mirror recordingStatus), and handle it in NetworkClient → window.guiStatus / a UI hook.

7. Not on the standard yet (to migrate later)#

  • Global app verbs (setPlaying, selectSource, Disconnect) still ride channel (b) JSON id 0x1000. These are app-level, not module-level, so they may legitimately stay — but a future cleanup could route them through a dedicated controller object's invokables too.
  • AudioProcessor still subscribes to a CommandDispatcher id (0x218). The CommandDispatcher infrastructure remains (it's generic); migrating Audio to a setX() invokable is the same recipe as §6. The recording migration removed the only UI-facing CommandDispatcher user.
  • IDataSource::handleWebCommand (the legacy fire-and-forget JSON hook) still exists as a no-op default with a known routing gap (architecture review §7.4); prefer Q_INVOKABLE.

8. Control CLI — channel (b) JSON as a scripting surface#

python/spikespeak_cli.py drives the app headlessly over the same WebSocket, using channel (b) JSON 0x1000 commands (not QWebChannel). WebSocketServer::onTextMessageReceived handles the CLI verbs — listConfigs, setProbeMap, setRecording, quit — alongside the existing global verbs (§7).

Deliberate divergence from Option A: recording and IMRO get a JSON command path here in addition to their QWebChannel path. setRecording fans out to mRecorderProcs by invoking each recorder's setRecording Q_INVOKABLE by name (QMetaObject::invokeMethod(..., Qt::DirectConnection, …) — the same thread + method the browser hits via QWebChannel); setProbeMap calls IDataSource::applyNamedMap (NPX override). This keeps the CLI QWebChannel-free (a Python client would otherwise have to speak the QWebChannel protocol). The GUI still uses the QWebChannel path; both call the same backend methods.

State-mirror events (stateSource / statePlaying / stateRecording, via broadcastJson) let a watching browser reflect a CLI-driven session without re-sending commands. Full reference: ControlCLI.md.
