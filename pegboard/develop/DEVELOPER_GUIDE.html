Developer guide

What the system is, how it is put together, what every file and function does, and — for the parts where the obvious implementation is the wrong one — why it is built the way it is.

For running a session, see OPERATOR_GUIDE.md. For using the rig, ENGINEERING_GUIDE.md; analyzing its data, ANALYSIS_GUIDE.md. When something is broken, DEBUGGING.md. Open work is in BACKLOG.md.

1. The one architectural fact

The ESP32 runs the experiment. The Pi records it.

Peg detection and stimulation happen entirely on the microcontroller and do not depend on the Pi at all. If the Pi's display dies mid-session the participant is still being stimulated — it just is not being recorded.

Everything else follows from that. The Pi is never in a control loop, so its latency, its scheduler and its browser cannot affect what the participant receives. It is a witness.

3. Firmware — microcontrollerCode/adafruitESP32Feather_s3_usb/

One .ino, currently pegboard-usb 1.3.0. Two pinned FreeRTOS tasks joined by a queue.

Why two cores

USBCDC::write() blocks for up to 250 ms (tx_timeout_ms, Arduino core 3.3.11) when the host stops draining the endpoint. In a single loop that stall lands inside peg detection and therefore delays the stimulation the participant receives. So:

taskcorepriorityowns
acquisitionTask03the scale, detection, the trigger, the self tests
commsTask12the USB link — the only task allowed to block

Core 0 for acquisition because loop() and the Arduino event task are both pinned to core 1 by CONFIG_ARDUINO_RUNNING_CORE=1.

emit() is the join: fixed-size Msg structs, copied by value, zero tick-wait, and on overflow the oldest message is discarded. Losing stale telemetry is always better than delaying the next stimulation trigger. Overflows are counted in droppedMsgs and reported by the tx_dropped self test.

BIST_CORE_AFFINITY asserts this arrangement at runtime rather than assuming it, because a toolchain change to CONFIG_ARDUINO_RUNNING_CORE would undo it silently.

Latency profiling

One Profile: line per confirmed placement, giving the stage breakdown of the interval between the acquisition pass starting and the trigger firing. This is what turns "where does the time go" from an inference into a measurement — the Pi cannot resolve these stages at all, because from outside they are a single message arriving afterwards.

stagewhat
acquire_usthe get_units(8) read that first sees the step
settle_usthe deliberate delay(100)
recheck_usthe confirming get_units(3)
verify_usthreshold arithmetic plus the register write — ~0 by construction

Cost to the participant's path: four micros() calls, measured at 0.0049 ms by the profile_cost self test. Two of the four only run on a pass that confirms a placement. Everything else — the trigger timestamp and both emit() calls — sits below TRIG_HIGH(), where MSG_PEG already sat.

The trigger timestamp is taken immediately after the edge, never before. Measuring it from in front would have been the one way this instrumentation could have cost something that mattered.

Consumed by analysis/latency_report.py via the latency_profile events the Pi records.

Messages out

Line-oriented ASCII, deliberately close to the old Wi-Fi wire format so the Pi parser barely changed and the raw log stays readable without a parser. Every line ends Seq: <n> — a uint16 that makes a dropped message detectable, which UDP never allowed.

Weight: 12.34567, Time: 4821, Seq: 9
WeightChange: 2.50000, Time: 5000, Seq: 10
Detection Latency: 211 ms, Pegs: 3, IPI: 1450 ms, Seq: 11
Starting timer! GO GO GO! Time: 53762, Seq: 135
Task reset. Ready for next session.
BIST: hx711_rate, status: PASS, value: 89.69, unit: SPS, lo: 60.00, hi: 110.00, note: ok, Seq: 38

Things that must not be changed casually

The peg-detection logic. minWeightChangeReq (1.25 g), weightThreshold (4 g), the delay(100) re-check and get_units(8) were tuned empirically over months across MS patients and healthy controls. The ~200 ms they cost is a settled experimental result, not an inefficiency. The USB rewrite preserved them byte-for-byte.

targetWeight stays unreachable. It is deliberately above what 25 pegs weigh so a run never self-terminates — a knock to the table could otherwise both end a session early and register a false placement. The operator always stops the run.

Nothing may be inserted between verification and TRIG_HIGH(). That interval is ~0 by construction and is the one part of the latency chain not already dominated by sensor settling. A Serial.write() there would inject up to 250 ms.

Every pinned task loop needs a real vTaskDelay. taskYIELD() only yields to equal-or-higher-priority tasks, so the idle task never runs and the 5 s task watchdog fires. The HX711 library's internal yield() has the same limitation.

4. Built-in self tests

22 checks — 12 in firmware, 10 on the Pi — reduced to one greenlight. The rationale, limits and measured values are in BACKLOG.md item 5; the operator-facing description is in OPERATOR_GUIDE.md.

Three design decisions worth not undoing:

Two suites, split on whether they can stimulate. The passive suite is safe whenever the task is not running. The trigger wire test drives TRIGGERPIN for 50 ms — a real pulse — because the Pi can confirm stimulation is being recorded only by seeing an edge it knows was sent. It is never automatic.

The greenlight is never green on absence. Any check that has not reported leaves the verdict unknown. A lamp that goes green because a test never ran would be trusted, and would be wrong. The two trigger tests are excluded from the verdict until they have a result, because not having stimulated is not a fault.

Firmware results are dropped when the board resets. Opening the serial port asserts DTR and reboots the board, so earlier results describe a different boot. They also expire after 30 minutes.

5. The Pi application — raspberry-pi5/

Flask + SocketIO. One background greenlet, process_data(), drains the link and the GPIO queue; everything else is a socket handler.

Two behaviors that look like bugs and are not:

  • The link is drained even when not streaming. The board is silent by design then, so it costs nothing — but without it a self test run before STREAM DATA sits unread in the kernel buffer, which is exactly when an operator wants to run one.
  • _finish_session() sends stop_timer. The board's task flag is independent of the Pi's recording state. Without this the board keeps detecting placements and firing the stimulator after the operator has stopped — delivering stimulation that nothing is recording.

serial_link.py — USB transport, stdlib only

No pyserial: the Pi has no reliable route to a package index, and a data-acquisition rig should not need a wheel download to boot. termios gives everything a CDC ACM device needs, and baud rate is meaningless on native USB.

find_port() prefers /dev/serial/by-id because ttyACM numbering shifts when other USB serial devices come and go. poll() never blocks. HUPCL is deliberately not set: with it the kernel drops DTR when the last fd closes, and the ESP32-S3 treats a DTR transition as a reboot request.

clock_sync.py — mapping board time onto Pi time

The board sends Time: <millis>; the Pi records arrival:

pi_recv_i = a * mcu_i + b + d_i          d_i >= 0

Because delay is non-negative, the true line is the lower envelope of the point cloud, not its least-squares center — fitting the center would bias every timestamp by the mean transport delay. refit() fits a by least squares over bucket minima, then sets b = min(pi_recv_i - a * mcu_i).

start_timer resets the firmware's startTime, so mcu_time_ms jumps backwards mid-session. That is a discontinuity, not drift: a backward jump beyond EPOCH_RESET_THRESHOLD_MS opens a new epoch, the model is refitted from scratch, and every row carries its epoch so a consumer can never mix parameters across a reset.

skew_implausible() flags a fit beyond CRYSTAL_PLAUSIBLE_SKEW_PPM (1000 ppm) — far outside crystal tolerance, so the board's milliseconds are not tracking real time.

stim_input.py — GPIO26 edge capture

Kernel edge events, not polling. The previous implementation called get_value() once per loop pass and only when a packet had just arrived, so a pulse that began and ended between two packets was invisible, and every recorded edge time was really "when we happened to look".

The kernel timestamps each transition against CLOCK_MONOTONIC — the same clock t_ms is defined on — at interrupt time. This is why the trigger is the most trustworthy time in the recording: no model sits between the event and its timestamp.

drain() pops (monotonic_ns, level) pairs; level is sampled alongside each scale reading to fill the gpio26 column.

bist.py — self tests, host side

parse_mcu_line(), is_bist_line(), sequence_of() parse the firmware's output. BistRegistry holds the latest result per test, tracks sequence continuity and runs the trigger-wire window. evaluate_pi_checks() recomputes the host-side checks on every status tick. summary() reduces the lot to one verdict.

Everything is stdlib-only so tests/test_display.py runs on the Pi itself.

recording.py — the on-disk format

SessionRecorder owns one session directory. sample(), event(), clock_fit(), raw(), close(). Rows are flushed periodically and events immediately — events are rare and losing one costs far more than losing a sample, and a crash mid-session must not cost the whole recording.

sanitize_component() reduces a subject name to [A-Za-z0-9_-] for the path. SessionExistsError is raised rather than overwriting; overwriting is possible but never accidental.

templates/index.html — the entire UI

CSS and JS in one file, ~3800 lines. No build step, no dependencies beyond Plotly and socket.io served locally.

Structural blocks, in source order: design tokens → desktop layout → the panel profile (@media (max-height: 820px), (max-width: 900px)) which carries the whole touchscreen design → dialogs and lamps → the portrait block at the end of the stylesheet → scripts.

The two media-query conditions matter. The panel profile is keyed on "short OR narrow", not "short": keyed on height alone it silently stopped applying the moment the panel was left in its native portrait orientation, and a 60 mm-wide touchscreen was rendered with desktop styles. The portrait block is last in the file because media queries add no specificity — placed earlier, the lamp and dialog rules that follow simply overrode it.

6. The recording format — schema v4

experiments/<subject_id>/<date>/<session>/
    session.json     manifest: metadata, clock model, provenance
    samples.csv      t_ms, pi_recv_ms, mcu_time_ms, mcu_read_ms, weight_g, gpio26, epoch
    events.csv       t_ms, pi_recv_ms, mcu_time_ms, event, value, detail, epoch
    clock_sync.csv   audit trail of the clock fit
    raw_udp.log      verbatim board traffic (name is historical; it is serial now)

<subject_id> is sanitized to [A-Za-z0-9_-]; <date> is YYYYMMDD. v2 used <date>/<subject>/<session>; v3 onward is subject-first so one subject's whole history is a single subtree.

v4 added one column, mcu_read_ms. Everything else is unchanged from v3, and the analysis package reads both (SUPPORTED_SCHEMAS = (3, 4)).

t_ms — the unified timebase

Milliseconds on the Pi session clock (CLOCK_MONOTONIC, zeroed at session start). Every row of samples.csv and events.csv carries it and it means the same thing in both.

sourcehow t_ms is derived
GPIO26 edgekernel edge timestamp minus t0. Exact.
weight samplemcu_read_ms mapped through the fitted clock model — an estimate of when the board finished taking the reading, not when its packet landed

That is the whole point: stimulation onset and the load trace can be compared without correcting for transport delay. Audit columns are kept alongside so nothing is lost — pi_recv_ms is raw arrival, mcu_time_ms and mcu_read_ms are the board's own stamps verbatim. If the model has not converged, t_ms falls back to pi_recv_ms and clock.sync.converged is false.

Which board stamp the fit uses matters. mcu_time_ms is taken at the top of the acquisition pass, ~93 ms before the reading it labels actually exists; fitting on it stamped every weight sample 93 ms early and made the recorded latency disagree with the board's own profiling by that amount. The fit uses mcu_read_ms where present and falls back to mcu_time_ms on v3 recordings, which carry the 93 ms bias — see §9 and docs/BACKLOG.md item 14.

events.csv

Same time columns, plus event (controlled vocabulary), value, detail.

weight_change is a delta in grams, not an absolute reading — it is deliberately never treated as a sample, or it would inject phantom 2.5 g readings into the trace.

session.json

Metadata, provenance, GPIO description, counts, and:

"schema_version": 4,
"clock": {
  "reference": "CLOCK_MONOTONIC",
  "unified_column": "t_ms",
  "t0_monotonic_ns": 0,
  "t0_unix_s": 0.0,
  "sync": { "method": "lower-envelope linear fit (min transport delay)",
            "converged": true, "epochs": 2, "offset_ms": 0.0, "skew_ppm": 0.0 }
}

Wall clock: unix = clock.t0_unix_s + t_ms / 1000.

task_duration_ms ≠ recording_duration_ms. They differ by 3× on a normal run (61 s of task inside a 209 s recording). Use the former for performance; reporting only the latter was actively misleading.

Readers must check schema_version. v3 and v4 are both loaded directly; v2 and legacy flat .txt sessions are read only through the analysis package's legacy importer, never silently reinterpreted.

Two totals, and they are not interchangeable. 229.0 ms is landing → stimulation, which is what the participant experiences and the number to quote. 211.1 ms is acquisition-pass-start → trigger, which is the board's own chain and the figure directly comparable to the 212.5 ms in the published paper. They differ by the 94 ms sampling lag, which the paper never counted. Quoting 211 as though it were the closed-loop latency understates it by 40 %.

The ~200 ms of averaging is not a defect — it is what months of testing across MS patients and healthy controls established as necessary for a stable reading. It is documented, not to be trimmed.

10. Decided, for the record

No self-termination. targetWeight stays above what 25 pegs weigh, so a run never ends by itself.

Task time is not recording time. session.json carries both.

A shutdown must never be queueable. Socket.IO buffers emits while disconnected and replays them on reconnect, so a shutdown pressed against a dead server fires whenever the server next starts — potentially unattended and mid-session. Both power actions refuse to send unless the socket is connected, and the dialog closes itself if the link drops.

Emoji icons, not SVG. Button icons are the emoji the operator already knows. SVG line icons remain as an automatic fallback if color emoji are unavailable, detected at load by a canvas probe.

Upright is the default orientation. It is what the panel does with no configuration at all, so the display comes up in an orientation the interface is designed for even if the rotation config is lost. The operator can switch with the Rotate the Screen desktop icon; the choice is remembered and re-applied by a labwc autostart entry.

Nothing is committed or pushed without being asked.

11. Working agreements

  • Never git add, commit, or push without being asked. Make changes, say what is ready, let the user decide. They push.
  • Verify, don't assert. If a number is synthetic, label it.
  • Operator-facing docs are for a clinical research associate — neuroscience or biology background, no engineering. But name the parts properly: the Raspberry Pi and GPIO26 are not to be hidden behind euphemism. Define, don't avoid.
  • The user is an electrical/computer engineer, so technical discussion with them can be direct.
