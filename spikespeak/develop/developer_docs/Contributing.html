Contributing#

How work is actually done in this repo. Short on purpose; the reasoning behind most of these lives in the page each one links to.

Branches and commits#

Work happens on a feature/<Thing> branch — feature/OneBoxSupport, feature/NIDAQSupport, feature/ProbeHeatmapAndDetachedViews, feature/AsapPerModule. One branch per subsystem or effort, not one per commit. main is GitHub's default branch and develop is the integration branch; nothing is pushed straight to either while a feature branch is live.

How merges have actually gone, as opposed to how you would guess. Read the merged PRs (gh pr list --state merged --json number,baseRefName,headRefName): #57, #58, #69 and #81 all targeted another feature branch — feature/OneBoxSupport (and feature/SpikeAudio) served as the long-lived integration line while OneBox work was open — and develop then took that line by fast-forward, not by PR. main has one commit on it, the initial one, and has never received a merge. So "PR into develop" is the shape to aim for, not a description of the log; if you are about to open a PR, ask the operator which base they want rather than inferring it.

As of 2026-09-03 no branch carries unmerged work. feature/OneBoxSupport was fast-forwarded into develop on 2026-09-01 (60889d7) and the ref has since been deleted: origin carries only develop and main, and gh pr list shows nothing open, so the next piece of work starts a new branch rather than joining one. That also unblocks the repo-wide reformat, which has been waiting on exactly this — see CodeStyle.md §3.

Closing out a feature branch#

Merging it and deleting the ref is not the end of it. The documentation site publishes one copy of the book per branch, and nothing takes a copy down when its branch goes away — the deploy action writes spikespeak/<branch>/ into the website repository, and the version list on that site's landing page is hand-written there, not generated here. Neither notices a merge. The full arrangement is in BuildingTheDocs.md, "The published site".

So when you close a branch out, in NeuralAscension/neuralascension.github.io (branch master):

  1. delete spikespeak/<branch>/ — about 40 MB per branch, served forever otherwise;
  2. delete that branch's link from spikespeak/index.html.

Both in one commit, and check the result against the origin rather than a browser reload: the page carries a ten-minute max-age, so your own tab will keep showing the old list well after the site is correct.

This is written down because it was missed. On 2026-09-03, two days after feature/OneBoxSupport was merged and deleted, https://neuralascension.com/spikespeak/ still offered it as "the active working branch", next to a build that predated the two-probe port fix, the config consolidation and the architecture overview — a visitor choosing the more active-sounding of the two links got the staler documentation. Cleaned up in 11d8f9e on the website repo. Four folders from branches closed before that one are still orphaned there: AsapPerModule, ProbeHeatmapAndDetachedViews, SpikeAudio, SpikeBandProcessor.

Commit messages are one imperative sentence saying what the commit makes true, not what files it touched. No trailing period. An optional lowercase area prefix (gui:, sim:, Intan:) when the subject would otherwise be ambiguous, and the issue number in parentheses when there is one:

Believe the device's clock, not the host's
Derive script paths from __file__, not the original machine's checkout
Fix .gitignore rules that silently matched nothing
sim: ripples reach the AP band, attenuated rather than eliminated
Put the Python suite in the gate, and test the sync pairing (#75 item 4)

Agents: do not git add, commit or push unless the operator asks. Leave the work in the tree and say what you changed. This is not a formality — the operator decides what lands, and an unrequested commit on a live feature branch is work they now have to undo.

Issues#

https://github.com/NeuralAscension/SpikesPeak/issues. Cite them by bare number in commits, docs and status entries — #49, #59, #65 — because that is how they are discussed on the rig, and the number is what makes a two-year-old paragraph findable.

Before you push#

Three suites: C++, Python, GUI. Testing.md is the only place the suite and case counts are maintained — quote the file, never the number. The counts have rotted in three separate documents at once, which is how two mandatory entry documents came to hand a newcomer two different answers on the same day.

python scripts/run_all_tests.py runs all three in order. A red suite that reaches the remote is a red suite for everyone who pulls, so run it before you push, not just before you hand back. If you added a test, prove it can fail — inject the regression, watch it go red, revert and rebuild (a stale bin/SpikesPeak.exe still carries the regression after the source is clean).

Run one gate at a time. Both runners take a shared lock (scripts/_gatelock.py), so a second one refuses rather than attaching to the first's backend — but the lock only covers the runners. Do not drive the backend by hand, edit webinterface/, or run build.bat while a gate is up: the frontend is served straight from the working tree and the exe is swapped underneath a live run. Exit code 0 from run_all_tests.py means nothing unless you passed --fatal.

House rules#

  • American English everywhere — color, behavior, analyze, optimize, artifact, gray — including code comments, docs and commit messages.
  • No scratch files in the repo. Logs, captures, screenshots and working files go to the session scratchpad. They were gitignored once, which meant git status looked clean while the repo root held 34 of them.
  • Never commit recording data. The referenced analysis figures stay; the .bins never do.
  • Absolute dates, never relative. "2026-08-20", not "last week" — every one of these pages outlives the session that wrote it.

Documentation conventions#

  • A page's row in README.md and its entry in scripts/build_docs.py GROUPS move in the same commit. They are the same list twice: the map a human reads and the map the book renders. The build prints a warning naming any page in neither, and such a page renders under "Unsorted", which is where docs go to be missed.
  • NextTask_*.md briefs are transient. Archive one to archive/ in the commit that finishes it, fold anything durable into the topic doc, and add a row to the archive table saying what superseded it. A finished brief left in "Plans and open briefs" reads as work waiting to be done — on this repo that can cost a session of rig time re-running a completed matrix.
  • ../SpikesPeak_Status.md is append-only. Add a dated section and an index row; never rewrite or reorder history.
  • A "current behavior" claim carries the date it was checked. Undated claims outlive the behavior they describe and there is then no way to tell which.
  • Reference source files as inline code spans — `src/core/Foo.cpp` — never as markdown links. The generated book contains only doc pages, so a link to ../src/… or ../scripts/… is a broken link in the book even though it resolves on GitHub.
  • Keep spaced separators out of headings (Scope: 2.0 only, not Scope — 2.0 only): GitHub and the book slugify them into different anchors, so the link works in exactly one of the two places the file is read.
  • One canonical home per topic. Put durable knowledge in the existing topic doc; new files are for genuinely new subsystems. Rebuild the book afterwards with python scripts/build_docs.py and read its last line — … N links, 0 broken, with no WARNING: above it.
