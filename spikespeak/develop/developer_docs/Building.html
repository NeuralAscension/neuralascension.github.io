Building and running SpikesPeak#

Everything here works from a plain terminal on Windows and Linux. Nothing needs Qt Creator, a "Developer Command Prompt", or any path edited into a script. macOS is not supported yet -- see the note under Prerequisites for exactly what is missing.

The short version#

Windows Linux
Build build.bat ./build.sh
Run run_spikespeak.bat ./run_spikespeak.sh
Run without opening a browser run_spikespeak.bat --no-browser ./run_spikespeak.sh --no-browser
C++ tests run automatically on every build run automatically on every build
Python tests python -m unittest discover python/tests python3 -m unittest discover python/tests
GUI tests python scripts/run_gui_tests.py python3 scripts/run_gui_tests.py
All three python scripts/run_all_tests.py python3 scripts/run_all_tests.py

build.bat and rebuild.bat hold the window open by default so a double-click does not close before you can read the result. Pass --no-pause (or set SP_NO_PAUSE=1) for scripts and CI:

build.bat --no-pause && run_spikespeak.bat --no-browser

That is a switch rather than auto-detection on purpose. The usual trick of looking for the script's own name in %cmdcmdline% cannot tell Explorer's cmd /c ""...build.bat" " apart from a scripted cmd /c build.bat, so it pauses inside automation and hangs it. A wrong pause costs a keypress; a wrong no-pause loses the output you opened the window to read.

Every one of them is a thin wrapper around scripts/spikespeak.py, which is the actual implementation and is identical on both platforms. If a wrapper ever misbehaves, call it directly:

python scripts/spikespeak.py build
python scripts/spikespeak.py run --no-browser

Where things end up#

bin/          the runnable app        <- build output, git-ignored, safe to delete
build/        object files, cache     <- git-ignored, safe to delete
dist/         cmake --install output  <- only if you ask for it

The app runs from bin/ and reads everything else straight out of the repo. It resolves config/, data/, webinterface/, imro_maps/ and CalibrationInfo/ as applicationDirPath()/../<name>, and from bin/ that is the repo root.

That has a consequence worth knowing, because it is the opposite of how this used to work:

Editing config/*.yaml or webinterface/*.js needs no build at all. Save the file, relaunch (or just reload the browser, for frontend files). There is exactly one copy of each of those directories, so there is nothing that can go stale behind you.

Until 2026-08-26 the build copied five directories next to the exe in the build tree, and the app read those. A frontend edit that was not followed by a build left the browser serving the previous version while the build reported success — which silently tested old code. That whole class of problem is gone with one copy of each directory.

First build, from a fresh clone#

build.bat --no-pause     # Windows  (drop --no-pause when you double-click it)
./build.sh               # Linux

That is the whole procedure. On first use it configures build/ (Ninja, Release, compile_commands.json on) and then builds. It finds the compiler, Qt and Ninja itself.

What it is finding for you, and why that matters on Windows:

  • The MSVC environment. A bare cmake --build in an ordinary terminal fails with Cannot open include file: 'type_traits' — the compiler runs but has no standard library on its include path, because vcvars64.bat has not run. spikespeak.py locates Visual Studio with vswhere and runs CMake inside that environment.
  • Ninja. Not on PATH on a normal Windows box. It arrives bundled with Qt Creator (C:\Qt\Tools\Ninja) or Visual Studio's CMake component, and the script checks both. If it finds neither it falls back to the default generator rather than failing.
  • Qt. Picked by matching ABI first, version second. With several Qt versions installed, the newest is often the wrong one: on this machine 6.10.0, 6.9.1, 6.9.0 and 6.8.3 are all present but only 6.7.3 ships an msvc2019_64 kit, so that is the one selected. A newer Qt with a MinGW-only kit would get part-way through find_package(Qt6) and fail on a component, which reads like a broken Qt install rather than the wrong one.

Set Qt6_DIR or CMAKE_PREFIX_PATH in your environment to override any of that.

Prerequisites#

Windows Linux
Compiler Visual Studio 2019+ (Desktop C++ workload) GCC 11+ — see the Clang note below
Qt 6.7, msvc2019_64 kit 6.7+, gcc_64. Components: Core Gui Widgets Network WebSockets WebChannel (+Test). WebEngine is not required
CMake ≥ 3.19 ≥ 3.19
HDF5 an SDK (headers + .lib) on CMAKE_PREFIX_PATH. The runtime is vendored in external/hdf5/extlibs/ (2.x) and copied to bin/ only when the build linked 2.x — a 1.x build uses the machine's own runtime, because the vendored DLLs would shadow it libhdf5-dev -- supplies both CXX and HL. Not optional: the synthetic-ripple play files are HDF5
Python 3.9+ (for the wrappers and the test runners) 3.9+
Ninja optional — bundled with Qt Creator or VS apt install ninja-build

Clang is untried, and macOS is not supported yet. The application target is already handled: the guard that puts -mavx2 -mfma on SPIKESPEAK_AVX2_SOURCES in the root CMakeLists.txt reads CMAKE_CXX_COMPILER_ID MATCHES "GNU" OR ... "Clang", and DisplayProcessor.cpp's vector body now carries __attribute__((target("avx2,fma"))) rather than bare intrinsics, so it needs no flag at all. (That attribute is not a Clang accommodation — it is why the scalar twin beside it stays baseline x86-64, which is the whole point of issue #34's runtime dispatch. See SimdDispatch.md.)

The residual exposure is the TEST targets, which is the opposite way round from how this note used to read. tests/CMakeLists.txt still applies the flags under a bare MATCHES "GNU" — in spikespeak_test() and again for bench_filter — and the tests keep the blanket flag deliberately (a test that fails to compile is louder than one that silently exercises half the dispatch). So under Clang the two targets that compile src/core/Avx2Filter.cpp directly, test_avx2filter and test_bandfilterprocessor, get no -mavx2 -mfma and the _mm256_fmadd_ps calls fail the same way they failed on GCC before 2026-08-25 — a hard compile error, so the C++ suite would not build at all.

Widening those two guards to "GNU|Clang" is the obvious fix and -mavx2 -mfma are valid Clang flags — but it has never been compiled, so it is a change to make on a Clang box rather than from here. Line numbers are omitted on purpose: this note carried two of them, both stale, and a stale line number reads as authority. Search for the compiler-ID guards.

macOS needs more than that anyway: the target is declared qt_add_executable(SpikesPeak WIN32 MACOSX_BUNDLE …), and inside a .app bundle applicationDirPath()/../<name> does not resolve to the repo root, which is the assumption the whole bin/ layout rests on.

Neuropixels and NI-DAQ hardware support is Windows only. Linux builds the same code with the vendor API stubbed out, so simulated sources, the full processing chain, the GUI and both test suites all work — which is what makes "run it in sim first" a real diagnostic rather than a gesture. See Testing.md §4.

If ./build.sh says Permission denied#

Shouldn't happen since 2026-08-26 -- build.sh, run_spikespeak.sh and _dobuild.sh are all mode 100755 in the index. On an older checkout, or for a script you add yourself, it takes both halves, because git update-index writes the index and leaves the file on disk exactly as unexecutable as it was:

chmod +x build.sh run_spikespeak.sh                      # makes them run NOW
git update-index --chmod=+x build.sh run_spikespeak.sh   # records the bit for everyone else

Or sidestep it entirely with python3 scripts/spikespeak.py build.

Running it#

run_spikespeak.bat                 # Windows  -- opens the GUI in a dedicated browser window
run_spikespeak.bat --no-browser    # backend only

With no flags it opens a chromeless app-window on its own profile (~/.spikespeak/browser-profile) via the first Chromium-family browser it finds -- Brave, Chrome or Edge -- so it is a separate session from your normal browsing, with no tab strip and remembered window geometry. If no Chromium is installed it falls back to a plain tab in your default browser. Closing that window drops the last WebSocket client, which shuts the backend down.

Always pass --no-browser for automated work, or you get a second GUI on top of whatever browser a test is already driving.

Do not run bin/SpikesPeak.exe directly. It exits immediately with 0xC0000135 (STATUS_DLL_NOT_FOUND): Qt's DLLs are not beside it and not on PATH. The launcher puts Qt, the Neuropixels API and HDF5 on PATH first — that is its whole job. The vendored Neuropixels and HDF5 DLLs are copied into bin/; Qt's are not, because they belong to your Qt installation.

The backend auto-quits about 2 s after the last WebSocket client disconnects, so closing the GUI tab shuts it down. Launched by double-click it keeps its console, and you can type connect, play, pause, disconnect, quit into it.

Hardware safety. Never force-kill the backend while a real probe or OneBox is connected — the FT601 USB handle is released only on a clean exit, and a kill costs a physical power-cycle. Shut down with quit, or the GUI's Disconnect. See README.md.

Testing#

The C++ suite runs automatically on every build and prints a per-suite pass/fail banner (~2 s). It does not fail the build by default, so a red suite is easy to walk past — configure with -DSPIKESPEAK_TESTS_FATAL=ON to make it fatal.

The Python suite covers the offline half — the SpikeGLX and Open Ephys converters, the loader's counts-to-microvolts scale, the config channel spec, the simulator's band-split model, and the sync pulse pairing every published closed-loop latency passes through. It is two seconds and needs no browser, no backend and no ports, but it is not part of the compile either:

python -m unittest discover python/tests

The GUI suite is not part of the build — it needs a browser and a running backend, so you have to run it yourself:

python scripts/run_gui_tests.py            # ~33 min, measured 2026-08-31
python scripts/run_all_tests.py            # C++, then Python, then GUI, behind a live progress page

Run the GUI suite whenever you touch webinterface/, the toolbar, the live view or the ripple dock, and before you push — a red suite that reaches the remote is red for everyone who pulls. Full detail in Testing.md, which is the only page that carries the suite counts.

Before you hand back#

  • [ ] build.bat --no-pause (or ./build.sh) → the C++ banner says ALL N SUITES PASSED, and the second line says the portable scalar pass did too
  • [ ] python -m unittest discover python/tests → OK
  • [ ] python scripts/run_gui_tests.py → ALL N GUI TESTS PASSED
  • [ ] Nothing left running: no SpikesPeak.exe, no stray browser, ports 1234/8234 free

python scripts/run_all_tests.py does the first three in one command. Check the N in each banner against Testing.md — the banners report how many suites ran, not how many exist, so a partial run is green.

VS Code#

.vscode/tasks.json and .vscode/settings.json are set up for this workflow:

  • Ctrl+Shift+B builds. Tasks also exist for Run (no browser), Test: C++ suite, Test: GUI suite and Test: everything.
  • The tasks go through scripts/spikespeak.py rather than the CMake Tools extension, because on Windows CMake Tools configures outside the MSVC environment and fails. This way one task file works on all three platforms.
  • IntelliSense reads build/compile_commands.json, generated on first configure. It appears after the first build; before that every Qt include shows red while the build itself is fine.

Recommended extensions: C/C++ (ms-vscode.cpptools) and Python. CMake Tools is optional and deliberately configured not to auto-configure on open.

Making a distributable copy#

cmake --install build --prefix /where/you/want/it

Defaults to dist/ if you omit --prefix. This is not how you run the repo — it stages a self-contained copy to take elsewhere, with its own config/, data/ and webinterface/. Keep it out of the way of bin/: a second, ageing copy of the app that someone can launch by accident is exactly the trap this layout removed.

Troubleshooting#

Symptom Cause Fix
Cannot open include file: 'type_traits' building outside the MSVC environment use build.bat, not a bare cmake --build
CMake was unable to find a build program corresponding to "Ninja" Ninja not on PATH and not found install it, or let the fallback generator run
Could not find a package configuration file provided by "Qt6" no Qt found, or none with a matching ABI install the msvc2019_64 kit, or set Qt6_DIR
Could NOT find HDF5 no HDF5 SDK. The DLLs vendored in external/hdf5/extlibs/ are the runtime only — no headers, no .lib — so a fresh clone runs without an HDF5 install but does not build without one install an HDF5 SDK (the vendored runtime is 2.x, so a 2.x SDK needs no re-vendoring) and put its prefix on CMAKE_PREFIX_PATH; on Linux apt install libhdf5-dev
