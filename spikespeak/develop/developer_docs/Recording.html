SpikesPeak — Recording#

How disk recording works, what a recording contains, how to verify one, and the known sharp edges.

Recording is a sink/processor — see [AddingASinkModule.md] for the sink lifecycle, and [SpikesPeak_Architecture_Review.md] for the data plane.

Reading order. §0 is how to record. §2 is what lands on disk and §2b is the sidecar that makes it readable — those two are current to 2026-08-29 and are what most readers want. §4 is the NP1.0 verification checklist, §6 the dated history of the original bring-up.

0. How to record (usage)#

  1. Pick a source & Play. Select a profile (e.g. NPX 1.0 with NI-DAQ) and press ▶ so data is streaming. Record is enabled only while playing (it records the live buffer).
  2. Press ● Record → set the location. The prompt asks for a recording name (animal/id) and an output directory on the SpikesPeak machine — use Browse… (a native folder dialog) or type a path. Confirming (Set Location) only arms the recorder — the Record button shows a muted-red ready ring; it does not start writing yet. (This two-step flow means picking a folder never starts a recording by surprise.)
  3. Press ● Record again to START. The button turns solid red and a flashing ● REC → name badge appears. Files are written live to a folder named after the recording — <directory>/<name>/<name>_<band>_<timestamp>.bin, e.g. mouse42/mouse42_ap_…bin, …_lfp_…bin, …_nidaq_…bin. One start records every configured stream (NPX AP + LFP + NI-DAQ) into that one folder.
  4. Which channels? Set by each recording's channels: in the YAML — read-out channel indices, which is what the recorder filters on and what the sidecar's columns.index_space: "readout_channel" declares. On NP1.0 at bank 0 these happen to equal electrode numbers; on NP2.0, and on any NP1.0 map that is not bank 0, they do not — the sidecar's columns.electrode array records which electrode each recorded column actually read. Only those are written; the sample configs record electrodes [1,2,3] (NPX) and NI-DAQ [0..7]. (Or pick them visually — the GUI record-channel picker has existed since 2026-07-06; §7.)
  5. Press ● Record again to stop. Files close; streaming keeps going — only Pause stops the stream. You can arm + start a new recording (fresh folder + timestamp) without pausing.

Headless / scripted: the same flow runs with no clicking via python/spikespeak_cli.py (select → waitready → probemap → play → record <dir> <name> → stop → pause → disconnect → quit), which drives the backend over the WebSocket; an open browser mirrors it live. See ControlCLI.md. To visualize a finished recording, python python/examples/plot_recording.py <dir> writes sync.png (NI-DAQ↔NPX timestamp sync) and channels.png (the recorded electrodes in µV) into the recording folder.

Verify a file with python verify_npx_recording.py <name>_ap_<ts>.bin --channels <N> --rate 30000 (--channels = the count in channels:; --rate 2500 for LFP). NI-DAQ files use a different layout ([double ts][double × N]), so the NPX verifier doesn't apply to them.

Metadata + postprocessing. Each .bin is written with a self-describing <file>.bin.json sidecar (band, record layout, sample rate, units, the electrode/channel list, and -- since metadata_version: 2 -- the counts-to-microvolts conversion, the applied IMRO and the probe identity; see §2b). The python/spikespeak_postprocess package reads those and returns a band for the electrode numbers you want, as NumPy or xarray:

from spikespeak_postprocess import Recording
rec = Recording(r"C:/Data/mouse42")
rec.bands()                                     # ['ap','lfp','nidaq']
sig = rec.load(channels=[1, 2], band="ap")      # electrodes 1 & 2 -> Signal (.data/.time/.fs)
uv  = sig.to_microvolts()
da  = rec.load(channels=2, band="lfp", output="xarray")
daq = rec.load(band="nidaq")                    # all NI-DAQ channels

# NI-DAQ ↔ NPX clock sync (shared TTL pulse on the NPX sync field + a NI-DAQ channel):
model = rec.synchronize(reference_band="ap", nidaq_sync_channel=0)   # drift_ppm / residual_ms
daq_synced = rec.load(band="nidaq", sync=True)  # timestamps on the Neuropixels clock

See python/README.md and python/examples/{plot_channel,synchronize_nidaq}.py.

Sync robustness (fixed 2026-07-17). synchronize() now defaults to match="auto". The NPX and NI-DAQ can capture a different number of sync pulses (one side stops a beat early); the old match="end" then paired the periodic 1 Hz train off by one and silently shifted the whole NI-DAQ→NPX map by a full sync period — invisible in the residual, because a shifted pairing fits a line just as well. "auto" estimates the true sub-period offset and nearest-edge-pairs, so a missing pulse at either end is safe. If you ever see ai4 events landing a whole sync-period off, check the pulse counts. Details: RippleClosedLoopAnalysis.md.

1. End-to-end path#

Recording now rides the per-module QWebChannel Q_INVOKABLE standard (Option A), the same way the IMRO panel talks to the NPX source — not the old 0x1001 binary command. Full pattern: ModuleCommunication.md.

[Record ▮] webinterface/main.js toggleRecord()
   └─ window.activeRecorders.forEach(r => r.setRecording(bool))   // QWebChannel RPC, no command id
        └─ QWebChannel → RecordProcessor::setRecording(bool)      src/modules/recording/RecordProcessor.cpp
             └─ QMetaObject::invokeMethod(this, …, QueuedConnection)   // marshal to the recorder's thread
                  └─ RecordProcessor::applyRecordingState(bool)   // opens/closes the output files

window.activeRecorders is bound on the deviceReady event after WebSocketServer::onSourceSelection registers every recorder to the QWebChannel. A profile can have more than one — e.g. config/NpxPxiNiDaq.yaml has proc.npx.recorder and proc.nidaq.recorder — and the single Record button fans out to all of them (per-recorder/per-channel config lives in each recorder's recordings: YAML; see §2–§3). A failed open is reported back via the recordingStatus event → toolbar (see §5).

Migrated 2026-06-25. Recording used to go over binary command id 0x1001 → CommandDispatcher → slHandleRecordingControlCommand. That path is gone; the Q_INVOKABLE is the single route, consistent with the NPX module.

UI gating: the Record button is enabled only while playing (main.js: recBtn.disabled = !isPlaying). So the workflow is Play first, then Record — the recorder reads the live buffer, so no data flows to disk unless streaming is active. The Record button turns solid red while recording; the Play button is a green ▶ when paused and a white ⏸ inside a green pulsing ring while streaming (see GuiTesting.md §6).

2. How many channels? All of them, on every profile an operator can pick#

Every hardware profile the source picker offers records all 384 probe channels. A recording block with no channels: key records the whole row — the serializers write sampleDimensions() values when the filter is empty — and none of the operator-facing hardware profiles has one.

The picker offers exactly two of these, since the 2026-08-26 source-selection refactor: the probe and the basestation are both read from the rig, so the only thing left to choose is whether to claim the NI-DAQ card.

profile (name:) in the dropdown? probe bands channels
Neuropixels yes — any basestation, any probe, all resolved by scan ap, lfp, raw all
PXIe with NI-DAQ yes, when a PXIe module is detected ap, lfp, raw all
OneBox gui_hidden — the explicit basestation override ap, lfp, raw all
PXIe gui_hidden — the explicit basestation override ap, lfp, raw all
PXIe + NI-DAQ gui_hidden — superseded by PXIe with NI-DAQ ap, lfp, raw all

PXIe + NI-DAQ (config/PxieNiDaq.yaml) is the older, told-what-to-open form of the profile directly below it in that table; PXIe with NI-DAQ (config/NeuropixelsNiDaq.yaml) is the replacement, and resolves the basestation from a scan instead. All three hidden profiles remain selectable by exact name from the control CLI — deliberately, because they are the explicit override when a OneBox and a PXIe module are attached at once (the scan refuses to guess between them) and because published measurements name them.

Confirmed on hardware, not only from the YAML: a PXIe + NP1.0 recording writes 774-byte frames, which is 6 + 2·384 — the header plus every channel.

The adc, nidaq and nidaq_di bands do carry explicit lists ([0..11], [0..7]), but those are complete — the OneBox ADC has twelve channels and the NI-DAQ eight, so listing them all is the same thing as recording everything.

The profiles that record three channels, and why they stay that way#

Several gui_hidden per-probe profiles record only [1, 2, 3] or [1, 192, 196]: NPX 1.0, NPX 1.0 (OneBox), NPX 2.0 Multishank, NPX 2.0 Multishank (OneBox), and the latency bench. This is deliberate and must not be "fixed". They exist for latency benches and as #63's ADC-throughput control, whose published 78.1 % / 99.99 % pair is only reproducible against the three-channel pair. Widening them would destroy that comparison.

They are hidden from the dropdown, but they remain selectable by exact name — which is how the OneBox latency matrix drove them. So a script that names one gets three channels, by design. If you are scripting a real session, name one of the five record-everything profiles in the table above — Neuropixels unless you have a reason not to.

Simulated and play-file profiles also record three channels, to keep the test suites fast.

This is enforced, not just documented. python/tests/test_config_channels.py fails if an operator-facing profile ever acquires a channels: list, and separately if a new profile records a subset without being declared an exemption. The failure this guards against is the worst kind: a narrowed recording looks completely normal afterwards — the sidecar honestly describes three columns and every converter honestly exports three — and the channels that were never written cannot be recovered.

2a. What gets written, and where#

The Record button prompts (2026-06-26). Clicking Record opens a GUI modal (AppController.showRecordDialog) for a recording name (animal/id) and an output directory on the SpikesPeak machine — pick it with the Browse… button (a native backend folder dialog; see below) or type/paste a path; both remembered in localStorage. On Start, every bound recorder gets that directory + name: setRecording(true, dir, name). Stop = setRecording(false, "", ""), no prompt.

Why a backend picker (not the browser's, like Save .imro)? Recording is written by the backend continuously at full rate, so it needs a real path on that machine — the browser's picker can't supply one. Save .imro is the opposite (a tiny text file the browser writes client-side). Full convention + the deferred-safe dialog details: SpikesPeak_Architecture_Review.md §7.5. The Browse… button sends a pickDirectory command → WebSocketServer opens QFileDialog::getExistingDirectory (deferred, DontUseNativeDialog) → returns the path via a directoryPicked event. The dialog opens on the SpikesPeak machine.

RecordProcessor::applyRecordingState(bool enable, QString outputDir, QString namePrefix) (runs on the recorder's own thread): - Start: the prompt outputDir overrides the YAML output_directory (created with one QDir().mkpath); if neither is set, the working directory is used. The dir is then nested into a per-session <namePrefix>/ subfolder (same mkpath) so a session's files group together. For each configured recording it opens QFile("<dir>/<namePrefix>/<namePrefix>_<output_filename>_<yyyyMMdd_hhmmss>.bin") in WriteOnly — e.g. mouse42_ap_20260626_143012.bin, …_lfp_…, …_nidaq_…. One timestamp is shared across the set so the AP + LFP + NI-DAQ files get the same suffix. Open failure ⇒ qWarning + a recordingStatus error event (§5) + skip that recording. - Stop: closes + frees every recording's file (guarded against a never-opened file).

Channel restriction. Each recording's channels: list (read-out indices) restricts what is written — only those channels are recorded (the interpreter filter). The NP1 configs split AP + LFP into separate files and give each its own channels:; the per-probe profiles ship a three-channel edit-me placeholder ([1, 2, 3] on NP1.0, [1, 192, 196] on NP2.0), and the NI-DAQ recorders ship [0..7], which is that card's whole set. Omit channels: to record all N — which is what every hardware profile the operator can pick does on its probe bands (§2; the simulated and play-file profiles the picker also offers keep their three-channel lists, to keep the suites fast).

File format — written by NpxDataInterpreter::serializeAvailableData (Npx.cpp), repeating per sample, native little-endian (x86; no byteswap):

┌─ per timebin ─────────────────────────────────────────────┐
│ uint32 timestamp │ uint16 sync │ int16 × N (channel data)  │
└───────────────────────────────────────────────────────────┘
   N = mRawData->sampleDimensions() = 384 for BOTH NP1 and NP2 (kMaxChannels).
   Record stride = 4 + 2 + 2·384 = 774 bytes. There is NO 385th sync channel.
   sync source: packetInfo->Status >> 6 for NP1 AND NP2 (AUX_IO<0:13>, matches OpenEphys).

CORRECTED 2026-06-25. An earlier revision of this doc claimed N = 385 with the sync in "channel index 384". That was wrong: the AP/LFP CircularBuffers are allocated kMaxChannels (384) wide, so there is no 385th channel — reading channelData[384] was an out-of-bounds read of garbage, and it was taken on every probe (sampleDimensions() is always 384, so the NP2 else branch was dead). Fixed in Npx.cpp: sync now comes from packetInfo->Status >> 6 for all probes, the value the demux actually stores. Use N = 384 in any reader.

  • With a YAML channels: [...] filter, only those channel indices are written (each int16), still preceded by timestamp + sync. With no filter, the whole N-wide block is written. (Superseded.) Each .bin DOES carry a self-describing <file>.bin.json sidecar -- band, record layout, sample rate, units and the electrode/channel list -- written by RecordProcessor.cpp. python/spikespeak_postprocess and every ripple_tools analyzer rely on it; a reader does NOT need to know N and the rate out-of-band.

2b. The sidecar: turning counts back into microvolts#

The requirement: every bit of the signal has to be reconstructible from the recorded data.

Until 2026-08-25 the sidecar failed that. It declared units: "adc_int16" and gave no way to convert. The per-channel amplifier gain that sets the microvolt scale is fixed by the applied IMRO and lives in the probe's amplifiers -- it is not recomputable from anything on disk. A session recorded with a non-default map therefore had a microvolt scale that could not be recovered from the files at all, and both consumers assumed the default anyway (DisplayProcessor.cpp's hardcoded 500/250, and python/spikespeak_postprocess/reader.py's _UV_PER_BIT). Nothing errors in that failure: the traces are real neural data, the file is the right length, and every microvolt figure is wrong by the gain ratio. Issues #28 / #40.

The sidecar is now metadata_version: 2. Every v1 key keeps its name and meaning -- this is purely additive, so ripple_tools/, python/spikespeak_postprocess and the offline exporters keep parsing these files unchanged. The new keys:

Key What it carries
scale The conversion, named. units, volts_per_count, microvolts_per_count, gain, uniform, the formula it was derived by, and its provenance. null with a scale_unavailable_reason if it could not be determined -- never a plausible default.
columns Parallel arrays in file column order: channel, electrode, shank, reference, gain, volts_per_count. index_space: "readout_channel" states what channels actually indexes.
acquisition Identity + configuration: probe (type, serial, part number), imro.text (the applied map verbatim), reference, basestation, calibration, adc, frame_timestamp_hz.
frame.timestamp_hz 100000 for NPX. The frame timestamp is a hardware TICK counter, not a sample index -- read as samples it is 3.33x wrong (AgentTraps.md, row 1).

Reading a channel in microvolts needs nothing but the sidecar:

import json, numpy as np
meta = json.load(open("m42_ap_20260825_140000.bin.json"))
n    = meta["frame"]["payload_channels"]
raw  = np.fromfile("m42_ap_20260825_140000.bin", dtype=np.int16)
raw  = raw.reshape(-1, n + 3)[:, 3:]              # drop [u32 ts][u16 sync]

uv = meta["scale"]["microvolts_per_count"]        # scalar when every column shares a gain...
if uv is None:                                    # ...else per column, and there is NO scalar to
    v  = np.array(meta["columns"]["volts_per_count"])   # pick up that would be wrong for some of them
    uv = v * 1e6
microvolts = raw * uv

Provenance matters and is written down. device-readback (the hardware said so this session), applied-map (from the IMRO pushed to the probe), compiled-constant (a datasheet figure for the part), simulated-constant (a simulator generated these samples -- no probe was involved), derived. A value read back from hardware and a value assumed are not the same evidence, and a future reader disputing a scale factor must be able to tell which one they are holding.

Per band, today:

Band Factor Provenance
data.npx.ap / .lfp (NP1.0) 1.2 V / 1024 / apGain (or lfGain), per channel applied-map
data.npx.raw (NP2.0) 1.0 V / gain / 2^adc_bits, resolved from the probe's own part number via Npx2Scale.hpp -- commercial parts (NP2003/4/13/14) are 12-bit gain-100 = 2.4414 uV/count, prototypes (NP2000/NP2010) are 14-bit gain-80 = 0.7629, a 3.2x spread. NP2 is fixed-gain: np_setGain is never called. An unrecognized part falls back to the commercial figure AND writes an unavailable_reason saying so. Corrected 2026-08-28: this block hardcoded gain 84 -- a value belonging to no variant -- so the sidecar was 1.190x high while the LIVE VIEW, which had used the part-resolved value since #65, was right. One recording, two scales device-readback (the part number comes from the probe)
data.npx.adc (OneBox) read back with np_ADC_getStreamConversionFactor at the current range device-readback (or derived if the call failed, and it says so)
data.nidaq.raw 1.0 -- DAQmx returns calibrated volts, so there is no gain in the path device-readback
data.nidaq.di line states, not a voltage; no microvolts_per_count is offered device-readback

Where the numbers come from. RecordProcessor holds no reference to any source and must not acquire one -- SourceRegistry::getSourceByName constructs a source that is absent (AgentTraps.md). So sources publish an immutable snapshot to RecordingMetadataService (src/core/RecordingMetadata.hpp), modeled on ChannelMapService, and the recorder reads it. Publishing happens inside publishChannelMap(), so the two snapshots can never describe different maps, and again on a OneBox ADC range change. It is built once per map change and read once per record press -- nothing per sample, nothing on the 30 kHz path, no new dependency, and no value the hardware was not already asked for at connect. A source withdraws on closeDataSource(), because a snapshot left standing after a disconnect would stamp the next recording with a probe that is gone -- which is worse than no metadata, since it looks like evidence.

Covered by tests/test_recordingmetadata.cpp, including the count -> microvolt round trip, the part-number-resolved NP2.0 scale, a mixed-gain map refusing to offer a scalar, the OneBox ADC getting no probe geometry, and the explicit-null-with-a-reason paths.

Still assumed elsewhere. src/modules/neuropixels/DisplayProcessor.cpp:248-257 still hardcodes 500/250 for the live NP1 microvolt scale, and python/spikespeak_postprocess/reader.py still carries _UV_PER_BIT. Neither affects what is written to disk any more, but both are wrong for a non-default map and should read the published gains / the sidecar instead.

3. Wiring (NP1.0)#

config/Npx1Pxi.yaml → proc.npx.recorder records two streams (AP + LFP), each restricted to a channels: list:

processors:
  - name: "proc.npx.recorder"
    recordings:
      - data_name: "data.npx.ap"
        data_interpreter_name: "interp.npx.ap"
        output_filename: "ap"
        channels: [1, 2, 3]       # ONLY these read-out channels; edit to your selection
        sample_rate_hz: 30000     # stamped into the .bin.json sidecar for postprocessing
      - data_name: "data.npx.lfp"
        data_interpreter_name: "interp.npx.lfp"
        output_filename: "lfp"
        channels: [1, 2, 3]
        sample_rate_hz: 2500

NPX 1.0 is gui_hidden and three-channel on purpose (§2) — it is a bench profile. A real session names Neuropixels, which omits channels: on every probe band and so records all 384. (Its adc block does carry a list, [0..11] — but that is the OneBox ADC's whole set, so it restricts nothing.)

So one Record toggle (after the name/dir prompt, name mouse42) creates mouse42_ap_<ts>.bin and mouse42_lfp_<ts>.bin in the chosen directory (+ mouse42_nidaq_<ts>.bin when the profile also has proc.nidaq.recorder). proc.npx.recorder and proc.nidaq.recorder both map to the same RecordProcessor class (registered in Utils.cpp); only the configured interpreters/streams differ.

4. Verification checklist (NP1.0)#

  1. Play → Record (enter a name + directory in the prompt) ~5 s → Stop. Confirm <name>_ap_<ts>.bin + <name>_lfp_<ts>.bin (+ <name>_nidaq_<ts>.bin if NI-DAQ) appear in the directory you chose.
  2. N = the number of channels in the recording's channels: list (NPX 1.0 records 3 → per-record stride = 4 + 2 + 2·N = 12 bytes for N=3; with no channels:, which is what every operator-facing hardware profile does, it's all 384 → 774 bytes). A whole file should be an exact multiple of that stride — or just read frame.bytes out of the sidecar, which states it.
  3. Read the first records in Python and verify monotonic timestamps and plausible int16 ranges, e.g.: python import numpy as np N = 3 # = len(channels) for this recording (3 in the bench configs; 384 if unrestricted) rec = np.dtype([('ts','<u4'),('sync','<u2'),('ch','<i2',N)]) d = np.fromfile('<name>_ap_<ts>.bin', dtype=rec) print(d['ts'][:5], d['ch'][:3]) # timestamps should step ~ uniformly; data ~ ADC counts Or just run the bundled verifier: python verify_npx_recording.py <name>_ap_<ts>.bin --channels 3 --rate 30000 (and --rate 2500 for the LFP file). Pass --channels matching the channels: count. It checks the stride, monotonic timestamps, sample-rate plausibility, and int16 ranges. (NI-DAQ files use a different [double ts][double × N] layout — the NPX verifier doesn't apply.)
  4. Confirm the recorded channel order matches the applied IMRO (recording is channel-ordered, like the stream — apply a known map and check a distinctive channel).
  5. Toggle Record on/off several times → each cycle should produce a fresh timestamped pair.

5. Known sharp edges#

Severity Where Issue Status
HIGH (crash) RecordProcessor.cpp (stop loop) Stop called outputFile->close() with no null check. If a start open failed (read-only dir / disk full → continue), or stop arrived without a successful start, outputFile was nullptr ⇒ crash. FIXED — stop loop now continues when outputFile == nullptr.
HIGH (data) Npx.cpp (sync read) sync read channelData[384] from a 384-wide row — an out-of-bounds read of garbage, always taken (sampleDimensions() is always 384, so the NP2 branch was dead). Corrupted the sync field and seeded the bogus "N=385" format. FIXED — sync now packetInfo->Status >> 6 for all probes (matches OpenEphys). Record is [ts][sync][int16×384] = 774 B.
HIGH (analysis) recording sidecar (all bands) The sidecar's num_channels describes the payload, not the frame. An NPX frame is [uint32 ts][uint16 sync][int16 x N] = N + 3 int16; NI-DAQ is [float64 ts][float64 x N]. A reader that took num_channels as the stride mis-de-interleaved the whole file, and because gcd of the wrong and right strides is rarely 1 the columns came out sample-wise distinct but statistically identical — which is what made the OneBox ADC look like failing hardware in #53. The layout was documented in a comment above writeMetadataSidecar() and nowhere a reader could see it. FIXED — the sidecar now carries a frame block (bytes, header_bytes, header[], payload_dtype, payload_channels, layout). Verified: a 15 s NP2.0 recording reports frame.bytes: 12, and filesize / 12 / 30000 = 15.00 s exactly. Recordings made before this still need the stride computed by hand as num_channels + 3 int16 (NPX).
HIGH (analysis) python/spikespeak_io.py (the single reader) An all-channel recording would not open. channels: [] with num_channels: 0 is the writer's documented sentinel for "the whole block was written; infer N from the frame" (src/core/RecordingMetadata.cpp), and it is the COMMON case — omitting channels: means record-everything, which every operator-facing profile does. The reader read it as zero channels and refused with "frame is 774 B but 6 + 20 = 6 B"*, while both converters read the same file happily. Two readers in one repo disagreeing about a documented sentinel is exactly what that module was created to prevent. Found on the rig during #52's configuration 4, 2026-09-01. FIXED — the sentinel is honored (frame.bytes gives N directly); the hard refusal is kept for a NON-empty channel list that contradicts the frame. python/tests/test_reader_all_channels.py pins both directions.
MEDIUM RecordProcessor.cpp (start loop) Output dir was the CWD only — not configurable, and a missing subdir failed silently. FIXED — optional output_directory: YAML key on the recorder processor; created on start via QDir().mkpath. Absent ⇒ CWD (legacy).
MEDIUM RecordProcessor.cpp (start loop) File-open failure was silent to the user (only qWarning). FIXED — emits sigIpErrorOccurred; WebSocketServer relays it as a recordingStatus event → toolbar status (window.guiStatus, red).
LOW Npx.cpp Endianness is native (fine on x86, undocumented). No metadata header — consider a sidecar .meta (rate, N, probe, IMRO). Open (low priority).

7. GUI record-channel selection (BUILT 2026-07-06)#

Pick recording channels visually instead of editing YAML. The probe viewer has a mode radio — Edit Map (the IMRO editor) vs Select Recording Channels — so you can set record channels at any time, including before you Play (it doesn't touch hardware). The full IMRO editor returns when you switch the radio back. (This decoupled radio approach was chosen over auto-flipping on Record, so it works independent of streaming state.)

Probe recording-selection mode (reuses the ImroManager probe map + its click / drag-box selection; webinterface/ImroManager.js renderRecordSelection + the probeMode === 'record' branch): - Shows only the electrodes in the applied probe map (appliedImroData) — the channels actually streaming; non-applied electrodes are not drawn. A note in the panel states this. - Color legend (dark-mode, colorblind-safe by luminance): green = will record, blue = applied, not recording, amber = reference (ch 191, excluded). - Default = record all: on entering the mode every applied, non-reference channel is selected. - Custom select: click an electrode toggles it; click-drag a vertical box adds the applied electrodes in that row band (the reserved reference ch 191 is always skipped). - Unselect all clears; Record all re-selects every applied channel; Set recording channels commits the current selection. - On commit the browser stores the read-out channel list in window.recordChannels, taken from the applied map. main.js toggleRecord passes it to every recorder as the 4th arg of setRecording(true, dir, name, channels). Empty/none ⇒ the YAML default (headless/CLI parity).

⚠️ The electrode → channel rule above is NP1.0 ONLY, and the page did not used to say so.

probe electrode → read-out channel reserved channel
NP1.0 electrode % 384 191 — its sites (191, 575, 959) are internal reference, drawn amber, never selectable
NP2.0 a per-shank block permutation, keyed "<shank>_<electrodeId>" — Np2::electrodeToChannel(shank, electrode) in Npx.hpp, mirrored in JS as NP2_electrodeToChannel. The bank is electrode_local / 384; the channel is a table lookup, deliberately scrambled by the probe. none

Applying the NP1 rule to a 2.0 probe gives you the wrong channel for every electrode and a phantom exclusion at 191 that the hardware does not have. The permutation was verified against all 5,120 rows of imec's official Electrode-Channel spreadsheet (2026-07-07; see Neuropixels2.0.md §7). The record-selection UI branches correctly — the prose is what was NP1-shaped.

Backend (RecordProcessor, §Part 3 rules): setRecording gained a channels (QVariantList) arg. When non-empty on start it's validated (0..kMaxChannels, unique) and becomes the session's activeRecordIndices, overriding the YAML channels: for that session only (the configured default is untouched and restores next session). It drives both serializeAvailableData and the .bin.json sidecar, so a GUI selection is recorded and self-described faithfully. No on-disk format change.

Verified (Linux/sim, in-browser via CDP): drag-selected 27 channels [176..190,192..203] (191 correctly excluded) → Set → Record → both ap and lfp .bin contained exactly those 27 channels (sidecar + spikespeak_postprocess confirm); Record-all → 383; toggle back to Edit Map restores the editor.

Did the recording get everything? Two answers, and which to believe#

Dropped samples are one of the two numbers this system is judged on, and until 2026-08-25 a shortfall was completely invisible: the counters advanced, the traces drew, the stall watchdog stayed quiet (it fires on total silence, not on a partial deficit), and the file was simply smaller than it should be. On the second machine a band recorded at 66 % of nominal across every run and logged zero WARN and zero CRITICAL.

Every record stop now reports two independent verdicts per band.

1. The wall-clock ratio — "how many"#

File size ÷ frame size, against the host's own start/stop clock and the profile's nominal rate:

[RecordProcessor] interp.npx.ap throughput 100.0% of nominal (300000 records in 10.0 s).
[RecordProcessor] interp.npx.ap recorded SHORT: 66.0% of nominal (198000 records in 10.0 s at
                  30000 Hz, expected ~300000). Samples were dropped between the source and the disk.

Below 95 % it is a warning and it reaches the operator's toolbar, not just output.log. It is deliberately loose: the window includes the start and stop edges and the rate is nominal, so a few percent is measurement rather than loss. Recordings shorter than 2 s are skipped entirely, because at that length the edges dominate and everything looks short — and a warning that cries wolf is one nobody reads twice.

An empty channels: list means the WHOLE ROW, not zero columns. This check divides the file size by the frame size, and a profile that records everything (Pxie.yaml, OneBox.yaml) has an empty filter. Passing that filter's length straight through computed a 6-byte header-only frame and inflated the count by the row width — 129× on a 384-channel probe, reported as 12904.60% of nominal. Being far above the threshold it always took the reassuring branch, so the check could not fire at all on exactly the profiles that record everything. Fixed 2026-08-29; resolvePayloadChannels() is now the one place that rule lives, shared with the sidecar, and it is unit-tested.

2. The device-clock span — "where"#

The probe's own 100 kHz tick counter, comparing the frames actually written against the number the span they cover implies:

[RecordProcessor] interp.npx.ap continuous: 300000 frames match the probe clock over ticks
                  8989550-9989548.
[RecordProcessor] interp.npx.ap is NOT CONTINUOUS: 299000 frames written where the probe clock
                  implies 300000 over the same span -- 1000 missing (0.33%), between ticks
                  8989550 and 9989548.

This is the better witness. It needs no host clock, it is exact rather than nominal, and a shortfall comes with a position — which is what tells you whether a loss coincided with a stimulus, a disk flush, or nothing at all.

Why a span and not a per-frame step test. Measured on real hardware (PXIe + NP1.0, 2026-08-29, 10 s), the AP band's per-frame tick delta is negative 8.3 % of the time:

band tick deltas observed negatives ticks/frame
ap −8, −7, +4, +5 25 003 of 300 048 3.3333 (= 100 kHz / 30 kHz)
lfp 39, 40, 41 0 39.9996 (= 100 kHz / 2.5 kHz)

The AP stamps advance within each 12-sample IMEC packet and then step back, netting exactly 40 ticks per packet. A per-frame "did the clock advance" test would therefore fire twenty-five thousand times on a perfectly healthy ten-second recording. The span is exact on both bands, so span-versus-count is the comparison that holds — and it costs two timestamp reads per batch, nothing per sample.

Cost. Two loads and two stores per batch in serializeAvailableData, and one division at stop. Nothing was added to the 30 kHz loop.

When they disagree, believe the device clock. It is measuring the data; the wall clock is measuring the host.

Both checks run on every stop, including a stop caused by Disconnect or quit — which used to skip the entire stop path, so the one session you most want them for was the one that never reported.

A recording also carries its own log#

Alongside the .bin files and their .json sidecars, a recording directory now contains <name>_<timestamp>.log -- a copy of the backend log for exactly the span of the recording, sharing the timestamp of the data files:

RecordingTests/logdemo/
    logdemo_20260819_231117.log
    logdemo_raw_20260819_231117.bin        + .bin.json
    logdemo_adc_20260819_231117.bin        + .bin.json
    logdemo_ripple.json                    (if the detector had channels at record start)
    logdemo_events.jsonl                   (if the detector ran during the recording)
File Written by What it is
<name>_<band>_<ts>.bin RecordProcessor one band's samples
<name>_<band>_<ts>.bin.json RecordProcessor that band's sidecar — §2b
<name>_<ts>.log RecordProcessor the backend log for the life of this recording
<name>_ripple.json RippleDetector::slWriteRippleSidecar the online thresholds and the resolved detection channels, at record start
<name>_events.jsonl RippleDetector, appended live one JSON object per line for every detection, latency measurement and confirmed stimulus, for the span of the recording. Open only while recording. Before 2026-08-28 these existed only as live WebSocket messages — if the stream was not captured at the time, they are gone.

Where the sidecars live, and the one date that changes it. Since 2026-08-28 everything above lands inside <dir>/<name>/. In recordings made before that, the bands were already in <dir>/<name>/ but <name>_ripple.json was written one level up, in <dir>/ — so copying "the recording folder" silently left the detection channels and trained thresholds behind. The analysis tools read both layouts and report which one they found; for an older recording, take the parent directory.

It exists because output.log is truncated on every start and so cannot answer "what was this rig doing when this file was written?" for data analyzed later. It covers the recording, not the session -- only the source connected while recording, nothing before Record was pressed or after it stopped. That scope is deliberate: everything in the file pertains to the data beside it. Full rationale and the format of a line: Logging.md.
