Benchmarks#

Two independent benchmarks live here:

  1. Rendering channel-density — how render cost scales with the number of live traces. Files: cdp_bench.py, plot_density.py, bench_channel_density*.csv, bench_channel_density.png, CHANNEL_DENSITY_REPORT.md.
  2. Ripple-filter threading (separate) — bench_ripple_filter.cpp + plot_bench.py, documented in developer_docs/RippleDetectorThreading.md.

This README covers #1.

There is one renderer now, so this is a single-arm sweep#

This benchmark used to be the measurement that would decide whether to replace SciChart. That decision has been made, measured on real hardware, and executed: SciChart.js v5.2.35 was removed from the tree on 2026-08-27, and webinterface/GlRenderer.js (GlColumnRenderer, WebGL2) is the only thing that draws traces. There is no second arm to switch to, and nothing selects a renderer any more — window.__setGl, window.__useGl and the SPIKESPEAK_GUI_RENDERER environment variable are all gone.

The comparison itself — design, data, mechanism and limits — is developer_docs/RendererExperiment.md, and its primary evidence lives in this directory as renderer_experiment.py, renderer_analysis.py, experiment_raw.csv and experiment_summary.csv. Do not rerun or rewrite those. They are a repeated-measures A/B against a renderer that is no longer in the tree, which makes them a record rather than a tool: the run cannot be repeated, and editing it would destroy the evidence the change rests on.

What remains useful is the sweep itself. It answers "how many traces will this build hold at 60 fps on this machine", and that question has to be re-asked after any renderer change, on any new rig, and for any probe/band combination that puts more work on the main thread.

What it measures#

cdp_bench.py drives the running GUI over CDP and sweeps columns × traces-per-strip (COLS=[1,2,4] × TRACES=[20,40,60,80] → 20…320 on-screen series) while traces are actually drawing. Per config it records: fps, frame time mean/p95/max ms, JS heap MB, main-thread busy fraction (Chrome TaskDuration delta ÷ wall-time — a single-core fraction, not a share of all cores, and the true ceiling), and a bound point-count sanity (>0 = traces really rendering, which guards the blank-surface trap). Output: bench_channel_density_<label>.csv plus one screenshot per config under shots/. plot_density.py renders the 4-panel figure.

Reproduce#

Prereqs — one backend and exactly one isolated Chrome on CDP:9222 (see developer_docs/GuiTesting.md). Exactly one: the server broadcasts the same stream to every WebSocket client and has no backpressure, so a second tab or a forgotten harness socket is load the browser under measurement did not have.

python run_spikespeak.py --no-browser          # Windows (or the Linux offscreen build)
chrome --remote-debugging-port=9222 "--remote-allow-origins=*" \
  --user-data-dir=<tmp>/sp_bench_profile --app=http://localhost:8234 --window-size=1920,1080

Then:

python benchmarks/cdp_bench.py <label>                                       # -> bench_channel_density_<label>.csv
python benchmarks/plot_density.py benchmarks/bench_channel_density_<label>.csv

The label is a required positional argument, and it now names the build or the rig, not a renderer arm — np2-onebox, gl-laptop, and so on. It is required because a hard-coded output path once let a second run silently overwrite the first one's numbers.

Both scripts are repo-relative (no hard-coded machine path) and the measurement is renderer-independent.

Historical reference — the SciChart baseline#

Kept because it is what the replacement was measured against. The table below records what the live view did in July 2026; it is not a target and cannot be reproduced, because the renderer it measures is no longer in the tree.

Measured Renderer Conditions Result Frozen data
2026-07-12 SciChart.js v5.2.35 (removed 2026-08-27) sim NP2 Multishank, 384-ch RAW @ 30 kHz, 1920×1080 on the primary monitor solid 60 fps to ~160 on-screen series; 4 × 60 = 86 % main-thread; 4 × 80 = 100 % saturated → ~45 fps bench_channel_density.csv + bench_channel_density.png; write-up in CHANNEL_DENSITY_REPORT.md

Trap — there are two SciChart-era density CSVs and they are not the same run. An earlier version of this README claimed bench_channel_density_scichart.csv was a copy of bench_channel_density.csv, and that claim has been repeated elsewhere in this directory. It is wrong: the files differ row for row. bench_channel_density.csv is the July sweep that CHANNEL_DENSITY_REPORT.md documents; bench_channel_density_scichart.csv is a later SciChart run, swept on 2026-08-27 during the replacement work, and bench_channel_density_webgl.csv is its WebGL2 counterpart from the same day. That last pair is the density-sweep companion to the repeated-measures experiment written up in developer_docs/RendererExperiment.md. Compare the pair against each other; do not compare either of them against the July file, because the conditions were not the same run.

On real hardware — OneBox + Neuropixels 2.0, four columns of 120 = 480 on-screen traces — the replacement used 4.28× less renderer main-thread CPU and 2.45× less CPU across all browser processes, and held a solid 60 fps where SciChart ran at 42 ± 5. GPU utilization (38.0 % → 35.9 %) and board power (19.8 W → 19.6 W) were at parity: the win is CPU, not GPU. Full account in developer_docs/RendererExperiment.md §3a.

Notes and traps#

  • The blank-surface guard is window.__benchPointCount(colIndex), answered by the column's GL renderer out of its own vertex buffer. It has no fallback, deliberately: if the global is missing the eval throws and the sweep dies loudly, where the old SciChart fallback (onScreenSeries[0].dataSeries) would have quietly gone on returning a number from nowhere after the renderer changed. It returns -1 for no such column or a column whose GL context was lost — such a cell measured nothing and its row is void — and it saturates at the window capacity (2400 at a 1 s window), so it proves "streaming and bound" and nothing finer.
  • cdp_bench.py's SETUP block assumes current DOM ids and globals: tab-btn-map, btn-apply-imro, playPauseBtn, tab-btn-data, channelsPerStrip, ripple-dock/ripple-dock-close, window.app.ui.colsSel, window.__tracesOverride, and window.__perfStats/window.__perfReset. The source is chosen over the WebSocket rather than through the picker, on purpose — the picker has been a <select>, a modal and an anchored menu, and each rename broke the sweep silently. If an id does move, update the setup block only; the metrics loop is renderer-independent.
  • The renderer swap renamed the plot DOM (scichart-container-N → chart-container-N, .scichart-container-wrapper → .chart-container-wrapper). The sweep does not touch either name, but anything you add here should use the new ones.
  • The fixed conditions in developer_docs/RendererContract.md §4.4 still apply. They existed to make two renderers comparable, and they are just as load-bearing when comparing this build against itself on another machine or another day.
  • shots/ holds per-config screenshots (throwaway evidence).
