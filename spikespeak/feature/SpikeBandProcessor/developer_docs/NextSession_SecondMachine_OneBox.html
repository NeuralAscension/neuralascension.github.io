Next session — stand SpikesPeak up on a second Windows machine (OneBox only)#

You are on a different machine from the one this code was developed on. Everything here has been built, run and tested on exactly one Windows box. Your job is to find out what of that survives the move, fix what does not, and report honestly on the rest.

Tracking issue: #52. You are configuration 5 of the five listed there: Windows + OneBox, no PXIe.

Read README.md (the doc map) and the repo-root CLAUDE.md before you start. This file is the brief; those two are the standing rules.

0. The one rule that costs hardware#

Never force-kill the backend while the OneBox is connected. The FT601 USB handle is released only on a clean exit; a kill costs a physical power-cycle of the box. Shut down with the WebSocket quit command or the GUI's Disconnect.

Since 2026-08-21 every teardown vendor call is bounded, so a wedged basestation no longer hangs shutdown — the app exits cleanly in ~9 s and tells you to power-cycle. That makes the rule cheaper to follow, not optional.

Two more, from painful experience:

  • Always launch with --no-browser for automated work: run_spikespeak.bat --no-browser. Without it main.cpp calls QDesktopServices::openUrl and opens a window in your default browser, on top of whatever browser you drove yourself. That is how a test run ends up with two GUIs on screen.
  • Never blanket-kill Chrome. Kill only the isolated debug-port profile you launched. A Get-Process chrome | Stop-Process closes the operator's real windows.

1. What you are trying to achieve#

In priority order:

  1. Build from a clean clone with no path edits, or document exactly which edits were needed.
  2. Both suites green — see §2. This is the definition of done for a build; a compile that produced a binary is not a green build.
  3. Validate the OneBox path on THIS rig — connect, stream, record, reconnect, clean teardown. That has only ever been proven on one box and one probe; a second independent rig is real evidence, not a formality.
  4. Fix or file every machine-specific assumption you hit, against #52.

You are not expected to fix #51 — see §5.

2. THE DEFINITION OF GREEN#

Both suites. Every time.

cmake --build build-Desktop_Qt_6_7_3_MSVC2019_64bit-Release

Runs the C++ suite automatically and prints a per-suite ✅/❌ banner. 15 suites, 316 cases, ~1.6 s. A failing suite does not stop the build (you usually still want the binary to debug with), which makes red easy to walk past. Do not.

python scripts/run_gui_tests.py

Runs the GUI suite — 6 tests driving a real Chrome over CDP against a real backend on a simulated source. ~10 min. It is not part of the compile, so you have to run it yourself, and you must run it whenever you touch webinterface/.

-DSPIKESPEAK_TESTS_FATAL=ON makes C++ red fatal; --fatal does the same for the GUI runner.

Full detail, and how to add a test: Testing.md. What the GUI tests cover and what they deliberately do not: GuiTestCoverage.md.

Run it from a shell that has already sourced vcvars64.bat, or the compiler is not found.

4. Order of work#

Do the no-hardware half first. It needs nothing plugged in and will surface most of the hardcoded-path problems, and you do not want to be debugging a build while a probe is connected.

  1. Clean clone → configure → build. Record every deviation.
  2. C++ suite green. It is Qt Test with no platform-specific code, so it is the most likely to pass unchanged. If it does not, that is a genuinely interesting finding.
  3. GUI suite green on the simulated source. Expect the Chrome path to bite first. Start the backend yourself once (run_spikespeak.bat --no-browser) and confirm the GUI loads at http://localhost:8234 before blaming the harness.
  4. Then the OneBox. §6.

5. Two tests you must NOT "fix"#

tests/gui/stream_options.py is expected to be RED. It catches #51 — switching source after acquisition has run fails while stateSource reports success. That is a real, pre-existing backend defect and the test is doing its job.

It passes when run standalone (python tests/gui/stream_options.py), because each source gets its own Gui, and a Gui that started its own backend also quits it — so the second source lands on a fresh backend. Under the runner the backend is shared and has already streamed, which is the operator's real situation. Do not make the test restart the backend between sources; that hides the bug rather than fixing it.

So on this machine, a "green" GUI run means 5 of 6, with stream_options red for that reason. If it is red for any other reason, that is a new finding — report it.

Prove any test you add can fail. Inject a regression, watch it go red, revert. An always-green test is worse than none, because it buys false confidence. toolbar_layout was validated this way: hiding #tb-peek-source while folded made it report UNREACHABLE at all seven folded widths.

6. The OneBox, on your rig#

Configs are selected by their internal name: field, not the filename. The relevant ones:

source name what it is
Simulated NPX 1.0 (OneBox) sim; needs no hardware
NPX 1.0 (OneBox) real NP1.0 on the OneBox
NPX 2.0 Multishank (OneBox) real NP2.0 on the OneBox
NPX 1.0 (OneBox, ASAP) as above with low_latency delivery

You have no PXIe. Any profile naming PXIe will not connect here, and that is expected — not a bug to chase. If it connects anyway, that IS a bug and is worth a report.

What to verify, in order:

  1. Connect → expect Found Neuropixels 1.0 Probe (or 2.0).
  2. Stream → count binary frames at the WebSocket, not pixels on screen. A healthy sim or real source delivers ~1650 frames / ~67 MB in 12 s. Zero frames with the GUI showing "Waiting for data…" is the 2026-08-20 failure mode; see Testing.md §4.
  3. Record, then confirm the .bin + .bin.json sidecars appear and the sidecar's band, rate and channel list are sane.
  4. Reconnect — disconnect and connect again in the same session.
  5. Clean teardown — quit over the WebSocket. Expect Released virtual slot 16 and connection closed (setSyncAsInput + closeProbe + closeBS + unmapBS) with no did not return within 3000 ms warnings. Those warnings mean the box stopped responding and needs a power-cycle; they are the guard working, not a code failure.

A useful sanity script for steps 1–2 lives in Testing.md §4; ripple_tools/rig.py gives you select / play / pause / quit from Python.

Sim first, always#

If something looks broken, run the simulated source first. Every sim source drives the same display processor, the same ring buffers, the same WebSocket and the same GUI as real hardware.

  • Sim streams, hardware does not → it is the rig, not the code. You have just saved yourself hours.
  • Neither streams → it is the code, and you have a reproducer that needs no hardware.

7. What is genuinely new since the last machine saw this code#

Commit d9620fd, on feature/OneBoxSupport. Worth understanding before you debug anything, because it changes what the counters mean:

  • Source liveness now counts committed samples, not timer ticks. SourceManager's stall watchdog fires within 3 s when a source stops delivering. Previously it could never fire, and a completely dead probe reported a healthy rig for three and a half minutes.
  • Every teardown vendor call is bounded (src/core/BoundedCall.hpp, src/modules/neuropixels/NpBounded.hpp). On timeout the call is abandoned, the rest of the sequence is skipped, and shutdown completes. Read BoundedCall.hpp — it deliberately leaks a blocked thread rather than let a driver wedge the app, and the reasoning is written there.
  • output.log rotates (output.1.log … output.5.log). Copy it before restarting anyway.
  • A test suite exists at all, for the first time.

8. Reporting back#

Put findings on #52, not in a new document. For each item: what you expected, what happened, and the smallest command that reproduces it.

SpikesPeak_Status.md is the canonical dated log — add a section there for the session, not a new *_Status.md file. Do not commit anything under RecordingTests/; referenced analysis figures stay, recording data never does. Keep scratch files out of the repo entirely.

Do not git add, commit or push unless the operator asks.
