Raspberry Pi 3B+ — AM Systems 2300 pulse generator (real-time)#

A real-time C program that turns a Raspberry Pi (3 / 4 / 5) into a closed-loop stimulation server: it listens for UDP connect / fire / quit from SpikesPeak (port 8888) and drives the AM Systems 2300 Digital Stimulus Isolator via its 3-line DB-9 control interface to emit biphasic pulse trains.

Audience: someone who has never used a Raspberry Pi, SSH, or Linux. Follow this top to bottom and you will turn a bare Raspberry Pi + a microSD card into the SpikesPeak "Stimulation Server": a small appliance that listens for fire messages from SpikesPeak and pulses the AM Systems 2300 stimulator. Every command is copy‑paste, and every command has a one‑line explanation. There is a Glossary at the bottom — if a word looks unfamiliar (SSH, GPIO, DHCP…), jump there first.

This guide assumes nothing is set up yet. If your Pi is already flashed and running, skip to §8 Verify it is running. For the terse operator checklist (not from scratch) see ../developer_docs/Pi3_Monday_Runbook.md; for the code/protocol reference see README.md (this file).

0. What you are building#

 SpikesPeak PC  ──Ethernet, UDP :8888──►  Raspberry Pi  ──3 wires (DB‑9)──►  AM Systems 2300  ──►  biphasic
 (ripple detect                          (this appliance)   On/Off, Sign,      (stimulus isolator)   current
  or Test Fire)                                             Pulse/Baseline)                          pulse

The Pi runs one tiny real‑time C program (pulse_generator) that: 1. listens on UDP port 8888 for the text messages connect (arm), fire (pulse), quit (disarm), and 2. drives three GPIO pins that go to the AM 2300's DB‑9 control port to make a biphasic pulse train.

It is turnkey: once set up, every time the Pi powers on the program auto‑starts — nothing to log into.

⚠️ SAFETY — read before wiring or firing#

  • Wire only with everything powered OFF (Pi unplugged, 2300 off). Double‑check every wire against the table in §6 before applying power.
  • The stimulator must be ARMED (SpikesPeak/you send connect) before fire does anything.
  • Never fire into tissue during setup. Bench‑test into a dummy load / the NI‑DAQ first.
  • On a real experiment with a Neuropixels probe / NI‑DAQ attached, shut SpikesPeak down gracefully (WebSocket Disconnect / quit) — never force‑kill it. Force‑kill leaves the probe streaming into nothing and can leave the stimulator armed. (See graceful-hardware-shutdown in the project notes.)

1. Parts checklist#

  • Raspberry Pi — a Pi 3, 3B+, 4, or 5 (this appliance is tiny; a Pi 3B+ is plenty).
  • microSD card, 8 GB or larger, + a card reader for your PC.
  • Ethernet cable (the stim link is wired for reliability).
  • Power supply for the Pi (Pi 3/3B+: 5 V / 2.5 A micro‑USB; Pi 4: USB‑C 5 V/3 A; Pi 5: 5 V/5 A USB‑C).
  • AM Systems 2300 stimulus isolator.
  • 3 jumper wires (female‑to‑female Dupont) or a DB‑9 breakout board, to connect the Pi header to the 2300's DB‑9 control port. A 4th wire for ground is required.
  • The SpikesPeak control PC (Windows), on the same wired network as the Pi.
  • Optional but recommended: an oscilloscope or the NI‑DAQ (to see the pulse), a 10 kΩ resistor (dummy load), a multimeter.

2. Flash the operating system onto the microSD (on your PC)#

You do this once, on your PC, with the official Raspberry Pi Imager.

  1. Download + install Raspberry Pi Imager: https://www.raspberrypi.com/software/ (Windows/macOS/Linux).
  2. Put the microSD card in your PC's card reader.
  3. Open Imager and click the three buttons: - CHOOSE DEVICE → your model (e.g. Raspberry Pi 3). - CHOOSE OS → Raspberry Pi OS (other) → Raspberry Pi OS Lite (64‑bit). "Lite" = no desktop; this box only needs to run one program. "64‑bit" matches all modern Pis. - CHOOSE STORAGE → your microSD card. Double‑check you picked the SD card, not another drive — this erases it.
  4. Click NEXT. Imager asks "Would you like to apply OS customisation settings?" → EDIT SETTINGS (older Imager: the ⚙ gear, or press Ctrl+Shift+X). Set: - Set hostname: stimserver (a friendly name; you'll reach the Pi at stimserver.local). - Set username and password: choose a username and password and write them down — you log in with these. (The production Pi in this lab uses username stimserver.) - Enable SSH (on the Services tab): choose Use password authentication. SSH is how you control a headless Pi (no monitor) from your PC. - Locale: set your timezone/keyboard. - (Wi‑Fi is optional — we use Ethernet. You may set your Wi‑Fi to make first boot easier.)
  5. SAVE, then YES to apply, and YES to erase & write. Wait for it to finish and verify, then remove the card.

3. First boot — find the Pi on the network#

  1. Put the microSD into the Pi. Plug the Ethernet cable into the Pi and into the same switch/router your PC uses. Plug in power. Wait ~90 seconds for it to boot.
  2. Find the Pi's address. It boots on automatic (DHCP) addressing first — it does not have the fixed 192.168.1.100 yet. Try these, in order, from your PC (open PowerShell or a terminal): - By name (easiest): ping stimserver.local — if it replies, the name works. - Router page: open your router's admin page and look at its "DHCP clients" / "device list" for stimserver. - Scan the subnet: nmap -sn 192.168.1.0/24 (install Nmap if needed) lists live devices.

If you can already reach it by name, you can use stimserver.local everywhere below in place of an IP.

4. First SSH login#

SSH is a secure remote terminal — you type commands on your PC and they run on the Pi.

ssh stimserver@stimserver.local

Replace stimserver with the username you chose. The first time it asks "Are you sure you want to continue connecting?" — type yes. Then enter the password you set in step 2. You now have a shell prompt on the Pi (it looks like stimserver@raspberrypi:~ $).

Windows has ssh built in. If password typing is refused, re‑check the username; usernames are case‑sensitive.

5. Give the Pi a fixed address (static IP) — from scratch#

SpikesPeak sends fire to the hard‑coded address 192.168.1.100, port 8888. So the Pi must always be at 192.168.1.100, and your PC must be on the same 192.168.1.x network (e.g. the PC at 192.168.1.201). "Static IP" just means fixed instead of automatically assigned (DHCP).

Modern Raspberry Pi OS (Bookworm) manages the network with NetworkManager. Out of the box the wired connection is named Wired connection 1. The installer script (next section) will automatically set the static IP only if the connection is named Stimulation Server — so the cleanest path is to rename it first, then give it the fixed address. Run these on the Pi:

# 1) Rename the default wired connection to the name the installer expects:
sudo nmcli con mod "Wired connection 1" connection.id "Stimulation Server"

# 2) Give it the fixed address 192.168.1.100 and turn on auto‑connect:
sudo nmcli con mod "Stimulation Server" ipv4.method manual ipv4.addresses 192.168.1.100/24 \
     ipv4.gateway 192.168.1.1 connection.autoconnect yes

# 3) Apply it now:
sudo nmcli con up "Stimulation Server"
  • Line 1 renames the connection (identity is the name, not the cable).
  • Line 2 sets the fixed IP/mask (/24), the router (gateway), and makes it reconnect on every boot.
  • Line 3 activates it.

Heads‑up: activating the new address will drop your current SSH session (its IP just changed). Reconnect at the new address: powershell ssh stimserver@192.168.1.100

Prefer menus? Run sudo nmtui → Edit a connection → select the wired one → rename it to Stimulation Server, set IPv4 CONFIGURATION to Manual, add address 192.168.1.100/24 and gateway 192.168.1.1, tick Automatically connect, OK, then Activate it.

Verify the address stuck:

ip -4 addr show eth0                    # should show: inet 192.168.1.100/24 ... eth0
nmcli -t -f NAME,DEVICE,STATE con show  # "Stimulation Server:eth0:activated"

Already‑running lab note: on the current production Pi the connection is still named Wired connection 1 but it does carry 192.168.1.100 (the IP was set on it directly). That works fine — but because the name isn't Stimulation Server, re‑running the installer will print No connection named Stimulation Server and skip the IP step (harmless, since the IP is already set). Renaming as above makes the installer fully manage it.

6. Wire the AM 2300 to the Pi header#

Power OFF the Pi and the 2300 while wiring. Verify every wire twice before powering on.

Find the pins on the Pi's 40‑pin header#

The header is the double row of 40 pins. Physical pin 1 is the one nearest the corner with a square solder pad (the others are round). Pins alternate down the two rows: the odd numbers (1,3,5…) are one row, the even numbers (2,4,6…) the other. Here are the pins you care about (● = used):

                    ┌─────────────────────────────┐
      3V3  power → (1) ● (2)  ← 5V power
     GPIO2       → (3)   (4)  ← 5V power   ⚠️ pin 4 is +5V, NOT a signal
     GPIO3       → (5)   (6)  ← GND
     GPIO4       → (7)   (8)  ← GPIO14
      GND    ●   → (9)  (10)  ← GPIO15
    GPIO17   ●   →(11)  (12)  ← GPIO18     ◄ pin 11 = GPIO17 = On/Off
    GPIO27   ●   →(13)  (14)  ← GND        ◄ pin 13 = GPIO27 = Sign
    GPIO22   ●   →(15)  (16)  ← GPIO23     ◄ pin 15 = GPIO22 = Pulse/Baseline
                    └─────────────────────────────┘

The wiring table (verified against the AM 2300 manual, p.6–7)#

AM 2300 DB‑9 pin Signal Raspberry Pi header pin GPIO (BCM)
4 On/Off physical pin 11 GPIO17
8 +/− Sign physical pin 13 GPIO27
9 Pulse/Baseline physical pin 15 GPIO22
3 or 7 Ground physical pin 9 (GND) —
  • Do NOT wire the 2300's Pin 5 (VCC) or its outputs Pin 1/2. The Pi's 3.3 V logic drives the 2300's high‑impedance TTL inputs safely; its stimulus output stays opto‑isolated from the Pi.
  • The code holds Pulse/Baseline (GPIO22) HIGH so the 2300 uses its front‑panel PULSE amplitude knob.

⚠️ Common wiring mistake — "pin 4"#

The On/Off signal is the AM 2300's DB‑9 pin 4, but on the Pi it comes out of GPIO17 = physical header pin 11 — not the Pi's physical pin 4. The Pi's physical pin 4 is a constant +5 V power pin. If you are probing the On/Off control (e.g. into an oscilloscope or NI‑DAQ), put the wire on physical pin 11 (GPIO17). A wire on physical pin 4 will just read a flat +5 V and never move.

Measuring the control line on the NI‑DAQ (bench test, no stimulator)#

If you want to watch the Pi's control pulse directly (2300 not connected): - Connect Pi physical pin 11 (GPIO17, On/Off) → your capture input (e.g. NI‑DAQ ai4). - Also connect a Pi GND (e.g. physical pin 9) → the capture's analog ground / AI GND, so the two devices share a reference. Without a common ground a single‑ended measurement floats and reads garbage. - On fire, GPIO17 idles at 0 V and pulses to 3.3 V; see §9 for what the waveform looks like.

7. Copy the program to the Pi and run the installer#

The Pi code lives in the repo folder raspberrypi_pulsegenerator/ (two files: the C program and setup.sh).

  1. Copy both files to the Pi — run this on your PC, from the repo root (scp = secure copy): powershell scp raspberrypi_pulsegenerator/pulse_generator_am2300.c raspberrypi_pulsegenerator/setup.sh stimserver@192.168.1.100:~/
  2. Run the installer once — on the Pi (over SSH): bash chmod +x ~/setup.sh # mark the script executable sudo ~/setup.sh # do the install (needs admin = sudo) The script prints 7 steps as it runs. In plain terms it:
  3. installs the compiler + the lgpio GPIO library,
  4. compiles the C program to /usr/local/bin/pulse_generator,
  5. sets the static IP (only if the connection is named Stimulation Server — see §5),
  6. reserves the last CPU core (via isolcpus) so pulse timing has no interference,
  7. installs a systemd service that auto‑starts the program on boot and auto‑restarts it if it ever crashes,
  8. sets the Pi to boot to a plain console (no desktop),
  9. disables background services this appliance does not need (Bluetooth, printing, etc.).
  10. Reboot once so the core reservation and static IP take full effect: bash sudo reboot Your SSH session ends; wait ~30 s and reconnect with ssh stimserver@192.168.1.100.

From now on it is turnkey: power on → the stim server is already running. Nothing to launch.

8. Verify it is running#

Run these on the Pi. This is the reliable check (see the note about logs below).

systemctl is-active pulsegenerator     # -> active
systemctl is-enabled pulsegenerator    # -> enabled   (starts on every boot)

Confirm it is actually listening on UDP 8888:

sudo ss -lunp | grep 8888
# -> UNCONN ... 0.0.0.0:8888 ... users:(("pulse_generator",pid=...))

Confirm the GPIO pins are claimed and at their idle levels (proves the program initialised the hardware):

pinctrl get 17 27 22
# expect:  17: op -- -- | lo   (On/Off  = LOW  = off)
#          27: op -- -- | lo   (Sign    = LOW)
#          22: op -- -- | hi   (Pulse/Baseline = HIGH = "use PULSE knob")

Why not journalctl?#

The program prints friendly banners ([GPIO] … VERIFIED [BCM (Pi 1‑4)], [RT] Pinned to CPU core 3, Listening on UDP :8888, -> Device ARMED, -> Fire: …). Under systemd those lines are buffered and do not appear in journalctl in real time (stdout is block‑buffered when it is a pipe, and the program does not flush). This is cosmetic — the service still works (the checks above prove it). If you want the live log, either run the program by hand (see below) or have someone add stdout line‑buffering to the service (ExecStart=/usr/bin/stdbuf -oL /usr/local/bin/pulse_generator).

See the banners live (debugging): stop the service and run the program in the foreground —

sudo systemctl stop pulsegenerator
sudo /usr/local/bin/pulse_generator      # prints [GPIO]/[RT]/Listening; Ctrl‑C to quit
sudo systemctl start pulsegenerator      # put the appliance back

9. Test fire#

Send an arm‑then‑fire from your PC (no GUI needed). Save this as testfire.py on the PC and run python testfire.py:

import socket, time
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.sendto(b"connect", ("192.168.1.100", 8888))   # ARM the device
time.sleep(0.2)
s.sendto(b"fire",    ("192.168.1.100", 8888))    # fire with defaults
  • A bare fire uses the built‑in defaults: 60 µs each phase, 10 µs interphase gap, 100 Hz, 500 ms total = a 50‑pulse train. (Full control: fire <phase_us> <gap_us> <freq_hz> <total_ms>.)
  • Send quit to disarm; quit also aborts a train already in progress.

What the On/Off line (GPIO17) shows on a scope / NI‑DAQ ai4: 50 pulses, one every 10 ms (100 Hz). Each pulse is a ~130 µs HIGH window (3.3 V) with a brief ~10 µs LOW notch in the middle — that notch is the interphase gap between the + and − phases. (Polarity itself is on the Sign line, GPIO27; the biphasic current shape appears at the 2300's isolated output, which is not connected during a bench test.) This matches the ESP32 baseline (~131 µs per pulse) the system was originally verified against.

10. Everyday operation#

  • Turnkey: plug the Pi in → the stim server runs. Nothing to log into. It auto‑restarts if it crashes.
  • Update the program later: copy a new pulse_generator_am2300.c and re‑run the installer: powershell scp raspberrypi_pulsegenerator/pulse_generator_am2300.c stimserver@192.168.1.100:~/ ssh stimserver@192.168.1.100 "sudo ~/setup.sh"
  • Graceful shutdown when it can reach an animal: always stop SpikesPeak via its WebSocket Disconnect / quit so the stimulator disarms; never force‑kill.
  • Protect the SD card from abrupt power‑off (optional): since you power the appliance by plugging/ unplugging, enable a read‑only overlay so a sudden cut can't corrupt the card: sudo raspi-config → Performance Options → Overlay File System → Enable. (Disable it, run the installer, re‑enable it, when you need to update.)

11. Troubleshooting#

Symptom Fix
ping stimserver.local fails Give it another ~30 s to boot; check the Ethernet link LED; try the router's device list or nmap -sn 192.168.1.0/24.
SSH: Permission denied Wrong username or password (both case‑sensitive). Use the exact values from Imager (step 2).
Can't reach 192.168.1.100 after §5 Your PC must be on 192.168.1.x too (e.g. .201). Check the cable goes to the same switch.
Installer prints No connection named Stimulation Server Do the rename in §5 first, or set the IP on Wired connection 1 directly. (Harmless if the IP is already set.)
systemctl is-active ≠ active See the real error: systemctl status pulsegenerator and sudo journalctl -u pulsegenerator -b (systemd's own lines do show). Usually a compile error in step 7 output.
sudo ss -lunp \| grep 8888 shows nothing The program isn't running/bound; check systemctl status and re‑run sudo ~/setup.sh.
Nothing on the scope when firing 1) Probe physical pin 11 (GPIO17), not physical pin 4 (that's +5 V). 2) Share a common ground (pin 9). 3) Confirm you sent connect before fire. 4) For the 2300's output, set its Range/Level knobs.
Two devices fight over 192.168.1.100 Power off any old ESP32 or Pi 5 that used to be the stim server — they share that IP.
Timing jitter you can't accept The stock kernel + isolcpus is fine for 60 µs phases; for a bounded worst case build a PREEMPT_RT kernel (raspberrypi_pulsegenerator/README.md §6).

12. Glossary#

  • SoC — "System on a Chip"; the Pi's main processor+peripherals in one chip.
  • GPIO — General‑Purpose Input/Output; the Pi's controllable digital pins. "GPIO17" is a pin name (BCM numbering); its physical position on the header is pin 11 — the two numbering schemes differ.
  • Header / pin — the 40‑pin double row on the Pi you plug wires into.
  • SSH — Secure Shell; a remote text terminal to the Pi. scp — Secure Copy; copies files over SSH.
  • mDNS / .local — lets you reach the Pi by hostname.local without knowing its IP.
  • DHCP vs static IP — DHCP = the network hands out an address automatically (can change); static = a fixed address you set (we need 192.168.1.100 fixed).
  • NetworkManager / nmcli / nmtui — the tool that manages network connections; nmcli is its command‑line, nmtui its text‑menu.
  • systemd / service / systemctl / journalctl — Linux's startup manager; a "service" is a program it keeps running; systemctl controls services; journalctl shows their logs.
  • TTL / active‑high — a digital signal where a HIGH voltage (here 3.3 V) means "on/1".
  • Biphasic, charge‑balanced pulse — a stimulus with a + phase then an equal − phase, so no net charge is injected (safer for tissue).
  • isolcpus / SCHED_FIFO / real‑time — Linux knobs that dedicate a CPU core and raise the program's scheduling priority so pulse timing isn't disturbed.
  • UDP — a fast, connectionless network message; SpikesPeak sends fire as one UDP packet to port 8888.

Reference: Architecture and Features#

This build is hardened for reliability and low jitter: - Runs on any 40-pin Pi (3 / 3B+ / 4 / 5) — the header gpiochip is auto-detected by label, and the fast GPIO path auto-detects the chip family (RP1 on Pi 5, BCM on Pi 1–4). One binary, no per-model editing. - True interphase gap — the output is driven to Zero between the + and − phases (charge-balanced, no mid-pulse polarity glitch). Default 10 µs, matching the ESP32. - Non-blocking receive (poll-based) — the main wait sleeps until a packet (low-latency wake, no busy polling), and a running train is abortable mid-train by sending quit. - Real-time: memory is locked (mlockall, no page-fault jitter), the process is pinned to a dedicated CPU core, and run at SCHED_FIFO. Isolate that core (isolcpus, below) for the tightest timing. - Direct register edges — a single store to the GPIO set/clear register (RP1 SYS_RIO on Pi 5, GPSET0/GPCLR0 on Pi 1–4; no syscall per edge, ~nanosecond edges). Auto-detected and self-verified against lgpio at startup, with automatic fallback to lgpio writes — fast and safe. - Safe shutdown — Ctrl-C/systemd stop drives the output to Zero before exiting.

Timing vs the ESP32: trigger latency is virtually identical (same UDP path; the 2300 adds only its ~6 µs control-to-output delay). Pulse edges are driven by direct register writes (nanosecond stores, no syscall), so with a dedicated core (isolcpus) and — if you need a bounded worst case — a PREEMPT_RT kernel (§6), the Pi gets essentially as close to the ESP32's hardware RMT as software timing allows.

Reference: Command / fire protocol (UDP :8888)#

Message Effect
connect ARM the device (SpikesPeak sends this on startup)
quit DISARM — and aborts a running train immediately
fire fire with the current parameters (defaults: 60 µs phase, 10 µs gap, 100 Hz, 500 ms = 50 pulses)
fire <phase_us> <freq_hz> <total_ms> set phase / rate / duration (gap unchanged)
fire <phase_us> <gap_us> <freq_hz> <total_ms> full control incl. interphase gap

Important — SpikesPeak sends a bare fire, so each ripple detection triggers the default 500 ms, 50-pulse train (the per-pulse shape — 60 µs +, 10 µs gap, 60 µs − — matches the old ESP32 pulse). For a single pulse per detection, either lower DEF_TOTAL_MS in the source (e.g. to make one pulse) or ask to have StimulatorClient::fire() send explicit parameters. quit aborts a train, so the closed loop can interrupt a stim.

Reference: Maximum real-time (PREEMPT_RT kernel) (optional, advanced)#

isolcpus + mlockall + SCHED_FIFO + the built-in direct-register edges already give excellent typical timing on the stock kernel. A PREEMPT_RT kernel adds a bounded worst case (it makes almost all kernel code preemptible), which matters when you need a hard guarantee rather than a good average. It is a kernel rebuild — do it only if you measure worst-case jitter you can't accept.

Measure first (so you know whether you even need it)#

sudo apt install -y rt-tests
# Hammer core 3 at RT prio 80 and watch the Max latency (let it run a few minutes):
sudo cyclictest -m -p 80 -a 3 -t 1 -n -i 200 -d 0

If Max stays within a few µs, you don't need PREEMPT_RT. If you see occasional big spikes (tens–hundreds of µs), PREEMPT_RT is what removes them.

Build a PREEMPT_RT kernel on the Pi (native build, over SSH)#

PREEMPT_RT has been mainline since Linux 6.12, so on a current Pi kernel it's just a config switch — no separate patch. Check uname -r first; on < 6.12 you'd also need the matching patch-<ver>-rtN from kernel.org before menuconfig.

uname -r                                    # e.g. 6.12.x  (RT is mainline at 6.12+)
sudo apt install -y git bc bison flex libssl-dev make libncurses-dev
git clone --depth=1 --branch rpi-6.12.y https://github.com/raspberrypi/linux
cd linux
make bcm2712_defconfig                       # Pi 5; use bcm2711_defconfig (Pi 4) or bcmrpi3_defconfig (Pi 3, 64-bit)
# Select the real-time preemption model, non-interactively:
./scripts/config --disable PREEMPT_VOLUNTARY --disable PREEMPT --enable PREEMPT_RT
make olddefconfig
#   ...or interactively: make menuconfig
#      General setup -> Preemption Model -> Fully Preemptible Kernel (Real-Time)
make -j4 Image.gz modules dtbs               # ~30-60 min on a Pi 5; much slower on a Pi 3 (or cross-compile per RPi docs)
sudo make -j4 modules_install
# Install under a CUSTOM name so you can always boot back to the stock kernel:
sudo cp arch/arm64/boot/Image.gz /boot/firmware/kernel_rt.img
sudo cp arch/arm64/boot/dts/broadcom/*.dtb /boot/firmware/
sudo cp arch/arm64/boot/dts/overlays/*.dtb* /boot/firmware/overlays/

Point the firmware at it in /boot/firmware/config.txt (revert by deleting this one line):

kernel=kernel_rt.img

sudo reboot
uname -a          # must now show  PREEMPT_RT
