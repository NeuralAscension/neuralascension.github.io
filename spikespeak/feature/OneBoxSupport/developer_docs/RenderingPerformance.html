Live-view rendering performance — SciChart limits, what we tried, and the off-ramps#

Everything we measured about rendering hundreds of streaming channels in the SpikesPeak browser live view (SciChart.js v5.2.35), what optimizations moved the needle (spoiler: almost none), why, and the concrete paths to go faster if we ever need to. Raw benchmark numbers live in benchmarks/CHANNEL_DENSITY_REPORT.md; this doc is the narrative.

SciChart was removed from SpikesPeak on 2026-08-27. webinterface/GlRenderer.js is the only live-view renderer, webinterface/ProbeMap.js draws the probe map in canvas 2D, and the vendored bundle is gone from webinterface/lib/. Read this document as the evidence trail that located the bottleneck: every measurement below was true of the code at the time it was taken and is left exactly as recorded. The advice has been corrected in place — a reader following the old density guidance would now throttle a renderer that does not need it. The finished comparison is RendererExperiment.md; the interface the replacement satisfies is RendererContract.md.

TL;DR#

  • SciChart renders on ONE main thread. It has no OffscreenCanvas/Web-Worker mode, and its .wasm is single-threaded (it uses WASM-SIMD, not threads), so COOP/COEP/SharedArrayBuffer do nothing for it.
  • On this box (RTX 3060 Ti, 16 cores) the wall is ~320 on-screen line series (e.g. 4 columns × 80): the main thread saturates at 100%, FPS drops to ~40. Below ~160–200 series it's a solid 60 fps.
  • The bottleneck is the DRAW of many series, not data ingestion. We moved the parse to a Web Worker and it changed nothing — because appendRange + SciChart's draw dominate, and both must stay on the main thread with SciChart.
  • There is no SciChart-side software fix that recovers 60 fps at 320 series. The fix was a different renderer — though not for the reason this line originally gave. "Move the WebGL drawing off the main thread" was the hypothesis of the day and it was wrong; see the harness section below. What had to go was the per-series CPU bookkeeping, and the replacement draws on the main thread quite happily.
  • The ≲ 160–200 density ceiling this document used to prescribe no longer applies. It was a SciChart limit and SciChart is gone. On the OneBox + NP2.0 rig the current renderer holds a solid 60 fps at 480 on-screen traces (four columns of 120), where SciChart managed 42 ± 5. Set the per-column channel dropdowns for the science you want to see, not for a frame-rate budget.

RE-MEASURED 2026-08-27 — and the architecture question is now answered#

Everything below this section predates the source-selection refactor. Two things changed:

The benchmark had stopped connecting. cdp_bench.py selected the sim by clicking a button inside #sim-picker-card, which stopped existing when the source picker became an anchored menu. The click was guarded if(b)b.click(), so it did nothing, raised nothing, and the sweep measured an idle, unconnected view at a beautiful 60 fps in all twelve cells. Fixed: it drives the backend over the WebSocket and now aborts when the view is not streaming. Anything measured between the picker change and 2026-08-27 is void.

The cost is PER-SERIES, by a factor of 9#

benchmarks/cdp_window_sweep.py (new) sweeps the time window at a fixed series count — 10× the points per series with no change in draw-call count. That is the one knob that separates the two candidate costs, and nobody had turned it.

window pts/series fps main-thread busy
1 s 2,400 56 0.677
2 s 4,800 56 0.721
5 s 12,000 56 0.870
10 s 24,000 45 0.999

The naive reading — "busy moved when the window grew, so it is vertex-bound" — is wrong, and the script printed exactly that verdict on its first run before the arithmetic was done properly. Both knobs add vertices; they add wildly different numbers of them. Normalize:

via SERIES  160 -> 240 @ 1 s :   +192,000 vertices   busy +0.219  =>  1.14e-06 per vertex
via POINTS  1 s -> 5 s @ 160 : +1,536,000 vertices   busy +0.193  =>  1.26e-07 per vertex

A vertex costs 9.1× more when it arrives as a new series than as a new point. So per-series overhead dominates, and the primary win for any replacement renderer is collapsing N series into one draw call / one vertex buffer — which is exactly what a custom WebGL2-in-a-worker renderer is for, and what the SubCharts stopgap below only partly buys. Decimating to pixel columns is a real but secondary win: points are not free (10× the window still drove busy 0.677 → 0.999), they are just an order of magnitude cheaper than series.

Why the Web Worker decode experiment measured nothing (now with the number)#

NetworkClient has been computing decode metrics and logging them to the console for months without anyone writing them down. Captured at 4 × 40, sim NP2 raw @ 30 kHz:

batches 41   avgParseMs 1.422   maxParseMs 1.90   maxGapMs 39.7   kB/s 2464

1.4 ms of decode per batch against a ~18 ms frame. Attempt A below moved exactly that to a worker and measured no gain, which is what you would predict from this number. It is not the bottleneck and moving it is not worth a worker round-trip.

BUILT AND MEASURED IN THE APP (2026-08-27) — the cliff is gone#

The full experimental record -- method, repeats, CPU and GPU data, the figures, the mechanism and the limits -- is in RendererExperiment.md. This section is the summary.

webinterface/GlRenderer.js is a WebGL2 trace renderer wired into the live view. For the duration of this A/B it sat behind window.__useGl, with SciChart as the default and window.__setGl(true) switching every column live without a reload — that is how the two arms below were measured in one session. Those globals were removed on 2026-08-27 along with SciChart itself; there is no renderer to select any more. window.__benchPointCount(colIndex) survives and now answers only from the GL renderer, returning -1 for no such column or a lost context.

Same protocol, same session, one variable.

layout series SciChart fps / busy WebGL2 fps / busy busy
1 × 20 20 56 / 0.194 56 / 0.103 1.9×
4 × 20 80 56 / 0.434 56 / 0.164 2.6×
4 × 40 160 56 / 0.658 56 / 0.179 3.7×
4 × 60 240 56 / 0.877 56 / 0.191 4.6×
4 × 80 320 44 / 0.999 56 / 0.208 4.8×

At 320 traces the frame-rate cliff disappears: 44 fps with the main thread saturated becomes a full 56 fps at 21 % busy, leaving 79 % of the thread free. The gain grows monotonically with density, which is the signature of per-series overhead being what was removed — exactly what the isolated harness predicted. Traces render correctly at 320 across four columns, with the same palette, depth ordering and labels.

Two mistakes made getting here, both of which produced confident wrong numbers#

The first A/B showed no gain at all — 41 fps vs 44, both saturated. The GL canvas was layered over the SciChart surface, so it looked like a swap, but SciChart was still bound, still being fed by appendRange, and still drawing. The app was paying for both renderers. A comparison that leaves the incumbent running is not a comparison; for the rest of the A/B, __useGl skipped the appends and hid the SciChart series.

The renderer appeared broken under test, painting 1.0 frames/s with every buffer full and correct. requestAnimationFrame does not fire in a window Chrome believes is occluded (AgentTraps.md §5f) — and setTimeout, the obvious fallback, is clamped to ~1 Hz in the same state. The GUI harness passed no anti-throttling flags, so every GUI test had been running against a page throttled to 1 Hz. Fixed in tests/gui/_harness.py; the renderer also schedules a timer alongside rAF so it cannot be held hostage by either one alone.

The GL drawing is not the cost — it is ~200x cheaper than the frame it sits in#

benchmarks/renderer_lab.html + renderer_lab_bench.py (new) draw the live view's exact data shape — N series, 2400 points each, a min/max pair per timebin, y offsets baked in, same palette and 1 px stroke — in raw WebGL2, with no backend, no WebSocket, no SciChart and no app. Two modes differing only in draw-call count: one drawArrays(LINE_STRIP) per series, versus a single drawElements(LINE_STRIP) for all series separated by the WebGL2 primitive-restart index.

The first run of this reported frame rate and every cell came back 57.4 fps / 17.4 ms — 20 series and 1280 series, 48 k vertices and 3 M, both modes, identical. That is the vsync cap, not a result. A benchmark pinned at vsync measures the monitor. It now times the draw itself.

80 192 k 0.060 0.025 2.4× 5.7 ms — 95×
160 384 k 0.075 0.023 3.3× 11.4 ms — 153×
240 576 k 0.062 0.029 2.1× 15.3 ms — 246×
320 768 k 0.076 0.020 3.8× 17.4 ms — 229×
640 1.5 M 0.117 0.023 5.1× —
1280 3.1 M 0.187 0.025 7.5× —

(drawMs is CPU time issuing the frame's draw calls; the SciChart column is its measured main_thread_busy × the 17.4 ms frame.)

Two things follow, and the second is the important one.

Collapsing draw calls works, as predicted. one is flat at ~0.023 ms from 20 series to 1280, while many grows linearly — 3.8× at today's wall, 7.5× at 1280. That is the 9.1×-per-series finding showing up exactly where it should.

But the raw draw is ~200× cheaper than the frame SciChart needs at the same density. 320 series is where the live view collapses to 44 fps with the main thread saturated; the same vertices go to the GPU in 0.076 ms, a fifth of a percent of the budget. So the wall is not the GL drawing, and it is not the vertex count either. It is the chart library's own per-series CPU work — its scene graph, its coordinate transforms, its JS↔WASM crossings — which a renderer with no per-series objects does not have. The replacement is not a marginal win; it removes the bottleneck rather than shrinking it.

Phase 2 — the upload, which was the one real threat, is a non-issue#

Phase 1 drew static buffers, so it was an upper bound. The live view must ingest ~40 new points per channel every frame (POINTS_PER_UPDATE 20 bins, min and max) — 100 kB at 320 series — write them into a ring, and draw. That is the irreducible work any renderer has, and the obvious place a naive replacement gives the win back.

It is also an architecture fork, because the buffer layout decides the upload:

  • series-major [s0 p0..pN][s1 p0..pN]… — each channel's new samples land at its own offset, so the frame costs N bufferSubData calls. Draws as a plain LINE_STRIP; memory order is already strip order.
  • time-major [t0 s0..sN][t1 s0..sN]… — one frame's samples are contiguous, so the frame is one bufferSubData. But consecutive memory is now different channels, so the strip must be gathered through a strided index buffer — built once, never re-uploaded. That trades upload cost for vertex-fetch locality, which is why draw is measured in both.
series s-major, N calls t-major, 1 call upload ratio draw delta
80 0.168 ms 0.048 ms 6.3× +0.003 ms
160 0.232 ms 0.049 ms 8.6× +0.006 ms
320 0.411 ms 0.050 ms 11.8× −0.003 ms
640 0.477 ms 0.053 ms 12.2× ±0.000 ms
1280 0.516 ms 0.048 ms 12.3× −0.004 ms

(Renderer cost = upload + draw.)

Time-major wins outright, and the strided index buffer costs nothing. The draw deltas are within ±0.008 ms — noise — and at the highest densities time-major is faster. Upload is 12× cheaper and, unlike series-major, flat in series count.

So at today's wall of 320 series the whole renderer costs 0.050 ms, or 0.3 % of the frame, and it is still 0.048 ms at 1280 series — four times the density that currently collapses the view. The phase-1 result survives contact with real ingestion.

On these numbers time-major is the right architecture: one time-major vertex buffer per column, one contiguous bufferSubData per frame, a strided index buffer built once, one drawElements(LINE_STRIP) with primitive restart. No worker, no OffscreenCanvas — at 0.3 % of a frame there is nothing to move off the main thread.

What actually shipped is series-major, and the reason is correctness, not performance. A time-major ring cannot express "draw the last window as one strip" through a static strided index buffer — the index buffer would have to be rebuilt or re-uploaded every time the write head moves, which is exactly the per-frame cost the layout was chosen to avoid; leave it static and the wrap point becomes a visible horizontal slash across every trace. The shipped renderer instead gives each row a 2 × capacity span written sequentially and compacts it about once a second, so the visible window is always one contiguous drawArrays range with no wrap seam.

The price is the 0.36 ms/frame in the table above (0.411 vs 0.050 at 320 series) — 2 % of a 17.4 ms budget, paid to keep the traces free of a rendering artifact. That is the correct trade today and it is worth revisiting only when 0.4 ms is the thing in the way; a time-major layout would then need a dynamic index buffer or a wrap-aware two-draw path, and both give some of the upload win back. Full reasoning: RendererExperiment.md §5.

fill is excluded from these totals, and must be. The harness generates synthetic samples (3×Math.sin + Math.random each), which the app does not do — it copies decoded floats out of a socket buffer. Reading the harness's fill as a renderer cost would be measuring the test. The app's real equivalent is NetworkClient's decode, already measured at 1.4 ms per batch, and already paid today by SciChart too. An earlier version of the harness also called the generator twice per point in the time-major path, which made that layout look ~50 % worse for a reason that had nothing to do with layout; fixed before the numbers above were taken.

What we tried (and the measured result)#

Attempt What Result Why
E — SciChart best-practices fifoCapacity, isSorted, containsNaN, batched appendRange with typed-array subarrays were already in place; we added SciChartDefaults.wasmBufferSizesKb = 32768 No FPS change (4×80 still ~40 fps / 100 %) That's memory-fragmentation tuning, not a frame-rate fix. The append path was already optimal.
A — Web Worker for data ingest A "transform worker": moved the binary parse + per-sample offset-baking off the main thread; posts transferable Float64Arrays; main thread only does appendRange + draw. Implemented + verified (worker active, traces render, graceful fallback). No gain at ANY density (4×40 = 65 % vs 63 %; 4×80 still ~43 fps / 100 %). Reverted. The parse was never the bottleneck. The draw of hundreds of line series (+ appendRange) dominates the main thread, and neither can move off it in SciChart. The worker round-trip offset the small parse saving.
B — SciChart in a Worker (OffscreenCanvas) (researched, not attempted) Not possible SciChart is DOM-coupled (interaction, tooltips; our channel labels are DOM overlays). No OffscreenCanvas/worker support.
D — COOP/COEP → SharedArrayBuffer (researched, deliberately skipped the C++ rebuild) Pointless SciChart's .wasm is single-threaded regardless; it uses WASM-SIMD. crossOriginIsolated does nothing for it.

The lesson: the "you have 16 cores, 1 is used" framing was correct, but the movable work (parse) wasn't the actual limiter. Always measure before believing a threading fix. SciChart's single-threaded draw is the hard floor here.

Optimizations that DON'T apply / are already done#

This section describes the SciChart implementation as it stood, and none of it is in the tree any more — the settings, the FIFO series and the four column surfaces went with the bundle on 2026-08-27. It is kept because it is the answer to "did you not just tune it?", and the answer is yes, first, and it bought nothing.

Per SciChart's own perf guidance, most tricks were already in the codebase or moot: - Single-surface-with-y-offset (all channels on one surface, offset in Y) — this is exactly what each ChartColumn already does internally (baked yOffset, one hidden Y axis, drawLabels:false). - Suppress axis/gridline drawing — already off (drawMajorGridLines:false, drawLabels:false). - FIFO typed-array series — already on (fifoCapacity, isSorted, containsNaN). - SubCharts API (SciChartSubSurface, consolidate the N column surfaces → 1 surface / 1 draw loop) — the ONE untried SciChart lever. Surfaces already share one WebGL context by default, so the expected win is only the per-surface overhead the data showed (~6 %: 80 series as 1×80 = 22 % vs 4×20 = 28 %). Not a fix for the 320-series wall; a modest polish at best, for a non-trivial refactor of ChartColumn.

The real fix (future): move WebGL drawing off the main thread — a different renderer#

Settled 2026-08-27, and by none of the three paths below as written. SciChart was replaced by a hand-written WebGL2 renderer (webinterface/GlRenderer.js) drawing on the main thread — no worker, no OffscreenCanvas, no vendored line-plot library, nothing bought. The premise of this section's first sentence turned out to be false: the isolated harness above put the same 768 k vertices on the GPU in 0.076 ms of a 17.4 ms frame, so once the per-series CPU bookkeeping was gone there was nothing left worth moving off the main thread. The section stays because the survey of what other high-density neural viewers do is still worth reading, and because it records honestly what we believed before the harness was written. Result: RendererExperiment.md.

The only way to break the ceiling is to render in a Web Worker via OffscreenCanvas, so the draw runs on an idle core and the GPU is fed directly. SciChart can't; several alternatives can, all keeping the HTML/CSS/JS UI (you wrap your own headers/labels/sliders around the canvas — the flexibility we want). (Researched via agy web-search 2026-07-12; treat the specifics as leads to verify with a small proof-of-concept, not gospel.)

Path 1 — Custom WebGL2 in a Worker (OffscreenCanvas) [recommended if we DIY]. Draw the line strips yourself in a worker; ingest the WS binary in the worker and push floats straight to GPU vertex buffers (zero-copy transferables); the main thread does nothing. Max performance (1000+ series @ 60 fps, ~0 % main-thread), MIT-friendly. Cost: you write the shaders, the scrolling window, and the axes/labels (but axes/labels can stay HTML/CSS — our strength). Reference implementations: - webgl-plot — MIT, WebGL line plotter, worker/OffscreenCanvas-capable, oscilloscope-style, 1000+ lines; basic (no built-in axes/legends → you supply the chrome). https://github.com/danchitnis/webgl-plot - narration.studio — WebGL2-in-a-worker high-density waveform drawing. https://github.com/stevenwaterman/narration.studio - regl / twgl — thin WebGL helpers, fully worker-compatible, if we want a bit more structure than raw GL.

Path 2 — LightningChart JS (commercial drop-in). Native OffscreenCanvas/worker rendering (reportedly since ~v8.3), production axes/zoom/legend, 800+ series @ 60 fps in a worker. Cost: proprietary license (~$2,750/dev — verify current pricing/version). Least effort, but a paid dependency. https://lightningchart.com/js-charts/docs/

Path 3 — SciChart SubCharts refactor (keep the current license). Consolidate to one surface (SciChartSubSurface). Low-to-medium effort, reuses SciChart — but still single-threaded on the main thread, so it only trims the ~6 % per-surface overhead and will hit the same wall at 768+ channels. A stopgap, not a solution.

What high-channel neural web viewers actually do (context): Neurosift (Flatiron / J. Magland) uses custom Canvas2D/WebGL + client-side level-of-detail decimation + WASM loaders (LINDI); NWB Explorer pre-downsamples server-side; real-time EEG/oscilloscope monitors write custom WebGL line-strip shaders in workers. The common thread: decimate to pixels + draw off the main thread, not a heavyweight main-thread chart library.

Recommendation: if/when SciChart's ceiling actually blocks the science, the best fit for "keep the web UI, swap the renderer" is Path 1 (webgl-plot or custom WebGL2 in a worker) — MIT, off-main-thread, and it leaves all the UI chrome to HTML/CSS/JS. Path 2 if we'd rather buy than build. This is a separate project; not urgent while ≤ ~200 on-screen series covers the workflows.

Practical guidance#

Rewritten 2026-08-27. This section used to say "keep total on-screen series ≲ 160–200", and that instruction is now wrong: it was a SciChart limit, and following it today would throttle a renderer that does not need throttling. The numbers behind the old ceiling are preserved in the tables above as measurements; they are not repeated here as advice.

  • There is no density ceiling to budget around. On the OneBox + NP2.0 rig, four columns of 120 — 480 on-screen traces, half again the density that used to collapse the view — hold a solid 60 fps with the renderer main thread at 0.225 of a core. SciChart on the same rig at the same density was 42 ± 5 fps at 0.964 of a core.
  • The per-column channels dropdown (Auto/20/40/60/80/120, independent per column/row) is now a what do you want to look at control rather than a performance budget.
  • Real multi-band loads (NP1 AP+LFP + NI-DAQ + ripple detection + recording) still add main-thread work on top of the traces, and that has not been re-measured against the current renderer. The headroom is much larger than it was; it is not infinite, and the ripple dock in particular still runs its own unconditional rAF loop.
