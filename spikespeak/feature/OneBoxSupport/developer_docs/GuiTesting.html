Driving & screenshotting the SpikesPeak GUI headlessly (for agents / CI)#

The UI is an external browser (served HTTP:8234, one WebSocket:1234) — SciChart renders in the browser, not the backend. So to verify frontend work (probe map, record-channel selection, the sim picker, live view, NP2.0 editor) without a human at the mouse, you drive a real browser programmatically and screenshot it. This was used heavily to build/verify the 2026-07-06 work and is the recommended way to check any GUI change.

Two layers: - Backend commands (select/play/record/quit) → python/spikespeak_cli.py over WS:1234. See ControlCLI.md. A watching browser mirrors CLI actions live. - Browser rendering + clicks/drags + screenshots → Chrome DevTools Protocol (CDP) against a Chromium-family browser (Brave/Chrome/Edge). Driver: python/tools/cdp.py. Cross-platform (works on Windows too — CDP screenshots are browser-based, not OS-screen-based).

Alternative quick screenshot (Linux/X11 only): DISPLAY=:0 import -window <wid> out.png (ImageMagick), window id from wmctrl -l. Not portable; prefer CDP's Page.captureScreenshot (clean page-only image).

1. Launch: one backend + one browser#

Backend (headless; --no-browser so it doesn't open its own window):

# Linux (this box): Qt 6.11.1; offscreen because WebEngineWidgets needs a platform plugin.
cd build/Desktop_Qt_6_11_1_Release
LD_LIBRARY_PATH=~/Qt/6.11.1/gcc_64/lib QT_QPA_PLATFORM=offscreen ./bin/SpikesPeak --no-browser &
# Windows: run the exe (PATH set per ControlCLI.md); --no-browser to skip the auto app-window.

Browser with the CDP debug port — an isolated app-window that does NOT touch the user's normal browser profile:

# Linux:
brave-browser --user-data-dir=/tmp/bravesp --remote-debugging-port=9222 "--remote-allow-origins=*" \
  --no-first-run --no-default-browser-check --disable-features=Translate,TranslateUI \
  --app=http://localhost:8234 --window-size=1760,1080 &
# Windows (adjust the exe path): brave.exe / chrome.exe / msedge.exe with the SAME flags.

Gotchas (each cost real time on 2026-07-06 — don't repeat them)#

  • QUOTE "--remote-allow-origins=*". A bare * gets glob-expanded by the shell → the flag is corrupted → CDP handshake fails 403. Chromium requires this flag OR a suppressed Origin header (the driver does suppress_origin=True, but keep the flag too).
  • IPv4/IPv6: the debug port sometimes binds [::1] only, so localhost (IPv4) refuses. cdp.py already tries 127.0.0.1, [::1], localhost.
  • Don't Page.reload when the browser is the only client. Reload drops the WS → the backend's 2 s grace-timer quits the backend. Relaunch the browser fresh instead of reloading.
  • window.app is exposed for inspection (the AppController): c.eval("JSON.stringify(window.app.simVariants)"), window.app.dataStore.streams, etc.

2. Drive it (python/tools/cdp.py)#

import sys; sys.path.insert(0, "python/tools")
from cdp import CDP
c = CDP()                                  # attaches to the page target on :9222
c.eval("document.title")                   # -> "SpikesPeak"
c.eval("document.getElementById('playPauseBtn').click();")
c.screenshot("/tmp/shot.png")              # then Read the PNG to eyeball it
c.click(x, y)                              # viewport pixels
c.drag(x0, y0, x1, y1)                     # e.g. a vertical box-select over the probe scatter
c.wheel(x, y, dy, times=n)                 # scroll the probe map's y-axis (dy>0 -> toward the tip)

Ready-made scenarios + helpers: python/tools/gui_scenarios.py (built on cdp.py). It consolidates the one-off drivers used to build/verify the NP1/NP2 GUI work into a Gui helper (connect_sim / connect_source / wait_ready / set_mode / tab / np2_drag / rec_set / shank_counts / shot) plus runnable scenarios:

python python/tools/gui_scenarios.py np2_smoke        # sim NP2: editor + record mode + live view
python python/tools/gui_scenarios.py hw1_record t1 15 # real 1.0 GUI record flow (arm -> Set -> Record 15s)
python python/tools/gui_scenarios.py np2_crossshank   # build a cross-shank NP2 map + record a subset
python python/tools/gui_scenarios.py mismatch_check   # select "NPX 2.0" and report the mismatch dialog

Import from gui_scenarios import Gui for custom flows. Screenshots land in <build>/bin/RecordingTests/. c.eval awaits promises, so QWebChannel calls work: c.eval("window.activeNpxModule.getImroAsJson().then(s=>JSON.parse(s).channels.length)").

3. Teardown discipline (don't leave messes; don't crash the probe)#

  • One backend + one browser at a time. Multiple GUIs = confusing state.
  • Correct teardown order: stop → pause → disconnect → quit (CLI or by clicking #disconnect then quitting). Never change/apply a probe map while streaming (invalid on real hardware).
  • Safe kills: backend pkill -x SpikesPeak (exact name — pkill -f bin/SpikesPeak also matches your own shell!). Test browser: kill by the debug-port owner (ss -ltnp | grep 9222 → pid → kill its pgid), or the isolated profile — never blanket-kill brave/chrome (that kills the user's real browser).
  • The backend auto-quits ~2 s after the last WS client disconnects (grace timer), so a one-shot CLI list can kill it if no browser is attached.

4. Environment notes#

  • Linux (this repo's dev box): Python harness needs requests + websocket-client + matplotlib → use conda base (source ~/anaconda3/bin/activate base; the system python lacks pip). pip install -e python gives spikespeak_postprocess. cmake/ninja live under ~/Qt/Tools.
  • Windows (hardware box): same CDP flow with brave.exe/chrome.exe/msedge.exe. CDP screenshots are cross-platform, so python/tools/cdp.py works unchanged; just launch the browser with the same flags. For a whole-screen grab instead, any Windows screenshot util works, but CDP's page-only PNG is cleaner.
  • The backend's own launch (no --no-browser) opens a dedicated browser app-window by default (main.cpp launchDedicatedBrowser); --tab opens a normal tab. For automated tests use --no-browser and drive your own CDP browser.

The two toolbar state buttons are CSS-driven (webinterface/style.css), scoped .toolbar button.<class> so the base .toolbar button {color:#fff} rule does not override them (a CSS-specificity bug — 0,1,1 base beat 0,1,0 — fixed 2026-07-12; it was why play/record stayed white/gray):

Button State Class Look
▶/⏸ Play paused play-ready green ▶ icon rgb(40,167,69) ("press to play")
▶/⏸ Play streaming play-streaming white ⏸ icon inside a green pulsing ring (play-stream-pulse, rgb(40,167,69))
● Record armed record-armed hollow pulsing red-orange ring
● Record recording record-color solid red bg rgb(229,57,53), white ●

Applied by setPlayingUI() / handleDeviceReady() / reflectRecording() / toggleRecord() in main.js. The play rules are scoped :enabled so a disabled (no-source) button stays grey, never green. The green streaming ring is the @keyframes play-stream-pulse animation (the green twin of rec-arm-pulse).

One-shot smoke test (CDP, no human). With a sim source connected on the port-9222 Chrome, these 9 checks ran and all PASS on 2026-07-12 (shots in benchmarks/shots/):

  1. play → streaming (frame count + bytes climb); play button = white ⏸ in a green ring while streaming, green ▶ when paused
  2. traces render — every column's SciChart series have points >0 (guards the blank-traces regression)
  3. Vertical⇄Horizontal orientation toggle, traces persist
  4. per-column DIFFERENT counts: col0.setTracesPerColumn(20) vs col1(60) → 20 vs 60 series, both render 5–8. record: Set Location arms (record-armed) → start = solid red → stop clean → .bin+.json on disk
  5. config inventory: all 16 config/*.yaml resolve their name: identity

Browser lifecycle — closing on backend disconnect (2026-07-14)#

The UI runs in an external browser (the backend opens a Chromium --app= window via main.cpp; --tab opens a normal tab; --no-browser opens nothing). Because it is a separate process, a stale front-end used to linger after the backend shut down. Fixed in webinterface/NetworkClient.js:

  • The socket now has an onclose handler, and the serverQuitting message both call one idempotent handleServerGone().
  • handleServerGone() calls window.close() — which a Chromium --app window is allowed to close — so the UI window closes itself when the backend quits or the connection drops. If the browser refuses the scripted close (a normal tab blocks it), it blanks the page with a clear "server disconnected" notice instead of leaving a frozen UI. It runs once even though both serverQuitting and onclose fire.

Verified: with the UI in a Chromium --app window, a backend quit closed the window itself (the CDP page target on the debug port disappeared; 0 window processes remained). Multiple windows (e.g. one per monitor) each get the event and each close.

Teardown discipline for CDP test browsers#

A CDP harness usually launches Chrome as a normal window (--new-window), which window.close() canNOT close — so the fallback notice shows, and you must still kill the process yourself. Kill only the isolated debug profile you launched (match its unique --user-data-dir tag), never a blanket taskkill /IM chrome.exe (that closes the user's real browser). Launch test browsers with a throwaway --user-data-dir=...<unique tag>... so they are easy to target on teardown.

Backend auto-quit on last client (2026-07-14)#

WebSocketServer shuts the whole backend down ~2 s after the LAST WebSocket client disconnects ("Last client gone; quitting in 2000 ms unless a client reconnects"). This is intentional — closing the browser exits the server. Consequence for testing: a CLI-only script that connects, does work, and disconnects will cause the server to exit shortly after (it looks like a crash but is not). To drive multiple connect/disconnect cycles headlessly, keep a persistent client connected (e.g. an --app browser window on a debug port) for the duration, so the auto-quit never fires. Disconnecting the source (not the WebSocket) does NOT trigger this — the browser stays connected.
