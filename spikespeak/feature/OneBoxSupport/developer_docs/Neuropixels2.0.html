SpikesPeak — Neuropixels 2.0 support (Task 3 runbook)#

What exists, what's stubbed, and the order to finish NP2.0 multishank channel selection + recording. The canonical hardware reference is the vendored OpenEphys plugin at Source-OpenEphys-Neuropixels-PXI/ (read it before writing hardware code).

Background: NP1.0 model + IMRO is in [../SpikesPeak_Status.md]; the live waveform view (which is already wired for 4 shanks) is in [LiveDataView.md].

0. PARITY TARGET — the 2026-07-06 infrastructure NP2.0 must work with (updated 2026-07-06)#

Since this runbook was first written, a large hardware-free stack was built for NP1.0 (Status §13–§14). NP2.0 must reach parity with it — do NOT just make 2.0 stream; make all of this work for 2.0 too:

  • Record-channel selection UI (parts 4+5) — Recording.md §7. The probe viewer has a mode radio (Edit Map | Select Recording Channels). Record mode + the map EDITOR are currently NP1-only (ImroManager.js: gated on probeIdStr === "0"; renderRecordSelection uses channelId + 384*bank and excludes ch 191; renderElectrodeMap's NP2 else-branch is a placeholder = Gap 3 below). Extend both to the 4-shank geometry (electrode = electrodeId, shank-aware; no NP1 modulo-384, no ch191 rule). The committed selection is window.recordChannels = {npx:[...], nidaq:[...]} (read-out channels); main.js routes each list to its recorder by name. The backend recorder is probe-agnostic already.
  • Simulated 2.0 source (its OWN class) — per the corrected per-module design (SimDataLinux.md), do NOT reuse SimDataSource (that's NP1 ap/lfp). Add source.npx.sim2 modelled on SimDataSource.{hpp,cpp} but writing int16 into data.npx.raw (NP2 is ONE raw buffer, not ap/lfp) with a default 2.0 IMRO map (shank/electrodeId). "2.0 + LFP": NP2 has no hardware LFP band — derive it with proc.lfp (LFPProcessor consumes data.npx.raw → data.lfp), exactly how NpxSynthRipples.yaml wires proc.lfp + proc.rippledetector. Add a SimNpx2.yaml config tagged sim_variant: so it joins the "Simulated Data" picker (main.js showSimPicker, backend ConfigManager::getSimVariant).
  • Simulated NI-DAQ — NiDaqSimSource (source.nidaq.sim) + the NI-DAQ record grid already exist and are probe-independent; a SimNpx2NiDaq.yaml (2.0 + NI-DAQ) should Just Work once the 2.0 sim exists.
  • Recorder override — RecordProcessor::setRecording(bool,dir,name, QVariantList channels) overrides the YAML channels: per session; interp.npx.raw records 2.0. Confirm the .bin.json sidecar + spikespeak_postprocess read it.
  • Shutdown / launch — fixed in main.cpp (no quit-hang, no startTimer warning; dedicated browser app-window). Don't regress these.

Net for NP2.0: the three HARDWARE gaps below (§4) PLUS (a) a simulated 2.0 source + derived LFP config, and (b) extending the record-selection MODE + EDITOR (Gap 3) to 4-shank so custom-channel recording works for 2.0 just like 1.0.

1. The probe variants#

ProbeType enum (NpInterface) — set by detectProbe() from the product number (NpInterface.cpp:~989):

Variant probeIdStr product # shanks electrodes
eNpx1 "0" / PRB* / NP1* — 1 960
eNpx2SingleShank "21" / NP200* NP200x 1 1280
eNpx2MultiShank "24" / NP201*,NP202*,*MS* NP201/NP202 4 1280/shank

NP2 geometry (used by the live view): within-shank electrode e → column e&1 (even=Left, odd=Right), row e>>1. 384 read-out channels as on NP1. ⚠️ The electrode↔channel wiring is NOT NP1's modulo-384: within a shank the bank = electrode_local / 384 sets the range, but the channel for an electrode comes from a per-shank block-permutation lookup table. The exact tables, geometry, np_* call sequence, and IMRO format are documented in OpenEphys-NP2-Reference.md (distilled from the vendored plugin) — read it before writing the default map / apply / editor.

2. IMRO entry formats (all parsed/serialized already)#

From parseImroContent (NpInterface.cpp:~597-667) and serializeImro (~1291-1301):

NP1            (channelId bank refId apGain lfGain apFilter)     # 6 fields
NP2 multishank (channelId shank bank refId electrodeId)         # 5 fields   <-- Task 3 focus
NP2 singleshank(channelId bank refId electrodeId)               # 4 fields ; shank implicitly 0, bank=bitmask

NP2 has no per-channel gain or AP-filter fields (fixed-gain probe) — that's the big API difference from NP1.

Refinements (2026-07-07) — see SpikesPeak_Status.md §17–§18#

  • Mapping VERIFIED vs the official manual (Neuropixels_2-0_User_Manual_V1-0-6/): Np2::electrodeToChannel matches all 5,120 rows of the Electrode-Channel .xlsx (Figs 35+37). The electrode number is a physical site (row=e>>1 = depth, col=e&1, El0=tip); the channel number is the amplifier index with no physical meaning; the .xlsx channel→electrode is deliberately SCRAMBLED (the block permutation).

  • Probe-type mismatch dialog: NeuropixelsSource::initDataSource infers the profile's expected probe from its output data and emits sigGuiStatus(...,"probe-mismatch") → main.js showProbeMismatch modal.
  • Per-shank rectangles + tips in the NP2 editor (ImroManager.js setShankVisuals / np2Shafts/np2Tips).
  • Record-mode selection is restricted to the applied (streamable) electrodes; edit-mode clicks always yield a valid map (each of 384 channels reads one electrode). GUI test harness: python/tools/gui_scenarios.py.

Real-2.0-hardware streaming robustness (2026-07-15/16 — built + VERIFIED on a live NP2 multishank)#

First real 2.0 multishank plugged into the Windows rig. Streaming worked on a fresh connect but pause/play and pick-channels (Bank apply) froze the live view (IMEC blue LED = FPGA streaming but host not reading, or display frozen while the FIFO stayed healthy). Four independent bugs, all now fixed + verified live (CDP-driven visible browser, 6/6 interleaved pause/play + Bank 0/1/2/3 applies advancing, 0 FIFO stalls): 1. FPGA-read stall on (re)play — NeuropixelsSource::startAcq fired np_setSWTrigger immediately after mWorkerThread->start(), i.e. BEFORE the worker's read loop existed → the FPGA streamed into a FIFO nobody drained (blue LED). Now the trigger is gated on the worker's sigDswStartedAcquiring (QueuedConnection, fires after mTimer->start()), so the reader is always up first. A throttled FIFO diagnostic ([Npx2MSProbe] FIFO: read N | available M | headroom H … STALL) makes any recurrence visible in the log. 2. Ring desync after a worker recreate — applyMapToHardware() does stopAcq()→write→startAcq(), which destroys + recreates the source worker. Npx2MSProbe started mCurrWriteInd = 0, so the new worker wrote at ring position 0 while the persistent consumers (display/ripple/LFP) kept reading at the old high index → stale/garbage data. Npx1Probe already seeds its write index from getTotalSamplesAdded(); NP2 was missing it. Added the same seed to the Npx2MSProbe ctor (no-op on first worker). 3. Display frozen after a reconfigure — np_setSWTrigger re-firing on a map apply RESETS the probe packet Timestamp toward 0, but DisplayProcessor binned by that hardware timestamp with a latched gotFirstTimestamp, so the new low timestamps never exceeded the old (high) timebinEndTimestamp → advanceBucket() never ran, no frames emitted (samples consumed but never shown). slDpGenerateDisplayData now detects the >1-bin backwards jump and re-baselines the timebin, so display resumes automatically with no manual pause/play. (Pause/play had hidden this by rebuilding the processor state — and only recovered once fix #2 also landed.) Shared with NP1. 4. NP2 raw traces drift off-screen — the raw wideband carries a large, slowly-drifting electrode DC offset; the probe display path drew samples straight at yOffset+sample (0-centred assumption, true only for the hardware-high-passed AP band), so the trace drifted below its row within minutes → blank view. NetworkClient.js now AC-couples streamId === 'raw' (slow min/max-midpoint baseline, same tracker as the NI-DAQ path, clamped to the row band). Frontend-only. NP1 ap/lfp untouched. - Files: NpInterface.cpp (#1 startAcq gate + FIFO log; #2 Npx2MSProbe ctor seed), DisplayProcessor.cpp (#3 timebin re-baseline), webinterface/NetworkClient.js (#4). Rebuild the build-Desktop_…-Release tree (_rebuild.bat = vcvars64 + cmake --build); frontend is copy-to-served-tree + reload. Verified by CDP screenshot at the time (screenshots are transient — see the screenshot policy in README.md).
