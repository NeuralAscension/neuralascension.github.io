Closed-loop latency — profiling, where the time goes, and the ASAP delivery flag#

The definition that matters#

Closed-loop latency = the time from the threshold being crossed (on the filtered probe signal) to the stimulus pulse being observed on the NI-DAQ.

That is the number quoted in RecordingTests/NP{1,2}_RIPPLE_TESTS.md, and it can only be measured offline, by ripple_tools/analyze_recording.py, because the ai4 pulse edge exists solely in the NI-DAQ recording and needs the sync fit to share a clock with the probe. Everything else on this page is a decomposition of that interval — useful for finding where the milliseconds live, never a replacement.

On a OneBox rig, read "NI-DAQ" as "the OneBox's own ADC". The definition is unchanged — threshold crossing → observed stimulus pulse — but the pulse is captured on an analog input of the same device as the probe, so both instants come from one 100 kHz hardware counter and no sync fit is involved. That removes the step where a periodic signal can be mis-paired (§24). Pass --stim-band adc --stim-channel <n> to the analyser; without it, it looks for a nidaq band, finds none, and silently reports no closed-loop latency. Measured results and the two silent traps this path exposes: ../RecordingTests/CLOSED_LOOP_LATENCY.md.

Measured (real hardware, pulse-anchored). Full results, figures and the delivery-mode comparison: ../RecordingTests/CLOSED_LOOP_LATENCY.md.

The complete matrix, ~1000 delivered stimuli per cell (2026-07-21). Both probes, both delivery modes:

configuration NP1.0 default NP1.0 ASAP NP2.0 default NP2.0 ASAP
1 ch 1.483 ms 0.977 ms 1.351 ms † 0.600 ms
2 ch, quorum 2 1.489 ms 0.942 ms 1.186 ms 0.608 ms
4 ch, quorum 3-of-4 1.484 ms 0.963 ms 1.124 ms 0.546 ms
ASAP saving — −506…−547 µs — −578…−751 µs

All cells n≈1000, 0 unmatched. Latency is flat across quorum size on both probes — within 6 µs (NP1 default) / 35 µs (NP1 ASAP) / 62 µs (NP2 ASAP): quorum decides which crossing fires, not the delivery delay. ASAP is sub-millisecond at every quorum on both probes. († np2_1ch_baseline has mild sync-clock curvature; burst-anchored cross-check 1.23 ms — read as ~1.2–1.35 ms. Does not affect any ASAP cell.)

NP2.0 is faster than NP1.0 in both modes (~0.3 ms default, ~0.37 ms ASAP). The gap is the probe→detector path, not the shared network: NP2 derives data.lfp in software from the fresh 30 kHz raw stream; NP1 waits on the hardware LFP band. See the NP2 upstream-latency note below.

Numbers published before 2026-07-21 were wrong — three offline clock/sync bugs (a ~10 ppm clock-scale ramp and two sync off-by-ones) inflated them. All are fixed and every recording re-analysed. The canonical write-up of the sync fit and all three bugs is in RippleClosedLoopAnalysis.md — read it before trusting any recorded latency. This doc does not re-derive them.

The full result tables, figures, and detection-integrity/sync numbers live in ../RecordingTests/CLOSED_LOOP_LATENCY.md (a tabbed NP1/NP2 page). This doc owns the method: the definition, the live per-stage instrumentation, the ASAP flag, and the mechanism of where the milliseconds go.

Live per-stage instrumentation#

The backend emits a rippleLatency WS event after every confirmed stimulus (i.e. once the stim server ACKs fired), and writes a latency_us summary into each recording's _ripple.json. Stages, all in microseconds on a steady clock:

field what it measures
sample_proc_us this sample entering the detector → quorum satisfied (ripple/envelope FIRs + state machine)
detector_backlog_us samples already queued behind the triggering one, expressed as time — how stale the data was when we first saw it
detect_to_send_us quorum satisfied → fire datagram leaves this host (backend software path)
send_to_ack_us network out + stimulator execution + network back
device_us the stim server's own packet-read → first-edge time, or -1 if the firmware doesn't report it
detect_to_ack_us the full confirmed loop this host can observe without a DAQ

Collect and summarise with:

python ripple_tools/latency_breakdown.py --n 1000 --fig lat.png --out lat.json

send_to_ack_us is not comparable to the NI-DAQ figure. The ACK is sent after the pulse train completes; the ai4 edge marks the start of the first pulse. With freq 1 Hz / train 500 ms the server clamps to a single pulse and ACKs immediately after it, so the two are within ~1 ms — but they are different quantities and the ACK figure also includes the return trip.

Where the time actually goes (n=100, live Pi, simulation)#

stage median p95 max
sample → quorum (filters + FSM) 2 µs 6 7
detector backlog 400 µs 800 1600
detect → datagram out 4 µs 12 13
datagram → fired ACK (net + Pi) 1345 µs 2062 2110
TOTAL detect → ACK 1349 µs 2065 2114

Two conclusions:

  1. Our compute is free. Filters, state machine and dispatch total ~6 µs. There is nothing worth optimising in the backend's processing path.
  2. The backlog is quantised to exact multiples of 400 µs (0 / 400 / 800 / 1600) — and 400 µs is precisely one NP1 LFP sample period (2.5 kHz). That is the signature of block delivery, not jitter. This quantisation is also why the stage split must be summarised with means, not medians — see the real-hardware section below.

Raw data: RecordingTests/latency/latency_stages_pi.{json,png} (simulation + live Pi).

Why the backlog exists — and the correction to an earlier claim#

Sources commit a block of samples at once:

mLfpData.commitWrite(mProducerId, n);          // SimDataSource  -- n samples per tick
mLfpData.commitWrite(mProducerId, actualSuperframes);   // NpInterface (real NP1)

and the consumer's waitForAvailable() drains the whole semaphore, so every sample in a block becomes visible at the same instant. The oldest sample in a block of N is therefore already (N-1) × sample_period old the first time any consumer can see it. On the 2.5 kHz NP1 LFP band that is 400 µs per extra sample in the block.

Correction. An earlier suggestion in this project — "have the detector process the newest available sample first" — was wrong, and would have made things worse. The detector already processes the oldest sample first and reaches it within microseconds of the block arriving; it cannot skip samples because the FIRs are stateful and need every one. The staleness is created upstream, by the delivery granularity, and cannot be recovered downstream. The lever is the producer, not the consumer.

The ASAP / low-latency flag#

low_latency: true on a source node makes it deliver in the smallest blocks the clock allows, trading CPU for freshness. It is per-source; the ripple / closed-loop configs now ship with it on by default and plain-streaming configs leave it off, so only loop-closing configs pay for it:

sources:
  - name: "source.npx.simdata"
    inject_ripples: true
    low_latency: true      # ASAP delivery -- smaller sample blocks, more CPU

Implementation: SimulatedDataSource::initDataSource parses the key and forwards it to SimNpx1Worker::setLowLatency, which drops the production tick from 1 ms to 0 (fire on every event-loop pass). The NP2 sim source (SimulatedData2Source / SimNpx2Worker) honours it identically as of 2026-07-24 — it previously hardcoded the 1 ms tick and silently ignored low_latency, so ASAP had no effect in NP2 simulation. The code default stays false (1 ms), so plain-streaming configs are unchanged — but the everyday ripple configs now set low_latency: true, so ripple detection defaults to ASAP on both probes (SimNpx{1,2}Ripples, SimNpx{1,2}RippleModule, SimNpx{1,2}NiDaqRipples, SimNpx2RealNiDaqRipples; real NP2 hardware already delivered ASAP via Npx2MSProbe::setLowLatency).

Module developer note — ASAP is opt-in, and only the ripple detector opts in by default. low_latency is a per-source flag whose code default is false. By project convention, the only module that enables it by default is the ripple detector (its configs set low_latency: true because it closes a sub-millisecond loop). Every other module — live display, recording, LFP derivation, audio, and any new processor or source you add — runs at the normal 1 ms poll and must NOT assume ASAP. If a new module genuinely needs sub-block-latency delivery, enable it explicitly on that config's source and measure the cost first (ASAP busy-spins ≈ one core, ~7× baseline CPU — see "CPU cost of ASAP" above). Do not flip the code default to make ASAP global: plain streaming/recording would pay the CPU for a latency win nothing but the closed loop uses.

Verified on real NP2.0 hardware (2026-07-24): [Npx2MSProbe] acquisition poll interval 0 ms (low_latency = true) with the Npx2PxiNiDaqAsap config; NP2 raw 30 kHz × 384 ch and NI-DAQ 40 kHz (AI + DI) streamed at rate.

Benchmark configs SimNpx1LatencyBaseline / SimNpx1LatencyAsap differ only in this flag (plus a 0.5 s ripple period so 1000 samples take ~9 min instead of ~33).

Measured effect (A/B, n=1000 each, live Pi, simulation)#

SimNpx1LatencyBaseline vs SimNpx1LatencyAsap — identical except the flag. Medians, microseconds:

stage baseline ASAP change
detector backlog 400 (max 2000) 0 (max 400) eliminated
sample -> quorum 2 5 +3
detect -> datagram out 4 12 +8
datagram -> fired ACK 1312 830 -482
TOTAL detect -> ACK 1316 840 -476 (-36%)
spread (sd) 431 129 3.3x tighter

Raw data: RecordingTests/latency/latency_{baseline,asap}_1000.{json,png}.

These are simulation artefacts, kept as the evidence behind this table. The authoritative hardware numbers are in ../RecordingTests/CLOSED_LOOP_LATENCY.md.

Read the total with care. The datagram -> ACK gain is NOT all real stimulus speed-up. The ACK is timestamped in StimulatorClient::onReadyRead, which runs during the detector's processEvents() BETWEEN batches -- so with 1 ms batching the backend can sit on an already-arrived ACK for up to a batch period before noticing it. ASAP mode services events far more often, so part of that -482 us is noticing the ACK sooner, not the pulse leaving sooner. The ai4 edge timing is unaffected by when we notice the ACK.

The defensible claim for the closed-loop definition (threshold crossing -> ai4) is therefore the backlog removed, and it should appear directly in a NI-DAQ-captured run.

That hardware confirmation is now done (2026-07-21, see the real-NP1.0 table below): the backlog goes to exactly 0 and the NI-DAQ-anchored median drops 506-547 us at every quorum level. The simulation under-predicted the saving because its backlog was smaller than the real probe's.

Cost: per-sample processing 2 -> 5 us and dispatch 4 -> 12 us (CPU contention with the busier production timer). ~17 us total against a ~840 us loop -- negligible, but real, which is why the flag is opt-in.

CPU cost of ASAP — the busy-spin (measured 2026-07-22)#

The ~17 us above is the added per-detection compute. The other, larger cost is process-level CPU. At interval 0 the acquisition QTimer re-fires on every event-loop pass, and because production is wall-clock-gated (SimDataSource.cpp:125 -- if (due <= 0) return;) the overwhelming majority of those firings do nothing but re-read the clock and return. That is a busy-spin that saturates roughly one core, occasionally emitting a single superframe. It is exactly the "trade CPU for freshness" the flag names.

Measured on the NP1 sim A/B (SimNpx1LatencyBaseline vs SimNpx1LatencyAsap -- byte-identical but the flag; played with the detector dormant (auto_start:false), so this is the pure source-poll cost), i7-11700K (8C / 16T), from SpikesPeak.exe TotalProcessorTime over a 40 s streaming window:

mode timer CPU (% of one core) % of the 16-thread machine
baseline 1 ms 13.4 % 0.84 %
ASAP interval 0 98 % (≈ one core pegged) 6.12 %

≈7x the CPU, +0.85 of a logical core; idle (connected, not streaming) is ~0 %. On the real probe the interval 0 path also calls np_readElectrodeData on every pass, so on-probe ASAP costs at least this -- the sim figure is a lower bound. This is the concrete reason the flag is opt-in and per-source: ~one core to shave the ~0.5 ms backlog off the loop is cheap for a closed-loop rig, wasteful for plain streaming. (Confirm the flag took via the production tick interval 0 ms (low_latency = true) log line before trusting an A/B.)

On real hardware — implemented 2026-07-21#

Npx1Probe polls np_readElectrodeData on a 1 ms timer and requests up to 64 superframes (NpInterface.cpp). At the 2.5 kHz LFP rate that accumulates 1–2 samples per commitWrite, measured as a 214–631 µs mean backlog on this rig — 15–43 % of the total closed-loop latency.

low_latency: true on the probe source now drives Npx1Probe::setLowLatency() (and, since 2026-07-21, Npx2MSProbe::setLowLatency() — same one-line timer change, setInterval(mLowLatency ? 0 : 1), wired in NeuropixelsSource::startAcq), which polls on every event-loop pass (interval 0) instead of every 1 ms. The request size is unchanged so the probe can still catch up if it ever falls behind — only the poll cadence changes. Configs Npx1PxiNiDaqAsap and Npx2PxiNiDaqAsap are byte-identical to their default configs apart from that key. The backend logs acquisition poll interval 0 ms (low_latency = true) at start — check it to confirm the flag actually took before trusting an A/B.

Staleness is still bounded below by the Neuropixels API's own packetisation: below that the data has not arrived yet and no software change can help.

−506 / −547 / −521 us (−34 to −37 %) median, IQR 4–5x tighter. ASAP zeroes the batching counter exactly — 0 us in every one of ~1000 events in all three ASAP runs, not merely a lower mean.

The detector's own compute is 8–15 us, two orders of magnitude below the loop total: there is nothing to gain by optimising the signal processing.

Use means, not medians, for the stage split. The backlog counter is quantised to one input sample (400 us at 2.5 kHz), so its median snaps to 0 / 400 / 800 us — two runs whose totals matched to 5 us reported medians of 400 us and 0 us. Medians are also not additive, so subtracting them from a median total pushed the discretisation error into the residual (1082 vs 1476 us). Both plotting scripts now use means, which are additive. The network + stimulator segment is a residual by subtraction, not a measurement.

Open item. The batching mean falls monotonically with channel count (631 / 381 / 214 us for 1 / 2 / 4 ch) while the NI-DAQ-anchored total stays flat at 1.483–1.489 ms, so the residual rises to compensate. The totals are trustworthy; this channel-count dependence of the attribution is unexplained. Treat the stage split as indicative, not exact.

−578 to −751 us (−49 to −56 %) median. NP2 goes sub-millisecond at every quorum, and faster than NP1 in both modes (~0.3 ms default, ~0.37 ms ASAP). († np2_1ch_baseline has mild sync-clock curvature; burst-anchored cross-check 1.23 ms — read it as ~1.2–1.35 ms. No ASAP cell is affected.)

The detector-side batching counter UNDER-reports the ASAP benefit on NP2 — a key difference from NP1. On NP1 the detector reads data.npx.lfp directly, so the probe-poll latency is the detector-input backlog: the counter went 631→0 us and matched the ~506 us total saving. On NP2 the detector runs off data.lfp derived by proc.lfp from the raw poll, so the 1 ms raw-poll latency sits upstream of the detector and its input counter cannot see it. The counter shows only ~230→60 us, but the NI-DAQ-anchored total drops ~578–751 us and the net + stim residual — which on NP1 was a near-fixed ~0.9 ms network floor — collapses ~0.4 ms (1030→515, 906→557, 950→527 us). That collapse is the removed upstream raw-poll latency. The lesson: on any probe whose detector input is derived through an intermediate processor, instrument the stage counter at the source poll, not just the detector input, or the split will mis-attribute the gain. The NI-DAQ total is always authoritative.

Figures#

ripple_tools/plot_latency_figure.py renders the five-panel latency figure (signal chain, histogram, CDF, stage decomposition, per-trial stability); plot_latency_compare.py renders the A/B. Both take --theme light|dark.

Palettes are validated, not eyeballed (scripts/validate_palette.js in the dataviz skill):

  • light (surface #fcfcfb): blue #2a78d6 / violet #4a3aa7 / aqua #1baf7a / orange #eb6834 — all checks pass; aqua's contrast is < 3:1 so it carries a direct label.
  • dark (surface #1a1a19): the light violet step collides with blue on a dark surface (protan ΔE 1.9, normal ΔE 9.8 — hard fail), so dark uses a validated 3-hue set (blue / aqua / orange) and encodes the ripple band by lightness + dash rather than a fourth hue. Identity is never colour-alone.

Gotchas that cost real time#

  • The backend auto-quits ~2 s after the last WebSocket client disconnects. Launch the backend and the collector as one uninterrupted sequence, or the second run finds a dead server and blocks in Rig() with no output at all.
  • Never run two collectors at once. The stale one's timeout calls disconnect_source and stops streaming out from under the live run.
  • rig.py's self.lock is a plain non-reentrant threading.Lock. The event dispatcher already holds it; re-acquiring it inside a handler deadlocks the reader thread and silently stops all capture — which looks exactly like "no ripples detected".
  • Check the stim server's own journal (journalctl -u pulsegenerator) before believing a "nothing is happening" reading on the client side. It is the independent ground truth for whether fires and ACKs are actually flowing.
