Analyzing pegboard data

For getting numbers out of the recordings. Written for whoever is running the study — you need to be comfortable running a Python script, but nothing here assumes an engineering background, and every concept is explained the first time it appears.

If you are running participants, that is OPERATOR_GUIDE.md. If you are changing the equipment, ENGINEERING_GUIDE.md.

What a recording contains

One session is one folder, named for the participant, the date and the session number:

experiments/ThumperBunny/20260810/005/

Inside are five files. You will mostly use the analysis package rather than opening these, but it helps to know what is there:

filewhat it holds
session.jsonwho, when, which hand, which condition, plus a summary
samples.csvthe weight on the board, about eleven times a second
events.csvevery peg placement, every stimulation, and equipment checks
clock_sync.csva record of how the two clocks were aligned (see below)
raw_udp.logeverything the pegboard said, verbatim, for troubleshooting

They are ordinary CSV files, so Excel, R and MATLAB open them directly. The Python package is just a convenient reader that knows what the columns mean.

Getting the data onto your computer

See "Copying the data onto another computer" in the operator guide for the click-by-click version. In short:

python3 tools/fetch_sessions.py

It copies only what is new, checks every file arrived intact, and never changes anything on the Pi.

Setting up, once

pip install -e .

That installs the pegboard package. It needs only numpy, so it will work in almost any Python environment you already have.

Check it worked:

import pegboard
print(pegboard.__version__)

Your first five minutes

import pegboard

s = pegboard.load_session("experiments/ThumperBunny/20260810/005")

print(s.label)              # ThumperBunny/20260810/005
print(s.hand)               # Right
print(s.session_type)       # taVNS
print(s.n_pegs)             # 25
print(round(s.duration_s))  # how long the recording ran

The two numbers you probably came for:

print(s.ipis_ms())          # gap between each peg and the next, milliseconds
print(s.stim_onsets_ms())   # when each stimulation actually started

An inter-peg interval (IPI) is the time between one peg going in and the next. It is the main performance measure: faster, steadier intervals mean better manual dexterity.

Summary numbers

Rather than computing them yourself:

from pegboard import metrics

print(metrics.mean_ipi(s))        # average interval, ms
print(metrics.median_ipi(s))      # middle interval — ignores one fumbled peg
print(metrics.sd_ipi(s))          # how variable the intervals were
print(metrics.cv_ipi(s))          # variability relative to speed
print(metrics.pegs_per_min(s))    # throughput
print(metrics.task_duration_s(s)) # how long the task itself took

Use median_ipi when a participant fumbles one peg. One long interval drags the mean up and makes a good run look bad; the median ignores it.

task_duration_s is not the length of the recording. The operator starts recording before the task and stops after, so a 60-second task can sit inside a 200-second recording. duration_s is the recording; task_duration_s is the task. For performance you almost always want the latter.

Several sessions at once

import pegboard

ds = pegboard.Dataset("experiments")

print(ds.subjects())                       # everyone with recordings
print(ds.dates("Thumper Bunny"))           # all their session dates
print(ds.trend("Thumper Bunny", "mean_ipi"))   # that metric, session by session

Names are matched forgivingly, so "Thumper Bunny", "thumperbunny" and "ThumperBunny" all find the same participant.

Loop over everything:

import numpy as np
from pegboard import metrics

for s in ds.sessions():
    ipi = metrics.mean_ipi(s)
    # A session that was started and abandoned has no pegs, so its metrics are
    # "not a number". That is normal in real data, and round() raises on it —
    # so check before formatting.
    print(s.label, s.hand, s.session_type,
          "n/a" if np.isnan(ipi) else round(ipi))

You will meet nan a lot. It means "not a number" and is how missing results are represented. Guard with np.isnan(x) before rounding, printing or comparing — nan is not equal to anything, including itself.

Comparing conditions

import pegboard
from pegboard import metrics

ds = pegboard.Dataset("experiments")
groups = {}
for s in ds.sessions():
    if s.n_pegs == 0:
        continue                       # an aborted session has nothing to compare
    groups.setdefault(s.session_type, []).append(metrics.mean_ipi(s))

for condition, values in sorted(groups.items()):
    mean = sum(values) / len(values)
    print(f"{condition:8s} n={len(values):2d}  mean IPI {mean:6.0f} ms")

Swap s.session_type for s.hand to compare hands instead.

Checking a session is sound before you analyze it

Worth doing once per session. It costs seconds and it catches the sessions you should not draw conclusions from.

Did every peg get stimulated?

The pegboard counts placements; the Raspberry Pi separately watches the stimulation wire. They come from different pieces of hardware, so if they agree you have real evidence the participant got what the protocol says.

for s in pegboard.Dataset("experiments").sessions():
    stims = len(s.stim_onsets_ms())
    verdict = "ok" if stims == s.n_pegs else "MISMATCH — investigate"
    print(f"{s.label}: {s.n_pegs} pegs, {stims} stimulations  {verdict}")

Was the equipment healthy?

Every self-test result is written into the recording, so a session carries its own evidence:

problems = [d for d in s.events.of("bist").detail if "status=PASS" not in d]
print("all checks passed" if not problems else problems)

An empty list here means every check passed while that session was being recorded. (Sessions record self-test results only if a check ran while recording was active, so an empty result can also simply mean none ran.)

Were any measurements lost?

print("clock aligned:", s.clock_converged)

If this is False, the two clocks were never matched well and the sample timings are less trustworthy. Stimulation timings are unaffected — those are recorded a different way (see below).

About time, and why there is more than one clock

This is the one genuinely confusing part of the data, and it is worth ten minutes.

There are two separate computers in the rig, each with its own clock:

  • the pegboard (the small ESP32 board), which reads the scale
  • the Raspberry Pi, which records everything

Neither clock knows about the other, and they run at very slightly different speeds. So the Pi continuously works out the relationship between them and uses it to put every measurement onto one shared timeline.

That shared timeline is the column called t_ms — milliseconds since the recording started. Use t_ms for everything. It means the same thing for a weight reading and for a stimulation, which is the entire reason it exists.

s.t_ms          # the shared timeline
s.weight_g      # weight on the board, grams
s.gpio26        # 1 while stimulation is being delivered, else 0

Why stimulation times are the most trustworthy

When the pegboard fires the stimulator it also puts a voltage on a wire to the Pi. The Pi's operating system timestamps that voltage change the instant it happens, directly on the shared timeline — no estimation involved.

So stim_onsets_ms() is exact, and stays exact even if the clock alignment is poor. Weight readings involve an estimate; stimulation times do not.

If you want the detail

model = s.clock_model()
print(model["converged"])    # was the alignment good enough to trust?
print(model["skew_ppm"])     # how differently the two clocks run, in parts per million
print(model["offset_ms"])    # the constant difference between them
print(model["fitted_on"])    # which pegboard timestamp the alignment used

You can also put a raw pegboard time onto the shared timeline yourself:

print(s.mcu_to_pi_ms(4821.0))

The two pegboard timestamps

Recordings made from 10 August 2026 onwards store two times from the pegboard for each weight reading:

  • mcu_time_ms — when it started taking the reading
  • mcu_read_ms — when it finished, about 93 ms later

The gap is real: a reading is the average of eight measurements, and taking eight measurements takes time.

if s.has_read_timestamps:
    print("acquisition window:", s.acquisition_lag_ms().mean().round(1), "ms")
else:
    print("older recording — only the start time was stored")

Older recordings have only the first, which meant weight readings were filed about 93 ms earlier than they actually happened. Both are kept now, so old and new recordings stay directly comparable. If you are comparing timings across recordings made before and after that date, this is the one difference to be aware of.

Making figures

import matplotlib.pyplot as plt
import pegboard

s = pegboard.load_session("experiments/ThumperBunny/20260810/005")

fig, ax = plt.subplots(figsize=(11, 4))
ax.plot(s.t_ms / 1000, s.weight_g, lw=1)

# Shade each stimulation.
for start, end in zip(s.stim_onsets_ms(), s.stim_offsets_ms()):
    ax.axvspan(start / 1000, end / 1000, color="red", alpha=0.15)

ax.set_xlabel("time (s)")
ax.set_ylabel("weight (g)")
ax.set_ylim(bottom=0)          # weight cannot be negative
fig.tight_layout()
fig.savefig("session.png", dpi=150)

Each step up in the trace is one peg. The red bands are stimulations.

A summary table of every session

import csv
import pegboard
from pegboard import metrics

rows = []
for s in pegboard.Dataset("experiments").sessions():
    rows.append({
        "subject": s.subject, "date": s.date, "session": s.session,
        "hand": s.hand, "condition": s.session_type,
        "pegs": s.n_pegs,
        "mean_ipi_ms": round(metrics.mean_ipi(s), 1),
        "median_ipi_ms": round(metrics.median_ipi(s), 1),
        "task_s": round(metrics.task_duration_s(s), 1),
        "stimulations": len(s.stim_onsets_ms()),
    })

with open("summary.csv", "w", newline="") as fh:
    writer = csv.DictWriter(fh, fieldnames=rows[0].keys())
    writer.writeheader()
    writer.writerows(rows)
print(f"wrote {len(rows)} sessions to summary.csv")

That is usually the most useful thing to produce first: one row per session, ready for statistics.

Writing your own measure

Any function that takes a session and returns a number works:

import numpy as np
import pegboard

def slowest_third_mean_ipi(session):
    """Average of the slowest third of intervals — a rough fatigue measure."""
    ipis = np.sort(session.ipis_ms())
    if len(ipis) < 3:
        return float("nan")
    return float(ipis[-len(ipis) // 3:].mean())

for s in pegboard.Dataset("experiments").sessions():
    value = slowest_third_mean_ipi(s)
    # An aborted session has no pegs, so the result is "not a number".
    print(s.label, "n/a" if np.isnan(value) else round(value))

Always handle the not-a-number case: an aborted or empty session is normal in real data, and round() raises an error on it.

Older recordings

Recordings from before this format existed are read deliberately, never by guessing:

from pegboard import legacy
rows = legacy.load_legacy_txt("experiments/20250523/ThumperBunny/001/001.txt")

The reader accepts the current format and the one before it. Anything older raises an error rather than being silently misinterpreted — the columns did not mean the same thing, and quietly reading them as if they did would produce plausible, wrong numbers.

If something looks wrong

what you seewhat it usually means
UnsupportedSchemaErrorthe recording predates this reader; use pegboard.legacy
Fewer stimulations than pegscheck the session's self-test results, and the trigger wire
clock_converged is Falsetoo little data for a good alignment; stimulation times are still exact
Metrics come back nanthe session has no pegs — usually an aborted run
Times look ~90 ms off between old and new recordingsthe two pegboard timestamps, above

For anything that looks like an equipment fault rather than an analysis question, DEBUGGING.md is the place, and the closed-loop latency report documents the timing of the whole chain from a peg landing to stimulation being delivered.
