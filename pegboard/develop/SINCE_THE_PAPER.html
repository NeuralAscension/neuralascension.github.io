Updates since the paper

This repository is a later build of the platform described in:

S. Dutta, A. Ellett, C. Welle, "Flexible, Real-Time Sensorized Grooved Pegboard Test Platform for Closed-Loop Neuromodulation", IEEE NER 2025, San Diego, pp. 119–124, doi 10.1109/NER61569.2025.11589061.

If you arrived from the paper or its DOI, this page tells you exactly where the system you read about and the system in this repository differ.

Two things before the differences. The validation result stands as published — n = 7 healthy adults, 98.9% true positive, 0.9% false positive. And the detection algorithm is structurally unchanged: sample the load cell, compare the change against a weight band, wait for the reading to settle, take a confirming read, trigger. Everything below is a change of constant, of transport, or of surrounding tooling. The method that produced those validation numbers is the method running now.

Why the latency number changed

The paper reports 212.5 ms predicted and 213–215 ms measured. This repository reports 229 ms. That is not a slowdown: it is the same chain, measured from a more honest origin.

The paper's 212.5 ms is the acquisition pass start to the stimulation trigger — sampling, settle, confirming read. Measured directly on the board, those same stages now take 211.07 ms median over 50 placements.

The confirming read is the row worth reading twice. It costs about half what the paper's arithmetic implies, because the HX711 keeps converting during delay(100) — the first sample is already waiting when the read begins, so the settle and the confirming read overlap.

What is new is the origin. The 229 ms figure is measured from the peg landing, so it carries the sampling lag the paper's chain never counted: the peg lands between two ADC reads, and the board does not learn about it until the next one. On the current build the breakdown is sampling lag 94 ms, detect plus settle 135 ms (IQR 133–137 ms), verify to TRIG_HIGH 0.006 ms, total 229 ms — all from the same 50 placements. That last term is ~0 by construction: once the confirming read agrees, the trigger goes high with nothing in between. The 229 ms is acquisition and settling.

The eight-sample average is not a candidate for trimming. Averaging eight readings instead of two is a tuned experimental result — months of testing across MS patients and healthy controls established it as necessary for a stable reading. It costs 69 ms and it is documented here so that nobody rediscovers it by removing it. The 100 ms settle is as tuned as the averaging, and shortening it would return less than its nominal value anyway, because the confirming read overlaps it. If latency has to come down, the acquisition cadence — the 93.9 ms loop period that sets the 94 ms sampling lag — is the only honest lever.

What exists now that the paper does not describe

None of the following was part of the build the paper reports. It is all new since.

22 built-in self tests. Twelve run on the firmware, ten on the Pi — sample rate, load-cell noise and drift, trigger line state, message continuity, disk, clock. They sit behind a single greenlight in the UI, so the pre-session check is one tap. The two trigger tests read not run by default, because running them fires the stimulator.

Schema v4 recordings with a fitted clock. Sessions are written to experiments/<subject>/<date>/<session>/ as session.json, samples.csv, events.csv, clock_sync.csv and the raw board log. The board's millis() is fitted onto the Pi's CLOCK_MONOTONIC by lower-envelope linear fit, so weight samples and GPIO26 trigger edges share one timebase and stimulation timing is directly comparable to load timing.

The mcu_read_ms fix. Schema v4 added a second board timestamp: when a reading finished, not only when it started. The two differ by about 93 ms, because a reading is the average of eight measurements. Before this, weight samples were stamped roughly 93 ms early, and the clock fit was made against the wrong end of the acquisition window. Both timestamps are now stored, so recordings made before and after the fix stay comparable.

An analysis package. src/pegboard, installed with pip install -e ., reads sessions, computes inter-peg intervals and summary metrics, and walks a whole dataset. SUPPORTED_SCHEMAS = (3, 4); anything older raises rather than being silently misread.

A closed-loop latency report. analysis/latency_report.py produces the timing write-up for the whole chain from a peg landing to stimulation being delivered. That is where the 229 ms figure and its stage breakdown come from, and it is published on the docs site under Reports → Closed-loop latency. The stage breakdown needs firmware profiling, so it exists only for sessions recorded on 1.2.0 or later.

A cross-platform transfer tool. tools/fetch_sessions.py copies recordings off the Pi, checks every file arrived intact, copies only what is new, and never modifies anything on the Pi.

A Pi install script. raspberry-pi5/install-pi.sh builds a card from a clean clone and is idempotent, so it is also how an update is applied. --check reports what it would change without changing anything.

The paper used an NI-DAQ both in early prototyping and in the validation study, where it recorded the 3.3 V trigger pulses and supplied the primary event timings, cross-verified against the patterns in the GUI-logged weight data. It is not part of the current rig: that role is now filled by the Pi's own kernel-timestamped GPIO26 edges together with firmware profiling.

What to cite, and where to look for current behavior
